> **面向读者**：产品经理、运营人员、开发者 | **难度**：⭐⭐⭐ 高级 | **阅读时间**：约 12 分钟

---

## 一句话说清楚

缓存是 OpenSquilla 省钱的**核心机制之一**。每次调用 AI 模型时，system prompt（系统提示词）和 tools（工具定义）通常占了输入内容的 70% 以上。如果能告诉 AI 厂商"这部分内容不变，你别重复计费"，就能把当次请求的费用降到原来的 1/10。

---

## 生活化比喻

> 缓存像你去餐厅点菜——菜单封面（system prompt + tools）永远不变。服务员说："封面不用每次重新打印，我记着呢。"你只需要付新点的菜（对话内容）的钱，封面免费。但如果菜单封面换了（换模型了），或者你换了座位（参数变了），缓存就失效了，需要重新打印封面。

## 一、缓存到底是谁在做？

```
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│   OpenSquilla 做的事（编排层）           Provider 做的事（执行层） │
│   ─────────────────────────             ────────────────────── │
│                                                                 │
│   ① 给 system prompt 加                      真正存储缓存        │
│     cache_control 标记 ──────────▶          ──────────▶         │
│     "这部分可以缓存"                        把 prompt 存起来      │
│                                                                 │
│   ② 记录快照（5 个 hash）                   下次请求时比对       │
│     作为基线                         ◀───   相同的部分不收费     │
│                                                                 │
│   ③ 读响应中的 cache_read_tokens ──◀───   返回给你：            │
│     对比上次，判断是否断裂                   "命中了 X tokens"    │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**OpenSquilla 的角色**：只是"建议者"和"观察者"——
- 告诉 Provider "这 70% 的内容不会变，你可以缓存"（打 `cache_control` 标记）
- 事后看 Provider 返回的 `cache_read_tokens`，判断缓存是否正常

**Provider 的角色**：真正做缓存的人——
- 按自己的规则决定缓存哪些、缓存多久
- 实际执行缓存命中时按 1/10 价格计费

## 二、缓存的三个步骤

### 步骤 1：标记缓存锚点（`prompt_cache.py`）

引擎处理管线第 4 阶段，给 **system prompt 和 tools 定义**打上 `cache_control` 标记，告诉 AI 厂商："这部分内容在对话之间不会变，你可以缓存起来，下次别重复计费。"

```
# 源码核心逻辑
cache_cfg = getattr(ctx.config, "prompt_cache", None)
if cache_cfg.effective_mode == "off":
    return ctx  # 没开缓存，直接跳过

# 记录缓存基准信息
ctx.metadata["cache_base_chars"] = len(base)        # 基准部分多长
ctx.metadata["cache_base_hash"] = hash(base)         # 基准部分的指纹
ctx.metadata["cache_enabled"] = True
```

### 步骤 2：记录快照，建立基线（`cache_break_monitor.py`）

每次发送请求前，系统对请求内容做 **5 个维度的哈希快照**：

| 快照维度 | 包含什么 | 为什么重要 |
|---------|---------|-----------|
| `system_hash` | system prompt 的哈希 | system prompt 变了 → 缓存全部失效 |
| `tools_hash` | 工具定义列表的哈希 | 工具变了 → 缓存失效 |
| `messages_prefix_hash` | 历史消息（去掉最后 2 条）的哈希 | 对话历史变了 → 缓存失效 |
| `cache_control_hash` | 模型参数（temperature、max_tokens 等）的哈希 | 参数变了 → 缓存失效 |
| `model` | 模型名称 | 换模型了 → 缓存失效 |

**关键设计**：历史消息会去掉最后 2 条再 hash，因为当前轮的消息可能变化，不影响缓存基准。

### 步骤 3：比对响应，检测缓存断裂

每次 AI 模型返回后，系统读取 `cache_read_tokens`（本次缓存命中了多少 tokens），和上一次的基线对比：

```
判断条件（两个条件同时满足才触发告警）：
  1. 下降量 >= 2000 tokens  （不是正常波动）
  2. 下降比例 >= 5%          （不是正常波动）
```

## 三、缓存什么时候会断裂？

从实际运行日志（114,324 行）中 65 次断裂事件分析：

| 断裂原因 | 次数 | 占比 | 是否可避免 |
|---------|:---:|:---:|:---:|
| `messages_prefix_hash` 变了（对话增长了） | 63 次 | 97% | ❌ 正常现象 |
| `cache_control_hash` 也变了（换模型/改参数） | 2 次 | 3% | ⚠️ 可优化 |

**97% 的断裂是因为对话增长了**——这是正常的，缓存本来就会随着对话轮数增加而逐渐减少命中。

**3% 的断裂是因为换模型或改参数**——这是可以优化的。比如从 kimi 换到 deepseek 时，如果提前把 thinking_budget 参数对齐，缓存就不会完全失效。

### 总体统计

| 指标 | 数值 | 说明 |
|------|:---:|------|

| 平均缓存命中 | ~50,000 tokens | 中等对话 |

### 真实日志例子

**例子 1：缓存正常断裂——对话增长了**

```
# 第 1 次请求：缓存命中 28,472 tokens（占 40%）
# 第 2 次请求：缓存命中降到 13,624 tokens（占 14%）

cache.break_detected
  reason=cache_read_drop
  changed_fields=['messages_prefix_hash']     ← 对话历史变了
  drop_tokens=14848     ← 下降了 14,848 tokens
  drop_ratio=0.5215     ← 下降了 52%
```

**例子 2：缓存大幅断裂——换模型了**

```
# 上一次：kimi-k2.7-code，缓存 55,296 tokens
# 这一次：仍用 kimi-k2.7-code，但参数变了

cache.break_detected
  changed_fields=['messages_prefix_hash', 'cache_control_hash']
  drop_tokens=45312     ← 下降了 45,312 tokens
  drop_ratio=0.8194     ← 下降了 82%！
```

**例子 3：缓存稳定——最好的情况**

```
# 对话稳定，缓存持续命中，83% 的请求都是这种状态
cache_read_tokens=259072  ← 命中 25.9 万 tokens
cache_read_tokens=258872  ← 稳定
cache_read_tokens=262144  ← 稳定
```

## 五、缓存对价格的影响——具体算一笔账

deepseek-v4-pro 的实际价格（源码 `_PRICING_TABLE`）：
- 输入：$0.435 / 1M tokens
- 缓存命中：$0.003625 / 1M tokens（缓存价格是原价的 **1/120**）

```
78% 缓存命中时（正常状态）：
  付费部分 = 22% × 70K tokens × $0.435 + 78% × 70K tokens × $0.003625
          ≈ $0.0067 + $0.0002
          ≈ $0.0069 / 次

14% 缓存命中时（缓存断裂）：
  付费部分 = 86% × 70K tokens × $0.435 + 14% × 70K tokens × $0.003625
          ≈ $0.0262 + $0.0004
          ≈ $0.0266 / 次

差距 ≈ 3.9 倍！
```

**缓存断裂一次，当次请求的费用可能翻近 4 倍。**

## 六、与路由器的配合

缓存和路由器是互相影响的：

| 场景 | 路由做什么 | 缓存影响 |
|------|----------|---------|
| 路由保持模型不变 | 推荐同一个模型 | ✅ 缓存持续命中 |
| 路由切换模型 | 从 R1 换到 R2 | 🔴 缓存失效，重建 |
| 路由器被绕过 | 固定用某个模型 | ✅ 缓存稳定（83%） |
| 编码模式 | 锁定 deepseek-v4-pro | ✅ 缓存稳定（但失去了省钱机会） |

**设计权衡**：路由切换模型可以省钱（用便宜模型），但会导致缓存失效（多花钱）。两者之间存在 trade-off。

## 七、关键配置

| 配置项 | 含义 | 默认值 |
|--------|------|--------|
| `prompt_cache.mode` | 缓存模式 | `off` / `static` / `dynamic` |
| `OPENSQUILLA_PROVIDER_COMPACTION_TINY_GUARD_CHARS` | 微小压缩保护阈值 | 0（关闭） |
| `OPENSQUILLA_PROVIDER_COMPACTION_PROTECT_RECENT_ASSISTANT` | 保护最近 AI 回复不被压缩 | 关闭 |

## 八、对产品/运营同学的一句话总结

> 缓存是 OpenSquilla 的"隐形省钱利器"——83% 的请求缓存稳定，命中时价格是原价的 1/10。缓存断裂时（17% 的情况），97% 是因为对话正常增长，3% 是因为换模型导致。系统会自动检测断裂并告警，但缓存本身由 AI 厂商（Provider）在服务端执行，OpenSquilla 只负责"建议缓存"和"观察断裂"。
