# 03-03 · 多提供商 AI 模型层（Provider）— 大白话版

> **模块规模**：35 个核心代码文件 | **核心协议**：统一流式接口协议 | **代码分析工具扫描**：44 个关键符号（跨 4 个文件） | **支持 AI 服务商**：10 种

---

## 定位

AI 模型层是 OpenSquilla 的"翻译官"。它把 OpenSquilla 内部的统一接口协议，翻译成各个 AI 厂商各自的数据格式，并统一返回。核心设计思想是**接口统一、实现隔离**——不管底层用的是 GPT、Claude 还是 DeepSeek，上层看到的都是同一种调用方式。

---

## 生活化比喻

> AI 模型层像一个**万能充电头**。手机只有 Type-C 口，但要在各国充电——中国（DeepSeek）、美国（OpenAI）、开源社区（Ollama）。万能充电头自动适配各种插座标准，你只管插上去。如果某个插座坏了（故障），充电头自动换一个（故障回退策略）。

## 三、多模型投票模式（Ensemble）

**问题**：单个模型可能不够好，怎么同时用多个模型并选出最佳结果？

**解决方案**：多模型投票模式实现了多个"提议者"并发 + 一个"汇总者"聚合的模式。

### 多模型投票架构（4 步）

```
步骤 1：多个提议者并发
  ┌─ 提议者 1 (Claude Sonnet) ──┐
  ├─ 提议者 2 (DeepSeek V4) ────┤── 同时调用
  ├─ 提议者 3 (Kimi K2.7) ──────┤
  └─ 提议者 N ... ──────────────┘
  每个提议者独立调用 AI，互不干扰

步骤 2：心跳保活
  等待慢的提议者时发送心跳信号
  防止长等待导致超时

步骤 3：汇总者聚合
  所有提议者结果汇总 → 汇总者模型
  汇总者看到所有提议者的输出，做最终决策
  工具调用只能由汇总者发出

步骤 4：用量统计
  每个提议者的用量独立追踪
  每个模型都计入实际用量
```

### 关键配置

| 参数 | 含义 | 默认值 |
|------|------|--------|
| 最少成功提议者数 | 至少需要几个提议者成功 | 1 |
| 法定人数宽限秒数 | 达到最小成功数后额外等待时间 | 0（立即停止） |
| 单个提议者超时 | 单个提议者最长等待时间 | 3600 秒 |
| 汇总者超时 | 汇总者最长等待时间 | 3600 秒 |
| 全部失败策略 | 所有提议者都失败时怎么做 | 降级到单个备用模型 |
| 是否打乱顺序 | 是否随机打乱提议者顺序 | 是 |
| 提议者能否调工具 | 是否允许提议者调用工具 | 否 |

## 四、统一错误分类体系

所有 AI 服务商的错误统一为标准错误类型：

| 错误类型 | 大白话 | 是否可重试 | 处理方式 |
|----------|------|-----------|---------|
| 被限流 | 调用太频繁，被限制了 | ✅ | 等一会儿再试 |
| 服务器过载 | 服务商服务器忙不过来 | ✅ | 等一会儿再试 |
| 网络抖动 | 网络不稳定，暂时超时 | ✅ | 等一会儿再试 |
| 上下文太长 | 对话内容超出模型处理范围 | ✅ | 压缩后重试 |
| 密钥错误 | 密钥错了 | ❌ | 告知用户修改 |
| 请求格式错误 | 请求格式有问题 | ❌ | 报告错误 |
| 内容被拒 | 内容被安全策略拦截 | ❌ | 告知用户 |
| 模型不存在 | 指定的模型名找不到 | ❌ | 切换备用模型 |
| 功能不支持 | 模型不支持这个功能 | ❌ | 降级处理 |
| 余额不足 | 账户没钱了 | ❌ | 告知用户 |

## 九、密钥管理详解

### 完整流程

```
步骤 1：初始化
  从环境变量/配置中读取密钥列表
  支持多个密钥

步骤 2：优先级排序
  按密钥的配置顺序排序
  可选：随机打乱实现负载均衡

步骤 3：获取密钥
  使用时取第一个可用密钥
  线程安全

步骤 4：故障切换
  如果密钥失效 → 标记为不可用
  自动切换到下一个密钥
  不可用密钥加入冷却期

步骤 5：全部失效
  所有密钥都失效 → 提示用户检查配置

步骤 6：冷却恢复
  冷却期过后，不可用密钥重新可用
  避免永久排除可能恢复的密钥
```

## 十三、一次 AI 调用的完整生命周期

从 AI 代理决定"我要调模型了"，到最终拿到响应结果，中间要经过一条完整的流水线。下面用大白话把每一步走一遍。

### 步骤 1：AI 代理组装消息

AI 代理在引擎中干活。当它需要调用 AI 时，先把对话历史、系统提示词、工具调用结果等拼成一个消息列表。每条消息包含"角色"（系统/用户/AI助手/工具）和"内容"（文本或内容块列表）。

### 步骤 2：调用统一聊天接口

AI 代理拿到组装好的消息后，调用统一聊天接口。返回的是一个流式事件迭代器，调用方逐条消费事件。

### 步骤 3：协议适配器翻译为 AI 服务商格式

每个 AI 服务商适配器的第一步，就是把 OpenSquilla 统一格式的消息列表翻译成目标 AI 服务商的数据格式。

以 OpenAI 为例：把消息对象转成 OpenAI 接口的 JSON 格式，同时处理系统提示词的注入、工具定义的翻译等。构造完整的网络请求数据。

Anthropic 适配器也做类似的事，但翻译目标变成 Anthropic 接口的格式。

### 步骤 4：发送网络请求

翻译完消息后，适配器发送异步网络请求。OpenAI 适配器发送到 OpenAI 的接口地址，带上认证信息。

这一步是流式请求，响应以流式格式逐块返回。

### 步骤 5：流式响应解析 → 统一事件

响应数据到达后，适配器逐行解析：

1. 解析流式数据，提取内容
2. 缓冲推理内容
3. 组装工具调用（开始 → 增量 → 结束生命周期）
4. 包装成 OpenSquilla 统一的事件类型：文字增量、工具调用开始、工具调用增量、工具调用结束、完成、错误

### 步骤 6：引擎消费事件

AI 代理在事件循环中消费事件：

- 文字增量 → 实时推送给网页界面
- 工具调用事件 → AI 代理执行工具后把结果加入消息继续下一轮
- 完成事件 → 本轮调用结束，携带词元用量、费用等统计信息
- 错误事件 → 出错，触发故障回退或错误处理

### 完整链路图（一目了然）

```
AI 代理组装消息
  │
  ▼
统一聊天接口.聊天(消息列表, 工具, 配置)
  │
  ▼
[适配器] 翻译消息 → AI 服务商数据格式
  │
  ▼
[适配器] 发送网络请求（流式）
  │
  ▼
[适配器] 解析流式响应 → 统一事件
  │ 文字增量 / 工具调用 / 完成 / 错误
  ▼
AI 代理消费事件 → 推文本/执行工具/统计用量
  │
  ▼
[结束] 本轮调用完成
```

## 十四、多模型投票模式的并发调用流程

多模型投票是 OpenSquilla 的"多模型投票"模式：同时让多个模型各自回答同一个问题，然后由一个汇总模型看所有答案，选出或综合出最佳结果。

### 整体架构

```
                    ┌─ 提议者 1 (Claude Sonnet) ──┐
用户问题 ──→        ├─ 提议者 2 (DeepSeek V4) ────┤── 同时调用
                    ├─ 提议者 3 (Kimi K2.7) ──────┤
                    └─ 提议者 N ... ──────────────┘
                                        │
                                   所有结果汇总
                                        │
                                        ▼
                              汇总者模型
                              （看到所有答案，做最终决策）
                                        │
                                        ▼
                                  最终回复
```

### 步骤 1：入口

当 AI 代理调用多模型投票模式的聊天接口时，入口方法委托给内部异步方法。

### 步骤 2：并发启动所有提议者

内部流程：
1. 先发一个心跳事件，告诉界面"正在跑 N 个提议者"
2. 创建一个进度队列
3. 启动所有提议者作为后台任务
4. 主循环从进度队列中取事件，实时推送给界面——如果队列空了超过 15 秒，发心跳事件防止界面以为卡死了

每个提议者调用内部收集方法：
- 实例化对应的 AI 服务商适配器
- 调用聊天接口获得事件流
- 收集所有文本增量，拼成完整文本
- 记录词元用量、耗时、费用等

### 步骤 3：法定人数控制

不是傻等所有提议者跑完，而是有智能的法定人数控制：

- **最少成功提议者数**：最少需要多少个提议者成功（默认 1）
- **法定人数宽限秒数**：一旦达到最小成功数，再等多少秒就停止等待（默认 0，即达到就立即停止）
- **法定人数不可达检测**：如果成功数 + 剩余运行数 < 最小要求数，直接取消剩余任务

### 步骤 4：收集结果

所有提议者跑完后，排序结果。每个结果包含：
- 完整输出文本
- 词元用量
- 耗时
- 错误信息（如果失败）

### 步骤 5：汇总者聚合

如果成功的提议者数量 >= 最少成功数：

1. 把每个成功提议者的输出打包，追加到消息后面
2. 启动汇总者模型
3. 让汇总者看到所有提议者的答案
4. 汇总者输出最终回复，同时汇总所有用量

如果成功的提议者不够：
- 降级到单个备用模型
- 或直接返回错误

### 步骤 6：用量统计

多模型投票的用量是累加的：完成事件里的输入词元、输出词元、费用等是所有提议者 + 汇总者的总和。用量明细字段按角色（提议者/汇总者）分别列出每个成员的用量。

## 十五、错误分类全流程

当 AI 调用出问题时，OpenSquilla 不是简单地把错误原样抛给用户，而是经过一套**表驱动分类系统**，把各种厂商千奇百怪的错误信息映射到标准错误类型，再根据类型决定恢复动作。

### 步骤 1：错误来源

错误可能来自多个层面：
- **网络层**：HTTP 429（限流）、401/403（认证失败）、5xx（服务器错误）等
- **应用层**：流式数据中返回错误字段、数据解析失败、空响应
- **传输层**：连接超时、连接被拒绝、网络不可达

所有错误最终被包装成错误事件，携带状态码、错误码、错误消息。

### 步骤 2：表驱动分类

错误分类函数接收三个参数：
- AI 服务商名称
- 网络状态码
- 错误码和消息文本

分类流程采用**三层匹配表**：

```
第一层：共享前置匹配（所有服务商通用的规则）
  ↓ 没命中
第二层：服务商家族匹配（不同服务商有不同的规则）
  ↓ 没命中
第三层：共享尾匹配（通用的兜底规则）
  ↓ 没命中
返回未知错误（记日志，方便后续添加新规则）
```

**大白话解释**：比如 OpenAI 返回了 HTTP 429（请求太多），分类函数先过共享前置，不命中 → 查 OpenAI 兼容家族表，状态码 429 命中 → 返回"被限流"。

### 步骤 3：决定恢复动作

分类完成后，把标准错误类型映射到 6 种恢复动作：

| 标准错误类型 | 恢复动作 | 含义 |
|---------------------|---------|------|
| 上下文太长 | 压缩后重试 | 精简上下文后重试同一个服务商 |
| 服务器过载、网络抖动 | 先重试再切换 | 先重试，还不行就切备用 |
| 被限流、余额不足、模型不存在、功能不支持 | 切换备用服务商 | 直接切到备用 |
| 密钥无效 | 配置失败 | 告知用户修改密钥 |
| 其他 | 原样告知 | 原样报告给用户 |

### 步骤 4：引擎层执行恢复

回到引擎层，当 AI 调用抛出异常或返回错误事件时：

1. 调用错误分类函数分类
2. 调用恢复决策函数决定动作
3. 根据动作执行：重试（带退避）、切备用（获取下一个服务商）、压缩上下文、或告知用户

### 完整流程图

```
AI 调用出错
  │
  ▼
错误分类函数(服务商名, 状态码, 错误码, 错误消息)
  │ 三层匹配表：共享前置 → 家族表 → 共享尾
  ▼
返回标准错误类型（13 种之一）
  │
  ▼
恢复决策函数(错误类型)
  ▼
返回恢复动作（6 种之一）
  │
  ├─ 压缩后重试 → 精简上下文 → 重试同一服务商
  ├─ 先重试再切换 → 退避重试 → 不行就切
  ├─ 切换备用服务商 → 直接切备用
  ├─ 配置失败 → 告知用户修改
  └─ 原样告知 → 原样报告用户
```
