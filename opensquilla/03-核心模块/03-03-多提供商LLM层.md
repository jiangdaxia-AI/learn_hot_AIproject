## 定位

提供商层是 OpenSquilla 的"翻译官"。它把 OpenSquilla 内部的统一 `LLMProvider` 协议，翻译成各个 AI 厂商各自的 API 格式，并统一返回。核心设计思想是**接口统一、实现隔离**。

> 来源：`provider/protocol.py` L181 `LLMProvider` 是统一抽象协议

---

## 生活化比喻

> 提供商层像一个**万能充电头**。手机只有 Type-C 口，但要在各国充电——中国（DeepSeek）、美国（OpenAI）、开源社区（Ollama）。万能充电头自动适配各种插座标准，你只管插上去。如果某个插座坏了（故障），充电头自动换一个（FallbackPolicy）。

## 一、LLMProvider 协议 — 统一接口

所有提供商适配器必须实现 `LLMProvider` 协议（`provider/protocol.py:181`）：

```python
class LLMProvider(Protocol):
    async def chat(messages, config) -> AsyncIterator[ProviderEvent]
    def metadata() -> ProviderMetadata
    def project_message_count(messages) -> int
    def resolve_quota_status() -> QuotaStatus
```

| 方法 | 返回值 | 职责 |
|------|--------|------|
| `chat()` | AsyncIterator[ProviderEvent] | 核心：发送消息，流式返回事件 |
| `metadata()` | ProviderMetadata | 返回提供商元信息（名称、模型列表、能力） |
| `project_message_count()` | int | 估算消息 token 数 |
| `resolve_quota_status()` | QuotaStatus | 查询配额状态 |

## 三、EnsembleProvider — 多模型并发模式

**问题**：单个模型可能不够好，怎么同时用多个模型并选出最佳结果？

**解决方案**：`EnsembleProvider`（`provider/ensemble.py:622`）实现了多 proposer 并发 + aggregator 聚合模式。

### Ensemble 架构（4 步）

```
步骤 1：多 Proposer 并发
  ┌─ Proposer 1 (Claude Sonnet) ──┐
  ├─ Proposer 2 (DeepSeek V4) ────┤── 并发调用
  ├─ Proposer 3 (Kimi K2.7) ──────┤
  └─ Proposer N ... ──────────────┘
  每个 proposer 独立调用 LLM，互不干扰

步骤 2：心跳保活
  等待慢 proposer 时发送心跳事件
  防止长等待导致超时

步骤 3：Aggregator 聚合
  所有 proposer 结果汇总 → Aggregator 模型
  Aggregator 看到所有 proposer 的输出，做最终决策
  工具调用只能由 Aggregator 发出

步骤 4：用量统计
  每个 proposer 的用量独立追踪
  accounts_physical_usage = True（每个模型段都计入实际用量）
```

### 关键配置

| 参数 | 含义 | 默认值 |
|------|------|--------|
| EnsembleMemberConfig | 单个成员配置（provider, model, weight） | - |
| EnsembleProvider | 合并后的 provider | - |
| build_ensemble_provider_from_config | 工厂函数 | - |

> 来源：`provider/ensemble.py` L205（EnsembleMemberConfig）, L622（EnsembleProvider）, L1443（ensemble_done）

## 四、ProviderFailure 分类 — 统一错误体系

所有提供商错误统一为 `ProviderFailureKind` 枚举（`provider/failures.py`）：

| 错误类型 | 含义 | 是否可重试 | 处理方式 |
|----------|------|-----------|---------|
| RATE_LIMITED | 被限流 | ✅ | 指数退避后重试 |
| PROVIDER_OVERLOADED | 提供商超载 | ✅ | 指数退避后重试 |
| TRANSPORT_TRANSIENT | 网络抖动 | ✅ | 指数退避后重试 |
| CONTEXT_OVERFLOW | 上下文溢出 | ✅ | 压缩后重试 |
| AUTH_INVALID | 密钥错误 | ❌ | 报告用户 |
| BAD_REQUEST | 请求格式错误 | ❌ | 报告错误 |
| POLICY_REFUSAL | 模型拒绝 | ❌ | 报告用户 |
| MODEL_NOT_FOUND | 模型不存在 | ❌ | 切换备用模型 |
| UNSUPPORTED_FEATURE | 不支持的功能 | ❌ | 降级处理 |
| INSUFFICIENT_CREDITS | 余额不足 | ❌ | 报告用户 |

> 来源：`provider/failures.py` ProviderFailureKind 枚举、`engine/fallback.py` L16-L23 `_RETRYABLE_FAILURE_KINDS`

## 五、CredentialPool — 凭证管理

`CredentialPool`（`provider/credentials.py`）管理 API Key 的获取和轮转：

```
步骤 1：从环境变量/配置中读取 API Key 列表
步骤 2：按优先级排序
步骤 3：使用时取第一个可用 key
步骤 4：如果 key 失效（AUTH_INVALID）→ 自动切换到下一个
步骤 5：全部失效 → 抛出 NoCredentialsAvailable
```

> 来源：`provider/credentials.py` CredentialPool, NoCredentialsAvailable

## 六、ModelSelector — 模型选择器

`ModelSelector`（`provider/selector.py`）负责选择具体模型：

```
步骤 1：接收 SquillaRouter 的路由建议（tier）
步骤 2：从配置文件查找该 tier 对应的模型
步骤 3：检查模型可用性（配额、凭证）
步骤 4：返回选定的模型 + 配置
步骤 5：如果首选不可用 → 使用 fallback 链
```

> 来源：`provider/selector.py` build_provider() 函数
