## 定位

通道层是 OpenSquilla 的"社交网络"。它让 AI 能接入飞书、Slack、Telegram、Discord 等各种聊天平台，在群聊里回答问题、执行命令、定时汇报。所有通道适配器都注册到 ChannelManager 统一管理生命周期。

---

## 生活化比喻

> 通道层就像一个人同时登录了微信、QQ、钉钉、飞书、Telegram。无论你在哪个 App 上找他，他都能回复你，而且记住你们在哪个 App 上聊过什么。每个 App 有自己的消息格式，通道层负责把各种格式翻译成统一的"内部语言"。

---

## 一、ManagedChannel 统一协议

所有通道适配器必须实现 ManagedChannel 协议 (channels/types.py:96)，这是整个通道层的"万能接口"：

| 方法 | 职责 | 说明 |
|------|------|------|
| start() | 建立与平台的连接 | 飞书初始化 SDK、Telegram 启动 Bot 轮询 |
| stop() | 断开连接，清理资源 | 关闭 WebSocket、停止轮询循环 |
| send(target, text) | 发送消息到指定目标 | 群聊/私聊/话题，自动适配各平台格式 |
| send_file(target, file) | 发送文件 | 上传附件到平台 |
| health() -> ChannelHealth | 返回 Unhealthy/Degraded/Healthy | 心跳检测，故障自动告警 |
| webhook_routes() -> list[Route] | 返回 Starlette 路由 | 用于接收平台回调 |
| parse_incoming(raw) -> InboundMessage | 解析入站消息 | 各平台格式 → 统一内部格式 |
| resolve_inbound_attachment(att) | 解析附件 | 下载图片/文件到本地 |
| supports(feature) -> bool | 能力查询 | 检查是否支持 thread/reaction/file 等 |

## 二、支持的所有通道（9 种 + WebSocket）— 逐个详解

### 2.1 飞书/Lark (feishu.py)

飞书适配器 (FeishuChannel, channels/feishu.py:658) 是整个系统最复杂的通道适配器，31 个调用者。

**配置字段** (FeishuChannelConfig, channels/feishu.py:219)：
| 字段 | 说明 |
|------|------|
| app_id / app_secret | 飞书应用凭证 |
| encrypt_key | 消息加密密钥（飞书安全模式） |
| verification_token | Webhook 验证令牌 |
| connection_mode | webhook 或 websocket（飞书支持长连接模式） |
| domain | feishu 或 lark（国际版） |
| api_base | 默认 https://open.feishu.cn/open-apis |
| event_dedupe_size | 事件去重窗口（默认 10,000） |
| token_refresh_margin_s | token 刷新提前量（默认 300 秒） |

**入站消息处理流程**：
1. 飞书服务器 POST 到 webhook_path → 网关接收
2. 验证签名（X-Lark-Signature 头 + timestamp + nonce 防重放）
3. URL 验证挑战（飞书首次配置时发送 challenge，需原样返回）
4. 解析事件类型（message/image/file/approval 等）
5. 事件去重（event_dedupe_size 窗口内相同 event_id 只处理一次）
6. 租户访问令牌缓存（tenant_access_token，token_refresh_margin_s 秒前刷新）
7. 构建统一 InboundMessage → 交给 ChannelManager 分发

**出站消息**：回复消息（feishu_chat_reply 使用原生回复 API）、发送消息（feishu_chat_send）、编辑消息（feishu_chat_edit）。飞书特有的能力：文档操作（feishu_doc_*）、表格操作（feishu_sheet）、云盘上传（feishu_drive_upload_artifact）、权限管理（feishu_perm_grant_member）。

### 2.2 Telegram (telegram.py)

Telegram 适配器 (TelegramChannel, channels/telegram.py:100)，15 个调用者。

**配置字段** (TelegramChannelConfig, channels/telegram.py:70)：
| 字段 | 说明 |
|------|------|
| token | Bot Token |
| transport_name | polling（轮询模式）或 webhook（回调模式） |
| webhook_path | Webhook 路径（默认 /telegram/events） |
| webhook_secret_token | Webhook 密钥令牌 |
| poll_timeout_s | 轮询超时（默认 30 秒） |
| poll_limit | 每次拉取消息数上限（默认 100） |
| poll_idle_sleep_s | 无消息时休眠间隔（默认 0.1 秒） |
| drop_pending_updates | 启动时是否丢弃积压消息 |
| allowed_updates | 允许的更新类型（message, callback_query 等） |

**两种传输模式**：
- **Polling 模式**：循环调用 getUpdates API，每次拉取 poll_limit 条消息，用 offset 去重
- **Webhook 模式**：Telegram 服务器主动 POST 到 webhook_url，用 X-Telegram-Bot-Api-Secret-Token 验证

**入站消息处理**：parse_incoming() 解析 Update 对象 → 提取 text/photo/document → 图片用 getFile API 获取最大尺寸版本 → 超大附件声明跳过下载

**出站消息**：send() 发文本、send_file() 发文件（直接 POST multipart 到 sendDocument API）

### 2.3 Slack (slack.py)

**两种连接模式**：
- **Socket Mode**：出站 WebSocket 长连接（类似飞书），需要 app_token，不需要公网 URL
- **Webhook 模式**：Events API 回调，需要 signing_secret 验证签名

**特色功能**：reply_in_thread（是否在话题中回复）、status_reactions（状态表情反馈）

### 2.4 钉钉 (dingtalk.py)

使用钉钉 Stream 模式（dingtalk-stream SDK），通过 WebSocket 长连接收发消息。支持企业内消息、群聊、审批卡片。

### 2.5-2.9 其他通道

| 通道 | 特点 |
|------|------|
| Discord | Bot API，支持 Guild/Channel 消息 |
| QQ | QQ Bot API（qq-botpy SDK），国内 IM 集成 |
| MS Teams | Microsoft Teams Bot Framework 适配 |
| Matrix | 去中心化 Matrix 协议，支持联邦 |
| 终端 | 本地 stdin/stdout 交互，无需网络 |

## 四、ChannelManager 生命周期（6 步）

ChannelManager (channels/manager.py:38) 管理所有通道的完整生命周期：

**步骤 1：from_config(config)** — 从网关配置读取所有通道入口，为每个 Enabled 通道构建 ManagedChannel 实例
**步骤 2：收集 Webhook 路由** — 调用每个通道的 webhook_routes()，将路由注册到 Starlette 应用
**步骤 3：start_all() 并发启动** — 所有通道并发启动，单个通道启动失败不影响其他通道
**步骤 4：run_channel_dispatch() 消息分发** — 接收入站消息 → 构建 session key（区分 DM/群聊/话题） → 调用 TurnRunner 执行代理逻辑
**步骤 5：健康监控** — 定期检查 health() 返回的 ChannelHealth（Unhealthy/Degraded/Healthy），故障通道自动重启（指数退避重试）
**步骤 6：stop_all() 并发停止** — 网关关闭时并发停止所有通道，清理资源

## 五、Session Key 构建（6 种会话类型）

每个入站消息需要构建正确的 session key，决定对话上下文如何隔离：

| 会话类型 | 构建函数 (session/keys.py) | Key 格式 | 适用场景 |
|----------|--------------------------|---------|---------|
| main | build_main_key(agent_id) | agent:main:main | 默认会话 |
| channel | build_channel_key(channel, chat_id) | channel:{channel}:{chat_id} | 群聊 |
| dm | build_direct_key(channel, user_id) | dm:{channel}:{user_id} | 私聊 |
| thread | build_thread_key(base_key, thread_id) | {base_key}/thread:{thread_id} | 话题回复 |
| cron | build_cron_key(job_id) | cron:{job_id} | 定时任务 |
| subagent | build_subagent_key(parent, run_id) | {parent}/sub:{run_id} | 子代理 |

## 六、通道健康状态

ChannelHealth 枚举 (channels/types.py) 定义三种状态：

| 状态 | 含义 | 触发条件 |
|------|------|---------|
| Healthy | 正常运行 | 心跳正常、消息收发正常 |
| Degraded | 降级运行 | 部分功能不可用（如文件上传失败但文本正常） |
| Unhealthy | 不可用 | 连接断开、API 返回错误 |

## 七、附件处理

所有通道共享附件处理逻辑 (channels/_attachment_io.py)：
- 入站附件：下载图片/文件 → 保存到本地附件工作区 → 注入到 Agent 上下文
- 出站附件：Agent 生成的 artifacts → 通过通道的 send_file() 上传到对应平台
- 大小限制：超大附件声明跳过下载，避免占用过多带宽
