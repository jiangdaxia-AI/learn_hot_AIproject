# 03-11 · 可观测性 — 通俗教材

> **文件数**：15 个文件 | **核心模块**：运行时诊断观察器（监测重复失败、文件读写循环、空验证等异常行为）、诊断状态管理器（控制诊断开关和模式） | **诊断事件**：8 种类型

---

## 定位

可观测性模块是 OpenSquilla 的"黑匣子记录仪"。它记录 AI 助手的每一次决策、工具调用、模型选择、上下文压缩等运行时事件，用于调试、性能分析和故障排查。

---

## 生活化比喻

> 可观测性像飞机上的黑匣子。飞行员（AI 助手）做了什么操作、什么时候做的、结果怎样——全部记录下来。出问题时翻黑匣子找原因，平时也能用来做性能分析。

## 二、四种诊断模式

系统会自动检测以下异常行为模式：

| 诊断模式 | 触发条件 | 默认阈值 | 通俗解释 |
|---------|---------|------|---------|
| 重复失败检测 | 同一个工具调用连续失败 | 3 次 | 同一个操作反复失败，可能是配置问题 |
| 重复读取文件检测 | 写入文件后反复读取同一文件 | 5 次 | AI 写完后反复检查，可能是"写完不放心" |
| 空验证检测 | 执行验证但没有任何变化 | 3 次 | AI 反复验证但什么都没改，可能是死循环 |
| 未完成工作检测 | AI 结束时还有未提交的修改 | 任意次 | AI 说"做完了"但实际还有改动没保存 |

### 诊断流程

系统在 AI 每次执行工具后自动检查：
1. 提取涉及的文件路径，分类是源码、测试、文档还是调试文件
2. 计算失败特征码，识别同一操作是否反复失败
3. 判断执行的命令是否为验证命令
4. 如果触发异常模式，生成诊断事件告警

## 三、诊断事件类型（8 种）

| 事件类型 | 含义 | 通俗解释 |
|----------|------|---------|
| 重复失败 | 同一工具调用连续失败 | "这个操作试了好几次都不行" |
| 写后反复读 | 写入文件后反复读取 | "写完文件后不放心，反复检查" |
| 验证无变化 | 验证但没有实际变更 | "跑了一遍检查，但什么都没改" |
| 结束时还有未保存的修改 | AI 结束时仍有未提交的更改 | "AI 说做完了，但还有东西没保存" |
| 工具循环 | 工具调用陷入循环 | "AI 在几个工具之间来回跳，出不来" |
| 上下文预算告警 | 对话上下文接近上限 | "聊天记录太多，快装不下了" |
| 压缩事件 | 触发上下文压缩 | "聊天记录太长，正在自动压缩" |
| 服务商健康事件 | AI 服务商出现异常 | "调用的 AI 服务响应慢了或失败了" |

### (1) 事件触发 - 四种诊断模式的触发条件与阈值

**源码位置**: engine/agent.py 第 8280-8310 行（主循环触发）和第 8850-8870 行（结束触发）

诊断检测嵌入在 Agent 的工具调用主循环中，每次 AI 执行完工具后自动触发，无需手动干预。四种触发模式各有独立阈值。

#### 1.1 重复失败：同一工具连续失败 3 次 -> 触发诊断

**大白话**：Agent 调用同一个工具（比如 exec_command 跑 pytest），连续 3 次返回 is_error=True，且错误信息高度相似（相同的 failure_anchor_hash），系统判定这个操作反复失败。

关键代码路径：agent.py 第 8261-8265 行提取 failure_anchor_summary，然后传给观察者。观察者内部用 failure_anchor_hash() 计算失败特征码，再与 _failure_anchor_counts 计数器比对。

**阈值**：RuntimeDiagnosticsThresholds.repeated_failure_anchor = 3

**分支逻辑**：
- 如果 failure_anchor_summary 为空（本次调用无错误）-> 跳过该检测，不累加计数器
- 如果 failure_anchor_hash 为 None（摘要为空或无法哈希）-> 计数器不增加
- 如果哈希与历史匹配 -> 计数 +1，达到 3 次 -> 生成 repeated_failure_anchor 事件
- 如果哈希是新的（不同错误）-> 新建计数器，旧计数器保留

#### 1.2 重复读取：写入后反复读取同一文件 5 次 -> 触发诊断

**大白话**：Agent 用 write_file 或 edit_file 写了一个源码文件，之后反复用 read_file 读取同一个文件。如果读了 6 次以上，说明写完不放心，反复检查，可能是陷入了检查-修改的死循环。

**阈值**：RuntimeDiagnosticsThresholds.repeated_source_read_after_write = 6（源码中阈值设为 6，即第 6 次读取时触发）

**分支逻辑**：
- 只统计 classify_path() == source 的路径（源码文件），不统计 scratch/debug 文件
- 必须有 write_records（本轮有写入记录）才会进入检测
- 用 _seen_read_records / _seen_write_records 做增量比较，只处理新出现的读写记录

#### 1.3 空验证：执行验证命令但 diff 无变化 3 次 -> 触发诊断

**大白话**：Agent 跑了 pytest 或 go test 等验证命令，但工作区的 diff 指纹跟上次完全一样（说明验证后什么都没改）。连续 3 次验证但没改任何东西，可能是 Agent 陷入了验证死循环。

**阈值**：RuntimeDiagnosticsThresholds.repeated_verification_without_diff_change = 3

**分支逻辑**：
- 先用 command_looks_like_focused_verification() 判断命令是否为验证命令（匹配 pytest、go test、npm test 等 30+ 种验证命令标记）
- 用 normalize_command_family() 将命令标准化为族（如 cargo:test、npm:test）
- 用 (command_family, diff_fingerprint) 作为联合键，确保同一命令 + 同一 diff 指纹才算重复
- 如果没有 write_records 或没有 diff_fingerprint -> 跳过检测

#### 1.4 未提交变更：Agent 在仍有未提交 diff 时结束 -> 触发诊断

**大白话**：Agent 的 turn 因为 terminal_error（超时/异常/主动停止）结束，但工作区还有未提交的 diff（改了一半的文件），说明 AI 说做完了但实际还有东西没保存。

**触发时机**：Agent 主循环结束后的 observe_finish_error() 调用，位于 agent.py 第 8856-8866 行。

**阈值**：无阈值，只要 diff_paths 不为空即触发。事件类型为 finish_error_with_non_empty_diff。

### (2) 观察者注册 - RuntimeDiagnosticsObserver 在 Agent 启动时初始化

**源码位置**: engine/agent.py 第 4493-4502 行（观察者构造）

观察者不是全局单例，而是每个 Agent turn 创建一个新实例，保证状态隔离。注册仅当 runtime_events_path 已配置或 runtime_recovery_mode == warn_model 时才创建。

#### 2.1 RuntimeDiagnosticsObserver 在 Agent 启动时注册

**大白话**：Agent 开始新一轮对话时，先检查配置里有没有开诊断功能。如果开了，就 new 一个 RuntimeDiagnosticsObserver，传入当前会话的 session_key 和 agent_id。这个观察者跟这一轮对话绑定，对话结束就销毁。

**分支逻辑**：
- 如果 runtime_events_path 为空 且 runtime_recovery_mode != warn_model -> runtime_diagnostics = None，跳过所有诊断检测
- 如果任一条件满足 -> 创建观察者，默认阈值由 RuntimeDiagnosticsThresholds 提供

#### 2.2 订阅工具调用完成事件（observe_tool_results）

**大白话**：观察者不主动拉数据，而是被动等 Agent 主循环推数据。每次工具调用完成后，Agent 调用 runtime_diagnostics.observe_tool_results(...)，把本轮所有工具调用结果、读写记录、diff 状态等一股脑传给观察者。

调用位置：agent.py 第 8291-8305 行，在一次迭代的所有工具执行完毕后。

#### 2.3 订阅 Agent 状态变更事件（observe_finish_error）

**大白话**：除了监听工具调用结果，观察者还监听 Agent 的结束事件。当 Agent 因为 terminal_error 终止时，调用 observe_finish_error() 检查是否还有未提交的 diff。

调用位置：agent.py 第 8856-8866 行。

### (3) 事件收集 - observe_tool_results() 接收并分类原始数据

**源码位置**: engine/runtime_diagnostics.py 第 153-272 行（observe_tool_results 方法）

这是观察者的入口方法，每轮工具调用后执行一次。方法接收 10 个参数，覆盖了本轮工具调用的全部上下文。

#### 3.1 observe_tool_results() 接收每次工具调用的结果

**大白话**：Agent 把本轮所有工具调用的参数（tool_calls）、执行结果（results）、读写记录（read_records / write_records）、临时文件记录（scratch_records）、diff 路径和指纹（diff_paths / diff_fingerprint）、以及失败摘要（failure_anchor_summary）一起传给观察者。观察者拿到这些数据后，开始做增量分析。

**关键设计**：_seen_read_records / _seen_write_records 做增量切片，确保每次只分析新出现的记录，不会重复统计历史记录。

#### 3.2 _unique_paths_from_records() 提取涉及的文件路径列表

**大白话**：从读写记录中提取所有涉及的文件路径，去重后返回。用 _record_relative_path() 获取相对路径，自动去除 /testbed/、/workspace/ 等前缀。

源码位置：runtime_diagnostics.py 第 520-530 行。

#### 3.3 构建 diff_path_classes 和 write_path_classes 字典

**大白话**：对 diff 中涉及的文件和写入的文件分别调用 classify_path() 分类，构建路径->分类的映射字典。这个字典后续会被写入诊断事件的 path_classes 字段，帮助分析 AI 改的是源码还是测试文件还是临时文件。

源码位置：runtime_diagnostics.py 第 165-167 行。

### (4) 路径分类 - classify_path 将文件路径分为 5 类

**源码位置**: engine/runtime_diagnostics.py 第 275-296 行（classify_path）、第 300-325 行（_path_looks_like_scratch_artifact）

路径分类是诊断系统的基础能力，直接影响后续所有模式匹配的准确性。系统将文件路径分为 5 类，分类优先级从高到低。

#### 4.1 classify_path() 按优先级依次匹配 5 种分类

**大白话**：拿到一个文件路径后，系统按顺序检查：是不是生成的代码？是不是文档？是不是测试文件？是不是临时调试文件？都不匹配的话，默认归类为源码（source）。这个分类决定了写后反复读检测的范围——只有 source 类文件才会被统计。

| 分类 | 匹配规则 | 示例 |
|------|---------|------|
| source | 不匹配任何特殊模式（默认） | src/main.py、lib/utils.js |
| test | test/**、tests/**、*.spec.*、*.test.* | tests/test_auth.py |
| docs | docs/**、doc/**、documentation/** | docs/api.md |
| generated | dist/**、build/**、*.generated.*、*.min.* | dist/bundle.js |
| debug | debug、scratch、tmp、repro 路径 | scratch/debug.py |

#### 4.2 _path_looks_like_scratch_artifact() 识别临时调试文件

**大白话**：除了路径中明晃晃的 debug、scratch 等目录名，系统还会检查文件名本身。如果文件名是 scratch.py、repro.py、verify.py、fix.py 等 25 种常见临时文件名，或者以 scratch_、debug_、tmp_ 等前缀开头，或者以 .bak、.tmp、.scratch 等后缀结尾，都归类为 debug。

#### 4.3 _normalize_path() 统一路径格式

**大白话**：在分类之前，先把所有路径统一格式——反斜杠转正斜杠、去掉 /testbed/、/workspace/、/repo/ 等容器前缀、去掉开头的 ./。这样不管路径从哪个环境来的，都能被正确匹配。

源码位置：runtime_diagnostics.py 第 540-550 行。

### (5) 模式匹配 - 三种检测器并行运行

**源码位置**: engine/runtime_diagnostics.py 第 190-272 行（observe_tool_results 中的三个检测块）、第 390-400 行（failure_anchor_hash）

观察者在一次 observe_tool_results() 调用中同时运行三个检测器，分别检测重复失败、重复读取、空验证。三个检测器之间互不影响，各自维护自己的计数器。

#### 5.1 重复失败检测：failure_anchor_hash() 计算失败锚点哈希

**大白话**：把错误摘要标准化——全部转小写、合并多余空格、把 /tmp/xxx 和 /var/tmp/xxx 中的随机路径替换为 path 占位符——然后做 SHA256 哈希取前 16 位。这样同一个错误出现在不同临时目录也能被识别为同一类失败。

源码位置：runtime_diagnostics.py 第 390-400 行。

**与历史失败记录对比**：哈希值作为 _failure_anchor_counts Counter 的键，直接累加计数。如果哈希值为 None（摘要为空），不累加。

#### 5.2 重复读取检测：统计同一文件在写入后的读取次数

**大白话**：只对 classify_path() == source 的源码文件做统计。遍历本轮新增的读取记录，如果路径分类为 source，则 _read_after_write_counts[path] 计数 +1。如果路径是 scratch、test 等非源码类型，直接跳过。

**注意**：源码中阈值设为 6（repeated_source_read_after_write = 6），即写后第 6 次读取同一文件时触发。阈值 6 比 5 多一次，是为了避免误报：AI 写完文件后读一次确认是正常行为，读 2-3 次也可能是合理的交叉引用，但 6 次以上的重复读取几乎可以确定是异常循环。

#### 5.3 空验证检测：命令族 + diff 指纹联合匹配

**大白话**：先检查工具调用中的命令是否为聚焦验证命令（如 pytest、go test、npm test），再检查命令族和 diff 指纹的组合是否重复出现。用 (command_family, diff_fingerprint) 作为联合键，确保检测的是同一个命令 + 同一个 diff 状态的重复，而不是不同命令但 diff 都不变的误报。

验证命令覆盖 30+ 种命令族，包括 pytest、go test、cargo test、npm test、mvn test 等。

### (6) 诊断决策 - 阈值比较与分支处理

**源码位置**: engine/runtime_diagnostics.py 第 190-272 行（三个检测块的阈值判断）

每个检测器在计数器更新后，立即与阈值比较。如果达到阈值，生成诊断事件；如果未达到，继续等待下一次工具调用。

#### 6.1 判断是否达到阈值（3 次 / 6 次 / 3 次）

**大白话**：三个检测器各有独立的阈值。重复失败 3 次触发，重复读取 6 次触发，空验证 3 次触发。阈值定义在 RuntimeDiagnosticsThresholds 数据类中，可配置但默认值如上。

**分支逻辑总览**：

| 检测器 | 未达到阈值 | 达到阈值 |
|--------|-----------|---------|
| 重复失败 | 计数器 +1，继续观察 | 生成 repeated_failure_anchor 事件，去重后返回 |
| 失败后源码编辑 | 计数器 + source_writes 数量 | 生成 edit_churn_after_failure 事件 |
| 重复读取 | 计数器 +1（仅 source 文件） | 生成 repeated_source_read_after_write 事件 |
| 空验证 | 计数器 +1（仅验证命令） | 生成 repeated_verification_without_diff_change 事件 |

#### 6.2 如果达到阈值 -> 生成诊断事件 -> 记录到 DecisionLog

**大白话**：达到阈值后，观察者调用 _event() 方法构造一个 JSON 事件字典，包含事件类型、触发次数、路径信息、diff 指纹等完整上下文。然后通过 _dedupe() 去重（同一 (reason, trigger_key_hash) 组合只发一次），最后返回给 Agent 主循环。

#### 6.3 如果未达到阈值 -> 更新计数器 -> 继续观察

**大白话**：计数器累加但不生成事件，观察者继续等待下一次 observe_tool_results() 调用。计数器在整个 Agent turn 生命周期内持续累积，不会被重置。

**去重机制**：即使达到阈值，同一类型的事件也只发一次。_dedupe() 方法用 (reason, trigger_key_hash) 作为去重键，存在 _emitted 集合中，防止同一模式反复触发重复事件。

源码位置：runtime_diagnostics.py 第 355-365 行。

### (7) 诊断事件生成 - _event() 构造结构化诊断事件

**源码位置**: engine/runtime_diagnostics.py 第 273-350 行（_event 方法）、observability/decision_log.py 第 1-350 行（DecisionEntry、write_decision_entry）

当模式匹配命中阈值后，观察者构造一个完整的 JSON 事件字典，包含丰富的上下文信息，方便后续排查。

#### 7.1 _event() 记录结构化字段：时间、Agent、工具、文件、模式类型

**大白话**：_event() 方法把所有诊断相关的上下文打包成一个 JSON 字典。核心字段包括：事件类型（reason / event_name）、会话标识（session_key）、迭代次数（iteration）、触发次数（trigger_count）、触发的工具名（tool_name）、命令族（command_family）、文件路径和分类（normalized_path、path_classes）、失败锚点哈希（failure_anchor_hash）、diff 指纹前后对比（diff_fingerprint_before / diff_fingerprint_after）、以及阈值配置快照（trigger_thresholds）。

#### 7.2 附加上下文：失败锚点摘要和增量证据

**大白话**：事件中附带 failure_anchor_excerpt（错误摘要的前 420 个字符，超长则截断并加哈希后缀），以及 evidence 对象（包含 latest_tool_result_error 布尔值、本轮新增的源码写入列表 new_source_writes、临时文件写入列表 new_scratch_writes）。这些证据帮助快速定位 AI 在失败的同时改了什么文件。

源码位置：runtime_diagnostics.py 第 215-218 行。

#### 7.3 附加工具调用链：触发诊断的工具调用序列

**大白话**：事件中通过 tool_name、command_family 隐式记录了触发诊断的工具调用。tool_name 取的是最后一个工具调用的名称，command_family 也是从最后一个工具调用中提取的命令族，这样就能追溯到是哪个工具调用触发了诊断。

源码位置：runtime_diagnostics.py 第 300-310 行。

### (8) 运行时事件持久化 - append_runtime_event 写入 JSONL

**源码位置**: engine/runtime_events.py 第 1-30 行（append_runtime_event）

诊断事件生成后，需要持久化到磁盘，以便后续回放和分析。写入过程是纯追加模式，不阻塞 Agent 主循环。

#### 8.1 append_runtime_event() 追加 JSON 事件到文件

**大白话**：Agent 主循环拿到诊断事件列表后，逐个调用 append_runtime_event() 写入 runtime_events_path（JSONL 文件）。每次写入一行 JSON，自动添加 created_at 和 timestamp 字段。如果文件路径为空或写入失败（OSError），静默吞掉，不影响 Agent 正常运行。

#### 8.2 与 DecisionLog 的关系：两条独立的日志流

**大白话**：运行时诊断事件和决策日志是两条独立的日志流，写入不同的文件：

| 日志流 | 文件路径 | 写入时机 | 内容 |
|--------|---------|---------|------|
| 运行时诊断事件 | runtime_events_path（配置指定） | 每次工具调用后立即写入 | 诊断事件 JSON（异常模式检测） |
| 决策日志 | ~/.opensquilla/logs/decisions-YYYYMMDD.jsonl | 每轮对话结束时写入 | 决策记录（路由、模型、用量等） |

两者独立存储，但都被诊断包收集时一起打包。诊断事件强调异常模式，决策日志强调正常决策轨迹。

### (9) 诊断包收集 - DiagnosticsBundle 打包脱敏后的诊断数据

**源码位置**: observability/bundle.py 第 1-400 行（collect_bundle）

当用户遇到 bug 需要提交诊断报告时，collect_bundle 一键收集所有诊断数据并打包为 ZIP。整个过程是纯磁盘读取，不依赖运行中的网关，不修改任何配置。

#### 9.1 collect_bundle() 打包：决策日志 + 安全日志 + 配置 + 错误日志

**大白话**：按顺序收集 8 类数据：(1) 脱敏后的配置文件（config.redacted.json）、(2) 离线医生报告（doctor.json）、(3) 诊断开关状态快照（diagnostics.json）、(4) 数据库中的错误记录（errors.jsonl）、(5) structlog 调试日志（debug.log*）、(6) 网关日志（gateway.log）、(7) 决策日志和追踪日志（按天数过滤）、(8) 桌面端日志（仅保留尾部 5MB）。每类数据都是尽力而为：某个文件读不到就记录到 collection_errors，不会中断整个打包。

| 包内文件 | 来源 | 脱敏方式 |
|---------|------|---------|
| config.redacted.json | 用户 TOML 配置 | 移除 API Key、密码等敏感字段 |
| doctor.json | 离线诊断报告 | 完整脱敏 |
| diagnostics.json | 诊断开关状态快照 | 无敏感数据 |
| errors.jsonl | sessions.db 的 turn_errors 表 | 完整脱敏 |
| decisions/*.jsonl | 最近 N 天的决策日志 | 逐行脱敏 |
| traces/*.jsonl | 最近 N 天的追踪日志 | 逐行脱敏 |
| logs/debug.log* | structlog 调试日志 | 逐行脱敏 |
| desktop/*.log | 桌面端日志 | 仅保留尾部 5MB |

#### 9.2 manifest.json 记录打包元信息

**大白话**：打包完成后，生成一个 manifest.json，记录打包时间、OpenSquilla 版本、Python 版本、操作系统信息、安装方式、日志目录、配置来源、环境变量、以及收集过程中遇到的错误和截断。这个清单帮助开发者快速了解用户的运行环境。

#### 9.3 按天数过滤决策日志和追踪日志

**大白话**：_recent_day_files() 函数扫描日志目录下的 decisions-YYYYMMDD.jsonl 和 traces-YYYYMMDD.jsonl 文件，只保留最近 N 天（默认 3 天）的文件。过滤逻辑基于文件名中的日期戳，与当前 UTC 日期做比较。

源码位置：bundle.py 第 130-145 行。

### (10) 脱敏处理 - scrub_text 清洗敏感信息

**源码位置**: observability/redact.py 第 1-120 行

所有写入诊断包的文本数据，在进入 ZIP 之前都经过 scrub_text 脱敏。这是最后一道防线，确保即使用户配置中的敏感信息通过其他路径泄露到了日志中，也会被清洗掉。

#### 10.1 scrub_text() 按顺序执行 4 层脱敏

**大白话**：脱敏引擎按顺序执行 4 层正则替换：(1) 匹配 key=value 形式的密钥赋值；(2) 匹配 Bearer 格式的 Authorization 头；(3) 匹配裸 Token（OpenAI、GitHub、AWS、Slack 等）；(4) 匹配 Slack incoming webhook URL。最后把用户主目录路径替换为波浪号。

#### 10.2 脱敏目标清单

| 脱敏目标 | 正则模式 | 说明 |
|---------|---------|------|
| key=value 密钥 | _ASSIGNMENT_RE | 将等号右侧的值替换为 [redacted] |
| Bearer Token | _BEARER_RE | 将 Bearer 后的 token 替换为 [redacted] |
| 裸 OpenAI Key | _BARE_TOKEN_RE | 匹配 sk- 前缀的密钥 |
| 裸 GitHub PAT | _BARE_TOKEN_RE | 匹配 ghp_ 前缀的个人访问令牌 |
| 裸 AWS Key | _BARE_TOKEN_RE | 匹配 AKIA 前缀的访问密钥 |
| 裸 JWT | _BARE_TOKEN_RE | 匹配 eyJ 开头的 JWT 令牌 |
| Slack Webhook | _SLACK_WEBHOOK_RE | 匹配 hooks.slack.com 的 webhook 路径 |
| 用户主目录 | Path.home() 替换 | 将 /Users/xxx 替换为 ~ |

#### 10.3 脱敏的幂等性设计

**大白话**：脱敏函数被设计为幂等的——对已经脱敏过的文本再次运行 scrub_text，结果不变。关键设计是在正则匹配中优先匹配已脱敏的 [redacted] 标记，避免重复脱敏叠加。

### (11) 回放与分析 - ReplayAPI 按时间/会话/模式查询诊断日志

**源码位置**: observability/replay.py 第 1-65 行（load_turn、format_transcript）、gateway/rpc_diagnostics.py 第 1-50 行（RPC 接口）、gateway/diagnostics.py 第 1-120 行（DiagnosticsState）

回放功能提供只读的历史决策查询，绝不重新执行工具。支持三种查询维度，两种查询入口。

#### 11.1 ReplayAPI 按时间范围查询诊断日志

**大白话**：load_turn() 函数按会话 + 轮次查询特定决策记录。它遍历日志目录下所有 decisions-*.jsonl 文件（按文件名排序），逐行解析 JSON，找到匹配的 (session_key, turn_id) 后返回。不需要预先知道日志在哪一天——自动扫描所有日期的文件。

#### 11.2 按会话 ID 过滤特定会话的诊断

**大白话**：collect_bundle() 支持 session_id 参数，在收集 errors.jsonl 时按会话 ID 过滤数据库查询。SQL 查询同时匹配 session_key 和 session_id 两个字段，确保无论数据库用什么字段存储会话标识，都能查到。

源码位置：bundle.py 第 230-240 行。

#### 11.3 按诊断模式类型聚合统计

**大白话**：诊断事件中的 reason / event_name 字段标识了事件类型（如 repeated_failure_anchor、repeated_source_read_after_write、repeated_verification_without_diff_change、finish_error_with_non_empty_diff、edit_churn_after_failure）。通过解析运行时事件 JSONL 文件，按 reason 字段分组聚合，即可统计每种诊断模式的触发频率和趋势。

format_transcript() 函数将决策记录渲染为人类可读的文本，方便快速浏览。

#### 诊断状态管理（DiagnosticsState）

**源码位置**：gateway/diagnostics.py 第 1-120 行

**大白话**：DiagnosticsState 是网关级别的诊断开关状态管理器。它支持三层配置：配置文件中的 diagnostics_enabled（配置层）、运行时 diagnostics.set RPC 调用（运行时层）、以及环境变量覆盖（环境层）。优先级：环境变量 > 运行时设置 > 配置文件。
