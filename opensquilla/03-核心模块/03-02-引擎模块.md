# 03-02 · 引擎模块（Engine）— 大白话版

> **模块规模**：43 个核心代码文件 | **核心大脑**：AI 代理（约 500 行核心主循环） | **代码关系图谱**：458 个依赖它的调用方 | **代码分析工具扫描**：45 个关键符号（跨 2 个文件）

---

## 定位

引擎是 OpenSquilla 的**大脑**。它不只是一个"调用 AI 模型的循环"，而是一个包含 14 个子系统的精密状态机（程序在有限个状态间按规则切换的运行模型），每个子系统解决一个具体的工程问题。

---

## 生活化比喻

> 引擎像一个**自动驾驶系统**。不是简单的"踩油门→到目的地"，而是：
> - **导航规划**：看地图、查路况、规划路线
> - **燃油管理**：还剩多少油？够不够到目的地？要不要中途加油？
> - **车型选择**：市区道路开小车（便宜模型），高速公路开大车（贵模型）
> - **故障应对**：轮胎爆了怎么办？换备胎（切换模型）继续走
> - **多任务并行**：主驾驶开车，副驾驶查导航（子代理）
> - **安全校验**：每次变道后确认安全
> - **死循环检测**：如果一直在绕圈，强制结束

## 一、AI 代理的状态机（6 个状态）

AI 代理是一个**显式状态机**，每个对话回合都会经历以下生命周期：

```
空闲 ──▶ 思考中 ──▶ 逐字输出中 ──▶ 完成
                │                      ▲
                │         ┌────────────┘
                ▼         │
           调用工具中 ────┘
                │
                ▼
              出错 ──▶ 故障回退策略：应该重试吗？ ──▶ 思考中 (重试/切换模型)
```

| 状态 | 含义 | 触发条件 |
|------|------|---------|
| 空闲 | 等待用户输入 | 对话初始化 |
| 思考中 | 调用 AI 模型，等待模型返回 | 收到用户消息 / 工具结果返回 |
| 逐字输出中 | AI 正在逐字输出文本 | AI 开始返回文本内容 |
| 调用工具中 | AI 决定调用工具 | AI 决定要搜网页、读文件等 |
| 完成 | 本轮回答完成 | AI 返回完成信号 / 达到最大循环次数 |
| 出错 | 出错了 | 网络错误、模型拒绝、工具崩溃 |

## 二、对话回合执行管线——一条消息的完整旅程

当用户发送一条消息（"帮我写一个排序函数"），这个消息不会直接丢给 AI。它要先经过 **对话回合执行器**（整个引擎的"总指挥"）的 8 个阶段流水线处理，每个阶段负责一个独立的职责。所有入口（网页、命令行、频道）最终都汇聚到这里。

### 8 个阶段的处理顺序

```
用户消息
   │
   ▼
┌─ 阶段 1：输入规范化 ─────────────────────────────────────────────┐
│ 把来自不同入口的消息统一成内部格式，识别消息类型（文本/图片/文件）  │
└──────┬─────────────────────────────────────────────────────────────┘
       ▼
┌─ 阶段 2：AI 提供商 + 工具准备 ────────────────────────────────────┐
│ 选择 AI 服务商，构建工具列表（30+ 个工具），为每个工具绑定权限处理   │
└──────┬─────────────────────────────────────────────────────────────┘
       ▼
┌─ 阶段 3：提示词组装 ──────────────────────────────────────────────┐
│ 拼装身份提示词 + 用户规则 + 工作区规则，加载技能、注入记忆           │
└──────┬─────────────────────────────────────────────────────────────┘
       ▼
┌─ 阶段 4：AI 代理初始化 ───────────────────────────────────────────┐
│ 解析上下文预算（还剩多少"思考空间"），构建配置，启动 AI 代理         │
└──────┬─────────────────────────────────────────────────────────────┘
       ▼
┌─ 阶段 5：压缩 + 历史加载 ─────────────────────────────────────────┐
│ 检查是否需要压缩旧对话，加载历史记录，追加用户消息                   │
└──────┬─────────────────────────────────────────────────────────────┘
       ▼
┌─ 阶段 6：附件处理 ────────────────────────────────────────────────┐
│ 解析用户上传的图片/文件，下载到本地，注入到对话中                    │
└──────┬─────────────────────────────────────────────────────────────┘
       ▼
┌─ 阶段 7：AI 流式消费 ─────────────────────────────────────────────┐
│ 调用 AI 模型 → 逐字输出 → 解析工具调用 → 执行工具 → 循环            │
└──────┬─────────────────────────────────────────────────────────────┘
       ▼
┌─ 阶段 8：回合收尾 ────────────────────────────────────────────────┐
│ 证据检查 → 差异验证 → 死循环检测 → 归档结果                         │
└────────────────────────────────────────────────────────────────────┘
```

### 每个阶段做了什么

**阶段 1 — 输入规范化**：把来自不同入口（网页、命令行、频道）的消息统一成内部格式。识别消息类型（文本/图片/文件）、提取附件引用、判断是否是系统事件（心跳、定时任务触发）。

**阶段 2 — AI 提供商 + 工具准备**：根据路由器决策结果选择 AI 服务商，然后构建工具定义列表，为每个工具绑定权限处理器。

**阶段 3 — 提示词组装**：拼接系统提示词（身份提示词 + 用户规则 + 工作区规则），加载技能、注入记忆、配置路由。

**阶段 4 — AI 代理初始化**：解析上下文预算（还剩多少"思考空间"），构建配置（100+ 个配置项），启动 AI 代理对象，注入故障回退、子代理管理等依赖。

**阶段 5 — 压缩 + 历史加载**：检查是否需要压缩（精简旧对话），加载历史消息，追加用户消息和附件。

**阶段 6 — 附件处理**：解析用户上传的图片/文件，下载到本地，生成图片块或文件块，注入到消息列表中。

**阶段 7 — AI 流式消费**：这是核心循环所在——调用 AI 模型的聊天方法，逐字接收流式输出，解析工具调用，执行工具，收集结果，循环直到 AI 返回"完成"或达到最大循环次数。

**阶段 8 — 回合收尾**：证据检查确认写入无误，差异验证比对实际改动和预期，死循环检测防止无限修改，最后归档回合结果。

> ⚠️ **注意**：证据检查（`finalize_evidence_gate`）和死循环检测（`post_write_convergence`）是 **opt-in 功能，默认关闭**。需要在配置中设置 `finalize_evidence_gate_enabled = true` 和 `post_write_convergence_enabled = true` 才会运行。详见下方 §八、§九 的补充说明。

## 三、AI 代理核心循环——思考 → 行动 → 再思考

AI 代理不只是"调用一次 AI 就结束"。它是一个**循环**：每次 AI 返回后，如果发现有工具调用，就执行工具、收集结果、再调一次 AI，直到 AI 说"我完成了"。

### 循环的 6 个步骤

```
┌──────────────────────────────────────────────────────────────────┐
│                    AI 代理核心循环（每轮对话）                     │
│                                                                  │
│  步骤 1：空闲 → 收到用户消息                                       │
│     │                                                            │
│     ▼                                                            │
│  步骤 2：思考中 → 预算检查器检查还剩多少"思考空间"                  │
│     │   ├─ 空间不足 → 触发压缩 → 腾出空间后重试                    │
│     │   └─ 空间充足 → 继续                                        │
│     ▼                                                            │
│  步骤 3：调用 AI 模型（发送消息列表 + 配置）                        │
│     │   └─ 流式接收 AI 返回的事件（文字/工具调用/完成）             │
│     ▼                                                            │
│  步骤 4：逐字输出中 → 逐字输出文本给用户                            │
│     │   └─ 遇到工具调用 → 切换到调用工具状态                       │
│     ▼                                                            │
│  步骤 5：调用工具中 → 解析工具名 + 参数                             │
│     │   ├─ 安全检查（沙箱策略）                                     │
│     │   ├─ 审批门控（危险操作需确认）                                │
│     │   ├─ 执行工具（搜网页/读文件/执行命令...）                    │
│     │   └─ 收集结果 → 追加到对话 → 回到步骤 2                      │
│     ▼                                                            │
│  步骤 6：完成 → AI 返回完成信号                                     │
│     │   ├─ 证据检查确认写入结果（⚠️ 默认关闭，需手动开启）            │
│     │   ├─ 死循环检测防止无限修改（⚠️ 默认关闭，需手动开启）          │
│     │   └─ 归档回合，返回结果给用户                                 │
│                                                                  │
│  出错时：出错 → 故障回退策略判断是否重试 → 重试/切换模型            │
└──────────────────────────────────────────────────────────────────┘
```

### 大白话解释

**步骤 1（空闲 → 思考中）**：AI 本来在"空闲"状态，收到用户消息后切换到"思考中"状态。

**步骤 2（预算检查）**：上下文预算管理器像一个"油箱表"——检查还剩多少"思考空间"。如果不够，先触发压缩（精简历史对话），腾出空间再继续。

**步骤 3（调用 AI）**：把组装好的消息列表（系统提示词 + 历史对话 + 用户消息 + 工具定义）发给 AI，流式接收响应。

**步骤 4（流式输出）**：AI 的回复逐字出现在屏幕上。如果 AI 说"我要调用工具 read_file"，就暂停输出，切换到工具调用模式。

**步骤 5（工具调用）**：先过安检（安全检查），再确认是否需要审批（危险操作），然后执行工具，把结果追加到对话中，回到步骤 2 让 AI 继续思考。

**步骤 6（完成）**：AI 说"我完成了"，提交完成信号。AI 代理做最后的检查（证据检查、死循环检测——⚠️ 两者默认关闭，需手动开启），确认没问题后返回结果。

## 四、故障回退策略——出错时怎么办

AI 调用不是每次都成功。网络超时、服务限流、模型过载……这些都很常见。故障回退策略是 OpenSquilla 的"容错机制"——出错后自动重试、切换备用模型。

### 回退循环的 5 个步骤

```
步骤 1：AI 调用失败（网络错误 / 超时 / 空响应）
   │
   ▼
步骤 2：错误分类
   │   ├─ 根据错误码和错误信息查表匹配
   │   └─ 输出：13 种标准错误类型之一
   │
   ▼
步骤 3：决定恢复动作
   │   ├─ 被限流了 → 等一会儿再试
   │   ├─ 服务器过载 → 先重试，不行再切换
   │   ├─ 上下文太长 → 压缩后重试
   │   ├─ 密钥错误 → 直接失败，需要用户修改配置
   │   ├─ 网络抖动 → 重试
   │   └─ 其他 → 切换备用模型 / 告知用户 / 直接失败
   │
   ▼
步骤 4：判断是否可重试
   │   ├─ 重试次数 >= 最大重试次数(3) → 不重试
   │   ├─ 错误类型不可重试（密钥错误）→ 不重试
   │   └─ 可重试 → 继续
   │
   ▼
步骤 5：等待一会儿再试（指数退避）
   │   ├─ 第 1 次重试：等约 1 秒
   │   ├─ 第 2 次重试：等约 2 秒
   │   ├─ 第 3 次重试：等约 4 秒
   │   └─ 最长等待：30 秒
   │
   ▼
   回到步骤 2（重试 AI 调用，或切换到备用模型列表中的下一个）
```

### 13 种错误类型对照表

| 错误类型 | 大白话 | 恢复动作 |
|---------|--------|---------|
| 被限流 | 调用太频繁，被限制了 | 等一会儿再试 |
| 服务器过载 | 服务商的服务器忙不过来了 | 先重试，不行再切换 |
| 上下文太长 | 对话内容超出模型处理范围 | 压缩后重试 |
| 网络抖动 | 网络不稳定，暂时超时 | 重试 |
| 密钥无效 | 密钥错了 | 直接失败（不重试） |
| 模型不存在 | 指定的模型名找不到 | 切换备用模型 |
| 余额不足 | 账户没钱了 | 告知用户 |
| 内容被拒 | 内容被安全策略拦截 | 告知用户 |
| 空响应 | 模型返回了空内容 | 重试 |
| 响应格式错误 | 返回的内容格式不对 | 先重试，不行再切换 |
| 请求参数错误 | 请求格式有问题 | 直接失败 |
| 功能不支持 | 模型不支持这个功能 | 切换备用模型 |
| 未知错误 | 不知道什么原因 | 告知用户 |

## 五、上下文预算管理器

**问题**：AI 的"记忆窗口"有限（比如一次最多处理 128K 个词元），对话太长会超出预算。怎么决定什么时候该精简旧对话？

**解决方案**：上下文预算管理器根据模型窗口大小计算各项预算。

### 内部算法（7 步）

```
输入：模型能处理的最大词元数（如 128K）

步骤 1：计算输出预留上限
	  预留上限 = 窗口词元数 // 2（即最多一半窗口给输出+思考）
	  实际输出预留 = min(max_output_tokens + thinking_budget_tokens, 预留上限)

步骤 2：计算上下文预留量
  大窗口模型（≥64K）预留 20K 词元
  小窗口模型预留 1/8

步骤 3：计算总预留量
  总预留量 = 输出预留 + 上下文预留

步骤 4：计算可用预算
  可用预算 = 最大词元数 - 总预留量

步骤 5：计算溢出阈值
  默认 85%，当输入词元 / 可用预算 > 85% 时触发精简

步骤 6：分类上下文预算（6 种类型）
  外部数据 / 本地文件 / 生成产物 / 错误信息 / 系统控制 / 未知
  不同类型有不同的最大字符数限制

步骤 7：输出预算快照
  记录窗口大小、预留量、可用量、阈值等信息
```

### 6 种上下文预算分类

| 分类 | 含义 | 限制 |
|------|------|------|
| 外部 | 来自外部工具的结果（搜网页、抓取网页） | 小窗口：4K-32K 字符，大窗口：64K-512K 字符 |
| 本地 | 本地文件读取结果 | 默认限制 |
| 产物 | AI 生成的文件 | 特殊处理 |
| 错误 | 工具错误信息 | 限制较小 |
| 控制 | 系统控制消息 | 不受限 |
| 未知 | 未分类（默认） | 默认限制 |

## 六、故障回退策略详解

**问题**：AI 提供商可能挂掉（限流、超载、网络抖动），怎么保证服务不中断？

**解决方案**：故障回退策略实现了自动重试 + 模型切换。

### 内部逻辑（6 步）

```
步骤 1：错误分类
  输入：错误消息 + 提供商名 + 状态码
  输出：标准错误类型

步骤 2：判断是否可重试
  可重试的类型：
    被限流 — 等一会儿再试
    服务器超载 — 等一会儿
    网络抖动 — 重试
    上下文溢出 — 压缩后重试
  不可重试的类型：
    密钥错误 — 重试没用
    请求格式错误 — 重试没用
    模型拒绝回答 — 重试没用
    模型不存在 — 重试没用

步骤 3：等待一会儿再试（指数退避）
  公式：等待时间 = 基础时间 × (2 ^ 重试次数) + 随机抖动
  默认：基础 1 秒，最长 30 秒
  第 1 次重试：约 1.5 秒，第 2 次：约 3 秒，第 3 次：约 6 秒

步骤 4：切换备用模型
  从备用模型列表中按顺序切换
  如果当前模型不在列表中，用第一个
  如果全部用完，返回无可用模型

步骤 5：自动切换包装器
  运行时在 AI 提供商外层包装，自动处理切换
  记录每次切换（健康账本跟踪）

步骤 6：最大重试次数
  默认最多重试 3 次，超过后放弃
```

## 七、子代理管理

**问题**：复杂任务需要并行处理多个子任务（如同时搜索多个资料源），怎么管理？

**解决方案**：子代理管理器管理子代理的完整生命周期。

### 核心数据结构

| 部件 | 作用 | 关键字段 |
|---|------|---------|
| 子代理启动参数 | 定义子代理的启动配置 | 任务描述、模型、超时时间(300秒)、最大循环次数、工作目录 |
| 子代理运行句柄 | 运行中子代理的引用 | 运行编号、任务名、状态、结果、错误信息 |
| 子代理注册表 | 管理活跃和已归档的子代理 | 运行列表、归档列表、父任务记录 |

### 生命周期（8 步）

```
步骤 1：深度检查
  当前嵌套深度 >= 最大生成深度？拒绝生成
  防止无限递归生成子代理

步骤 2：并发检查
  活跃子代理数 >= 限制？等待或拒绝

步骤 3：创建子代理
  创建后台任务运行子代理
  注册到注册表
  记录父任务（用于孤儿检测）

步骤 4：状态跟踪
  状态：运行中 | 完成 | 出错 | 中止 | 已归档 | 孤儿

步骤 5：超时控制
  默认 300 秒超时

步骤 6：孤儿清理
  父任务已完成但子代理仍在运行 → 自动中止
  遍历父任务列表，检查父任务是否已完成

步骤 7：状态持久化
  保存为可读格式（不含运行中的任务对象）
  保存运行编号、任务名、状态、结果、错误、创建时间、完成时间

步骤 8：状态恢复
  从持久化数据恢复，所有恢复的句柄标记为"孤儿"
```

## 八、写入后证据检查 ⚠️（opt-in 功能，默认关闭）

> **重要**：此功能默认关闭。源码 `engine/types.py` 中 `finalize_evidence_gate_enabled: bool = False`。需要在 gateway 配置中设置 `[prompt] finalize_evidence_gate = true` 才会运行。

**问题**：AI 写了一个文件，但写的内容对不对？有没有产生错误？

**解决方案**：写入后证据跟踪器跟踪每次写入和执行，在回合结束时判断是否需要"追问"AI。

### 内部逻辑（9 步）

```
步骤 1：观察写入
  记录：文件路径、是否出错、循环次数
  判断：如果是中间产物文件 → 注册为"产物"（不重置执行窗口）
         如果是临时笔记 → 忽略
         其他写入 → 标记"已编辑源码"，重置执行计数

步骤 2：观察执行
  记录：命令、是否失败、退出码、是否超时、失败原因
  过滤：非验证类操作 → 跳过
         命令格式错误 → 跳过
         运行时暂存了 → 跳过

步骤 3：红色证据收集
  记录：失败命令、失败退出码、是否超时
  收集失败线索（最多 5 个）
  收集失败产物路径

步骤 4：构建观察结果
  输出：触发原因、失败命令、失败退出码、是否超时、
        失败线索、失败产物路径、执行计数、失败计数等

步骤 5：触发判断
  如果触发原因非空 → 触发追问

步骤 6：追问消息生成
  如果触发 → 生成一条追问消息，要求 AI 解释/修复
  追问有次数限制

步骤 7：追问后重试
  AI 收到追问消息后重新进入思考状态
  最多追问有限次数

步骤 8：门控键生成
  基于执行工具名和写入工具名生成唯一键
  用于跨回合追踪

步骤 9：记录与清理
  记录所有证据到事件日志
  清理临时产物
```

## 九、写入后死循环检测 ⚠️（opt-in 功能，默认关闭）

> **重要**：此功能默认关闭。源码 `engine/types.py` 中 `post_write_convergence_enabled: bool = False`。需要在 gateway 配置中设置 `[prompt] post_write_convergence = true` 才会运行。

**问题**：AI 在写代码模式下可能陷入"改了又改、验证→再改→再验证"的死循环，文件改动已经稳定了但 AI 还在继续。

**解决方案**：写入后收敛检测器检测稳定状态并强制结束。

### 内部状态机（4 态）

```
观察 ──▶ 警告 ──▶ 强制结束
   │                    ▲
   └──▶ 重置 ◀──────────┘
```

### 详细逻辑（5 步）

```
步骤 1：观察
  输入：循环次数、AI 调用次数、文件写入次数、
        改动文件数、改动指纹（对改动内容计算的唯一标识）、改动路径、
        是否验证成功、验证后是否继续活动

步骤 2：资格检查
  条件（全部满足才触发）：
    有文件被改动
    改动指纹非空
    改动路径非空
    验证成功过
    验证后继续活动

步骤 3：指纹变化检测
  如果改动指纹变了 → 重置（新一轮修改）
  如果改动指纹不变 → 稳定计数 +1

步骤 4：警告
  条件：稳定计数 >= 警告阈值（默认 3）且未警告过
  动作：在上下文中插入警告消息

步骤 5：强制结束
  条件：稳定计数 >= 警告触发时的计数 + 强制结束阈值（默认 3）
  动作：强制结束当前回合
```

## 十、上下文压缩

**问题**：长对话（如 50 轮）超出 AI 处理窗口，怎么精简旧内容？

**解决方案**：压缩配置 + 压缩函数

### 压缩算法（6 步）

```
步骤 1：触发判断
  触发条件：输入词元 / 可用预算 > 阈值（默认 85%）
  触发类型：词元预算不足 | 消息数量太多 | 手动触发

步骤 2：配置构建
  从 AI 提供商读取模型配置：
    每块占比：40%（每块占 40% 窗口）
    最小块：15%
    安全系数：1.2
    默认分块数：2
    保留策略：严格保留关键标识
    超时时间：90 秒

步骤 3：分块处理
  将历史消息按比例分块

步骤 4：AI 压缩
  每块发送给 AI 生成摘要
  保留关键信息：命令、路径、标识符、错误标记、产物名、决策前缀

步骤 5：关键信息提取
  提取必须保留的关键信息类型：
    命令 / 路径 / 标识符 / 错误 / 产物 / 决策
  这些关键信息确保压缩后不丢失重要上下文

步骤 6：结果组装
  摘要：压缩后的精简内容
  保留消息：尾部保留的消息
  移除数量：被压缩的消息数
  压缩前后词元数对比
  覆盖状态：压缩是否完整
  缺失的关键信息
  必须保留的关键信息
```

## 十五、编码模式（Coding Mode）

**定位**：编码模式是 OpenSquilla 的一个**操作员开关**——不是自动检测你是否在写代码，而是你手动开启后，系统会强制采用一套"代码任务安全流程"。

### 编码模式做了什么

| 变化 | 正常模式 | 编码模式 |
|------|---------|---------|
| 模型选择 | 路由器自动选择（R0~R3） | **锁定 deepseek-v4-pro**（路由被绕过） |
| 文件写入 | 允许 `write_file`、`edit_file` | **禁用**，强制走 `code-task` |
| 代码提交 | 允许 `git_commit` | **禁用** |
| 核心指令 | 无特殊指令 | 注入 `code-task solve` 指令 |

### 为什么要这样设计？

编码模式的设计理念是**安全 > 效率**。它强制 AI 通过 `code-task` 子代理来改代码，而不是直接编辑文件。`code-task` 子代理内部有完整的红→绿验证流程（写测试 → 跑测试 → 确认通过 → 提交），避免 AI 直接改文件可能引入的 bug。

### 编码模式对系统的影响

**1. 路由被绕过**：编码模式通过 `router_control` 的 `set_hold` 机制锁定模型为 `tier:c1`（deepseek-v4-pro）。这意味着：
- 简单问题也在用 deepseek-v4-pro（本来应该用 flash）
- 路由器的 8 维度特征提取、8 条安全规则全部不参与决策
- 日志中只有 `resolve_model.applied`，没有 `squilla_router.routed`

**2. 工具被过滤**：编码模式下以下 9 个工具被 `tool_filtered` 拒绝（源码 `tools/policy_config.py` 中的 `CODING_MODE_DENIED_TOOLS`）：
- `write_file`、`edit_file`、`apply_patch`（禁止直接写文件）
- `execute_code`（禁止直接执行 Python 代码）
- `git_commit`（禁止直接提交代码）
- `create_csv`、`create_xlsx`、`create_pdf_report`、`create_pptx`（禁止直接生成文件）

**3. 缓存稳定**：因为模型锁定，system prompt 和 tools 定义不变，缓存命中率反而更高（83%）。

### 实际运行数据

从实际日志中，编码模式触发了 201 次 `coding_mode.enforced`。每次开启编码模式的 turn 都会注入 `code-task` 指令。

### 源码对应

- `engine/steps/coding_mode.py`：编码模式的核心逻辑
- `engine/types.py` 中的 `coding_mode_enabled` 标志
- 源码注释明确说明："Coding mode is an UNCONDITIONAL operator toggle, not an intent classifier."

## 十六、上下文预算实际运行数据

**问题**：文档描述了上下文预算的 7 步算法，但实际运行时预算设置是否合理？压缩是否在预期时机触发？

### 实际日志数据

从实际运行日志（5,892 次 API 请求）中提取：

| 指标 | 数值 | 说明 |
|------|:---:|------|
| proof_budget（预算上限） | 2,896,800 chars | 约 724K tokens |
| effective_budget（实际可用） | 2,880,416 chars | 扣掉 10% 安全余量 |
| 实际消息最大尺寸 | 1,189,414 chars | 最高利用率 41% |
| fits=True | 5,894 / 5,894 次 | **100% 的请求从未突破预算** |
| compact_needed=True | 210 / 5,894 次 | 仅 3.6% 触发压缩 |
| budget_limited | 0 次 | 从未触发"预算不足"路径 |
| 预算利用率（最高） | 41% | 1.19M / 2.88M |

### 结论

**预算设置过于宽松**。2.88M chars 的预算上限，实际消息最大只有 1.19M chars，利用率最高 41%。这意味着：
- 压缩机制几乎形同虚设（仅 3.6% 的请求触发压缩）
- 文档描述的"空间不足 → 触发压缩 → 腾出空间后重试"路径从未触发
- 压缩只在 `compact_needed=True` 时触发，且都是 tier-0/1/2 的轻量压缩（裁剪工具参数、压缩尾部），真正的硬截断（tier-3/4）从未触发

### 为什么预算这么大？

预算来自模型的实际上下文窗口。deepseek-v4-pro 的窗口是 128K tokens，按 1 char ≈ 0.25 token 估算，实际 budget 约 724K tokens。但系统只用了最多 300K tokens，剩下的 400K+ tokens 是空闲的。

**这不是 bug，但说明预算管理器在当前配置下几乎没有发挥作用。**

  |------|-----------|------|
  | `write_file` | 编码模式 | 禁止直接写文件 |
  | `edit_file` | 编码模式 | 禁止直接编辑文件 |
  | `apply_patch` | 编码模式 | 禁止直接打补丁 |
  | `execute_code` | 编码模式 | 禁止直接执行 Python 代码 |
  | `git_commit` | 编码模式 | 禁止直接提交代码 |
  | `create_csv` | 编码模式 | 禁止直接生成 CSV |
  | `create_xlsx` | 编码模式 | 禁止直接生成 Excel |
  | `create_pdf_report` | 编码模式 | 禁止直接生成 PDF |
  | `create_pptx` | 编码模式 | 禁止直接生成 PPTX |
  | `image_generate` | owner_full 策略 | 禁止直接生成图片（非编码模式，是策略拒绝） |

  > **源码验证**：`tools/policy_config.py` 中 `CODING_MODE_DENIED_TOOLS = frozenset({"write_file", "edit_file", "apply_patch", "execute_code", "git_commit", "create_csv", "create_pdf_report", "create_pptx", "create_xlsx"})`。`image_generate` 不在其中，由 `owner_full` 策略而非编码模式拒绝。

### 对 AI 行为的影响

被拒绝的工具不会出现在 AI 的工具列表中，AI 看不到它们，也就不会尝试调用。这迫使 AI 通过 `code-task` 子代理来间接完成这些操作。

### 源码对应

- `engine/steps/tool_policy.py`：工具策略配置
- `tools/policy_config.py`：工具策略配置定义
- `tools/visibility.py`：工具可见性过滤（`tool_filtered` 事件）

## 二十、Turn Policy（循环迭代控制）

每次 AI 对话回合，系统需要决定"AI 最多可以调用多少次工具（迭代次数）"。这个上限由 `turn_policy.py` 的 **5 级优先级链** 决定：

| 优先级 | 来源 | 说明 |
|:---:|------|------|
| 1 | 显式参数 | 调用方直接传入的 `max_iterations` |
| 2 | 会话配置 | 当前会话的 `agent_max_iterations` 设置 |
| 3 | 环境变量 | `OPENSQUILLA_AGENT_MAX_ITERATIONS` |
| 4 | 网关配置 | `gateway_config.agent_max_iterations` |
| 5 | `AgentConfig` 默认值 | 硬编码的兜底默认值 |

**优先级逻辑**：从 1 到 5 依次检查，第一个非空的有效值直接生效，后面的不再检查。

**源码位置**：`engine/turn_policy.py` 的 `resolve_turn_policy()` 函数。

## 二十一、Compaction Control（压缩后继续决策）

压缩完成后，系统需要决定"接下来怎么办"。`compaction_control.py` 定义了 **6 种继续/终止决策**：

| 决策 | 含义 | 触发条件 |
|------|------|---------|
| `continue_after_compaction` | 继续执行 | 压缩成功，prompt 确实变小了 |
| `retry_after_compaction` | 再压缩一次 | prompt 没变小，但还有重试次数 |
| `degraded_continue` | 降级继续 | 语义 flush 失败但 raw session 是持久的 |
| `partial_after_compaction` | 部分完成 | 重试耗尽，需要 finalization |
| `failed_after_compaction` | 失败 | finalization 也失败了 |
| `blocked_after_compaction` | 阻止继续 | 上下文无法挽救或 receipt 不安全 |

**决策逻辑**：`decide_compaction_continuation()` 接收 7 个布尔参数（`receipt_safe`, `raw_session_durable`, `semantic_flush_ok`, `prompt_changed`, `finalization_attempted`, `context_unsalvageable`），按优先级顺序判断。

**源码位置**：`engine/compaction_control.py`。

## 二十二、用量追踪（Usage Tracking）

引擎通过 `usage.py` 跟踪每个会话的 token 消耗和费用：

### 数据结构

| 类 | 作用 |
|------|------|
| `ModelUsage` | 单个模型的用量：input/output tokens、cache read/write、billed_cost |
| `SessionUsage` | 整个会话的聚合：按模型拆分、按 deployment 拆分 |
| `UsageTracker` | 全局追踪器：`add()` 记录用量，`get()` 查询，`checkpoint()` 做快照 |
| `SessionTotalsSnapshot` | 某个时间点的总用量快照 |

### 费用计算

费用分为两部分：
- **billed_cost**：Provider 直接返回的账单金额（来源可信）
- **unbilled_estimate**：Provider 没返回账单时，用定价表估算

每个模型有三种费用来源标记：
- `provider_billed`：全部有账单
- `opensquilla_estimate`：全部靠估算
- `mixed`：部分有账单、部分估算

**源码位置**：`engine/usage.py`。

## 二十六、Fallback Policy（故障回退策略）

`fallback.py` 定义了独立的 `FallbackPolicy` 类：

| 属性 | 默认值 | 说明 |
|------|:---:|------|
| `max_retries` | 3 | 最大重试次数 |
| `base_backoff_ms` | 1000 | 基础退避时间（1 秒） |
| `max_backoff_ms` | 30000 | 最大退避时间（30 秒） |

**可重试的错误类型**（只有这 4 种会重试）：
- `RATE_LIMITED`：被限流
- `PROVIDER_OVERLOADED`：提供商过载
- `TRANSPORT_TRANSIENT`：网络瞬断
- `CONTEXT_OVERFLOW`：上下文溢出

**不可重试的错误**（AUTH_INVALID、MODEL_NOT_FOUND、UNSUPPORTED_FEATURE 等直接失败）。

**退避算法**：`base_ms * 2^attempt + random(0, base_ms/2)`，cap 在 `max_backoff_ms`。

**源码位置**：`engine/fallback.py`。

## 二十七、从属引擎子系统（完整清单）

以下子系统未在之前章节详细展开，此处给出完整覆盖：

### 1. 产物交付（`artifact_delivery.py`）

每次 AI 生成文件后，由产物交付系统负责验证和发布。核心约束：
- 文件大小上限（`DEFAULT_ARTIFACT_MAX_BYTES`）
- 磁盘总配额（`DEFAULT_ARTIFACT_DISK_BUDGET_BYTES`）
- PPTX 格式独立验证（`validate_artifact_for_delivery`）
- 文件名安全化处理（`_safe_filename`）

### 2. 斜杠命令注册表（`commands.py`）

统一管理所有交互界面（CLI、Web、频道）的斜杠命令。支持的 Surface：
- `WEB_CHAT`：网页聊天
- `CLI_GATEWAY`：网关 CLI
- `CLI_STANDALONE`：独立 CLI
- `CHANNEL`：频道适配器

### 3. 上下文组装（`context.py`）

定义 `ContextFiles` 数据类，从工作区加载引导文件：
- `SOUL.md` → `soul` 字段
- `IDENTITY.md` → `identity` 字段
- `USER.md` → `user` 字段
- `TOOLS.md` → `tools` 字段
- `MEMORY.md` → `memory` 字段

### 4. 回合结果分类（`outcome.py`）

定义 6 种回合结果：

| 类型 | 含义 |
|------|------|
| `completed` | 正常完成 |
| `partial` | 部分完成 |
| `budgetLimited` | 预算受限 |
| `blocked` | 被阻断 |
| `failed` | 失败 |
| `interrupted` | 被中断 |

10 种预算相关错误码（`_BUDGET_CODES`），包括 `current_turn_context_exhausted`、`provider_request_too_large`、`tool_run_budget_exhausted` 等。

### 5. 管线定义（`pipeline.py`）

`TurnContext` 数据类承载整个管线传递的上下文：消息、session_key、config、provider、model、tool_defs、system_prompt、metadata 等。每个 step 签名为 `TurnStep = Callable[[TurnContext], Awaitable[TurnContext]]`。

### 6. 进度看门狗（`progress_watchdog.py`）

`ProgressObservation` 记录每轮迭代的 20+ 个维度：迭代次数、工具成功/失败、文件写入数、receipt 变化数、scratch 写入数等。`ProgressAction` 三种状态：`observe`（观察）、`warn`（警告）、`block`（阻断）。

### 7. 思考/推理清理（`thinking.py`）

`drop_reasoning()` 跨提供商兼容：移除 Anthropic 的 `ContentBlockThinking` 块、清除 DeepSeek/OpenRouter 的 `reasoning_content` 字段。可选保留工具调用推理。

### 8. 会话写锁（`session_lock.py`）

`SessionWriteLock`：基于 `session_key` 的异步锁，防止同一会话的并发写入。每个 session 一个 `asyncio.Lock` 实例。

### 9. 会话清洗（`session_sanitize.py`）

构建干净的请求视图——移除 OpenSquilla 内部记账信息，只保留 AI 模型需要的内容块（text/tool_use/tool_result/image/document）。

### 10. 回合入口（`start_turn.py`）

`_turn_kwargs()` 统一构造回合参数：attachments、mode、run_kind、no_memory_capture、elevation_mode、reply_to 等。生成 `PipelineStepRecord` 记录 `start_turn_via_runtime`。

### 11. 流包装器（`stream_wrappers.py`）

4 种异步流包装器：
- `repair_json_stream`：修复 JSON 参数中的格式错误
- `idle_timeout_stream`：N 秒无事件触发超时
- `trim_tool_names_stream`：裁剪工具名中的空白
- `heartbeat_stream`：上游静默时发送心跳

### 12. 选择器覆写（`selector_override.py`）

统一应用模型覆写（路由模型 + 显式 per-turn 模型）。包含跨提供商凭证解析和 `_ROUTE_SAVINGS_KEYS`（savings_pct、savings_max_price_per_m、savings_routed_price_per_m）。

### 13. 用量记账（`usage_accounting.py`）

`UsageCallStart` 代表一次 `provider.chat` 调用。支持重试/回退/工具循环的独立 call index。ensemble 调用保持一个 envelope，内部 per-model items 可分别聚合。

### 14. HTTP 用量上报（`usage_http.py`）

处理非流式 `/chat/completions` 直接请求的用量记账。与 `usage_accounting.py` 共享 `UsageAccountingScope` 和 `UsageCallStart`。

### 15. 提权三态（`elevation_triage.py`）

`RuleAssessment` 输出 4 级风险：low/medium/high/critical。每个评估包含：风险等级、用户授权、allow/deny 结果、理由、是否可人工确认。

### 16. 最终差异合约（`final_diff_contract.py`）

`classify_final_diff_path()` 将文件路径分入 3 类：source、test-like、scratch。按 5 组正则模式匹配测试路径、scratch 路径、文档路径等。

### 17. 推理提示（`reasoning_hint.py`）

为推理模型注入格式提示：` thinking... response` 语法。识别模型家族：gpt-5、codex、glm-4.7、glm-4.6、deepseek-r1。

### 18. 路由决策事件（`router_decision.py`）

`RouterDecisionEvent` 构造：从 `TurnContext` 提取路由决策、概率分布、置信度门控、模型窗口解析等。

### 19. 运行时诊断（`runtime_diagnostics.py`）

`RuntimeDiagnosticsObserver` 观察者模式：提取工具调用结果的路径、分类、失败锚点。支持 4 种诊断模式：重复失败、重复读文件、空验证、未完成工作。

### 20. 运行时事件（`runtime_events.py`）

`append_runtime_event()`：JSONL 格式追加事件到指定路径。不阻塞 agent 控制流，失败时静默返回。

### 21. 运行时恢复（`runtime_recovery.py`）

3 种恢复模式：`off` / `log` / `warn_model`。2 种恢复动作：`prefill`（预填充推理）和 `nudge`（轻推继续）。`ReasoningPrefillRecoveryMode` 额外支持 `recover` 模式。

### 22. 运行时状态胶囊（`runtime_state_capsule.py`）

`build_runtime_state_capsule()`：构建当前工作区状态快照，包含 git diff 路径、source/test/scratch 分类、文档变更等。

### 23. 历史管理（`history.py`）

`_SYNTHETIC_USER_PREFIXES` 标记 4 种系统注入前缀：`[Available skills for this turn]`、`[Context summary]`、`[Request context for this turn]`、`[Runtime context for this turn]`。用于孤立的工具调用配对修复。

### 24. 补丁证据账本（`patch_evidence_ledger.py`）

`_MAX_TOOL_EVENTS=2000`、`_MAX_TEXT_CHARS=600`、`_MAX_FAILURE_ANCHORS=300` — 限制证据记录大小。支持文档路径模式匹配（`docs/**`、`doc/**` 等）。

### 25. 挂钩系统（`hooks/`）

3 个文件：
- `__init__.py`：钩子注册
- `defaults.py`：默认钩子实现
- `types.py`：钩子类型定义
