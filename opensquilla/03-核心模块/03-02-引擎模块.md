# 03-02 · 引擎模块（Engine）— 大白话版

> **模块规模**：43 个核心代码文件 | **核心大脑**：AI 代理（约 500 行核心主循环） | **代码关系图谱**：458 个依赖它的调用方 | **代码分析工具扫描**：45 个关键符号（跨 2 个文件）

---

## 定位

引擎是 OpenSquilla 的**大脑**。它不只是一个"调用 AI 模型的循环"，而是一个包含 14 个子系统的精密状态机（程序在有限个状态间按规则切换的运行模型），每个子系统解决一个具体的工程问题。

---

## 生活化比喻

> 引擎像一个**自动驾驶系统**。不是简单的"踩油门→到目的地"，而是：
> - **导航规划**：看地图、查路况、规划路线
> - **燃油管理**：还剩多少油？够不够到目的地？要不要中途加油？
> - **车型选择**：市区道路开小车（便宜模型），高速公路开大车（贵模型）
> - **故障应对**：轮胎爆了怎么办？换备胎（切换模型）继续走
> - **多任务并行**：主驾驶开车，副驾驶查导航（子代理）
> - **安全校验**：每次变道后确认安全
> - **死循环检测**：如果一直在绕圈，强制结束

## 一、AI 代理的状态机（6 个状态）

AI 代理是一个**显式状态机**，每个对话回合都会经历以下生命周期：

```
空闲 ──▶ 思考中 ──▶ 逐字输出中 ──▶ 完成
                │                      ▲
                │         ┌────────────┘
                ▼         │
           调用工具中 ────┘
                │
                ▼
              出错 ──▶ 故障回退策略：应该重试吗？ ──▶ 思考中 (重试/切换模型)
```

| 状态 | 含义 | 触发条件 |
|------|------|---------|
| 空闲 | 等待用户输入 | 对话初始化 |
| 思考中 | 调用 AI 模型，等待模型返回 | 收到用户消息 / 工具结果返回 |
| 逐字输出中 | AI 正在逐字输出文本 | AI 开始返回文本内容 |
| 调用工具中 | AI 决定调用工具 | AI 决定要搜网页、读文件等 |
| 完成 | 本轮回答完成 | AI 返回完成信号 / 达到最大循环次数 |
| 出错 | 出错了 | 网络错误、模型拒绝、工具崩溃 |

## 二、对话回合执行管线——一条消息的完整旅程

当用户发送一条消息（"帮我写一个排序函数"），这个消息不会直接丢给 AI。它要先经过 **对话回合执行器**（整个引擎的"总指挥"）的 8 个阶段流水线处理，每个阶段负责一个独立的职责。所有入口（网页、命令行、频道）最终都汇聚到这里。

### 8 个阶段的处理顺序

```
用户消息
   │
   ▼
┌─ 阶段 1：输入规范化 ─────────────────────────────────────────────┐
│ 把来自不同入口的消息统一成内部格式，识别消息类型（文本/图片/文件）  │
└──────┬─────────────────────────────────────────────────────────────┘
       ▼
┌─ 阶段 2：AI 提供商 + 工具准备 ────────────────────────────────────┐
│ 选择 AI 服务商，构建工具列表（30+ 个工具），为每个工具绑定权限处理   │
└──────┬─────────────────────────────────────────────────────────────┘
       ▼
┌─ 阶段 3：提示词组装 ──────────────────────────────────────────────┐
│ 拼装身份提示词 + 用户规则 + 工作区规则，加载技能、注入记忆           │
└──────┬─────────────────────────────────────────────────────────────┘
       ▼
┌─ 阶段 4：AI 代理初始化 ───────────────────────────────────────────┐
│ 解析上下文预算（还剩多少"思考空间"），构建配置，启动 AI 代理         │
└──────┬─────────────────────────────────────────────────────────────┘
       ▼
┌─ 阶段 5：压缩 + 历史加载 ─────────────────────────────────────────┐
│ 检查是否需要压缩旧对话，加载历史记录，追加用户消息                   │
└──────┬─────────────────────────────────────────────────────────────┘
       ▼
┌─ 阶段 6：附件处理 ────────────────────────────────────────────────┐
│ 解析用户上传的图片/文件，下载到本地，注入到对话中                    │
└──────┬─────────────────────────────────────────────────────────────┘
       ▼
┌─ 阶段 7：AI 流式消费 ─────────────────────────────────────────────┐
│ 调用 AI 模型 → 逐字输出 → 解析工具调用 → 执行工具 → 循环            │
└──────┬─────────────────────────────────────────────────────────────┘
       ▼
┌─ 阶段 8：回合收尾 ────────────────────────────────────────────────┐
│ 证据检查 → 差异验证 → 死循环检测 → 归档结果                         │
└────────────────────────────────────────────────────────────────────┘
```

### 每个阶段做了什么

**阶段 1 — 输入规范化**：把来自不同入口（网页、命令行、频道）的消息统一成内部格式。识别消息类型（文本/图片/文件）、提取附件引用、判断是否是系统事件（心跳、定时任务触发）。

**阶段 2 — AI 提供商 + 工具准备**：根据路由器决策结果选择 AI 服务商，然后构建工具定义列表，为每个工具绑定权限处理器。

**阶段 3 — 提示词组装**：拼接系统提示词（身份提示词 + 用户规则 + 工作区规则），加载技能、注入记忆、配置路由。

**阶段 4 — AI 代理初始化**：解析上下文预算（还剩多少"思考空间"），构建配置（100+ 个配置项），启动 AI 代理对象，注入故障回退、子代理管理等依赖。

**阶段 5 — 压缩 + 历史加载**：检查是否需要压缩（精简旧对话），加载历史消息，追加用户消息和附件。

**阶段 6 — 附件处理**：解析用户上传的图片/文件，下载到本地，生成图片块或文件块，注入到消息列表中。

**阶段 7 — AI 流式消费**：这是核心循环所在——调用 AI 模型的聊天方法，逐字接收流式输出，解析工具调用，执行工具，收集结果，循环直到 AI 返回"完成"或达到最大循环次数。

**阶段 8 — 回合收尾**：证据检查确认写入无误，差异验证比对实际改动和预期，死循环检测防止无限修改，最后归档回合结果。

## 三、AI 代理核心循环——思考 → 行动 → 再思考

AI 代理不只是"调用一次 AI 就结束"。它是一个**循环**：每次 AI 返回后，如果发现有工具调用，就执行工具、收集结果、再调一次 AI，直到 AI 说"我完成了"。

### 循环的 6 个步骤

```
┌──────────────────────────────────────────────────────────────────┐
│                    AI 代理核心循环（每轮对话）                     │
│                                                                  │
│  步骤 1：空闲 → 收到用户消息                                       │
│     │                                                            │
│     ▼                                                            │
│  步骤 2：思考中 → 预算检查器检查还剩多少"思考空间"                  │
│     │   ├─ 空间不足 → 触发压缩 → 腾出空间后重试                    │
│     │   └─ 空间充足 → 继续                                        │
│     ▼                                                            │
│  步骤 3：调用 AI 模型（发送消息列表 + 配置）                        │
│     │   └─ 流式接收 AI 返回的事件（文字/工具调用/完成）             │
│     ▼                                                            │
│  步骤 4：逐字输出中 → 逐字输出文本给用户                            │
│     │   └─ 遇到工具调用 → 切换到调用工具状态                       │
│     ▼                                                            │
│  步骤 5：调用工具中 → 解析工具名 + 参数                             │
│     │   ├─ 安全检查（沙箱策略）                                     │
│     │   ├─ 审批门控（危险操作需确认）                                │
│     │   ├─ 执行工具（搜网页/读文件/执行命令...）                    │
│     │   └─ 收集结果 → 追加到对话 → 回到步骤 2                      │
│     ▼                                                            │
│  步骤 6：完成 → AI 返回完成信号                                     │
│     │   ├─ 证据检查确认写入结果                                     │
│     │   ├─ 死循环检测防止无限修改                                   │
│     │   └─ 归档回合，返回结果给用户                                 │
│                                                                  │
│  出错时：出错 → 故障回退策略判断是否重试 → 重试/切换模型            │
└──────────────────────────────────────────────────────────────────┘
```

### 大白话解释

**步骤 1（空闲 → 思考中）**：AI 本来在"空闲"状态，收到用户消息后切换到"思考中"状态。

**步骤 2（预算检查）**：上下文预算管理器像一个"油箱表"——检查还剩多少"思考空间"。如果不够，先触发压缩（精简历史对话），腾出空间再继续。

**步骤 3（调用 AI）**：把组装好的消息列表（系统提示词 + 历史对话 + 用户消息 + 工具定义）发给 AI，流式接收响应。

**步骤 4（流式输出）**：AI 的回复逐字出现在屏幕上。如果 AI 说"我要调用工具 read_file"，就暂停输出，切换到工具调用模式。

**步骤 5（工具调用）**：先过安检（安全检查），再确认是否需要审批（危险操作），然后执行工具，把结果追加到对话中，回到步骤 2 让 AI 继续思考。

**步骤 6（完成）**：AI 说"我完成了"，提交完成信号。AI 代理做最后的检查（证据检查、死循环检测），确认没问题后返回结果。

## 四、故障回退策略——出错时怎么办

AI 调用不是每次都成功。网络超时、服务限流、模型过载……这些都很常见。故障回退策略是 OpenSquilla 的"容错机制"——出错后自动重试、切换备用模型。

### 回退循环的 5 个步骤

```
步骤 1：AI 调用失败（网络错误 / 超时 / 空响应）
   │
   ▼
步骤 2：错误分类
   │   ├─ 根据错误码和错误信息查表匹配
   │   └─ 输出：13 种标准错误类型之一
   │
   ▼
步骤 3：决定恢复动作
   │   ├─ 被限流了 → 等一会儿再试
   │   ├─ 服务器过载 → 先重试，不行再切换
   │   ├─ 上下文太长 → 压缩后重试
   │   ├─ 密钥错误 → 直接失败，需要用户修改配置
   │   ├─ 网络抖动 → 重试
   │   └─ 其他 → 切换备用模型 / 告知用户 / 直接失败
   │
   ▼
步骤 4：判断是否可重试
   │   ├─ 重试次数 >= 最大重试次数(3) → 不重试
   │   ├─ 错误类型不可重试（密钥错误）→ 不重试
   │   └─ 可重试 → 继续
   │
   ▼
步骤 5：等待一会儿再试（指数退避）
   │   ├─ 第 1 次重试：等约 1 秒
   │   ├─ 第 2 次重试：等约 2 秒
   │   ├─ 第 3 次重试：等约 4 秒
   │   └─ 最长等待：30 秒
   │
   ▼
   回到步骤 2（重试 AI 调用，或切换到备用模型列表中的下一个）
```

### 13 种错误类型对照表

| 错误类型 | 大白话 | 恢复动作 |
|---------|--------|---------|
| 被限流 | 调用太频繁，被限制了 | 等一会儿再试 |
| 服务器过载 | 服务商的服务器忙不过来了 | 先重试，不行再切换 |
| 上下文太长 | 对话内容超出模型处理范围 | 压缩后重试 |
| 网络抖动 | 网络不稳定，暂时超时 | 重试 |
| 密钥无效 | 密钥错了 | 直接失败（不重试） |
| 模型不存在 | 指定的模型名找不到 | 切换备用模型 |
| 余额不足 | 账户没钱了 | 告知用户 |
| 内容被拒 | 内容被安全策略拦截 | 告知用户 |
| 空响应 | 模型返回了空内容 | 重试 |
| 响应格式错误 | 返回的内容格式不对 | 先重试，不行再切换 |
| 请求参数错误 | 请求格式有问题 | 直接失败 |
| 功能不支持 | 模型不支持这个功能 | 切换备用模型 |
| 未知错误 | 不知道什么原因 | 告知用户 |

## 五、上下文预算管理器

**问题**：AI 的"记忆窗口"有限（比如一次最多处理 128K 个词元），对话太长会超出预算。怎么决定什么时候该精简旧对话？

**解决方案**：上下文预算管理器根据模型窗口大小计算各项预算。

### 内部算法（7 步）

```
输入：模型能处理的最大词元数（如 128K）

步骤 1：计算输出预留量
  预留一半窗口给模型输出+思考

步骤 2：计算上下文预留量
  大窗口模型（≥64K）预留 20K 词元
  小窗口模型预留 1/8

步骤 3：计算总预留量
  总预留量 = 输出预留 + 上下文预留

步骤 4：计算可用预算
  可用预算 = 最大词元数 - 总预留量

步骤 5：计算溢出阈值
  默认 85%，当输入词元 / 可用预算 > 85% 时触发精简

步骤 6：分类上下文预算（6 种类型）
  外部数据 / 本地文件 / 生成产物 / 错误信息 / 系统控制 / 未知
  不同类型有不同的最大字符数限制

步骤 7：输出预算快照
  记录窗口大小、预留量、可用量、阈值等信息
```

### 6 种上下文预算分类

| 分类 | 含义 | 限制 |
|------|------|------|
| 外部 | 来自外部工具的结果（搜网页、抓取网页） | 小窗口：4K-32K 字符，大窗口：64K-512K 字符 |
| 本地 | 本地文件读取结果 | 默认限制 |
| 产物 | AI 生成的文件 | 特殊处理 |
| 错误 | 工具错误信息 | 限制较小 |
| 控制 | 系统控制消息 | 不受限 |
| 未知 | 未分类（默认） | 默认限制 |

## 六、故障回退策略详解

**问题**：AI 提供商可能挂掉（限流、超载、网络抖动），怎么保证服务不中断？

**解决方案**：故障回退策略实现了自动重试 + 模型切换。

### 内部逻辑（6 步）

```
步骤 1：错误分类
  输入：错误消息 + 提供商名 + 状态码
  输出：标准错误类型

步骤 2：判断是否可重试
  可重试的类型：
    被限流 — 等一会儿再试
    服务器超载 — 等一会儿
    网络抖动 — 重试
    上下文溢出 — 压缩后重试
  不可重试的类型：
    密钥错误 — 重试没用
    请求格式错误 — 重试没用
    模型拒绝回答 — 重试没用
    模型不存在 — 重试没用

步骤 3：等待一会儿再试（指数退避）
  公式：等待时间 = 基础时间 × (2 ^ 重试次数) + 随机抖动
  默认：基础 1 秒，最长 30 秒
  第 1 次重试：约 1.5 秒，第 2 次：约 3 秒，第 3 次：约 6 秒

步骤 4：切换备用模型
  从备用模型列表中按顺序切换
  如果当前模型不在列表中，用第一个
  如果全部用完，返回无可用模型

步骤 5：自动切换包装器
  运行时在 AI 提供商外层包装，自动处理切换
  记录每次切换（健康账本跟踪）

步骤 6：最大重试次数
  默认最多重试 3 次，超过后放弃
```

## 七、子代理管理

**问题**：复杂任务需要并行处理多个子任务（如同时搜索多个资料源），怎么管理？

**解决方案**：子代理管理器管理子代理的完整生命周期。

### 核心数据结构

| 部件 | 作用 | 关键字段 |
|---|------|---------|
| 子代理启动参数 | 定义子代理的启动配置 | 任务描述、模型、超时时间(300秒)、最大循环次数、工作目录 |
| 子代理运行句柄 | 运行中子代理的引用 | 运行编号、任务名、状态、结果、错误信息 |
| 子代理注册表 | 管理活跃和已归档的子代理 | 运行列表、归档列表、父任务记录 |

### 生命周期（8 步）

```
步骤 1：深度检查
  当前嵌套深度 >= 最大生成深度？拒绝生成
  防止无限递归生成子代理

步骤 2：并发检查
  活跃子代理数 >= 限制？等待或拒绝

步骤 3：创建子代理
  创建后台任务运行子代理
  注册到注册表
  记录父任务（用于孤儿检测）

步骤 4：状态跟踪
  状态：运行中 | 完成 | 出错 | 中止 | 已归档 | 孤儿

步骤 5：超时控制
  默认 300 秒超时

步骤 6：孤儿清理
  父任务已完成但子代理仍在运行 → 自动中止
  遍历父任务列表，检查父任务是否已完成

步骤 7：状态持久化
  保存为可读格式（不含运行中的任务对象）
  保存运行编号、任务名、状态、结果、错误、创建时间、完成时间

步骤 8：状态恢复
  从持久化数据恢复，所有恢复的句柄标记为"孤儿"
```

## 八、写入后证据检查

**问题**：AI 写了一个文件，但写的内容对不对？有没有产生错误？

**解决方案**：写入后证据跟踪器跟踪每次写入和执行，在回合结束时判断是否需要"追问"AI。

### 内部逻辑（9 步）

```
步骤 1：观察写入
  记录：文件路径、是否出错、循环次数
  判断：如果是中间产物文件 → 注册为"产物"（不重置执行窗口）
         如果是临时笔记 → 忽略
         其他写入 → 标记"已编辑源码"，重置执行计数

步骤 2：观察执行
  记录：命令、是否失败、退出码、是否超时、失败原因
  过滤：非验证类操作 → 跳过
         命令格式错误 → 跳过
         运行时暂存了 → 跳过

步骤 3：红色证据收集
  记录：失败命令、失败退出码、是否超时
  收集失败线索（最多 5 个）
  收集失败产物路径

步骤 4：构建观察结果
  输出：触发原因、失败命令、失败退出码、是否超时、
        失败线索、失败产物路径、执行计数、失败计数等

步骤 5：触发判断
  如果触发原因非空 → 触发追问

步骤 6：追问消息生成
  如果触发 → 生成一条追问消息，要求 AI 解释/修复
  追问有次数限制

步骤 7：追问后重试
  AI 收到追问消息后重新进入思考状态
  最多追问有限次数

步骤 8：门控键生成
  基于执行工具名和写入工具名生成唯一键
  用于跨回合追踪

步骤 9：记录与清理
  记录所有证据到事件日志
  清理临时产物
```

## 九、写入后死循环检测

**问题**：AI 在写代码模式下可能陷入"改了又改、验证→再改→再验证"的死循环，文件改动已经稳定了但 AI 还在继续。

**解决方案**：写入后收敛检测器检测稳定状态并强制结束。

### 内部状态机（4 态）

```
观察 ──▶ 警告 ──▶ 强制结束
   │                    ▲
   └──▶ 重置 ◀──────────┘
```

### 详细逻辑（5 步）

```
步骤 1：观察
  输入：循环次数、AI 调用次数、文件写入次数、
        改动文件数、改动指纹（对改动内容计算的唯一标识）、改动路径、
        是否验证成功、验证后是否继续活动

步骤 2：资格检查
  条件（全部满足才触发）：
    有文件被改动
    改动指纹非空
    改动路径非空
    验证成功过
    验证后继续活动

步骤 3：指纹变化检测
  如果改动指纹变了 → 重置（新一轮修改）
  如果改动指纹不变 → 稳定计数 +1

步骤 4：警告
  条件：稳定计数 >= 警告阈值（默认 3）且未警告过
  动作：在上下文中插入警告消息

步骤 5：强制结束
  条件：稳定计数 >= 警告触发时的计数 + 强制结束阈值（默认 3）
  动作：强制结束当前回合
```

## 十、上下文压缩

**问题**：长对话（如 50 轮）超出 AI 处理窗口，怎么精简旧内容？

**解决方案**：压缩配置 + 压缩函数

### 压缩算法（6 步）

```
步骤 1：触发判断
  触发条件：输入词元 / 可用预算 > 阈值（默认 85%）
  触发类型：词元预算不足 | 消息数量太多 | 手动触发

步骤 2：配置构建
  从 AI 提供商读取模型配置：
    每块占比：40%（每块占 40% 窗口）
    最小块：15%
    安全系数：1.2
    默认分块数：2
    保留策略：严格保留关键标识
    超时时间：90 秒

步骤 3：分块处理
  将历史消息按比例分块

步骤 4：AI 压缩
  每块发送给 AI 生成摘要
  保留关键信息：命令、路径、标识符、错误标记、产物名、决策前缀

步骤 5：关键信息提取
  提取必须保留的关键信息类型：
    命令 / 路径 / 标识符 / 错误 / 产物 / 决策
  这些关键信息确保压缩后不丢失重要上下文

步骤 6：结果组装
  摘要：压缩后的精简内容
  保留消息：尾部保留的消息
  移除数量：被压缩的消息数
  压缩前后词元数对比
  覆盖状态：压缩是否完整
  缺失的关键信息
  必须保留的关键信息
```

## 十一、对话回合执行器管线

对话回合执行器是单个回合的完整执行管线，包含 4 个阶段：

| 阶段 | 职责 |
|------|------|
| 1. AI 代理初始化 | 启动 AI 代理、加载配置、注入工具、解析预算 |
| 2. 提示词组装 | 组装系统提示词 + 历史对话 + 工具定义 |
| 3. 执行管线 | 实际调用 AI 模型 |
| 4. 收尾 | 保存对话、记录用量、触发证据检查 |

## 十四、关键设计决策

| 设计点 | 说明 |
|--------|------|
| 500 行主循环 | 核心逻辑极简，复杂功能通过 14 个子模块组合 |
| 事件驱动架构 | 所有状态变更通过事件传递（10+ 种事件类型） |
| 子代理隔离 | 子代理有独立配置、受限工具集、独立用量追踪，深度限制防止无限递归 |
| 退避回退链 | 等待时间指数增长（1 秒→2 秒→4 秒→…→30 秒），模型列表轮转 |
| 证据检查 | 写入后必须验证，防止 AI"声称写入了但实际内容不对" |
| 死循环检测 | 稳定改动连续 3 轮不变→警告，6 轮不变→强制结束，防止死循环 |
| 缓存失效检测 | 检测 AI 缓存失效，自动触发压缩 |
| 提权三态 | 操作前自动评估是否需要提升权限 |
| 差异检查 | 最终输出与期望差异检查，比对实际改动和预期目标 |
| 工具结果压缩 | 大型工具结果超出限制时自动压缩，保留关键信息 |
