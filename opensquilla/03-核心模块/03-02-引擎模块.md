## 定位

引擎是 OpenSquilla 的**大脑**。它不只是一个"调用 LLM 的循环"，而是一个包含 14 个子系统的精密状态机，每个子系统解决一个具体的工程问题。

> 来源：`engine/agent.py` L5 "Agent core — explicit state machine + tool loop. Core loop is under 500 lines."

---

## 生活化比喻

> 引擎像一个**自动驾驶系统**。不是简单的"踩油门→到目的地"，而是：
> - **导航规划**（ContextAssembly）：看地图、查路况、规划路线
> - **燃油管理**（ContextBudgetGovernor）：还剩多少油？够不够到目的地？要不要中途加油？
> - **车型选择**（SquillaRouter）：市区道路开小车（便宜模型），高速公路开大车（贵模型）
> - **故障应对**（FallbackPolicy）：轮胎爆了怎么办？换备胎（切换模型）继续走
> - **多任务并行**（SubagentManager）：主驾驶开车，副驾驶查导航（子代理）
> - **安全校验**（FinalizeEvidenceGate）：每次变道（写入文件）后确认安全
> - **死循环检测**（PostWriteConvergenceTracker）：如果一直在绕圈（稳定 diff 不动），强制结束

## 二、ContextBudgetGovernor — 上下文预算管理器

**问题**：LLM 的上下文窗口有限（如 128K tokens），对话太长会超出预算。怎么决定什么时候该压缩？

**解决方案**：`ContextBudgetGovernor`（`context_budget.py:69`）根据模型窗口大小计算各项预算。

### 内部算法（7 步）

```
输入：模型上下文窗口大小 (context_window_tokens)
│
▼
步骤 1：计算输出预留 (output_reserve)
  output_reserve = min(max_output_tokens + thinking_budget_tokens, context_tokens // 2)
  大白话：预留一半窗口给模型输出+思考

步骤 2：计算上下文预留 (context_reserve)
  if context_tokens >= 64_000:  # LARGE_CONTEXT_MIN_TOKENS
      context_reserve = 20_000  # CONTEXT_RESERVE_FLOOR_TOKENS
  else:
      context_reserve = max(512, context_tokens // 8)
  大白话：大窗口预留 20K tokens，小窗口预留 1/8

步骤 3：计算总预留 (reserved_tokens)
  reserved_tokens = min(context_tokens - 1, output_reserve + context_reserve)

步骤 4：计算可用预算 (usable_tokens)
  usable_tokens = max(1, context_tokens - reserved_tokens)

步骤 5：计算溢出阈值 (threshold)
  threshold = clamp(配置值, 0.1, 0.95)，默认 0.85
  当输入 tokens / usable_tokens > threshold 时触发压缩

步骤 6：分类上下文预算 (ContextBudgetClass)
  EXTERNAL / LOCAL / ARTIFACT / ERROR / CONTROL / UNKNOWN
  不同类型有不同的最大字符数限制

步骤 7：输出 ContextBudgetSnapshot
  {context_window_tokens, reserved_tokens, usable_tokens, threshold,
   provider_request_max_chars, default_tool_argument_max_chars, ...}
```

### 6 种上下文预算分类

| 分类 | 枚举值 | 含义 | 限制 |
|------|--------|------|------|
| 外部 | `EXTERNAL` | 来自外部工具的结果（web_search, web_fetch） | SMALL: 4K-32K chars, LARGE: 64K-512K chars |
| 本地 | `LOCAL` | 本地文件读取结果 | 默认限制 |
| 产物 | `ARTIFACT` | 生成的文件产物 | 特殊处理 |
| 错误 | `ERROR` | 工具错误信息 | 限制较小 |
| 控制 | `CONTROL` | 系统控制消息 | 不受限 |
| 未知 | `UNKNOWN` | 未分类（默认） | 默认限制 |

> 来源：`context_budget.py` L9-L17（常量）, L20-L26（枚举）, L69-L149（Governor 类）

## 三、FallbackPolicy — 故障回退策略

**问题**：AI 提供商可能挂掉（限流、超载、网络抖动），怎么保证服务不中断？

**解决方案**：`FallbackPolicy`（`engine/fallback.py:27`）实现了自动重试 + 模型切换。

### 内部逻辑（6 步）

```
步骤 1：错误分类 (classify_error)
  输入：错误消息 + 提供商名 + HTTP 状态码
  调用：provider/failures.py classify_provider_error()
  输出：ProviderFailureKind 枚举

步骤 2：判断是否可重试 (should_retry)
  可重试的类型（_RETRYABLE_FAILURE_KINDS）：
    RATE_LIMITED — 被限流了，等一会儿再试
    PROVIDER_OVERLOADED — 提供商超载，等一会儿
    TRANSPORT_TRANSIENT — 网络抖动，重试
    CONTEXT_OVERFLOW — 上下文溢出，压缩后重试
  不可重试的类型：
    AUTH_INVALID — 密钥错了，重试没用
    BAD_REQUEST — 请求格式错误
    POLICY_REFUSAL — 模型拒绝回答
    MODEL_NOT_FOUND — 模型不存在

步骤 3：指数退避 (backoff_sleep)
  公式：delay_ms = min(base_ms * (2^attempt) + random_jitter, max_ms)
  默认：base=1000ms, max=30000ms
  第 1 次重试：~1.5 秒，第 2 次：~3 秒，第 3 次：~6 秒

步骤 4：切换备用模型 (get_fallback_model)
  从 fallback_models 列表中按顺序切换
  如果当前模型不在列表中，用第一个
  如果全部用完，返回 None

步骤 5：_SelectorFallbackProvider 包装器
  运行时在 provider 外层包装，自动处理切换
  记录每次切换（health ledger）

步骤 6：最大重试次数
  默认 max_retries=3，超过后放弃
```

> 来源：`engine/fallback.py` L16-L23（可重试类型）, L27-L74（FallbackPolicy 类）, L77-L103（backoff_sleep）

## 四、SubagentManager — 子代理管理

**问题**：复杂任务需要并行处理多个子任务（如同时搜索多个资料源），怎么管理？

**解决方案**：`SubagentManager`（`engine/subagent.py:165`）管理子代理的完整生命周期。

| 类 | 作用 | 关键字段 | 源码 |
|---|------|---------|------|
| `SubagentSpec` | 子代理启动参数 | task, label, model_id, timeout(300s), max_iterations, workspace_dir | `subagent.py:23` |
| `SubagentHandle` | 运行中子代理的引用 | run_id, label, task(asyncio.Task), status, result, error, parent_task_id | `subagent.py:36` |

### 生命周期（8 步）

```
步骤 1：深度检查 (_check_depth)
  当前深度 >= MAX_SPAWN_DEPTH? 拒绝生成
  防止无限递归生成子代理

步骤 2：并发检查 (_check_concurrent)
  活跃子代理数 >= 限制? 等待或拒绝

步骤 3：创建子代理 (spawn)
  创建 asyncio.Task 运行子代理
  注册到 SubagentRegistry

  SubagentSpec.timeout 默认 300 秒
  _run_with_timeout 包装

步骤 6：孤儿清理 (cleanup_orphans)
  父任务已完成但子代理仍在运行 → 自动 abort
  遍历 _parent_tasks，检查 parent_task.done()

步骤 7：状态持久化 (save_state)
  序列化为 JSON（不含 asyncio.Task 对象）
  保存 run_id, label, status, result, error, spawned_at, completed_at

步骤 8：状态恢复 (load_state)
  从 JSON 恢复，所有恢复的 handle 标记为 'orphaned'
  创建已取消的占位 asyncio.Task
```

## 五、FinalizeEvidenceGate — 写入后证据门控

**问题**：AI 写了一个文件，但写的内容对不对？有没有产生错误？

**解决方案**：`FinalizeEvidenceTracker`（`engine/finalize_evidence_gate.py:887`）跟踪每次写入和执行，在 turn 结束时判断是否需要"挑战"（追问 AI）。

### 内部逻辑（9 步）

```
步骤 1：观察写入 (observe_write)
  输入：文件路径, is_error, iteration, scratch
  判断逻辑：
    - 如果 looks_repro_artifact_path(path) → 注册为"产物"（不重置执行窗口）
    - 如果是 scratch note（FIX_SUMMARY.md 等）→ 忽略
    - 其他写入 → 标记 source_edit_seen=True，重置 post_edit_executions

步骤 2：观察执行 (observe_execution)
  输入：命令, red(是否失败), exit_code, timed_out, status_reason, failure_anchors
  过滤逻辑：
    - 如果 status_reason 是非验证类（拒绝/取消）→ 跳过
    - 如果 exit_code 是命令格式错误（127等）→ 跳过
    - 如果运行时 stash 了 → 跳过（结果是 stash 前的状态）
    - 如果 is_detector_findings_exit → 特殊处理

步骤 3：红色证据收集
  记录：red_command, red_exit_code, red_timed_out, red_status_reason
  收集 failure_anchors（最多 5 个）
  收集 red_artifact_paths

步骤 4：构建观察结果 (build_observation)
  输出 FinalizeEvidenceObservation:
    triggers, red_command, red_exit_code, red_timed_out,
    red_failure_anchors, red_artifact_paths,
    deleted_never_green_repro_paths,
    post_edit_execution_count, post_edit_red_count,
    source_edit_seen, has_workspace_diff

步骤 5：触发判断 (should_challenge)
  if triggers 非空 → 触发挑战
  primary_reason = triggers[0]

步骤 6：挑战消息生成 (finalize_evidence_challenge_message)
  如果触发 → 生成一条追问消息，要求 AI 解释/修复
  挑战限制：FINALIZE_EVIDENCE_GATE_CHALLENGE_LIMIT

步骤 7：挑战后重试
  AI 收到挑战消息后重新进入 THINKING 状态
  最多挑战 CHALLENGE_LIMIT 次

步骤 8：门控键生成 (finalize_evidence_gate_key)
  基于执行工具名和写入工具名生成唯一键
  用于跨 turn 追踪

步骤 9：记录与清理
  记录所有证据到 event log
  清理临时产物
```

> 来源：`engine/finalize_evidence_gate.py` L844-L884（FinalizeEvidenceObservation）, L887-L984（FinalizeEvidenceTracker）

## 六、PostWriteConvergenceTracker — 写入后收敛检测

**问题**：AI 在写代码模式下可能陷入"改了又改、验证→再改→再验证"的死循环，diff 已经稳定了但 AI 还在继续。

**解决方案**：`PostWriteConvergenceTracker`（`engine/post_write_convergence.py:33`）检测稳定 diff 并强制结束。

### 内部状态机（4 态）

```
OBSERVE ──▶ WARN ──▶ FINALIZE
   │                    ▲
   └──▶ RESET ◀─────────┘
```

### 详细逻辑（5 步）

```
步骤 1：观察 (observe)
  输入 PostWriteConvergenceObservation:
    iteration, provider_call_count, workspace_write_count,
    changed_receipt_count, diff_fingerprint, diff_paths,
    focused_verification_success_observed, continued_activity_after_verification

步骤 2：资格检查 (_eligible)
  条件（全部满足才触发）：
    changed_receipt_count > 0
    diff_fingerprint 非空
    diff_paths 非空
    focused_verification_success_observed = True
    continued_activity_after_verification = True

步骤 3：指纹变化检测
  如果 diff_fingerprint 变了 → RESET（新的一轮修改）
  如果 diff_fingerprint 不变 → stable_count += 1

步骤 4：警告 (_should_warn)
  条件：stable_count >= warn_threshold（默认 3）且未警告过
  动作：返回 "warn"，在上下文中插入警告消息

步骤 5：强制结束 (_should_finalize)
  条件：stable_count >= warned_at_count + finalize_after_warning（默认 3）
  动作：返回 "finalize"，强制结束当前 turn
```

> 来源：`engine/post_write_convergence.py` L8（PostWriteConvergenceAction 类型）, L12-L21（Observation）, L24-L31（Decision）, L33-L139（Tracker 类）

## 七、Compaction — 上下文压缩

**问题**：长对话（如 50 轮）超出 LLM 上下文窗口，怎么压缩旧内容？

**解决方案**：`CompactionConfig` + `compact_context`（`session/compaction.py:32`）

### 压缩算法（6 步）

```
步骤 1：触发判断
  触发条件：input_tokens / usable_tokens > threshold（默认 0.85）
  触发类型：token_budget | message_count | explicit

步骤 2：配置构建 (build_compaction_config_from_provider)
  从 provider 读取模型配置：
    base_chunk_ratio: 0.4（每块占 40% 窗口）
    min_chunk_ratio: 0.15（最小块 15%）
    safety_margin: 1.2（安全系数）
    default_parts: 2（默认分 2 块）
    identifier_policy: "strict"（严格保留标识符）
    timeout_seconds: 90.0
    protected_recent_messages: 0（保护最近 N 条消息）

步骤 3：分块处理
  将历史消息按 base_chunk_ratio 分块
  如果 forced_prefix_cut 已设置，使用精确边界

步骤 4：LLM 压缩
  每块发送给 LLM（使用 compaction model）生成摘要
  保留关键信息：命令、路径、标识符、错误标记、产物名、决策前缀

步骤 5：Obligation 提取
  提取 CompactionObligation：
    kind: 类型（command/path/identifier/error/artifact/decision）
    value: 值
    source_role: 来源角色
  这些 obligations 确保压缩后不丢失关键上下文

步骤 6：结果组装 (CompactionResult)
  summary: 压缩后的摘要
  kept_entries: 保留的消息（尾部）
  removed_count: 被压缩的消息数
  tokens_before / tokens_after: 压缩前后 token 数
  coverage_status: 覆盖状态
  missing_obligations: 缺失的关键信息
  critical_carry_forward: 必须保留的关键信息
```

> 来源：`session/compaction.py` L32-L46（CompactionConfig）, L49-L61（CompactionRequest）, L65-L85（CompactionResult）, L96-L132（build_compaction_config_from_provider）
