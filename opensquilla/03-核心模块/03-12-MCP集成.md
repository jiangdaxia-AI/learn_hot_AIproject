# 03-12 · MCP 集成 — 通俗教材

> **TL;DR**：MCP（Model Context Protocol，模型上下文协议）让 OpenSquilla 能连接外部工具（如数据库、文件系统），也能把自己的工具暴露给其他 AI 应用。
> - **客户端模式**：OpenSquilla 连接别人的工具 → 适合产品/运营阅读
> - **服务端模式**：别人连接 OpenSquilla 的工具 → 适合技术负责人

> **文件数**：客户端 6 + 服务端 3 = 9 个文件 | **核心模块**：MCP 服务器配置（定义连接参数）、MCP 客户端（负责连接和调用外部工具） | **影响范围**：被 19 处代码调用 | **服务端**：MCP 服务器工厂（创建 MCP 服务器的入口函数）

## 定位

MCP 集成是 OpenSquilla 的"万能转接头"。MCP（Model Context Protocol，模型上下文协议）是一种让 AI 应用标准化连接外部工具的开放协议。通过 MCP，OpenSquilla 可以连接任何支持 MCP 的外部工具服务器——比如数据库查询工具、文件管理工具、第三方 API 工具——无缝扩展 AI 助手的能力。同时，OpenSquilla 自身也可以作为 MCP 服务器，把自己的工具暴露给其他 AI 应用使用。

---

## 生活化比喻

> MCP 像**USB-C 扩展坞**。你的电脑只有一个 USB-C 口，但通过扩展坞可以接显示器、键盘、鼠标、网线。MCP 就是 AI 助手的"扩展坞协议"——OpenSquilla 通过 MCP 连接各种外部工具，也可以被其他 AI 应用连接。

## 一、MCP 双角色架构

OpenSquilla 同时扮演两个角色——既能连接别人的工具，也能让别人连接自己的工具：

```
┌──────────────────────────────────────────────┐
│              OpenSquilla                      │
│                                              │
│  ┌──────────────────────┐                    │
│  │ MCP 客户端（消费者）   │                    │
│  │ • 连接外部 MCP 服务器  │  ←─── 外部 MCP 服务器
│  │ • 发现对方有哪些工具    │      (数据库/文件系统/API)
│  │ • 调用远程工具         │                    │
│  └──────────────────────┘                    │
│                                              │
│  ┌──────────────────────┐                    │
│  │ MCP 服务器（提供者）   │                    │
│  │ • 暴露 OpenSquilla 工具│  → 外部 MCP 客户端
│  │ • 支持两种连接方式     │     (其他 AI 应用)
│  └──────────────────────┘                    │
└──────────────────────────────────────────────┘
```

## 二、MCP 客户端模块详解（6 个文件）

作为"消费者"，MCP 客户端负责连接外部工具服务器：

| 文件 | 通俗解释 | 职责 |
|------|---------|------|
| 数据类型定义 | 定义服务器配置、工具定义、工具调用结果等数据结构 | 规定"连接参数长什么样、工具怎么描述、结果怎么返回" |
| 客户端连接管理 | 管理与一个 MCP 服务器的连接 | 负责"连上去、调工具、断开" |
| 服务发现 | 发现外部 MCP 服务器，列出对方有哪些工具可用 | 自动扫描"对方有什么能力" |
| 远程连接客户端 | 通过 HTTP 长连接方式连接远程服务器 | 通过网络连接远处的工具 |
| 本地连接客户端 | 通过启动子进程方式连接本地工具 | 直接在本地启动工具程序 |
| 包入口 | 导出公共接口 | 模块的对外入口 |

### 客户端连接流程

像一个打电话的过程：

1. **拨号**：根据配置选择连接方式
   - 本地模式：启动一个子程序，通过标准输入输出通信
   - 远程模式：建立 HTTP 长连接，通过事件流通信
2. **问能力**：询问对方"你有什么工具？" → 获取工具列表（名称、描述、参数）
3. **调工具**：告诉对方"帮我执行这个工具，参数是这些" → 获取执行结果
4. **挂断**：断开连接，清理子程序或网络连接

## 三、MCP 服务器模块详解（2 个文件）

作为"提供者"，MCP 服务器把 OpenSquilla 的工具暴露给外部使用：

| 文件 | 通俗解释 | 职责 |
|------|---------|------|
| 服务器创建 | 创建 MCP 服务器，暴露 OpenSquilla 的工具库 | 把 OpenSquilla 的能力包装成 MCP 标准接口 |
| 桥接层 | 把 MCP 协议的请求翻译成 OpenSquilla 内部调用 | 充当"翻译官"，让外部请求能调用内部功能 |

### 两种连接方式

| 方式 | 适用场景 | 命令 |
|------|---------|------|
| 本地连接 | 本机上的其他程序连接 | `opensquilla mcp-server --transport stdio` |
| 远程连接 | 网络上的其他程序连接 | `opensquilla mcp-server --transport sse --port 3001` |

### 暴露的工具

OpenSquilla 通过 MCP 暴露的工具包括：
- 命令执行（运行 shell 命令、后台进程管理）
- 文件操作（读取文件、列出目录、搜索文件、搜索内容）
- 网页搜索（搜索网页、抓取网页内容、发现链接）
- 记忆读写（存储和检索 AI 记忆）
- 版本管理（查看代码变更、提交日志、工作区状态）
- 发布产物（生成文件并发布）
- 定时任务（管理定时任务）
- 以及其他所有非内部工具

## 四、MCP 服务器配置结构

配置一个外部 MCP 服务器需要以下信息：

| 字段 | 说明 |
|------|------|
| 名称 | 服务器的唯一标识（自己取名） |
| 启动命令 | 本地模式下，启动服务器的命令 |
| 命令参数 | 命令的附加参数 |
| 环境变量 | 服务器运行时需要的环境变量 |
| 远程地址 | 远程模式下的连接地址 |
| 是否启用 | 开关，控制是否启用这个服务器 |

### 配置示例（自然语言描述）

在配置文件中，可以这样配置：
- 配置一个本地文件系统工具：命令为 `npx`，参数为 MCP 文件系统服务器包 + 允许访问的目录路径
- 配置一个远程数据库工具：地址为 `http://localhost:3001/sse`

## 五、工具定义和调用结果

每个外部工具的信息包含：
- **工具名称**：叫什么名字
- **工具描述**：这个工具是干嘛的
- **参数定义**：需要什么参数，每个参数的类型和说明

调用结果包含：
- **结果内容**：工具执行后返回的内容
- **是否出错**：执行是否成功

## 六、外部服务器发现机制

服务发现机制管理多个 MCP 服务器的连接：

1. **初始化**：从配置文件加载所有已配置的服务器信息
2. **启动**：同时连接所有已启用的服务器
   - 本地客户端：启动子程序
   - 远程客户端：建立网络连接
3. **发现工具**：汇总所有服务器提供的工具列表 → 注入到 AI 助手的工具注册表中
4. **调用工具**：AI 助手调用外部工具时 → 通过 MCP 客户端转发请求 → 结果返回给 AI 助手
5. **关闭**：断开所有连接

### 逐步源码拆解

#### ① 服务发现

**触发点**：网关启动时，`gateway/boot.py` 第 2630-2665 行遍历 `config.mcp.servers` 配置列表，为每个已启用的服务器构造 `MCPServerConfig` 并调用 `discover_and_register()`。

**1.1 扫描配置文件中的 MCP 服务器列表**

网关启动到第 2630 行时，先检查 `config.mcp.enabled` 是否为 `True` 以及 `config.mcp.servers` 列表是否非空。如果 MCP 功能未启用或没有配置任何服务器，直接跳过整个 MCP 发现流程，打一条 `mcp_enabled_no_servers` 日志。

如果配置了服务器，则遍历 `config.mcp.servers` 列表中的每个条目。每个条目包含：`name`（服务器名）、`transport`（`"stdio"` 或 `"sse"`）、`command`/`args`（stdio 专用）或 `url`（sse 专用）、`env`（环境变量）、`tool_timeout_seconds`（工具超时时间）。这些字段在第 2638-2644 行被映射到 `MCPServerConfig` 数据类中。

> 源码位置：`gateway/boot.py:2630-2644`，`mcp/types.py:9-19`

**1.2 对每个服务器发起连接尝试 → 获取 tools/list**

每个服务器配置被包装为 `MCPServerConfig` 后，调用 `discover_and_register(mcp_cfg, tool_registry)`。这个函数内部做了三件事：创建客户端 → 连接服务器 → 列出工具 → 注册工具。整个过程用 `asyncio.wait_for()` 包裹，超时时间由 `config.mcp.connect_timeout_seconds` 控制。

> 源码位置：`gateway/boot.py:2645-2648`，`mcp/discovery.py:114-147`

**1.3 如果连接失败 → 标记为不可用 → 跳过该服务器**

`discover_and_register()` 内部如果任何一步出错（连接失败、工具列表获取失败、注册失败），异常会向上传播到 `gateway/boot.py` 的 try/except 块。这里有两条分支：

- **TimeoutError**：记录 `mcp_server_timeout` 警告日志，包含服务器名和超时时间，然后跳过该服务器。
- **其他异常**：记录 `mcp_server_failed` 警告日志，包含服务器名和错误信息，然后跳过该服务器。

无论哪种失败，都不会影响其他服务器的发现和注册，也不会阻止网关启动——MCP 服务器是"尽力而为"的，一个挂了不影响全局。

> 源码位置：`gateway/boot.py:2649-2665`

---

#### ② 建立连接

`discover_and_register()` 的第一步是调用 `create_client(config)` 创建客户端，然后调用 `client.connect()` 建立连接。

**2.1 stdio 方式：MCPStdioClient 启动子进程 → 通过 stdin/stdout JSON-RPC 通信**

`create_client()` 检查 `config.transport`：
- 如果是 `"stdio"`，从 `mcp/stdio.py` 导入 `MCPStdioClient`，传入配置创建实例。

`MCPStdioClient.connect()` 的具体做法：
1. 用 `asyncio.create_subprocess_exec()` 启动子进程，传入 `command` 和 `args`，将子进程的 `stdin` 设为 `PIPE`、`stdout` 设为 `PIPE`。如果配置了 `env`，会合并到当前环境变量中传给子进程。
2. 子进程启动后，OpenSquilla 和它之间通过 stdin/stdout 通信，每条 JSON-RPC 消息占一行（LF 结尾），这是 MCP 协议 2024-11-05 版本规定的 stdio 传输格式。

> 源码位置：`mcp/discovery.py:58-69`，`mcp/stdio.py:50-64`

**2.2 SSE 方式：MCPSSEClient 通过 HTTP 长连接 → Server-Sent Events 推送**

如果是 `"sse"`，从 `mcp/sse.py` 导入 `MCPSSEClient`。

`MCPSSEClient.connect()` 的具体做法：
1. 创建一个 `httpx.AsyncClient` 实例，设置超时时间。
2. 启动后台异步任务 `_read_stream()`，向 `url` 发起 `GET` 请求，建立一个持久的 SSE 流。
3. 后台任务逐行读取 SSE 事件流，等待名为 `endpoint` 的事件——这个事件携带了后续发送 JSON-RPC 请求的 POST 地址（消息端点 URL）。
4. `connect()` 等待 `endpoint` 事件到达（最多等 30 秒）。如果超时还没收到 `endpoint` 事件，就回退到配置中指定的 `message_endpoint`（默认 `/message`）作为消息端点。

> 源码位置：`mcp/sse.py:67-95`，`mcp/sse.py:97-123`

**2.3 连接握手：发送 initialize 请求 → 验证协议版本 → 获取服务器能力**

无论 stdio 还是 SSE，建立传输通道后，都需要完成 MCP 协议握手。握手分两步：

**第一步**：发送 `initialize` 请求。请求参数包含：
- `protocolVersion: "2024-11-05"` — 声明自己支持的协议版本。
- `capabilities: {}` — 声明自己的客户端能力（OpenSquilla 目前不声明特殊能力）。
- `clientInfo: {name: "opensquilla", version: ...}` — 标识客户端身份。

服务器返回 `initialize` 响应，包含服务器的协议版本和能力声明。

**第二步**：发送 `notifications/initialized` 通知。这是一个单向通知（不需要响应），告诉服务器"我这边初始化完毕了"。服务器收到这个通知后，才算正式进入工作状态。

stdlib 和 SSE 的握手逻辑完全一致，只是底层传输方式不同。

> 源码位置：`mcp/stdio.py:66-76`，`mcp/sse.py:87-95`

---

#### ③ 工具发现

连接建立后，`discover_and_register()` 调用 `client.list_tools()` 获取外部服务器提供的工具列表。

**3.1 发送 tools/list 请求 → 获取服务器提供的工具列表**

`list_tools()` 发送一个 JSON-RPC 请求：`{"method": "tools/list", "params": null}`。这是一个标准的 MCP 协议请求，服务器必须返回它拥有的所有工具。

- stdio 路径：`_send_request("tools/list")` → 写入 stdin → 读取 stdout 响应。
- SSE 路径：`_send_and_receive("tools/list")` → POST 到消息端点 → 等待 SSE 流返回。

> 源码位置：`mcp/stdio.py:169-180`，`mcp/sse.py:202-213`

**3.2 每个工具包含 name、description、inputSchema（JSON Schema 参数定义）**

服务器返回的响应格式为：
```json
{
  "result": {
    "tools": [
      {
        "name": "db_query",
        "description": "Execute a SQL query against the database",
        "inputSchema": {
          "type": "object",
          "properties": {
            "sql": {"type": "string", "description": "SQL query to execute"}
          },
          "required": ["sql"]
        }
      }
    ]
  }
}
```

OpenSquilla 解析 `result.tools` 数组，为每个工具构造一个 `MCPToolDef` 数据对象，包含 `name`、`description`、`input_schema` 三个字段。

> 源码位置：`mcp/stdio.py:171-180`，`mcp/sse.py:206-213`，`mcp/types.py:21-24`

**3.3 将外部工具转换为 ToolDefinition 格式 → 准备注册**

`list_tools()` 返回 `list[MCPToolDef]`，但这还不是 OpenSquilla 内部能用的格式。下一步 `_make_tool_handler()` 会从 `MCPToolDef.input_schema` 中提取 `properties` 和 `required`，映射为 `ToolSpec`（OpenSquilla 内部的工具规格定义），使得外部工具看起来和原生工具一模一样。

> 源码位置：`mcp/discovery.py:138-147`

---

#### ④ 工具注册

工具列表拿到后，`discover_and_register()` 遍历每个 `MCPToolDef`，调用 `_make_tool_handler()` 逐个注册。

**4.1 为每个外部工具创建 RegisteredTool 对象**

`_make_tool_handler()` 从 `MCPToolDef.input_schema` 中提取 `properties`（参数定义字典）和 `required`（必填参数列表），然后构造一个 `ToolSpec` 对象：

```python
spec = ToolSpec(
    name=f"mcp_{tool_name}",       # 加 mcp_ 前缀，避免和内部工具重名
    description=tool_def.description,
    parameters=properties,          # JSON Schema properties
    required=required,              # JSON Schema required
)
```

工具名加 `mcp_` 前缀是因为：外部工具名可能和 OpenSquilla 内置工具名冲突（比如都叫 `read_file`），加前缀后变成 `mcp_read_file`，就不会冲突了。

> 源码位置：`mcp/discovery.py:80-90`

**4.2 设置 handler 为 MCP 转发函数**

然后创建一个异步 `handler` 闭包函数。这个 handler 是 Agent 调用 MCP 工具时的实际执行入口。它的核心逻辑：

```python
async def handler(**kwargs):
    result = await asyncio.wait_for(
        client.call_tool(tool_name, kwargs),  # 转发到外部服务器
        timeout=timeout_seconds,
    )
    if result.is_error:
        raise SafeToolError(result.content)   # 服务器报错 → 抛给 Agent
    return result.content                      # 正常结果 → 返回给 Agent
```

关键点：handler 通过闭包捕获了 `client`（MCP 客户端实例）和 `tool_name`（原始工具名），这样每次调用时都能准确地转发到正确的服务器和工具。

> 源码位置：`mcp/discovery.py:92-109`

**4.3 注册到 ToolRegistry → Agent 现在可以调用这个工具**

最后调用 `registry.register(spec, handler)` 把工具规格和 handler 注册到全局 `ToolRegistry`。注册完成后，Agent 的工具列表中就会出现 `mcp_db_query` 这样的工具，LLM 可以像调用内置工具一样调用它。

注册成功后，`discover_and_register()` 将 `ActiveMCPClient` 条目追加到模块级 `_active_clients` 列表中，确保 MCP 客户端在网关运行期间保持活跃，不会提前被垃圾回收。

> 源码位置：`mcp/discovery.py:111`，`mcp/discovery.py:137-147`

#### ⑤ Agent 调用

工具注册完成后，Agent 可以在对话中"看到"所有以 `mcp_` 开头的工具。当 Agent 决定调用某个 MCP 工具时，流程如下。

**5.1 LLM 返回 tool_use 事件，包含 MCP 工具名和参数**

Agent 与 LLM 交互时，LLM 返回的响应中可能包含 `tool_use` 内容块。每个 `tool_use` 块包含：
- `name`：工具名，例如 `mcp_db_query`。
- `input`：工具参数，以 JSON 对象形式提供，例如 `{"sql": "SELECT * FROM users"}`。

OpenSquilla 的调度系统解析 `tool_use` 块，提取工具名和参数，然后查找 `ToolRegistry` 中对应的 handler。

**5.2 Agent 解析工具名 → 发现是 MCP 工具 → 走 MCP 调用路径**

调度系统根据工具名在 `ToolRegistry` 中查找。由于 MCP 工具在注册时使用了 `mcp_` 前缀，查找逻辑和内置工具完全一致——调度系统不需要知道这个工具是本地的还是远程的。找到 handler 后，直接调用 `handler(**input)`，传入 LLM 提供的参数。

> 源码位置：`mcp/discovery.py:92`（handler 函数签名接收 `**kwargs`）

**5.3 参数验证：对照 inputSchema 检查参数格式**

参数验证发生在两个层面：

1. **OpenSquilla 层面**：`ToolSpec` 中声明了 `parameters` 和 `required`，`ToolRegistry` 在调用 handler 之前会做基本的参数校验（必填参数检查、类型检查）。
2. **MCP 服务器层面**：外部服务器收到 `tools/call` 请求后，会根据自己的 `inputSchema` 再次校验参数。如果参数不合法，服务器返回 `isError: true` 的响应，OpenSquilla 将其转为 `SafeToolError` 抛给 Agent。

> 源码位置：`mcp/discovery.py:80-90`（ToolSpec 构造），`mcp/stdio.py:182-197`（call_tool 的 isError 检查）

---

#### ⑥ 请求转发

handler 调用 `client.call_tool(tool_name, kwargs)` 后，请求进入传输层，根据连接类型走不同的转发路径。

**6.1 MCPClient 将参数封装为 tools/call JSON-RPC 请求**

不管哪种传输方式，请求都会被封装为标准的 JSON-RPC 2.0 格式：

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "tools/call",
  "params": {
    "name": "db_query",
    "arguments": {"sql": "SELECT * FROM users"}
  }
}
```

- `jsonrpc`：固定为 `"2.0"`。
- `id`：自增的请求 ID，用于匹配响应。
- `method`：`"tools/call"`，MCP 协议规定的调用工具方法名。
- `params.name`：要调用的工具名（原始名称，不带 `mcp_` 前缀）。
- `params.arguments`：工具参数，直接透传 Agent 提供的 `kwargs`。

> 源码位置：`mcp/stdio.py:99-119`（`_send_request`），`mcp/sse.py:168-191`（`_send_and_receive`）

**6.2 stdio 方式：写入子进程 stdin**

`MCPStdioClient._send_request()` 的流程：

1. 获取 `_request_lock`（异步锁），确保同一时间只有一个协程在读/写子进程——因为 stdin/stdout 是共享的，并发读写会导致响应错乱。
2. 生成递增的 `request_id`。
3. 用 `json.dumps()` 序列化请求，加上 `
` 换行符，编码为 UTF-8 字节。
4. 调用 `self._process.stdin.write(encoded)` 写入子进程的 stdin。
5. 调用 `await self._process.stdin.drain()` 确保数据被刷新到管道。
6. 调用 `_read_response(req_id)` 等待匹配的响应。

> 源码位置：`mcp/stdio.py:99-119`

**6.3 SSE 方式：HTTP POST 到服务器端点**

`MCPSSEClient._send_and_receive()` 的流程：

1. 检查 `_message_url` 是否已设置（即 `endpoint` 握手是否完成）。
2. 生成递增的 `request_id`。
3. 创建一个 `asyncio.Future` 对象，存入 `_pending` 字典（key 为 `request_id`）。
4. 用 `httpx.AsyncClient.post()` 把 JSON-RPC 请求 POST 到消息端点 URL。
5. 调用 `asyncio.wait_for(future, timeout=...)` 等待 SSE 流返回匹配的响应。
6. 无论成功还是失败，在 `finally` 块中从 `_pending` 字典移除对应的 Future。

这里的关键设计是：POST 请求和 SSE 响应在两条不同的 HTTP 通道上——POST 只负责发送请求，响应通过之前打开的 SSE 长连接异步返回。`_pending` 字典就是连接这两条通道的"对号牌"。

> 源码位置：`mcp/sse.py:168-191`

---

#### ⑦ 远程执行

JSON-RPC 请求到达外部 MCP 服务器后，服务器开始执行工具逻辑。

**7.1 外部服务器接收请求 → 执行工具逻辑**

外部 MCP 服务器（可以是任何实现 MCP 协议的服务）收到 `tools/call` 请求后：
1. 解析 JSON-RPC 请求体，提取 `method`（`"tools/call"`）、`params.name`（工具名）、`params.arguments`（参数）。
2. 在自己的工具注册表中查找工具名对应的实现函数。
3. 调用实现函数，传入参数。
4. 将执行结果封装为 JSON-RPC 响应返回。

> 这是外部服务器的行为，OpenSquilla 不控制这一部分。

**7.2 如果执行超时 → 客户端取消等待 → 返回超时错误**

OpenSquilla 在 handler 层用 `asyncio.wait_for(client.call_tool(...), timeout=timeout_seconds)` 包裹了调用。超时时间由 `MCPServerConfig.tool_timeout_seconds` 控制（默认 30 秒）。

如果外部服务器在超时时间内没有返回响应：
- `asyncio.wait_for()` 抛出 `TimeoutError`。
- handler 捕获 `TimeoutError`，抛出 `SafeToolError("MCP tool 'xxx' timed out after 30s")`。
- `SafeToolError` 被调度系统捕获，以 `is_error=True` 的执行状态返回给 Agent，Agent 看到的是错误信息而非空结果。

> 源码位置：`mcp/discovery.py:92-101`

**7.3 如果执行出错 → 返回错误响应**

外部服务器执行出错时，有两种返回方式：

1. **JSON-RPC 级别错误**：响应的顶层包含 `"error"` 字段（而非 `"result"`）。OpenSquilla 的 `call_tool()` 检测到 `"error" in response` 时，返回 `MCPToolResult(content=error_message, is_error=True)`。

2. **工具级别错误**：响应的 `"result"` 中包含 `"isError": true`。这是 MCP 协议规定的——工具执行失败但不构成协议错误时使用。OpenSquilla 的 `call_tool()` 检查 `result.get("isError", False)`，如果为 `True`，同样返回 `is_error=True` 的结果。

两种情况下，handler 都会检测到 `result.is_error == True`，然后抛出 `SafeToolError`。

> 源码位置：`mcp/stdio.py:182-197`，`mcp/sse.py:215-232`

---

#### ⑧ 结果接收

外部服务器返回 JSON-RPC 响应后，OpenSquilla 的传输层接收并解析响应。

**8.1 接收 JSON-RPC 响应 → 解析 content 数组**

**stdio 路径**：`_read_response()` 逐行读取子进程 stdout。每行尝试解析为 JSON 对象：
- 如果是通知（有 `method` 但没有 `id`）→ 跳过，记录 debug 日志。
- 如果 `id` 不匹配当前期望的 `request_id` → 跳过（可能是之前的延迟响应）。
- 如果 `id` 匹配 → 返回该消息。

如果子进程 stdout 关闭（`readline()` 返回空字节），抛出 `ConnectionError("MCP stdio server closed the connection")`。

**SSE 路径**：`_handle_event()` 解析 SSE 事件数据。每个 SSE 事件可能包含 JSON 数据。解析后检查 `id` 是否在 `_pending` 字典中，如果在，说明这是一个等待中的请求的响应，调用 `future.set_result(message)` 唤醒等待的协程。

> 源码位置：`mcp/stdio.py:131-167`，`mcp/sse.py:125-145`

**8.2 每个 content 项可能是 text、image、resource 类型**

MCP 协议规定，工具执行结果放在 `result.content` 数组中。每个 `content` 项是一个对象，包含 `type` 字段：

- `{"type": "text", "text": "..."}` — 文本内容。
- `{"type": "image", "data": "...", "mimeType": "image/png"}` — 图片内容（base64 编码）。
- `{"type": "resource", "resource": {...}}` — 资源引用（如文件 URI）。

OpenSquilla 当前只处理 `type: "text"` 的内容，用 `"
".join(...)` 把所有文本项拼接成一个字符串。图片和资源类型暂时被忽略。

> 源码位置：`mcp/stdio.py:193-194`，`mcp/sse.py:229`

**8.3 合并所有 content 项为最终结果**

`call_tool()` 返回 `MCPToolResult(content=text, is_error=...)`。`content` 字段是所有文本项拼接后的字符串，`is_error` 标志表示执行是否出错。

> 源码位置：`mcp/stdio.py:197`，`mcp/sse.py:232`，`mcp/types.py:28-31`

---

#### ⑨ 结果返回

`call_tool()` 的结果返回到 handler 后，handler 负责将结果传递给 Agent。

**9.1 将 MCP 结果包装为 ToolResult 实体**

handler 检查 `result.is_error`：
- 如果 `is_error == True`：抛出 `SafeToolError(result.content)`。调度系统捕获后，会以 `is_error=True` 的执行状态记录这次工具调用，Agent 收到的是错误信息。
- 如果 `is_error == False`：返回 `result.content`（纯文本字符串）。调度系统以正常执行状态记录，Agent 收到工具执行结果。

> 源码位置：`mcp/discovery.py:107-109`

**9.2 注入到 Agent 消息列表**

调度系统将 handler 的返回值（或异常）包装为 `tool_result` 内容块，追加到 Agent 的消息历史中。消息格式类似于：

```
[user]  帮我查一下用户表
[assistant] 调用 mcp_db_query(sql="SELECT * FROM users")
[tool_result] 查询结果: 42 行数据
```

LLM 在下一轮对话中可以看到完整的调用历史，包括工具名、参数和执行结果。

**9.3 Agent 根据结果决定下一步**

Agent（LLM）收到 `tool_result` 后，根据内容决定下一步行动：
- 结果正常：总结结果、回答用户问题。
- 结果异常（`is_error=True`）：可能向用户报告错误，或尝试用不同参数重试。
- 需要更多信息：可能调用另一个工具继续查询。

这一步完全由 Agent（LLM）自主决策，MCP 层不参与。

#### ⑩ 连接管理

MCP 客户端连接在网关运行期间一直保持活跃，直到网关关闭时才统一清理。

**10.1 网关关闭时 → close_active_clients() 清理所有连接**

网关关闭流程在 `gateway/boot.py` 第 1765-1770 行：从 `mcp.discovery` 导入 `close_active_clients`，调用 `await close_active_clients()`，记录 `gateway.mcp_clients_closed` 日志。

`close_active_clients()` 遍历 `_active_clients` 全局列表，对每个 `ActiveMCPClient` 调用 `entry.close()`。如果 `owner` 参数不为 `None`，只关闭匹配的 owner 或服务器名，否则关闭全部。

关闭完成后，`_active_clients` 列表被清空（或保留不匹配的条目）。

> 源码位置：`gateway/boot.py:1765-1770`，`mcp/discovery.py:37-55`

**10.2 stdio 方式：先 terminate() → 等待 2 秒 → kill() 强制终止**

`MCPStdioClient.close()` 分三步关闭子进程：

1. **检查进程状态**：如果 `process.returncode` 不为 `None`，说明进程已经自己退出了，直接返回。
2. **优雅终止**：调用 `process.terminate()` 发送 `SIGTERM` 信号。如果进程已经不存在（`ProcessLookupError`），忽略。
3. **等待**：用 `asyncio.wait_for(process.wait(), timeout=2.0)` 等待进程退出，最多等 2 秒。
4. **强制终止**：如果 2 秒后进程还没退出（`TimeoutError`），调用 `process.kill()` 发送 `SIGKILL` 信号强制杀死，然后 `await process.wait()` 等待确认。

> 源码位置：`mcp/stdio.py:78-97`（`_CLOSE_TIMEOUT_SECONDS = 2.0`）

**10.3 SSE 方式：取消 reader 任务 → 关闭 HTTP 客户端**

`MCPSSEClient.close()` 分三步清理 SSE 连接：

1. **设置关闭标志**：`self._closed = True`，防止新的请求进入。
2. **取消 reader 任务**：调用 `self._reader_task.cancel()` 取消后台读取 SSE 流的协程，然后 `await` 等待它完成（捕获 `CancelledError`）。
3. **失败所有等待中的请求**：调用 `_fail_pending(ConnectionError("MCP SSE client closed"))`，遍历 `_pending` 字典中所有未完成的 Future，用 `set_exception()` 将它们标记为失败。这样任何正在 `await` 这些 Future 的协程都会收到 `ConnectionError`。
4. **关闭 HTTP 客户端**：调用 `await self._client.aclose()` 关闭 `httpx.AsyncClient`。

> 源码位置：`mcp/sse.py:153-166`，`mcp/sse.py:147-151`（`_fail_pending`）

### 两种传输方式完整对比

| 维度 | stdio | SSE |
|------|-------|-----|
