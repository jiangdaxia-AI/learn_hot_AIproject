# 05 · 数据模型

> **说明**：本章介绍 OpenSquilla 系统中各种"数据"是怎么组织的。适合产品经理和运营人员了解系统内部的数据结构，帮助理解功能之间的关系。用生活化的比喻来解释每个概念。

---

## 5.1 实体关系总览

如果把 OpenSquilla 比作一家餐厅，那么各个数据模块就是餐厅里的不同角色和物品：

餐厅老板（网关全局配置）
  ├──→ 供应商合同（AI 服务商的配置：用哪个模型、密钥是什么）
  │     ├──→ 供应商信息（服务商类型、模型名称、费用）
  │     └──→ 门禁卡（API 密钥，每次调用 AI 都要出示）
  ├──→ 外卖平台账号（飞书、Slack 等通道的配置）
  │     └──→ 外卖接单器（运行时接收消息、发送回复的适配器）
  └──→ 厨房安全规范（沙箱安全策略：哪些操作可以做、哪些不行）

大堂经理（会话管理器）
  ├──→ 包厢记录本（每个会话的档案：编号、状态、聊了多少轮、用了多少 token）
  │     ├── 包厢编号、房间号、服务员编号
  │     ├── 状态：正在用餐 / 已结账 / 出问题了 / 被赶走了 / 超时了
  │     ├── 用餐类型：单人包间 / 大桌聚餐 / 外卖通道
  │     ├── 第几轮点菜、吃进去了多少 token、吐出来了多少 token
  │     └──→ 压缩笔记（把长对话压缩成摘要，省空间）
  ├──→ 压缩规则（什么时候压缩、怎么压缩、保留哪些关键信息）
  └──→ 任务流水账（记录每个 AI 任务的排队→执行→成功/失败全过程）

AI 大厨（机器人核心）
  ├──→ AI 供应商接口（统一调用不同 AI 模型的标准方法）
  ├──→ 菜谱配置（AI 的运行时参数：最多做几道菜、超时多久、预算多少）
  ├──→ 工具箱（AI 可以用的所有工具清单和说明）
  ├──→ 帮厨管理（管理 AI 生成的子任务，控制深度和并发数）
  │     ├──→ 帮厨任务单（子任务描述、标签、用哪个模型、超时多久）
  │     ├──→ 帮厨状态牌（跟踪正在执行的子任务状态和结果）
  │     └──→ 帮厨花名册（登记所有子任务、支持归档和清理）
  ├──→ 预算控制（计算 token 配额，确保不超出 AI 模型的上下文限制）
  │     └──→ 预算快照（当前还剩多少 token、各类操作的上限）
  ├──→ 应急方案（AI 调用失败后的重试和切换策略）
  ├──→ 安全检查（出菜前检查 AI 是否做了危险操作）
  ├──→ 重复修改检测（AI 反复修改同一个文件时触发警告）
  └──→ 压缩规则

定时闹钟（调度引擎）
  ├──→ 闹钟设置（定时任务：什么时候触发、做什么、结果发给谁）
  │     ├── 时间规则：按 cron 表达式 / 固定间隔 / 一次性定时
  │     ├── 任务类型：提醒 / 系统事件 / 触发 AI
  │     └── 会话目标：主会话 / 独立会话 / 当前会话 / 指定会话
  ├──→ 闹钟记录本（所有定时任务存在 SQLite 数据库里）
  ├──→ 定时器（控制闹钟精度、防止重复触发、启动时追赶错过的任务）
  └──→ 包厢清理工（定期删除过期的定时任务会话，默认保留 24 小时）

## 5.2 引擎层数据模型（AI 大厨的工作台）

| 数据概念 | 通俗解释 | 关键信息 |
|---------|---------|---------|
| AI 运行状态 | AI 当前在干什么：空闲 / 思考中 / 用工具 / 打字输出 / 完成 / 出错 | 6 种状态，像红绿灯一样切换 |
| AI 事件类型 | AI 状态变化时发出的通知：输出文字了、工具执行完了、本轮结束了、出错了等 | 10+ 种事件类型，像不同的门铃提示音 |
| AI 运行配置 | AI 的行为参数：最多对话几轮、超时多久、token 预算多少、是否开启深度思考等 | 100+ 项配置，像菜谱上的详细参数 |
| 上下文预算分类 | token 预算分成 6 个池子：外部输入 / 本地文件 / 生成的产物 / 错误信息 / 系统控制指令 | 每个池子有独立的上限 |
| 预算快照 | 当前 AI 还剩多少 token 可以用，各类操作的上限是多少 | 像余额提醒，快用完时会触发压缩 |
| 应急方案 | 主模型挂了怎么办：最多重试 3 次、备用模型列表、重试间隔从 1 秒起指数增长 | 默认最多重试 3 次，间隔 1s→2s→4s |
| 子任务参数 | 让 AI 生成子任务时指定：做什么、打什么标签、用哪个模型、超时多久 | 子任务默认 300 秒超时 |
| 子任务状态牌 | 跟踪每个子任务：编号、标签、状态、结果、错误信息 | 像快递单号，随时查进度 |
| 重复修改决策 | AI 反复修改同一个文件时的处理：继续观察 / 警告 / 强制终止 / 重置 | 防止 AI 陷入死循环 |
| 安全检查汇总 | 最终检查 AI 这轮做了什么：有没有执行危险命令、文件有没有改对、有没有遗留问题 | 像出菜前的最后一眼检查 |

## 5.3 AI 服务商层数据模型（供应商管理）

| 数据概念 | 通俗解释 | 关键信息 |
|---------|---------|---------|
| AI 服务商接口 | 调用不同 AI 模型的统一方法：发消息、查模型列表 | 不管底层是 OpenAI 还是 Anthropic，调用方式一样 |
| 错误分类 | AI 返回错误时，自动识别是什么问题：限流、过载、断网、上下文太长、密钥错等 | 10+ 种错误类型，每种有对应的应对策略 |
| 密钥池 | 管理多个 API 密钥，轮流使用，某个密钥被限流了就换下一个 | 像多个门禁卡，一张刷不了换另一张 |
| 多模型组合 | 同时调用多个 AI 模型，各自给出答案，再汇总最优结果 | 每个模型有权重，像评委打分 |
| 聊天参数 | 单次 AI 调用的设置：用哪个模型、温度（创造力高低）、最多输出多少 token、深度思考预算 | 温度越高 AI 越"放飞自我" |
| 服务商信息 | 服务商的只读身份信息：名称、版本、支持哪些功能、收费标准 | 像供应商名片 |
| 路由结果 | 智能路由器选模型的结果：选了哪个档位、各个档位的概率、难度分、用了哪个具体模型 | 像"根据题目难度，推荐用中等难度的模型" |

## 5.4 会话层数据模型（包厢管理）

| 数据概念 | 通俗解释 | 关键信息 |
|---------|---------|---------|
| 会话档案 | 每个会话的完整记录：编号、状态、类型、聊了多少轮、用了多少 token、创建时间 | 像包厢的登记卡 |
| 会话状态 | 会话当前是什么状态：正在聊 / 聊完了 / 出错了 / 暂停了 | 4 种状态 |
| 会话类型 | 这个会话是怎么产生的：私聊 / 群聊 / 话题串 / 定时任务 / 子任务 | 5 种来源 |
| 压缩摘要 | 长对话被压缩后的摘要，存文本内容和 token 统计 | 像把一本小说缩成一段简介 |
| 压缩规则 | 什么时候压缩、怎么压缩：分块比例、保留哪些关键信息、用哪个模型来压缩 | 控制压缩行为的参数 |
| 压缩请求 | 一次压缩操作：要压缩哪个会话、当前有哪些消息、用什么规则 | 像"请帮我把这 100 条消息压缩成 500 字摘要" |
| 压缩结果 | 压缩后得到什么：摘要文本、保留了哪些关键信息、去掉了多少条、前后 token 对比 | 像"压缩前 10000 token，压缩后 500 token" |
| 任务流水账 | 记录每个 AI 任务从排队到完成的完整过程 | 像外卖订单的全程追踪 |
| 任务状态 | 任务当前进度：排队中 / 执行中 / 成功了 / 失败了 / 取消了 / 超时了 | 6 种状态 |
| 会话意图 | 用户想干什么：继续聊 / 开新对话 / 重置当前对话 | 决定会话的走向 |
| 排队模式 | 多条消息的排队方式：先进先出 / 按优先级 | 像银行叫号 |
| 消息来源 | 这条消息是谁发的：真人用户 / 另一个会话 / 系统内部 | 3 种来源 |

## 5.5 调度层数据模型（定时闹钟管理）

| 数据概念 | 通俗解释 | 关键信息 |
|---------|---------|---------|
| 定时任务 | 一个闹钟的完整定义：编号、什么时候响、做什么事、结果发给谁、是否启用 | 像手机闹钟的设置 |
| 时间规则 | 闹钟的触发方式：按 cron 表达式（如"每天 9 点"）/ 固定间隔（如"每 30 分钟"）/ 一次性（如"下午 3 点响一次"） | 3 种模式 |
| 任务类型 | 闹钟响了要做什么：发提醒 / 触发系统事件 / 让 AI 做事 | 3 种类型 |
| 会话目标 | AI 执行任务时用哪个会话：主会话 / 独立的新会话 / 当前会话 / 指定会话 | 决定任务在哪个"包厢"里执行 |
| 任务状态 | 任务当前状态：等待中 / 执行中 / 完成了 / 失败了 / 取消了 | 5 种状态 |
| 执行记录 | 每次任务执行的详细记录：什么时候开始、什么时候结束、结果如何、有没有报错 | 像闹钟的使用历史 |
| 任务预约 | 防止多个闹钟同时触发同一个任务：先锁定，执行完再释放 | 像餐厅预订，一座不能同时给两个人 |
| 手动执行结果 | 手动触发任务时的执行结果：状态、输出内容、错误信息、退避时间 | 当你手动按了"立即执行"按钮 |

## 5.6 安全层数据模型（厨房安全规范）

| 数据概念 | 通俗解释 | 关键信息 |
|---------|---------|---------|
| 沙箱安全策略 | AI 执行操作时的安全规则：安全等级、能不能联网、能访问哪些文件夹、资源上限 | 像给 AI 画了一个"安全圈"，圈外的事不能做 |
| 安全等级 | 从低到高：禁用（不隔离）/ 标准 / 严格 / 锁定 | 等级越高，AI 能做的事越少 |
| 网络模式 | AI 能不能上网：不能联网 / 只能访问白名单 / 完全放开 | 像给 AI 设置了"飞行模式"或"仅限 WiFi" |
| 资源限制 | AI 执行操作的硬限制：最多用多少 CPU 时间、最多占多少内存、最长运行多久 | 防止 AI 把电脑跑死 |
| 沙箱执行结果 | AI 执行命令后的结果：退出码（0=成功）、输出内容、有没有被截断、有没有超时 | 像命令执行后的回执单 |
| 运行环境 | AI 执行时的环境上下文：什么模式、授权了哪些文件夹、授权了哪些网络 | 临时给 AI 分配的工作环境 |

## 5.7 数据存储方式

| 数据类型 | 存在哪里 | 格式 | 通俗解释 |
|---------|---------|------|---------|
| 会话数据 | SQLite 数据库 | 会话档案表 | 包厢登记本，记录每个会话的基本信息 |
| 会话消息 | SQLite + 文件系统 | JSON 格式 | 完整聊天记录，像对话的逐字稿 |
| 长期记忆 | SQLite + 向量搜索 | 向量嵌入 | AI 的"记忆笔记本"，支持语义搜索（按意思找，不按关键词） |
| 定时任务 | SQLite 数据库 | 定时任务表 | 闹钟清单，记录所有定时任务的设置 |
| 系统配置 | TOML 文件 | opensquilla.toml | 餐厅的"经营手册"，定义网关、通道、服务商等全部配置 |
| 机器人配置 | TOML 文件 | agents.toml | 每个 AI 机器人的"员工档案"，定义各自的行为参数 |
| 技能文件 | Markdown 文件 | SKILL.md | 给 AI 的"操作手册"，告诉它遇到什么情况该怎么做 |
| 路由模型 | 二进制文件 | 模型文件 + 特征数据 | 智能路由器的"大脑"，用 LightGBM 算法训练出来的判断模型 |
| 诊断数据 | 文件系统 | JSON / 日志 | 系统运行日志，出问题时用来排查 |

## 核心概念速记

把整个数据模型用一句话串起来：

> **网关**（餐厅老板）管理着**通道**（外卖平台）和**沙箱**（安全规范），**会话管理器**（大堂经理）维护每个**会话**（包厢）的档案，**AI 引擎**（大厨）通过**服务商接口**（供应商）调用模型，**智能路由器**（领班）选最合适的模型，**调度器**（闹钟）按时触发任务，**应急方案**（替补机制）在出问题时自动切换。

## 5.8 一次真实对话中的数据流转

上面用餐厅比喻介绍了各个角色和物品，但还没讲它们是怎么配合的。下面以用户发一条消息为例，走一遍完整的数据流转。每一步都标注了涉及的数据实体和关键字段，用大白话说明发生了什么。

### 场景：用户说帮我写个排序函数

```
用户输入 帮我写个排序函数
        │
        ▼
┌─────────────────────────────────────────────────────┐
│ 第 1 步 · 创建用户消息                                  │
│                                                       │
│ 实体：Message                                          │
│   role        = "user"          ← 消息来源是真人用户       │
│   content     = "帮我写个排序函数"  ← 用户说的原话          │
│   timestamp   = 2026-07-22T20:18:00  ← 什么时候发的       │
│   message_id  = "msg_abc123"     ← 系统分配的唯一编号      │
│                                                       │
│ 大白话：系统收到用户的消息，先把它包装成一条标准的            │
│ "Message 实体"，就像服务员在点菜单上写下"3号桌要一份宫保鸡丁"。 │
└──────────────────────┬──────────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────────────┐
│ 第 2 步 · 会话查找（找到/创建聊天包厢）                     │
│                                                       │
│ 实体：Session                                          │
│   session_id    = "sess_xyz789"  ← 这个包厢的编号        │
│   status        = "active"       ← 包厢正在使用中         │
│   session_type  = "private"      ← 这是单人私聊          │
│   user_id       = "u_10086"      ← 谁在聊               │
│   created_at    = 2026-07-20     ← 这个包厢什么时候开的    │
│                                                       │
│ 调用：SessionManager.get_or_create(user_id, channel)    │
│                                                       │
│ 大白话：大堂经理（SessionManager）查登记本，看用户之前       │
│ 有没有开过包厢。有就继续用，没有就新开一个。                  │
│ 这一步决定了消息要放进哪个"包厢"里。                        │
└──────────────────────┬──────────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────────────┐
│ 第 3 步 · 上下文组装（给 AI 大厨准备"食材"）                │
│                                                       │
│ 三种"食材"拼在一起：                                     │
│                                                       │
│ ① 历史消息（从 Session 加载）                             │
│    实体：Message[]（数组）                                │
│      messages = [                                      │
│        {role:"user", content:"你好"},                   │
│        {role:"assistant", content:"你好！有什么可以帮您？"}, │
│        {role:"user", content:"帮我写个排序函数"}  ← 当前这条 │
│      ]                                                │
│    大白话：从包厢的聊天记录里翻出之前的对话，              │
│    让 AI 知道"之前聊了什么"。                            │
│                                                       │
│ ② 相关记忆（从 Memory 检索）                              │
│    实体：MemoryEntry（向量搜索返回的条目）                   │
│      memory_results = [                                │
│        {content:"用户是 Python 开发者", score:0.92},     │
│        {content:"用户偏好简洁代码", score:0.87}          │
│      ]                                                │
│    大白话：翻 AI 的"记忆笔记本"，用语义搜索找到和当前问题     │
│    相关的过往信息。不是按关键词搜，是按意思搜。               │
│                                                       │
│ ③ 系统配置（从 AgentConfig 获取）                          │
│    实体：AgentConfig                                     │
│      model          = "claude-sonnet-4"  ← 用哪个模型    │
│      max_turns      = 30               ← 最多聊几轮     │
│      temperature    = 0.7              ← 创造力高低      │
│      system_prompt  = "你是一个编程助手…" ← AI 的角色设定  │
│      tools          = ["read_file", "write_file", …]    │
│                                                       │
│    大白话：拿出 AI 的"员工手册"（AgentConfig），             │
│    告诉它"你是谁、你能用什么工具、你的行为边界是什么"。        │
└──────────────────────┬──────────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────────────┐
│ 第 4 步 · LLM 调用（AI 大厨开始"做菜"）                     │
│                                                       │
│ 实体：Provider（AI 服务商接口）                             │
│   provider_type  = "anthropic"   ← 用的是哪家 AI 公司    │
│   model          = "claude-sonnet-4"  ← 具体模型        │
│   认证方式        = 出示门禁卡（身份凭证）                    │
│                                                       │
│ 调用过程：                                              │
│   Provider.chat(                                       │
│     messages    = [历史消息 + 记忆 + 当前消息],            │
│     config      = AgentConfig,                          │
│     stream      = true    ← 流式返回，一个字一个字往外蹦    │
│   )                                                   │
│                                                       │
│ 返回结果 → 创建新的 Message 实体：                          │
│   role        = "assistant"     ← 这条是 AI 说的         │
│   content     = "好的，这是一个 Python 排序函数…"           │
│   消耗字数     = 156            ← AI 输出了多少字           │
│                                                       │
│ 大白话：AI 大厨收到"菜单"（上下文）后开始做菜。               │
│ 做菜的过程是"流式"的——一个字一个字往外蹦，                 │
│ 像厨师一边炒菜一边往外端，不用等全部做完才上菜。              │
│ 做完后把"菜"（AI 回复）也包装成一条 Message 实体。            │
└──────────────────────┬──────────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────────────┐
│ 第 5 步 · 工具调用（AI 需要"帮手"时）                       │
│                                                       │
│ 有时候 AI 不是直接回复，而是决定"我要用工具"。               │
│ 比如 AI 说："我先看看你项目里有什么文件"                    │
│                                                       │
│ ① 创建 ToolCall 实体（AI 说"我要用这个工具"）                │
│   tool_call_id  = "tc_001"        ← 工具调用的编号       │
│   tool_name     = "list_dir"      ← 调用哪个工具         │
│   arguments     = {"path":"/src"} ← 传给工具的参数       │
│   status        = "pending"       ← 等着执行             │
│                                                       │
│ ② 执行工具（系统真正去跑这个操作）                           │
│   沙箱里执行：ls /src → 返回文件列表                       │
│   SandboxPolicy 检查：这个操作在安全圈里吗？✅               │
│                                                       │
│ ③ 创建 ToolResult 实体（工具执行完的结果）                   │
│   tool_call_id   = "tc_001"       ← 对应哪个工具调用      │
│   output         = "main.py, utils.py, …"  ← 执行结果   │
│   exit_code      = 0             ← 0=成功               │
│   duration_ms    = 234           ← 执行花了多少毫秒      │
│                                                       │
│ ④ 把 ToolResult 再喂给 AI，AI 继续思考 → 回到第 4 步        │
│                                                       │
│ 大白话：AI 不只是动嘴，还能动手。                          │
│ 它说"我要看看文件"→ 创建 ToolCall（点菜单），               │
│ 系统去执行 → 拿到结果（ToolResult），                      │
│ 再把结果告诉 AI → AI 基于结果继续回答。                     │
│ 这一轮可能重复多次，AI 可以连续调用多个工具。                 │
└──────────────────────┬──────────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────────────┐
│ 第 6 步 · 会话更新（"结账"和打扫）                          │
│                                                       │
│ 实体：Session（更新字段）                                  │
│   input_tokens   += 512    ← 本轮输入消耗的量             │
│   output_tokens  += 156    ← 本轮输出产生的量             │
│   turn_count     += 1      ← 聊了第几轮了                │
│   updated_at     = 2026-07-22T20:18:05  ← 最后活跃时间   │
│                                                       │
│ 触发 Compaction 检查（对话压缩）：                          │
│   实体：CompactionRule                                   │
│     trigger_threshold = 10000  ← 超过 10000 就压缩       │
│     当前 total = input_tokens + output_tokens            │
│     如果超过阈值 → 把旧消息压缩成 CompactionSummary        │
│                                                       │
│ 实体：CompactionSummary（压缩结果）                         │
│   summary_text  = "用户是 Python 开发者，之前讨论了排序算法…" │
│   original_len  = 8500           ← 压缩前大小            │
│   compressed_len = 420           ← 压缩后大小            │
│                                                       │
│ 持久化：                                                │
│   所有变更写入 SQLite 数据库（Session 表 + Message 表）      │
│   记忆条目写入向量数据库（Memory 表）                        │
│                                                       │
│ 大白话：聊完一轮后，大堂经理更新包厢的登记信息——              │
│ 记下这轮花了多少 token、聊到第几轮了。                      │
│ 然后检查"包厢里的聊天记录是不是太长了"，                    │
│ 如果太长就压缩成摘要，省空间。最后把所有数据存进数据库。        │
│ 就像吃完饭结账、收拾桌子、存档小票。                         │
└─────────────────────────────────────────────────────┘
```
### 6 步总结

| 步骤 | 干什么 | 核心实体 | 餐厅比喻 |
|------|--------|---------|---------|
| 1. 创建消息 | 把用户输入包装成标准格式 | Message | 写点菜单 |
| 2. 会话查找 | 找到或创建聊天包厢 | Session、SessionManager | 大堂经理查登记本 |
| 3. 上下文组装 | 拼历史消息 + 记忆 + 配置 | Message[]、MemoryEntry、AgentConfig | 备菜（食材 + 记忆 + 菜谱） |
| 4. LLM 调用 | 调用 AI 模型，流式返回 | Provider、Message(assistant) | 大厨做菜、逐盘上菜 |
| 5. 工具调用 | AI 使用工具，拿到结果再继续 | ToolCall、ToolResult | 大厨喊帮手、帮手交差 |
| 6. 会话更新 | 更新用量统计，检查压缩，持久化 | Session、CompactionRule、CompactionSummary | 结账、打扫、存档 |

### 12 步总结

| 步骤 | 干什么 | 核心实体 | 源码路径 | 餐厅比喻 |
|------|--------|---------|---------|---------|
| 1. 消息到达 | 创建 Message + TranscriptEntry，触摸 SessionNode | Message, TranscriptEntry, SessionNode | turn_runner/input_stage.py | 服务员接单写单 |
| 2. 会话查找 | SQLite 查/建 SessionNode，规范化 session_key | SessionNode, SessionStorage | session/manager.py::get_or_create | 大堂经理查登记本 |
| 3. 路由决策 | SquillaRouter 分类 + RoutingPolicyEngine 把关 | SquillaRouter, RoutingDecision | engine/steps/squilla_router.py | 领班分配合适的厨师 |
| 4. 上下文组装 | 加载历史 + 检索记忆 + 获取配置 + 拼装 prompt | TranscriptEntry[], MemoryEntry, AgentConfig | turn_runner/prompt_assembler_stage.py | 备菜（食材+记忆+菜谱） |
| 5. 压缩检查 | T3 升级压缩 + 通用 overflow 压缩 | CompactionRequest, SessionSummary | turn_runner/compaction_and_history_stage.py | 整理老账本腾空间 |
| 6. Provider 调用 | Agent 状态机 → Provider.chat → 流式返回 | AgentState, StreamEvent, TextDeltaEvent | engine/agent.py::_turn_generator | 大厨做菜逐盘上菜 |
| 7. 工具调用 | 创建 ToolCall → 沙箱检查 → 执行 → ToolResult | ToolCall, ToolResult, ExecutionStatus | engine/agent.py::_execute_tool | 大厨喊帮手 |
| 8. 结果回传 | ToolResult 追加到消息列表 → 返回步骤 6 | Message(role="tool"), turn_messages[] | engine/agent.py 工具循环 | 帮手交差→大厨继续 |
| 9. 迭代控制 | 次数/预算/超时/死循环检测 | iterations, total_*_tokens, ProgressWatchdog | engine/agent.py 循环控制变量 | 厨房流程管控 |
| 10. 会话持久化 | TranscriptEntry(SQL) + SessionNode UPDATE + 记忆捕获 | TranscriptEntry, SessionNode, MemoryDurableReceipt | turn_runner/turn_finalizer_stage.py | 结账写入数据库 |
