## 定位

自动故障转移是 OmniRoute 的"保险丝"。当你在用的 AI 服务突然不可用（限流、宕机、余额不足），系统自动切换到备用服务商，你完全感觉不到切换。

> 来源：open-sse/services/emergencyFallback.ts L25-65 EmergencyFallbackConfig

---

## 生活化比喻

> 故障转移像**外卖平台的智能调度**：
> - 你点了一份外卖，首选餐厅（首选提供商）接单了
> - 如果餐厅太忙（限流），系统自动把订单转给附近另一家能做同样菜的餐厅（备用提供商）
> - 如果连着 3 家餐厅都拒绝了（熔断），系统暂停向该区域派单，过一会儿再试
> - 你全程只看到"骑手已接单"，不知道背后换了 3 家餐厅

## 一、ComboCooldownRetry — 智能重试调度器

### 问题

AI 提供商经常限流——"你请求太频繁了，请稍后再试"。但如果每次都等固定时间再重试，效率很低。

### 解决方案

ComboCooldownRetry 是一个纯函数（无副作用），根据错误类型和 Provider 状态决定"等多久、重试几次、换哪个 Provider"。

### 内部算法：5 步重试决策

```
提供商返回错误
  │
  ▼
步骤 1：判断错误类型
  - 限流错误（429 Too Many Requests）→ 可重试
  - 服务器错误（500/502/503）→ 可重试
  - 认证错误（401 Unauthorized）→ 不可重试，直接跳过
  - 余额不足（402 Payment Required）→ 不可重试，直接跳过
  大白话：判断是"临时堵车"还是"路封了"，前者等待，后者绕路

步骤 2：计算冷却时间
  - 第 1 次失败 → 等 1 秒
  - 第 2 次失败 → 等 2 秒
  - 第 3 次失败 → 等 4 秒
  - 以此类推（指数退避）
  大白话：失败次数越多，等待时间越长，避免"反复撞墙"

步骤 3：选择下一个提供商
  - 从 Combo 配置中按优先级选下一个
  - 跳过已标记为"冷却中"的提供商
  大白话：从候选名单中选下一个可用的快递公司

步骤 4：检查是否超过最大重试次数
  - 默认最大重试 3 次
  - 超过 → 返回错误给用户
  大白话：换了 3 家都不行，如实告诉用户

步骤 5：标记重试原因
  - 明确区分"可重试"和"不可重试"的原因
  - 50ms 容差：避免时钟偏差导致误判
  大白话：记录为什么换提供商，方便事后分析
```

> 来源：codegraph 源码 ComboCooldownRetry 纯函数逻辑（237 行）

### ComboCooldownRetry 核心数据结构

| 字段 | 类型 | 大白话 |
|------|------|--------|
| reason | 枚举 | 为什么会触发重试（限流/超时/服务器错误） |
| retryable | 布尔 | 是否值得重试（认证失败就不重试了） |
| cooldownMs | 数字 | 需要冷却多少毫秒 |
| targetProvider | 字符串 | 下一个要尝试的提供商 |
| attemptNumber | 数字 | 当前是第几次尝试 |

## 二、熔断器 (Circuit Breaker) — 防止连锁故障

### 问题

如果 A 提供商宕机了，大量请求涌入 B 提供商，B 也可能被压垮。这就像"雪崩"——一个故障引发连锁反应。

### 解决方案

熔断器像一个"智能电闸"：当某个提供商连续失败达到阈值，自动"跳闸"——暂停向该提供商发请求，等冷却后再尝试。

### 3 种熔断器状态

| 状态 | 大白话 | 触发器 |
|------|--------|--------|
| **关闭（正常）** | 电路正常，请求正常通过 | 初始状态 |
| **打开（熔断）** | 电路断开，拒绝所有请求 | 连续失败达到阈值（默认 3 次） |
| **半开（试探）** | 允许少量请求通过，测试是否恢复 | 冷却时间到（默认 60 秒） |

```
关闭状态 ──连续失败3次──▶ 打开状态 ──冷却60秒──▶ 半开状态
    ▲                                                    │
    └──────────── 试探成功 ───────────────────────────────┘
    如果试探失败 → 回到打开状态，冷却时间翻倍（最多 300 秒）
```

## 三、EmergencyFallback — 紧急回退

### 问题

熔断器需要时间触发。但如果整个 Combo（提供商组合）全部不可用怎么办？需要有一个"最后的救命稻草"。

### 解决方案

EmergencyFallback 是一个全局开关：当检测到严重故障时，把所有请求重定向到一个"保底"提供商。

### 内部算法：4 步紧急回退

```
步骤 1：isEmergencyFallbackEnvEnabled() — 检查全局开关
  - 500ms 缓存：避免每次都查数据库
  - 大白话：看看"紧急模式"开关有没有打开

步骤 2：shouldUseFallback() — 判断是否需要回退
  - 匹配 15 个预算关键词：budget/free/emergency/fallback/safe/backup
  - 大白话：检查当前提供商是否在"紧急回退名单"里

步骤 3：FallbackResult — 返回决策
  - FallbackDecision：需要回退，指向备用提供商
  - NoFallbackDecision：不需要回退，继续正常流程
  大白话：通知系统"换路"还是"继续走"

步骤 4：handleSingleModelChat() — 执行回退
  - 切换提供商 → 重新发起请求
  大白话：实际执行切换动作
```

> 来源：open-sse/services/emergencyFallback.ts L17-65

### EmergencyFallbackConfig 完整配置

| 字段 | 默认值 | 大白话 |
|------|--------|--------|
| enabled | true | 是否启用紧急回退 |
| provider | "nvidia" | 回退到哪个提供商 |
| model | "openai/gpt-oss-120b" | 回退到哪个模型（免费模型） |
| triggerOn402 | true | HTTP 402 错误是否触发回退 |
| triggerOnBudgetKeywords | true | 检测到预算关键词是否触发回退 |
| budgetKeywords | 15 个关键词 | 触发紧急回退的"暗号"（如 "insufficient funds"、"budget exceeded"） |
| skipForToolRequests | true | 工具调用请求是否跳过回退 |
| maxOutputTokens | 4096 | 回退模型的最大输出 token 数 |

## 四、配额 AutoPing — 保活机制

### 问题

很多 AI 提供商提供免费额度，但需要"活跃使用"才不回收。如果你一周没调用，免费额度可能被取消。

### 解决方案

QuotaAutoPing 定时给提供商发送"心跳请求"（ping），保持账号活跃，防止免费额度被回收。

### 内部算法：5 步自动 Ping

```
步骤 1：QuotaAutoPingDeps 初始化
  - 数据库连接、凭据管理器、熔断器状态
  大白话：准备好所有需要的工具

步骤 2：isPingCandidateBlocked() — 检查是否被阻止
  - 熔断器打开 → 跳过
  - 配额已用完 → 跳过
  大白话：如果提供商已经"拉黑"了，就别发了

步骤 3：refreshConnectionForPing() — 刷新连接
  - 刷新 OAuth token
  - 更新 API Key
  大白话：确保"钥匙"还没过期

步骤 4：pingConnection() — 发送心跳
  - 发送一个最小请求（不消耗 token）
  大白话：轻轻"碰一下"提供商，告诉它"我还活着"

步骤 5：记录结果
  - 成功 → 更新最后活跃时间
  - 失败 → 更新熔断器计数
  大白话：记录"打卡"成功或失败
```

## 五、关键设计决策

| 设计决策 | 大白话 |
|----------|--------|
| 指数退避而非固定等待 | 失败越多等越久，避免"反复撞墙" |
| 熔断器独立于重试 | 重试管"换谁"，熔断器管"啥时候别再试了" |
| 紧急回退作为最后防线 | 不是常规操作，只在"全部挂了"时才触发 |
| 50ms 容差 | 防止因为时钟不同步导致误判 |
| 500ms 缓存 | 紧急开关状态不需要实时更新，减少数据库压力 |
