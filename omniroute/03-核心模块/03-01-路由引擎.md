# 03-01 · 路由引擎 — 深度剖析

> **文件数**：src/sse/ + open-sse/ | **核心**：SSE 流式代理 | **提供商**：160+ | **codegraph 符号**：29 个

---

## 定位

路由引擎是 OmniRoute 的**心脏**。它就像一个"万能翻译官"——不管你用的是 OpenAI、Claude、Gemini 还是其他任何 AI 服务，你只需要用一种格式发送请求，引擎自动帮你翻译成对应服务商能理解的格式，把结果翻译回来，如果一家服务商临时不可用，自动换另一家。

> 来源：src/sse/handlers/、open-sse/ 目录

---

## 生活化比喻

> 路由引擎像一个**旅行社的智能客服系统**：
> - 客户想订机票（用户发 API 请求），不需要知道每家航空公司的订票流程
> - 客服系统自动检查客户身份（认证）、确认预算（配额）、选择最优航班（Combo 选择）
> - 如果首选航空公司满了（提供商限流），自动切换到备选（故障转移）
> - 订票全程录像（代理捕获），方便事后查账
> - 客户只需要用一种格式下单，系统自动适配各家航空公司的接口

## 一、3 层架构（大白话版）

系统分 3 层，像一个快递公司的运作流程：

```
第 1 层：收件窗口（入口层）
  用户从哪寄快递：
  - 网页版（Next.js 仪表盘，200+ 个页面）
  - 手机 App（Express 5 后端）
  - 开源协议（OpenSSE 标准接口）
  大白话：不管你从哪个窗口寄，快递单号格式都一样

第 2 层：分拣中心（代理引擎层）
  快递到了后做什么：
  - 拆包检查（安检流程：验证身份、检查包裹大小、防伪造）
  - 贴标签（记录寄件人信息）
  - 选快递公司（自动选最优提供商）
  - 压缩打包（压缩内容，节省运费）
  大白话：自动处理所有繁琐手续，不需要人工操作

第 3 层：快递公司（提供商适配层）
  实际送货的快递公司：
  - 160+ 家快递公司可选
  - 3 种合作方式：签合同（API Key）、授权登录（OAuth）、免费试用（Web 客户端）
  - 20 家需要授权登录
  - 14 家提供免费试用
  大白话：覆盖几乎所有主流 AI 服务
```

> 来源：codegraph explore "sse proxy engine" 的 29 个符号、扫描结果 200+ 路由

## 二、请求处理流程 —— 从入口到提供商

> ⚠️ 原文档描述的"12 步 AuthZ Pipeline"（`runAuthzPipeline` 及 12 个函数名）在源码中**不存在**。以下是源码中实际的请求处理流程。

### 实际的请求处理流程

```
用户请求到达 OmniRoute
  │
  ▼
┌─ 第 1 步：Next.js 中间件 ──────────────────────────────────────────┐
│ 请求首先经过 Next.js 中间件层。中间件负责：                          │
│   - 身份认证：验证 API Key 或 OAuth Token                           │
│   - 速率限制：检查请求是否超过配额                                    │
│   - 日志记录：记录请求基本信息                                       │
│ 大白话：门卫检查你的门禁卡和访客记录                                  │
└──────────────────────┬──────────────────────────────────────────────┘
                       ▼
┌─ 第 2 步：API 路由匹配 ─────────────────────────────────────────────┐
│ Next.js 将请求路由到对应的 API 端点（src/app/api/ 目录）。            │
│ 聊天请求 → /api/chat → src/sse/handlers/chat.ts                     │
│ 大白话：前台根据你的需求，把你带到正确的窗口                          │
└──────────────────────┬──────────────────────────────────────────────┘
                       ▼
┌─ 第 3 步：SSE 处理器 ───────────────────────────────────────────────┐
│ chat.ts 处理器接收请求，执行核心逻辑：                                │
│   - 解析请求体（模型、消息、参数）                                    │
│   - 应用压缩策略（RTK + Caveman）                                    │
│   - 调用 Combo 选择最优提供商                                        │
│ 大白话：分拣中心拆包、压缩、选快递公司                                │
└──────────────────────┬──────────────────────────────────────────────┘
                       ▼
┌─ 第 4 步：proxyFetch 代理转发 ──────────────────────────────────────┐
│ 通过 proxyFetch 将请求转发给选中的 AI 提供商。                        │
│   - 自动处理 TLS 指纹（绕过反爬检测）                                 │
│   - 自动处理代理（HTTP/SOCKS5 代理）                                 │
│   - 自动重试（网络错误、超时）                                        │
│   - 记录 AppliedProxySink（实际使用的代理信息）                       │
│ 大白话：快递公司取件、配送，全程追踪                                  │
└──────────────────────┬──────────────────────────────────────────────┘
                       ▼
┌─ 第 5 步：流式返回 ─────────────────────────────────────────────────┐
│ 将 AI 提供商的响应以 SSE 流式返回给用户。                             │
│   - 实时转发 token                                                   │
│   - 处理错误和重试                                                    │
│   - 记录用量统计                                                      │
│ 大白话：快递送到，拆包验货，签收                                      │
```

## 三、请求捕获机制（proxyFetch）—— 全程录像

### 问题
如果出了错，怎么知道是哪个环节出了问题？需要一份完整的"操作记录"。

### 解决方案
系统自动记录每次请求的完整信息：谁发的、发给了哪个 AI 服务商、服务商返回了什么、用了多少 token。

### 内部算法（5 步）

```
客户下单（用户发送请求）
  │
  ▼
步骤 1: 开启录像
  runWithAppliedProxyCapture()
  大白话：开始记录这次操作
  源码：open-sse/utils/proxyFetch.ts

步骤 2: 放入录像机
  appliedProxyContext
  大白话：创建一个"录像带"，存储本次操作的完整记录
  源码：open-sse/utils/proxyFetch.ts

步骤 3: 修改信封
  自动添加认证信息到请求头
  大白话：在快递单上自动填好你的身份信息，不需要你手动填

步骤 4: 发出快递
  发送请求到目标 AI 服务商
  大白话：实际把请求发给 AI 服务商

步骤 5: 收货录像
  捕获 AI 服务商返回的完整响应
  大白话：记录 AI 服务商返回了什么，用了多少 token
  返回 AppliedProxySink（录像带）
  源码：open-sse/utils/proxyFetch.ts:42
```

### 数据结构：AppliedProxySink（代理追踪）

`AppliedProxySink` 是一个简单的追踪对象，记录实际应用的代理配置。它只有一个字段 `proxy`，记录本次请求实际使用的代理配置（HTTP/SOCKS5 代理地址、认证信息等）。当执行器内部使用自己的代理时，`proxy` 字段会被更新为执行器实际使用的代理。

**大白话**：就像快递单上的"实际配送员"——不管谁接的单，最后送货的人会被记录下来，方便追踪。

> 来源：open-sse/utils/proxyFetch.ts:42
