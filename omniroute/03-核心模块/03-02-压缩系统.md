# 03-02 · 压缩系统 — 深度剖析

> **文件数**：open-sse/services/compression/ | **核心**：RTK + Caveman 双引擎 | **codegraph 符号**：50 个（跨 5 个文件）

---

## 定位

压缩系统是 OmniRoute 的"省钱引擎"。每次你跟 AI 聊天，背后都要花钱——每 1000 个字（token）几分钱。压缩系统的任务就是：把你说的话和 AI 的回话"压缩打包"，不改变意思但减少字数，直接省钱。

> 来源：open-sse/services/compression/types.ts L249-285 CompressionStats 接口

---

## 生活化比喻

> 压缩系统像**搬家公司的打包师傅**：
> - 你的东西（对话内容）很多很杂，师傅不会一件件搬，而是**分类打包**（结构化压缩）
> - 先把易碎品单独包好（保留关键信息），再把衣服用真空袋压缩（去掉冗余）
> - 最后标注每个箱子装了什么（压缩统计），方便拆箱时快速找到
> - 如果同样的东西之前搬过，师傅直接复用上次的打包方案（QuantumLock 缓存）

## 一、双引擎架构

OmniRoute 有 2 套压缩引擎，像两种不同的打包方式：

| 引擎 | 英文 | 大白话 | 适用场景 |
|------|------|--------|---------|
| **RTK** | RTK Compression | 结构化压缩：把内容按类型分类打包 | 长对话、多轮工具调用 |
| **Caveman** | Caveman Compression | 规则压缩：用预设规则删掉废话 | 简短对话、快速压缩 |

两者可以同时使用，像"先用真空袋压缩衣服，再用箱子分类打包"。

> 来源：open-sse/services/compression/engines/

---

## 二、Caveman 压缩引擎 — 规则驱动的"断舍离"

### 问题

对话中大量内容是"废话"——反复确认、重复说明、格式标记。这些内容对 AI 理解上下文没有帮助，但白白占用了 token 额度。

### 解决方案

Caveman 用一套预设**规则**（CavemanRule）自动识别和删除冗余内容，像一个"断舍离专家"。

### 内部算法：5 步规则压缩

```
原始对话内容
  │
  ▼
步骤 1：extractPreservedBlocks() — 提取保留块
  大白话：先把不能删的部分（代码块、URL、特定格式）提取出来，保护起来
  源码：compression/preservation.ts

步骤 2：getRulesForContext() — 根据上下文选择规则
  大白话：根据消息的角色（用户/系统/助手）和压缩强度，选出适用的规则
  源码：compression/cavemanRules.ts

步骤 3：逐条应用规则
  大白话：对每条消息，用选中的规则逐一匹配——删除冗余短语、礼貌用语、重复表达
  规则包括：redundant_phrasing（冗余短语）、pleasantries（客套话）、hedging（模糊表达）、redundant_directive（冗余指令）等
  源码：compression/caveman.ts — cavemanCompress()

步骤 4：restorePreservedBlocks() — 恢复保留块
  大白话：把步骤 1 中提取出来的保护内容放回去
  源码：compression/preservation.ts

步骤 5：createCompressionStats() + validateCompression()
  大白话：记录"原来多长→压缩后多长→省了多少钱"，并验证压缩结果是否有效
  源码：compression/stats.ts、compression/validation.ts
```

### 压缩规则数据结构

| 字段 | 类型 | 大白话 |
|------|------|--------|
| CavemanRule | 规则定义 | 一条"删除规则"，比如"删掉所有'好的，我明白了'" |
| CavemanConfig | 规则配置 | 哪些规则启用、哪些禁用 |
| CavemanIntensity | 强度等级 | 轻度/中度/重度压缩，像洗衣机的"轻柔/标准/强力"模式 |

> 来源：open-sse/services/compression/types.ts L29 CavemanIntensity, L45 CavemanRule, L56 CavemanConfig

## 三、RTK 压缩引擎 — 结构化压缩

### 问题

Caveman 只能删废话，但有些内容不能删只能"重组"。比如一段代码 100 行，但 AI 只需要知道"这段代码实现了排序功能，用了快速排序算法"——这需要理解内容后重新组织。

### 解决方案

RTK 把内容按类型（文本、代码、工具结果、图片）分类，对每类用不同的压缩策略，像一个"智能分类打包机"。

### 内部算法：5 步 RTK 压缩

```
步骤 1：adaptBodyForCompression(body, config)
  大白话：把消息体转成 RTK 能处理的格式
步骤 2：processRtkContent()
  大白话：分析内容，识别"这是代码"、"这是对话"、"这是工具返回结果"
步骤 3：processToolResultBlocks()
  大白话：工具返回的结果通常很长（比如一段代码），RTK 只保留关键信息
步骤 4：resolveToolMeta()
  大白话：提取工具调用的元信息（用了什么工具、参数是什么）
步骤 5：mergeRtkConfig()
  大白话：把用户自定义的压缩配置合并进来
```

> 来源：codegraph explore "compression caveman" — applyRtkCompression 调用链

### RTK 支持 5 种内容类型

RTK 根据内容类型使用不同的压缩策略：

| 内容类型 | 大白话 | 压缩策略 |
|--------|--------|---------|
| 代码差异 | 代码 diff 输出（如 Git diff） | 只保留变更摘要，删掉完整 diff |
| 结构化表格 | 表格数据 | 只保留表头和关键行 |
| 基础设施变更 | Terraform 等基础设施计划 | 只保留变更摘要 |
| 测试结果 | 测试通过/失败输出 | 失败时保留详情，通过时只保留摘要 |
| 通用类型 | 共享类型定义 | 按通用规则压缩 |

> 来源：open-sse/services/compression/engines/rtk/renderers/

## 四、QuantumLock 缓存 — 避免重复压缩

### 问题

同一个对话可能被压缩多次（每次 AI 回复后都要重新压缩整个对话历史）。如果每次都从头压缩，浪费计算资源。

### 解决方案

QuantumLock 是一个缓存前缀稳定化机制。当相同的请求体到达时，系统识别出"这个已经压缩过了"，直接返回缓存的压缩结果。

### 工作原理

| 做什么 | 大白话 |
|--------|--------|
| 计算缓存键 | 根据请求体内容生成唯一标识——就像给包裹贴条形码 |
| 检查缓存 | 压缩前先查缓存——有条形码就直接用旧方案，没有就执行压缩并存缓存 |
| 构建缓存上下文 | 收集压缩配置和检测上下文——打包师傅需要知道"用什么箱子、包多紧"

### 大白话理解

QuantumLock 就像快递公司的"打包方案库"：同样尺寸的箱子、同样的物品，之前已经设计过最佳打包方案，下次直接复用，不用重新设计。

> 来源：open-sse/services/compression/quantumLock/
步骤 2：QuantumLock 缓存检查 → 命中则直接返回
> 来源：open-sse/services/compression/quantumLock/

## 五、CompressionStats — 压缩统计

每次压缩后生成一份"压缩账单"：

| 字段 | 类型 | 大白话 |
|------|------|--------|
| originalTokens | 数字 | 压缩前用了多少 token（花了多少钱） |
| compressedTokens | 数字 | 压缩后用了多少 token（省了多少钱） |
| savingsPercent | 数字 | 节省百分比（比如 30% 表示省了 3 成） |
| techniquesUsed | 数组 | 用了哪些压缩技巧 |
| mode | 枚举 | 压缩模式（自动/手动/禁用） |
| engine | 字符串 | 用的哪个引擎（RTK 还是 Caveman） |
| rulesApplied | 数组 | 应用了哪些规则 |
| durationMs | 数字 | 压缩花了多少毫秒 |
| validationWarnings | 数组 | 压缩过程中的警告信息 |

> 来源：open-sse/services/compression/types.ts L249-285 CompressionStats 接口

## 六、关键设计决策

| 设计决策 | 大白话 |
|----------|--------|
| 双引擎而非单引擎 | 不同场景用不同压缩方式，像"搬家打包衣服用真空袋，打包瓷器用泡沫箱" |
| 规则驱动而非 AI 驱动 | 规则压缩速度极快（毫秒级），不需要额外调用 AI |
| QuantumLock 缓存 | 同一对话多次压缩不重复计算，节省 CPU |
| 强度可调 | 用户可以选择"轻度压缩"（保留更多细节）或"重度压缩"（最大化省钱） |
| 压缩统计透明 | 每次压缩后告诉用户"省了多少钱"，让省钱效果可见 |
