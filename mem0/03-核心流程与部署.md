## 1. 流程 1：add() 记忆添加的完整旅程

这是 mem0 最核心的流程。我们从用户说一句话开始，一步步追踪数据在 7 层架构中的完整流转。

### 场景设定

用户 "user_123" 在聊天应用中说了这样一句话：

**"我叫张三，今年 28 岁，喜欢川菜，住在北京朝阳区。对了，我最近买了一个 iPhone 15 Pro。"**

然后聊天应用调用 `memory.add("我叫张三，今年28岁，喜欢川菜，住在北京朝阳区。对了，我最近买了一个iPhone 15 Pro。", user_id="user_123")`。

这一行简单的代码，背后发生了什么？让我们逐层追踪。

### 第 1 层：用户接口层

聊天应用调用 `memory.add()` 方法。这是 Python SDK 的接口。如果是 TypeScript 应用，调用方式完全一样，只是语言不同。如果是云平台，调用方式也完全一样，只是底层通过 HTTPS 而不是本地调用。

### 第 2 层：Memory 核心层 —— 参数校验

Memory 类收到 add() 调用后，首先做参数校验。检查 user_id 是否为空——如果为空，直接抛出错误。

**为什么 user_id 必须非空？** 因为 user_id 是记忆的"归属标签"。没有这个标签，记忆就不知道属于谁。在你的 SaaS 应用中，如果有 1000 个用户，每个用户的记忆必须通过 user_id 来隔离。如果 user_id 为空，记忆就无法归属于任何用户，后续的 search 也无法过滤。

### 第 2 层：Memory 核心层 —— Phase 0（上下文收集）

mem0 收集 user_123 最近 10 条消息作为上下文。假设 user_123 之前说过"我最近在考虑换手机"，这条消息就会被收集。

**为什么需要上下文？** 因为单条消息可能信息不完整。比如 user_123 只说"最后买了 Pro 版本"，如果没有上下文，LLM 根本不知道"Pro 版本"指的是什么。有了上下文，LLM 就知道"Pro 版本"指的是 iPhone 15 Pro。

**为什么是 10 条？** 这是经验值。太少（2-3 条）可能信息不足，太多（50-100 条）可能包含无关信息，还会消耗更多 Token。10 条是一个平衡点。这个数字是可配置的——如果你的应用场景需要更长的上下文，可以调大。

### 第 2 层：Memory 核心层 —— Phase 1（已有记忆检索）

mem0 语义搜索 user_123 的已有记忆。假设 user_123 之前说过"我喜欢吃辣"，这条记忆会被检索出来。

**为什么需要检索已有记忆？** 这是 2026.04 新算法的关键优化。旧算法需要两次 LLM 调用——第一次提取增量记忆，第二次判断是否需要替换已有记忆。新算法通过提前检索已有记忆，把"提取"和"判断"合并为一次 LLM 调用。

具体来说，LLM 会收到这样的信息："用户已有记忆：喜欢辣。用户新消息：我叫张三，喜欢川菜。"LLM 看到后就知道，"喜欢川菜"是对"喜欢辣"的补充，而不是完全新的信息。

### 第 3 层：工厂层 —— 创建 LLM 实例

mem0 调用 LlmFactory.create(provider, config) 创建 LLM 实例。provider 是你配置的 LLM 提供商（如 "openai"、"deepseek"、"ollama"）。

**工厂在做什么？** 工厂查询注册表，找到 "openai" 对应的实现类，读取配置（api_key、model、temperature），创建实例。如果配置的 provider 是 "deepseek"，工厂就创建 DeepSeek 实例。代码不需要知道具体是哪个 LLM，只需要调用统一接口。

### 第 4 层：后端适配器层 —— LLM 提取记忆

LLM 实例收到请求，调用 OpenAI API（或其他提供商），发送 ADDITIVE_EXTRACTION_PROMPT 提示词和用户消息。

提示词告诉 LLM："你需要从以下对话中提取关键事实。如果发现用户有新的信息，添加为新记忆。如果发现用户修改了已有信息，标记为需要替换。返回 JSON 格式的结果。"

LLM 分析后，返回 JSON：

```json
{
  "additive": [
    {"memory": "用户叫张三"},
    {"memory": "用户28岁"},
    {"memory": "用户喜欢川菜"},
    {"memory": "用户住在北京朝阳区"},
    {"memory": "用户最近购买了iPhone 15 Pro"}
  ],
  "replacements": []
}
```

LLM 提取了 5 条新记忆，没有需要替换的旧记忆。如果是更新场景（比如"我搬家了，现在住上海"），LLM 会在 replacements 中返回需要替换的记忆。

**为什么 LLM 能理解"喜欢川菜"和"喜欢辣"的关系？** 因为 LLM 有语义理解能力。它知道"川菜"是辣的，所以"喜欢川菜"是对"喜欢辣"的具体化，不是矛盾的信息。这就是为什么用 LLM 来提取记忆——它比简单的关键词匹配聪明得多。

### 第 3 层：工厂层 —— 创建 Embedding 实例

mem0 调用 EmbedderFactory.create(provider, config) 创建 Embedding 实例。provider 是你配置的 Embedding 提供商（如 "openai"、"huggingface"、"ollama"）。

### 第 4 层：后端适配器层 —— 批量 Embedding

Embedding 实例收到请求，把 5 条记忆文本一次性发送给 Embedding API。API 返回 5 个向量（每个向量是 1536 维的数字，使用 OpenAI text-embedding-3-small 时）。

**为什么批量发送？** 这是 Token -90% 的关键。旧算法每条记忆单独调用 Embedding API，5 条记忆需要 5 次 API 调用。新算法一次调用嵌入所有 5 条记忆，只需要 1 次 API 调用。API 调用次数减少了 80%。

**向量是什么？** 向量是一串数字，代表文本的"语义指纹"。两条语义相似的文本，它们的向量在空间中距离很近。比如"喜欢川菜"和"爱吃辣"的向量距离很近，"喜欢川菜"和"住在北京"的向量距离很远。### 第 2 层：Memory 核心层 —— Phase 4（逐条 CPU 处理）

mem0 在 CPU 上计算每条记忆的 MD5 哈希值。哈希值就像记忆的"指纹"——相同内容的记忆会生成相同的哈希。

**为什么在 CPU 上处理？** 因为这个操作不消耗 API 调用，完全在本地完成。不需要网络请求，速度很快。

### 第 2 层：Memory 核心层 —— Phase 5（哈希去重）

mem0 查询 SQLiteManager，检查这 5 个哈希值是否已经存在。如果 user_123 之前已经说过"我叫张三"，这条记忆的哈希值已经存在，mem0 就跳过它。

**去重是全局的**——即使不同 user_id 的相同记忆，也会被去重。这确保了向量存储中不会有完全相同的重复记忆。

### 第 3 层：工厂层 —— 创建 VectorStore 实例

mem0 调用 VectorStoreFactory.create(provider, config) 创建 VectorStore 实例。provider 是你配置的向量存储提供商（如 "qdrant"、"pinecone"、"chroma"）。

### 第 4 层：后端适配器层 —— 批量持久化

VectorStore 实例收到请求，把去重后的 5 条记忆（向量 + 文本 + 元数据）一次性批量写入向量数据库。

**为什么批量写入？** 和批量 Embedding 同样的道理——减少 API 调用次数。旧算法每条记忆单独写入，5 条记忆需要 5 次写入操作。新算法一次写入所有 5 条记忆。

### 第 2 层：Memory 核心层 —— Phase 7（批量实体链接）

mem0 从记忆中提取实体：张三（PERSON）、川菜（FOOD）、北京朝阳区（LOCATION）、iPhone 15 Pro（PRODUCT）。然后：

1. 全局去重：检查实体存储中是否已有这些实体。如果"张三"已经存在，不重复插入
2. 批量嵌入：将实体名向量化
3. 搜索后 upsert：在实体存储中搜索相似实体。如果找到相似的，更新；如果没找到，插入新实体

**实体存储为什么独立？** 因为实体和记忆的访问模式不同。记忆是"内容"，实体是"索引"。独立后可以单独优化实体检索的性能。

### 第 6 层：辅助服务层 —— 保存消息

SQLiteManager 保存原始消息和操作记录。包括：谁（user_123）在什么时候（时间戳）添加了哪些记忆（5 条记忆 ID）。

### 第 2 层：Memory 核心层 —— Phase 8（返回结果）

mem0 把 5 条记忆的 ID 返回给应用。add() 流程结束。

**整个流程总结：** 从一句"我叫张三"到 5 条记忆存入向量数据库，经历了 9 个阶段、3 层工厂、4 个后端适配器。但对用户来说，只是一行代码。这就是 mem0 的价值——把复杂的东西藏在里面，暴露简单的接口。

## 2. 流程 2：search() 记忆搜索的完整旅程

### 场景设定

user_123 在聊天应用中问："我喜欢吃什么？"

聊天应用调用 `memory.search("我喜欢吃什么？", user_id="user_123", top_k=5)`。

### 第 2 层：Memory 核心层 —— Step 1（预处理）

mem0 对查询文本进行词形还原。中文用 jieba 分词，把"我喜欢吃什么"分成"我"、"喜欢"、"吃"、"什么"。

同时提取实体。如果查询中包含已知实体，记录下来。比如"我喜欢吃什么"中可能包含 FOOD 类型的实体。

**为什么需要分词？** 因为 BM25 关键词搜索需要知道查询中有哪些关键词。中文不像英文有空格分隔，所以需要 jieba 来分词。"喜欢"和"吃"是两个独立的关键词，BM25 会在文档中搜索这两个词。

**为什么需要提取实体？** 因为实体加成可以提高搜索质量。如果查询中包含 FOOD 类型的实体，给包含 FOOD 实体的记忆额外加分。

### 第 3 层：工厂层 —— 创建 Embedding 实例

mem0 调用 EmbedderFactory.create() 创建 Embedding 实例。

### 第 4 层：后端适配器层 —— 向量化查询

Embedding 实例把"我喜欢吃什么？"转换成 1536 维向量。这个向量代表了查询的"语义指纹"。

### 第 4 层：后端适配器层 —— 语义搜索

VectorStore 实例在向量数据库中搜索与查询向量最相似的记忆。超取 4 倍——top_k=5 时实际搜索 20 条。

**为什么超取？** 因为语义搜索可能漏掉一些相关结果。比如"我喜欢吃什么"和"用户爱吃川菜"在语义上接近，但向量距离可能不够近。超取后再通过后续步骤筛选，提高召回率。

**向量搜索的原理：** 在 1536 维空间中，计算查询向量和每条记忆向量的余弦相似度。相似度越高，说明语义越接近。返回相似度最高的 20 条。

### 第 2 层：Memory 核心层 —— Step 4（BM25 关键词搜索）

mem0 用 BM25 算法在已索引的文档中搜索"喜欢"、"吃"等关键词。

**BM25 是什么？** BM25 是一种经典的关键词搜索算法。它会考虑三个因素：
- 词频（TF）：关键词在文档中出现的次数。出现越多，分数越高
- 逆文档频率（IDF）：关键词在所有文档中的稀有程度。越稀有，权重越高
- 文档长度：长文档和短文档的公平比较。防止长文档仅仅因为更长就获得更高分数

**为什么需要 BM25？** 因为语义搜索可能漏掉精确匹配。比如"川菜"这个词在向量空间中可能和"辣"很近，但"川菜"和"川菜"的精确匹配只靠语义搜索是不够的。BM25 弥补了语义搜索的这个缺陷。

### 第 2 层：Memory 核心层 —— Step 5（计算 BM25 分数）

mem0 将 BM25 的原始分数归一化，和语义分数统一到相同尺度。

**为什么需要归一化？** 因为语义分数和 BM25 分数在完全不同的尺度上。语义分数是 0-1 的余弦相似度，BM25 分数可能是 0-100 的任意值。不归一化就无法公平比较。

### 第 2 层：Memory 核心层 —— Step 6（计算实体加成）

mem0 检查查询中是否包含已知实体。如果查询中包含 FOOD 类型的实体，给包含该实体的记忆额外加分。比如"用户喜欢川菜"这条记忆包含 FOOD 实体，会得到额外加分。

**ENTITY_BOOST_WEIGHT 参数控制实体加成的权重。** 默认值在代码中定义，可以根据需要调整。如果实体加成太强，可能把不相关的记忆也排到前面。如果太弱，实体加成的效果不明显。

### 第 2 层：Memory 核心层 —— Step 7（构建候选集）

mem0 合并语义搜索和 BM25 的结果，去重。两种搜索方式可能返回相同的记忆，需要去重。

### 第 2 层：Memory 核心层 —— Step 8（打分排序）

mem0 融合三种分数：语义相似度 + BM25 关键词匹配 + 实体加成。按总分排序，返回 top 5 条。

### 第 2 层：Memory 核心层 —— Step 9（格式化返回）

mem0 将结果格式化为 MemoryItem 列表，返回给应用。每条 MemoryItem 包含：记忆 ID、记忆内容、搜索得分、元数据等。

**整个流程总结：** 从一句"我喜欢吃什么"到 5 条最相关的记忆，经历了 9 个步骤、3 种搜索信号。但对用户来说，只是一行代码。## 3. 流程 3：update() 记忆更新

### 场景

user_123 说："我搬家了，现在住上海浦东。"

聊天应用调用 `memory.update(memory_id="mem_xxx", data="用户住在上海浦东")`。

### 流程

1. mem0 根据 memory_id 找到要更新的记忆
2. 重新向量化新内容"用户住在上海浦东"
3. 更新向量数据库中的向量和文本
4. 更新 SQLiteManager 中的哈希值
5. 返回更新后的记忆

**关键点：** 更新后，旧的"用户住在北京朝阳区"不再存在。搜索"用户住在哪里"时，只会返回"用户住在上海浦东"。这避免了记忆矛盾——同一个问题不会有两个不同的答案。

## 4. 流程 4：delete() 记忆删除

### 场景

user_123 说："算了，我不喜欢川菜了。"

聊天应用调用 `memory.delete(memory_id="mem_yyy")`。

### 硬删除

1. mem0 根据 memory_id 找到要删除的记忆
2. 从向量数据库中删除
3. 从 SQLiteManager 中删除
4. 返回删除成功

不可恢复。适用于"用户明确表示不需要这条信息"的场景。

### 衰减删除

user_123 说："今天心情不好。"（这条信息只今天有效）

聊天应用调用 `memory.delete(memory_id="mem_zzz", expires_at="2026-07-22")`。

1. mem0 不立即删除，而是设置过期时间
2. search() 时自动过滤过期的记忆
3. 定期清理任务最终删除过期的记忆

适用于"临时信息"的场景。比如：
- 用户今天的心情
- 用户今天想吃什么
- 用户当前的会话状态
- 用户临时提出的偏好

## 5. 流程 5：Agent 自主注册

### 场景

一个 AI Agent（比如 Claude Code）需要记忆能力。它不需要人类帮它注册，可以自己注册。

### 流程

1. Agent 在终端执行：`mem0 init --agent --agent-caller claude-code`
2. CLI 生成一个匿名用户 ID
3. CLI 向云平台注册，获取 API Key
4. CLI 把 API Key 保存到本地配置文件
5. Agent 现在可以使用 mem0 的 API 了

**对产品运营的价值：** 这意味着 Agent 可以自主使用 mem0，不需要人工干预。人类可以后续通过邮箱绑定来认领这个 Agent 的账户，把 Agent 的记忆归属到自己的账户下。

## 6. 三种部署模式详解

mem0 提供了三种部署模式，按需选择。

### 6.1 库模式

**安装方式：** `pip install mem0ai`

**适用场景：** 测试、原型开发、单个应用。

**优点：**
- 零配置，一行命令即可开始
- 本地运行，不需要网络
- 数据完全在本地，隐私安全

**缺点：**
- 不支持多用户并发
- 没有管理界面
- 数据存储在本地，无法共享

**工作原理：** 默认使用 Qdrant（本地模式）作为向量存储，SQLite 作为元数据存储。所有数据都在本地文件系统中。

### 6.2 自托管模式

**安装方式：** `docker compose up`

**适用场景：** 团队使用、企业部署。

**优点：**
- 支持多用户并发
- 有 Web 管理界面
- 支持 RBAC 和审计日志
- 数据在企业内部，安全可控

**缺点：**
- 需要自己部署和维护
- 需要配置 PostgreSQL 和向量数据库
- 有一定的运维成本

**工作原理：** FastAPI 服务作为 API 服务器，PostgreSQL 存储元数据，向量数据库（Qdrant/Pinecone 等）存储向量数据。用户通过 REST API 或 SDK 访问。

### 6.3 云平台模式

**安装方式：** 注册 app.mem0.ai

**适用场景：** 生产环境零运维。

**优点：**
- 零运维，mem0 团队负责维护
- 自动扩容，支持高并发
- 有 Web 管理界面

**缺点：**
- 数据存储在云平台，需要信任 mem0 团队
- 按使用量付费
- 网络延迟比本地模式高

**工作原理：** 客户端通过 HTTPS 调用 app.mem0.ai 的 API。所有数据存储在 mem0 的云基础设施中。## 7. 核心数据实体

### 7.1 MemoryItem（记忆条目）

这是 mem0 最基本的数据单元。一条记忆就是一个 MemoryItem。

| 字段 | 含义 | 例子 |
|------|------|------|
| id | 唯一标识 | "mem_abc123" |
| memory | 记忆内容 | "用户喜欢川菜" |
| hash | 内容哈希（MD5） | "a1b2c3d4..." |
| metadata | 元数据 | {"user_id": "user_123", "entities": ["FOOD"]} |
| score | 搜索得分 | 0.95 |
| created_at | 创建时间 | "2026-07-21T10:00:00Z" |
| updated_at | 更新时间 | "2026-07-21T10:00:00Z" |

### 7.2 MemoryConfig（配置）

| 配置项 | 含义 | 例子 |
|------|------|------|
| vector_store | 向量存储配置 | {"provider": "qdrant", "host": "localhost"} |
| llm | LLM 配置 | {"provider": "openai", "model": "gpt-4o"} |
| embedder | Embedding 配置 | {"provider": "openai", "model": "text-embedding-3-small"} |
| reranker | Reranker 配置 | {"provider": "cohere"} |
| history_db_path | 历史数据库路径 | "~/.mem0/history.db" |

### 7.3 自托管版数据模型

**User：**
| 字段 | 含义 |
|------|------|
| id | 用户 ID |
| name | 用户名 |
| email | 邮箱 |
| password_hash | 密码哈希 |
| role | 角色（admin/member） |
| created_at | 注册时间 |
| last_login_at | 最后登录时间 |

**APIKey：**
| 字段 | 含义 |

## 8. 安全机制

### 8.1 敏感字段脱敏

mem0 在日志输出时自动脱敏 20+ 个敏感字段名。任何匹配 api_key、password、token、secret 等字段的值，都会被替换为 [REDACTED]。

**为什么重要？** 因为日志可能被分享给第三方（比如技术支持），如果日志中包含 API Key，就会有安全风险。脱敏机制确保敏感信息不会泄露。

### 8.2 API Key 哈希存储

自托管版的 API Key 只存储 SHA256 哈希值，不存储明文。即使数据库被泄露，攻击者也无法获取 API Key。

### 8.3 输入校验

search() 的 query 参数必须是非空字符串。add() 的 user_id 必须非空。这些校验在系统入口就完成，防止非法数据进入系统。

## 9. 数据生命周期

从创建到删除，一条记忆的完整生命周期：

1. **创建：** add() → LLM 提取 → Embedding 向量化 → 哈希去重 → 向量库存储 + SQLite 记录
2. **读取：** search() → 查询向量化 → 语义搜索 + BM25 + 实体加成 → 排序返回
3. **更新：** update() → 重新向量化 → 更新向量库 + 更新 SQLite 记录 + 更新哈希
4. **删除（硬）：** delete() → 向量库删除 + SQLite 删除
5. **删除（衰减）：** delete() 带过期时间 → 设置过期时间戳 → search() 时过滤过期记忆 → 定期清理

## 总结

mem0 的核心流程围绕 add-search-update-delete 四个 CRUD 操作展开。add() 的 9 阶段管道和 search() 的 9 步流程是最复杂的两个流程，也是 mem0 核心竞争力的体现。Agent 自主注册让 AI Agent 可以无需人工干预地使用 mem0。三种部署模式满足不同场景的需求。数据实体以 MemoryItem 为核心，围绕它构建了配置层、存储层和自托管层。安全机制确保敏感数据不会泄露。## 补充：add() 流程的 9 阶段对照表

search() 的 Step 8 使用 `score_and_rank()` 函数融合三种信号。基于源码（main.py），融合机制如下：

**三种信号：**

1. **语义相似度（Semantic）：** 查询向量和记忆向量的余弦相似度。值域 0-1。越高越相似。
2. **BM25 关键词匹配（Keyword）：** 经典 TF-IDF 变体。考虑词频（关键词在记忆中出现次数）、逆文档频率（关键词在所有记忆中的稀有度）、文档长度（长记忆和短记忆的公平比较）。原始分数经过 `normalize_bm25()` 归一化到 0-1 区间。
3. **实体加成（Entity Boost）：** 如果查询中包含已知实体（如 PERSON、PRODUCT、LOCATION），给包含该实体的记忆额外加分。加成权重由 `ENTITY_BOOST_WEIGHT` 控制。

**融合方式：** 最终分数 = 语义分数 + BM25 分数 + 实体加成。三种分数直接相加（不是加权平均），因为它们在归一化后处于相同尺度。

**为什么需要三种信号？** 单一信号都有缺陷。纯语义搜索可能漏掉精确匹配（如"iPhone 15"和"苹果手机"语义不同但指同一产品），纯关键词搜索可能漏掉语义关联（"喜欢"和"爱吃"字面不同），实体加成帮两者建立桥梁。

## 补充：add() 的 ADD-only 提取（2026.04 新算法）

旧算法中，add() 的 LLM 提取阶段需要两次调用：一次提取增量记忆（additions），一次判断是否需要替换已有记忆（replacements）。新算法改为**单次 ADD-only 提取**：

- LLM 在一次调用中同时返回 additions（新增记忆）和 replacements（替换记忆）
- 记忆累积存储，不覆盖旧记忆（除非明确标记为替换）
- Agent 生成的事实以同等权重存储（当 Agent 确认某个操作时，该信息与用户直接输入的信息同等对待）

**实际效果：** Token 消耗从两次 LLM 调用减少到一次（-50%），加上批量 Embedding 和批量写入，总 Token 消耗降低 90%。

## 补充：search() 的 top_k 超取机制

search() 默认超取 4 倍。如果 top_k=10，实际从向量数据库搜索 40 条。为什么？

- 语义搜索的结果不一定是最相关的前 10 条——可能包含一些"语义相似但不相关"的结果
- 超取后，通过 BM25 关键词搜索和实体加成进行二次筛选和排序
- 最终返回的 top_k 条是经过三种信号融合排序后的最优结果
- 超取倍数可配置，默认 4 倍是经验值——在召回率和性能之间取得平衡

## 补充：词形还原（Lemmatization）详解

基于源码 `utils.py`，`lemmatize_for_bm25()` 函数对查询文本进行词形还原：

- **中文：** 使用 jieba 分词，将查询拆分为独立词汇
- **英文：** 使用 NLTK 词形还原，确保 "running" 和 "run" 被视为同一个词
- **目的：** 为 BM25 关键词搜索提供准确的索引词，而不是原始查询文本

**为什么需要词形还原？** 因为 BM25 是精确匹配算法。如果用户搜索 "running"，但记忆存储的是 "run"，BM25 默认匹配不到。词形还原将两者都归一化为 "run"，提高匹配率。
