## 1. 什么是 mem0？—— 先理解"AI 为什么需要记忆"

### 1.1 一个生活中的场景

想象你第一次去一家餐厅。服务员热情地招待你："欢迎光临！请问您想吃什么？"你点了一份宫保鸡丁。

第二天你又去了同一家餐厅。同一个服务员走过来，又问："欢迎光临，第一次来吗？请问您想吃什么？"

你心里想：我昨天才来过，你怎么就不记得了？

**这就是现在的 AI 应用。** 每次对话都是全新的，它不记得你上次说过什么、不记得你的名字、不记得你的偏好。每次见面都要重新自我介绍。

### 1.2 为什么 AI 会"失忆"？

这要从 AI 的工作原理说起。AI 大模型（比如 ChatGPT）的本质是一个"预测下一个词"的机器。它没有数据库、没有文件系统、没有"记住"的能力。它只能根据你当前输入的文字，预测最合适的回答。

你每次跟 ChatGPT 对话，它看到的只有当前对话窗口内的内容。这个窗口有长度限制（比如 GPT-4 是 128K tokens，大约 10 万汉字）。超过窗口的内容，它就"看不见"了。

打个比方：AI 就像一个有超强分析能力但只有 10 秒记忆的人。你跟他聊了 10 分钟，他只能记住最后 10 秒说了什么。前面的 9 分 50 秒，全部忘光了。

**这就是 mem0 要解决的问题。** mem0 给 AI 装上了一颗"人造海马体"——人脑中负责把短期记忆转化为长期记忆的器官。有了 mem0，AI 可以：
- 记住你是谁（姓名、年龄、职业）
- 记住你的偏好（喜欢川菜、讨厌香菜）
- 记住你聊过什么（上次聊到哪个话题了）
- 记住你的习惯（每天几点起床、用什么设备）

### 1.3 mem0 是怎么工作的？—— 一个简单的类比

把 mem0 想象成一个"超级秘书"。这个秘书的工作流程是：

1. **听**（add）：你说话时，秘书在旁听，把关键信息记下来。比如你说"我叫张三，住北京，喜欢川菜"，秘书在笔记本上写下三条备忘。
2. **找**（search）：你问"我喜欢吃什么？"，秘书翻笔记本，找到"喜欢川菜"这条备忘，告诉你。
3. **改**（update）：你说"我搬家了，现在住上海"，秘书把"住北京"划掉，改成"住上海"。
4. **删**（delete）：你说"对了，我不喜欢川菜了"，秘书把"喜欢川菜"这条撕掉。

这个"超级秘书"就是 mem0。它帮 AI 记住了所有需要记住的东西，让 AI 可以专注于"思考"和"回答"，而不是"回忆"。

### 1.4 mem0 的"后台"是什么？

上面的类比中，秘书用的是"笔记本"。但 mem0 用的不是笔记本，而是一套复杂的系统：

- 向量数据库：相当于"超级索引"，可以根据语义相似度快速找到相关记忆
- Embedding 模型：把文本变成"数字指纹"（向量），"喜欢川菜"和"爱吃川菜"的数字指纹很接近
- LLM（大语言模型）：从杂乱对话中提取结构化的关键信息
- 实体存储：记录"张三"是人名、"川菜"是食物、"北京"是地点

这些组件共同构成了 mem0 的"记忆系统"。但好消息是：你不需要理解这些组件怎么工作，只需要知道 mem0 提供了 add 和 search 两个简单的 API。

### 痛点 1：每个 AI 应用都在重复造轮子

**问题描述**：任何一个聊天机器人，只要想"记住"用户，都需要做以下事情：

1. 选一个向量数据库。市场上至少有 20 种选择：Qdrant、Pinecone、Chroma、Milvus、Weaviate、PGVector、Redis、Faiss、MongoDB、Elasticsearch……每一种都有自己的安装方式、API 风格、性能特点、价格模型。选错了怎么办？迁移成本非常高。

2. 选一个 Embedding 模型。需要把文本变成向量（数字指纹），才能进行语义搜索。可选的有 OpenAI、HuggingFace、Ollama、FastEmbed……每个模型的向量维度不同（1536？768？384？），质量不同，价格不同。

3. 写 LLM 提取逻辑。不能直接把对话原文存下来——"我啊，叫张三，爱吃辣，住北京"这种口语化表达需要被整理成结构化的记忆。怎么让 LLM 提取关键信息？提示词怎么写？返回格式怎么定义？

4. 写搜索逻辑。用户问"我喜欢吃什么"，怎么找到最相关的记忆？纯语义搜索可能漏掉，纯关键词搜索可能不准确。需要融合多种搜索方式。

5. 处理记忆更新。用户说"我搬家了"，怎么找到旧的地址记忆并更新？怎么避免记忆矛盾？

6. 处理多租户隔离。1000 个用户的记忆怎么互不干扰？

**这就像每个餐厅都要自己种菜、自己养猪、自己酿酒。** 不现实，也没必要。mem0 把这些事情全包了，你只需要调用一个 API。

### 痛点 2：记忆质量差，提取不准确

**问题描述**：如果只是简单地把对话原文存下来，那叫"聊天记录"，不叫"记忆"。两者的区别是什么？

聊天记录："我啊，叫张三，爱吃辣，住北京，对了，其实我不太能吃辣，但就是喜欢那个味道"

记忆应该提取出：
- 用户叫张三
- 用户喜欢川菜（喜欢辣的味道）
- 用户住在北京
- 用户不太能吃辣（但喜欢辣味）

这需要 LLM 来进行"语义理解"和"信息提取"。但普通的 LLM 调用可能：
- 提取出"用户爱吃辣"和"用户不太能吃辣"两条矛盾信息
- 漏掉"用户住在北京"
- 把"我喜欢那个味道"理解为"喜欢某种香水"

mem0 内置了精心设计的 ADDITIVE_EXTRACTION_PROMPT 提示词，专门优化过记忆提取的质量。2026.04 的新算法还在 LoCoMo 和 LongMemEval 两个基准测试上取得了 92.5 和 94.4 的分数（旧算法是 71.4 和 67.8）。

### 痛点 3：后端选型困难，切换成本高

**问题描述**：假设你一开始选择了 Qdrant 作为向量数据库。系统上线 3 个月后，你发现 Pinecone 的云服务更适合你的需求——自动扩容、免运维、全球部署。

怎么办？如果代码是直接调用 Qdrant 的 API 写的，你需要：
- 重写所有向量存储的代码（可能几百行）
- 重新测试所有搜索功能
- 迁移所有数据（格式可能不兼容）
- 可能影响线上服务

mem0 用工厂模式解决了这个问题。所有后端（向量存储、Embedding、LLM）都通过统一的接口暴露。切换后端只需要改一行配置，代码完全不用动。

**具体的例子**：从 OpenAI 切换到 Ollama 本地模型，只需要把配置中的 `llm.provider` 从 `"openai"` 改成 `"ollama"`，工厂会自动创建 Ollama 的实例。整个切换过程只需要改一行配置。

### 痛点 4：记忆缺乏结构化，搜索不准确

**问题描述**：普通的记忆存储只是文本，没有结构。搜索"用户喜欢什么"时，可能漏掉"用户爱吃川菜"这条记忆，因为"喜欢"和"爱吃"在字面上不一样。

更严重的是，不同的表述指向同一个实体："iPhone 15"和"苹果手机"、"张三"和"张总"、"朝阳区"和"北京朝阳"。如果只是文本匹配，这些关联会全部丢失。

mem0 通过实体提取解决了这个问题。它会自动识别：
- "张三" → PERSON 类型的实体
- "川菜" → FOOD 类型的实体
- "北京朝阳区" → LOCATION 类型的实体

搜索时，如果查询中包含已知实体，会给包含该实体的记忆额外加分。比如搜索"用户喜欢什么吃的"，实体 FOOD 会激活，所有包含 FOOD 类型实体的记忆都会得到加分。

### 痛点 5：记忆无限增长，检索越来越慢

**问题描述**：用户用久了，记忆越来越多。一个活跃用户可能有几千条记忆。1000 条记忆时搜索很快，10000 条时就慢了，100000 条时可能根本搜不到想要的。

而且，很多记忆是"临时性的"——"用户今天想吃什么"、"用户今天心情不好"、"用户正在看某部电影"。这些信息只在当天有效，但如果不清理，就会一直占用存储空间。

mem0 支持衰减机制——记忆可以设置过期时间，到期自动失效。临时信息 24 小时后自动过期，不需要手动清理。同时，mem0 的向量搜索支持超取 + 重排序，即使在大规模记忆库中也能保持搜索速度。## 3. 核心功能详解 —— 四个基本操作是怎么工作的

### 3.1 添加记忆（add）—— 把对话变成记忆

这是 mem0 最核心的功能。你给 mem0 一段对话，它自动提取关键事实，存为记忆。

**举个例子**：用户说"我啊，叫张三，今年28岁，喜欢川菜，住在北京朝阳区，对了，其实我不太能吃辣，但就是喜欢那个味道。"

mem0 不会把这段话原样存下来。它会做以下处理：

**第一步：理解上下文。** mem0 先看看这个用户之前说过什么（最近 10 条消息）。如果用户之前说过"我喜欢吃辣"，那 mem0 就知道"喜欢川菜"是和"喜欢吃辣"相关的信息，不是全新的信息。这避免了重复提取。

**第二步：调用 LLM 提取关键事实。** mem0 把这段话发给 LLM，LLM 提取出结构化的记忆：
- 用户叫张三
- 用户 28 岁
- 用户喜欢川菜（喜欢辣的味道）
- 用户住在北京朝阳区
- 用户不太能吃辣（但喜欢辣味）

注意，LLM 区分了"喜欢川菜"和"不太能吃辣"——这两条不矛盾，因为"喜欢那个味道"和"不能吃辣"是两回事。这就是好的 LLM 提取的价值。

**第三步：给每条记忆打上"指纹"。** mem0 调用 Embedding 模型，把每条记忆文本变成一串数字（向量）。"用户叫张三"变成 1536 个数字，这些数字代表这句话的"语义指纹"。

**第四步：检查是否有重复。** mem0 计算每条记忆的 MD5 哈希值（内容指纹），检查数据库中是否已有相同的记忆。如果"用户叫张三"之前已经存过了，就跳过。这避免了重复存储。

**第五步：存入数据库。** 向量（语义指纹）+ 文本 + 元数据（user_id、时间戳等）一起存入向量数据库。

**第六步：提取实体并建立关联。** mem0 从记忆中提取实体：张三（PERSON）、川菜（FOOD）、北京朝阳区（LOCATION）。这些实体存入独立的实体存储，后续搜索时可以通过实体关联找到相关记忆。

**整个过程在 9 个阶段中完成，但用户只需要调用一行 API。** 这就是 mem0 的价值——把复杂的处理逻辑封装起来，暴露简单的接口。

### 3.2 搜索记忆（search）—— 找到最相关的记忆

用户问"我喜欢吃什么？"，mem0 要找到最相关的记忆。

**为什么不能简单地"搜关键词"？** 因为人类的语言是模糊的。"喜欢吃什么"和"爱吃川菜"在字面上没有共同的关键词，但语义上高度相关。

mem0 用了三种搜索方式，然后把结果融合起来：

**方式一：语义搜索。** 把"我喜欢吃什么"向量化，在向量数据库中搜索最相似的向量。向量相似度高的记忆，说明语义上接近。比如"用户喜欢川菜"的向量和"我喜欢吃什么"的向量很接近。

**方式二：关键词搜索。** 用 BM25 算法搜索"喜欢"、"吃"等关键词。BM25 是一种经典的搜索引擎算法，它比简单的"包含关键词"更聪明——它会考虑关键词在文档中出现的次数、关键词在所有文档中的稀有程度、文档长度等因素。

**方式三：实体加成。** 如果查询中包含已知实体（比如 FOOD 类型），给包含该实体的记忆额外加分。比如"用户喜欢川菜"包含 FOOD 实体，会得到额外加分。

**三种方式互补，搜索质量最高。** 纯语义搜索可能漏掉关键词匹配，纯关键词搜索可能不理解语义，实体加成让实体层面的关联发挥作用。三种方式融合，就像一个"搜索委员会"——每个委员都有自己的专长，综合投票决定最终排名。

### 3.3 更新记忆（update）—— 修改已有的记忆

用户说"我搬家了，现在住上海了"。mem0 需要更新之前的"用户住在北京朝阳区"。

这个过程比较直接：指定要更新的记忆 ID 和新内容，mem0 重新向量化、重新存储、更新哈希值。旧的"北京朝阳区"记忆被替换为"上海"。

**为什么需要 update 而不是 delete + add？** 因为 update 保持了记忆的连续性。如果先 delete 再 add，中间会有一个"记忆消失"的时间窗口，可能导致搜索时找不到这条记忆。update 是原子操作——要么成功，要么失败，不存在中间状态。

### 3.4 删除记忆（delete）—— 移除不需要的记忆

两种删除方式，适用于不同的业务场景：

**硬删除**：直接从向量数据库中删除。和数据库的 DELETE 一样，删了就没了，不可恢复。适用于"用户明确要求删除"的场景。

**衰减删除（decay）**：设置过期时间，到期自动失效。适用于临时信息，比如"用户今天想吃什么"、"用户今天心情不好"。这些信息只在当天有效，24 小时后自动过期，不需要手动清理。

**为什么需要衰减删除？** 因为用户的记忆是动态的。一个人每天的心情、想吃什么、在做什么都会变化。如果这些临时信息永远存在，搜索时会返回大量"过时"的结果。衰减删除让记忆自动清理，保持记忆库的"新鲜度"。## 4. 目标用户 —— 谁需要 mem0？

mem0 不是给所有人用的。它解决的是"AI 应用需要记忆"这个具体问题。以下是四类典型用户：

### 4.1 AI 应用开发者

**典型场景**：你正在做一个 AI 聊天机器人（客服、教育、陪伴、医疗问诊等），需要在对话中"记住"用户的信息。

**核心痛点**：你知道需要记忆功能，但不想自己管理向量数据库、Embedding 模型、LLM 提取逻辑。这些都是基础设施，和你的业务逻辑无关。

**mem0 怎么帮你**：你只需要 `pip install mem0ai`，然后调用 `m.add()` 和 `m.search()`。剩下的——向量数据库选型、Embedding 模型调用、LLM 提取逻辑——mem0 全包了。你可以把精力放在业务逻辑上，而不是基础设施上。

**为什么选 mem0 而不是自己写？** 自己写可能需要 2-4 周的开发时间，而且质量难以保证。mem0 经过 25,000+ GitHub Stars 社区验证，质量有保障。而且后续的维护、升级、bug 修复都由 mem0 团队负责。

### 4.2 平台团队

**典型场景**：你在一个 SaaS 公司，公司有多个 AI 应用（客服机器人、营销助手、内部知识库等），需要统一的记忆管理平台。

**核心痛点**：每个应用各自管理记忆，数据分散、无法统一管控、安全合规难以保证。

**mem0 怎么帮你**：自托管版支持 Docker 部署，提供 RBAC 权限控制、API Key 管理、审计日志。你可以部署一个统一的 mem0 实例，所有 AI 应用共用。通过 user_id、agent_id、app_id、run_id 四个维度隔离不同应用的数据。

**为什么选自托管而不是云平台？** 数据安全——所有数据都在你自己的服务器上，不经过第三方。合规——支持审计日志、数据脱敏、访问控制。灵活——可以根据自己的需求扩展。

### 4.3 AI Agent 本身

**典型场景**：Claude Code、Cursor、Codex 等编程 Agent 需要跨会话记忆。比如"记住用户偏好用 TypeScript 而不是 JavaScript"、"记住项目中常用的 API 端点"。

**核心痛点**：Agent 没有"用户账户"的概念，无法通过传统的注册流程获取 API Key。

**mem0 怎么帮你**：CLI 工具支持 Agent 自主注册。Agent 运行 `mem0 init --agent --agent-caller claude-code`，自动生成匿名用户 ID、向云平台注册、获取 API Key、保存到本地。整个过程不需要人工干预。人类可以后续通过邮箱绑定来认领这个 Agent 的账户。

**为什么 Agent 需要记忆？** 没有记忆的 Agent 每次执行任务都是"从零开始"。它不知道用户之前做了什么、偏好什么、遇到过什么问题。有记忆的 Agent 可以"记住"用户的编码风格、项目结构、常用命令，效率大幅提升。

### 4.4 企业 IT

**典型场景**：公司部署 AI 应用，需要合规、审计、数据安全。

**核心痛点**：AI 应用处理用户数据，需要满足 GDPR、SOC2 等合规要求。需要审计日志、数据脱敏、访问控制。

**mem0 怎么帮你**：自托管版提供完整的审计功能——每个 API 请求都记录 method、path、status_code、latency_ms。API Key 只存储 SHA256 哈希值，不存储明文。敏感字段自动脱敏。支持 admin 和 member 两种角色。

mem0 最大的设计特点是"后端无关"——你可以随时更换底层组件，不影响业务代码。这就像乐高积木：你可以把红色积木换成蓝色积木，整体结构不变。

### 6.1 向量存储（25+ 种选择）

向量存储是 mem0 记忆的物理存储层。每条记忆被转换成向量后，存入向量数据库。

**为什么需要 25+ 种选择？** 因为不同的场景有不同的需求。一个个人项目可能只需要 Chroma（轻量、本地），一个企业级应用可能需要 Milvus（分布式、高可用），一个已经在用 PostgreSQL 的团队可能想用 PGVector（零额外部署）。

**25+ 种向量存储按使用场景分类：**

| 分类 | 代表 | 特点 | 适用场景 |
|------|------|------|---------|
| 开源高性能 | Qdrant | 用 Rust 写的，性能极高，支持过滤和分组 | 需要高性能的中型项目 |
| 云服务 | Pinecone | 免运维，自动扩容，全球部署 | 不想管基础设施的团队 |
| 轻量本地 | Chroma | 安装简单，适合本地开发 | 原型开发、个人项目 |
| 分布式 | Milvus | 支持水平扩展，十亿级向量 | 大规模生产环境 |
| 自带向量化 | Weaviate | 向量搜索 + 向量化一体化 | 想要一站式解决方案 |
| 数据库插件 | PGVector | PostgreSQL 扩展，零额外部署 | 已经在用 PostgreSQL 的团队 |
| 内存缓存 | Redis | 极快，但数据不持久化 | 需要低延迟的缓存场景 |
| 全文搜索 | Elasticsearch | 向量搜索 + 全文搜索一体化 | 需要全文搜索的场景 |
| 文档数据库 | MongoDB | 向量搜索 + 文档存储一体化 | 已经在用 MongoDB 的团队 |
| Facebook 开源 | Faiss | Facebook 开源的向量搜索库 | 需要极致性能的团队 |

**切换后端有多简单？** 只需要改一行配置。比如从 Qdrant 切换到 Pinecone：

- 旧配置：`vector_store.provider = "qdrant"`
- 新配置：`vector_store.provider = "pinecone"`

mem0 的工厂模式会自动创建 Pinecone 的实例，你的业务代码完全不用动。

### 6.2 Embedding 模型（12+ 种选择）

Embedding 模型把文本变成向量。一个好的 Embedding 模型能让"喜欢川菜"和"爱吃川菜"的向量距离很近，但和"住在北京"的向量距离很远。

**12+ 种 Embedding 模型按需求分类：**

| 分类 | 代表 | 特点 | 适用场景 |
|------|------|------|---------|
| 最高质量 | OpenAI text-embedding-3-small/large | 质量最高，有费用 | 追求质量的商业应用 |
| 企业集成 | Azure OpenAI | 与 Azure 生态集成 | 已经在用 Azure 的企业 |
| 开源可定制 | HuggingFace | 开源，可在本地部署 | 需要定制模型的团队 |
| 本地离线 | Ollama | 完全离线，隐私保护 | 需要数据隐私的场景 |
| 轻量快速 | FastEmbed | 快速，轻量 | 需要低延迟的场景 |
| Google 生态 | Gemini | 与 GCP 集成 | 已经在用 Google Cloud 的团队 |
| 统一接口 | LangChain | 统一多种 Embedding 的接口 | 已经在用 LangChain 的团队 |

**为什么 Embedding 模型的选择很重要？** 因为 Embedding 模型的质量直接决定了搜索的准确性。如果 Embedding 模型把"喜欢川菜"和"爱吃川菜"映射到距离很远的向量，搜索时就找不到这条记忆。OpenAI 的 text-embedding-3 是目前质量最高的选择之一，但需要付费。Ollama 可以免费在本地运行，但质量稍低。

### 6.3 LLM（20+ 种选择）

LLM 负责从对话中提取关键信息。这是 mem0 最核心的"智能"来源。

**20+ 种 LLM 按需求分类：**

| 分类 | 代表 | 特点 | 适用场景 |
|------|------|------|---------|
| 综合最强 | OpenAI GPT-4o | 质量最高，有费用 | 追求质量的商业应用 |
| 长上下文 | Anthropic Claude | 长上下文处理能力强 | 需要处理长对话的场景 |
| 高性价比 | DeepSeek | 质量高，价格低 | 需要控制成本的场景 |
| 低延迟 | Groq | 极低延迟 | 需要实时响应的场景 |
| 本地离线 | Ollama | 完全离线，隐私保护 | 需要数据隐私的场景 |
| 开源 | vLLM、Together | 开源，可定制 | 需要定制模型的团队 |

**为什么需要 20+ 种 LLM？** 因为 LLM 的选择直接影响两个关键指标：提取质量和成本。GPT-4o 提取质量最高，但每次调用需要消耗 Token（费用）。DeepSeek 质量接近 GPT-4o，但价格便宜很多。Ollama 完全免费，但质量稍低。你可以根据预算和质量要求选择最合适的 LLM。

## 7. 2026 年 4 月新算法 —— mem0 的"核武器"

2026 年 4 月，mem0 发布了一个重大算法更新。这个更新被 mem0 团队称为"新算法"（New Algorithm），因为它在 Token 消耗、延迟和记忆质量上都有数量级的提升。

### 7.1 旧算法 vs 新算法

| 维度 | 旧算法 | 新算法 | 提升幅度 |
|------|--------|--------|---------|
| LoCoMo 基准分数 | 71.4 | 92.5 | +29.6% |
| LongMemEval 基准分数 | 67.8 | 94.4 | +39.2% |
| Token 消耗 | 7,000+ | 700 | -90% |
| 延迟 P50 | 基准 | 0.88 秒 | -89% |
| LLM 调用次数 | 2 次 | 1 次 | -50% |
| Embedding 调用 | 逐条 | 批量 | 减少 90% |
| 实体链接 | 不支持 | 支持 | 全新功能 |
| 多信号检索 | 只有语义 | 语义 + 关键词 + 实体 | 全新功能 |
| 时序推理 | 不支持 | 支持 | 全新功能 |
| 衰减机制 | 不支持 | 支持 | 全新功能 |

### 7.2 新算法的核心思路

旧算法的工作流程是：

1. 第一次 LLM 调用：提取增量记忆（"用户说了什么新信息？"）
2. 第二次 LLM 调用：判断是否需要替换已有记忆（"这条新信息和旧记忆矛盾吗？"）
3. 每条记忆单独调用 Embedding API（4 条记忆 = 4 次 API 调用）
4. 每条记忆单独写入向量数据库（4 条记忆 = 4 次写入）

新算法的工作流程是：

1. 单次 LLM 调用：同时提取增量记忆 + 判断是否需要替换（"用户说了什么新信息？哪些旧信息需要更新？"）
2. 所有记忆一次性批量调用 Embedding API（4 条记忆 = 1 次 API 调用）
3. 所有记忆一次性批量写入向量数据库（4 条记忆 = 1 次写入）

**核心优化是"批量处理"。** 这就像快递配送——旧算法是每件快递单独送一趟，新算法是全部装车一起送。Token 消耗从 7,000 降到 700（-90%），延迟从秒级降到毫秒级（-89%）。

### 7.3 新算法带来的新功能

除了性能提升，新算法还带来了四个全新功能：

**实体链接**：自动识别"张三"和"user_123"是同一个实体，建立关联。搜索"张三"时，也能找到"user_123"相关的记忆。

**多信号检索**：融合语义搜索 + 关键词搜索 + 实体加成三种信号。单一信号可能漏掉相关结果，三种信号互补，搜索质量最高。

**时序推理**：理解记忆中的时间关系。知道"上周"、"昨天"、"2024年"的相对顺序，在搜索时能根据时间相关性排序。

**衰减机制**：记忆可以设置过期时间，到期自动失效。临时信息不需要手动清理，自动过期。## 8. 三种部署模式 —— 按需选择

mem0 提供三种使用方式，从简单到复杂，按需选择。

### 8.1 库模式 —— 最简单

**安装方式**：`pip install mem0ai`

**数据存储**：本地 Qdrant（向量）+ SQLite（元数据）

**适用场景**：测试、原型、单个应用。你正在开发一个 AI 聊天机器人，想快速验证记忆功能，不想部署任何额外服务。

**优点**：零配置，一行命令安装。所有数据在本地，不需要网络连接。适合快速原型开发。

**缺点**：不支持多应用共享。数据在本地，换机器就没了。不支持团队协作。

**典型用户**：独立开发者、正在做 PoC 的团队。

### 8.2 自托管 —— 团队/企业使用

**安装方式**：`docker compose up`

**数据存储**：PostgreSQL（元数据）+ 向量数据库（可选 Qdrant、Pinecone 等）

**适用场景**：团队使用、企业部署。你需要为多个 AI 应用提供统一的记忆管理，需要权限控制、审计日志、数据安全。

**优点**：数据在自己服务器上，安全可控。支持 RBAC 权限控制、API Key 管理、审计日志。多应用共享。可水平扩展。

**缺点**：需要自己运维。需要配置 Docker 环境。需要管理数据库。

**典型用户**：平台团队、企业 IT。

### 8.3 云平台 —— 零运维

**访问方式**：app.mem0.ai（注册即用）

**数据存储**：mem0 托管

**适用场景**：生产环境，不想管基础设施。你只需要记忆功能，不想管服务器、数据库、备份。

**优点**：零运维。自动扩容。全球部署。mem0 团队负责所有基础设施。

**缺点**：数据在第三方服务器上。有费用（按使用量计费）。需要网络连接。

**典型用户**：追求快速上线的创业团队。

### 8.4 三种模式的共同点

**API 完全一致。** 无论你用的是库模式、自托管还是云平台，API 都是一样的。你可以在库模式下开发，部署时切换到自托管或云平台，代码不需要改。这就是"后端无关"设计的好处。

**渐进式升级路径**：库模式 → 自托管 → 云平台。你不需要一开始就部署完整的服务栈。可以从本地开发开始，有需要时再升级。

## 9. 五条核心设计理念 —— mem0 为什么这样设计？

### 理念 1：记忆层独立

**设计原则**：记忆管理从应用代码中解耦。你不需要在应用里写向量数据库的查询语句，只需要调用 add 和 search。

**为什么这样设计？** 因为记忆管理是基础设施，不是业务逻辑。基础设施应该被封装起来，通过标准接口暴露。就像你不会在业务代码里写 TCP 协议的处理逻辑一样，你也不应该在业务代码里写向量数据库的查询逻辑。

**实际效果**：你的应用代码只关心"用户说了什么、需要什么记忆"，不关心"向量数据库怎么存、Embedding 模型怎么调"。关注点分离，代码更清晰。

### 理念 2：后端无关

**设计原则**：切换向量存储、Embedding 模型、LLM 提供商只需改一行配置。工厂模式在背后自动创建对应的实例。

**为什么这样设计？** 因为技术选型是动态的。今天的最佳选择，明天可能就不是了。如果你把代码写死在一个后端上，切换成本很高。后端无关让切换成本降到零。

**实际效果**：你可以从 OpenAI 切到 Ollama、从 Qdrant 切到 Pinecone、从 GPT-4o 切到 DeepSeek，只需要改一行配置。代码完全不用动。

### 理念 3：多租户支持

**设计原则**：user_id、agent_id、app_id、run_id 四个维度隔离不同实体的记忆。不同 user_id 的记忆即使内容完全相同，也是独立存储、独立检索的。

**为什么这样设计？** 因为现实世界中的 AI 应用几乎都是多租户的。一个 SaaS 产品可能有 1000 个用户，每个用户的记忆必须互相隔离。如果用户 A 的记忆被用户 B 搜索到，那就是严重的数据泄露。

**实际效果**：你可以在同一个 mem0 实例中为 1000 个用户维护完全隔离的记忆空间。每个用户只能看到自己的记忆。

### 理念 4：渐进式增强

**设计原则**：从 pip install 的库模式开始，到 docker compose up 的自托管，再到云平台，按需升级。

**为什么这样设计？** 因为不同阶段的需求不同。原型阶段不需要复杂的部署，生产阶段需要高可用和权限控制。渐进式增强让你在合适的时间做合适的升级。

**实际效果**：你不需要一开始就部署完整的服务栈。可以从本地开发开始，有需要时再升级到自托管或云平台。

### 理念 5：算法优先

**设计原则**：2026.04 新算法是核心竞争力。单次 LLM 调用、批量处理、实体链接、多信号检索、时序推理、衰减机制——这些不是功能列表，而是让记忆真正"有用"的关键。

**为什么这样设计？** 因为记忆管理的核心挑战不是"怎么存"，而是"怎么提取"和"怎么检索"。如果提取质量差，存再多记忆也没用。如果检索不准确，再快的搜索也没意义。

**实际效果**：2026.04 新算法在 LoCoMo 和 LongMemEval 两个基准测试上取得了 92.5 和 94.4 的高分，远超旧算法（71.4 和 67.8）。Token 消耗降低 90%，延迟降低 89%。## 10. 竞品对比 —— mem0 和其他方案的区别

### 10.1 和 LangChain Memory 的区别

LangChain Memory 是 LangChain 框架自带的记忆模块。它提供了 ConversationBufferMemory、ConversationSummaryMemory 等记忆类型。

**关键区别**：LangChain Memory 是"框架内"的记忆，mem0 是"独立于框架"的记忆。LangChain Memory 只能在 LangChain 应用中使用，mem0 可以在任何 Python 应用中使用。LangChain Memory 的功能比较简单（主要是对话历史管理），mem0 提供完整的记忆管理（提取、搜索、更新、删除、实体链接、衰减）。

**什么时候用 LangChain Memory？** 你已经在用 LangChain 框架，只需要简单的对话历史管理。

**什么时候用 mem0？** 你需要真正的记忆管理——不只是"记住对话"，而是"提取关键信息并建立结构化记忆"。

### 10.2 和 Pinecone 的区别

Pinecone 是一个向量数据库，mem0 是记忆管理平台。Pinecone 是 mem0 可以使用的向量存储后端之一。

**关键区别**：Pinecone 只负责"存储向量"，不负责"提取记忆"、"搜索优化"、"实体链接"、"衰减管理"。这些功能需要你自己写。mem0 把这些功能全包了，Pinecone 只是它底层可以选择的向量存储之一。

**什么时候用 Pinecone？** 你只需要向量存储，不需要记忆管理逻辑。

**什么时候用 mem0？** 你需要完整的记忆管理，Pinecone 可以作为 mem0 的向量存储后端。

### 10.3 和 Zep 的区别

Zep 是另一个 AI 记忆管理平台。和 mem0 定位类似，但设计理念不同。

**关键区别**：

| 维度 | mem0 | Zep |
|------|------|-----|
| 向量存储 | 25+ 后端可选 | 自研 |
| Embedding | 12+ 后端可选 | 内置 |
| LLM | 20+ 后端可选 | 内置 |
| 实体提取 | 内置 | 内置 |
| 时序推理 | 2026.04 新增 | 内置 |
| 衰减机制 | 2026.04 新增 | 内置 |
| 多语言 SDK | Python + TypeScript | Python + TypeScript |
| 自托管 | 支持 | 支持 |
| 开源 | Apache 2.0 | Apache 2.0 |
| 后端无关 | 是 | 否 |

**mem0 的优势**：后端无关，切换灵活。Zep 的向量存储和 Embedding 是内置的，不能切换。mem0 支持 25+ 向量存储和 12+ Embedding，选择更灵活。

**Zep 的优势**：时序推理和衰减机制比 mem0 早发布。但 mem0 在 2026.04 已经补齐了这些功能。

### 10.4 和 OpenAI Memory 的区别

OpenAI 的 Memory 功能是 ChatGPT 内置的记忆管理。它只能用于 ChatGPT，不能用于你自己的 AI 应用。

**关键区别**：OpenAI Memory 是"闭源"、"仅限 ChatGPT"，mem0 是"开源"、"任何 AI 应用"。如果你在开发自己的 AI 应用，不能用 OpenAI Memory，只能用 mem0 或自己写。

通知系统不是简单的"提示用户"，而是一个基于 PostHog 特性标志的远程控制展示系统。核心机制：

**展示控制：** 通知通过 PostHog 特性标志（feature flag）远程控制。mem0 团队可以在不发布新版本的情况下，远程开启/关闭某个通知，或者修改通知文案。这就像手机上 App 的"远程配置"——你在服务端改一个开关，客户端的行为就变了。

**频率限制（Rate Limiting）：** 每个通知类型有严格的展示频率限制，防止骚扰用户。所有通知的默认上限是 7 天内最多展示 10 次。超过上限后，通知在当前进程内不再触发。

**五种通知类型及其触发条件：**

| 通知类型 | 触发条件 | 具体阈值 |
|---------|---------|---------|
| 首次运行（first_run） | 用户第一次使用 mem0 | 每个用户仅触发一次 |
| 时序使用（temporal_usage） | 搜索时检测到时间相关查询 | 查询包含日期、时间戳、相对时间短语（昨天/上周） |
| 衰减使用（decay_usage） | 频繁使用 delete 操作 | 累计删除 5 次以上 |
| 规模阈值（scale_threshold） | 记忆数量或 top_k 参数过大 | 记忆数 > 2000 或 top_k > 50 |
| 慢查询（performance_slow_query） | 搜索耗时过长 | 单次搜索 > 2.0 秒 |

**特性错误通知：** 当用户使用了 OSS 版不支持的参数（如 timestamp、decay），mem0 不会崩溃，而是返回一段提示文案，告知用户该功能仅在托管平台可用。

**对产品运营的价值：** 通知系统可以帮助你了解用户的使用模式——他们是否频繁删除记忆（说明记忆提取质量可能有问题）、搜索是否太慢（说明需要升级向量存储）、记忆数量是否接近上限（说明需要扩容）。

# mem0 架构与核心模块 —— 从 7 层架构到 24 个核心模块

> GitHub: https://github.com/mem0ai/mem0 | commit fec2fe6 | Apache 2.0

## 1. 为什么需要理解架构？

先回答一个问题：你作为产品经理，为什么需要理解 mem0 的架构？

因为架构决定了 mem0 能做什么、不能做什么、以及将来能扩展什么。

举个例子：如果你知道 mem0 的向量存储层是"可插拔"的，你就知道可以随时从本地 Qdrant 切换到云端的 Pinecone，不需要重写任何代码。如果你知道工厂模式是怎么工作的，你就知道为什么 mem0 能支持 25 种向量数据库——不是硬编码，而是通过统一的接口。

理解架构，就是理解 mem0 的"生长能力"——它能在多大程度上适应你的业务需求变化。

## 2. 7 层架构全景图

把 mem0 想象成一栋 7 层大楼。每层有明确的职责，层与层之间通过标准接口通信。改一层不影响其他层。

### 第 1 层：用户接口层 —— 你看到的部分

这一层是用户直接接触的部分。你可以通过以下方式使用 mem0：

- Python SDK：在你的 Python 代码里 `from mem0 import Memory`，然后调用 `m.add()` 和 `m.search()`
- TypeScript SDK：在 Node.js 代码里使用，API 和 Python 版本一致
- REST API：通过 HTTP 请求调用自托管版的 API
- 云平台 API：通过 app.mem0.ai 的 API 调用，不需要自己部署
- CLI 工具：在终端里使用命令行工具

**为什么提供了这么多接口？** 因为不同的用户有不同的使用场景。Python 开发者喜欢 SDK，前端开发者喜欢 TypeScript，运维团队喜欢 REST API，不想运维的团队喜欢云平台。mem0 覆盖了所有场景。

### 第 2 层：Memory 核心层 —— 大脑

这一层是 mem0 的"大脑"。所有的记忆管理逻辑都在这里。核心类是 `Memory`（文件：mem0/memory/main.py，3790 行）。

Memory 类提供了 7 个核心方法：

| 方法 | 作用 | 类比 |
|------|------|------|
| add() | 添加记忆 | 秘书在笔记本上写备忘 |
| search() | 搜索记忆 | 秘书翻笔记本找笔记 |
| update() | 更新记忆 | 秘书划掉旧笔记，写新的 |
| delete() | 删除记忆 | 秘书撕掉一页笔记 |
| get_all() | 分页获取所有记忆 | 秘书按页码翻笔记本 |
| history() | 查看记忆变更历史 | 秘书翻日志看谁改了什么 |
| reset() | 清空所有记忆 | 秘书把笔记本全撕了 |

每个方法内部都有复杂的处理逻辑，但我们从外部看，只需要知道这些方法的名字和作用。这就是"封装"的好处——复杂的东西藏在里面，外面看起来很简单。

### 第 3 层：工厂层 —— 万能转接头

这一层是 mem0 实现"后端无关"的关键。有四个工厂类：

- VectorStoreFactory：创建向量存储实例
- EmbedderFactory：创建 Embedding 实例
- LlmFactory：创建 LLM 实例
- RerankerFactory：创建 Reranker 实例

**工厂模式是什么？** 工厂模式就像一个"万能转接头"。你有一个中国插头（你的代码），要插到不同国家的插座（不同的后端）。工厂就是那个转接头——你把配置给它，它给你一个能用的实例。

比如，你告诉工厂"我要用 Qdrant"，工厂就创建一个 Qdrant 实例。你告诉工厂"我要用 Pinecone"，工厂就创建一个 Pinecone 实例。你不需要知道 Qdrant 和 Pinecone 内部怎么实现，只需要知道它们都实现了相同的接口。

**为什么需要工厂模式？** 因为 mem0 要支持 25+ 向量存储、12+ Embedding、20+ LLM。如果不用工厂模式，每种后端都要写一套 if-else 判断，代码会非常混乱。工厂模式让每种后端都通过相同的接口暴露，切换后端时不需要修改任何业务代码。### 第 4 层：后端适配器层 —— 25+ 种后端

这一层是真正的"干活"的地方。工厂创建了实例，这些实例负责实际的向量存储、文本嵌入、LLM 调用。

**向量存储适配器（25+ 种）：**

mem0 支持 25+ 种向量数据库，每种都有自己的适配器。适配器实现了 VectorStoreBase 抽象基类中定义的接口（insert、search、delete、update 等）。

| 类别 | 代表 | 适用场景 |
|------|------|---------|
| 开源高性能 | Qdrant、Milvus、Weaviate | 生产环境，需要高性能和可控性 |
| 云服务 | Pinecone、Databricks、Azure AI Search | 不想自己运维，按量付费 |
| 轻量本地 | Chroma、Faiss | 开发测试，快速上手 |
| 数据库插件 | PGVector、Redis、MongoDB、Elasticsearch | 已有这些数据库，不想引入新组件 |
| 全文搜索 | Elasticsearch、OpenSearch | 需要全文搜索能力的场景 |

**为什么支持这么多？** 因为不同的团队有不同的技术栈。一个团队可能已经在用 PostgreSQL，他们就可以用 PGVector 插件，不需要再部署一个 Qdrant。另一个团队可能想要最高性能，他们就会选 Milvus。mem0 不强制你用什么，让你根据自己情况选择。

**Embedding 适配器（12+ 种）：**

Embedding 模型负责把文本变成向量。支持 OpenAI、HuggingFace、Ollama、FastEmbed、Gemini 等。

**LLM 适配器（20+ 种）：**

LLM 负责从对话中提取记忆、生成查询。支持 OpenAI、Anthropic、DeepSeek、Groq、Ollama 等。

**Reranker 适配器（5 种）：**

Reranker 负责对 search 结果进行二次排序。支持 Cohere、HuggingFace、Voyage、LLM-based、No-op。

### 第 5 层：配置层 —— 所有配置在这里

这一层管理 mem0 的所有配置。核心是 Pydantic 配置模型。

**MemoryConfig：** 根配置类，包含四个子配置：
- VectorStoreConfig：向量存储配置（provider、host、port、api_key 等）
- LlmConfig：LLM 配置（provider、model、temperature、api_key 等）
- EmbedderConfig：Embedding 配置（provider、model、dimensions 等）
- RerankerConfig：Reranker 配置（provider、model 等）

**为什么用 Pydantic？** Pydantic 是一种 Python 库，专门用于数据校验。它会自动检查你传入的配置是否正确。比如，如果你把 provider 写成 "opneai"（拼写错误），Pydantic 会在启动时就报错，而不是等到运行时才发现。这种"早发现、早修复"的机制能节省大量调试时间。

**提示词模板：** 定义在 configs/prompts.py 中。包含 LLM 提取记忆时使用的提示词模板。这些模板可以自定义，但默认的模板已经覆盖了大多数场景。

### 第 6 层：辅助服务层 —— 幕后英雄

这一层提供非核心但必要的辅助功能。

**存储管理（SQLiteManager）：** 管理记忆的元数据（操作历史、去重哈希）。库模式使用 SQLite，自托管模式使用 PostgreSQL。

**通知系统（notices.py）：** 智能使用提示。当检测到特定使用模式时，自动向用户展示功能建议。比如，当记忆数量接近限制时，提示用户考虑升级；当用户使用 delete 时，提示衰减功能的存在。

**遥测系统（telemetry.py）：** 可选的匿名使用统计。通过环境变量控制开关。不收集敏感数据。

**安全机制（security.py）：** 三层保护：敏感字段脱敏（20+ 个字段名自动替换为 [REDACTED]）、运行时字段保护（非序列化对象保护）、输入校验（query 非空、user_id 非空）。

**词形还原（lemmatization.py）：** 对中英文查询进行词形还原。中文用 jieba 分词，英文用 NLTK 词形还原。这确保"running"和"run"在 BM25 搜索中被视为同一个词。

**打分排序（scoring.py）：** 融合语义分数、BM25 分数、实体加成，计算最终排序分数。

### 第 7 层：数据存储层 —— 数据实际存储的地方

这一层是数据实际存储的地方。分为两部分：

**向量数据：** 存储在 25+ 向量数据库之一。每条记忆对应一个向量 + 文本 + 元数据。

**元数据：** 存储在 SQLite（库模式）或 PostgreSQL（自托管模式）。包括操作历史、去重哈希、用户信息、API Key 等。

**实体存储：** 独立的向量库，专门存储实体（人名、地名、产品名等）。与记忆向量库分离，互不干扰。## 3. 工厂模式详解 —— mem0 的"万能转接头"

工厂模式是 mem0 实现"后端无关"的核心机制。我们深入看看它是怎么工作的。

### 3.1 什么是工厂模式？

先讲一个生活中的例子。你去餐厅点菜，服务员问你要什么饮料。你说"可乐"。服务员去后厨，从冰箱里拿了一瓶可乐给你。你不需要自己进后厨找冰箱，你只需要告诉服务员你要什么，服务员帮你拿。

在 mem0 中，工厂（Factory）就是那个"服务员"。你告诉工厂"我要用 Qdrant 作为向量存储"，工厂就去"后厨"（代码库）找到 Qdrant 的实现类，创建实例，返回给你。你不需要知道 Qdrant 怎么初始化、怎么连接、需要什么参数——工厂全帮你处理了。

### 3.2 四个工厂类

mem0 有四个工厂类，分别负责创建不同类型的后端实例：

**VectorStoreFactory（向量存储工厂）：**

创建向量存储实例。根据配置中的 provider 字段（如 "qdrant"、"pinecone"、"chroma"）创建对应的实例。内部维护一个注册表，将 provider 名称映射到具体的实现类。

举个例子：你配置 provider="qdrant"，工厂自动创建 Qdrant 实例，处理 Qdrant 特有的连接参数（host、port、collection_name）。你配置 provider="pinecone"，工厂自动创建 Pinecone 实例，处理 Pinecone 特有的参数（api_key、environment、index_name）。

**EmbedderFactory（Embedding 工厂）：**

创建 Embedding 实例。根据配置中的 provider 字段（如 "openai"、"huggingface"、"ollama"）创建对应的实例。

不同的 Embedding 提供商生成的向量维度不同。比如 OpenAI text-embedding-3-small 生成 1536 维向量，OpenAI text-embedding-3-large 生成 3072 维向量。工厂会自动处理这些差异。

**LlmFactory（LLM 工厂）：**

创建 LLM 实例。根据配置中的 provider 字段（如 "openai"、"anthropic"、"deepseek"）创建对应的实例。

不同的 LLM 有不同的 API 格式、不同的参数。比如 OpenAI 用 ChatCompletion API，Anthropic 用 Messages API。工厂会自动适配这些差异。

**RerankerFactory（Reranker 工厂）：**

创建 Reranker 实例。Reranker 是可选的——如果未配置，工厂返回 No-op 实例（什么都不做）。

### 3.3 工厂模式带来的好处

**好处 1：切换后端只需改一行配置。**

从 Qdrant 切换到 Pinecone：把配置文件中的 `provider: "qdrant"` 改成 `provider: "pinecone"`，加上 Pinecone 的 API Key。重启应用。完成。代码一行都不用改。

**好处 2：新增后端不需要改核心代码。**

如果 mem0 团队想支持一个新的向量数据库（比如 ClickHouse），只需要写一个新的适配器类，实现 VectorStoreBase 接口，然后注册到工厂。核心代码完全不用动。

**好处 3：测试时可以切换后端。**

开发时用 Chroma（轻量本地），测试时用 Qdrant（开源高性能），生产环境用 Pinecone（云服务高可用）。三个环境用不同的后端，但代码完全一样。

**好处 4：降低成本。**

如果你的 LLM 调用量很大，可以切换到 DeepSeek（高性价比）。如果你的 Embedding 调用量很大，可以切换到 FastEmbed（本地免费）。工厂模式让这种切换变得非常简单。

## 4. 核心模块详解 —— 24 个模块逐一拆解

mem0 有 24 个核心模块。我们不一一列出代码细节，而是从"这个模块做什么、为什么需要、怎么工作"三个角度来理解。

### 4.1 Memory 核心（mod:memory_core）

这是 mem0 的"大脑"。3790 行代码，7 个核心方法。最重要的是 add() 和 search()。

**add() 的 9 阶段管道（V3 Phased Batch Pipeline）：**

这是 2026.04 新算法的核心。旧算法需要两次 LLM 调用，新算法合并为一次。

- Phase 0 — 上下文收集：收集最近 10 条消息作为上下文。为什么是 10 条？因为太少（2-3 条）可能信息不足，太多（50-100 条）可能包含无关信息。10 条是经验值，平衡了上下文质量和 Token 消耗。
- Phase 1 — 已有记忆检索：语义搜索已有记忆，避免 LLM 重复提取已经知道的信息。这是新算法只需要一次 LLM 调用的关键——LLM 在提取新记忆时，已经知道哪些记忆已经存在。
- Phase 2 — LLM 提取：单次调用 LLM，同时提取增量记忆和替换记忆。LLM 返回 JSON 格式的结果。
- Phase 3 — 批量 Embedding：将所有提取的文本一次性批量向量化。这是 Token -90% 的关键——旧算法每条记忆单独调用 API，新算法一次调用嵌入所有文本。
- Phase 4 — 逐条 CPU 处理：计算每条记忆的 MD5 哈希，用于去重。这个操作不消耗 API 调用。
- Phase 5 — 哈希去重：检查数据库中是否已存在相同哈希。去重是全局的——不同 user_id 的相同记忆也被去重。
- Phase 6 — 批量持久化：一次性将去重后的记忆批量写入向量数据库。
- Phase 7 — 批量实体链接：提取实体 → 全局去重 → 批量嵌入 → 搜索后 upsert。实体存储使用独立的向量库。
- Phase 8 — 保存消息 + 返回：将原始消息保存到 SQLiteManager，返回记忆 ID 列表。

**search() 的 9 步流程：**

- Step 1 — 预处理：词形还原 + 实体提取。中文用 jieba 分词，英文用 NLTK 词形还原。
- Step 2 — 向量化：Embedding 模型将查询向量化。
- Step 3 — 语义搜索：向量数据库 ANN 检索，超取 4 倍。top_k=10 时实际搜索 40 条。
- Step 4 — 关键词搜索：BM25 倒排索引匹配，捕捉精确词汇匹配。
- Step 5 — 计算 BM25 分数：归一化 BM25 分数，与语义分数统一到相同尺度。
- Step 6 — 计算实体加成：如果查询包含已知实体，给包含该实体的记忆加分。
- Step 7 — 构建候选集：合并语义搜索和 BM25 结果，去重。
- Step 8 — 打分排序：融合语义分数 + BM25 分数 + 实体加成，按总分排序。
- Step 9 — 格式化返回：返回按分数排序的前 top_k 条 MemoryItem。### 4.2 实体存储（mod:entity_store）

mem0 有一个独立的实体存储系统，与记忆向量库完全分离。

**什么是实体？** 实体是指对话中出现的具体事物：人名（张三）、地名（北京）、产品名（iPhone 15）、组织名（字节跳动）等。mem0 自动识别这些实体，存入独立的实体向量库。

**实体存储的工作流程：**

1. 当 add() 提取记忆时，同时提取实体。比如从"张三在北京买了 iPhone 15"中提取 PERSON=张三、LOCATION=北京、PRODUCT=iPhone 15
2. 全局去重：检查实体存储中是否已有这些实体。如果"张三"已经存在，就不重复插入
3. 批量嵌入：将实体名向量化
4. 搜索后 upsert：在实体存储中搜索相似实体，找到则更新，没找到则插入

**实体存储为什么独立？** 因为实体和记忆的访问模式不同。记忆是"内容"，实体是"索引"。实体存储独立后，可以单独优化实体检索的性能，不影响记忆检索。

**实体存储的价值：** 当 search() 时，如果查询包含已知实体，给包含该实体的记忆额外加分。比如搜索"iPhone 15 价格"时，实体存储识别出 PRODUCT=iPhone 15，所有包含该实体的记忆都会得到额外加分。这解决了"同一实体不同表述"的问题——"iPhone 15"和"苹果手机"在向量空间可能距离很远，但通过实体链接，它们被关联起来了。

### 4.3 去重机制（mod:dedup）

add() 的 Phase 5 使用 MD5 哈希进行去重。

**为什么需要去重？** 因为用户可能重复提到相同的信息。比如用户第一天说"我喜欢川菜"，第二天又说"我想吃川菜"。LLM 提取时可能两次都提取出"用户喜欢川菜"。如果不做去重，向量库中就会有两份相同的记忆。

**去重怎么工作？**

1. 计算每条记忆的 MD5 哈希值（一串 32 位的十六进制数字）
2. 查询 SQLiteManager 是否已存在相同哈希
3. 如果存在，跳过该记忆
4. 如果不存在，记录哈希并存储

**去重是全局的：** 即使两个不同 user_id 的相同记忆，也会被去重。这确保了向量存储中不会有完全相同的重复记忆。

### 4.4 通知系统（mod:notices）

mem0 内置了智能使用提示系统。当检测到特定使用模式时，自动展示功能建议。

**可以检测的模式：**

- 规模阈值：当记忆数量接近限制时，提示用户考虑升级
- 衰减使用：当用户使用 delete 时，提示衰减功能的存在
- 时序使用：当 search 时检查是否使用了时序元数据，提示时序推理功能
- 慢查询：超过 PERFORMANCE_SLOW_QUERY_THRESHOLD_SECONDS 阈值时提示优化
- 首次运行：首次使用时展示功能概览

**对产品运营的价值：** 这些提示可以帮助你了解用户的使用模式——他们是否在用"过时"的方式使用系统？是否需要调整产品策略？

### 4.5 遥测系统（mod:telemetry）

可选的匿名使用统计，使用 PostHog 进行事件追踪。通过 MEM0_TELEMETRY 环境变量控制开关。遥测系统只收集匿名使用统计，不收集敏感数据。

### 4.6 安全机制（mod:security）

三层保护：

- 敏感字段脱敏：_SENSITIVE_FIELDS_EXACT 集合定义了 20+ 个敏感字段名（api_key、password、token、secret 等），日志输出时自动替换为 [REDACTED]
- 运行时字段保护：_RUNTIME_FIELDS 集合保护非序列化对象（如 AWS 签名器、HTTP 连接类），防止错误序列化
- 输入校验：search() 的 query 参数必须是非空字符串，add() 的 user_id 必须非空

### 4.7 词形还原（mod:lemmatization）

lemmatize_for_bm25() 对中英文查询进行词形还原。中文用 jieba 分词，英文用 NLTK 词形还原。这确保"running"和"run"在 BM25 搜索中被视为同一个词。

### 4.8 打分排序（mod:scoring）

score_and_rank() 函数融合三种分数：语义分数 + BM25 分数 + 实体加成。每种分数的权重可配置。ENTITY_BOOST_WEIGHT 控制实体加成的权重。

### 4.9 提示词系统（mod:prompts）

定义在 configs/prompts.py 中。包含 LLM 提取记忆时使用的提示词模板。ADDITIVE_EXTRACTION_PROMPT 是核心提示词，告诉 LLM 从文本中提取新的事实，同时识别哪些已有记忆需要更新。AGENT_CONTEXT_SUFFIX 是 Agent 上下文后缀，让 LLM 理解它是在为 Agent 提取记忆。

### 4.10 存储管理（mod:storage）

SQLiteManager 管理记忆的元数据。包括操作历史（谁在什么时候添加了哪条记忆）、去重哈希（MD5 值）、消息存储（原始对话文本）。库模式使用 SQLite，自托管模式使用 PostgreSQL。

### 4.11 配置系统（mod:configs）

Pydantic 配置模型。MemoryConfig 包含四个子配置。每种后端有独立的 Config 类，通过 Union 类型统一管理。支持配置热更新——自托管版可以通过 API 更新配置，无需重启服务。### 4.12 云平台客户端（mod:client）

MemoryClient 类提供与云平台（app.mem0.ai）的通信。它实现了与本地 Memory 类相同的 API，但底层通过 HTTPS 调用云平台 API。这意味着你可以在本地开发时使用本地 Memory 类，部署到生产时切换到 MemoryClient，代码不需要改。

### 4.13 自托管 Server（mod:server）

自托管版提供完整的 REST API 服务。基于 FastAPI 框架，包含以下组件：

- 路由：/api/v1/memories（添加、搜索、更新、删除记忆）、/api/v1/agents（Agent 管理）、/api/v1/config（配置管理）
- 认证：JWT 认证 + API Key 认证。支持 admin 和 member 两种角色
- 限流：基于 SlowAPI 的请求限流
- 数据模型：User、APIKey、RequestLog 三张核心表
- 数据库迁移：7 个 Alembic 迁移版本

### 4.14 TypeScript SDK（mod:ts_sdk）

提供与 Python SDK 一致的 API。Memory 类位于 src/oss/src/memory/index.ts。支持 add、search、update、delete 等操作。

### 4.15 OpenMemory UI（mod:openmemory）

Web 管理界面，用于可视化管理记忆。API 后端使用 FastAPI，UI 前端使用 React。支持记忆搜索、浏览、删除、导出等操作。

### 4.16 CLI 工具（mod:cli）

命令行工具，支持 Agent 自主注册。核心命令：mem0 init --agent --agent-caller <name>。Agent 注册后可以独立使用 mem0 的 API，无需人工干预。

### 4.17 Reranker 重排序（mod:reranker）

对 search 结果进行二次排序，提升最相关记忆的排名。支持 5 个后端：Cohere、HuggingFace、Voyage、LLM-based、No-op。Reranker 是可选的，如果未配置则跳过重排序步骤。

### 4.18 Server 认证（mod:server_auth）

自托管版的认证系统。支持两种方式：
- JWT 认证：用户登录后获取 JWT Token，Bearer 方式传递
- API Key 认证：创建 API Key，通过 Header 传递。API Key 存储时只保存 SHA256 哈希值，不保存明文
- RBAC：admin 和 member 两种角色。admin 可以管理 API Key 和用户，member 只能使用记忆 API

### 4.19 Server 数据模型（mod:server_models）

自托管版的 SQLAlchemy 数据模型：

- User：id、name、email、password_hash、role、created_at、last_login_at
- APIKey：id、key_prefix、key_hash、label、created_by、revoked_at、last_used_at
- RequestLog：id、method、path、status_code、latency_ms、user_id、api_key_id

### 4.20 Server 限流（mod:server_rate_limit）

基于 SlowAPI 的请求限流，防止 API 滥用。限流策略基于 IP 和 API Key。

## 5. 架构如何支撑业务需求

现在我们把架构和业务需求对应起来，看看架构设计是如何支撑实际业务的。

### 5.1 业务需求：我是一家 SaaS 公司，有 1000 个用户

**架构支撑：** 多租户隔离。通过 user_id 维度，1000 个用户的记忆完全隔离。不同 user_id 的记忆即使内容相同，也是独立存储和检索的。add() 和 search() 时，user_id 作为过滤条件传递给向量存储。

### 5.2 业务需求：我想从本地 Qdrant 迁移到云端 Pinecone

**架构支撑：** 后端无关。修改配置中的 provider 字段，从 "qdrant" 改为 "pinecone"，加上 Pinecone 的 API Key。代码一行不用改。工厂模式自动创建 Pinecone 实例。

### 5.3 业务需求：我想用 DeepSeek 替代 OpenAI 来降低成本

**架构支撑：** 后端无关。修改配置中的 llm.provider 字段，从 "openai" 改为 "deepseek"。LlmFactory 自动创建 DeepSeek 实例。API 调用量大的时候，这个切换能节省 50-80% 的 LLM 成本。

### 5.4 业务需求：我想让记忆自动过期，不需要手动清理

**架构支撑：** 衰减机制。delete() 支持衰减模式，设置过期时间。search() 自动过滤过期记忆。定期清理任务最终删除过期记忆。

### 5.5 业务需求：我想让 Agent 自主注册，不需要人工干预

**架构支撑：** CLI 工具。Agent 通过 `mem0 init --agent --agent-caller claude-code` 一键注册。CLI 生成匿名用户 ID，向云平台注册，获取 API Key，保存到本地。

## 总结

## 4. 第 6 层详解：辅助服务层 —— 幕后英雄

前面 5 层已经覆盖了 mem0 的核心路径（用户调用 → Memory 核心 → 工厂创建后端 → 配置驱动）。但还有 6 个重要的辅助模块，它们不直接参与 add/search 的主流程，但为整个系统提供了质量保障。每个模块都值得了解。

### 4.1 存储管理（SQLiteManager）

**文件位置**：mem0/memory/storage.py

**做什么**：SQLiteManager 是 mem0 的"元数据记录本"。它不存储向量（那个在向量数据库里），而是存储：
- 每次操作的历史记录（谁在什么时候添加/更新/删除了什么记忆）
- MD5 哈希值（用于去重——相同内容的记忆只存一次）
- 操作类型（ADD/UPDATE/DELETE）

**为什么需要它？** 向量数据库擅长"相似度搜索"，但不擅长"查询历史"。比如你想知道"user_123 在过去 7 天添加了哪些记忆"，向量数据库做不了这件事。SQLiteManager 负责这类结构化查询。

**对产品运营的价值**：你可以通过 SQLiteManager 查询用户的操作历史，做数据分析（比如"活跃用户每天添加多少条记忆"）。

### 4.2 通知系统（notices）

**文件位置**：mem0/memory/notices.py

**做什么**：自动检测用户的使用模式，当发现"用户可能不知道某个功能存在"时，主动展示提示。有 5 种检测：

| 检测类型 | 触发条件 | 提示内容 |
|---------|---------|---------|
| 规模阈值 | 记忆数接近向量库限制 | "你已接近记忆上限，考虑升级到更大规模的向量存储" |
| 衰减使用 | 用户使用 delete() 但没有启用衰减 | "你知道衰减机制吗？记忆可以设置过期时间自动失效" |
| 时序使用 | 记忆包含时间元数据但没有使用时序推理 | "你可以在搜索时利用时间信息，提高搜索质量" |
| 慢查询 | search() 耗时超过阈值 | "搜索速度较慢，可以优化向量存储配置" |
| 首次运行 | 第一次使用 mem0 | "欢迎使用 mem0，这是功能概览和快速入门指南" |

**为什么需要它？** mem0 的功能很多（衰减、时序推理、多信号检索），但用户不一定知道。通知系统像"智能助手"，在合适的时机提醒用户"嘿，你还有一个功能可能对你有用"。

**对产品运营的价值**：通知系统可以帮助你提高功能使用率。如果大量用户只用 add/search 而不知道衰减机制，通知系统会自动提醒他们。

### 4.3 遥测系统（telemetry）

**文件位置**：mem0/memory/telemetry.py

**做什么**：可选的匿名使用统计，使用 PostHog 进行事件追踪。通过 MEM0_TELEMETRY 环境变量控制开关。

**收集什么**：匿名使用统计，不收集敏感数据。capture_event() 函数发送事件，capture_client_event() 用于客户端遥测。

**为什么需要它？** mem0 团队需要知道用户如何使用产品，哪些功能被频繁使用，哪些功能被忽略。这帮助团队决定下一步开发方向。

**对产品运营的价值**：你可以通过遥测数据了解用户的使用行为，优化产品功能。遥测是完全可选的，可以通过环境变量关闭。

### 4.4 安全机制（security）

**文件位置**：mem0/memory/main.py（_SENSITIVE_FIELDS_EXACT 和 _RUNTIME_FIELDS 集合）

**做什么**：三层安全保护：

1. **敏感字段脱敏**：_SENSITIVE_FIELDS_EXACT 集合定义了 20+ 个敏感字段名（api_key、password、token、secret、authorization 等）。日志输出时，任何匹配的字段值都会被替换为 [REDACTED]。这意味着即使日志被泄露，敏感信息也不会暴露。

2. **运行时字段保护**：_RUNTIME_FIELDS 集合保护非序列化对象（如 AWS 签名器、HTTP 连接类）。这些对象不能被序列化，如果错误地尝试序列化会导致程序崩溃。_RUNTIME_FIELDS 确保这些对象被安全地跳过。

3. **输入校验**：search() 的 query 参数必须是非空字符串，否则抛出 ValidationError。add() 的 user_id 必须非空。

**对产品运营的价值**：安全机制是产品合规的基础。如果你的产品需要 SOC2 或 ISO 27001 认证，mem0 的安全脱敏和输入校验是重要的合规支撑。### 4.5 词形还原（lemmatization）

**文件位置**：mem0/utils/lemmatization.py

**做什么**：lemmatize_for_bm25() 函数对查询文本进行词形还原。中文用 jieba 分词，英文用 NLTK 词形还原。

**为什么需要它？** 因为 BM25 关键词搜索是"精确匹配"算法。如果用户搜索"running"，而记忆里是"run"，BM25 会认为这是两个不同的词。词形还原把"running"还原为"run"，确保搜索"running"时能找到包含"run"的记忆。

**对产品运营的价值**：词形还原直接影响搜索质量。没有它，用户搜"likes"找不到"like"的记忆，搜索体验会大打折扣。

### 4.6 打分排序（scoring）

**文件位置**：mem0/utils/scoring.py（或 mem0/memory/utils.py 中的相关函数）

**做什么**：score_and_rank() 函数融合三种搜索信号，给出最终排名：

1. **语义分数**（向量相似度）：查询向量和记忆向量的余弦相似度，范围 0-1
2. **BM25 分数**（关键词匹配）：查询中的关键词在记忆中出现的频率，通过 normalize_bm25() 归一化到 0-1
3. **实体加成**（ENTITY_BOOST_WEIGHT）：如果查询包含已知实体，包含该实体的记忆获得额外加分

**为什么需要三种信号融合？** 单一信号都有缺陷。纯语义搜索可能漏掉精确匹配，纯关键词搜索不理解语义，实体加成让专有名词（人名、产品名）得到更好的匹配。三种信号互补，搜索结果最准确。

**对产品运营的价值**：搜索质量直接影响用户体验。如果用户搜"iPhone 15"却找不到"我买了苹果手机"这条记忆，用户会认为 mem0 不好用。打分排序确保搜索质量。

### 4.7 提示词系统（prompts）

**文件位置**：mem0/configs/prompts.py

**做什么**：定义了 LLM 提取记忆时使用的提示词模板：

- **ADDITIVE_EXTRACTION_PROMPT**：增量提取提示词。告诉 LLM"从对话中提取新的事实，已有的不要重复提取"
- **generate_additive_extraction_prompt()**：动态生成提示词，包含用户已有记忆作为上下文。LLM 看到"用户已有这些记忆"后，就知道哪些是新信息、哪些是更新
- **AGENT_CONTEXT_SUFFIX**：Agent 上下文后缀。告诉 LLM"你是在为 AI Agent 提取记忆"，让 LLM 调整提取策略
- **PROCEDURAL_MEMORY_SYSTEM_PROMPT**：程序记忆提示词。用于提取"怎么做"而非"是什么"的知识

**为什么需要提示词系统？** 提取质量取决于 LLM 的"理解"程度。好的提示词让 LLM 提取更准确、更完整。提示词系统是 mem0 记忆质量的基础。

## 5. 第 7 层详解：客户端/服务端层 —— 怎么用 mem0

第 7 层是 mem0 的"交付层"，决定了用户以什么方式使用 mem0。包含 5 个子模块。

### 5.1 云平台客户端（MemoryClient）

**文件位置**：mem0/client/

**做什么**：通过 HTTPS 调用 mem0.ai 的云端 API。提供与本地 Memory 类完全一致的 API（add/search/update/delete）。

**什么时候用**：不想自己部署和维护向量数据库的团队。注册 app.mem0.ai 获取 API Key，直接调用。

### 5.2 自托管 Server

**文件位置**：server/

**做什么**：FastAPI 自托管服务器。提供 REST API、JWT + API Key 认证、RBAC（admin/member）、SlowAPI 限流、SQLAlchemy ORM、Alembic 数据库迁移、请求日志。

**核心组件**：
- **server/auth.py**：JWT 认证 + API Key 认证。API Key 只存哈希值，不存明文。密码哈希存储
- **server/models.py**：SQLAlchemy 模型。User（id/name/email/password_hash/role）、APIKey（key_prefix/key_hash/revoked_at）、RequestLog（method/path/status_code/latency_ms）
- **server/rate_limit.py**：基于 SlowAPI 的请求限流，基于 IP 和 API Key

**什么时候用**：团队使用、企业部署。需要自托管 + 权限控制 + 审计日志的场景。

### 5.3 TypeScript SDK

**文件位置**：mem0-ts/

**做什么**：Node.js 和浏览器环境的 TypeScript SDK。提供与 Python SDK 一致的 Memory 类 API。

**什么时候用**：前端开发者、全栈团队、Node.js 项目。

### 5.4 OpenMemory UI

**文件位置**：openmemory/

**做什么**：Web 管理界面。Python FastAPI 后端 + React TSX 前端。可视化管理记忆：搜索、浏览、删除、导出。

**什么时候用**：需要可视化界面管理记忆的场景。自托管部署时自带 Dashboard。

### 5.5 CLI 工具

**文件位置**：cli/

**做什么**：命令行工具。支持 Agent 自主注册（mem0 init --agent --agent-caller claude-code）。Python 和 Node.js 两种实现。

**什么时候用**：AI Agent 需要自主注册和使用 mem0。不需要人工干预，Agent 自己执行 CLI 命令完成注册。

## 总结

mem0 的 7 层架构体现了"关注点分离"和"后端无关"两大原则。第 1 层（用户接口）决定了"怎么调用"，第 2 层（Memory 核心）是"大脑"，第 3 层（工厂）是"万能转接头"，第 4 层（后端适配器）是"可替换的引擎"，第 5 层（配置）是"控制面板"，第 6 层（辅助服务）是"质量保障"，第 7 层（客户端/服务端）是"交付方式"。

理解了这个架构，你就理解了 mem0 的"生长能力"——它能在多大程度上适应你的业务需求变化。从库模式到自托管，从 Qdrant 到 Pinecone，从 OpenAI 到 DeepSeek，mem0 的设计让你可以随时切换，不需要重写代码。## 补充：遥测系统详解（基于 telemetry.py 源码，241 行）

# mem0 核心流程与部署 —— 从添加到搜索的完整旅程

> GitHub: https://github.com/mem0ai/mem0 | commit fec2fe6 | Apache 2.0
> 分析时间: 2026-07-21 | Understand-Anything 知识图谱: 24 节点, 20 边, 7 层
> 本章面向产品经理、运营、非技术人员。每个流程讲碎、讲透。

---

## 1. 流程 1：add() 记忆添加的完整旅程

这是 mem0 最核心的流程。我们从用户说一句话开始，一步步追踪数据在 7 层架构中的完整流转。

### 场景设定

用户 "user_123" 在聊天应用中说了这样一句话：

**"我叫张三，今年 28 岁，喜欢川菜，住在北京朝阳区。对了，我最近买了一个 iPhone 15 Pro。"**

然后聊天应用调用 `memory.add("我叫张三，今年28岁，喜欢川菜，住在北京朝阳区。对了，我最近买了一个iPhone 15 Pro。", user_id="user_123")`。

这一行简单的代码，背后发生了什么？让我们逐层追踪。

### 第 1 层：用户接口层

聊天应用调用 `memory.add()` 方法。这是 Python SDK 的接口。如果是 TypeScript 应用，调用方式完全一样，只是语言不同。如果是云平台，调用方式也完全一样，只是底层通过 HTTPS 而不是本地调用。

### 第 2 层：Memory 核心层 —— 参数校验

Memory 类收到 add() 调用后，首先做参数校验。检查 user_id 是否为空——如果为空，直接抛出错误。

**为什么 user_id 必须非空？** 因为 user_id 是记忆的"归属标签"。没有这个标签，记忆就不知道属于谁。在你的 SaaS 应用中，如果有 1000 个用户，每个用户的记忆必须通过 user_id 来隔离。如果 user_id 为空，记忆就无法归属于任何用户，后续的 search 也无法过滤。

### 第 2 层：Memory 核心层 —— Phase 0（上下文收集）

mem0 收集 user_123 最近 10 条消息作为上下文。假设 user_123 之前说过"我最近在考虑换手机"，这条消息就会被收集。

**为什么需要上下文？** 因为单条消息可能信息不完整。比如 user_123 只说"最后买了 Pro 版本"，如果没有上下文，LLM 根本不知道"Pro 版本"指的是什么。有了上下文，LLM 就知道"Pro 版本"指的是 iPhone 15 Pro。

**为什么是 10 条？** 这是经验值。太少（2-3 条）可能信息不足，太多（50-100 条）可能包含无关信息，还会消耗更多 Token。10 条是一个平衡点。这个数字是可配置的——如果你的应用场景需要更长的上下文，可以调大。

### 第 2 层：Memory 核心层 —— Phase 1（已有记忆检索）

mem0 语义搜索 user_123 的已有记忆。假设 user_123 之前说过"我喜欢吃辣"，这条记忆会被检索出来。

**为什么需要检索已有记忆？** 这是 2026.04 新算法的关键优化。旧算法需要两次 LLM 调用——第一次提取增量记忆，第二次判断是否需要替换已有记忆。新算法通过提前检索已有记忆，把"提取"和"判断"合并为一次 LLM 调用。

具体来说，LLM 会收到这样的信息："用户已有记忆：喜欢辣。用户新消息：我叫张三，喜欢川菜。"LLM 看到后就知道，"喜欢川菜"是对"喜欢辣"的补充，而不是完全新的信息。

### 第 3 层：工厂层 —— 创建 LLM 实例

mem0 调用 LlmFactory.create(provider, config) 创建 LLM 实例。provider 是你配置的 LLM 提供商（如 "openai"、"deepseek"、"ollama"）。

**工厂在做什么？** 工厂查询注册表，找到 "openai" 对应的实现类，读取配置（api_key、model、temperature），创建实例。如果配置的 provider 是 "deepseek"，工厂就创建 DeepSeek 实例。代码不需要知道具体是哪个 LLM，只需要调用统一接口。

### 第 4 层：后端适配器层 —— LLM 提取记忆

LLM 实例收到请求，调用 OpenAI API（或其他提供商），发送 ADDITIVE_EXTRACTION_PROMPT 提示词和用户消息。

提示词告诉 LLM："你需要从以下对话中提取关键事实。如果发现用户有新的信息，添加为新记忆。如果发现用户修改了已有信息，标记为需要替换。返回 JSON 格式的结果。"

LLM 分析后，返回 JSON：

```json
{
  "additive": [
    {"memory": "用户叫张三"},
    {"memory": "用户28岁"},
    {"memory": "用户喜欢川菜"},
    {"memory": "用户住在北京朝阳区"},
    {"memory": "用户最近购买了iPhone 15 Pro"}
  ],
  "replacements": []
}
```

LLM 提取了 5 条新记忆，没有需要替换的旧记忆。如果是更新场景（比如"我搬家了，现在住上海"），LLM 会在 replacements 中返回需要替换的记忆。

**为什么 LLM 能理解"喜欢川菜"和"喜欢辣"的关系？** 因为 LLM 有语义理解能力。它知道"川菜"是辣的，所以"喜欢川菜"是对"喜欢辣"的具体化，不是矛盾的信息。这就是为什么用 LLM 来提取记忆——它比简单的关键词匹配聪明得多。

### 第 3 层：工厂层 —— 创建 Embedding 实例

mem0 调用 EmbedderFactory.create(provider, config) 创建 Embedding 实例。provider 是你配置的 Embedding 提供商（如 "openai"、"huggingface"、"ollama"）。

### 第 4 层：后端适配器层 —— 批量 Embedding

Embedding 实例收到请求，把 5 条记忆文本一次性发送给 Embedding API。API 返回 5 个向量（每个向量是 1536 维的数字，使用 OpenAI text-embedding-3-small 时）。

**为什么批量发送？** 这是 Token -90% 的关键。旧算法每条记忆单独调用 Embedding API，5 条记忆需要 5 次 API 调用。新算法一次调用嵌入所有 5 条记忆，只需要 1 次 API 调用。API 调用次数减少了 80%。

**向量是什么？** 向量是一串数字，代表文本的"语义指纹"。两条语义相似的文本，它们的向量在空间中距离很近。比如"喜欢川菜"和"爱吃辣"的向量距离很近，"喜欢川菜"和"住在北京"的向量距离很远。### 第 2 层：Memory 核心层 —— Phase 4（逐条 CPU 处理）

mem0 在 CPU 上计算每条记忆的 MD5 哈希值。哈希值就像记忆的"指纹"——相同内容的记忆会生成相同的哈希。

**为什么在 CPU 上处理？** 因为这个操作不消耗 API 调用，完全在本地完成。不需要网络请求，速度很快。

### 第 2 层：Memory 核心层 —— Phase 5（哈希去重）

mem0 查询 SQLiteManager，检查这 5 个哈希值是否已经存在。如果 user_123 之前已经说过"我叫张三"，这条记忆的哈希值已经存在，mem0 就跳过它。

**去重是全局的**——即使不同 user_id 的相同记忆，也会被去重。这确保了向量存储中不会有完全相同的重复记忆。

### 第 3 层：工厂层 —— 创建 VectorStore 实例

mem0 调用 VectorStoreFactory.create(provider, config) 创建 VectorStore 实例。provider 是你配置的向量存储提供商（如 "qdrant"、"pinecone"、"chroma"）。

### 第 4 层：后端适配器层 —— 批量持久化

VectorStore 实例收到请求，把去重后的 5 条记忆（向量 + 文本 + 元数据）一次性批量写入向量数据库。

**为什么批量写入？** 和批量 Embedding 同样的道理——减少 API 调用次数。旧算法每条记忆单独写入，5 条记忆需要 5 次写入操作。新算法一次写入所有 5 条记忆。

### 第 2 层：Memory 核心层 —— Phase 7（批量实体链接）

mem0 从记忆中提取实体：张三（PERSON）、川菜（FOOD）、北京朝阳区（LOCATION）、iPhone 15 Pro（PRODUCT）。然后：

1. 全局去重：检查实体存储中是否已有这些实体。如果"张三"已经存在，不重复插入
2. 批量嵌入：将实体名向量化
3. 搜索后 upsert：在实体存储中搜索相似实体。如果找到相似的，更新；如果没找到，插入新实体

**实体存储为什么独立？** 因为实体和记忆的访问模式不同。记忆是"内容"，实体是"索引"。独立后可以单独优化实体检索的性能。

### 第 6 层：辅助服务层 —— 保存消息

SQLiteManager 保存原始消息和操作记录。包括：谁（user_123）在什么时候（时间戳）添加了哪些记忆（5 条记忆 ID）。

### 第 2 层：Memory 核心层 —— Phase 8（返回结果）

mem0 把 5 条记忆的 ID 返回给应用。add() 流程结束。

**整个流程总结：** 从一句"我叫张三"到 5 条记忆存入向量数据库，经历了 9 个阶段、3 层工厂、4 个后端适配器。但对用户来说，只是一行代码。这就是 mem0 的价值——把复杂的东西藏在里面，暴露简单的接口。

## 2. 流程 2：search() 记忆搜索的完整旅程

### 场景设定

user_123 在聊天应用中问："我喜欢吃什么？"

聊天应用调用 `memory.search("我喜欢吃什么？", user_id="user_123", top_k=5)`。

### 第 2 层：Memory 核心层 —— Step 1（预处理）

mem0 对查询文本进行词形还原。中文用 jieba 分词，把"我喜欢吃什么"分成"我"、"喜欢"、"吃"、"什么"。

同时提取实体。如果查询中包含已知实体，记录下来。比如"我喜欢吃什么"中可能包含 FOOD 类型的实体。

**为什么需要分词？** 因为 BM25 关键词搜索需要知道查询中有哪些关键词。中文不像英文有空格分隔，所以需要 jieba 来分词。"喜欢"和"吃"是两个独立的关键词，BM25 会在文档中搜索这两个词。

**为什么需要提取实体？** 因为实体加成可以提高搜索质量。如果查询中包含 FOOD 类型的实体，给包含 FOOD 实体的记忆额外加分。

### 第 3 层：工厂层 —— 创建 Embedding 实例

mem0 调用 EmbedderFactory.create() 创建 Embedding 实例。

### 第 4 层：后端适配器层 —— 向量化查询

Embedding 实例把"我喜欢吃什么？"转换成 1536 维向量。这个向量代表了查询的"语义指纹"。

### 第 4 层：后端适配器层 —— 语义搜索

VectorStore 实例在向量数据库中搜索与查询向量最相似的记忆。超取 4 倍——top_k=5 时实际搜索 20 条。

**为什么超取？** 因为语义搜索可能漏掉一些相关结果。比如"我喜欢吃什么"和"用户爱吃川菜"在语义上接近，但向量距离可能不够近。超取后再通过后续步骤筛选，提高召回率。

**向量搜索的原理：** 在 1536 维空间中，计算查询向量和每条记忆向量的余弦相似度。相似度越高，说明语义越接近。返回相似度最高的 20 条。

### 第 2 层：Memory 核心层 —— Step 4（BM25 关键词搜索）

mem0 用 BM25 算法在已索引的文档中搜索"喜欢"、"吃"等关键词。

**BM25 是什么？** BM25 是一种经典的关键词搜索算法。它会考虑三个因素：
- 词频（TF）：关键词在文档中出现的次数。出现越多，分数越高
- 逆文档频率（IDF）：关键词在所有文档中的稀有程度。越稀有，权重越高
- 文档长度：长文档和短文档的公平比较。防止长文档仅仅因为更长就获得更高分数

**为什么需要 BM25？** 因为语义搜索可能漏掉精确匹配。比如"川菜"这个词在向量空间中可能和"辣"很近，但"川菜"和"川菜"的精确匹配只靠语义搜索是不够的。BM25 弥补了语义搜索的这个缺陷。

### 第 2 层：Memory 核心层 —— Step 5（计算 BM25 分数）

mem0 将 BM25 的原始分数归一化，和语义分数统一到相同尺度。

**为什么需要归一化？** 因为语义分数和 BM25 分数在完全不同的尺度上。语义分数是 0-1 的余弦相似度，BM25 分数可能是 0-100 的任意值。不归一化就无法公平比较。

### 第 2 层：Memory 核心层 —— Step 6（计算实体加成）

mem0 检查查询中是否包含已知实体。如果查询中包含 FOOD 类型的实体，给包含该实体的记忆额外加分。比如"用户喜欢川菜"这条记忆包含 FOOD 实体，会得到额外加分。

**ENTITY_BOOST_WEIGHT 参数控制实体加成的权重。** 默认值在代码中定义，可以根据需要调整。如果实体加成太强，可能把不相关的记忆也排到前面。如果太弱，实体加成的效果不明显。

### 第 2 层：Memory 核心层 —— Step 7（构建候选集）

mem0 合并语义搜索和 BM25 的结果，去重。两种搜索方式可能返回相同的记忆，需要去重。

### 第 2 层：Memory 核心层 —— Step 8（打分排序）

mem0 融合三种分数：语义相似度 + BM25 关键词匹配 + 实体加成。按总分排序，返回 top 5 条。

### 第 2 层：Memory 核心层 —— Step 9（格式化返回）

mem0 将结果格式化为 MemoryItem 列表，返回给应用。每条 MemoryItem 包含：记忆 ID、记忆内容、搜索得分、元数据等。

**整个流程总结：** 从一句"我喜欢吃什么"到 5 条最相关的记忆，经历了 9 个步骤、3 种搜索信号。但对用户来说，只是一行代码。## 3. 流程 3：update() 记忆更新

### 场景

user_123 说："我搬家了，现在住上海浦东。"

聊天应用调用 `memory.update(memory_id="mem_xxx", data="用户住在上海浦东")`。

### 流程

1. mem0 根据 memory_id 找到要更新的记忆
2. 重新向量化新内容"用户住在上海浦东"
3. 更新向量数据库中的向量和文本
4. 更新 SQLiteManager 中的哈希值
5. 返回更新后的记忆

**关键点：** 更新后，旧的"用户住在北京朝阳区"不再存在。搜索"用户住在哪里"时，只会返回"用户住在上海浦东"。这避免了记忆矛盾——同一个问题不会有两个不同的答案。

## 4. 流程 4：delete() 记忆删除

### 场景

user_123 说："算了，我不喜欢川菜了。"

聊天应用调用 `memory.delete(memory_id="mem_yyy")`。

### 硬删除

1. mem0 根据 memory_id 找到要删除的记忆
2. 从向量数据库中删除
3. 从 SQLiteManager 中删除
4. 返回删除成功

不可恢复。适用于"用户明确表示不需要这条信息"的场景。

### 衰减删除

user_123 说："今天心情不好。"（这条信息只今天有效）

聊天应用调用 `memory.delete(memory_id="mem_zzz", expires_at="2026-07-22")`。

1. mem0 不立即删除，而是设置过期时间
2. search() 时自动过滤过期的记忆
3. 定期清理任务最终删除过期的记忆

适用于"临时信息"的场景。比如：
- 用户今天的心情
- 用户今天想吃什么
- 用户当前的会话状态
- 用户临时提出的偏好

## 5. 流程 5：Agent 自主注册

### 流程

3. CLI 向云平台注册，获取 API Key

mem0 提供了三种部署模式，按需选择。

### 6.1 库模式

**安装方式：** `pip install mem0ai`

- 数据存储在本地，无法共享

**适用场景：** 团队使用、企业部署。

- 需要配置 PostgreSQL 和向量数据库
- 有一定的运维成本

**工作原理：** FastAPI 服务作为 API 服务器，PostgreSQL 存储元数据，向量数据库（Qdrant/Pinecone 等）存储向量数据。用户通过 REST API 或 SDK 访问。

**安装方式：** 注册 app.mem0.ai

**适用场景：** 生产环境零运维。

**优点：**
- 零运维，mem0 团队负责维护
- 自动扩容，支持高并发
- 有 Web 管理界面

**缺点：**
- 数据存储在云平台，需要信任 mem0 团队
- 按使用量付费
- 网络延迟比本地模式高

**工作原理：** 客户端通过 HTTPS 调用 app.mem0.ai 的 API。所有数据存储在 mem0 的云基础设施中。## 7. 核心数据实体

## 8. 安全机制

### 8.1 敏感字段脱敏

mem0 在日志输出时自动脱敏 20+ 个敏感字段名。任何匹配 api_key、password、token、secret 等字段的值，都会被替换为 [REDACTED]。

**为什么重要？** 因为日志可能被分享给第三方（比如技术支持），如果日志中包含 API Key，就会有安全风险。脱敏机制确保敏感信息不会泄露。

### 8.2 API Key 哈希存储

自托管版的 API Key 只存储 SHA256 哈希值，不存储明文。即使数据库被泄露，攻击者也无法获取 API Key。

### 8.3 输入校验

search() 的 query 参数必须是非空字符串。add() 的 user_id 必须非空。这些校验在系统入口就完成，防止非法数据进入系统。

## 9. 数据生命周期

从创建到删除，一条记忆的完整生命周期：

1. **创建：** add() → LLM 提取 → Embedding 向量化 → 哈希去重 → 向量库存储 + SQLite 记录
2. **读取：** search() → 查询向量化 → 语义搜索 + BM25 + 实体加成 → 排序返回
3. **更新：** update() → 重新向量化 → 更新向量库 + 更新 SQLite 记录 + 更新哈希
4. **删除（硬）：** delete() → 向量库删除 + SQLite 删除
5. **删除（衰减）：** delete() 带过期时间 → 设置过期时间戳 → search() 时过滤过期记忆 → 定期清理

search() 的 Step 8 使用 `score_and_rank()` 函数融合三种信号。基于源码（main.py），融合机制如下：

**三种信号：**

1. **语义相似度（Semantic）：** 查询向量和记忆向量的余弦相似度。值域 0-1。越高越相似。
2. **BM25 关键词匹配（Keyword）：** 经典 TF-IDF 变体。考虑词频（关键词在记忆中出现次数）、逆文档频率（关键词在所有记忆中的稀有度）、文档长度（长记忆和短记忆的公平比较）。原始分数经过 `normalize_bm25()` 归一化到 0-1 区间。
3. **实体加成（Entity Boost）：** 如果查询中包含已知实体（如 PERSON、PRODUCT、LOCATION），给包含该实体的记忆额外加分。加成权重由 `ENTITY_BOOST_WEIGHT` 控制。

**融合方式：** 最终分数 = 语义分数 + BM25 分数 + 实体加成。三种分数直接相加（不是加权平均），因为它们在归一化后处于相同尺度。

**为什么需要三种信号？** 单一信号都有缺陷。纯语义搜索可能漏掉精确匹配（如"iPhone 15"和"苹果手机"语义不同但指同一产品），纯关键词搜索可能漏掉语义关联（"喜欢"和"爱吃"字面不同），实体加成帮两者建立桥梁。

## 补充：add() 的 ADD-only 提取（2026.04 新算法）

旧算法中，add() 的 LLM 提取阶段需要两次调用：一次提取增量记忆（additions），一次判断是否需要替换已有记忆（replacements）。新算法改为**单次 ADD-only 提取**：

- LLM 在一次调用中同时返回 additions（新增记忆）和 replacements（替换记忆）
- 记忆累积存储，不覆盖旧记忆（除非明确标记为替换）
- Agent 生成的事实以同等权重存储（当 Agent 确认某个操作时，该信息与用户直接输入的信息同等对待）

**实际效果：** Token 消耗从两次 LLM 调用减少到一次（-50%），加上批量 Embedding 和批量写入，总 Token 消耗降低 90%。

## 补充：search() 的 top_k 超取机制

search() 默认超取 4 倍。如果 top_k=10，实际从向量数据库搜索 40 条。为什么？

- 语义搜索的结果不一定是最相关的前 10 条——可能包含一些"语义相似但不相关"的结果
- 超取后，通过 BM25 关键词搜索和实体加成进行二次筛选和排序
- 最终返回的 top_k 条是经过三种信号融合排序后的最优结果
- 超取倍数可配置，默认 4 倍是经验值——在召回率和性能之间取得平衡

## 补充：词形还原（Lemmatization）详解

基于源码 `utils.py`，`lemmatize_for_bm25()` 函数对查询文本进行词形还原：

- **中文：** 使用 jieba 分词，将查询拆分为独立词汇
- **英文：** 使用 NLTK 词形还原，确保 "running" 和 "run" 被视为同一个词
- **目的：** 为 BM25 关键词搜索提供准确的索引词，而不是原始查询文本

**为什么需要词形还原？** 因为 BM25 是精确匹配算法。如果用户搜索 "running"，但记忆存储的是 "run"，BM25 默认匹配不到。词形还原将两者都归一化为 "run"，提高匹配率。
