# jcode 系统全景

> GitHub: https://github.com/1jehuang/jcode | v0.54.3 | commit: 5a0dab7
> 分析时间: 2026-07-20 | CodeGraph 索引: 38,815 节点, 155,075 边

## 一句话定位

jcode 是一个用 Rust 编写的下一代终端 AI 编码代理。不像 IDE 插件，它住在终端里——你给它任务描述，它自主规划、调用工具、读写文件，直到完成。

## 目标用户

独立开发者: 终端里快速实现功能、修 bug
技术负责人: 代码审查、自动化重构
开源维护者: 处理 issue、review PR，多会话并发
学习者: 理解代码库、画出架构图

## 核心痛点与解决方案

1. AI 记不住: 三级记忆系统(L1/L2/L3)，跨会话记住偏好
2. 大项目搜不动: 本地 ONNX 向量嵌入，语义搜索整个代码库
3. 单 Agent 能力有限: Swarm 多 Agent 协调，分工协作
4. 模型被锁定: 8+ Provider，一行配置切换
5. 资源占用大: Rust 原生编译，单会话 27.8MB
6. 终端体验差: 全功能 TUI，Markdown/Mermaid 渲染

## 技术栈

Rust: 主力语言，1100 个 .rs 文件
Tokio: 异步运行时，支撑并发 Agent
Ratatui: 终端 UI 框架
ONNX Runtime: 本地向量嵌入引擎
Tree-sitter: 代码语法解析
SQLite: 本地数据持久化

## 项目规模

总文件数: 1,239
Rust 文件: 1,100
代码实体: 38,815
实体关系: 155,075
Rust Crates: 67 个
Provider 支持: 8+ (Anthropic, OpenAI, Gemini, Copilot, Antigravity, OpenRouter, Bedrock, Cursor)
内置工具: 30+

## 核心设计理念

1. 一切在终端: 不依赖 IDE，命令行即全部
2. 多 Agent 协作: Swarm 模式让多个 Agent 像团队一样工作
3. 本地优先: 嵌入和搜索在本地完成，数据不出本机
4. Provider 无关: 通过统一的 Provider 抽象层，支持任意 LLM
5. 极致性能: Rust 编译为原生二进制，启动快、内存小

## 四、技术栈全景

### 4.1 核心语言：Rust

jcode 几乎 100% 用 Rust 编写。为什么选 Rust？

- **性能**：Rust 编译为原生机器码，没有垃圾回收器（GC）的停顿，启动极快
- **内存安全**：Rust 的所有权系统在编译时保证内存安全，不会有内存泄漏或悬垂指针
- **资源效率**：Rust 程序的内存占用极低，这对多会话场景至关重要

白话解释：Rust 就像是一个超级严格的质检员，在你写代码的时候就检查出所有内存问题，而不是等程序崩溃了才发现。代价是写起来更难，但换来的是运行时的极致性能。

## 五、项目规模与架构层次

jcode 的代码组织非常清晰，按照功能分为 **7 个架构层次**：

### 第 1 层：入口层（Entry Layer）

**模块**：CLI 命令分发

这是 jcode 的大门。当你输入 jcode 命令时，这一层负责解析你的意图：
- 你想打开交互式界面？路由到 TUI
- 你想直接运行一条命令？路由到 Agent
- 你想启动服务器？路由到 Server 模式

### 第 2 层：应用编排层（App Orchestration Layer）

**模块**：应用核心

这是 jcode 的大脑中枢。它负责管理所有子系统的生命周期：启动 Agent、初始化会话、连接 TUI 界面、处理通知、管理更新。所有模块都通过这一层协调工作。

### 第 3 层：Agent 层（Agent Layer）

**模块**：Agent 运行时、Swarm 蜂群协调、计划引擎

这是 jcode 的灵魂所在。Agent 运行时是一个循环引擎：
1. 接收你的指令
2. 调用 AI 模型分析
3. 决定需要什么工具
4. 执行工具调用
5. 返回结果
6. 重复直到任务完成

**Swarm 蜂群协调**让多个 Agent 同时工作，**计划引擎**负责把复杂任务拆解成可执行的步骤。

### 第 4 层：TUI 界面层（Terminal UI Layer）

**模块**：TUI 终端界面、桌面应用

这是你看到的界面。jcode 的终端 UI 支持：
- Markdown 渲染（代码高亮、表格、列表）
- Mermaid 图表渲染（比传统方案快 1800 倍）
- 信息小部件（只在屏幕空白处显示，不占主空间）
- 侧边栏（实时显示文件内容、diff 对比）
- 千帧级渲染（你的显示器刷新率都追不上）

### 第 5 层：工具层（Tool Layer）

**模块**：工具核心、模糊搜索、PDF 处理

jcode 内置 **30+ 工具**，涵盖：
- 文件操作（读写、搜索、替换）
- 代码执行（运行 shell 命令、脚本）
- 浏览器自动化（Firefox 控制）
- Git 操作
- 网络请求
- 代码搜索（Agent Grep：不仅搜文本，还返回函数列表、结构信息）

### 第 6 层：服务层（Service Layer）

**模块**：多 Provider 体系、记忆系统、会话管理、上下文压缩、向量嵌入

这是 jcode 的核心竞争力所在：
- **记忆系统**：自动提取、存储、检索对话记忆
- **上下文压缩**：长对话自动总结，保留关键信息
- **向量嵌入**：本地 ONNX 模型，语义搜索和记忆检索
- **会话管理**：多会话隔离、历史浏览、跨工具会话导入

### 第 7 层：基础设施层（Infrastructure Layer）

**模块**：配置管理、认证系统、日志系统、构建系统、遥测系统、导入系统

支撑整个系统运行的基础设施。

## 为什么用 Rust

Rust 是 jcode 选择的技术栈，原因很明确:
1. 性能: 直接编译为机器码，没有运行时开销
2. 内存安全: 编译期检查内存错误，不会出现野指针和内存泄漏
3. 并发: Tokio 异步运行时，轻松处理多 Agent 并发
4. 单二进制: 编译后是一个独立可执行文件，无需安装依赖
5. 跨平台: 一套代码编译到 macOS/Windows/Linux
6. 生态: crates.io 上有丰富的库，Tree-sitter/Ratatui 等都是 Rust 生态的明星项目

## 七、核心设计理念

### 7.1 性能至上（Performance First）

jcode 的设计哲学是把性能榨到极致。这不是一句口号，而是贯穿整个代码库的指导思想：

- **用 Rust 替代 TypeScript**：几乎所有竞品都用 TypeScript/JavaScript，jcode 是唯一用 Rust 的
- **自定义渲染引擎**：Mermaid 图表渲染比传统方案快 1800 倍
- **自定义滚动实现**：绕过终端原生的滚动限制
- **自定义终端**：作者甚至自己写了一个终端（Handterm），只为解决原生终端的滚动限制

白话解释：作者认为，AI 编程工具的性能瓶颈不在 AI 模型本身，而在工具链。AI 模型已经很快了，但工具启动慢、渲染慢、内存占用大，拖了后腿。jcode 的目标是让工具本身零感知延迟。

### 7.2 多 Agent 协作（Swarm First）

jcode 不是一个 AI + 一个你的模式，而是一群 AI + 一个你的模式。

Swarm 架构的核心思想：
- **蜂后（Coordinator）**：接收你的指令，分解任务，分配工作
- **工蜂（Worker Agents）**：并行执行子任务，互相通信
- **自动冲突解决**：当 Agent A 修改了 Agent B 正在读的文件，系统会自动通知并协调
- **深度蜂群模式**：Agent 可以继续派生子 Agent，形成多级协作树

### 7.3 人脑式记忆（Memory as a Graph）

jcode 的记忆系统不是简单的保存对话记录，而是模仿人脑的关联记忆：

- **自动提取**：每轮对话后，系统自动提取关键信息
- **向量存储**：每条记忆被编码为向量（一组数字），存储在图中
- **语义检索**：新对话时，系统自动搜索最相关的记忆
- **级联激活**：找到一条记忆后，沿着关联边找到更多相关记忆
- **自动整理**：Ambient 模式会定期整理记忆，合并重复、删除过时、标记冲突

### 7.4 无限定制（Self-Development）

jcode 的自我开发模式是一个独特的设计：你可以让 jcode 修改自己的源代码。

这意味着：
- 你可以让 jcode 学会新的工具或技能
- 你可以让 jcode 改变自己的行为模式
- 你可以让 jcode 修复自己的 bug
- 整个过程自动编译、测试、热加载

白话解释：其他 AI 工具像是成品菜，你只能吃固定的菜单。jcode 让你可以进厨房自己炒菜，想加什么调料加什么调料。

### 7.5 Provider 中立（Provider Agnostic）

jcode 不绑定任何 AI 模型提供商。你可以用：
- 你已有的订阅（Claude Pro、ChatGPT Plus、Copilot）
- 你自己的 API Key
- 本地运行的模型（完全离线）
- 任何兼容 OpenAI API 的服务

这种设计意味着你永远不会被锁定在某一家 AI 公司。

### 7.6 离线优先 + 本地智能

jcode 的向量嵌入引擎运行在本地（ONNX 模型），不需要联网。记忆系统完全在本地运行。这意味着：
- 你的代码和数据不会离开你的机器
- 在网络受限的环境中也能用
- 记忆检索没有网络延迟

### 7.7 终端原生（Terminal Native）

jcode 认为终端才是开发者的家。它不依赖浏览器、不需要 Electron、不启动图形界面。这带来一系列好处：
- 在 SSH 远程服务器上无缝运行
- 可以和 tmux、screen 等终端复用器配合
- 可以在 CI/CD 流水线中运行
- 启动快、资源少

## 八、功能模块详解（用大白话）

### 8.1 Agent 运行时：AI 的大脑循环

Agent 运行时是 jcode 最核心的模块。你可以把它想象成一个思考-行动循环：

1. **思考**：AI 分析你的指令，决定下一步做什么
2. **行动**：调用工具（读文件、运行命令、搜索代码等）
3. **观察**：查看工具返回的结果
4. **重复**：直到任务完成

这个循环会一直运行，直到 AI 认为任务完成，或者你手动中断。

### 8.2 Swarm 蜂群：让多个 AI 一起干活

如果你有一个大任务（比如重构整个认证模块），一个 AI 从头做到尾会很慢。Swarm 模式的做法是：

1. **分解**：主 Agent 把任务拆成子任务（改数据库层、改 API 层、改前端、写测试）
2. **派发**：每个子任务派给一个子 Agent
3. **并行**：子 Agent 同时工作，互不阻塞
4. **协作**：Agent 之间可以互相发消息、通知文件变更
5. **汇总**：主 Agent 收集所有结果，做最终整合

### 8.3 记忆系统：让 AI 记住关于你的一切

jcode 的记忆系统有三层：

**第一层：自动记忆**
- 每轮对话后，系统自动提取你觉得重要的信息
- 比如用户偏好 pnpm 而不是 npm、项目使用 PostgreSQL 数据库
- 这些记忆被编码为向量，存储在本地

**第二层：语义检索**
- 新对话开始时，系统自动搜索与当前话题最相关的记忆
- 比如你问数据库怎么连，系统会检索到这个项目用的 PostgreSQL
- 这些记忆被自动注入到 AI 的上下文中，不需要你手动提醒

**第三层：记忆整理**
- Ambient 模式会定期检查记忆：有没有重复的？有没有过时的？有没有冲突的？
- 自动合并、删除、标记，保持记忆库的整洁

### 8.4 上下文压缩：长对话不爆内存

每轮对话都会消耗 AI 的上下文窗口（context window，可以理解为 AI 的短期记忆容量）。对话太长，上下文窗口满了，AI 就会忘记最开始的对话。

jcode 的上下文压缩技术：
- 自动检测对话是否过长
- 将早期对话总结为简短的摘要
- 保留关键信息，丢弃冗余内容
- 确保 AI 始终能看到最重要的上下文

### 8.5 计划引擎：让 AI 先想清楚再做

很多 AI 工具是走一步看一步的。它不知道整个任务有多大，只是闷头干活。jcode 的计划引擎会先让 AI 制定一个完整的执行计划，然后按计划一步步执行。

这就像盖房子：有图纸再施工，比边盖边想要靠谱得多。

### 8.6 浏览器自动化：让 AI 操作网页

jcode 内置了浏览器自动化工具，通过 Firefox Agent Bridge 实现：
- 可以打开网页、截图、点击按钮、填写表单
- 可以提取网页内容进行分析
- 可以在 Web 应用中进行端到端测试

### 8.7 会话导入：从其他工具无缝迁移

你不必从零开始。jcode 支持从以下工具导入会话：
- Claude Code
- Codex CLI
- OpenCode
- pi

如果你的 Claude Code 崩溃了，可以无缝切换到 jcode，从上次中断的地方继续。

## 十、技术亮点深挖

### 10.1 为什么 Rust 是关键竞争力

在 AI 编程工具领域，语言选择不是喜好问题，而是战略决策。

**竞品都用的 TypeScript/JavaScript**：
- 优点：开发快，生态丰富
- 缺点：启动慢（需要加载 Node.js 运行时），内存占用大（V8 引擎 + GC），单线程模型受限

**jcode 用的 Rust**：
- 优点：启动极快（原生二进制），内存占用极低（无 GC），真正的并发
- 缺点：开发门槛高，编译慢

jcode 作者选择了更难的路，但换来了不可逾越的性能壁垒。竞品如果想追上 jcode 的性能，几乎需要重写整个代码库。

### 10.2 自定义 Mermaid 渲染器

jcode 作者自己写了一个 Mermaid 渲染器（mermaid-rs-renderer），比传统方案快 1800 倍。

传统方案：用浏览器或 Node.js 渲染 Mermaid，转换为图片，在终端显示
jcode 方案：Rust 原生渲染，直接输出到终端

为什么这很重要？在 AI 编程场景中，AI 经常需要输出架构图、流程图、时序图来帮助理解代码结构。如果每次渲染图都要等一秒，体验会很差。jcode 做到了几乎瞬间。

### 10.3 Agent Grep：为 AI 优化的代码搜索

jcode 的 Agent Grep 不是普通的 grep。它会在搜索结果中附加：
- 文件中的函数列表
- 每个函数的位置偏移
- 文件结构概览

这样 AI 不需要额外读取文件就能大致了解文件内容，大幅节省了上下文窗口的消耗。

### 10.4 Claude 缓存感知

jcode 对 AI 模型的底层行为有深入理解。比如 Claude 的缓存机制：

- Claude 会在 5 分钟内保持上下文缓存（省 tokens）
- 超过 5 分钟，缓存过期，下次调用会多花很多 tokens
- jcode 的 UI 会主动提醒你缓存过期，甚至告诉你是否有意外的缓存丢失

这种对细节的关注，体现了 jcode 作为工程师的工具的产品哲学。

## 十二、总结：jcode 的独特价值

### 12.1 三个关键词

1. **性能**：不是快一点，是快一个数量级
2. **协作**：不是一个 AI，是一群 AI 协同工作
3. **记忆**：不是每次都从零开始，是越用越了解你

### 12.2 与竞品的本质差异

大多数 AI 编程工具是 AI 模型 + 聊天界面。jcode 是 AI 模型 + 操作系统。

聊天界面只能做一件事：你问，AI 答。操作系统可以管理多个进程、协调资源、记住状态、自动化任务。

jcode 的野心不是做一个更好的聊天框，而是成为**开发者与 AI 协作的操作系统**。

### 12.3 适合谁？

- 如果你每天在终端里工作超过 4 小时，jcode 可能是你今年最重要的工具
- 如果你需要同时管理多个技术任务，jcode 的 Swarm 模式会改变你的工作方式
- 如果你对 AI 工具的性能和定制化有极致要求，jcode 是目前唯一的选择
- 如果你需要在远程服务器上使用 AI 编程助手，jcode 是原生方案

### 12.4 不适合谁？

- 如果你更喜欢图形界面，jcode 的终端 UI 可能不适合你
- 如果你只需要简单的代码补全，IDE 内置的 Copilot 已经够用
- 如果你在 Windows 上主要用 WSL 之外的工具，jcode 的 Windows 支持还在完善中

## 第一层：CLI 入口层

### 这层是干什么的？

简单说，就是**用户敲命令的第一站**。你打开终端输入 `jcode`，操作系统加载 jcode 程序，第一行代码就从这里开始执行。

### 用大白话解释

把 jcode 想象成一个"多功能瑞士军刀"。你按不同的方式打开它，它就干不同的事：

- 你输入 `jcode`（不加参数）→ 打开 TUI 聊天界面
- 你输入 `jcode chat` → 进入命令行对话模式
- 你输入 `jcode serve` → 启动后台服务器（供其他窗口连接）
- 你输入 `jcode login --provider claude` → 登录 Claude 账号
- 你输入 `jcode --resume abc123` → 恢复之前的会话 abc123
- 你输入 `jcode swarm` → 启动多 Agent 协作模式

CLI 入口层就是那个"读心人"——它解析你的命令，搞清楚你想干什么，然后**把活儿派给对应的模块**。

### 技术细节（用大白话）

CLI 入口层用了一个叫 `clap` 的 Rust 库来做命令行解析。`clap` 就像是一个"命令翻译官"：

1. 你敲 `jcode --provider openai --model gpt-5.5`
2. `clap` 把它翻译成结构化数据：`{ provider: "openai", model: "gpt-5.5" }`
3. 入口层根据这些数据，决定启动哪个子系统

### 支持的命令一览

| 命令 | 干什么 | 典型场景 |
|------|--------|---------|
| `jcode`（无参数） | 启动 TUI 交互界面 | 日常编码对话 |
| `jcode chat` | 单次对话模式 | 脚本化调用、CI/CD 集成 |
| `jcode serve` | 启动后台服务器 | 多窗口共享同一个 jcode 进程 |
| `jcode login` | OAuth 登录 | 首次配置 AI 账号 |
| `jcode --resume <id>` | 恢复会话 | 继续昨天的活 |
| `jcode swarm` | 多 Agent 协作 | 复杂项目需要分工 |
| `jcode update` | 检查更新 | 升级到最新版 |
| `jcode setup-hotkey` | 配置全局快捷键 | macOS 上 Cmd+; 快速唤起 |

### 启动流程（从零到界面出现）

```
用户敲 jcode
    │
    ├─ 1. 配置内存分配器（jemalloc/glibc 调优）
    │     "让内存用得又快又省"
    │
    ├─ 2. 检查是否是快捷键唤起
    │     "如果是 Cmd+; 唤起的，走特殊逻辑"
    │
    ├─ 3. 初始化 Tokio 异步运行时
    │     "Rust 的异步引擎，相当于给程序装上多线程大脑"
    │
    ├─ 4. 解析命令行参数
    │     "搞懂用户想干什么"
    │
    ├─ 5. 初始化日志系统
    │     "开始记日志，方便排查问题"
    │
    ├─ 6. 注册外部 Provider 运行时
    │     "加载各种 AI 模型的驱动"
    │
    ├─ 7. 路由到对应子系统
    │     "把活儿派出去"
    │
    └─ 8. 启动 TUI 或 Server
          "用户看到界面"
```

**性能数据**：从敲命令到第一帧画面出现仅需 **14ms**（毫秒），比同类工具快 27~245 倍。

## 第二层：应用编排层

### 这层是干什么的？

这是整个 jcode 的**总管家**。如果把 jcode 比作一个公司，这层就是 CEO——它不亲自写代码，不亲自调 AI，但它**协调所有部门**，确保一切正常运转。

### 核心职责

| 职责 | 大白话解释 |
|------|-----------|
| **生命周期管理** | 谁来启动？谁来关闭？什么时候该重启？ |
| **会话调度** | 用户开了 3 个会话，怎么分配资源？ |
| **Agent 编排** | 什么时候叫 Agent 干活？怎么把结果传回界面？ |
| **通知分发** | 文件被改了、会话完成了、更新可用了——通知谁？ |
| **更新检查** | 新版本发布了吗？要不要自动更新？ |
| **遥测上报** | 用户用了多久？哪个功能最受欢迎？（匿名统计） |

### 为什么需要这一层？

你可能会问：为什么不让 CLI 入口层直接调用 Agent 层？非要加一个"中间人"？

答案很简单：**解耦（让各部分独立变化）**。

举个例子：假设没有应用编排层，CLI 入口层直接调用 Agent 层。那么每次你想加一个新功能（比如"在会话结束时自动保存记忆"），你就得改 CLI 入口层的代码——但 CLI 入口层本来只负责"解析命令"，不应该管"记忆保存"。这就像让前台接待员同时管财务——虽然也能干，但职责混乱，一出问题很难排查。

有了应用编排层：
- **CLI 入口层**只管"用户想干什么"
- **应用编排层**管"谁来干、什么时候干、干完怎么通知"
- **Agent 层**只管"跟 AI 对话、执行工具"

各司其职，互不干扰。

### 启动时做了什么？

应用编排层在启动时会做一系列"初始化"工作，相当于"公司开张前的准备"：

1. **启动性能计时器** — 记录每个启动步骤花了多少时间，用于性能优化
2. **安装崩溃处理** — 万一程序崩了，至少能优雅退出，不乱丢数据
3. **初始化日志** — 开始记日志
4. **清理旧日志/会话备份** — 后台线程自动清理，不阻塞启动
5. **注册配置变更回调** — 用户改了配置，自动刷新认证状态
6. **注册 API Key 后备解析器** — 从环境变量/其他 CLI 工具里自动找 API Key
7. **注册外部 Provider** — 加载 Gemini、Cursor、Copilot 等运行时
8. **注册权限通知分发器** — 工具需要权限时，通过这个通道弹窗询问
9. **注册记忆条目提供者** — 技能（Skills）自动转化为记忆条目
10. **注册 Server 生成器** — TUI 可以请求启动/重启后台服务器

这些步骤看着多，但 jcode 设计得很巧妙——**很多工作是并行做的，不互相等待**，所以启动速度极快。

## 第三层：Agent 层

### 这层是干什么的？

这是 jcode 的**灵魂**。Agent 层的核心工作就是：

> 用户说一句话 → Agent 理解意图 → 调 AI 模型 → AI 说"我需要执行这个工具" → Agent 执行工具 → 把结果给 AI → AI 再思考 → 反复循环 → 最终输出答案

这个循环在业界叫 **Agent Loop（Agent 循环）**。

### Agent 层包含三个核心模块

```
┌─────────────────────────────────────────────────────────────┐
│                      Agent 层                                │
│                                                             │
│  ┌─────────────────┐  ┌─────────────────┐  ┌─────────────┐ │
│  │  agent_runtime   │  │   swarm_core    │  │  plan_core   │ │
│  │  Agent 运行时    │  │   Swarm 群协调   │  │  计划引擎    │ │
│  │                 │  │                 │  │             │ │
│  │ "单个 Agent 的  │  │ "多个 Agent 的  │  │ "复杂任务   │ │
│  │  思考-执行循环" │  │  协作与通信"    │  │  自动拆解"  │ │
│  └────────┬────────┘  └────────┬────────┘  └──────┬──────┘ │
│           │                    │                   │        │
```

### 3.1 Agent 运行时：思考-执行循环

这是最核心的模块。它的工作流程如下：

```
┌──────────────────────────────────────────────────────────┐
│                    Agent Loop                             │
│                                                          │
│  用户: "帮我把这个 Bug 修了"                              │
│       │                                                  │
│       ▼                                                  │
│  ┌─────────┐    ┌──────────┐    ┌──────────┐            │
│  │ 1. 读取  │───▶│ 2. 调用   │───▶│ 3. AI 返回│           │
│  │   记忆   │    │   AI 模型 │    │   思考结果│           │
│  └─────────┘    └──────────┘    └────┬─────┘            │
│                                      │                   │
│                    ┌─────────────────┤                   │
│                    ▼                 ▼                   │
│            ┌──────────┐      ┌──────────┐               │
│            │ AI 说:    │      │ AI 说:    │               │
│            │ "我直接   │      │ "我需要   │               │
│            │  回答你"  │      │  执行工具"│               │
│            └────┬─────┘      └────┬─────┘               │
│                 │                 │                      │
│                 ▼                 ▼                      │
│            ┌──────────┐      ┌──────────┐               │
│            │ 4. 输出   │      │ 4. 执行   │               │
│            │   答案    │      │   工具    │               │
│            └──────────┘      └────┬─────┘               │
│                                   │                      │
│                                   ▼                      │
│                            ┌──────────┐                  │
│                            │ 5. 工具   │                  │
│                            │   返回结果│                  │
│                            └────┬─────┘                  │
│                                 │                        │
│                                 ▼                        │
│                            ┌──────────┐                  │
│                            │ 6. 把结果│                  │
│                            │   给 AI  │────── 循环 ──────┘
│                            └──────────┘   (回到步骤 2)
│                                                          │
│  循环什么时候结束？                                       │
│  - AI 说"我完成了"（不再需要工具）                        │
│  - 达到最大循环次数（防止无限循环）                       │
│  - 用户手动中断                                          │
└──────────────────────────────────────────────────────────┘
```

**用大白话描述**：

想象你有一个非常聪明的助手，但他在一个空房间里，只有一台电脑。你给他一个任务，他不能直接帮你做——他需要：
1. 先回忆一下之前有没有做过类似的事（读记忆）
2. 想一想要怎么做（调 AI 模型）
3. 如果需要查文件，就"打开文件"（执行工具）
4. 如果需要跑代码，就"运行命令"（执行工具）
5. 把工具的结果拿回来，再想一想（回到步骤 2）
6. 直到他觉得"做完了"，给你最终答案

### 3.2 Swarm 群协调：多 Agent 协作

这是 jcode 的**杀手级功能**。传统 AI 编码工具只有一个 Agent，jcode 可以同时跑多个。

**场景举例**：

你想做一个网站，包含前端页面、后端 API、数据库设计。传统方式只能一个一个来，Agent A 做完前端再做后端。但 jcode 可以这样：

```
                    主 Agent（协调者）
                    "做一个完整的网站"
                          │
            ┌─────────────┼─────────────┐
            ▼             ▼             ▼
      子 Agent A      子 Agent B      子 Agent C
      "做前端页面"    "做后端 API"    "设计数据库"
            │             │             │
            └─────────────┼─────────────┘
                          │
                    自动合并结果
```

**Swarm 的智能之处**：

1. **自动冲突检测**：Agent A 改了文件 X，Agent B 也读了文件 X → 服务器通知 Agent B "文件变了，你注意一下"
2. **Agent 间通信**：Agent 可以互相发消息——"嘿，我把 API 接口改了一下，你前端记得适配"
3. **自动管理**：Agent 的创建、通信、完成状态追踪，全部自动

### 3.3 计划引擎：智能任务拆解

计划引擎是"大脑的大脑"。当你给一个复杂任务时，它自动把任务拆成小步骤。

**举例**：

用户说："帮我把这个项目从 JavaScript 迁移到 TypeScript"

计划引擎会自动拆解：
```
1. 分析项目结构，列出所有 .js 文件
2. 安装 TypeScript 依赖
3. 创建 tsconfig.json
4. 逐个文件: 重命名 .js → .ts，修复类型错误
5. 运行测试，确保功能正常
6. 更新构建配置
```

然后计划引擎把这些步骤分配给 Swarm 并行执行，大大加快速度。

### 上下文折叠

Agent 跟 AI 对话时，每次对话都有"上下文"——也就是 AI 能"看到"的历史消息。但 AI 模型有上下文长度限制（比如 Claude 能看 20 万 token，约等于一本中篇小说）。

当对话太长时，Agent 需要做**上下文折叠**：把旧的、不重要的对话内容压缩成摘要，腾出空间给新内容。这就像你看完一章书后，在脑子里记一个"本章讲了什么"，而不是背下每个字。

jcode 的上下文折叠做得非常智能——它知道哪些信息是"关键信息"（比如用户的核心需求），哪些是"过程信息"（比如中间某次失败的尝试），折叠时保留前者、压缩后者。

### 这层是干什么的？

**TUI = Terminal User Interface（终端用户界面）**。就是你在终端里看到的那个界面。

jcode 不用浏览器、不用 Electron，直接在你的终端里画出漂亮的界面——包括聊天框、侧边栏、Mermaid 图表、代码高亮、Diff 对比等。

### 用大白话解释 TUI 核心

在终端里画界面，听起来很"复古"，但实际上 jcode 把终端 UI 做到了极致：

| 功能 | 大白话解释 | 技术细节 |
|------|-----------|---------|
| **会话列表** | 左边一栏显示你开了几个会话，可以切换 | 模糊搜索，几百个会话秒找 |

### 用大白话解释桌面应用

jcode 虽然是终端应用，但它也提供了桌面端体验（主要是 macOS）：

- **菜单栏图标**：在 macOS 顶部菜单栏显示一个小图标，点击可以快速操作
- **全局快捷键**：按 `Cmd+;` 在任何地方唤起 jcode
- **剪贴板集成**：AI 可以直接读取/写入你的剪贴板
- **截图**：AI 可以截取屏幕，这在"看图写代码"场景下非常有用
- **系统通知**：任务完成时发送 macOS 通知

### 为什么终端 UI 能做这么漂亮？

jcode 使用了两个关键 Rust 库：

- **ratatui**：一个终端 UI 框架，提供了"在终端里画窗口、按钮、列表"的能力。你可以把它理解为"终端里的 HTML+CSS"
- **crossterm**：一个跨平台终端控制库，处理键盘输入、鼠标事件、颜色、光标等底层操作

加上 jcode 自己的大量定制渲染代码（15+ 个 TUI 相关的 crate），最终实现了在纯文本终端里渲染出接近 GUI 的体验。

### 渲染性能

jcode 的渲染速度超过 **1000 FPS**（帧每秒）——你的显示器根本跟不上。这意味着：
- 不会出现闪烁，不会出现撕裂
- 滚动丝滑（自研滚动实现）
- 输入延迟极低（首帧 14ms，可输入 48ms）

### 5.1 多 Provider 体系：AI 模型的"万能插座"

jcode 支持连接 8 种以上的 AI 模型提供商，就像一个"万能插座"——不管你用的是哪个 AI 服务，插上就能用。

| Provider | 接入方式 | 说明 |
|----------|---------|------|
| **Anthropic (Claude)** | OAuth 登录 | 最常用的接入方式，用你的 Claude 订阅 |
| **OpenAI (ChatGPT/Codex)** | OAuth 登录 | 用你的 ChatGPT 订阅 |
| **Google Gemini** | OAuth 登录 | 用你的 Google 账号 |
| **GitHub Copilot** | OAuth 登录 | 用你的 GitHub 订阅 |
| **OpenRouter** | API Key | 聚合平台，一个 Key 访问多种模型 |
| **AWS Bedrock** | IAM 凭证 | 企业级 AWS 用户 |
| **Cursor** | 本地凭证 | 复用 Cursor 编辑器的登录状态 |
| **Antigravity** | OAuth 登录 | 另一个 AI 编码平台 |
| **Azure OpenAI** | API Key | 微软 Azure 的企业用户 |
| **自定义 OpenAI 兼容** | API Key + URL | 任何兼容 OpenAI API 的服务（Ollama、LM Studio 等） |

**Provider 的设计亮点**：

1. **自动检测**：如果你已经登录了 Claude Desktop 或 Cursor，jcode 能自动找到你的登录凭证，不用重复登录
2. **热切换**：在会话中可以随时切换模型——"这个简单问题用便宜的模型，那个复杂问题用贵的模型"
3. **故障转移**：一个 Provider 挂了，可以自动切换到备用的
4. **OAuth 流程**：浏览器自动打开登录页面，授权后自动回调，全程不用手动复制粘贴 Key

### 5.2 记忆系统：让 AI 记住你

这是 jcode 最让人惊艳的功能之一。传统的 AI 编码工具是"金鱼记忆"——每次新会话都是白纸一张，不记得你之前说过什么、做过什么。

jcode 的记忆系统就像一个**真正的同事**——它会记住你的偏好、项目的背景、之前的决策，越用越聪明。

**记忆系统的工作原理**（用大白话）：

```
对话进行中...
    │
    ▼
┌─────────────────────────────────────────────┐
│  1. 语义漂移检测                            │
│  "对话话题是不是变了？变化够大吗？"           │
│  如果变了 → 触发记忆提取                     │
└────────────────────┬────────────────────────┘
                     │
                     ▼
┌─────────────────────────────────────────────┐
│  2. 记忆提取（Memory SideAgent）             │
│  一个后台 Agent 悄悄分析对话，提取关键信息：   │
│  - "用户喜欢用 Rust，不喜欢 Python"          │
│  - "这个项目数据库用的是 PostgreSQL"          │
│  - "上次重构时决定用微服务架构"               │
└────────────────────┬────────────────────────┘
                     │
                     ▼
┌─────────────────────────────────────────────┐
│  3. 向量嵌入（Embedding）                    │
│  把文字记忆转成数学向量（一串数字）            │
│  相似的记忆，向量也相似                       │
│  "向量嵌入"就像给每段记忆打上 GPS 坐标         │
└────────────────────┬────────────────────────┘
                     │
                     ▼
┌─────────────────────────────────────────────┐
│  4. 记忆检索                                 │
│  新对话开始时，用当前话题的向量去匹配           │
│  找到最相关的记忆，自动注入到对话中             │
│  "你说的这个话题，我之前记得..."              │
└─────────────────────────────────────────────┘
```

**记忆的三种使用方式**：

| 方式 | 说明 | 举例 |
|------|------|------|
| **被动召回** | 自动检索相关记忆，不需要用户操作 | 你提到"数据库"，自动召回"上次用的是 PostgreSQL" |
| **主动工具** | Agent 可以主动调用记忆工具搜索/存储 | `memory_search("数据库迁移方案")` |
| **会话搜索** | 搜索历史会话内容（传统 RAG） | 搜索"上次那个 Bug 是怎么修的" |

**记忆的维护**：

jcode 在后台（Ambient 模式）会定期做记忆维护：
- **去重**：删掉重复的记忆
- **合并**：把相关的记忆整理成一条
- **过期检测**：标记过时的信息
- **冲突检测**：发现矛盾的记忆，提醒用户

### 5.3 会话管理：多任务并行

jcode 支持同时开多个会话，就像浏览器可以开多个标签页。每个会话是**完全隔离**的——会话 1 的对话不会"污染"会话 2 的上下文。但共享记忆是**跨会话共享**的，所以你在会话 1 里学到的知识，会话 2 也能用上。

**会话管理核心能力**：创建/恢复、历史浏览、导入导出（从 Claude Code、Codex 等）、自动备份。

### 5.4 上下文压缩

当对话越来越长，就需要"压缩"——把不重要的内容缩成摘要，保留关键信息。

jcode 的上下文压缩很智能：
- **保留关键决策**：用户说"用 PostgreSQL"——这个不能丢
- **压缩中间过程**：Agent 尝试了 3 种方案，前 2 种失败了——压缩成"尝试了 2 种方案后选择第 3 种"
- **保留错误教训**：某些操作导致了问题——保留这个教训，避免重蹈覆辙

### 5.5 向量嵌入

这是记忆系统的"引擎"。jcode 在本地运行一个 AI 模型（ONNX 格式，MiniLM），把文字转成数学向量。

**为什么要在本地跑？**
- **隐私**：你的数据不出你的电脑
- **速度**：不需要网络请求，毫秒级响应
- **成本**：不需要额外付费

**性能数据**：嵌入模型本地运行约 87MB 内存，每次嵌入约需几十毫秒。

## 架构决策记录



### ADR-003: 为什么分成 70+ 个 Crate？

看到 jcode 的源码目录，你可能会被 `crates/` 下 70+ 个子目录吓到。这是故意的。

**核心原因：编译速度**

Rust 的编译单元是 crate。如果把所有代码放在一个 crate 里，改一行代码就要重新编译整个项目（可能 5-10 分钟）。但如果拆成 70 个小 crate，改一行代码只需要重新编译那个小 crate（可能 10-30 秒）。

**Crate 拆分原则**：

```
jcode-base          ← 基础类型和工具（改动最少）
    ↑
jcode-app-core      ← 应用核心逻辑（偶尔改动）
    ↑
jcode-tui           ← TUI 界面（经常改动）
    ↑
jcode (root)        ← CLI 入口（改动频繁）
```

Provider 运行时（gemini、cursor、copilot 等）被放在独立的 crate 里，这样改一个 Provider 不会导致整个应用重编译。

**影响**：开发体验显著提升，编译等待时间从"去喝杯咖啡"变成"刷一下手机"。但代价是 crate 之间的依赖关系需要精心管理，否则会出现循环依赖。

### ADR-004: 为什么需要 Swarm 而不是单 Agent 多步骤？

| 因素 | Swarm（多 Agent 并行） | 单 Agent 多步骤 |
|------|----------------------|----------------|
| 速度 | 并行执行，快 | 串行执行，慢 |
| 复杂性 | 需要冲突检测和通信 | 简单，不需要协调 |
| 适用场景 | 大型项目、多模块 | 小型任务、单文件 |

**决策**：引入 Swarm 虽然增加了复杂度，但对于实际项目来说，并行执行带来的效率提升远超协调成本。

**影响**：Swarm 是 jcode 的差异化功能之一。它让 jcode 从"AI 助手"升级为"AI 开发团队"。

### ADR-005: 为什么本地运行嵌入模型而不是调用云端 API？

| 因素 | 本地 ONNX 模型 | 云端 Embedding API |
|------|---------------|-------------------|
| 隐私 | ✅ 数据不出电脑 | ❌ 数据发送到云端 |
| 速度 | 毫秒级（无网络延迟） | 几十到几百毫秒 |
| 成本 | 免费（多占 87MB 内存） | 按 Token 计费 |
| 离线可用 | ✅ | ❌ |

**决策**：记忆系统是高频操作，如果每次都调云端 API，延迟和成本都不可接受。本地运行虽然多占 87MB 内存，但换来了隐私、速度和零成本。

**影响**：jcode 在启动时会加载一个约 87MB 的 ONNX 模型到内存中。这是 jcode 内存占用从 27.8MB（embedding 关闭）到 167.1MB（embedding 开启）的主要原因。但即使如此，仍然远低于同类工具。

### ADR-006: 为什么 Provider 设计成插件式？

**决策**：每个 AI 模型提供商（Anthropic、OpenAI、Gemini 等）都是一个独立的 crate，通过统一的接口注册到 Provider 注册表中。

**好处**：添加新 Provider 不需要改核心代码；一个 Provider 的 Bug 不会影响其他 Provider；用户可以自由选择 Provider，甚至同时配置多个；社区可以贡献第三方 Provider。

**影响**：Provider 接口需要精心设计，确保所有 Provider 的行为一致。jcode 通过 Provider Doctor 工具来自动诊断 Provider 配置问题。

### ADR-007: 为什么采用上下文折叠而不是无限扩展上下文？

| 因素 | 上下文折叠 | 无限扩展上下文 |
|------|-----------|---------------|
| Token 成本 | 低（折叠后占空间小） | 高（每次请求都带完整历史） |
| 响应速度 | 快（上下文小） | 慢（上下文大） |
| 模型限制 | 兼容所有模型 | 需要模型支持超长上下文 |

**决策**：采用智能上下文折叠，在保留关键信息的同时压缩历史。这是工程上的务实选择——不是所有模型都支持超长上下文，而且即使支持，Token 成本也太高。

**影响**：折叠策略需要不断调优。折叠太激进会丢失重要信息，折叠太保守又起不到压缩效果。jcode 通过语义分析来识别"关键信息"，在这方面持续迭代。

## 性能与资源设计

### 性能数据总览

| 指标 | jcode | 行业平均 | 领先倍数 |
|------|-------|---------|---------|
| 启动速度（首帧） | **14.0 ms** | 500-3500 ms | 27x - 245x |
| 可输入时间 | **48.7 ms** | 380-3500 ms | 7x - 72x |
| 1 会话内存 | **27.8 MB** | 140-386 MB | 5x - 14x |
| 10 会话内存 | **117 MB** | 334-3237 MB | 3x - 28x |
| 每会话增量 | **~10 MB** | 21-318 MB | 2x - 32x |
| 渲染帧率 | **1000+ FPS** | 30-60 FPS | 16x - 33x |

### 为什么 jcode 这么快？

**1. Rust 语言本身**

Rust 是系统级编程语言，编译成原生机器码，没有虚拟机、没有垃圾回收器（GC）。这意味着：
- 启动时不需要加载运行时环境
- 运行时不需要 GC 暂停（"stop the world"）
- 内存布局紧凑，CPU 缓存友好

**2. 异步运行时 (Tokio)**

jcode 使用 Tokio 作为异步运行时。Tokio 是 Rust 生态中最成熟的异步框架，可以高效地处理数千个并发任务，而只使用少量线程。

**3. 内存分配器调优**

jcode 对内存分配器做了精细调优：
- 使用 jemalloc（默认）或 glibc malloc
- 配置了 arena 数量、脏页回收策略、mmap 阈值
- 确保大块内存（如 ONNX 模型）用完后立即归还给操作系统

**4. 关键路径优化**

jcode 对性能敏感的关键路径做了专门优化：
- 模糊搜索：opt-level=3，使用 SIMD 加速
- 文本渲染：cosmic-text 等库 opt-level=3
- 嵌入模型：tract ONNX 推理 opt-level=3
- 动画计算：jcode-tui-anim opt-level=3
- 图片处理：png/jpeg 解码 opt-level=3

**5. 增量编译**

虽然编译速度不是运行时性能，但 jcode 的 70+ crate 拆分让开发迭代更快，团队能更快地优化性能。

### 为什么 jcode 这么省内存？

**1. 无浏览器内核**

jcode 是纯终端应用，不需要嵌入 Chromium 或 WebKit。这意味着直接省掉了 200-500MB 的内存开销。

**2. 会话共享进程**

jcode 的所有会话共享同一个进程，而不是每个会话启动一个进程。这意味着：
- 代码段（text segment）共享：一份，多人用
- 连接池复用：HTTP 连接、WebSocket 连接共享
- 内存池复用：分配器层面共享内存池

**3. 原生二进制**

Rust 编译成单个二进制文件，没有解释器或虚拟机的内存开销。

**4. 精确控制**

Rust 的所有权系统让开发者精确控制内存的分配和释放。没有垃圾回收器意味着不会有"内存已经不用了但 GC 还没回收"的情况。

## 1. 项目总览

### 一句话说明

jcode 是一个用 Rust 从头构建的 AI 编码代理。它不是 ChatGPT 的插件或 VS Code 的扩展，
而是一个独立运行的 AI 程序员，能理解你的代码仓库、制定修改计划、自动写代码、跑测试，
甚至能同时派出多个子代理并行干活。

### 为什么叫下一代？

市面上的 AI 编码工具（如 GitHub Copilot、Cursor）大多工作在补全层面：你写一行，它猜下一行。
jcode 则工作在代理层面：你给它一个需求（比如把登录模块从 JWT 改成 OAuth 2.0），
它自己规划步骤、修改文件、运行测试、修复报错，像一个真正的初级工程师一样完成整个任务。

### 为什么用 Rust？

Rust 是一门以零成本抽象和内存安全著称的系统编程语言。用 Rust 构建 jcode 意味着：

- **启动快**：毫秒级冷启动，不像 Python/Node.js 工具需要等几秒
- **内存省**：一个 Agent 进程只占几十 MB，可以同时跑几十个 Swarm 子代理
- **跨平台**：一套代码编译出 macOS / Linux / Windows 原生二进制
- **不依赖运行时**：不需要安装 Python、Node.js，用户下载一个二进制文件就能跑

## 2. Agent 运行时

### 一句话说明

Agent 运行时是 jcode 的大脑中枢。它负责接收用户指令、调度工具、与大模型对话、管理整个任务的生命周期，就像一个项目经理在协调各方资源。

### 业务价值

| 维度 | 说明 |
|------|------|
| **可靠性** | 任务状态持久化，断点续跑，不会因为网络波动丢掉进度 |
| **可控性** | 每一步操作都有日志，出问题可以回溯到具体哪一步 |
| **并发性** | 一个运行时可以同时管理多个任务，互不干扰 |
| **扩展性** | 新增工具、新增 Provider 只需注册，不用改核心逻辑 |

### 使用场景

1. **单任务执行**：用户说帮我修复 issue #42，Agent 运行时启动一个会话，从理解需求到提交 PR 全自动完成
2. **多任务并行**：同时处理重构用户模块和写单元测试，两个任务不同会话，互不干扰
3. **长任务挂起**：一个重构任务跑了 30 分钟，用户关掉终端，下次打开自动恢复进度
4. **CI/CD 集成**：作为 GitHub Actions 的一个步骤，自动修复 lint 报错

### 关键流程

```
用户输入 '修复登录页面的 bug'
        |
        v
+---------------------+
|  1. 解析指令         |  理解用户意图，提取关键信息
|     (Parser)        |
+---------+-----------+
          |
          v
+---------------------+
|  2. 创建会话         |  分配唯一 Session ID，初始化上下文
|     (Session)       |
+---------+-----------+
          |
          v
+---------------------+
|  3. 进入主循环       |  +---------------------------+
|     (Main Loop)     |  |  a. 构建 Prompt            |
|                     |  |  b. 调用大模型              |
|                     |  |  c. 解析模型返回            |
|                     |  |  d. 执行工具调用            |
|                     |  |  e. 收集结果，更新上下文     |
|                     |  |  f. 判断是否完成            |
|                     |  +---------------------------+
+---------+-----------+
          |
          v
+---------------------+
|  4. 输出结果         |  生成摘要、PR 描述、变更日志
|     (Result)        |
+---------------------+
```

### 核心设计

#### 状态机模型

Agent 运行时采用有限状态机设计，每个任务会话严格处于以下状态之一：

```
IDLE -> PLANNING -> EXECUTING -> VERIFYING -> DONE
                      |               |
                    PAUSED          FAILED
                      |               |
                   RESUMED         RETRYING
```

- **IDLE**：空闲，等待用户指令
- **PLANNING**：制定计划中，调用计划引擎
- **EXECUTING**：执行中，工具调用和模型交互
- **VERIFYING**：验证阶段，跑测试、检查 lint
- **DONE**：任务完成
- **PAUSED**：用户手动暂停或系统挂起
- **FAILED**：执行失败，但可重试
- **RETRYING**：正在重试上一次失败的任务

这个设计的好处是：**状态可预测、可恢复、可审计**。不像某些工具黑盒执行，你不知道它现在在干嘛、卡在哪一步。

#### 事件驱动架构

Agent 运行时内部是事件驱动的，每个操作（工具调用开始、模型返回、错误发生）都产生一个事件，进入事件总线。这样做的好处：

- **解耦**：日志模块、UI 模块、监控模块各自订阅关心的事件，互不影响
- **可观测**：任何时候都能看到现在正在执行什么
- **可扩展**：新增一个模块，只需订阅相关事件即可

#### 会话持久化

每个会话的状态（包括对话历史、工具调用记录、中间产出）都持久化到磁盘。这意味着：

- 用户关掉终端不会丢失进度
- 可以回溯任意历史会话
- 支持会话分叉：从某个中间状态尝试不同的方案

## 3. Swarm 群协调系统

### 一句话说明

Swarm 是 jcode 的分身术。当任务太复杂、太大，一个 Agent 搞不定时，Swarm 能自动拆解任务，派出多个子代理同时干活，最后把结果合并回来。

### 业务价值

| 维度 | 说明 |
|------|------|
| **速度** | 多个子代理并行工作，任务总耗时 = 最慢子任务的时间，而非所有子任务之和 |
| **质量** | 每个子代理专注一个子任务，比一个大代理一心多用更不容易出错 |
| **规模** | 理论上可以同时管理几十个子代理，处理超大型代码仓库 |
| **隔离** | 子代理之间互不干扰，一个子任务失败不影响其他 |

### 使用场景

1. **大型重构**：把整个项目从 JavaScript 迁移到 TypeScript，Swarm 按文件/模块拆分，每个子代理负责一个模块
2. **多仓库联动**：更新前端 API 调用以匹配后端新接口，一个子代理改前端，一个改后端，一个更新文档
3. **全面测试**：给所有模块写单元测试，每个子代理负责一个模块的测试
4. **代码审查**：审查这次 PR 的所有变更，多个子代理从安全性、性能、可读性等不同角度审查

### 关键流程

```
用户输入 '把所有 .js 文件改成 .ts，并修复类型错误'
        |
        v
+-------------------------------+
|  1. 任务分解 (Decompose)      |  分析任务，拆成子任务
|     发现 23 个 .js 文件       |
|     -> 拆成 4 组，每组 5-6 个  |
+---------------+---------------+
                |
                v
+-------------------------------+
|  2. 创建 Swarm                |  启动协调器 + 4 个子代理
|     Coordinator: 1 个         |
|     Workers: 4 个             |
+---------------+---------------+
                |
      +---------+---------+---------+
      v         v         v         v
  +--------+ +--------+ +--------+ +--------+
  |Worker 1| |Worker 2| |Worker 3| |Worker 4|
  |改5个文件| |改6个文件| |改6个文件| |改6个文件|
  +----+---+ +----+---+ +----+---+ +----+---+
       |          |          |          |
       +----------+----------+----------+
                  |          |
                  v          v
+-------------------------------+
|  3. 结果合并 (Merge)          |  Coordinator 收集结果
|     检查冲突，合并变更         |
+---------------+---------------+
                |
                v
+-------------------------------+
|  4. 统一验证                  |  跑全量测试，确保合并后没问题
+-------------------------------+
```

### 核心设计

#### Coordinator-Worker 模式

Swarm 系统采用经典的协调者-工作者模式：

- **Coordinator（协调者）**：不干活，只负责分活和收活。它分析任务、拆解子任务、分配给 Worker、收集结果、处理冲突。
- **Worker（工作者）**：每个 Worker 就是一个完整的 Agent 运行时实例，有独立的上下文、独立的工具访问权限，专心完成自己的子任务。

打个比方：Coordinator 是包工头，Workers 是装修工人。包工头不贴瓷砖，但他知道哪个工人擅长什么、谁来干哪个房间、最后怎么验收。

#### 动态分派策略

jcode 的 Swarm 不是简单地平均分配，而是根据以下因素动态决策：

1. **文件大小**：大文件分给一个 Worker，小文件打包
2. **依赖关系**：有依赖的模块尽量分给同一个 Worker，减少跨 Worker 通信
3. **Worker 状态**：空闲的 Worker 优先分配，正在忙的少分配
4. **历史表现**：如果某个 Worker 在类似任务上成功率高，多分配

#### 冲突处理

当多个 Worker 修改了同一个文件（或相关联的文件），Coordinator 需要合并。jcode 采用分层策略：

- **第一层**：Git 自动合并，如果文件不同区域被修改，自动合并
- **第二层**：语义分析，如果 Git 合并不了，尝试理解变更意图，智能合并
- **第三层**：人工介入，如果实在合并不了，标记冲突，让用户决定

#### 通信机制

Worker 之间不会直接通信（避免耦合），而是通过 Coordinator 中转。通信内容仅限于：

- 子任务状态更新（完成 / 失败 / 进度）
- 需求澄清（Worker 发现模糊需求，请求 Coordinator 澄清）
- 依赖通知（Worker A 完成了一个接口定义，Worker B 需要知道）

## 4. 计划引擎

### 一句话说明

计划引擎是 jcode 的战略规划部。在执行任何实际操作之前，它先分析任务、制定多步骤计划、评估风险，确保不是拍脑袋就干。

### 业务价值

| 维度 | 说明 |
|------|------|
| **减少返工** | 先想清楚再动手，比边做边改少走弯路 |
| **可预测性** | 用户能看到完整计划，心里有数 |
| **风险控制** | 提前识别高风险步骤，制定回滚方案 |
| **成本控制** | 避免无效的模型调用，节省 Token 消耗 |

### 使用场景

1. **复杂需求**：把支付模块从 Stripe 换成支付宝，计划引擎分析影响范围，列出所有需要修改的文件
2. **多步骤任务**：升级项目依赖，修复兼容性问题，更新 CI 配置，拆成 3 个阶段，每个阶段有明确的验收标准
3. **风险任务**：重构核心数据库层，识别高风险点，制定回滚计划
4. **探索性任务**：分析这个项目为什么编译慢，先计划分析步骤，再执行

### 关键流程

```
用户输入复杂需求
        |
        v
+--------------------------------+
|  1. 需求理解                    |
|  - 提取关键意图                 |
|  - 识别约束条件                 |
|  - 确定成功标准                 |
+----------------+---------------+
                 |
                 v
+--------------------------------+
|  2. 上下文收集                  |
|  - 读取项目结构                 |
|  - 分析依赖关系                 |
|  - 搜索相关代码                 |
|  - 查阅历史类似任务             |
+----------------+---------------+
                 |
                 v
+--------------------------------+
|  3. 计划生成                    |
|  - 拆解为步骤序列               |
|  - 标注每步依赖                 |
|  - 估算每步复杂度               |
|  - 制定回滚/容错策略            |
+----------------+---------------+
                 |
                 v
+--------------------------------+
|  4. 计划审核                    |
|  - 展示计划给用户               |
|  - 用户确认/修改/拒绝           |
|  - 记录审核结果                 |
+----------------+---------------+
                 |
                 v
+--------------------------------+
|  5. 计划执行                    |
|  - 按步骤执行                   |
|  - 每步完成后验证               |
|  - 异常时触发回滚               |
+--------------------------------+
```

### 核心设计

#### 分层计划结构

jcode 的计划不是扁平的步骤列表，而是分层结构：

```
任务：迁移支付模块
+-- 阶段 1：分析现状
|   +-- 步骤 1.1：列出所有 Stripe 相关代码
|   +-- 步骤 1.2：分析调用链路
|   +-- 步骤 1.3：生成影响范围报告
+-- 阶段 2：实现新接口
|   +-- 步骤 2.1：定义支付宝接口抽象
|   +-- 步骤 2.2：实现支付宝适配器
|   +-- 步骤 2.3：编写单元测试
+-- 阶段 3：替换调用
|   +-- 步骤 3.1：逐个替换调用点
|   +-- 步骤 3.2：更新配置文件
+-- 阶段 4：清理与验证
    +-- 步骤 4.1：移除 Stripe 依赖
    +-- 步骤 4.2：跑集成测试
    +-- 步骤 4.3：更新文档
```

每个步骤都有：
- **前置条件**：前面哪些步骤必须完成
- **验收标准**：怎么判断这一步做完了、做对了
- **回滚方案**：如果这一步失败，怎么恢复
- **预估耗时**：大模型估算的 Token 消耗和代码量

#### 动态调整

计划不是一成不变的。执行过程中，如果发现新情况，计划引擎会动态调整：

- 步骤 2.2 发现 SDK 需要额外配置 -> 在步骤 2.2 和 2.3 之间插入一个新步骤
- 步骤 3.1 发现某个调用点比预期复杂 -> 把该步骤拆成两个子步骤
- 步骤 4.1 发现还有未分析的引用 -> 回退到阶段 1，重新分析

#### 计划模板

对于常见任务类型，jcode 内置了计划模板：

- **代码迁移**：分析 -> 实现 -> 替换 -> 清理
- **Bug 修复**：复现 -> 定位 -> 修复 -> 测试 -> 回归
- **功能开发**：设计 -> 实现 -> 测试 -> 文档
- **性能优化**：测量 -> 分析瓶颈 -> 优化 -> 再测量

模板让计划生成更快、更稳定，同时也允许用户自定义模板。

## 5. 多 Provider 体系

### 一句话说明

多 Provider 体系是 jcode 的模型路由器。它让 jcode 能同时对接 8+ 个大模型服务商（OpenAI、Anthropic、DeepSeek、MiniMax 等），根据不同任务自动选择最合适的模型，也能在某个服务商宕机时自动切换。

### 业务价值

| 维度 | 说明 |
|------|------|
| **不绑定厂商** | 不会被某个服务商绑架，随时切换 |
| **成本优化** | 简单任务用便宜模型，复杂任务用强模型，省 Token 费 |
| **高可用** | 主模型挂了自动切备用模型，任务不中断 |
| **合规灵活** | 不同地区用不同模型，满足数据合规要求 |

### 使用场景

1. **成本敏感**：日常代码补全用 DeepSeek（便宜），复杂重构用 Claude（强）
2. **高可用需求**：线上 CI 不能停，主模型超时自动切备用
3. **多模型对比**：同一个问题发给 3 个模型，对比答案质量
4. **区域合规**：中国区数据用国产模型，海外数据用 OpenAI

### 支持的 Provider（8+）

```
+-----------------------------------------------------------+
|                    Provider 抽象层                         |
|         统一的接口：chat() / stream() / embed()            |
+---------+---------+----------+----------+-----------------+
| OpenAI  |Anthropic| DeepSeek | MiniMax  |  通义千问        |
| GPT-4o  | Claude  | V3/R1    |  ABAB    |  Qwen-Max       |
+---------+---------+----------+----------+-----------------+
| 智谱    | 月之暗面 | 百川     | 本地模型  |  更多...        |
| GLM-4   | Kimi    | Baichuan | Ollama   |  可扩展         |
+---------+---------+----------+----------+-----------------+
```

### 核心设计

#### 统一抽象层

所有 Provider 实现同一个 trait（接口），对外暴露三个核心方法：

```rust
// 伪代码示意
trait Provider {
    // 对话：发消息，拿回复
    async fn chat(&self, messages: Vec<Message>) -> Response;
    
    // 流式对话：一个字一个字往外蹦（打字机效果）
    async fn stream(&self, messages: Vec<Message>) -> Stream<Response>;
    
    // 嵌入：把文本转成向量（用于搜索和记忆）
    async fn embed(&self, texts: Vec<String>) -> Vec<Vec<f32>>;
}
```

这个抽象层的设计哲学是：**上层代码不关心用的是哪个模型**。Agent 运行时只调用 `provider.chat(messages)`，至于背后是 OpenAI 还是 DeepSeek，由配置决定。

#### 智能路由

jcode 不是简单地用户选哪个就用哪个，而是有一个智能路由层：

```
任务请求 -> 路由器分析
                |
      +---------+---------+
      v         v         v
    成本      能力      可用性
    检查      匹配      检查
      |         |         |
      +---------+---------+
                v
           选择最优 Provider
```

路由决策考虑的因素：

1. **任务类型**：代码生成 -> 强模型；代码补全 -> 快模型；嵌入 -> 专用模型
2. **成本预算**：用户设置了月度预算，优先用便宜模型
3. **延迟要求**：交互式场景要求 2 秒内响应，后台任务可以等
4. **可用性**：主模型 5 秒没响应，自动切备用
5. **历史成功率**：某类任务在某个模型上成功率更高，优先选择

#### 故障转移

```
用户请求
    |
    v
Provider A (首选) --超时--> Provider B (备用) --也挂了--> Provider C (兜底)
    |                          |                          |
    成功                       成功                       成功/失败
```

故障转移是自动的，对用户透明。用户不会看到模型调用失败的错误，而是在日志里看到已从 Provider A 切换到 Provider B。

#### 成本追踪

每个 Provider 调用都会记录 Token 消耗和费用。用户可以：

- 按项目、按任务、按日期查看费用明细
- 设置每日/每月预算上限
- 对比不同模型在同类任务上的性价比

## 6. 记忆系统

### 一句话说明

记忆系统是 jcode 的长期记忆。它让 jcode 记住你项目的编码规范、你的个人偏好、之前解决过的问题，这样下次遇到类似情况时不用从头教它。

### 业务价值

| 维度 | 说明 |
|------|------|
| **个性化** | 记住你的编码风格、命名习惯、项目约定 |
| **效率** | 类似问题不用重复分析，直接调取历史经验 |
| **一致性** | 确保所有代码修改风格统一 |
| **知识积累** | 项目越用越聪明，经验不断沉淀 |

### 使用场景

1. **编码规范记忆**：我们项目用 camelCase 命名，不用 snake_case -> 之后所有代码生成都遵循这个规范
2. **项目结构记忆**：数据库层在 src/db/，API 层在 src/api/ -> 新代码自动放到正确位置
3. **问题经验记忆**：上次 N+1 查询问题是因为没加 .includes() -> 下次自动检查
4. **用户偏好记忆**：我更喜欢先写测试再写实现 -> 自动调整工作流

### 记忆层次结构

```
+--------------------------------------------+
|              工作记忆                       |
|         (Working Memory)                   |
|   当前会话的上下文，会话结束即清空           |
|   容量：当前对话 + 最近工具调用             |
+--------------------------------------------+
|              短期记忆                       |
|         (Short-term Memory)                |
|   最近几次会话的关键信息                    |
|   容量：最近 10 次会话的摘要                |
+--------------------------------------------+
|              长期记忆                       |
|         (Long-term Memory)                 |
|   持久化的项目知识和用户偏好                 |
|   容量：不限，但需要检索                     |
+--------------------------------------------+
|              共享记忆                       |
|         (Shared Memory)                    |
|   团队成员共享的项目规范和经验               |
|   容量：团队级别的知识库                     |
+--------------------------------------------+
```

### 核心设计

#### 自动记忆提取

jcode 不会让用户手动教它。而是在每次会话结束后，自动从对话中提取有价值的信息：

```
会话结束 -> 分析对话内容
                |
                v
           提取关键信息
           - 编码规范：用户提到用 4 空格缩进
           - 项目约定：修改了 .eslintrc，说明项目用 ESLint
           - 踩坑经验：花 3 轮修复了某个依赖冲突
                |
                v
           存入记忆库（带标签和向量）
```

#### 向量检索

记忆不是简单的关键词匹配，而是基于向量相似度的语义检索。当你问怎么处理数据库连接时，即使记忆里没有精确匹配数据库连接这几个字，也能找到数据库连接池配置、数据库超时设置等相关记忆。

具体实现见第 9 节：向量嵌入。

#### 记忆优先级

不是所有记忆都一样重要。jcode 给记忆打分：

- **频率**：被引用越多次，分数越高
- **时效**：最近的信息比很久以前的更重要
- **相关性**：和当前任务越相关的分数越高
- **来源**：用户明确说的 > 自动推断的

#### 遗忘机制

记忆系统不是只增不减。它也有遗忘机制：

- 长期未被引用的记忆会被降权
- 相互矛盾的记忆会触发澄清（比如你之前说用 2 空格缩进，但现在项目配置是 4 空格，我该按哪个？）
- 过时的信息（如当前 Node 版本是 16 -> 实际已升级到 20）会被标记为过期

## 7. TUI 终端界面

### 一句话说明

TUI（Terminal User Interface，终端用户界面）是 jcode 的仪表盘。在终端里画出一个漂亮的交互界面，让你实时看到 Agent 在做什么、进度如何、当前在调用哪个工具、消耗了多少 Token。

### 业务价值

| 维度 | 说明 |
|------|------|
| **直观** | 不用读日志文件，一眼看到任务状态 |
| **实时** | 打字机效果展示模型输出，像在看 AI 思考 |
| **可操作** | 在界面里暂停、恢复、取消任务 |
| **轻量** | 不需要浏览器，SSH 远程也能用 |

### 使用场景

1. **日常开发**：在终端里开着 jcode TUI，像多了个副屏监控
2. **远程服务器**：SSH 到服务器，用 TUI 管理 jcode 任务
3. **演示/教学**：给团队演示 jcode 怎么工作的，TUI 比日志直观
4. **长时间任务**：跑一个 30 分钟的重构，TUI 显示实时进度条

### 界面布局

TUI 界面分为几个区域：

- **顶部状态栏**：显示版本号、当前会话 ID、使用的 Provider 和 Token 消耗量
- **任务计划面板**：显示当前任务的步骤列表，每步有状态标记（已完成/进行中/待处理）
- **实时状态面板**：当前步骤序号、进度百分比、耗时、Token 消耗
- **对话窗口**：Agent 和用户的对话历史，包含工具调用和结果
- **底部快捷键栏**：显示可用的键盘操作

### 核心设计

#### 声明式渲染

TUI 采用声明式渲染：每个组件（面板、进度条、对话窗口）声明自己的状态，框架负责把状态渲染成终端字符。这类似于 React 的 UI = f(state) 思想，但在终端里实现。

好处是：状态变化时只需更新对应组件，不用整屏重绘，避免了闪烁。

#### 事件驱动更新

TUI 订阅 Agent 运行时的事件总线（见第 2 节），当事件发生时自动更新界面：

- 工具调用开始 -> 对话窗口显示工具名称
- 模型返回 -> 对话窗口显示打字机效果
- 步骤完成 -> 计划面板打勾
- Token 消耗 -> 状态栏更新数字

#### 键盘快捷键

所有操作都有键盘快捷键，不需要鼠标：

| 按键 | 功能 |
|------|------|
| P | 暂停当前任务 |
| R | 恢复暂停的任务 |
| C | 取消当前任务 |
| D | 查看详情（日志、Token 明细） |
| H | 帮助面板 |
| Q | 退出（任务在后台继续） |
| Tab | 切换面板焦点 |
| 上下箭头 | 滚动对话窗口 |

#### 自适应布局

TUI 根据终端窗口大小自动调整布局：

- 宽终端（大于 120 列）：双栏布局，计划 + 对话并排
- 窄终端（80-120 列）：单栏布局，面板上下排列
- 极窄终端（小于 80 列）：极简模式，只显示对话窗口

## 8. 上下文压缩

### 一句话说明

上下文压缩是 jcode 的笔记整理术。当对话越来越长、Token 快用完时，自动把历史对话压缩成精炼的摘要，保留关键信息，丢掉废话，让大模型始终有足够的上下文空间继续工作。

### 业务价值

| 维度 | 说明 |
|------|------|
| **突破 Token 限制** | 理论上可以处理无限长的任务，不受模型上下文窗口限制 |
| **降低成本** | 压缩后的上下文更短，每次调用消耗更少 Token |
| **提升质量** | 去掉噪声信息，模型聚焦在关键内容上 |
| **长任务支持** | 一个任务跑几个小时、几千轮对话，不会因为上下文溢出而崩溃 |

### 为什么需要上下文压缩？

大模型有一个上下文窗口的概念——它只能记住最近的 N 个 Token。比如 Claude 3.5 Sonnet 的上下文窗口是 200K Token，听起来很多，但在实际编码任务中：

- 一个文件可能有 1000 行，大约 3000 Token
- 读 10 个文件，大约 30000 Token
- 跑 20 轮对话（每轮含工具调用结果），大约 80000 Token
- 跑 50 轮，上下文就满了！

如果不压缩，Agent 要么忘记最早的信息（比如用户最初的需求），要么直接报错。上下文压缩解决了这个问题。

### 关键流程

```
对话历史（原始）
+----------------------------------------+
| 轮次 1: 用户说修复登录 bug             |
| 轮次 2: Agent 读了 5 个文件            |  <- 5000 Token
| 轮次 3: Agent 分析了代码结构           |
| ...                                    |
| 轮次 50: Agent 在修第 10 个文件        |  <- 180000 Token，快满了！
+----------------------------------------+
                |
                v 触发压缩
+----------------------------------------+
| 压缩结果                                |
|                                        |
| 任务目标: 修复登录页面 JWT 过期 bug     |
| 关键发现:                               |
| - 问题在 src/auth/login.ts:42           |
| - expiresIn 写成了 1000ms               |
| - 已修改文件: login.ts, auth.ts, ...    |
| - 待处理: 测试验证                      |
| 当前状态: 第 3 步/共 4 步               |
|                                        |  <- 压缩后只有 2000 Token
+----------------------------------------+
```

### 核心设计

#### 分层压缩策略

jcode 不是把所有内容一股脑压缩，而是分层处理：

1. **冗余去重**：同一段代码被反复读取？只保留第一次的完整内容，后续用引用替代
2. **工具输出摘要**：read_file 返回了 500 行代码，但 Agent 只改了 3 行 -> 只保留这 3 行和上下文
3. **对话摘要**：把 10 轮试错对话压缩成经过 10 轮调试，最终确定问题在 X
4. **结构化保留**：任务目标、当前进度、已修改文件列表 -> 这些必须保留，不能丢

#### 压缩触发时机

压缩不是满了再压，而是提前触发：

- **75% 阈值**：上下文使用率达到 75%，触发轻度压缩（去重、工具输出摘要）
- **90% 阈值**：触发深度压缩（对话摘要、冗余清理）
- **95% 阈值**：触发激进压缩（只保留核心任务信息）

#### 压缩质量保证

压缩后的摘要必须满足：

- **任务目标不丢失**：用户最初的需求必须保留
- **进度不丢失**：做到了哪一步、下一步是什么必须清楚
- **关键决策不丢失**：为什么选方案 A 不选方案 B 必须保留
- **可逆性**：如果压缩丢失了重要信息导致 Agent 出错，支持解压缩回退

#### 增量压缩

不是每次都重新压缩全部历史。而是：

- 维护一个压缩基准（已压缩的历史摘要）
- 新的对话追加到基准后面
- 当总长度再次超过阈值，只压缩新增部分，合并到基准

这样避免了重复压缩的开销，也让压缩更稳定。

## 9. 向量嵌入 / ONNX

### 一句话说明

向量嵌入是 jcode 的语义搜索引擎。它能把任何文本（代码、文档、对话）转换成一串数字（向量），然后通过数学计算找到语义上最相似的内容，支撑记忆检索、代码搜索、上下文匹配等功能。

### 用大白话解释向量嵌入

想象你有一个图书馆，里面有 10000 本书。你想找关于数据库连接池的书。

- **传统搜索**：只能匹配书名里包含数据库、连接池这些词的书。如果有一本书叫《MySQL 性能优化》，内容完全相关但书名没这些词，就搜不到。
- **向量搜索**：每本书都被转换成一个 768 维的坐标。语义相近的书，坐标也相近。《数据库连接池实战》和《MySQL 性能优化》的坐标非常接近，一搜就能找到。

### 业务价值

| 维度 | 说明 |
|------|------|
| **语义理解** | 搜怎么让程序跑更快能找到性能优化相关代码，即使没出现快字 |
| **离线运行** | 用 ONNX 本地推理，不需要联网调 API |
| **零成本** | 本地计算，不消耗 API Token |
| **隐私安全** | 代码不出本地，不需要上传到云端 |

### 为什么用 ONNX？

ONNX（Open Neural Network Exchange）是一个开放的神经网络模型格式。用 ONNX 的好处：

- **跨平台**：同一个模型文件在 macOS、Linux、Windows 上都能跑
- **高性能**：底层用 C++ 实现，比 Python 快 10-100 倍
- **无依赖**：不需要安装 PyTorch、TensorFlow，Rust 直接加载 ONNX 模型
- **模型可选**：可以换不同的嵌入模型（BGE、E5、GTE 等），不需要改代码

### 关键流程

```
文本输入：修复数据库连接超时的问题
        |
        v
+------------------------+
|  1. 分词 (Tokenize)     |  把文本拆成词元
|  修复, 数据库,           |
|  连接, 超时,            |
|  的, 问题               |
+------------+-----------+
             |
             v
+------------------------+
|  2. ONNX 推理           |  加载嵌入模型，前向传播
|  模型: BGE-small-zh     |
|  输入: 词元序列         |
|  输出: 768维向量        |
+------------+-----------+
             |
             v
+------------------------+
|  3. 向量归一化          |  标准化向量，方便计算相似度
|  0.023, -0.15,         |
|  0.087, ..., 0.042     |
+------------+-----------+
             |
             v
+------------------------+
|  4. 存入向量索引        |  加入向量数据库
|  (Faiss / Annoy)       |
+------------------------+
```

### 核心设计

#### 嵌入模型选择

jcode 支持多种嵌入模型，用户可以根据场景选择：

| 模型 | 维度 | 优势 | 适用场景 |
|------|------|------|----------|
| BGE-small-zh | 512 | 中文效果好，体积小 | 中文项目 |
| BGE-large-en | 1024 | 英文效果好，精度高 | 英文项目 |
| E5-base-v2 | 768 | 通用性好 | 混合项目 |
| GTE-small | 384 | 速度最快 | 实时搜索 |
| CodeBERT | 768 | 代码专用 | 代码搜索 |

#### 混合检索

只用向量搜索不够，jcode 采用混合检索策略：

搜索结果 = 向量搜索(语义相似) x 0.7 + 关键词搜索(BM25) x 0.3

- 向量搜索负责语义理解：搜登录能找到 sign in
- 关键词搜索负责精确匹配：搜 JWT_SECRET 必须精确匹配

两者互补，召回率更高。

#### 增量索引

代码仓库可能有上万个文件，全部嵌入一遍很慢。jcode 采用增量索引：

- 首次索引：全量嵌入所有文件
- 后续更新：只嵌入修改过的文件
- Git 感知：通过 git diff 精确定位变更文件

#### 应用场景

向量嵌入在 jcode 中支撑了多个功能：

| 功能 | 说明 |
|------|------|
| 记忆检索 | 从长期记忆中搜索相关经验 |
| 代码搜索 | 找项目中所有处理 JWT 的地方 |
| 上下文选择 | 从大仓库中筛选最相关的文件放入上下文 |
| 相似问题推荐 | 这个报错之前遇到过，解决方案是... |
| 代码克隆检测 | 识别重复代码，建议抽取公共函数 |

## 10. 桌面应用

### 一句话说明

桌面应用是 jcode 的图形化外壳。用 Tauri 框架构建的跨平台桌面应用，让不习惯命令行的用户也能用上 jcode 的全部能力，提供项目面板、可视化配置、一键操作等体验。

### 业务价值

| 维度 | 说明 |
|------|------|
| **降低门槛** | 不需要学命令行，打开 App 就能用 |
| **可视化** | 项目结构树、任务进度图、Token 消耗图表 |
| **配置管理** | 图形化配置 Provider、API Key、模型参数 |
| **跨平台** | macOS / Windows / Linux 统一体验 |

### 使用场景

1. **新手入门**：第一次用 jcode，桌面 App 引导你配置、选择项目、发出第一个指令
2. **项目管理**：同时管理多个项目，切换方便
3. **团队协作**：可视化查看团队共享记忆、编码规范
4. **监控面板**：实时查看 Token 消耗、任务成功率、模型调用延迟

### 核心设计

#### Tauri 架构

桌面应用基于 Tauri 框架，架构如下：

```
+----------------------------------+
|         前端 (WebView)            |
|     React / Vue / Svelte         |
|     负责 UI 渲染和交互            |
+----------------------------------+
|        Tauri Bridge (IPC)        |
|     前后端通信桥梁                |
+----------------------------------+
|        Rust 后端                  |
|     调用 jcode 核心库             |
|     文件系统、进程管理、配置       |
+----------------------------------+
```

为什么选 Tauri 而不是 Electron？

| 对比 | Tauri | Electron |
|------|-------|----------|
| 安装包大小 | 约 10MB | 约 150MB |
| 内存占用 | 约 50MB | 约 200MB |
| 启动速度 | 小于 1 秒 | 3-5 秒 |
| 前端框架 | 任意 | 任意 |
| 后端语言 | Rust | Node.js |

jcode 核心本身就是 Rust 写的，用 Tauri 可以直接复用核心代码，不需要 Node.js 中间层。

#### 功能模块

桌面应用提供以下功能模块：

1. **项目面板**：项目列表、最近打开、项目结构树
2. **任务面板**：当前任务状态、历史任务列表、任务详情
3. **对话窗口**：和 Agent 的对话界面，支持 Markdown 渲染
4. **配置面板**：Provider 配置、模型选择、API Key 管理
5. **记忆面板**：查看和管理长期记忆
6. **监控面板**：Token 消耗、响应延迟、成功率图表
7. **设置面板**：主题、语言、快捷键、自动更新

#### 与 CLI 的关系

桌面应用和命令行版本共享同一套核心代码，功能完全对等：

- CLI 有的功能，桌面应用都有（反过来不一定）
- 桌面应用是 CLI 的超集，提供更多可视化功能
- 配置和记忆在 CLI 和桌面应用之间同步

## 11. 工具系统

### 一句话说明

工具系统是 jcode 的工具箱。Agent 不是只能想，还能做：读文件、写代码、跑命令、搜代码、查文档、管理 Git……30+ 个工具让 Agent 能真正操作你的代码仓库。

### 业务价值

| 维度 | 说明 |
|------|------|
| **能力边界** | Agent 能做什么，完全取决于工具有多少 |
| **安全性** | 每个工具都有权限控制，危险操作需确认 |
| **可扩展** | 用户可以自定义工具，满足特殊需求 |

### 核心设计

#### 工具注册机制

新增工具非常简单：实现一个 trait，注册到工具注册表即可。

```rust
// 伪代码示意
trait Tool {
    fn name(&self) -> &str;           // 工具名称
    fn description(&self) -> &str;    // 工具描述（给大模型看的）
    fn parameters(&self) -> Schema;   // 参数定义（JSON Schema）
    async fn execute(&self, params: Value) -> Result<Value>;  // 执行逻辑
}
```

这个设计的好处：

- **大模型自动理解**：description 和 parameters 会被注入到 Prompt 中，大模型自己决定什么时候调用哪个工具
- **类型安全**：参数定义用 JSON Schema，调用时自动校验
- **易于扩展**：第三方可以写自己的工具插件

#### 权限分级

不是所有工具都能随便调用。jcode 有三级权限：

| 级别 | 权限 | 示例工具 |
|------|------|----------|
| **只读** | 只能读，不能改 | read_file、grep_search、git_log |
| **写入** | 可以修改文件 | write_file、edit_file、git_commit |
| **危险** | 可能造成破坏性后果 | exec_command（rm -rf）、git_push --force |

- 只读工具：Agent 可以自由调用
- 写入工具：首次使用时弹窗确认，可勾选本次会话不再询问
- 危险工具：每次调用都需要用户确认

#### 工具调用格式

大模型返回的不是自然语言，而是结构化的工具调用指令：

```json
{
  "tool": "read_file",
  "params": {
    "path": "src/auth/login.ts",
    "offset": 40,
    "limit": 10
  }
}
```

Agent 运行时解析这个指令，调用真正的工具函数，把结果返回给大模型。大模型看到结果后，决定下一步做什么。

#### 工具组合

单个工具的能力有限，但组合起来就很强大。例如：

```
'修复这个 bug' ->
  1. grep_search('JWT')      -> 找到相关文件
  2. read_file('login.ts')   -> 理解代码
  3. git_log('login.ts')     -> 看谁改的、什么时候改的
  4. edit_file('login.ts')   -> 修改代码
  5. exec_command('npm test')-> 跑测试验证
  6. git_diff()              -> 查看变更
  7. git_commit('fix: ...')  -> 提交
```

```
|   |
+-- 14. 记忆更新 (jcode-memory-types)
|   |  自动提取关键信息:
|   |    - user_auth.rs 的 login 函数已重构
|   |    - 添加了 bcrypt 哈希和 anyhow 错误处理
|   |    - 用户偏好先看分析再改代码
|   |  写入 L2 和 L3 记忆库
|   |
+-- 15. 上下文压缩检查 (jcode-compaction-core)
|   |  检查对话长度是否超过阈值
|   |  如果过长 -> 触发压缩 -> 总结早期对话
|   |
+-- 16. 会话状态保存 (jcode-session-types)
    保存到 SQLite 数据库
    等待用户下一条消息
```

### 白话解读

这个过程就像一个有经验的开发者带着一个外脑在工作：

1. **先回忆**（记忆检索）：我上次处理这个模块时是怎么做的？用户有什么偏好？
2. **先看清楚**（第 1 轮 LLM + read_file）：先读文件，理解现状
3. **分析问题**（第 2 轮 LLM）：找到代码的问题所在
4. **动手改**（write_file）：写出新的代码
5. **验证**（execute_code）：跑测试确保没问题
6. **汇报**（最终回复）：告诉用户改了什么
7. **存档**（记忆更新）：记住这次的经验，下次不用重新学

整个过程，Agent 不是一次性回答，而是反复思考、验证、迭代，直到确认任务完成。这就是 Agent 循环（Agent Loop）的核心价值。

## 流程二：Swarm 多 Agent 协作

这是 jcode 区别于所有竞品的杀手级功能。当任务复杂到无法单人完成时，Swarm 模式启动多个 Agent 并行工作。

### 涉及模块

| 模块 | 角色 |
|------|------|
| jcode-plan | 计划引擎，拆解任务 |
| jcode-swarm-core | Swarm 协调器，管理 Agent 群 |
| jcode-agent-runtime | 每个子 Agent 的运行实例 |
| jcode-session-types | 每个 Agent 的独立会话 |
| jcode-tool-core | 工具执行，含文件冲突检测 |
| jcode-provider-* | 每个 Agent 可配不同 Provider |
| jcode-compaction-core | 每个 Agent 独立的上下文压缩 |

### 涉及数据

| 数据实体 | 说明 |
|----------|------|
| Plan | 任务分解计划，含步骤和依赖关系 |
| SubAgent | 每个子 Agent 的会话和状态 |
| Message | Agent 间通信消息 |
| FileLock | 文件占用锁，防止同时修改 |

### 白话解读

Swarm 模式就像一个项目经理带着三个开发人员：

1. **项目经理**（计划引擎 + Swarm 协调器）：分析任务规模，分配给不同的人
2. **开发 A**（Agent A）：负责核心模块，独立工作
3. **开发 B**（Agent B）：负责工具模块，独立工作
4. **开发 C**（Agent C）：负责辅助模块，独立工作

关键设计是冲突检测和 Agent 间通信。三个开发人员各自在自己的工位上干活，但如果 A 想改一个 B 正在看的文件，系统会自动通知双方，避免冲突。这比传统 AI 工具一个 AI 串行干所有事的效率高得多。

### Swarm 适用的场景

- 代码重构：一个 Agent 改逻辑，一个 Agent 写测试，一个 Agent 更新文档
- 多仓库操作：前端和后端 Agent 同时修改，自动协调 API 接口
- Code Review：一个 Agent 审查代码，一个 Agent 写修复建议，一个 Agent 执行修复
- 知识迁移：一个 Agent 分析旧代码，一个 Agent 写新代码，一个 Agent 做对比验证

## 流程三：记忆与学习系统

jcode 的记忆系统不是简单的保存对话记录，而是模仿人脑的关联记忆——它会自动提取关键信息、建立关联、在需要时精准检索。

### 涉及模块

| 模块 | 角色 |
|------|------|
| jcode-memory-types | 记忆数据结构定义，三级存储 |
| jcode-embedding | 文本向量化，语义搜索 |
| jcode-compaction-core | 记忆整理，去重合并 |
| jcode-agent-runtime | 记忆注入 Prompt |
| jcode-session-types | 会话级别的记忆关联 |

### 涉及数据

| 数据实体 | 说明 |
|----------|------|
| Memory (L1) | 原始事件流，当前会话的完整记录 |
| Memory (L2) | 会话摘要，压缩后的关键信息 |
| Memory (L3) | 长期偏好，跨会话的向量化知识 |
| Embedding | 向量，用于语义搜索 |
| MemoryGraph | 记忆图谱，记忆之间的关联边 |

### 白话解读

jcode 的记忆系统就像一个有超强记忆力的助手：

- **自动记笔记**（记忆生成）：每次对话结束，自动提取关键信息存入笔记本
- **智能索引**（向量化）：不是按日期翻笔记，而是按意思搜索——你说 logout，它能找到登录相关的笔记
- **联想记忆**（记忆图谱）：找到一个记忆点后，自动联想到相关的其他记忆——像人脑的哦对了，还有这个
- **定期整理**（记忆整理）：定期清理重复的、过时的笔记，保持笔记本整洁

### 记忆系统的产品价值

对用户来说，这意味着：
- 不需要每次对话都重新介绍项目背景
- 不需要重复说明自己的偏好
- 跨项目积累经验——在项目 A 学到的，在项目 B 也能用
- 团队协作场景下，每个成员的偏好都可以被记忆

## 流程四：Provider 切换与容灾

jcode 支持 8 种以上的 AI 模型提供商，并且可以在同一会话中无缝切换。更关键的是，它有完整的容灾机制——当一个 Provider 不可用时，自动降级到备用 Provider。

### 涉及模块

| 模块 | 角色 |
|------|------|
| jcode-config-types | 读取 Provider 配置 |
| jcode-provider-core | Provider 抽象层，统一接口 |
| jcode-provider-metadata | Provider 元数据管理 |
| jcode-provider-doctor | Provider 健康检查 |
| jcode-provider-anthropic | Anthropic (Claude) 适配器 |
| jcode-provider-openai | OpenAI (GPT) 适配器 |
| jcode-provider-gemini | Google Gemini 适配器 |
| jcode-provider-copilot | GitHub Copilot 适配器 |
| jcode-provider-openrouter | OpenRouter 适配器 |
| jcode-provider-bedrock | AWS Bedrock 适配器 |
| jcode-auth-types | 认证管理 |
| jcode-agent-runtime | Agent 运行时，使用 Provider |

### 涉及数据

| 数据实体 | 说明 |
|----------|------|
| Provider | Provider 配置，含 API Key、模型列表 |
| ModelConfig | 模型配置，含温度、最大 Token 等 |
| AuthToken | OAuth Token 或 API Key |
| HealthStatus | Provider 健康状态 |

```
|   |  当前 Provider: Anthropic Claude
|   |  备用 Provider 列表 (按优先级):
|   |    1. OpenAI GPT-4o (同级别的替代)
|   |    2. Gemini 2.5 Pro (功能类似)
|   |    3. OpenRouter (可访问多个模型)
|   |
|   |  决策逻辑:
|   |    -> 如果当前任务需要代码理解能力 -> 优先选 OpenAI
|   |    -> 如果当前任务需要长上下文 -> 优先选 Gemini (1M 上下文)
|   |    -> 如果是一般任务 -> 按优先级顺序尝试
|   |
+-- 10. 切换执行
|   |  自动切换到 OpenAI GPT-4o
|   |  重新构建 Prompt (适配 OpenAI 格式)
|   |  从断点继续: 工具调用结果不丢失
|   |
+-- 11. 用户通知
|   |  在 TUI 中显示提示:
|   |    !! Anthropic 暂时不可用 (503)
|   |    OK 已自动切换到 OpenAI GPT-4o
|   |    ## 本次切换耗时: 0.8 秒
|   |
+-- 12. 恢复检测
    |  定期检查 Anthropic 是否恢复
    |  恢复后: 下次调用可选切回 (不强制，避免频繁切换)
```

### 白话解读

Provider 切换就像手机的双卡双待：

- **手动切换**：用户想换模型，改一行配置就行，不需要重启，对话历史不丢失
- **自动容灾**：一个模型挂了，jcode 自动切换到另一个，用户几乎无感知
- **智能选择**：不是随便切，而是根据当前任务的特点选择最合适的备用模型

### Provider 切换的产品价值

- 不锁定厂商：用户可以随时更换 AI 提供商
- 成本优化：普通任务用便宜模型，复杂任务用贵模型
- 高可用：一个模型挂了不影响工作
- 灵活的实验：用户可以对比不同模型的效果

## 流程六：上下文压缩

当对话太长时，AI 的上下文窗口会满，导致忘记前面的内容。上下文压缩自动解决这个问题。

### 涉及模块

| 模块 | 角色 |
|------|------|
| jcode-compaction-core | 压缩引擎，触发和执行压缩 |
| jcode-agent-runtime | 压缩后的上下文注入 |
| jcode-memory-types | 压缩结果存入 L2 记忆 |

### 端到端流程图

```
对话进行中，消息数量不断增长...
|
+-- 1. 触发检查 (jcode-compaction-core)
|   |  每次对话后检查:
|   |    Token 使用量 / 模型上下文上限 = 使用率
|   |
|   |  阈值设定:
|   |    使用率 < 60%: 无需压缩
|   |    使用率 60-80%: 轻度压缩 (压缩工具调用结果)
|   |    使用率 80-95%: 中度压缩 (压缩早期对话轮次)
|   |    使用率 > 95%: 深度压缩 (压缩所有非关键信息)
|   |
|   |  当前: 使用率 82% -> 触发中度压缩
|   |
+-- 2. 分层压缩策略
|   |
|   |  第 1 层: 压缩工具调用结果 (最不重要的先压)
|   |    原始: read_file 返回了 500 行代码
|   |    压缩后: 该文件包含 user_auth 模块，主要函数有 login/logout 等
|   |
|   |  第 2 层: 压缩对话轮次
|   |    原始: 3 轮失败的尝试 + 1 轮成功的修改
|   |    压缩后: 经过 3 次尝试后，最终通过修改数据库连接池配置解决了问题
|   |
|   |  第 3 层: 压缩用户消息 (最重要的最后压)
|   |    原始: 详细的 200 字需求描述
|   |    压缩后: 保留核心需求: 重构 user_auth，添加密码哈希和错误处理
|   |
+-- 3. 压缩执行
|   |  调用 LLM (使用轻量模型，节省成本):
|   |    请将以下对话压缩为结构化摘要，保留:
|   |     - 关键决策和原因
|   |     - 最终采用的方案
|   |     - 重要的错误及解决方案
|   |     - 用户的明确偏好
|   |     丢弃: 冗余的确认、重复的尝试、填充语
|   |
|   |  压缩结果:
|   |    原始: 15,000 token
|   |    压缩后: 800 token
|   |    压缩比: 约 18:1
|   |
+-- 4. 上下文重构
|   |  原始上下文:
|   |    [系统提示] [记忆] [消息1] [消息2] ... [消息50] [当前消息]
|   |
|   |  压缩后上下文:
|   |    [系统提示] [记忆] [压缩摘要] [消息41] ... [消息50] [当前消息]
|   |
|   |  释放空间: 约 12,000 token
|   |  使用率: 从 82% 降到 45%
|   |
+-- 5. 压缩记录保存
    |  压缩摘要存入 L2 记忆
    |  下次对话可以直接检索压缩摘要，无需重复压缩
```

### 白话解读

上下文压缩就像读书时的划重点：

- 一本 500 页的书，你不可能每次都从头读
- 第一次读时，你划出重点，下次只看重点就能回忆起来
- jcode 的上下文压缩就是这个逻辑——把长对话中真正重要的提取出来，丢掉嗯、好的、明白了这些废话

## 总结：jcode 的流程设计哲学

### 设计原则

1. **自动化优先**：记忆提取、上下文压缩、Provider 容灾，全部自动触发，用户无需手动操作
2. **断点续传**：Overnight 任务、Swarm 子任务、上下文压缩，都支持从中间状态恢复
3. **资源隔离**：每个 Agent 独立会话、独立上下文，互相不干扰
4. **优雅降级**：Provider 故障时自动切换，压缩阈值分层触发，工具失败时重试
5. **用户透明**：所有后台操作都有通知，用户可以随时查看、干预

### 与竞品的流程差异

| 流程 | jcode | Claude Code | Cursor | Copilot |
|------|-------|-------------|--------|---------|
| 单次对话 | Agent Loop (多轮迭代) | 单轮问答 | 代码补全 | 行内建议 |
| 多 Agent | Swarm 原生并行 | 不支持 | 不支持 | 不支持 |
| 记忆系统 | 三级自动记忆 | 不支持 | 不支持 | 不支持 |
| 上下文压缩 | 分层智能压缩 | 简单截断 | 不支持 | 不支持 |
| Provider 容灾 | 自动降级切换 | 不支持 | 有限 | 不支持 |
| 后台任务 | Overnight 模式 | 不支持 | 不支持 | 不支持 |
| 会话导入 | 4 种工具 | 不支持 | 不支持 | 不支持 |

### 一句话总结

jcode 的流程设计不是一个 AI 聊天框，而是一个 AI 操作系统——它管理着多个 Agent 的生命周期，自动处理记忆、压缩、容灾、升级，让用户只需要关注我要做什么，而不是怎么让 AI 做。

```
          │ （向量嵌入）  │
          └──────────────┘
```

### 关系速查表

| 关系 | 类型 | 含义 |
|------|------|------|
| 用户 → 会话 | 1 对多 | 一个用户可以有多个会话（不同项目、不同任务） |
| 用户 → 记忆 | 1 对 1 | 每个用户有一套长期记忆（L3） |
| 会话 → 消息 | 1 对多 | 一个会话包含多条对话消息 |
| 会话 → 计划 | 1 对多 | 一个会话可以有多个任务计划 |
| 会话 → 提供商 | 多对 1 | 多个会话可以用同一个 AI 模型提供商 |
| 会话 → 记忆 | 1 对 1 | 每个会话有自己的工作记忆（L1）和摘要（L2） |
| 计划 → 子代理 | 1 对多 | 一个计划可以派出多个子代理并行执行 |
| 子代理 → 工具 | 多对多 | 每个子代理可以调用多个工具 |
| 配置 → 提供商/工具/UI | 1 对多 | 一份配置影响多个组件的运行参数 |
| 会话 → 配置 | 多对 1 | 多个会话可以共享同一份配置 |

### 实体分类

jcode 的实体可以分为三个层次：

**核心层（业务核心）**：Session、Message、Memory、Provider、Tool、Plan、Config

**支撑层（辅助运行）**：Embedding、Auth、Gateway、Build、Telemetry

**高级层（特定功能）**：Batch、Background、Notification、Import、Desktop

本文档重点讲解核心层的 7 个实体，支撑层和高级层在最后做简要说明。

## 核心实体一：Session（会话）

### 一句话概括

**Session 是 jcode 的一等公民。** 如果把 jcode 比作一个操作系统，Session 就是里面的"进程"——每个 Session 是一个独立的运行单元，有自己的上下文、自己的记忆、自己的生命周期。

### 业务含义

Session 代表"一次 AI 编码对话的完整记录"。你打开 jcode，跟 AI 聊了一个小时，让它帮你重构了一个模块、修了三个 Bug、写了五个测试——这整个过程就是一个 Session。

一个 Session 不只是"聊天记录"，它包含：

- 你跟 AI 说了什么（消息列表）
- AI 做了什么（工具调用记录）
- 当时用了哪个模型（Provider 配置）
- 项目文件在哪（工作目录）
- 启用了哪些工具（工具开关）
- 对话进行到哪了（状态、上下文窗口大小）

### 核心字段

| 字段名 | 类型 | 业务含义 | 大白话解释 |
|--------|------|---------|-----------|
| session_id | 唯一标识 | 会话的唯一 ID | 就像身份证号，全局唯一，用来恢复、分享、引用 |
| title | 文本 | 会话标题 | 自动生成（如"重构 user_auth 模块"），也可以手动改 |
| messages | 列表 | 消息历史 | 完整对话记录，从第一句到最新一句 |
| provider | 枚举 | 当前使用的 AI 模型提供商 | 比如 Anthropic、OpenAI、DeepSeek |
| model | 文本 | 当前使用的具体模型 | 比如 claude-sonnet-4-20250514、gpt-4o |
| workspace | 路径 | 工作目录 | 项目代码在磁盘上的位置 |
| context_window | 数值 | 上下文窗口大小（token 数） | 当前 AI 能"看到"多少历史消息 |
| tools_enabled | 列表 | 启用的工具清单 | 这个会话里哪些工具可用 |
| status | 枚举 | 会话状态 | 进行中 / 已暂停 / 已完成 / 已归档 |
| created_at | 时间戳 | 创建时间 | 什么时候开的这个会话 |
| updated_at | 时间戳 | 最后活跃时间 | 最后一次发消息或收到回复的时间 |
| metadata | 键值对 | 扩展元数据 | 放一些自定义标签、备注 |

### 会话状态流转

一个 Session 从生到死，经历以下状态：

```
                    ┌──────────┐
                    │  CREATED │  ← 用户输入第一个问题
                    │  已创建   │
                    └────┬─────┘
                         │
                         ▼
                    ┌──────────┐
            ┌───────│  ACTIVE  │───────┐

            │            │             │
            │  上下文超限  │   用户关闭终端
            │            ▼             │
            │   ┌──────────────┐       │

            │   │  压缩中      │       │
            │   └──────┬───────┘       │

            │   ┌──────────────┐  ┌──────────┐
            │   │  COMPACTED   │  │  PAUSED  │
            │   │  已压缩       │  │  已暂停   │
            │   └──────┬───────┘  └────┬─────┘

            │          │         用户重新打开
            │          │               │
            │          └───────┬───────┘

            │      │ COMPLETED│ │  FAILED  │

            │           │      用户选择重试
            │           │            │
            │           │            ▼
            │           │      ┌──────────┐

            │           │      │  重试中   │
            │           │      └──────────┘
            │           │

            │           │

            │     ┌──────────┐
            │     │ ARCHIVED │
            │     │  已归档   │
            │     └──────────┘
```

### 生命周期详解

**1. 创建（CREATED）**

用户在终端输入 `jcode`，或在一个已有会话中输入第一条消息时，Session 被创建。这时候系统会：
- 分配一个全局唯一的 session_id
- 记录当前工作目录（workspace）
- 加载默认或用户指定的 Provider 和模型
- 自动生成一个标题占位（后续根据第一条消息优化）

**2. 活跃（ACTIVE）**

这是 Session 的主要状态。用户跟 AI 对话、AI 调用工具，所有消息都追加到 messages 列表中。此时：
- 每一条消息都实时写入 SQLite 数据库，不怕断电
- 上下文窗口逐渐被填满
- 用户在 TUI 中看到流式输出

**3. 压缩（COMPACTING → COMPACTED）**

当对话太长，消息的 token 总数接近模型的上下文上限时，jcode 自动触发上下文压缩。压缩的过程是：
- 把早期对话内容喂给 AI，让 AI 生成一个"摘要"
- 用摘要替换原来的详细消息，腾出空间给新消息
- 压缩后的 session 回到 ACTIVE 状态，继续对话

这个机制保证了对话可以"无限长"——理论上可以聊三天三夜，AI 也不会"忘记"重要信息。

**4. 暂停（PAUSED）**

用户关闭终端、电脑休眠、或者显式输入暂停命令时，Session 进入暂停状态。此时：
- 所有消息和状态都已经持久化到 SQLite
- Provider 连接被释放，不再占用网络资源
- 下次用户打开 jcode，自动恢复

**5. 恢复（RESUMED）**

从 PAUSED 状态回到 ACTIVE。恢复时：
- 从 SQLite 加载完整的消息列表
- 重新建立与 Provider 的连接
- 触发记忆检索，注入 L2/L3 记忆
- 用户看到的就是上次离开时的状态

**6. 完成（COMPLETED）**

Agent 完成任务（AI 说"我完成了"，不再需要调用工具），或者用户手动标记完成。完成后：
- 自动触发记忆提取——把本次会话的关键信息写入 L2/L3
- 生成会话摘要
- 可以导出、分享

**7. 失败（FAILED → RETRYING）**

如果 Agent 执行过程中遇到不可恢复的错误（比如网络断了且重试了多次都没恢复），Session 进入 FAILED 状态。用户可以：
- 查看失败原因（日志会详细记录是哪一步出错）
- 选择重试：系统从最近的检查点恢复，继续执行
- 或者放弃，归档

**8. 归档（ARCHIVED）**

长期不活跃的会话（默认 30 天），自动移到归档存储。归档后：
- 消息内容被压缩，只保留摘要
- 不占用活跃会话列表空间
- 随时可以手动恢复

### 会话的"分身"能力

jcode 支持会话分叉（Fork）——从一个会话的某个中间状态，复制出一个新会话，尝试不同的方向。

举个例子：你在 Session A 中让 AI 修复一个 Bug，AI 在第 5 轮给出了两种方案。你选择分叉：
- Session A 继续走方案一
- Session B（分叉出来的）走方案二
- 两个会话互不干扰，各自发展

分叉后，两个会话共享"分叉点"之前的历史消息，但之后的修改各自独立。这让你可以并行尝试多种方案，最后选最好的那个。

## 核心实体二：Message（消息）

### 一句话概括

**Message 是对话的最小原子。** 每一轮交互中，用户说的一句话、AI 回复的一段文字、AI 调用的一次工具、工具返回的结果，都是一条 Message。

### 业务含义

如果把 Session 比作一本书，Message 就是书里的每一页。它记录了对话的完整历史——谁说了什么、什么时候说的、AI 想了什么、调用了什么工具。

Message 不是简单的"文本"，它是一段结构化的数据，包含角色、内容、时间戳、关联关系等。

### 消息类型

jcode 的消息分为四种角色，每种角色的含义和内容格式都不同：

| 角色 | 标识 | 大白话解释 | 谁产生的 | 内容格式 |
|------|------|-----------|---------|---------|
| 用户消息 | user | 你在聊天框里输入的内容 | 用户 | 纯文本，可能包含附件引用 |
| AI 回复 | assistant | AI 给你的回答 | AI 模型 | 文本 + 可选的工具调用请求 |
| 工具结果 | tool_result | AI 调用了工具，工具返回的结果 | jcode 工具系统 | 结构化数据（文件内容、命令输出等） |
| 系统消息 | system | jcode 内部的通知、提示 | jcode 系统 | 文本（提示词、压缩摘要等） |

### 核心字段

| 字段名 | 类型 | 业务含义 | 大白话解释 |
|--------|------|---------|-----------|
| message_id | 唯一标识 | 消息的唯一 ID | 用于引用、跳转、关联 |
| role | 枚举 | 消息角色 | user / assistant / tool_result / system |
| content | 文本 | 消息正文 | 用户输入的文字，或 AI 回复的文字 |
| tool_calls | 列表 | 工具调用请求 | 只有 assistant 消息有，AI 说"请帮我执行这个工具" |
| tool_call_id | 标识 | 工具调用 ID | 只有 tool_result 消息有，对应哪次工具调用 |
| timestamp | 时间戳 | 消息产生时间 | 精确到毫秒 |
| token_count | 数值 | 估算的 token 数 | 用于计算上下文窗口用量和费用 |
| parent_message_id | 标识 | 引用的消息 | 用于分叉、重试场景，标记"这条消息是回复谁的" |
| metadata | 键值对 | 扩展元数据 | 比如消息的渲染偏好、是否被折叠 |

### 消息与工具调用的关系

这是理解 jcode 数据模型的关键。一次 AI 调用工具的过程，在 Message 层面是这样记录的：

```
1. 用户 Message (user): "帮我读一下 user_auth.rs"

2. AI Message (assistant): "好的，让我来读取文件"
   └── tool_calls: [
         { tool_call_id: "abc123", name: "read_file", params: { path: "user_auth.rs" } }
       ]

3. 工具结果 Message (tool_result):
   └── tool_call_id: "abc123"
   └── content: "（文件 user_auth.rs 的完整内容，200 行代码）"

4. AI Message (assistant): "我看到了，这个文件里有一个 login 函数..."
   └── tool_calls: [
         { tool_call_id: "def456", name: "write_file", params: { ... } }
       ]

5. 工具结果 Message (tool_result):
   └── tool_call_id: "def456"
   └── content: "写入成功"

6. AI Message (assistant): "重构完成！以下是变更摘要..."
   （这次没有 tool_calls，说明 AI 认为任务完成了）
```

通过 tool_call_id 把 AI 的"请求"和工具的"结果"关联起来，形成一条完整的调用链。

### 消息的分层价值

Message 不只是"聊天记录"，它对 jcode 的不同功能有不同的价值：

| 功能 | 怎么用 Message |
|------|---------------|
| 上下文窗口 | 把最近的 N 条 Message 发给 AI 模型，让它"记住"聊天历史 |
| 记忆提取 | 对话结束后，分析 Message 内容，提取关键信息存入记忆 |
| 会话恢复 | 从 SQLite 加载 Message 列表，重建对话状态 |
| 会话导出 | 把 Message 列表导出为 JSON/Markdown，方便分享 |
| 分叉重试 | 从某条 Message 开始分叉，尝试不同的回复路径 |
| 用量统计 | 累加所有 Message 的 token_count，算费用 |

### 消息的生命周期

一条 Message 从产生到被清理，经历以下阶段：

1. **产生**：用户输入、AI 回复、或工具执行完成时创建
2. **存储**：立即写入 SQLite，即使程序崩溃也不会丢
3. **渲染**：TUI 界面根据 Message 的 role 和 content 渲染（用户消息左对齐，AI 消息右对齐，代码块高亮）
4. **参与上下文**：被包含在发给 AI 的 Prompt 中
5. **压缩**：当上下文超限时，旧 Message 被压缩为摘要（system 消息），原始 Message 被标记为"已压缩"
6. **归档**：会话归档后，Message 也被压缩存储

## 核心实体三：Memory（记忆系统）

### 一句话概括

**Memory 是 jcode 的"长期记忆"**——它让 jcode 在对话结束后不"失忆"，下次对话时自动回忆起之前聊过的内容。

### 业务含义

普通的 AI 聊天工具是"金鱼记忆"——每次对话都是独立的，关掉就忘了。jcode 不同，它有三层记忆系统，模仿人脑的工作方式：

- **L1（工作记忆）**：当前对话的完整记录，就像你在脑子里记住的"刚才在聊什么"
- **L2（短期记忆）**：从对话中提取的关键信息摘要，就像你每天写的"工作日志"
- **L3（长期记忆）**：跨所有会话的持久偏好和知识，就像你的"工作习惯"和"技术栈偏好"

### 三级记忆架构

```
┌─────────────────────────────────────────────────────────────────┐
│                        记忆系统全景                              │
│                                                                 │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  L1：工作记忆（Working Memory）                          │   │
│  │  ┌─────────────────────────────────────────────────┐    │   │
│  │  │ 原始事件流，当前会话的完整对话记录                  │    │   │
│  │  │ 存储：当前 Session 的 messages 列表               │    │   │
│  │  │ 检索：直接读取                                     │    │   │
│  │  │ 生命周期：会话期间                                  │    │   │
│  │  │ 容量：取决于模型上下文窗口（通常 20 万 token）       │    │   │
│  │  └─────────────────────────────────────────────────┘    │   │
│  └─────────────────────────────────────────────────────────┘   │
│                              │                                  │
│                    对话结束，自动提取                             │
│                              ▼                                  │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  L2：会话摘要（Session Summary）                         │   │
│  │  ┌─────────────────────────────────────────────────┐    │   │
│  │  │ 压缩后的对话关键信息，结构化的摘要                  │    │   │
│  │  │ 存储：SQLite 中的 memories 表                      │    │   │
│  │  │ 检索：关键词匹配 + 语义搜索                         │    │   │
│  │  │ 生命周期：跨会话（保留 30 天）                      │    │   │
│  │  │ 内容：决策记录、Bug 修复方案、技术选择、项目约定     │    │   │
│  │  └─────────────────────────────────────────────────┘    │   │
│  └─────────────────────────────────────────────────────────┘   │
│                              │                                  │
│                    定期整理，提取共性                             │
│                              ▼                                  │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  L3：长期偏好（Long-term Preferences）                   │   │
│  │  ┌─────────────────────────────────────────────────┐    │   │
│  │  │ 用户明确表达的偏好 + AI 自动学习的行为模式         │    │   │
│  │  │ 存储：向量库（语义搜索） + 文件（preferences.md）    │    │   │
│  │  │ 检索：语义搜索（向量相似度）                        │    │   │
│  │  │ 生命周期：永久（除非手动删除）                      │    │   │
│  │  │ 内容：工具偏好、代码风格、技术栈、命名习惯           │    │   │
│  │  └─────────────────────────────────────────────────┘    │   │
│  └─────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────┘
```

### 每层记忆的核心字段

**L1 工作记忆**

L1 就是 Session 的 messages 列表，不需要单独的字段。它的"字段"就是 Message 的字段。

**L2 会话摘要**

| 字段名 | 类型 | 业务含义 | 大白话解释 |
|--------|------|---------|-----------|
| memory_id | 唯一标识 | 记忆条目的 ID | 唯一标识一条记忆 |
| session_id | 标识 | 来源会话 | 这条记忆是从哪个会话提取的 |
| category | 枚举 | 记忆类别 | 偏好 / 决策 / 约定 / 问题解决 |
| content | 文本 | 记忆内容 | 用自然语言描述的关键信息 |
| importance | 数值 | 重要性评分 | 0-10，越高越重要，越不容易被清理 |
| created_at | 时间戳 | 提取时间 | 什么时候生成的 |
| last_accessed_at | 时间戳 | 最后检索时间 | 最近一次被检索到，用于判断是否"过期" |
| access_count | 数值 | 被检索次数 | 被检索的次数越多，说明越有用 |
| expired | 布尔 | 是否过期 | 过期的记忆在检索时权重降低 |

**L3 长期偏好**

| 字段名 | 类型 | 业务含义 | 大白话解释 |
|--------|------|---------|-----------|
| preference_id | 唯一标识 | 偏好条目的 ID | 唯一标识 |
| category | 枚举 | 偏好类别 | 工具偏好 / 代码风格 / 技术栈 / 命名习惯 / 交互偏好 |
| key | 文本 | 偏好键 | 比如 "package_manager" |
| value | 文本 | 偏好值 | 比如 "pnpm" |
| source | 枚举 | 来源 | 用户明确设置 / AI 自动学习 |
| confidence | 数值 | 置信度 | 0-1，AI 自动学习的偏好置信度可能较低 |
| embedding | 向量 | 语义向量 | 用于语义搜索，找到语义上相关的偏好 |

### 记忆的生命周期

**L1 工作记忆的生命周期**：

```
会话开始 → 消息逐条追加 → 会话结束 → 自动转为 L2 提取的原材料
```

L1 的生命周期等于 Session 的生命周期。会话归档后，L1 被压缩存储。

**L2 会话摘要的生命周期**：

```
会话结束 → 自动提取关键信息 → 生成 L2 条目 → 存入 SQLite
    │
    │ 新会话开始 → 自动检索相关 L2 → 注入 Prompt
    │
    │ 30 天后 → 自动清理（或转为 L3 如果足够重要）
    │
    │ 与已有 L2 相似 → 合并去重
    │
    │ 被标记为过期 → 降低检索权重
```

**L3 长期偏好的生命周期**：

```
用户首次设置偏好 / AI 从多次会话中学习
    │
    ▼
存入向量库 + preferences.md 文件
    │
    ▼
每次新会话 → 语义搜索相关偏好 → 注入 Prompt
    │
    │ 用户修改偏好 → 更新
    │ AI 发现不匹配 → 降低置信度
    │ 长期未使用 → 降低权重
    │ 用户手动删除 → 移除
```

### 记忆图谱（Memory Graph）

jcode 不仅仅把记忆当成"独立条目"存储，它还会分析记忆之间的关联，构建一个**记忆图谱**。

举个例子：

```
记忆 A: "user_auth 模块使用 bcrypt 进行密码哈希"
记忆 B: "用户偏好使用 anyhow 处理错误"
记忆 C: "项目使用 PostgreSQL 数据库"
记忆 D: "测试文件放在 tests/ 目录"

它们之间的关联：
  A ←→ B (同模块相关：都在 user_auth 中用到)
  A ←→ C (同项目相关：都是同一个仓库的)
  B ←→ D (同一次对话中产生的)
```

关联类型包括：

| 关联类型 | 含义 | 例子 |
|---------|------|------|
| 同模块关联 | 都是关于同一个代码模块的 | 都涉及 user_auth.rs |
| 同项目关联 | 都是同一个代码仓库的 | 都是 my-project 的 |
| 同类型关联 | 都是同一类信息的 | 都是"技术决策"类 |
| 时序关联 | 在同一次对话中产生的 | 同一次聊出来的 |
| 因果关联 | 一个决定导致了另一个 | 因为选了 bcrypt，所以需要处理密码哈希 |

记忆图谱的作用是**级联激活**。当你检索到记忆 A 时，跟 A 强关联的记忆 B、C、D 也会被一起激活，让 AI 获得更全面的上下文。

## 核心实体四：Provider（模型提供商）

### 一句话概括

**Provider 是 jcode 的"万能插座"**——它把不同 AI 模型服务商的 API 差异封装成统一的接口，让上层代码不关心底层到底用的是 Claude 还是 GPT。

### 业务含义

jcode 支持 8 种以上的 AI 模型提供商。每个 Provider 的 API 格式、认证方式、能力范围都不同。Provider 实体的作用就是把这些差异"藏起来"，对外暴露统一的接口。

对用户来说，切换 Provider 就像换一个充电插头——插上就能用，不需要重新学习。

### 核心字段

| 字段名 | 类型 | 业务含义 | 大白话解释 |
|--------|------|---------|-----------|
| provider_id | 唯一标识 | 提供商的唯一 ID | 比如 "anthropic"、"openai"、"deepseek" |
| display_name | 文本 | 显示名称 | 在 UI 中展示的名字，比如 "Anthropic (Claude)" |
| auth_method | 枚举 | 认证方式 | api_key / oauth / env / local_credentials |
| api_key | 加密文本 | API 密钥 | 加密存储，不会明文出现在日志中 |
| base_url | URL | API 端点 | 请求发到哪个地址 |
| models | 列表 | 支持的模型列表 | 每个模型有名称、能力标记、价格信息 |
| capabilities | 标记集合 | 能力标记 | 支持 vision / tools / streaming / embedding 等 |
| rate_limit | 配置 | 速率限制 | 每分钟最多发多少请求、每分钟最多消耗多少 token |
| health_status | 枚举 | 健康状态 | healthy / degraded / down |
| latency_stats | 统计 | 延迟统计 | 平均响应时间、P50/P95/P99 |
| token_usage | 统计 | Token 用量 | 今天用了多少、本月用了多少 |
| error_count | 数值 | 错误计数 | 最近出了多少次错 |

### 支持的 Provider 一览

| Provider | 模型系列 | 接入方式 | 核心优势 | 适用场景 |
|----------|---------|---------|---------|---------|
| Anthropic | Claude 系列 | OAuth 登录 | 代码理解最强，200K 上下文 | 复杂重构、代码审查 |
| OpenAI | GPT-4o / 4.1 | OAuth 登录 | 综合能力最强 | 通用编码任务 |
| Google | Gemini 2.5 | OAuth 登录 | 100 万 token 上下文，超长文件 | 大项目分析 |
| GitHub Copilot | Copilot | OAuth 登录 | 深度集成 GitHub | GitHub 工作流 |
| OpenRouter | 200+ 模型 | API Key | 一个 Key 访问多种模型，聚合平台 | 多模型对比、成本优化 |
| AWS Bedrock | Claude (AWS) | IAM 凭证 | 企业合规，VPC 内运行 | 企业用户、数据合规 |
| Cursor | Cursor Agent | 本地凭证 | 复用 Cursor 编辑器的登录状态 | Cursor 用户无缝迁移 |
| DeepSeek | V3 / R1 | API Key | 性价比极高 | 成本敏感场景 |
| MiniMax | ABAB 系列 | API Key | 国产模型，中文能力强 | 中文编码场景 |
| 通义千问 | Qwen-Max | API Key | 阿里云生态 | 阿里云用户 |
| 智谱 | GLM-4 | API Key | 国产模型 | 国内合规需求 |
| 月之暗面 | Kimi | API Key | 长上下文 | 中文长文档 |
| 本地模型 | Ollama | 本地连接 | 完全离线，数据不出本机 | 离线开发、敏感项目 |

### Provider 的生命周期

```
用户首次配置 Provider
    │
    ├─ 方式 1：OAuth 登录
    │   └── 浏览器打开登录页 → 用户授权 → 回调 → 获取 Token → 加密存储
    │
    ├─ 方式 2：API Key
    │   └── 用户输入 Key → 验证有效性 → 加密存储
    │
    ├─ 方式 3：环境变量
    │   └── 从系统环境变量自动读取 → 验证
    │
    └─ 方式 4：本地凭证
        └── 从其他工具（Cursor、Copilot）的本地文件读取
    │
    ▼
Provider 注册到运行时
    │
    ▼
会话使用 Provider
    │  ├── Agent 调用 chat() → Provider 发送 API 请求
    │  ├── 记录 token_usage、latency_stats
    │  └── 监控 health_status
    │
    │ 健康检查失败 → health_status = degraded
    │ 连续失败 → health_status = down → 自动切换到备用 Provider
    │
    ▼
用户删除或更换 Provider → 从运行时注销 → 加密的 API Key 被清除
```

### 智能路由

jcode 不是简单地"用户选哪个就用哪个"，它有一个智能路由层，根据以下因素自动选择最优 Provider：

| 因素 | 说明 | 例子 |
|------|------|------|
| 任务类型 | 不同类型的任务适合不同的模型 | 代码生成用强模型，代码补全用快模型 |
| 成本预算 | 用户设置了月度预算上限 | 预算快用完时，自动切便宜模型 |
| 延迟要求 | 交互式场景要求快速响应 | 聊天时用快模型，后台任务可以等 |
| 可用性 | 主模型挂了自动切备用 | Claude 超时 → 自动切 GPT |
| 历史成功率 | 某类任务在某个模型上成功率更高 | 重构任务在 Claude 上成功率 95% |

## 核心实体五：Tool（工具）

### 一句话概括

**Tool 是 jcode 的"手和脚"**——AI 模型本身只能"想"和"说"，但 Tool 让它能"做"：读文件、写代码、跑命令、搜网页。

### 业务含义

如果把 AI 模型比作一个"大脑"，Tool 就是它的"四肢"。没有 Tool，AI 只能回答你"应该怎么做"；有了 Tool，AI 能直接帮你"做"。

jcode 内置了 30+ 个工具，涵盖文件操作、代码执行、Git 管理、网页搜索、PDF 阅读等。每个 Tool 都是一个独立的、可插拔的模块。

### 核心字段

| 字段名 | 类型 | 业务含义 | 大白话解释 |
|--------|------|---------|-----------|
| tool_name | 标识 | 工具名称 | 唯一标识，比如 "read_file"、"execute_code" |
| display_name | 文本 | 显示名称 | 在 UI 中展示的名字，比如 "读取文件" |
| description | 文本 | 功能描述 | 告诉 AI 这个工具是干什么的，AI 根据描述决定是否调用 |
| parameters | Schema | 参数定义 | JSON Schema 格式，定义这个工具需要哪些输入参数 |
| handler | 函数 | 执行函数 | 工具被调用时实际执行的代码 |
| requires_approval | 布尔 | 是否需要用户确认 | 危险操作（写文件、执行命令）需要用户点头 |
| category | 枚举 | 工具分类 | 文件操作 / 代码执行 / Git / 搜索 / 浏览器 / 其他 |
| is_enabled | 布尔 | 是否启用 | 用户可以在配置中关闭某些工具 |
| timeout | 数值 | 超时时间 | 工具执行超过这个时间就强制终止 |

### 工具分类与清单

**文件操作类**

| 工具名 | 功能 | 需要确认？ | 典型场景 |
|--------|------|-----------|---------|
| read_file | 读取文件内容 | 否 | AI 说"让我看看这个文件的代码" |
| write_file | 写入文件 | 是 | AI 说"我帮你写好了新代码" |
| edit_file | 编辑文件（精确替换） | 是 | AI 说"把第 15 行改成..." |
| list_dir | 列出目录内容 | 否 | AI 说"让我看看项目结构" |
| glob_search | 按模式搜索文件 | 否 | AI 说"找所有 .js 文件" |
| grep_search | 搜索文件内容 | 否 | AI 说"找所有调用 login 的地方" |

**代码执行类**

| 工具名 | 功能 | 需要确认？ | 典型场景 |
|--------|------|-----------|---------|
| exec_command | 执行 Shell 命令 | 是 | AI 说"运行 cargo test" |
| background_process | 后台执行命令 | 是 | AI 说"启动开发服务器" |
| process | 管理后台进程 | 否 | 查看后台进程状态 |

**Git 操作类**

| 工具名 | 功能 | 需要确认？ | 典型场景 |
|--------|------|-----------|---------|
| git_diff | 查看变更 | 否 | AI 说"让我看看你改了什么" |
| git_log | 查看提交历史 | 否 | AI 说"看看最近的提交" |
| git_status | 查看工作区状态 | 否 | AI 说"看看有哪些文件被修改了" |

**搜索类**

| 工具名 | 功能 | 需要确认？ | 典型场景 |
|--------|------|-----------|---------|

|--------|------|-----------|---------|

| tts | 文本转语音 | 否 | 语音输出 |
| session_status | 查看会话状态 | 否 | 查看用量和费用 |

### 工具的权限控制

jcode 对工具有精细的权限控制，分为三个级别：

**级别 1：自动执行（无需确认）**
- 只读操作：读文件、搜索、查看状态
- 没有副作用，不会修改任何东西
- 典型工具：read_file、grep_search、git_status

**级别 2：需要确认（弹窗询问）**
- 写操作：写文件、执行命令、Git 提交
- 有副作用，但可逆（Git 可以回滚）
- 典型工具：write_file、exec_command、git_diff

**级别 3：需要额外授权（二次确认）**
- 危险操作：删除文件、强制推送、访问网络
- 有不可逆的副作用
- 用户需要在配置中显式开启

### 工具的生命周期

```
工具被定义（内置 30+ 或用户自定义）
    │
    ▼
工具注册到工具注册表（Tool Registry）
    │
    ▼
会话启动时，根据配置加载启用的工具列表
    │
    ▼
Agent 构建 Prompt 时，将工具列表注入到系统提示中
    │  AI 看到："你可以使用以下工具：read_file、write_file、..."
    │
    ▼
AI 决定调用工具 → 返回 tool_call 请求
    │
    ├─ 检查权限：需要确认？
    │   ├─ 是 → 弹窗询问用户 → 用户同意 → 执行
    │   └─ 否 → 直接执行
    │
    ▼
执行工具 → 返回结果 → 作为 tool_result 消息追加到对话
    │
    ▼
工具执行结果交给 AI → AI 继续思考 → 可能再次调用工具
    │
    ▼
用户禁用了某个工具 → 从会话中移除 → AI 不再知道这个工具的存在
```

## 核心实体六：Plan（计划）

### 一句话概括

**Plan 是 jcode 的"项目计划书"**——当任务复杂到需要多步骤时，Plan 把任务拆成可执行的小步骤，每个步骤有明确的验收标准和依赖关系。

### 业务含义

如果用户说"帮我修一个 Bug"，Agent 可能不需要 Plan——直接读文件、改代码、跑测试，三步搞定。但如果用户说"把这个项目从 JavaScript 迁移到 TypeScript"，那就需要 Plan 了——这个任务涉及几十个文件、多个阶段、有依赖关系。

Plan 就是 jcode 的"先想清楚再动手"机制。

### 核心字段

| 字段名 | 类型 | 业务含义 | 大白话解释 |
|--------|------|---------|-----------|
| plan_id | 唯一标识 | 计划的唯一 ID | 全局唯一，用于追踪和引用 |
| session_id | 标识 | 所属会话 | 这个计划是在哪个会话中创建的 |
| title | 文本 | 计划标题 | 比如 "JavaScript 迁移到 TypeScript" |
| description | 文本 | 计划描述 | 更详细的说明 |
| steps | 列表 | 步骤列表 | 每个步骤有独立的描述、状态、结果 |
| status | 枚举 | 整体状态 | pending / running / completed / failed |
| execution_mode | 枚举 | 执行模式 | sequential（串行）/ parallel（并行）/ mixed（混合） |
| created_at | 时间戳 | 创建时间 | 计划什么时候生成的 |
| started_at | 时间戳 | 开始执行时间 | 什么时候开始执行的 |
| completed_at | 时间戳 | 完成时间 | 什么时候全部完成的 |
| assigned_agents | 列表 | 分配的 Agent | Swarm 模式下，哪些子 Agent 负责哪些步骤 |

### 步骤（Step）结构

每个步骤是一个独立的执行单元：

| 字段名 | 类型 | 业务含义 | 大白话解释 |
|--------|------|---------|-----------|
| step_id | 标识 | 步骤 ID | 在计划内唯一 |
| order | 数值 | 执行顺序 | 第几步 |
| description | 文本 | 步骤描述 | 这一步要做什么 |
| preconditions | 列表 | 前置条件 | 哪些步骤必须先完成 |
| acceptance_criteria | 文本 | 验收标准 | 怎么判断这一步做完了、做对了 |
| rollback_plan | 文本 | 回滚方案 | 如果这一步失败，怎么恢复 |
| estimated_tokens | 数值 | 预估 token 消耗 | 这一步大概要花多少钱 |
| status | 枚举 | 步骤状态 | pending / running / completed / failed / skipped |
| result | 文本 | 执行结果 | 完成后的输出摘要 |
| started_at | 时间戳 | 开始时间 | 这一步什么时候开始的 |
| completed_at | 时间戳 | 完成时间 | 这一步什么时候完成的 |

### 执行模式

**串行模式（Sequential）**

```
步骤 1 → 步骤 2 → 步骤 3 → 步骤 4
```

适合有严格依赖关系的任务。比如"先读文件，再改代码，再跑测试"——每一步都依赖上一步的结果。

**并行模式（Parallel）**

```
步骤 1 ─┐
步骤 2 ─┼── 同时执行
步骤 3 ─┘
```

适合互相独立的子任务。比如"给三个独立的模块各写一份测试"——三个模块互不依赖，可以同时进行。

**混合模式（Mixed）**

```
阶段 1: 步骤 1 → 步骤 2 (串行)
阶段 2: 步骤 3 ─┐
        步骤 4 ─┼── 并行
        步骤 5 ─┘
阶段 3: 步骤 6 (依赖于阶段 2 全部完成)
```

最常见的模式。大部分任务既有串行依赖，也有可并行部分。

### Plan 的生命周期

```
用户提出复杂需求
    │
    ▼
计划引擎分析任务 → 拆解步骤 → 生成 Plan
    │
    ▼
Plan 展示给用户 → 用户审核
    │
    ├─ 同意 → 开始执行
    ├─ 修改 → 调整步骤 → 重新展示
    └─ 拒绝 → Plan 归档，重新分析
    │
    ▼
执行 Plan
    │
    ├─ 串行模式：Step 1 → Step 2 → Step 3 → ...
    ├─ 并行模式：Step 1, 2, 3 同时 → 汇总
    └─ 混合模式：先串行阶段 1，再并行阶段 2，再串行阶段 3
    │
    │ 每步完成 → 更新 status → 验证验收标准
    │ 步骤失败 → 触发回滚 → 尝试修复 → 重试
    │ 发现新情况 → 动态调整 Plan（插入新步骤、拆分步骤）
    │
    ▼
所有步骤完成 → Plan completed
    │
    ▼
Plan 归档 → 作为 L2 记忆的一部分保存
```

## 核心实体七：Config（配置）

### 一句话概括

**Config 是 jcode 的"控制面板"**——它决定了 jcode 怎么运行、用什么模型、开什么工具、长什么样子。

### 业务含义

jcode 的配置不是"一锤子买卖"，而是分层的——不同层级有不同的优先级，高层覆盖低层。这让你可以为不同的项目设置不同的配置，同时保留全局默认值。

### 配置层级

```
┌─────────────────────────────────────────────────────────┐
│           配置优先级（从高到低）                          │
│                                                         │
│  ┌─────────────────────────────────────────────────┐   │
```

## 支撑实体详解

除了 7 个核心实体，jcode 还有一批支撑实体，它们不直接参与核心业务，但为系统运行提供了必要的基础能力。

### Embedding（向量嵌入）

**一句话概括**：Embedding 是 jcode 的"语义搜索引擎"——它把文本转成数字向量，让机器能理解"密码哈希"和"bcrypt"是一个意思。

**核心字段**：

| 字段名 | 含义 | 说明 |
|--------|------|------|
| model | ONNX 模型名称 | 本地运行的嵌入模型，不需要联网 |
| dimension | 向量维度 | 384 / 768 / 1024，维度越高表达力越强 |
| cache | 缓存策略 | 已经计算过的文本不再重复计算 |
| batch_size | 批量大小 | 一次处理多少条文本 |

**白话解释**：把一段文字变成一串数字（比如 768 个小数），相似的文字会被映射到相近的数字。这样"密码哈希"和"bcrypt 加密"在数字空间中就很近，搜一个就能找到另一个。

### Auth（认证）

**一句话概括**：Auth 管理用户登录各种 AI 服务的凭证。

**核心字段**：

| 字段名 | 含义 | 说明 |
|--------|------|------|
| provider | 关联的 Provider | 这份凭证是给哪个 Provider 用的 |
| auth_method | 认证方式 | api_key / oauth / env / local_credentials |
| access_token | 访问令牌 | 加密存储 |
| refresh_token | 刷新令牌 | 用于自动续期 |
| expires_at | 过期时间 | 过期前自动刷新 |

### Gateway（网关连接）

**一句话概括**：Gateway 管理 jcode 与外部网关服务的连接状态。

**核心字段**：

| 字段名 | 含义 | 说明 |
|--------|------|------|
| endpoint | 网关地址 | 连接哪个网关 |
| status | 连接状态 | connected / disconnected / reconnecting |
| latency | 延迟 | 网络延迟（毫秒） |
| retry_count | 重试次数 | 最近失败后重试了多少次 |

### Build（构建元数据）

**一句话概括**：记录 jcode 自身的版本和构建信息。

**核心字段**：

| 字段名 | 含义 | 说明 |
|--------|------|------|
| version | 版本号 | 比如 v0.54.3 |
| commit | Git commit hash | 精确到哪个提交 |
| timestamp | 构建时间 | 什么时候编译的 |
| platform | 目标平台 | macOS / Linux / Windows |
| features | 编译特性 | 启用了哪些功能 |

### Telemetry（遥测数据）

**一句话概括**：可选的匿名使用统计，帮助 jcode 团队了解产品使用情况。

**核心字段**：

| 字段名 | 含义 | 说明 |
|--------|------|------|
| event_type | 事件类型 | 比如 session_started、tool_called |
| payload | 事件数据 | 匿名化的数据，不包含用户内容 |
| timestamp | 事件时间 | 什么时候发生的 |
| session_id | 关联会话 | 匿名化的会话 ID |
| user_opted_in | 用户是否同意 | 用户必须主动同意才会上报 |

### Import（导入数据）

**一句话概括**：从其他 AI 编码工具（Claude Code、Codex、Cursor）导入历史数据。

**核心字段**：

| 字段名 | 含义 | 说明 |
|--------|------|------|
| source | 来源工具 | claude_code / codex / cursor |
| format | 原始格式 | json / yaml / toml |
| mapping | 字段映射 | 来源工具的字段怎么对应 jcode 的字段 |
| status | 导入状态 | pending / running / completed / failed |

### Batch（批量任务）

**一句话概括**：批量处理多个会话或任务。

**核心字段**：

| 字段名 | 含义 | 说明 |
|--------|------|------|
| task_list | 任务列表 | 要批量处理的任务清单 |
| concurrency | 并发数 | 同时处理几个 |
| progress | 进度 | 完成了多少 |
| results | 结果汇总 | 每个任务的执行结果 |

### Background（后台任务）

**一句话概括**：管理后台定时任务，比如记忆整理、日志清理、更新检查。

**核心字段**：

| 字段名 | 含义 | 说明 |
|--------|------|------|
| task_type | 任务类型 | memory_compaction / log_cleanup / update_check |
| schedule | 调度策略 | 多久执行一次 |
| priority | 优先级 | 高优先级先执行 |
| status | 任务状态 | pending / running / done / failed |
| retry_policy | 重试策略 | 失败后怎么重试 |

### Notification（通知）

**一句话概括**：管理通知配置，比如任务完成时发送桌面通知。

**核心字段**：

| 字段名 | 含义 | 说明 |
|--------|------|------|
| channel | 通知渠道 | desktop / system / email |
| event_types | 触发事件 | 哪些事件触发通知 |
| template | 通知模板 | 通知的内容格式 |
| enabled | 是否启用 | 开关 |

### Desktop（桌面状态）

**一句话概括**：记录桌面应用的 UI 状态。

**核心字段**：

| 字段名 | 含义 | 说明 |
|--------|------|------|
| window_state | 窗口状态 | 位置、大小、是否最大化 |
| tray_enabled | 系统托盘 | 是否在菜单栏显示图标 |
| hotkey | 全局快捷键 | 比如 Cmd+; |
| theme | 主题 | light / dark |
| always_on_top | 是否置顶 | 窗口是否始终在最前面 |

## 实体间协作关系

### 场景一：用户发起一次对话

```
用户输入 "帮我重构 user_auth.rs"

1. Config 提供默认 Provider 和模型
2. Session 创建或恢复，加载历史 Message
3. Memory 检索 L2/L3 记忆，注入 Prompt
4. Provider 连接 AI 模型
5. Agent 构建 Prompt（系统提示 + 工具列表 + 记忆 + 历史消息 + 用户输入）
6. Tool 列表被注入到 Prompt，AI 知道可以用哪些工具
7. AI 返回 → 可能需要调用 Tool → Tool 执行 → 返回结果
8. 每轮交互都追加到 Message 列表
9. 对话结束 → Memory 自动提取关键信息
```

### 场景二：Swarm 多 Agent 协作

```
用户输入 "给整个项目写单元测试"

1. Plan 引擎分析任务，生成 Plan（3 个阶段，15 个步骤）
2. Swarm 协调器创建 3 个子 Agent
3. 每个子 Agent 有自己的 Session + Provider + Tool 权限
4. Plan 的步骤分配给不同的子 Agent
5. 子 Agent 并行执行，各自调用 Tool
6. 子 Agent 之间通过 Coordinator 通信
7. 结果汇总到 Plan
8. 所有步骤完成 → Plan completed
9. 整个过程的 Memory 写入 L2
```

### 场景三：会话恢复

```
用户关闭终端，一天后重新打开

1. Session 从 SQLite 加载（状态：PAUSED → RESUMED）
2. Message 列表完整恢复
3. Memory 重新检索 L2/L3
4. Provider 重新建立连接
5. Config 重新加载（可能有变更）
6. 用户看到的就是上次离开时的状态，无缝继续
```

## 数据持久化架构

### 存储方案

jcode 使用 **SQLite** 作为主存储引擎。选择 SQLite 的原因很务实：

| 优势 | 说明 |
|------|------|
| 零配置 | 不需要安装数据库服务，不需要 Docker，不需要配置端口 |
| 单文件 | 一个 .db 文件包含所有数据，备份就是复制一个文件 |
| 事务 | 保证数据一致性，不会出现"写了一半"的情况 |
| WAL 模式 | 支持并发读写，读操作不会阻塞写操作 |
| 嵌入式 | 编译到二进制中，没有外部依赖 |
| 跨平台 | macOS、Linux、Windows 都一样用 |

### 存储位置

| 数据 | 存储位置 | 格式 |
|------|---------|------|
| 会话和消息 | ~/.jcode/jcode.db | SQLite |
| 记忆（L2） | ~/.jcode/jcode.db | SQLite |
| 记忆（L3） | ~/.jcode/preferences.md + 向量库 | 文件 + SQLite |
| API Key | 系统 Keychain / Keyring | 加密存储 |
| 配置文件 | ~/.jcode/config.toml | TOML |
| 项目配置 | 项目根目录/.jcode/config.toml | TOML |
| 日志 | ~/.jcode/logs/ | 文本文件 |
| 备份 | ~/.jcode/backups/ | SQLite 副本 |
| 向量缓存 | ~/.jcode/cache/ | 二进制文件 |

### 数据库表结构概览

| 表名 | 存储内容 | 关键字段 |
|------|---------|---------|
| sessions | 会话信息 | session_id, title, provider, model, status, workspace, created_at, updated_at |
| messages | 消息记录 | message_id, session_id, role, content, tool_calls, timestamp, token_count |
| memories | 记忆条目 | memory_id, session_id, category, content, importance, embedding |
| providers | Provider 配置 | provider_id, auth_method, base_url, models, capabilities |
| tools | 工具定义 | tool_name, description, parameters, category, requires_approval |
| plans | 计划记录 | plan_id, session_id, title, steps, status, execution_mode |
| config | 配置项 | key, value, scope (global/project/session) |

## 数据安全与隐私

### 敏感数据保护

jcode 对敏感数据的处理非常谨慎：

| 数据类型 | 保护措施 |
|---------|---------|
| API Key | 存入系统 Keychain（macOS）/ Keyring（Linux）/ 加密存储（Windows），不写明文到文件 |
| OAuth Token | 加密存储，自动刷新，过期自动清除 |
| 对话内容 | 仅存储在本地 SQLite，不上传到 jcode 服务器 |
| 遥测数据 | 完全可选，用户主动同意才上报，上报内容匿名化 |
| 项目代码 | 仅在本地处理，不会发送到 jcode 服务器 |

### 数据所有权

用户完全拥有自己的数据：

- 所有数据存储在本地（~/.jcode/ 目录）
- 可以随时导出为 JSON 格式
- 可以随时删除（删除 ~/.jcode/ 目录即可）
- 切换到其他工具时，可以通过 Import 功能迁移数据

## 总结：jcode 数据设计的五个原则

回顾 jcode 的所有数据实体，可以归纳出五个设计原则：

### 原则一：以 Session 为中心

一切围绕 Session 展开。Message 是 Session 的内容，Memory 是 Session 的提取物，Plan 是 Session 的执行蓝图，Tool 是 Session 的执行能力。这个设计让 jcode 的"工作单元"概念非常清晰——一个 Session 就是一个完整的、自包含的工作单元。

### 原则二：记忆是核心竞争力

大部分 AI 工具是"金鱼记忆"，jcode 的三级记忆系统（L1/L2/L3）让它能"记住你、理解你、适应你"。记忆不是简单存储，而是自动提取、自动关联、自动检索——你不需要手动管理，它像人脑一样自动工作。

### 原则三：Provider 解耦

通过 Provider 抽象层，jcode 把 AI 模型变成了"可插拔的插件"。切换模型不需要改任何代码，添加新 Provider 不需要动核心逻辑。这让 jcode 不被任何一个模型提供商绑定。

### 原则四：配置分层，灵活覆盖

四级配置优先级（命令行 > 环境变量 > 项目 > 全局）让用户在不同粒度上控制 jcode 的行为。全局设一个默认，项目有特殊需求就覆盖，临时需要换模型就用命令行参数。

### 原则五：数据本地化，隐私优先

所有用户数据存储在本地，SQLite 单文件让备份和迁移变得极其简单。API Key 用系统级加密存储，不写明文。用户完全拥有自己的数据，随时可以导出或删除。
