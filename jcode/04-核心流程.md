## 为什么需要理解核心流程

jcode 不是简单的你问 AI 答的聊天框。它内部有 7 层架构、76 个独立模块、30+ 工具，每一步操作都涉及多个模块的精确配合。理解核心流程，你就能回答以下问题：

- 用户输入一句话，jcode 内部经历了什么，才最终输出答案？
- 多个 Agent 同时干活，怎么保证不互相踩脚？
- jcode 怎么记住你三天前的对话？
- 切换模型提供商时，为什么用户可以无感知？

本文档用 8 个端到端流程回答这些问题。每个流程都配有 ASCII 流程图，标注参与的模块和流转的数据。

## 流程一：一次编码对话的完整旅程

这是 jcode 最高频、最核心的流程。

以用户输入"帮我重构 user_auth.rs 中的 login 函数"为例，走一遍完整的端到端流程。

### 涉及模块

| 模块 | 角色 |
|------|------|
| CLI 入口层 (src/main.rs) | 接收用户命令，启动 TUI |
| jcode-app-core | 应用编排，管理生命周期 |
| jcode-session-types | 会话管理，加载/保存对话 |
| jcode-memory-types | 记忆检索，找历史上下文 |
| jcode-embedding | 向量嵌入，语义搜索记忆 |
| jcode-agent-runtime | Agent 循环引擎 |
| jcode-provider-anthropic | 调用 Claude 模型 |
| jcode-tool-core | 工具执行核心 |
| jcode-tui | 终端 UI 渲染 |
| jcode-compaction-core | 上下文压缩 |

### 涉及数据

| 数据实体 | 说明 |
|----------|------|
| Session | 当前会话对象，包含消息列表、Provider 配置 |
| Message | 每一条用户消息和 AI 回复 |
| Memory (L1/L2/L3) | 三级记忆，提供历史上下文 |
| Plan | 如有任务计划，提供执行步骤 |
| Config | 当前生效的配置 |

|   |   - 添加 bcrypt 密码哈希
|   |   - 增加输入验证和错误处理

|   |   - 所有测试通过
|   |  无更多工具调用 -> Agent 循环结束
|   |

|   |  流式输出 AI 回复 (实时显示生成过程)
|   |  Markdown 渲染: 代码高亮、列表、引用
|   |  更新侧边栏: 显示文件变更 diff

|   |

|   |  自动提取关键信息:

### 白话解读

这个过程就像一个有经验的开发者带着一个外脑在工作：

1. **先回忆**（记忆检索）：我上次处理这个模块时是怎么做的？用户有什么偏好？
2. **先看清楚**（第 1 轮 LLM + read_file）：先读文件，理解现状
3. **分析问题**（第 2 轮 LLM）：找到代码的问题所在
4. **动手改**（write_file）：写出新的代码
5. **验证**（execute_code）：跑测试确保没问题
6. **汇报**（最终回复）：告诉用户改了什么
7. **存档**（记忆更新）：记住这次的经验，下次不用重新学

整个过程，Agent 不是一次性回答，而是反复思考、验证、迭代，直到确认任务完成。这就是 Agent 循环（Agent Loop）的核心价值。

## 流程二：Swarm 多 Agent 协作

这是 jcode 区别于所有竞品的杀手级功能。当任务复杂到无法单人完成时，Swarm 模式启动多个 Agent 并行工作。

### 涉及模块

| 模块 | 角色 |
|------|------|
| jcode-plan | 计划引擎，拆解任务 |
| jcode-swarm-core | Swarm 协调器，管理 Agent 群 |
| jcode-agent-runtime | 每个子 Agent 的运行实例 |
| jcode-session-types | 每个 Agent 的独立会话 |
| jcode-tool-core | 工具执行，含文件冲突检测 |
| jcode-provider-* | 每个 Agent 可配不同 Provider |
| jcode-compaction-core | 每个 Agent 独立的上下文压缩 |

### 涉及数据

| 数据实体 | 说明 |
|----------|------|
| Plan | 任务分解计划，含步骤和依赖关系 |
| SubAgent | 每个子 Agent 的会话和状态 |
| Message | Agent 间通信消息 |
| FileLock | 文件占用锁，防止同时修改 |

### 白话解读

Swarm 模式就像一个项目经理带着三个开发人员：

1. **项目经理**（计划引擎 + Swarm 协调器）：分析任务规模，分配给不同的人
2. **开发 A**（Agent A）：负责核心模块，独立工作
3. **开发 B**（Agent B）：负责工具模块，独立工作
4. **开发 C**（Agent C）：负责辅助模块，独立工作

关键设计是冲突检测和 Agent 间通信。三个开发人员各自在自己的工位上干活，但如果 A 想改一个 B 正在看的文件，系统会自动通知双方，避免冲突。这比传统 AI 工具一个 AI 串行干所有事的效率高得多。

### Swarm 适用的场景

- 代码重构：一个 Agent 改逻辑，一个 Agent 写测试，一个 Agent 更新文档
- 多仓库操作：前端和后端 Agent 同时修改，自动协调 API 接口
- Code Review：一个 Agent 审查代码，一个 Agent 写修复建议，一个 Agent 执行修复
- 知识迁移：一个 Agent 分析旧代码，一个 Agent 写新代码，一个 Agent 做对比验证

## 流程三：记忆与学习系统

jcode 的记忆系统不是简单的保存对话记录，而是模仿人脑的关联记忆——它会自动提取关键信息、建立关联、在需要时精准检索。

### 涉及模块

| 模块 | 角色 |
|------|------|
| jcode-memory-types | 记忆数据结构定义，三级存储 |
| jcode-embedding | 文本向量化，语义搜索 |
| jcode-compaction-core | 记忆整理，去重合并 |
| jcode-agent-runtime | 记忆注入 Prompt |
| jcode-session-types | 会话级别的记忆关联 |

### 涉及数据

| 数据实体 | 说明 |
|----------|------|
| Memory (L1) | 原始事件流，当前会话的完整记录 |
| Memory (L2) | 会话摘要，压缩后的关键信息 |
| Memory (L3) | 长期偏好，跨会话的向量化知识 |
| Embedding | 向量，用于语义搜索 |
| MemoryGraph | 记忆图谱，记忆之间的关联边 |

    Agent 自动:
    - 使用 bcrypt 处理密码 (记忆 1)
    - 使用 anyhow 处理错误 (记忆 2)

|   |

### 白话解读

jcode 的记忆系统就像一个有超强记忆力的助手：

- **自动记笔记**（记忆生成）：每次对话结束，自动提取关键信息存入笔记本
- **智能索引**（向量化）：不是按日期翻笔记，而是按意思搜索——你说 logout，它能找到登录相关的笔记
- **联想记忆**（记忆图谱）：找到一个记忆点后，自动联想到相关的其他记忆——像人脑的哦对了，还有这个
- **定期整理**（记忆整理）：定期清理重复的、过时的笔记，保持笔记本整洁

### 记忆系统的产品价值

对用户来说，这意味着：
- 不需要每次对话都重新介绍项目背景
- 不需要重复说明自己的偏好
- 跨项目积累经验——在项目 A 学到的，在项目 B 也能用
- 团队协作场景下，每个成员的偏好都可以被记忆

## 流程四：Provider 切换与容灾

jcode 支持 8 种以上的 AI 模型提供商，并且可以在同一会话中无缝切换。更关键的是，它有完整的容灾机制——当一个 Provider 不可用时，自动降级到备用 Provider。

### 涉及模块

| 模块 | 角色 |
|------|------|
| jcode-config-types | 读取 Provider 配置 |
| jcode-provider-core | Provider 抽象层，统一接口 |
| jcode-provider-metadata | Provider 元数据管理 |
| jcode-provider-doctor | Provider 健康检查 |
| jcode-provider-anthropic | Anthropic (Claude) 适配器 |
| jcode-provider-openai | OpenAI (GPT) 适配器 |
| jcode-provider-gemini | Google Gemini 适配器 |
| jcode-provider-copilot | GitHub Copilot 适配器 |
| jcode-provider-openrouter | OpenRouter 适配器 |
| jcode-provider-bedrock | AWS Bedrock 适配器 |
| jcode-auth-types | 认证管理 |
| jcode-agent-runtime | Agent 运行时，使用 Provider |

### 涉及数据

| 数据实体 | 说明 |
|----------|------|
| Provider | Provider 配置，含 API Key、模型列表 |
| ModelConfig | 模型配置，含温度、最大 Token 等 |
| AuthToken | OAuth Token 或 API Key |
| HealthStatus | Provider 健康状态 |

### 端到端流程图

```
+-----------------------------------------------------------------------+
|                     Provider 切换与容灾流程                             |
+-----------------------------------------------------------------------+

[场景 1: 手动切换 Provider]

用户输入: 切换到 Gemini 模型 或 修改配置文件
|
+-- 1. 配置读取 (jcode-config-types)
|   |  读取当前配置: provider: gemini, model: gemini-2.5-pro
|   |  优先级: 会话配置 > 项目配置 > 全局配置 > 默认值
|   |
+-- 2. Provider 解析 (jcode-provider-metadata)
|   |  查找 gemini 的 Provider 元数据:
|   |    - base_url: https://generativelanguage.googleapis.com
|   |    - 认证方式: OAuth (Google 账号)
|   |    - 能力: 支持 tools, streaming, vision, 1M 上下文
|   |    - 定价: 约 1.25 美元/百万输入 token
|   |
+-- 3. 认证检查 (jcode-auth-types)
|   |  查找 Gemini 的认证凭证:
|   |    -> 已有 OAuth Token -> 检查是否过期
|   |    -> 没有 -> 提示用户登录
|   |    -> 已过期 -> 自动刷新 Token
|   |
+-- 4. Provider 初始化 (jcode-provider-gemini)
|   |  创建 Gemini Provider 实例
|   |  加载模型列表: gemini-2.5-pro, gemini-2.5-flash, ...
|   |  初始化速率限制器
|   |
+-- 5. 健康检查 (jcode-provider-doctor)
|   |  发送测试请求: 验证 API 连通性
|   |  测量延迟: 首 token 延迟、平均延迟
|   |  检查功能: 工具调用是否支持? 流式输出是否正常?
|   |
+-- 6. 运行时切换
|   |  更新 Agent 的 Provider 引用: 从 Anthropic -> Gemini
|   |  调整工具定义: 不同 Provider 的工具格式略有不同
|   |  更新 Token 计数器: 不同 Provider 的 Token 计算方式不同
|   |  更新用量追踪: 开始记录 Gemini 的用量
|   |
+-- 7. 无缝生效
|   |  当前对话上下文保持不变
|   |  记忆系统不变
|   |  所有工具仍然可用
|   |  下一次 LLM 调用自动使用 Gemini
|   |
+-- 用户无感知，无需重启 jcode

[场景 2: 自动容灾 -- Provider 故障时自动降级]

Agent 循环中，调用 LLM
|
+-- 8. 调用失败检测
|   |  调用 Anthropic API -> 返回 429 (速率限制)
|   |  错误类型识别:
|   |    - 429: 速率限制 -> 等待后重试
|   |    - 503: 服务不可用 -> 切换到备用 Provider
|   |    - 401: 认证失败 -> 提示用户重新登录
|   |    - 超时: 网络问题 -> 重试 3 次，仍失败则切换
|   |
+-- 9. 自动降级策略
|   |  当前 Provider: Anthropic Claude
|   |  备用 Provider 列表 (按优先级):
|   |    1. OpenAI GPT-4o (同级别的替代)
|   |    2. Gemini 2.5 Pro (功能类似)
|   |    3. OpenRouter (可访问多个模型)
|   |
|   |  决策逻辑:
|   |    -> 如果当前任务需要代码理解能力 -> 优先选 OpenAI
|   |    -> 如果当前任务需要长上下文 -> 优先选 Gemini (1M 上下文)
|   |    -> 如果是一般任务 -> 按优先级顺序尝试
|   |
+-- 10. 切换执行
|   |  自动切换到 OpenAI GPT-4o
|   |  重新构建 Prompt (适配 OpenAI 格式)
|   |  从断点继续: 工具调用结果不丢失
|   |
+-- 11. 用户通知
|   |  在 TUI 中显示提示:
|   |    !! Anthropic 暂时不可用 (503)
|   |    OK 已自动切换到 OpenAI GPT-4o
|   |    ## 本次切换耗时: 0.8 秒
|   |
+-- 12. 恢复检测
    |  定期检查 Anthropic 是否恢复
    |  恢复后: 下次调用可选切回 (不强制，避免频繁切换)
```

### 白话解读

Provider 切换就像手机的双卡双待：

- **手动切换**：用户想换模型，改一行配置就行，不需要重启，对话历史不丢失
- **自动容灾**：一个模型挂了，jcode 自动切换到另一个，用户几乎无感知
- **智能选择**：不是随便切，而是根据当前任务的特点选择最合适的备用模型

### Provider 切换的产品价值

- 不锁定厂商：用户可以随时更换 AI 提供商
- 成本优化：普通任务用便宜模型，复杂任务用贵模型
- 高可用：一个模型挂了不影响工作
- 灵活的实验：用户可以对比不同模型的效果

## 流程六：上下文压缩

当对话太长时，AI 的上下文窗口会满，导致忘记前面的内容。上下文压缩自动解决这个问题。

### 涉及模块

| 模块 | 角色 |
|------|------|
| jcode-compaction-core | 压缩引擎，触发和执行压缩 |
| jcode-agent-runtime | 压缩后的上下文注入 |
| jcode-memory-types | 压缩结果存入 L2 记忆 |

### 端到端流程图

```
对话进行中，消息数量不断增长...
|
+-- 1. 触发检查 (jcode-compaction-core)
|   |  每次对话后检查:
|   |    Token 使用量 / 模型上下文上限 = 使用率
|   |
|   |  阈值设定:
|   |    使用率 < 60%: 无需压缩
|   |    使用率 60-80%: 轻度压缩 (压缩工具调用结果)
|   |    使用率 80-95%: 中度压缩 (压缩早期对话轮次)
|   |    使用率 > 95%: 深度压缩 (压缩所有非关键信息)
|   |
|   |  当前: 使用率 82% -> 触发中度压缩
|   |
+-- 2. 分层压缩策略
|   |
|   |  第 1 层: 压缩工具调用结果 (最不重要的先压)
|   |    原始: read_file 返回了 500 行代码
|   |    压缩后: 该文件包含 user_auth 模块，主要函数有 login/logout 等
|   |
|   |  第 2 层: 压缩对话轮次
|   |    原始: 3 轮失败的尝试 + 1 轮成功的修改
|   |    压缩后: 经过 3 次尝试后，最终通过修改数据库连接池配置解决了问题
|   |
|   |  第 3 层: 压缩用户消息 (最重要的最后压)
|   |    原始: 详细的 200 字需求描述
|   |    压缩后: 保留核心需求: 重构 user_auth，添加密码哈希和错误处理
|   |
+-- 3. 压缩执行
|   |  调用 LLM (使用轻量模型，节省成本):
|   |    请将以下对话压缩为结构化摘要，保留:
|   |     - 关键决策和原因
|   |     - 最终采用的方案
|   |     - 重要的错误及解决方案
|   |     - 用户的明确偏好
|   |     丢弃: 冗余的确认、重复的尝试、填充语
|   |
|   |  压缩结果:
|   |    原始: 15,000 token
|   |    压缩后: 800 token
|   |    压缩比: 约 18:1
|   |
+-- 4. 上下文重构
|   |  原始上下文:
|   |    [系统提示] [记忆] [消息1] [消息2] ... [消息50] [当前消息]
|   |
|   |  压缩后上下文:
|   |    [系统提示] [记忆] [压缩摘要] [消息41] ... [消息50] [当前消息]
|   |
|   |  释放空间: 约 12,000 token
|   |  使用率: 从 82% 降到 45%
|   |
+-- 5. 压缩记录保存
    |  压缩摘要存入 L2 记忆
    |  下次对话可以直接检索压缩摘要，无需重复压缩
```

### 白话解读

上下文压缩就像读书时的划重点：

- 一本 500 页的书，你不可能每次都从头读
- 第一次读时，你划出重点，下次只看重点就能回忆起来
- jcode 的上下文压缩就是这个逻辑——把长对话中真正重要的提取出来，丢掉嗯、好的、明白了这些废话

## 总结：jcode 的流程设计哲学

### 设计原则

1. **自动化优先**：记忆提取、上下文压缩、Provider 容灾，全部自动触发，用户无需手动操作
2. **断点续传**：Overnight 任务、Swarm 子任务、上下文压缩，都支持从中间状态恢复
3. **资源隔离**：每个 Agent 独立会话、独立上下文，互相不干扰
4. **优雅降级**：Provider 故障时自动切换，压缩阈值分层触发，工具失败时重试
5. **用户透明**：所有后台操作都有通知，用户可以随时查看、干预

### 与竞品的流程差异

| 流程 | jcode | Claude Code | Cursor | Copilot |
|------|-------|-------------|--------|---------|
| 单次对话 | Agent Loop (多轮迭代) | 单轮问答 | 代码补全 | 行内建议 |
| 多 Agent | Swarm 原生并行 | 不支持 | 不支持 | 不支持 |
| 记忆系统 | 三级自动记忆 | 不支持 | 不支持 | 不支持 |
| 上下文压缩 | 分层智能压缩 | 简单截断 | 不支持 | 不支持 |
| Provider 容灾 | 自动降级切换 | 不支持 | 有限 | 不支持 |
| 后台任务 | Overnight 模式 | 不支持 | 不支持 | 不支持 |
| 会话导入 | 4 种工具 | 不支持 | 不支持 | 不支持 |

### 一句话总结

jcode 的流程设计不是一个 AI 聊天框，而是一个 AI 操作系统——它管理着多个 Agent 的生命周期，自动处理记忆、压缩、容灾、升级，让用户只需要关注我要做什么，而不是怎么让 AI 做。
