## 一句话概括

**jcode 是一个用 Rust 写的高性能 AI 编码助手。** 它不像传统 IDE 插件那样"寄生"在编辑器里，而是一个独立的终端应用——你打开终端，输入 `jcode`，就能跟 AI 对话、让它帮你写代码、改 Bug、查文档。它背后支持 8 种以上的 AI 模型提供商（Claude、GPT、Gemini 等），内置 30+ 工具，可以同时开多个会话干活，还能让多个 AI Agent 像团队一样协作。

### 各层之间的依赖关系

```
第 1 层 (CLI入口) ──调用──▶ 第 2 层 (应用编排)
                                │
              ┌─────────────────┼─────────────────┐
              ▼                 ▼                  ▼
        第 3 层 (Agent)   第 4 层 (TUI)      第 5 层 (服务)
              │                 │                  │
              │                 ▼                  │
              │           显示会话列表 ◀───────────┘
              │                 │
              ▼                 ▼
        第 6 层 (工具)   第 7 层 (基础设施)
              │
              ▼
        第 5 层 (服务: 模糊搜索、PDF)
```

**核心原则：上层依赖下层，下层不知道上层在干什么。**

这意味着：
- 工具层不知道是谁在调用它——Agent 可以调用，Swarm 可以调用，甚至你可以手动调用
- 服务层（Provider、记忆、会话）只提供能力，不关心谁在用
- 基础设施层是"地基"，谁都可以用，但它不主动找任何人

## 第一层：CLI 入口层

### 这层是干什么的？

简单说，就是**用户敲命令的第一站**。你打开终端输入 `jcode`，操作系统加载 jcode 程序，第一行代码就从这里开始执行。

### 用大白话解释

把 jcode 想象成一个"多功能瑞士军刀"。你按不同的方式打开它，它就干不同的事：

- 你输入 `jcode`（不加参数）→ 打开 TUI 聊天界面
- 你输入 `jcode chat` → 进入命令行对话模式
- 你输入 `jcode serve` → 启动后台服务器（供其他窗口连接）
- 你输入 `jcode login --provider claude` → 登录 Claude 账号
- 你输入 `jcode --resume abc123` → 恢复之前的会话 abc123
- 你输入 `jcode swarm` → 启动多 Agent 协作模式

CLI 入口层就是那个"读心人"——它解析你的命令，搞清楚你想干什么，然后**把活儿派给对应的模块**。

### 技术细节（用大白话）

CLI 入口层用了一个叫 `clap` 的 Rust 库来做命令行解析。`clap` 就像是一个"命令翻译官"：

1. 你敲 `jcode --provider openai --model gpt-5.5`
2. `clap` 把它翻译成结构化数据：`{ provider: "openai", model: "gpt-5.5" }`
3. 入口层根据这些数据，决定启动哪个子系统

### 支持的命令一览

| 命令 | 干什么 | 典型场景 |
|------|--------|---------|
| `jcode`（无参数） | 启动 TUI 交互界面 | 日常编码对话 |
| `jcode chat` | 单次对话模式 | 脚本化调用、CI/CD 集成 |
| `jcode serve` | 启动后台服务器 | 多窗口共享同一个 jcode 进程 |
| `jcode login` | OAuth 登录 | 首次配置 AI 账号 |
| `jcode --resume <id>` | 恢复会话 | 继续昨天的活 |
| `jcode swarm` | 多 Agent 协作 | 复杂项目需要分工 |
| `jcode update` | 检查更新 | 升级到最新版 |
| `jcode setup-hotkey` | 配置全局快捷键 | macOS 上 Cmd+; 快速唤起 |

### 启动流程（从零到界面出现）

```
用户敲 jcode
    │
    ├─ 1. 配置内存分配器（jemalloc/glibc 调优）
    │     "让内存用得又快又省"
    │
    ├─ 2. 检查是否是快捷键唤起
    │     "如果是 Cmd+; 唤起的，走特殊逻辑"
    │
    ├─ 3. 初始化 Tokio 异步运行时
    │     "Rust 的异步引擎，相当于给程序装上多线程大脑"
    │
    ├─ 4. 解析命令行参数
    │     "搞懂用户想干什么"
    │
    ├─ 5. 初始化日志系统
    │     "开始记日志，方便排查问题"
    │
    ├─ 6. 注册外部 Provider 运行时
    │     "加载各种 AI 模型的驱动"
    │
    ├─ 7. 路由到对应子系统
    │     "把活儿派出去"
    │
    └─ 8. 启动 TUI 或 Server
          "用户看到界面"
```

**性能数据**：从敲命令到第一帧画面出现仅需 **14ms**（毫秒），比同类工具快 27~245 倍。

## 第二层：应用编排层

### 这层是干什么的？

这是整个 jcode 的**总管家**。如果把 jcode 比作一个公司，这层就是 CEO——它不亲自写代码，不亲自调 AI，但它**协调所有部门**，确保一切正常运转。

### 核心职责

| 职责 | 大白话解释 |
|------|-----------|
| **生命周期管理** | 谁来启动？谁来关闭？什么时候该重启？ |
| **会话调度** | 用户开了 3 个会话，怎么分配资源？ |
| **Agent 编排** | 什么时候叫 Agent 干活？怎么把结果传回界面？ |
| **通知分发** | 文件被改了、会话完成了、更新可用了——通知谁？ |
| **更新检查** | 新版本发布了吗？要不要自动更新？ |
| **遥测上报** | 用户用了多久？哪个功能最受欢迎？（匿名统计） |

### 为什么需要这一层？

你可能会问：为什么不让 CLI 入口层直接调用 Agent 层？非要加一个"中间人"？

答案很简单：**解耦（让各部分独立变化）**。

举个例子：假设没有应用编排层，CLI 入口层直接调用 Agent 层。那么每次你想加一个新功能（比如"在会话结束时自动保存记忆"），你就得改 CLI 入口层的代码——但 CLI 入口层本来只负责"解析命令"，不应该管"记忆保存"。这就像让前台接待员同时管财务——虽然也能干，但职责混乱，一出问题很难排查。

有了应用编排层：
- **CLI 入口层**只管"用户想干什么"
- **应用编排层**管"谁来干、什么时候干、干完怎么通知"
- **Agent 层**只管"跟 AI 对话、执行工具"

各司其职，互不干扰。

### 启动时做了什么？

应用编排层在启动时会做一系列"初始化"工作，相当于"公司开张前的准备"：

1. **启动性能计时器** — 记录每个启动步骤花了多少时间，用于性能优化
2. **安装崩溃处理** — 万一程序崩了，至少能优雅退出，不乱丢数据
3. **初始化日志** — 开始记日志
4. **清理旧日志/会话备份** — 后台线程自动清理，不阻塞启动
5. **注册配置变更回调** — 用户改了配置，自动刷新认证状态
6. **注册 API Key 后备解析器** — 从环境变量/其他 CLI 工具里自动找 API Key
7. **注册外部 Provider** — 加载 Gemini、Cursor、Copilot 等运行时
8. **注册权限通知分发器** — 工具需要权限时，通过这个通道弹窗询问
9. **注册记忆条目提供者** — 技能（Skills）自动转化为记忆条目
10. **注册 Server 生成器** — TUI 可以请求启动/重启后台服务器

这些步骤看着多，但 jcode 设计得很巧妙——**很多工作是并行做的，不互相等待**，所以启动速度极快。

## 第三层：Agent 层

### 这层是干什么的？

这是 jcode 的**灵魂**。Agent 层的核心工作就是：

> 用户说一句话 → Agent 理解意图 → 调 AI 模型 → AI 说"我需要执行这个工具" → Agent 执行工具 → 把结果给 AI → AI 再思考 → 反复循环 → 最终输出答案

这个循环在业界叫 **Agent Loop（Agent 循环）**。

```
│  │                 │  │                 │  │             │ │
│  │ "单个 Agent 的  │  │ "多个 Agent 的  │  │ "复杂任务   │ │
│  │  思考-执行循环" │  │  协作与通信"    │  │  自动拆解"  │ │
│  └────────┬────────┘  └────────┬────────┘  └──────┬──────┘ │
```

### 3.1 Agent 运行时：思考-执行循环

这是最核心的模块。它的工作流程如下：

```
┌──────────────────────────────────────────────────────────┐
│                    Agent Loop                             │
│                                                          │
│  用户: "帮我把这个 Bug 修了"                              │
│       │                                                  │
│       ▼                                                  │
│  ┌─────────┐    ┌──────────┐    ┌──────────┐            │
│  │ 1. 读取  │───▶│ 2. 调用   │───▶│ 3. AI 返回│           │
│  │   记忆   │    │   AI 模型 │    │   思考结果│           │
│  └─────────┘    └──────────┘    └────┬─────┘            │
│                                      │                   │
│                    ┌─────────────────┤                   │
│                    ▼                 ▼                   │
│            ┌──────────┐      ┌──────────┐               │
│            │ AI 说:    │      │ AI 说:    │               │
│            │ "我直接   │      │ "我需要   │               │
│            │  回答你"  │      │  执行工具"│               │
│            └────┬─────┘      └────┬─────┘               │
│                 │                 │                      │
│                 ▼                 ▼                      │
│            ┌──────────┐      ┌──────────┐               │
│            │ 4. 输出   │      │ 4. 执行   │               │
│            │   答案    │      │   工具    │               │
│            └──────────┘      └────┬─────┘               │
│                                   │                      │
│                                   ▼                      │
│                            ┌──────────┐                  │
│                            │ 5. 工具   │                  │
│                            │   返回结果│                  │
│                            └────┬─────┘                  │
│                                 │                        │
│                                 ▼                        │
│                            ┌──────────┐                  │
│                            │ 6. 把结果│                  │
│                            │   给 AI  │────── 循环 ──────┘
│                            └──────────┘   (回到步骤 2)
│                                                          │
│  循环什么时候结束？                                       │
│  - AI 说"我完成了"（不再需要工具）                        │
│  - 达到最大循环次数（防止无限循环）                       │
│  - 用户手动中断                                          │
└──────────────────────────────────────────────────────────┘
```

**用大白话描述**：

想象你有一个非常聪明的助手，但他在一个空房间里，只有一台电脑。你给他一个任务，他不能直接帮你做——他需要：
1. 先回忆一下之前有没有做过类似的事（读记忆）
2. 想一想要怎么做（调 AI 模型）
3. 如果需要查文件，就"打开文件"（执行工具）
4. 如果需要跑代码，就"运行命令"（执行工具）
5. 把工具的结果拿回来，再想一想（回到步骤 2）
6. 直到他觉得"做完了"，给你最终答案

### 3.2 Swarm 群协调：多 Agent 协作

这是 jcode 的**杀手级功能**。传统 AI 编码工具只有一个 Agent，jcode 可以同时跑多个。

**场景举例**：

你想做一个网站，包含前端页面、后端 API、数据库设计。传统方式只能一个一个来，Agent A 做完前端再做后端。但 jcode 可以这样：

```
                    主 Agent（协调者）
                    "做一个完整的网站"
                          │
            ┌─────────────┼─────────────┐
            ▼             ▼             ▼
      子 Agent A      子 Agent B      子 Agent C
      "做前端页面"    "做后端 API"    "设计数据库"
            │             │             │
            └─────────────┼─────────────┘
                          │
                    自动合并结果
```

**Swarm 的智能之处**：

1. **自动冲突检测**：Agent A 改了文件 X，Agent B 也读了文件 X → 服务器通知 Agent B "文件变了，你注意一下"
2. **Agent 间通信**：Agent 可以互相发消息——"嘿，我把 API 接口改了一下，你前端记得适配"
3. **自动管理**：Agent 的创建、通信、完成状态追踪，全部自动

### 3.3 计划引擎：智能任务拆解

计划引擎是"大脑的大脑"。当你给一个复杂任务时，它自动把任务拆成小步骤。

**举例**：

用户说："帮我把这个项目从 JavaScript 迁移到 TypeScript"

计划引擎会自动拆解：
```
1. 分析项目结构，列出所有 .js 文件
2. 安装 TypeScript 依赖
3. 创建 tsconfig.json
4. 逐个文件: 重命名 .js → .ts，修复类型错误
5. 运行测试，确保功能正常
6. 更新构建配置
```

然后计划引擎把这些步骤分配给 Swarm 并行执行，大大加快速度。

### 上下文折叠

Agent 跟 AI 对话时，每次对话都有"上下文"——也就是 AI 能"看到"的历史消息。但 AI 模型有上下文长度限制（比如 Claude 能看 20 万 token，约等于一本中篇小说）。

当对话太长时，Agent 需要做**上下文折叠**：把旧的、不重要的对话内容压缩成摘要，腾出空间给新内容。这就像你看完一章书后，在脑子里记一个"本章讲了什么"，而不是背下每个字。

jcode 的上下文折叠做得非常智能——它知道哪些信息是"关键信息"（比如用户的核心需求），哪些是"过程信息"（比如中间某次失败的尝试），折叠时保留前者、压缩后者。

## 第四层：TUI 界面层

### 这层是干什么的？

**TUI = Terminal User Interface（终端用户界面）**。就是你在终端里看到的那个界面。

jcode 不用浏览器、不用 Electron，直接在你的终端里画出漂亮的界面——包括聊天框、侧边栏、Mermaid 图表、代码高亮、Diff 对比等。

### TUI 层包含两个核心模块

```
┌─────────────────────────────────────────────────────────────┐
│                      TUI 界面层                              │
│                                                             │
│  ┌──────────────────────────┐  ┌──────────────────────────┐ │
│  │       tui_core           │  │        desktop           │ │
│  │       终端 UI 核心        │  │       桌面应用            │ │
```

### 用大白话解释桌面应用

jcode 虽然是终端应用，但它也提供了桌面端体验（主要是 macOS）：

- **菜单栏图标**：在 macOS 顶部菜单栏显示一个小图标，点击可以快速操作
- **全局快捷键**：按 `Cmd+;` 在任何地方唤起 jcode
- **剪贴板集成**：AI 可以直接读取/写入你的剪贴板
- **截图**：AI 可以截取屏幕，这在"看图写代码"场景下非常有用
- **系统通知**：任务完成时发送 macOS 通知

### 为什么终端 UI 能做这么漂亮？

jcode 使用了两个关键 Rust 库：

- **ratatui**：一个终端 UI 框架，提供了"在终端里画窗口、按钮、列表"的能力。你可以把它理解为"终端里的 HTML+CSS"
- **crossterm**：一个跨平台终端控制库，处理键盘输入、鼠标事件、颜色、光标等底层操作

加上 jcode 自己的大量定制渲染代码（15+ 个 TUI 相关的 crate），最终实现了在纯文本终端里渲染出接近 GUI 的体验。

### 渲染性能

jcode 的渲染速度超过 **1000 FPS**（帧每秒）——你的显示器根本跟不上。这意味着：
- 不会出现闪烁，不会出现撕裂
- 滚动丝滑（自研滚动实现）
- 输入延迟极低（首帧 14ms，可输入 48ms）

### 5.1 多 Provider 体系：AI 模型的"万能插座"

jcode 支持连接 8 种以上的 AI 模型提供商，就像一个"万能插座"——不管你用的是哪个 AI 服务，插上就能用。

| Provider | 接入方式 | 说明 |
|----------|---------|------|
| **Anthropic (Claude)** | OAuth 登录 | 最常用的接入方式，用你的 Claude 订阅 |
| **OpenAI (ChatGPT/Codex)** | OAuth 登录 | 用你的 ChatGPT 订阅 |
| **Google Gemini** | OAuth 登录 | 用你的 Google 账号 |
| **GitHub Copilot** | OAuth 登录 | 用你的 GitHub 订阅 |
| **OpenRouter** | API Key | 聚合平台，一个 Key 访问多种模型 |
| **AWS Bedrock** | IAM 凭证 | 企业级 AWS 用户 |
| **Cursor** | 本地凭证 | 复用 Cursor 编辑器的登录状态 |
| **Antigravity** | OAuth 登录 | 另一个 AI 编码平台 |
| **Azure OpenAI** | API Key | 微软 Azure 的企业用户 |
| **自定义 OpenAI 兼容** | API Key + URL | 任何兼容 OpenAI API 的服务（Ollama、LM Studio 等） |

**Provider 的设计亮点**：

1. **自动检测**：如果你已经登录了 Claude Desktop 或 Cursor，jcode 能自动找到你的登录凭证，不用重复登录
2. **热切换**：在会话中可以随时切换模型——"这个简单问题用便宜的模型，那个复杂问题用贵的模型"
3. **故障转移**：一个 Provider 挂了，可以自动切换到备用的
4. **OAuth 流程**：浏览器自动打开登录页面，授权后自动回调，全程不用手动复制粘贴 Key

### 5.2 记忆系统：让 AI 记住你

这是 jcode 最让人惊艳的功能之一。传统的 AI 编码工具是"金鱼记忆"——每次新会话都是白纸一张，不记得你之前说过什么、做过什么。

jcode 的记忆系统就像一个**真正的同事**——它会记住你的偏好、项目的背景、之前的决策，越用越聪明。

**记忆系统的工作原理**（用大白话）：

```
对话进行中...
    │
    ▼
┌─────────────────────────────────────────────┐
│  1. 语义漂移检测                            │
│  "对话话题是不是变了？变化够大吗？"           │
│  如果变了 → 触发记忆提取                     │
└────────────────────┬────────────────────────┘
                     │
                     ▼
┌─────────────────────────────────────────────┐
│  2. 记忆提取（Memory SideAgent）             │
│  一个后台 Agent 悄悄分析对话，提取关键信息：   │
│  - "用户喜欢用 Rust，不喜欢 Python"          │
│  - "这个项目数据库用的是 PostgreSQL"          │
│  - "上次重构时决定用微服务架构"               │
└────────────────────┬────────────────────────┘
                     │
                     ▼
┌─────────────────────────────────────────────┐
│  3. 向量嵌入（Embedding）                    │
│  把文字记忆转成数学向量（一串数字）            │
│  相似的记忆，向量也相似                       │
│  "向量嵌入"就像给每段记忆打上 GPS 坐标         │
└────────────────────┬────────────────────────┘
                     │
                     ▼
┌─────────────────────────────────────────────┐
│  4. 记忆检索                                 │
│  新对话开始时，用当前话题的向量去匹配           │
│  找到最相关的记忆，自动注入到对话中             │
│  "你说的这个话题，我之前记得..."              │
└─────────────────────────────────────────────┘
```

**记忆的三种使用方式**：

| 方式 | 说明 | 举例 |
|------|------|------|
| **被动召回** | 自动检索相关记忆，不需要用户操作 | 你提到"数据库"，自动召回"上次用的是 PostgreSQL" |
| **主动工具** | Agent 可以主动调用记忆工具搜索/存储 | `memory_search("数据库迁移方案")` |
| **会话搜索** | 搜索历史会话内容（传统 RAG） | 搜索"上次那个 Bug 是怎么修的" |

**记忆的维护**：

jcode 在后台（Ambient 模式）会定期做记忆维护：
- **去重**：删掉重复的记忆
- **合并**：把相关的记忆整理成一条
- **过期检测**：标记过时的信息
- **冲突检测**：发现矛盾的记忆，提醒用户

### 5.3 会话管理：多任务并行

jcode 支持同时开多个会话，就像浏览器可以开多个标签页。每个会话是**完全隔离**的——会话 1 的对话不会"污染"会话 2 的上下文。但共享记忆是**跨会话共享**的，所以你在会话 1 里学到的知识，会话 2 也能用上。

**会话管理核心能力**：创建/恢复、历史浏览、导入导出（从 Claude Code、Codex 等）、自动备份。

### 5.4 上下文压缩

当对话越来越长，就需要"压缩"——把不重要的内容缩成摘要，保留关键信息。

jcode 的上下文压缩很智能：
- **保留关键决策**：用户说"用 PostgreSQL"——这个不能丢
- **压缩中间过程**：Agent 尝试了 3 种方案，前 2 种失败了——压缩成"尝试了 2 种方案后选择第 3 种"
- **保留错误教训**：某些操作导致了问题——保留这个教训，避免重蹈覆辙

### 5.5 向量嵌入

这是记忆系统的"引擎"。jcode 在本地运行一个 AI 模型（ONNX 格式，MiniLM），把文字转成数学向量。

**为什么要在本地跑？**
- **隐私**：你的数据不出你的电脑
- **速度**：不需要网络请求，毫秒级响应
- **成本**：不需要额外付费

**性能数据**：嵌入模型本地运行约 87MB 内存，每次嵌入约需几十毫秒。

```
每个工具 = {
    名称: "read_file",
    描述: "读取文件内容",
    参数: { path: "文件路径", offset: "起始行", limit: "行数" },

```

### 工具安全机制

jcode 对工具有严格的安全控制：

1. **权限系统**：危险操作（如执行 Shell 命令）需要用户确认
2. **工具白名单**：可以通过 `--tools` 参数限制 AI 能使用哪些工具
3. **工具配置档**：预设"完整工具集"、"轻量工具集"、"无工具"三档
4. **工作目录隔离**：AI 只能操作指定目录下的文件

### 模糊搜索 (fuzzy)

这是一个独立的子模块，但被工具层广泛使用。它的作用是在大量候选项中快速找到匹配项。你输入 `mdl`，它就能匹配到 `model`、`middleware`、`modal` 等。这在搜索文件、切换会话、选择模型时非常有用。jcode 对模糊搜索做了极致优化（opt-level=3），确保每次按键的搜索都在毫秒级完成。

## 架构决策记录



### ADR-003: 为什么分成 70+ 个 Crate？

看到 jcode 的源码目录，你可能会被 `crates/` 下 70+ 个子目录吓到。这是故意的。

**核心原因：编译速度**

Rust 的编译单元是 crate。如果把所有代码放在一个 crate 里，改一行代码就要重新编译整个项目（可能 5-10 分钟）。但如果拆成 70 个小 crate，改一行代码只需要重新编译那个小 crate（可能 10-30 秒）。

**Crate 拆分原则**：

```
jcode-base          ← 基础类型和工具（改动最少）
    ↑
jcode-app-core      ← 应用核心逻辑（偶尔改动）
    ↑
jcode-tui           ← TUI 界面（经常改动）
    ↑
jcode (root)        ← CLI 入口（改动频繁）
```

Provider 运行时（gemini、cursor、copilot 等）被放在独立的 crate 里，这样改一个 Provider 不会导致整个应用重编译。

**影响**：开发体验显著提升，编译等待时间从"去喝杯咖啡"变成"刷一下手机"。但代价是 crate 之间的依赖关系需要精心管理，否则会出现循环依赖。

### ADR-004: 为什么需要 Swarm 而不是单 Agent 多步骤？

| 因素 | Swarm（多 Agent 并行） | 单 Agent 多步骤 |
|------|----------------------|----------------|
| 速度 | 并行执行，快 | 串行执行，慢 |
| 复杂性 | 需要冲突检测和通信 | 简单，不需要协调 |
| 适用场景 | 大型项目、多模块 | 小型任务、单文件 |

**决策**：引入 Swarm 虽然增加了复杂度，但对于实际项目来说，并行执行带来的效率提升远超协调成本。

**影响**：Swarm 是 jcode 的差异化功能之一。它让 jcode 从"AI 助手"升级为"AI 开发团队"。

### ADR-005: 为什么本地运行嵌入模型而不是调用云端 API？

| 因素 | 本地 ONNX 模型 | 云端 Embedding API |
|------|---------------|-------------------|
| 隐私 | ✅ 数据不出电脑 | ❌ 数据发送到云端 |
| 速度 | 毫秒级（无网络延迟） | 几十到几百毫秒 |
| 成本 | 免费（多占 87MB 内存） | 按 Token 计费 |
| 离线可用 | ✅ | ❌ |

**决策**：记忆系统是高频操作，如果每次都调云端 API，延迟和成本都不可接受。本地运行虽然多占 87MB 内存，但换来了隐私、速度和零成本。

**影响**：jcode 在启动时会加载一个约 87MB 的 ONNX 模型到内存中。这是 jcode 内存占用从 27.8MB（embedding 关闭）到 167.1MB（embedding 开启）的主要原因。但即使如此，仍然远低于同类工具。

### ADR-006: 为什么 Provider 设计成插件式？

**决策**：每个 AI 模型提供商（Anthropic、OpenAI、Gemini 等）都是一个独立的 crate，通过统一的接口注册到 Provider 注册表中。

**好处**：添加新 Provider 不需要改核心代码；一个 Provider 的 Bug 不会影响其他 Provider；用户可以自由选择 Provider，甚至同时配置多个；社区可以贡献第三方 Provider。

**影响**：Provider 接口需要精心设计，确保所有 Provider 的行为一致。jcode 通过 Provider Doctor 工具来自动诊断 Provider 配置问题。

### ADR-007: 为什么采用上下文折叠而不是无限扩展上下文？

| 因素 | 上下文折叠 | 无限扩展上下文 |
|------|-----------|---------------|
| Token 成本 | 低（折叠后占空间小） | 高（每次请求都带完整历史） |
| 响应速度 | 快（上下文小） | 慢（上下文大） |
| 模型限制 | 兼容所有模型 | 需要模型支持超长上下文 |

**决策**：采用智能上下文折叠，在保留关键信息的同时压缩历史。这是工程上的务实选择——不是所有模型都支持超长上下文，而且即使支持，Token 成本也太高。

**影响**：折叠策略需要不断调优。折叠太激进会丢失重要信息，折叠太保守又起不到压缩效果。jcode 通过语义分析来识别"关键信息"，在这方面持续迭代。

## 性能与资源设计

### 性能数据总览

| 指标 | jcode | 行业平均 | 领先倍数 |
|------|-------|---------|---------|
| 启动速度（首帧） | **14.0 ms** | 500-3500 ms | 27x - 245x |
| 可输入时间 | **48.7 ms** | 380-3500 ms | 7x - 72x |
| 1 会话内存 | **27.8 MB** | 140-386 MB | 5x - 14x |
| 10 会话内存 | **117 MB** | 334-3237 MB | 3x - 28x |
| 每会话增量 | **~10 MB** | 21-318 MB | 2x - 32x |
| 渲染帧率 | **1000+ FPS** | 30-60 FPS | 16x - 33x |

### 为什么 jcode 这么快？

**1. Rust 语言本身**

Rust 是系统级编程语言，编译成原生机器码，没有虚拟机、没有垃圾回收器（GC）。这意味着：
- 启动时不需要加载运行时环境
- 运行时不需要 GC 暂停（"stop the world"）
- 内存布局紧凑，CPU 缓存友好

**2. 异步运行时 (Tokio)**

jcode 使用 Tokio 作为异步运行时。Tokio 是 Rust 生态中最成熟的异步框架，可以高效地处理数千个并发任务，而只使用少量线程。

**3. 内存分配器调优**

jcode 对内存分配器做了精细调优：
- 使用 jemalloc（默认）或 glibc malloc
- 配置了 arena 数量、脏页回收策略、mmap 阈值
- 确保大块内存（如 ONNX 模型）用完后立即归还给操作系统

**4. 关键路径优化**

jcode 对性能敏感的关键路径做了专门优化：
- 模糊搜索：opt-level=3，使用 SIMD 加速
- 文本渲染：cosmic-text 等库 opt-level=3
- 嵌入模型：tract ONNX 推理 opt-level=3
- 动画计算：jcode-tui-anim opt-level=3
- 图片处理：png/jpeg 解码 opt-level=3

**5. 增量编译**

虽然编译速度不是运行时性能，但 jcode 的 70+ crate 拆分让开发迭代更快，团队能更快地优化性能。

### 为什么 jcode 这么省内存？

**1. 无浏览器内核**

jcode 是纯终端应用，不需要嵌入 Chromium 或 WebKit。这意味着直接省掉了 200-500MB 的内存开销。

**2. 会话共享进程**

jcode 的所有会话共享同一个进程，而不是每个会话启动一个进程。这意味着：
- 代码段（text segment）共享：一份，多人用
- 连接池复用：HTTP 连接、WebSocket 连接共享
- 内存池复用：分配器层面共享内存池

**3. 原生二进制**

Rust 编译成单个二进制文件，没有解释器或虚拟机的内存开销。

**4. 精确控制**

Rust 的所有权系统让开发者精确控制内存的分配和释放。没有垃圾回收器意味着不会有"内存已经不用了但 GC 还没回收"的情况。

## 总结

jcode 的架构设计遵循了**分层解耦、性能优先、本地优先**三大原则：

1. **分层解耦**：7 层架构，每层职责清晰，上层依赖下层，互不干扰
2. **性能优先**：Rust 原生二进制 + 异步运行时 + 精细内存管理 + 关键路径优化，实现 14ms 启动、<50ms 可交互
3. **本地优先**：记忆系统、嵌入模型在本地运行，保护隐私，降低延迟，零成本

对于产品经理和运营来说，理解这些架构决策有助于：
- 向用户解释 jcode 为什么快、为什么省资源
- 评估新功能的技术可行性（比如能不能加一个新 Provider？——能，因为 Provider 是插件式的）
- 规划产品路线图（比如能不能做 VS Code 插件？——需要额外评估，但核心 Agent 层可以复用）
