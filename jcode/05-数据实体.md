## 为什么需要理解数据实体

如果你只把 jcode 当成一个"问 AI 问题、AI 回答"的聊天框，那你就错过了它 80% 的能力。jcode 真正的价值在于：**它会记住你、理解你、适应你**。而这一切，靠的就是它精心设计的数据模型。

理解数据实体，你能回答以下问题：

- 关掉终端再打开，jcode 怎么知道上次聊到哪了？
- 三天前你告诉 jcode"用 pnpm 别用 npm"，它怎么记住的？
- 换了 Claude 换 GPT，为什么对话不中断、记忆不丢失？
- 一个重构任务失败了，怎么从失败点继续而不是从头开始？
- 多个 Agent 同时干活，怎么保证不互相踩脚？

所有这些问题，答案都藏在数据实体里。

本文档用产品经理和运营能听懂的大白话，逐一拆解 jcode 的每一个数据实体——它存什么、怎么用、从生到死经历了什么生命周期。

### 关系速查表

| 关系 | 类型 | 含义 |
|------|------|------|
| 用户 → 会话 | 1 对多 | 一个用户可以有多个会话（不同项目、不同任务） |
| 用户 → 记忆 | 1 对 1 | 每个用户有一套长期记忆（L3） |
| 会话 → 消息 | 1 对多 | 一个会话包含多条对话消息 |
| 会话 → 计划 | 1 对多 | 一个会话可以有多个任务计划 |
| 会话 → 提供商 | 多对 1 | 多个会话可以用同一个 AI 模型提供商 |

| 子代理 → 工具 | 多对多 | 每个子代理可以调用多个工具 |
| 配置 → 提供商/工具/UI | 1 对多 | 一份配置影响多个组件的运行参数 |
| 会话 → 配置 | 多对 1 | 多个会话可以共享同一份配置 |

### 实体分类

jcode 的实体可以分为三个层次：

**核心层（业务核心）**：Session、Message、Memory、Provider、Tool、Plan、Config

**支撑层（辅助运行）**：Embedding、Auth、Gateway、Build、Telemetry

**高级层（特定功能）**：Batch、Background、Notification、Import、Desktop

本文档重点讲解核心层的 7 个实体，支撑层和高级层在最后做简要说明。

## 核心实体一：Session（会话）

### 一句话概括

**Session 是 jcode 的一等公民。** 如果把 jcode 比作一个操作系统，Session 就是里面的"进程"——每个 Session 是一个独立的运行单元，有自己的上下文、自己的记忆、自己的生命周期。

### 业务含义

Session 代表"一次 AI 编码对话的完整记录"。你打开 jcode，跟 AI 聊了一个小时，让它帮你重构了一个模块、修了三个 Bug、写了五个测试——这整个过程就是一个 Session。

一个 Session 不只是"聊天记录"，它包含：

- 你跟 AI 说了什么（消息列表）
- AI 做了什么（工具调用记录）
- 当时用了哪个模型（Provider 配置）
- 项目文件在哪（工作目录）
- 启用了哪些工具（工具开关）
- 对话进行到哪了（状态、上下文窗口大小）

### 核心字段

| 字段名 | 类型 | 业务含义 | 大白话解释 |
|--------|------|---------|-----------|
| session_id | 唯一标识 | 会话的唯一 ID | 就像身份证号，全局唯一，用来恢复、分享、引用 |
| title | 文本 | 会话标题 | 自动生成（如"重构 user_auth 模块"），也可以手动改 |
| messages | 列表 | 消息历史 | 完整对话记录，从第一句到最新一句 |
| provider | 枚举 | 当前使用的 AI 模型提供商 | 比如 Anthropic、OpenAI、DeepSeek |
| model | 文本 | 当前使用的具体模型 | 比如 claude-sonnet-4-20250514、gpt-4o |
| workspace | 路径 | 工作目录 | 项目代码在磁盘上的位置 |
| context_window | 数值 | 上下文窗口大小（token 数） | 当前 AI 能"看到"多少历史消息 |
| tools_enabled | 列表 | 启用的工具清单 | 这个会话里哪些工具可用 |
| status | 枚举 | 会话状态 | 进行中 / 已暂停 / 已完成 / 已归档 |
| created_at | 时间戳 | 创建时间 | 什么时候开的这个会话 |
| updated_at | 时间戳 | 最后活跃时间 | 最后一次发消息或收到回复的时间 |
| metadata | 键值对 | 扩展元数据 | 放一些自定义标签、备注 |

### 生命周期详解

**1. 创建（CREATED）**

用户在终端输入 `jcode`，或在一个已有会话中输入第一条消息时，Session 被创建。这时候系统会：
- 分配一个全局唯一的 session_id
- 记录当前工作目录（workspace）
- 加载默认或用户指定的 Provider 和模型
- 自动生成一个标题占位（后续根据第一条消息优化）

**2. 活跃（ACTIVE）**

这是 Session 的主要状态。用户跟 AI 对话、AI 调用工具，所有消息都追加到 messages 列表中。此时：
- 每一条消息都实时写入 SQLite 数据库，不怕断电
- 上下文窗口逐渐被填满
- 用户在 TUI 中看到流式输出

**3. 压缩（COMPACTING → COMPACTED）**

当对话太长，消息的 token 总数接近模型的上下文上限时，jcode 自动触发上下文压缩。压缩的过程是：
- 把早期对话内容喂给 AI，让 AI 生成一个"摘要"
- 用摘要替换原来的详细消息，腾出空间给新消息
- 压缩后的 session 回到 ACTIVE 状态，继续对话

这个机制保证了对话可以"无限长"——理论上可以聊三天三夜，AI 也不会"忘记"重要信息。

**4. 暂停（PAUSED）**

用户关闭终端、电脑休眠、或者显式输入暂停命令时，Session 进入暂停状态。此时：
- 所有消息和状态都已经持久化到 SQLite
- Provider 连接被释放，不再占用网络资源
- 下次用户打开 jcode，自动恢复

**5. 恢复（RESUMED）**

从 PAUSED 状态回到 ACTIVE。恢复时：
- 从 SQLite 加载完整的消息列表
- 重新建立与 Provider 的连接
- 触发记忆检索，注入 L2/L3 记忆
- 用户看到的就是上次离开时的状态

**6. 完成（COMPLETED）**

Agent 完成任务（AI 说"我完成了"，不再需要调用工具），或者用户手动标记完成。完成后：
- 自动触发记忆提取——把本次会话的关键信息写入 L2/L3
- 生成会话摘要
- 可以导出、分享

**7. 失败（FAILED → RETRYING）**

如果 Agent 执行过程中遇到不可恢复的错误（比如网络断了且重试了多次都没恢复），Session 进入 FAILED 状态。用户可以：
- 查看失败原因（日志会详细记录是哪一步出错）
- 选择重试：系统从最近的检查点恢复，继续执行
- 或者放弃，归档

**8. 归档（ARCHIVED）**

长期不活跃的会话（默认 30 天），自动移到归档存储。归档后：
- 消息内容被压缩，只保留摘要
- 不占用活跃会话列表空间
- 随时可以手动恢复

### 会话的"分身"能力

jcode 支持会话分叉（Fork）——从一个会话的某个中间状态，复制出一个新会话，尝试不同的方向。

举个例子：你在 Session A 中让 AI 修复一个 Bug，AI 在第 5 轮给出了两种方案。你选择分叉：
- Session A 继续走方案一
- Session B（分叉出来的）走方案二
- 两个会话互不干扰，各自发展

分叉后，两个会话共享"分叉点"之前的历史消息，但之后的修改各自独立。这让你可以并行尝试多种方案，最后选最好的那个。

## 核心实体二：Message（消息）

### 一句话概括

**Message 是对话的最小原子。** 每一轮交互中，用户说的一句话、AI 回复的一段文字、AI 调用的一次工具、工具返回的结果，都是一条 Message。

### 业务含义

如果把 Session 比作一本书，Message 就是书里的每一页。它记录了对话的完整历史——谁说了什么、什么时候说的、AI 想了什么、调用了什么工具。

Message 不是简单的"文本"，它是一段结构化的数据，包含角色、内容、时间戳、关联关系等。

### 消息类型

jcode 的消息分为四种角色，每种角色的含义和内容格式都不同：

| 角色 | 标识 | 大白话解释 | 谁产生的 | 内容格式 |
|------|------|-----------|---------|---------|
| 用户消息 | user | 你在聊天框里输入的内容 | 用户 | 纯文本，可能包含附件引用 |
| AI 回复 | assistant | AI 给你的回答 | AI 模型 | 文本 + 可选的工具调用请求 |
| 工具结果 | tool_result | AI 调用了工具，工具返回的结果 | jcode 工具系统 | 结构化数据（文件内容、命令输出等） |
| 系统消息 | system | jcode 内部的通知、提示 | jcode 系统 | 文本（提示词、压缩摘要等） |

### 核心字段

| 字段名 | 类型 | 业务含义 | 大白话解释 |
|--------|------|---------|-----------|
| message_id | 唯一标识 | 消息的唯一 ID | 用于引用、跳转、关联 |
| role | 枚举 | 消息角色 | user / assistant / tool_result / system |
| content | 文本 | 消息正文 | 用户输入的文字，或 AI 回复的文字 |
| tool_calls | 列表 | 工具调用请求 | 只有 assistant 消息有，AI 说"请帮我执行这个工具" |
| tool_call_id | 标识 | 工具调用 ID | 只有 tool_result 消息有，对应哪次工具调用 |
| timestamp | 时间戳 | 消息产生时间 | 精确到毫秒 |
| token_count | 数值 | 估算的 token 数 | 用于计算上下文窗口用量和费用 |
| parent_message_id | 标识 | 引用的消息 | 用于分叉、重试场景，标记"这条消息是回复谁的" |
| metadata | 键值对 | 扩展元数据 | 比如消息的渲染偏好、是否被折叠 |

### 消息与工具调用的关系

这是理解 jcode 数据模型的关键。一次 AI 调用工具的过程，在 Message 层面是这样记录的：

```
1. 用户 Message (user): "帮我读一下 user_auth.rs"

2. AI Message (assistant): "好的，让我来读取文件"
   └── tool_calls: [
         { tool_call_id: "abc123", name: "read_file", params: { path: "user_auth.rs" } }
       ]

3. 工具结果 Message (tool_result):
   └── tool_call_id: "abc123"
   └── content: "（文件 user_auth.rs 的完整内容，200 行代码）"

4. AI Message (assistant): "我看到了，这个文件里有一个 login 函数..."
   └── tool_calls: [
         { tool_call_id: "def456", name: "write_file", params: { ... } }
       ]

5. 工具结果 Message (tool_result):
   └── tool_call_id: "def456"
   └── content: "写入成功"

6. AI Message (assistant): "重构完成！以下是变更摘要..."
   （这次没有 tool_calls，说明 AI 认为任务完成了）
```

通过 tool_call_id 把 AI 的"请求"和工具的"结果"关联起来，形成一条完整的调用链。

### 消息的分层价值

Message 不只是"聊天记录"，它对 jcode 的不同功能有不同的价值：

| 功能 | 怎么用 Message |
|------|---------------|
| 上下文窗口 | 把最近的 N 条 Message 发给 AI 模型，让它"记住"聊天历史 |
| 记忆提取 | 对话结束后，分析 Message 内容，提取关键信息存入记忆 |
| 会话恢复 | 从 SQLite 加载 Message 列表，重建对话状态 |
| 会话导出 | 把 Message 列表导出为 JSON/Markdown，方便分享 |
| 分叉重试 | 从某条 Message 开始分叉，尝试不同的回复路径 |
| 用量统计 | 累加所有 Message 的 token_count，算费用 |

### 消息的生命周期

一条 Message 从产生到被清理，经历以下阶段：

1. **产生**：用户输入、AI 回复、或工具执行完成时创建
2. **存储**：立即写入 SQLite，即使程序崩溃也不会丢
3. **渲染**：TUI 界面根据 Message 的 role 和 content 渲染（用户消息左对齐，AI 消息右对齐，代码块高亮）
4. **参与上下文**：被包含在发给 AI 的 Prompt 中
5. **压缩**：当上下文超限时，旧 Message 被压缩为摘要（system 消息），原始 Message 被标记为"已压缩"
6. **归档**：会话归档后，Message 也被压缩存储

## 核心实体三：Memory（记忆系统）

### 一句话概括

**Memory 是 jcode 的"长期记忆"**——它让 jcode 在对话结束后不"失忆"，下次对话时自动回忆起之前聊过的内容。

### 业务含义

普通的 AI 聊天工具是"金鱼记忆"——每次对话都是独立的，关掉就忘了。jcode 不同，它有三层记忆系统，模仿人脑的工作方式：

- **L1（工作记忆）**：当前对话的完整记录，就像你在脑子里记住的"刚才在聊什么"
- **L2（短期记忆）**：从对话中提取的关键信息摘要，就像你每天写的"工作日志"
- **L3（长期记忆）**：跨所有会话的持久偏好和知识，就像你的"工作习惯"和"技术栈偏好"

### 三级记忆架构

```
┌─────────────────────────────────────────────────────────────────┐
│                        记忆系统全景                              │
│                                                                 │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  L1：工作记忆（Working Memory）                          │   │
│  │  ┌─────────────────────────────────────────────────┐    │   │
│  │  │ 原始事件流，当前会话的完整对话记录                  │    │   │
│  │  │ 存储：当前 Session 的 messages 列表               │    │   │
│  │  │ 检索：直接读取                                     │    │   │
│  │  │ 生命周期：会话期间                                  │    │   │
│  │  │ 容量：取决于模型上下文窗口（通常 20 万 token）       │    │   │
│  │  └─────────────────────────────────────────────────┘    │   │
│  └─────────────────────────────────────────────────────────┘   │
│                              │                                  │
│                    对话结束，自动提取                             │
│                              ▼                                  │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  L2：会话摘要（Session Summary）                         │   │
│  │  ┌─────────────────────────────────────────────────┐    │   │
│  │  │ 压缩后的对话关键信息，结构化的摘要                  │    │   │
│  │  │ 存储：SQLite 中的 memories 表                      │    │   │
│  │  │ 检索：关键词匹配 + 语义搜索                         │    │   │
│  │  │ 生命周期：跨会话（保留 30 天）                      │    │   │
│  │  │ 内容：决策记录、Bug 修复方案、技术选择、项目约定     │    │   │
│  │  └─────────────────────────────────────────────────┘    │   │
│  └─────────────────────────────────────────────────────────┘   │
│                              │                                  │
│                    定期整理，提取共性                             │
│                              ▼                                  │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  L3：长期偏好（Long-term Preferences）                   │   │
│  │  ┌─────────────────────────────────────────────────┐    │   │
│  │  │ 用户明确表达的偏好 + AI 自动学习的行为模式         │    │   │
│  │  │ 存储：向量库（语义搜索） + 文件（preferences.md）    │    │   │
│  │  │ 检索：语义搜索（向量相似度）                        │    │   │
│  │  │ 生命周期：永久（除非手动删除）                      │    │   │
│  │  │ 内容：工具偏好、代码风格、技术栈、命名习惯           │    │   │
│  │  └─────────────────────────────────────────────────┘    │   │
│  └─────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────┘
```

### 每层记忆的核心字段

**L1 工作记忆**

L1 就是 Session 的 messages 列表，不需要单独的字段。它的"字段"就是 Message 的字段。

**L2 会话摘要**

| 字段名 | 类型 | 业务含义 | 大白话解释 |
|--------|------|---------|-----------|
| memory_id | 唯一标识 | 记忆条目的 ID | 唯一标识一条记忆 |
| session_id | 标识 | 来源会话 | 这条记忆是从哪个会话提取的 |
| category | 枚举 | 记忆类别 | 偏好 / 决策 / 约定 / 问题解决 |
| content | 文本 | 记忆内容 | 用自然语言描述的关键信息 |
| importance | 数值 | 重要性评分 | 0-10，越高越重要，越不容易被清理 |
| created_at | 时间戳 | 提取时间 | 什么时候生成的 |
| last_accessed_at | 时间戳 | 最后检索时间 | 最近一次被检索到，用于判断是否"过期" |
| access_count | 数值 | 被检索次数 | 被检索的次数越多，说明越有用 |
| expired | 布尔 | 是否过期 | 过期的记忆在检索时权重降低 |

**L3 长期偏好**

| 字段名 | 类型 | 业务含义 | 大白话解释 |
|--------|------|---------|-----------|
| preference_id | 唯一标识 | 偏好条目的 ID | 唯一标识 |
| category | 枚举 | 偏好类别 | 工具偏好 / 代码风格 / 技术栈 / 命名习惯 / 交互偏好 |
| key | 文本 | 偏好键 | 比如 "package_manager" |
| value | 文本 | 偏好值 | 比如 "pnpm" |
| source | 枚举 | 来源 | 用户明确设置 / AI 自动学习 |
| confidence | 数值 | 置信度 | 0-1，AI 自动学习的偏好置信度可能较低 |
| embedding | 向量 | 语义向量 | 用于语义搜索，找到语义上相关的偏好 |

### 记忆的生命周期

**L1 工作记忆的生命周期**：

```
会话开始 → 消息逐条追加 → 会话结束 → 自动转为 L2 提取的原材料
```

L1 的生命周期等于 Session 的生命周期。会话归档后，L1 被压缩存储。

**L2 会话摘要的生命周期**：

```
会话结束 → 自动提取关键信息 → 生成 L2 条目 → 存入 SQLite
    │
    │ 新会话开始 → 自动检索相关 L2 → 注入 Prompt
    │
    │ 30 天后 → 自动清理（或转为 L3 如果足够重要）
    │
    │ 与已有 L2 相似 → 合并去重
    │
    │ 被标记为过期 → 降低检索权重
```

**L3 长期偏好的生命周期**：

```
用户首次设置偏好 / AI 从多次会话中学习
    │
    ▼
存入向量库 + preferences.md 文件
    │
    ▼
每次新会话 → 语义搜索相关偏好 → 注入 Prompt
    │
    │ 用户修改偏好 → 更新
    │ AI 发现不匹配 → 降低置信度
    │ 长期未使用 → 降低权重
    │ 用户手动删除 → 移除
```

### 记忆图谱（Memory Graph）

jcode 不仅仅把记忆当成"独立条目"存储，它还会分析记忆之间的关联，构建一个**记忆图谱**。

举个例子：

```
记忆 A: "user_auth 模块使用 bcrypt 进行密码哈希"
记忆 B: "用户偏好使用 anyhow 处理错误"
记忆 C: "项目使用 PostgreSQL 数据库"
记忆 D: "测试文件放在 tests/ 目录"

它们之间的关联：
  A ←→ B (同模块相关：都在 user_auth 中用到)
  A ←→ C (同项目相关：都是同一个仓库的)
  B ←→ D (同一次对话中产生的)
```

关联类型包括：

| 关联类型 | 含义 | 例子 |
|---------|------|------|
| 同模块关联 | 都是关于同一个代码模块的 | 都涉及 user_auth.rs |
| 同项目关联 | 都是同一个代码仓库的 | 都是 my-project 的 |
| 同类型关联 | 都是同一类信息的 | 都是"技术决策"类 |
| 时序关联 | 在同一次对话中产生的 | 同一次聊出来的 |
| 因果关联 | 一个决定导致了另一个 | 因为选了 bcrypt，所以需要处理密码哈希 |

记忆图谱的作用是**级联激活**。当你检索到记忆 A 时，跟 A 强关联的记忆 B、C、D 也会被一起激活，让 AI 获得更全面的上下文。

## 核心实体四：Provider（模型提供商）

### 一句话概括

**Provider 是 jcode 的"万能插座"**——它把不同 AI 模型服务商的 API 差异封装成统一的接口，让上层代码不关心底层到底用的是 Claude 还是 GPT。

### 业务含义

jcode 支持 8 种以上的 AI 模型提供商。每个 Provider 的 API 格式、认证方式、能力范围都不同。Provider 实体的作用就是把这些差异"藏起来"，对外暴露统一的接口。

对用户来说，切换 Provider 就像换一个充电插头——插上就能用，不需要重新学习。

### 核心字段

| 字段名 | 类型 | 业务含义 | 大白话解释 |
|--------|------|---------|-----------|
| provider_id | 唯一标识 | 提供商的唯一 ID | 比如 "anthropic"、"openai"、"deepseek" |
| display_name | 文本 | 显示名称 | 在 UI 中展示的名字，比如 "Anthropic (Claude)" |
| auth_method | 枚举 | 认证方式 | api_key / oauth / env / local_credentials |
| api_key | 加密文本 | API 密钥 | 加密存储，不会明文出现在日志中 |
| base_url | URL | API 端点 | 请求发到哪个地址 |
| models | 列表 | 支持的模型列表 | 每个模型有名称、能力标记、价格信息 |
| capabilities | 标记集合 | 能力标记 | 支持 vision / tools / streaming / embedding 等 |
| rate_limit | 配置 | 速率限制 | 每分钟最多发多少请求、每分钟最多消耗多少 token |
| health_status | 枚举 | 健康状态 | healthy / degraded / down |
| latency_stats | 统计 | 延迟统计 | 平均响应时间、P50/P95/P99 |
| token_usage | 统计 | Token 用量 | 今天用了多少、本月用了多少 |
| error_count | 数值 | 错误计数 | 最近出了多少次错 |

### 支持的 Provider 一览

| Provider | 模型系列 | 接入方式 | 核心优势 | 适用场景 |
|----------|---------|---------|---------|---------|
| Anthropic | Claude 系列 | OAuth 登录 | 代码理解最强，200K 上下文 | 复杂重构、代码审查 |
| OpenAI | GPT-4o / 4.1 | OAuth 登录 | 综合能力最强 | 通用编码任务 |
| Google | Gemini 2.5 | OAuth 登录 | 100 万 token 上下文，超长文件 | 大项目分析 |
| GitHub Copilot | Copilot | OAuth 登录 | 深度集成 GitHub | GitHub 工作流 |
| OpenRouter | 200+ 模型 | API Key | 一个 Key 访问多种模型，聚合平台 | 多模型对比、成本优化 |
| AWS Bedrock | Claude (AWS) | IAM 凭证 | 企业合规，VPC 内运行 | 企业用户、数据合规 |
| Cursor | Cursor Agent | 本地凭证 | 复用 Cursor 编辑器的登录状态 | Cursor 用户无缝迁移 |
| DeepSeek | V3 / R1 | API Key | 性价比极高 | 成本敏感场景 |
| MiniMax | ABAB 系列 | API Key | 国产模型，中文能力强 | 中文编码场景 |
| 通义千问 | Qwen-Max | API Key | 阿里云生态 | 阿里云用户 |
| 智谱 | GLM-4 | API Key | 国产模型 | 国内合规需求 |
| 月之暗面 | Kimi | API Key | 长上下文 | 中文长文档 |
| 本地模型 | Ollama | 本地连接 | 完全离线，数据不出本机 | 离线开发、敏感项目 |

### Provider 的生命周期

```
用户首次配置 Provider
    │
    ├─ 方式 1：OAuth 登录
    │   └── 浏览器打开登录页 → 用户授权 → 回调 → 获取 Token → 加密存储
    │
    ├─ 方式 2：API Key
    │   └── 用户输入 Key → 验证有效性 → 加密存储
    │
    ├─ 方式 3：环境变量
    │   └── 从系统环境变量自动读取 → 验证
    │
    └─ 方式 4：本地凭证
        └── 从其他工具（Cursor、Copilot）的本地文件读取
    │
    ▼
Provider 注册到运行时
    │
    ▼
会话使用 Provider
    │  ├── Agent 调用 chat() → Provider 发送 API 请求
    │  ├── 记录 token_usage、latency_stats
    │  └── 监控 health_status
    │
    │ 健康检查失败 → health_status = degraded
    │ 连续失败 → health_status = down → 自动切换到备用 Provider
    │
    ▼
用户删除或更换 Provider → 从运行时注销 → 加密的 API Key 被清除
```

### 智能路由

jcode 不是简单地"用户选哪个就用哪个"，它有一个智能路由层，根据以下因素自动选择最优 Provider：

| 因素 | 说明 | 例子 |
|------|------|------|
| 任务类型 | 不同类型的任务适合不同的模型 | 代码生成用强模型，代码补全用快模型 |
| 成本预算 | 用户设置了月度预算上限 | 预算快用完时，自动切便宜模型 |
| 延迟要求 | 交互式场景要求快速响应 | 聊天时用快模型，后台任务可以等 |
| 可用性 | 主模型挂了自动切备用 | Claude 超时 → 自动切 GPT |
| 历史成功率 | 某类任务在某个模型上成功率更高 | 重构任务在 Claude 上成功率 95% |

## 核心实体五：Tool（工具）

### 一句话概括

**Tool 是 jcode 的"手和脚"**——AI 模型本身只能"想"和"说"，但 Tool 让它能"做"：读文件、写代码、跑命令、搜网页。

### 业务含义

如果把 AI 模型比作一个"大脑"，Tool 就是它的"四肢"。没有 Tool，AI 只能回答你"应该怎么做"；有了 Tool，AI 能直接帮你"做"。

jcode 内置了 30+ 个工具，涵盖文件操作、代码执行、Git 管理、网页搜索、PDF 阅读等。每个 Tool 都是一个独立的、可插拔的模块。

### 核心字段

| 字段名 | 类型 | 业务含义 | 大白话解释 |
|--------|------|---------|-----------|
| tool_name | 标识 | 工具名称 | 唯一标识，比如 "read_file"、"execute_code" |
| display_name | 文本 | 显示名称 | 在 UI 中展示的名字，比如 "读取文件" |
| description | 文本 | 功能描述 | 告诉 AI 这个工具是干什么的，AI 根据描述决定是否调用 |
| parameters | Schema | 参数定义 | JSON Schema 格式，定义这个工具需要哪些输入参数 |
| handler | 函数 | 执行函数 | 工具被调用时实际执行的代码 |
| requires_approval | 布尔 | 是否需要用户确认 | 危险操作（写文件、执行命令）需要用户点头 |
| category | 枚举 | 工具分类 | 文件操作 / 代码执行 / Git / 搜索 / 浏览器 / 其他 |
| is_enabled | 布尔 | 是否启用 | 用户可以在配置中关闭某些工具 |
| timeout | 数值 | 超时时间 | 工具执行超过这个时间就强制终止 |

### 工具分类与清单

### 工具的权限控制

jcode 对工具有精细的权限控制，分为三个级别：

**级别 1：自动执行（无需确认）**
- 只读操作：读文件、搜索、查看状态
- 没有副作用，不会修改任何东西
- 典型工具：read_file、grep_search、git_status

**级别 2：需要确认（弹窗询问）**
- 写操作：写文件、执行命令、Git 提交
- 有副作用，但可逆（Git 可以回滚）
- 典型工具：write_file、exec_command、git_diff

**级别 3：需要额外授权（二次确认）**
- 危险操作：删除文件、强制推送、访问网络
- 有不可逆的副作用
- 用户需要在配置中显式开启

### 工具的生命周期

```
工具被定义（内置 30+ 或用户自定义）
    │
    ▼
工具注册到工具注册表（Tool Registry）
    │
    ▼
会话启动时，根据配置加载启用的工具列表
    │
    ▼
Agent 构建 Prompt 时，将工具列表注入到系统提示中
    │  AI 看到："你可以使用以下工具：read_file、write_file、..."
    │
    ▼
AI 决定调用工具 → 返回 tool_call 请求
    │
    ├─ 检查权限：需要确认？
    │   ├─ 是 → 弹窗询问用户 → 用户同意 → 执行
    │   └─ 否 → 直接执行
    │
    ▼
执行工具 → 返回结果 → 作为 tool_result 消息追加到对话
    │
    ▼
工具执行结果交给 AI → AI 继续思考 → 可能再次调用工具
    │
    ▼
用户禁用了某个工具 → 从会话中移除 → AI 不再知道这个工具的存在
```

## 核心实体六：Plan（计划）

### 一句话概括

**Plan 是 jcode 的"项目计划书"**——当任务复杂到需要多步骤时，Plan 把任务拆成可执行的小步骤，每个步骤有明确的验收标准和依赖关系。

### 业务含义

如果用户说"帮我修一个 Bug"，Agent 可能不需要 Plan——直接读文件、改代码、跑测试，三步搞定。但如果用户说"把这个项目从 JavaScript 迁移到 TypeScript"，那就需要 Plan 了——这个任务涉及几十个文件、多个阶段、有依赖关系。

Plan 就是 jcode 的"先想清楚再动手"机制。

### 核心字段

| 字段名 | 类型 | 业务含义 | 大白话解释 |
|--------|------|---------|-----------|
| plan_id | 唯一标识 | 计划的唯一 ID | 全局唯一，用于追踪和引用 |
| session_id | 标识 | 所属会话 | 这个计划是在哪个会话中创建的 |
| title | 文本 | 计划标题 | 比如 "JavaScript 迁移到 TypeScript" |
| description | 文本 | 计划描述 | 更详细的说明 |
| steps | 列表 | 步骤列表 | 每个步骤有独立的描述、状态、结果 |
| status | 枚举 | 整体状态 | pending / running / completed / failed |
| execution_mode | 枚举 | 执行模式 | sequential（串行）/ parallel（并行）/ mixed（混合） |
| created_at | 时间戳 | 创建时间 | 计划什么时候生成的 |
| started_at | 时间戳 | 开始执行时间 | 什么时候开始执行的 |
| completed_at | 时间戳 | 完成时间 | 什么时候全部完成的 |
| assigned_agents | 列表 | 分配的 Agent | Swarm 模式下，哪些子 Agent 负责哪些步骤 |

### 步骤（Step）结构

每个步骤是一个独立的执行单元：

| 字段名 | 类型 | 业务含义 | 大白话解释 |
|--------|------|---------|-----------|
| step_id | 标识 | 步骤 ID | 在计划内唯一 |
| order | 数值 | 执行顺序 | 第几步 |
| description | 文本 | 步骤描述 | 这一步要做什么 |
| preconditions | 列表 | 前置条件 | 哪些步骤必须先完成 |
| acceptance_criteria | 文本 | 验收标准 | 怎么判断这一步做完了、做对了 |
| rollback_plan | 文本 | 回滚方案 | 如果这一步失败，怎么恢复 |
| estimated_tokens | 数值 | 预估 token 消耗 | 这一步大概要花多少钱 |
| status | 枚举 | 步骤状态 | pending / running / completed / failed / skipped |
| result | 文本 | 执行结果 | 完成后的输出摘要 |
| started_at | 时间戳 | 开始时间 | 这一步什么时候开始的 |
| completed_at | 时间戳 | 完成时间 | 这一步什么时候完成的 |

### 执行模式

**串行模式（Sequential）**

```
步骤 1 → 步骤 2 → 步骤 3 → 步骤 4
```

适合有严格依赖关系的任务。比如"先读文件，再改代码，再跑测试"——每一步都依赖上一步的结果。

**并行模式（Parallel）**

```
步骤 1 ─┐
步骤 2 ─┼── 同时执行
步骤 3 ─┘
```

适合互相独立的子任务。比如"给三个独立的模块各写一份测试"——三个模块互不依赖，可以同时进行。

**混合模式（Mixed）**

```
阶段 1: 步骤 1 → 步骤 2 (串行)
阶段 2: 步骤 3 ─┐
        步骤 4 ─┼── 并行
        步骤 5 ─┘
阶段 3: 步骤 6 (依赖于阶段 2 全部完成)
```

最常见的模式。大部分任务既有串行依赖，也有可并行部分。

### Plan 的生命周期

```
用户提出复杂需求
    │
    ▼
计划引擎分析任务 → 拆解步骤 → 生成 Plan
    │
    ▼
Plan 展示给用户 → 用户审核
    │
    ├─ 同意 → 开始执行
    ├─ 修改 → 调整步骤 → 重新展示
    └─ 拒绝 → Plan 归档，重新分析
    │
    ▼
执行 Plan
    │
    ├─ 串行模式：Step 1 → Step 2 → Step 3 → ...
    ├─ 并行模式：Step 1, 2, 3 同时 → 汇总
    └─ 混合模式：先串行阶段 1，再并行阶段 2，再串行阶段 3
    │
    │ 每步完成 → 更新 status → 验证验收标准
    │ 步骤失败 → 触发回滚 → 尝试修复 → 重试
    │ 发现新情况 → 动态调整 Plan（插入新步骤、拆分步骤）
    │
    ▼
所有步骤完成 → Plan completed
    │
    ▼
Plan 归档 → 作为 L2 记忆的一部分保存
```

## 核心实体七：Config（配置）

### 一句话概括

**Config 是 jcode 的"控制面板"**——它决定了 jcode 怎么运行、用什么模型、开什么工具、长什么样子。

### 业务含义

jcode 的配置不是"一锤子买卖"，而是分层的——不同层级有不同的优先级，高层覆盖低层。这让你可以为不同的项目设置不同的配置，同时保留全局默认值。

### 配置层级

```
┌─────────────────────────────────────────────────────────┐
│           配置优先级（从高到低）                          │
│                                                         │
│  ┌─────────────────────────────────────────────────┐   │
│  │  第 4 层：命令行参数                              │   │
│  │  jcode --provider openai --model gpt-4o          │   │
│  │  优先级最高，覆盖所有其他配置                      │   │
│  └─────────────────────────────────────────────────┘   │
│                          ▲ 覆盖                          │
│  ┌─────────────────────────────────────────────────┐   │
│  │  第 3 层：环境变量                                │   │
│  │  export JCODE_PROVIDER=openai                    │   │
│  │  适合 CI/CD 和自动化脚本                          │   │
│  └─────────────────────────────────────────────────┘   │
│                          ▲ 覆盖                          │
│  ┌─────────────────────────────────────────────────┐   │
│  │  第 2 层：项目级配置                              │   │
│  │  .jcode/config.toml（放在项目根目录）             │   │
│  │  项目特定的设置，比如这个项目用哪个模型            │   │
│  └─────────────────────────────────────────────────┘   │
│                          ▲ 覆盖                          │
│  ┌─────────────────────────────────────────────────┐   │
│  │  第 1 层：全局默认配置                            │   │
│  │  ~/.jcode/config.toml                            │   │
```

## 支撑实体详解

除了 7 个核心实体，jcode 还有一批支撑实体，它们不直接参与核心业务，但为系统运行提供了必要的基础能力。

### Embedding（向量嵌入）

**一句话概括**：Embedding 是 jcode 的"语义搜索引擎"——它把文本转成数字向量，让机器能理解"密码哈希"和"bcrypt"是一个意思。

**核心字段**：

| 字段名 | 含义 | 说明 |
|--------|------|------|
| model | ONNX 模型名称 | 本地运行的嵌入模型，不需要联网 |
| dimension | 向量维度 | 384 / 768 / 1024，维度越高表达力越强 |
| cache | 缓存策略 | 已经计算过的文本不再重复计算 |
| batch_size | 批量大小 | 一次处理多少条文本 |

**白话解释**：把一段文字变成一串数字（比如 768 个小数），相似的文字会被映射到相近的数字。这样"密码哈希"和"bcrypt 加密"在数字空间中就很近，搜一个就能找到另一个。

### Auth（认证）

**一句话概括**：Auth 管理用户登录各种 AI 服务的凭证。

**核心字段**：

| 字段名 | 含义 | 说明 |
|--------|------|------|
| provider | 关联的 Provider | 这份凭证是给哪个 Provider 用的 |
| auth_method | 认证方式 | api_key / oauth / env / local_credentials |
| access_token | 访问令牌 | 加密存储 |
| refresh_token | 刷新令牌 | 用于自动续期 |
| expires_at | 过期时间 | 过期前自动刷新 |

### Gateway（网关连接）

**一句话概括**：Gateway 管理 jcode 与外部网关服务的连接状态。

**核心字段**：

| 字段名 | 含义 | 说明 |
|--------|------|------|
| endpoint | 网关地址 | 连接哪个网关 |
| status | 连接状态 | connected / disconnected / reconnecting |
| latency | 延迟 | 网络延迟（毫秒） |
| retry_count | 重试次数 | 最近失败后重试了多少次 |

### Build（构建元数据）

**一句话概括**：记录 jcode 自身的版本和构建信息。

**核心字段**：

| 字段名 | 含义 | 说明 |
|--------|------|------|
| version | 版本号 | 比如 v0.54.3 |
| commit | Git commit hash | 精确到哪个提交 |
| timestamp | 构建时间 | 什么时候编译的 |
| platform | 目标平台 | macOS / Linux / Windows |
| features | 编译特性 | 启用了哪些功能 |

### Telemetry（遥测数据）

**一句话概括**：可选的匿名使用统计，帮助 jcode 团队了解产品使用情况。

**核心字段**：

| 字段名 | 含义 | 说明 |
|--------|------|------|
| event_type | 事件类型 | 比如 session_started、tool_called |
| payload | 事件数据 | 匿名化的数据，不包含用户内容 |
| timestamp | 事件时间 | 什么时候发生的 |
| session_id | 关联会话 | 匿名化的会话 ID |
| user_opted_in | 用户是否同意 | 用户必须主动同意才会上报 |

### Import（导入数据）

**一句话概括**：从其他 AI 编码工具（Claude Code、Codex、Cursor）导入历史数据。

**核心字段**：

| 字段名 | 含义 | 说明 |
|--------|------|------|
| source | 来源工具 | claude_code / codex / cursor |
| format | 原始格式 | json / yaml / toml |
| mapping | 字段映射 | 来源工具的字段怎么对应 jcode 的字段 |
| status | 导入状态 | pending / running / completed / failed |

### Batch（批量任务）

**一句话概括**：批量处理多个会话或任务。

**核心字段**：

| 字段名 | 含义 | 说明 |
|--------|------|------|
| task_list | 任务列表 | 要批量处理的任务清单 |
| concurrency | 并发数 | 同时处理几个 |
| progress | 进度 | 完成了多少 |
| results | 结果汇总 | 每个任务的执行结果 |

### Background（后台任务）

**一句话概括**：管理后台定时任务，比如记忆整理、日志清理、更新检查。

**核心字段**：

| 字段名 | 含义 | 说明 |
|--------|------|------|
| task_type | 任务类型 | memory_compaction / log_cleanup / update_check |
| schedule | 调度策略 | 多久执行一次 |
| priority | 优先级 | 高优先级先执行 |
| status | 任务状态 | pending / running / done / failed |
| retry_policy | 重试策略 | 失败后怎么重试 |

### Notification（通知）

**一句话概括**：管理通知配置，比如任务完成时发送桌面通知。

**核心字段**：

| 字段名 | 含义 | 说明 |
|--------|------|------|
| channel | 通知渠道 | desktop / system / email |
| event_types | 触发事件 | 哪些事件触发通知 |
| template | 通知模板 | 通知的内容格式 |
| enabled | 是否启用 | 开关 |

### Desktop（桌面状态）

**一句话概括**：记录桌面应用的 UI 状态。

**核心字段**：

| 字段名 | 含义 | 说明 |
|--------|------|------|
| window_state | 窗口状态 | 位置、大小、是否最大化 |
| tray_enabled | 系统托盘 | 是否在菜单栏显示图标 |
| hotkey | 全局快捷键 | 比如 Cmd+; |
| theme | 主题 | light / dark |
| always_on_top | 是否置顶 | 窗口是否始终在最前面 |

## 实体间协作关系

### 场景一：用户发起一次对话

```
用户输入 "帮我重构 user_auth.rs"

1. Config 提供默认 Provider 和模型
2. Session 创建或恢复，加载历史 Message
3. Memory 检索 L2/L3 记忆，注入 Prompt
4. Provider 连接 AI 模型
5. Agent 构建 Prompt（系统提示 + 工具列表 + 记忆 + 历史消息 + 用户输入）
6. Tool 列表被注入到 Prompt，AI 知道可以用哪些工具
7. AI 返回 → 可能需要调用 Tool → Tool 执行 → 返回结果
8. 每轮交互都追加到 Message 列表
9. 对话结束 → Memory 自动提取关键信息
```

### 场景二：Swarm 多 Agent 协作

```
用户输入 "给整个项目写单元测试"

1. Plan 引擎分析任务，生成 Plan（3 个阶段，15 个步骤）
2. Swarm 协调器创建 3 个子 Agent
3. 每个子 Agent 有自己的 Session + Provider + Tool 权限
4. Plan 的步骤分配给不同的子 Agent
5. 子 Agent 并行执行，各自调用 Tool
6. 子 Agent 之间通过 Coordinator 通信
7. 结果汇总到 Plan
8. 所有步骤完成 → Plan completed
9. 整个过程的 Memory 写入 L2
```

### 场景三：会话恢复

```
用户关闭终端，一天后重新打开

1. Session 从 SQLite 加载（状态：PAUSED → RESUMED）
2. Message 列表完整恢复
3. Memory 重新检索 L2/L3
4. Provider 重新建立连接
5. Config 重新加载（可能有变更）
6. 用户看到的就是上次离开时的状态，无缝继续
```

## 数据持久化架构

### 存储方案

jcode 使用 **SQLite** 作为主存储引擎。选择 SQLite 的原因很务实：

| 优势 | 说明 |
|------|------|
| 零配置 | 不需要安装数据库服务，不需要 Docker，不需要配置端口 |
| 单文件 | 一个 .db 文件包含所有数据，备份就是复制一个文件 |
| 事务 | 保证数据一致性，不会出现"写了一半"的情况 |
| WAL 模式 | 支持并发读写，读操作不会阻塞写操作 |
| 嵌入式 | 编译到二进制中，没有外部依赖 |
| 跨平台 | macOS、Linux、Windows 都一样用 |

### 存储位置

| 数据 | 存储位置 | 格式 |
|------|---------|------|
| 会话和消息 | ~/.jcode/jcode.db | SQLite |
| 记忆（L2） | ~/.jcode/jcode.db | SQLite |
| 记忆（L3） | ~/.jcode/preferences.md + 向量库 | 文件 + SQLite |
| API Key | 系统 Keychain / Keyring | 加密存储 |
| 配置文件 | ~/.jcode/config.toml | TOML |
| 项目配置 | 项目根目录/.jcode/config.toml | TOML |
| 日志 | ~/.jcode/logs/ | 文本文件 |
| 备份 | ~/.jcode/backups/ | SQLite 副本 |
| 向量缓存 | ~/.jcode/cache/ | 二进制文件 |

### 数据库表结构概览

| 表名 | 存储内容 | 关键字段 |
|------|---------|---------|
| sessions | 会话信息 | session_id, title, provider, model, status, workspace, created_at, updated_at |
| messages | 消息记录 | message_id, session_id, role, content, tool_calls, timestamp, token_count |
| memories | 记忆条目 | memory_id, session_id, category, content, importance, embedding |
| providers | Provider 配置 | provider_id, auth_method, base_url, models, capabilities |
| tools | 工具定义 | tool_name, description, parameters, category, requires_approval |
| plans | 计划记录 | plan_id, session_id, title, steps, status, execution_mode |
| config | 配置项 | key, value, scope (global/project/session) |

## 数据安全与隐私

### 敏感数据保护

jcode 对敏感数据的处理非常谨慎：

| 数据类型 | 保护措施 |
|---------|---------|
| API Key | 存入系统 Keychain（macOS）/ Keyring（Linux）/ 加密存储（Windows），不写明文到文件 |
| OAuth Token | 加密存储，自动刷新，过期自动清除 |
| 对话内容 | 仅存储在本地 SQLite，不上传到 jcode 服务器 |
| 遥测数据 | 完全可选，用户主动同意才上报，上报内容匿名化 |
| 项目代码 | 仅在本地处理，不会发送到 jcode 服务器 |

### 数据所有权

用户完全拥有自己的数据：

- 所有数据存储在本地（~/.jcode/ 目录）
- 可以随时导出为 JSON 格式
- 可以随时删除（删除 ~/.jcode/ 目录即可）
- 切换到其他工具时，可以通过 Import 功能迁移数据

## 总结：jcode 数据设计的五个原则

回顾 jcode 的所有数据实体，可以归纳出五个设计原则：

### 原则一：以 Session 为中心

一切围绕 Session 展开。Message 是 Session 的内容，Memory 是 Session 的提取物，Plan 是 Session 的执行蓝图，Tool 是 Session 的执行能力。这个设计让 jcode 的"工作单元"概念非常清晰——一个 Session 就是一个完整的、自包含的工作单元。

### 原则二：记忆是核心竞争力

大部分 AI 工具是"金鱼记忆"，jcode 的三级记忆系统（L1/L2/L3）让它能"记住你、理解你、适应你"。记忆不是简单存储，而是自动提取、自动关联、自动检索——你不需要手动管理，它像人脑一样自动工作。

### 原则三：Provider 解耦

通过 Provider 抽象层，jcode 把 AI 模型变成了"可插拔的插件"。切换模型不需要改任何代码，添加新 Provider 不需要动核心逻辑。这让 jcode 不被任何一个模型提供商绑定。

### 原则四：配置分层，灵活覆盖

四级配置优先级（命令行 > 环境变量 > 项目 > 全局）让用户在不同粒度上控制 jcode 的行为。全局设一个默认，项目有特殊需求就覆盖，临时需要换模型就用命令行参数。

### 原则五：数据本地化，隐私优先

所有用户数据存储在本地，SQLite 单文件让备份和迁移变得极其简单。API Key 用系统级加密存储，不写明文。用户完全拥有自己的数据，随时可以导出或删除。
