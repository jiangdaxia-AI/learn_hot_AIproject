## 1. 项目总览

### 一句话说明

jcode 是一个用 Rust 从头构建的 AI 编码代理。它不是 ChatGPT 的插件或 VS Code 的扩展，
而是一个独立运行的 AI 程序员，能理解你的代码仓库、制定修改计划、自动写代码、跑测试，
甚至能同时派出多个子代理并行干活。

### 为什么叫下一代？

市面上的 AI 编码工具（如 GitHub Copilot、Cursor）大多工作在补全层面：你写一行，它猜下一行。
jcode 则工作在代理层面：你给它一个需求（比如把登录模块从 JWT（JSON Web Token，一种身份认证令牌）改成 OAuth 2.0（一种开放授权协议标准）），
它自己规划步骤、修改文件、运行测试、修复报错，像一个真正的初级工程师一样完成整个任务。

### 为什么用 Rust？

Rust 是一门以零成本抽象和内存安全著称的系统编程语言。用 Rust 构建 jcode 意味着：

- **启动快**：毫秒级冷启动，不像 Python/Node.js（两种主流编程语言运行时）工具需要等几秒
- **内存省**：一个 Agent 进程只占几十 MB，可以同时跑几十个 Swarm 子代理
- **跨平台**：一套代码编译出 macOS / Linux / Windows 原生二进制
- **不依赖运行时**：不需要安装 Python、Node.js（两种编程语言运行时），用户下载一个二进制文件就能跑

## 2. Agent 运行时

### 一句话说明

Agent 运行时是 jcode 的大脑中枢。它负责接收用户指令、调度工具、与大模型对话、管理整个任务的生命周期，就像一个项目经理在协调各方资源。

### 业务价值

| 维度 | 说明 |
|------|------|
| **可靠性** | 任务状态持久化，断点续跑，不会因为网络波动丢掉进度 |
| **可控性** | 每一步操作都有日志，出问题可以回溯到具体哪一步 |
| **并发性** | 一个运行时可以同时管理多个任务，互不干扰 |
| **扩展性** | 新增工具、新增 Provider 只需注册，不用改核心逻辑 |

### 使用场景

1. **单任务执行**：用户说帮我修复 issue #42，Agent 运行时启动一个会话，从理解需求到提交 PR（Pull Request，代码合并请求） 全自动完成
2. **多任务并行**：同时处理重构用户模块和写单元测试，两个任务不同会话，互不干扰
3. **长任务挂起**：一个重构任务跑了 30 分钟，用户关掉终端，下次打开自动恢复进度
4. **CI/CD（持续集成/持续部署，代码自动测试和发布）集成**：作为 GitHub Actions（GitHub 的自动化工作流平台）的一个步骤，自动修复 lint（代码静态检查工具，自动发现代码风格问题）报错

### 关键流程

```
用户输入 '修复登录页面的 bug'
        |
        v
+---------------------+
|  1. 解析指令         |  理解用户意图，提取关键信息
|     (Parser)        |
+---------+-----------+
          |
          v
+---------------------+
|  2. 创建会话         |  分配唯一 Session ID，初始化上下文
|     (Session)       |
+---------+-----------+
          |
          v
+---------------------+
|  3. 进入主循环       |  +---------------------------+
|     (Main Loop)     |  |  a. 构建 Prompt            |
|                     |  |  b. 调用大模型              |
|                     |  |  c. 解析模型返回            |
|                     |  |  d. 执行工具调用            |
|                     |  |  e. 收集结果，更新上下文     |
|                     |  |  f. 判断是否完成            |
|                     |  +---------------------------+
+---------+-----------+
          |
          v
+---------------------+
|  4. 输出结果         |  生成摘要、PR（Pull Request）描述、变更日志
|     (Result)        |
+---------------------+
```

### 核心设计

#### 状态机模型

Agent 运行时采用有限状态机设计，每个任务会话严格处于以下状态之一：

```
IDLE -> PLANNING -> EXECUTING -> VERIFYING -> DONE
                      |               |
                    PAUSED          FAILED
                      |               |
                   RESUMED         RETRYING
```

- **IDLE**：空闲，等待用户指令
- **PLANNING**：制定计划中，调用计划引擎
- **EXECUTING**：执行中，工具调用和模型交互
- **VERIFYING**：验证阶段，跑测试、检查 lint（代码静态检查）
- **DONE**：任务完成
- **PAUSED**：用户手动暂停或系统挂起
- **FAILED**：执行失败，但可重试
- **RETRYING**：正在重试上一次失败的任务

这个设计的好处是：**状态可预测、可恢复、可审计**。不像某些工具黑盒执行，你不知道它现在在干嘛、卡在哪一步。

#### 事件驱动架构

Agent 运行时内部是事件驱动的，每个操作（工具调用开始、模型返回、错误发生）都产生一个事件，进入事件总线。这样做的好处：

- **解耦**：日志模块、UI 模块、监控模块各自订阅关心的事件，互不影响
- **可观测**：任何时候都能看到现在正在执行什么
- **可扩展**：新增一个模块，只需订阅相关事件即可

#### 会话持久化

每个会话的状态（包括对话历史、工具调用记录、中间产出）都持久化到磁盘。这意味着：

- 用户关掉终端不会丢失进度
- 可以回溯任意历史会话
- 支持会话分叉：从某个中间状态尝试不同的方案

## 3. Swarm 群协调系统

### 一句话说明

Swarm 是 jcode 的分身术。当任务太复杂、太大，一个 Agent 搞不定时，Swarm 能自动拆解任务，派出多个子代理同时干活，最后把结果合并回来。

### 业务价值

| 维度 | 说明 |
|------|------|
| **速度** | 多个子代理并行工作，任务总耗时 = 最慢子任务的时间，而非所有子任务之和 |
| **质量** | 每个子代理专注一个子任务，比一个大代理一心多用更不容易出错 |
| **规模** | 理论上可以同时管理几十个子代理，处理超大型代码仓库 |
| **隔离** | 子代理之间互不干扰，一个子任务失败不影响其他 |

### 使用场景

1. **大型重构**：把整个项目从 JavaScript 迁移到 TypeScript（带类型系统的 JavaScript 超集），Swarm 按文件/模块拆分，每个子代理负责一个模块
2. **多仓库联动**：更新前端 API 调用以匹配后端新接口，一个子代理改前端，一个改后端，一个更新文档
3. **全面测试**：给所有模块写单元测试，每个子代理负责一个模块的测试
4. **代码审查**：审查这次 PR（Pull Request） 的所有变更，多个子代理从安全性、性能、可读性等不同角度审查

### 关键流程

```
用户输入 '把所有 .js（JavaScript）文件改成 .ts（TypeScript），并修复类型错误'
        |
        v
+-------------------------------+
|  1. 任务分解 (Decompose)      |  分析任务，拆成子任务
|     发现 23 个 .js 文件       |
|     -> 拆成 4 组，每组 5-6 个  |
+---------------+---------------+
                |
                v
+-------------------------------+
|  2. 创建 Swarm                |  启动协调器 + 4 个子代理
|     Coordinator: 1 个         |
|     Workers: 4 个             |
+---------------+---------------+
                |
      +---------+---------+---------+
      v         v         v         v
  +--------+ +--------+ +--------+ +--------+
  |Worker 1| |Worker 2| |Worker 3| |Worker 4|
  |改5个文件| |改6个文件| |改6个文件| |改6个文件|
  +----+---+ +----+---+ +----+---+ +----+---+
       |          |          |          |
       +----------+----------+----------+
                  |          |
                  v          v
+-------------------------------+
|  3. 结果合并 (Merge)          |  Coordinator 收集结果
|     检查冲突，合并变更         |
+---------------+---------------+
                |
                v
+-------------------------------+
|  4. 统一验证                  |  跑全量测试，确保合并后没问题
+-------------------------------+
```

### 核心设计

#### Coordinator-Worker 模式

Swarm 系统采用经典的协调者-工作者模式：

- **Coordinator（协调者）**：不干活，只负责分活和收活。它分析任务、拆解子任务、分配给 Worker、收集结果、处理冲突。
- **Worker（工作者）**：每个 Worker 就是一个完整的 Agent 运行时实例，有独立的上下文、独立的工具访问权限，专心完成自己的子任务。

打个比方：Coordinator 是包工头，Workers 是装修工人。包工头不贴瓷砖，但他知道哪个工人擅长什么、谁来干哪个房间、最后怎么验收。

#### 动态分派策略

jcode 的 Swarm 不是简单地平均分配，而是根据以下因素动态决策：

1. **文件大小**：大文件分给一个 Worker，小文件打包
2. **依赖关系**：有依赖的模块尽量分给同一个 Worker，减少跨 Worker 通信
3. **Worker 状态**：空闲的 Worker 优先分配，正在忙的少分配
4. **历史表现**：如果某个 Worker 在类似任务上成功率高，多分配

#### 冲突处理

当多个 Worker 修改了同一个文件（或相关联的文件），Coordinator 需要合并。jcode 采用分层策略：

- **第一层**：Git 自动合并，如果文件不同区域被修改，自动合并
- **第二层**：语义分析，如果 Git 合并不了，尝试理解变更意图，智能合并
- **第三层**：人工介入，如果实在合并不了，标记冲突，让用户决定

#### 通信机制

Worker 之间不会直接通信（避免耦合），而是通过 Coordinator 中转。通信内容仅限于：

- 子任务状态更新（完成 / 失败 / 进度）
- 需求澄清（Worker 发现模糊需求，请求 Coordinator 澄清）
- 依赖通知（Worker A 完成了一个接口定义，Worker B 需要知道）

## 4. 计划引擎

### 一句话说明

计划引擎是 jcode 的战略规划部。在执行任何实际操作之前，它先分析任务、制定多步骤计划、评估风险，确保不是拍脑袋就干。

### 业务价值

| 维度 | 说明 |
|------|------|
| **减少返工** | 先想清楚再动手，比边做边改少走弯路 |
| **可预测性** | 用户能看到完整计划，心里有数 |
| **风险控制** | 提前识别高风险步骤，制定回滚方案 |
| **成本控制** | 避免无效的模型调用，节省 Token 消耗 |

### 使用场景

1. **复杂需求**：把支付模块从 Stripe（海外支付服务商）换成支付宝，计划引擎分析影响范围，列出所有需要修改的文件
2. **多步骤任务**：升级项目依赖，修复兼容性问题，更新 CI（持续集成）配置，拆成 3 个阶段，每个阶段有明确的验收标准
3. **风险任务**：重构核心数据库层，识别高风险点，制定回滚计划
4. **探索性任务**：分析这个项目为什么编译慢，先计划分析步骤，再执行

### 关键流程

```
用户输入复杂需求
        |
        v
+--------------------------------+
|  1. 需求理解                    |
|  - 提取关键意图                 |
|  - 识别约束条件                 |
|  - 确定成功标准                 |
+----------------+---------------+
                 |
                 v
+--------------------------------+
|  2. 上下文收集                  |
|  - 读取项目结构                 |
|  - 分析依赖关系                 |
|  - 搜索相关代码                 |
|  - 查阅历史类似任务             |
+----------------+---------------+
                 |
                 v
+--------------------------------+
|  3. 计划生成                    |
|  - 拆解为步骤序列               |
|  - 标注每步依赖                 |
|  - 估算每步复杂度               |
|  - 制定回滚/容错策略            |
+----------------+---------------+
                 |
                 v
+--------------------------------+
|  4. 计划审核                    |
|  - 展示计划给用户               |
|  - 用户确认/修改/拒绝           |
|  - 记录审核结果                 |
+----------------+---------------+
                 |
                 v
+--------------------------------+
|  5. 计划执行                    |
|  - 按步骤执行                   |
|  - 每步完成后验证               |
|  - 异常时触发回滚               |
+--------------------------------+
```

### 核心设计

#### 分层计划结构

jcode 的计划不是扁平的步骤列表，而是分层结构：

```
任务：迁移支付模块
+-- 阶段 1：分析现状
|   +-- 步骤 1.1：列出所有 Stripe（海外支付服务商）相关代码
|   +-- 步骤 1.2：分析调用链路
|   +-- 步骤 1.3：生成影响范围报告
+-- 阶段 2：实现新接口
|   +-- 步骤 2.1：定义支付宝接口抽象
|   +-- 步骤 2.2：实现支付宝适配器
|   +-- 步骤 2.3：编写单元测试
+-- 阶段 3：替换调用
|   +-- 步骤 3.1：逐个替换调用点
|   +-- 步骤 3.2：更新配置文件
+-- 阶段 4：清理与验证
    +-- 步骤 4.1：移除 Stripe（海外支付服务商）依赖
    +-- 步骤 4.2：跑集成测试
    +-- 步骤 4.3：更新文档
```

每个步骤都有：
- **前置条件**：前面哪些步骤必须完成
- **验收标准**：怎么判断这一步做完了、做对了
- **回滚方案**：如果这一步失败，怎么恢复
- **预估耗时**：大模型估算的 Token 消耗和代码量

#### 动态调整

计划不是一成不变的。执行过程中，如果发现新情况，计划引擎会动态调整：

- 步骤 2.2 发现 SDK（软件开发工具包，第三方提供的代码库）需要额外配置 -> 在步骤 2.2 和 2.3 之间插入一个新步骤
- 步骤 3.1 发现某个调用点比预期复杂 -> 把该步骤拆成两个子步骤
- 步骤 4.1 发现还有未分析的引用 -> 回退到阶段 1，重新分析

#### 计划模板

对于常见任务类型，jcode 内置了计划模板：

- **代码迁移**：分析 -> 实现 -> 替换 -> 清理
- **Bug 修复**：复现 -> 定位 -> 修复 -> 测试 -> 回归
- **功能开发**：设计 -> 实现 -> 测试 -> 文档
- **性能优化**：测量 -> 分析瓶颈 -> 优化 -> 再测量

模板让计划生成更快、更稳定，同时也允许用户自定义模板。

## 5. 多 Provider 体系

### 一句话说明

多 Provider 体系是 jcode 的模型路由器。它让 jcode 能同时对接 8+ 个大模型服务商（OpenAI、Anthropic、DeepSeek、MiniMax 等），根据不同任务自动选择最合适的模型，也能在某个服务商宕机时自动切换。

### 业务价值

| 维度 | 说明 |
|------|------|
| **不绑定厂商** | 不会被某个服务商绑架，随时切换 |
| **成本优化** | 简单任务用便宜模型，复杂任务用强模型，省 Token 费 |
| **高可用** | 主模型挂了自动切备用模型，任务不中断 |
| **合规灵活** | 不同地区用不同模型，满足数据合规要求 |

### 使用场景

1. **成本敏感**：日常代码补全用 DeepSeek（便宜），复杂重构用 Claude（强）
2. **高可用需求**：线上 CI 不能停，主模型超时自动切备用
3. **多模型对比**：同一个问题发给 3 个模型，对比答案质量
4. **区域合规**：中国区数据用国产模型，海外数据用 OpenAI

### 支持的 Provider（8+）

```
+-----------------------------------------------------------+
|                    Provider 抽象层                         |
|         统一的接口：chat() / stream() / embed()            |
+---------+---------+----------+----------+-----------------+
| OpenAI  |Anthropic| DeepSeek | MiniMax  |  通义千问        |
| GPT-4o  | Claude  | V3/R1    |  ABAB    |  Qwen-Max       |
+---------+---------+----------+----------+-----------------+
| 智谱    | 月之暗面 | 百川     | 本地模型  |  更多...        |
| GLM-4   | Kimi    | Baichuan | Ollama   |  可扩展         |
+---------+---------+----------+----------+-----------------+
```

### 核心设计

#### 统一抽象层

所有 Provider 实现同一个 trait（接口），对外暴露三个核心方法：

```rust
// 伪代码示意
trait Provider {
    // 对话：发消息，拿回复
    async fn chat(&self, messages: Vec<Message>) -> Response;
    
    // 流式对话：一个字一个字往外蹦（打字机效果）
    async fn stream(&self, messages: Vec<Message>) -> Stream<Response>;
    
    // 嵌入：把文本转成向量（用于搜索和记忆）
    async fn embed(&self, texts: Vec<String>) -> Vec<Vec<f32>>;
}
```

这个抽象层的设计哲学是：**上层代码不关心用的是哪个模型**。Agent 运行时只调用 `provider.chat(messages)`，至于背后是 OpenAI 还是 DeepSeek，由配置决定。

#### 智能路由

jcode 不是简单地用户选哪个就用哪个，而是有一个智能路由层：

```
任务请求 -> 路由器分析
                |
      +---------+---------+
      v         v         v
    成本      能力      可用性
    检查      匹配      检查
      |         |         |
      +---------+---------+
                v
           选择最优 Provider
```

路由决策考虑的因素：

1. **任务类型**：代码生成 -> 强模型；代码补全 -> 快模型；嵌入 -> 专用模型
2. **成本预算**：用户设置了月度预算，优先用便宜模型
3. **延迟要求**：交互式场景要求 2 秒内响应，后台任务可以等
4. **可用性**：主模型 5 秒没响应，自动切备用
5. **历史成功率**：某类任务在某个模型上成功率更高，优先选择

#### 故障转移

```
用户请求
    |
    v
Provider A (首选) --超时--> Provider B (备用) --也挂了--> Provider C (兜底)
    |                          |                          |
    成功                       成功                       成功/失败
```

故障转移是自动的，对用户透明。用户不会看到模型调用失败的错误，而是在日志里看到已从 Provider A 切换到 Provider B。

#### 成本追踪

每个 Provider 调用都会记录 Token 消耗和费用。用户可以：

- 按项目、按任务、按日期查看费用明细
- 设置每日/每月预算上限
- 对比不同模型在同类任务上的性价比

## 6. 记忆系统

### 一句话说明

记忆系统是 jcode 的长期记忆。它让 jcode 记住你项目的编码规范、你的个人偏好、之前解决过的问题，这样下次遇到类似情况时不用从头教它。

### 业务价值

| 维度 | 说明 |
|------|------|
| **个性化** | 记住你的编码风格、命名习惯、项目约定 |
| **效率** | 类似问题不用重复分析，直接调取历史经验 |
| **一致性** | 确保所有代码修改风格统一 |
| **知识积累** | 项目越用越聪明，经验不断沉淀 |

### 使用场景

1. **编码规范记忆**：我们项目用 camelCase（驼峰命名，如 userName）命名，不用 snake_case（下划线命名，如 user_name） -> 之后所有代码生成都遵循这个规范
2. **项目结构记忆**：数据库层在 src/db/，API 层在 src/api/ -> 新代码自动放到正确位置
3. **问题经验记忆**：上次 N+1 查询（一种常见数据库性能问题：查 1 次主表后又逐条查了 N 次关联表）问题是因为没加 .includes()（数据库预加载关联数据的方法） -> 下次自动检查
4. **用户偏好记忆**：我更喜欢先写测试再写实现 -> 自动调整工作流

### 记忆层次结构

```
+--------------------------------------------+
|              工作记忆                       |
|         (Working Memory)                   |
|   当前会话的上下文，会话结束即清空           |
|   容量：当前对话 + 最近工具调用             |
+--------------------------------------------+
|              短期记忆                       |
|         (Short-term Memory)                |
|   最近几次会话的关键信息                    |
|   容量：最近 10 次会话的摘要                |
+--------------------------------------------+
|              长期记忆                       |
|         (Long-term Memory)                 |
|   持久化的项目知识和用户偏好                 |
|   容量：不限，但需要检索                     |
+--------------------------------------------+
|              共享记忆                       |
|         (Shared Memory)                    |
|   团队成员共享的项目规范和经验               |
|   容量：团队级别的知识库                     |
+--------------------------------------------+
```

### 核心设计

#### 自动记忆提取

jcode 不会让用户手动教它。而是在每次会话结束后，自动从对话中提取有价值的信息：

```
会话结束 -> 分析对话内容
                |
                v
           提取关键信息
           - 编码规范：用户提到用 4 空格缩进
           - 项目约定：修改了 .eslintrc（ESLint 的配置文件），说明项目用 ESLint（JavaScript 代码检查工具）
           - 踩坑经验：花 3 轮修复了某个依赖冲突
                |
                v
           存入记忆库（带标签和向量）
```

#### 向量检索

记忆不是简单的关键词匹配，而是基于向量相似度的语义检索。当你问怎么处理数据库连接时，即使记忆里没有精确匹配数据库连接这几个字，也能找到数据库连接池配置、数据库超时设置等相关记忆。

具体实现见第 9 节：向量嵌入。

#### 记忆优先级

不是所有记忆都一样重要。jcode 给记忆打分：

- **频率**：被引用越多次，分数越高
- **时效**：最近的信息比很久以前的更重要
- **相关性**：和当前任务越相关的分数越高
- **来源**：用户明确说的 > 自动推断的

#### 遗忘机制

记忆系统不是只增不减。它也有遗忘机制：

- 长期未被引用的记忆会被降权
- 相互矛盾的记忆会触发澄清（比如你之前说用 2 空格缩进，但现在项目配置是 4 空格，我该按哪个？）
- 过时的信息（如当前 Node 版本是 16 -> 实际已升级到 20）会被标记为过期

## 7. TUI 终端界面

### 一句话说明

TUI（Terminal User Interface，终端用户界面）是 jcode 的仪表盘。在终端里画出一个漂亮的交互界面，让你实时看到 Agent 在做什么、进度如何、当前在调用哪个工具、消耗了多少 Token。

### 业务价值

| 维度 | 说明 |
|------|------|
| **直观** | 不用读日志文件，一眼看到任务状态 |
| **实时** | 打字机效果展示模型输出，像在看 AI 思考 |
| **可操作** | 在界面里暂停、恢复、取消任务 |
| **轻量** | 不需要浏览器，SSH（安全远程连接协议）远程也能用 |

### 使用场景

1. **日常开发**：在终端里开着 jcode TUI，像多了个副屏监控
2. **远程服务器**：SSH（安全远程连接）到服务器，用 TUI 管理 jcode 任务
3. **演示/教学**：给团队演示 jcode 怎么工作的，TUI 比日志直观
4. **长时间任务**：跑一个 30 分钟的重构，TUI 显示实时进度条

### 界面布局

TUI 界面分为几个区域：

- **顶部状态栏**：显示版本号、当前会话 ID、使用的 Provider 和 Token 消耗量
- **任务计划面板**：显示当前任务的步骤列表，每步有状态标记（已完成/进行中/待处理）
- **实时状态面板**：当前步骤序号、进度百分比、耗时、Token 消耗
- **对话窗口**：Agent 和用户的对话历史，包含工具调用和结果
- **底部快捷键栏**：显示可用的键盘操作

### 核心设计

#### 声明式渲染

TUI 采用声明式渲染：每个组件（面板、进度条、对话窗口）声明自己的状态，框架负责把状态渲染成终端字符。这类似于 React（一种前端界面框架）的 UI = f(state) 思想，但在终端里实现。

好处是：状态变化时只需更新对应组件，不用整屏重绘，避免了闪烁。

#### 事件驱动更新

TUI 订阅 Agent 运行时的事件总线（见第 2 节），当事件发生时自动更新界面：

- 工具调用开始 -> 对话窗口显示工具名称
- 模型返回 -> 对话窗口显示打字机效果
- 步骤完成 -> 计划面板打勾
- Token 消耗 -> 状态栏更新数字

#### 键盘快捷键

所有操作都有键盘快捷键，不需要鼠标：

| 按键 | 功能 |
|------|------|
| P | 暂停当前任务 |
| R | 恢复暂停的任务 |
| C | 取消当前任务 |
| D | 查看详情（日志、Token 明细） |
| H | 帮助面板 |
| Q | 退出（任务在后台继续） |
| Tab | 切换面板焦点 |
| 上下箭头 | 滚动对话窗口 |

#### 自适应布局

TUI 根据终端窗口大小自动调整布局：

- 宽终端（大于 120 列）：双栏布局，计划 + 对话并排
- 窄终端（80-120 列）：单栏布局，面板上下排列
- 极窄终端（小于 80 列）：极简模式，只显示对话窗口

## 8. 上下文压缩

### 一句话说明

上下文压缩是 jcode 的笔记整理术。当对话越来越长、Token 快用完时，自动把历史对话压缩成精炼的摘要，保留关键信息，丢掉废话，让大模型始终有足够的上下文空间继续工作。

### 业务价值

| 维度 | 说明 |
|------|------|
| **突破 Token 限制** | 理论上可以处理无限长的任务，不受模型上下文窗口限制 |
| **降低成本** | 压缩后的上下文更短，每次调用消耗更少 Token |
| **提升质量** | 去掉噪声信息，模型聚焦在关键内容上 |
| **长任务支持** | 一个任务跑几个小时、几千轮对话，不会因为上下文溢出而崩溃 |

### 为什么需要上下文压缩？

大模型有一个上下文窗口的概念——它只能记住最近的 N 个 Token。比如 Claude 3.5 Sonnet 的上下文窗口是 200K Token，听起来很多，但在实际编码任务中：

- 一个文件可能有 1000 行，大约 3000 Token
- 读 10 个文件，大约 30000 Token
- 跑 20 轮对话（每轮含工具调用结果），大约 80000 Token
- 跑 50 轮，上下文就满了！

如果不压缩，Agent 要么忘记最早的信息（比如用户最初的需求），要么直接报错。上下文压缩解决了这个问题。

### 关键流程

```
对话历史（原始）
+----------------------------------------+
| 轮次 1: 用户说修复登录 bug             |
| 轮次 2: Agent 读了 5 个文件            |  <- 5000 Token
| 轮次 3: Agent 分析了代码结构           |
| ...                                    |
| 轮次 50: Agent 在修第 10 个文件        |  <- 180000 Token，快满了！
+----------------------------------------+
                |
                v 触发压缩
+----------------------------------------+
| 压缩结果                                |
|                                        |
| 任务目标: 修复登录页面 JWT 过期 bug     |
| 关键发现:                               |
| - 问题在 src/auth/login.ts:42           |
| - expiresIn 写成了 1000ms               |
| - 已修改文件: login.ts, auth.ts, ...    |
| - 待处理: 测试验证                      |
| 当前状态: 第 3 步/共 4 步               |
|                                        |  <- 压缩后只有 2000 Token
+----------------------------------------+
```

### 核心设计

#### 分层压缩策略

jcode 不是把所有内容一股脑压缩，而是分层处理：

1. **冗余去重**：同一段代码被反复读取？只保留第一次的完整内容，后续用引用替代
2. **工具输出摘要**：read_file 返回了 500 行代码，但 Agent 只改了 3 行 -> 只保留这 3 行和上下文
3. **对话摘要**：把 10 轮试错对话压缩成经过 10 轮调试，最终确定问题在 X
4. **结构化保留**：任务目标、当前进度、已修改文件列表 -> 这些必须保留，不能丢

#### 压缩触发时机

压缩不是满了再压，而是提前触发：

- **75% 阈值**：上下文使用率达到 75%，触发轻度压缩（去重、工具输出摘要）
- **90% 阈值**：触发深度压缩（对话摘要、冗余清理）
- **95% 阈值**：触发激进压缩（只保留核心任务信息）

#### 压缩质量保证

压缩后的摘要必须满足：

- **任务目标不丢失**：用户最初的需求必须保留
- **进度不丢失**：做到了哪一步、下一步是什么必须清楚
- **关键决策不丢失**：为什么选方案 A 不选方案 B 必须保留
- **可逆性**：如果压缩丢失了重要信息导致 Agent 出错，支持解压缩回退

#### 增量压缩

不是每次都重新压缩全部历史。而是：

- 维护一个压缩基准（已压缩的历史摘要）
- 新的对话追加到基准后面
- 当总长度再次超过阈值，只压缩新增部分，合并到基准

这样避免了重复压缩的开销，也让压缩更稳定。

## 9. 向量嵌入 / ONNX

### 一句话说明

向量嵌入是 jcode 的语义搜索引擎。它能把任何文本（代码、文档、对话）转换成一串数字（向量），然后通过数学计算找到语义上最相似的内容，支撑记忆检索、代码搜索、上下文匹配等功能。

### 用大白话解释向量嵌入

想象你有一个图书馆，里面有 10000 本书。你想找关于数据库连接池的书。

- **传统搜索**：只能匹配书名里包含数据库、连接池这些词的书。如果有一本书叫《MySQL 性能优化》，内容完全相关但书名没这些词，就搜不到。
- **向量搜索**：每本书都被转换成一个 768 维的坐标。语义相近的书，坐标也相近。《数据库连接池实战》和《MySQL 性能优化》的坐标非常接近，一搜就能找到。

### 业务价值

| 维度 | 说明 |
|------|------|
| **语义理解** | 搜怎么让程序跑更快能找到性能优化相关代码，即使没出现快字 |
| **离线运行** | 用 ONNX 本地推理，不需要联网调 API |
| **零成本** | 本地计算，不消耗 API Token |
| **隐私安全** | 代码不出本地，不需要上传到云端 |

### 为什么用 ONNX？

ONNX（Open Neural Network Exchange）是一个开放的神经网络模型格式。用 ONNX 的好处：

- **跨平台**：同一个模型文件在 macOS、Linux、Windows 上都能跑
- **高性能**：底层用 C++ 实现，比 Python 快 10-100 倍
- **无依赖**：不需要安装 PyTorch、TensorFlow（两种深度学习框架），Rust 直接加载 ONNX 模型
- **模型可选**：可以换不同的嵌入模型（BGE、E5、GTE 等），不需要改代码

### 关键流程

```
文本输入：修复数据库连接超时的问题
        |
        v
+------------------------+
|  1. 分词 (Tokenize)     |  把文本拆成词元
|  修复, 数据库,           |
|  连接, 超时,            |
|  的, 问题               |
+------------+-----------+
             |
             v
+------------------------+
|  2. ONNX 推理           |  加载嵌入模型，前向传播
|  模型: BGE-small-zh     |
|  输入: 词元序列         |
|  输出: 768维向量        |
+------------+-----------+
             |
             v
+------------------------+
|  3. 向量归一化          |  标准化向量，方便计算相似度
|  0.023, -0.15,         |
|  0.087, ..., 0.042     |
+------------+-----------+
             |
             v
+------------------------+
|  4. 存入向量索引        |  加入向量数据库
|  （Faiss / Annoy，两种高性能向量索引库）       |
+------------------------+
```

### 核心设计

#### 嵌入模型选择

jcode 支持多种嵌入模型，用户可以根据场景选择：

| 模型 | 维度 | 优势 | 适用场景 |
|------|------|------|----------|
| BGE-small-zh（BGE 中文小模型） | 512 | 中文效果好，体积小 | 中文项目 |
| BGE-large-en（BGE 英文大模型） | 1024 | 英文效果好，精度高 | 英文项目 |
| E5-base-v2（E5 通用模型） | 768 | 通用性好 | 混合项目 |
| GTE-small（GTE 轻量模型） | 384 | 速度最快 | 实时搜索 |
| CodeBERT（代码语义专用模型） | 768 | 代码专用 | 代码搜索 |

#### 混合检索

只用向量搜索不够，jcode 采用混合检索策略：

搜索结果 = 向量搜索(语义相似) x 0.7 + 关键词搜索（BM25，一种经典的关键词匹配算法） x 0.3

- 向量搜索负责语义理解：搜登录能找到 sign in
- 关键词搜索负责精确匹配：搜 JWT_SECRET 必须精确匹配

两者互补，召回率更高。

#### 增量索引

代码仓库可能有上万个文件，全部嵌入一遍很慢。jcode 采用增量索引：

- 首次索引：全量嵌入所有文件
- 后续更新：只嵌入修改过的文件
- Git 感知：通过 git diff 精确定位变更文件

#### 应用场景

向量嵌入在 jcode 中支撑了多个功能：

| 功能 | 说明 |
|------|------|
| 记忆检索 | 从长期记忆中搜索相关经验 |
| 代码搜索 | 找项目中所有处理 JWT 的地方 |
| 上下文选择 | 从大仓库中筛选最相关的文件放入上下文 |
| 相似问题推荐 | 这个报错之前遇到过，解决方案是... |
| 代码克隆检测 | 识别重复代码，建议抽取公共函数 |

## 10. 桌面应用

### 一句话说明

桌面应用是 jcode 的图形化外壳。用 Tauri 框架构建的跨平台桌面应用，让不习惯命令行的用户也能用上 jcode 的全部能力，提供项目面板、可视化配置、一键操作等体验。

### 业务价值

| 维度 | 说明 |
|------|------|
| **降低门槛** | 不需要学命令行，打开 App 就能用 |
| **可视化** | 项目结构树、任务进度图、Token 消耗图表 |
| **配置管理** | 图形化配置 Provider、API Key（应用程序接口密钥）、模型参数 |
| **跨平台** | macOS / Windows / Linux 统一体验 |

### 使用场景

1. **新手入门**：第一次用 jcode，桌面 App 引导你配置、选择项目、发出第一个指令
2. **项目管理**：同时管理多个项目，切换方便
3. **团队协作**：可视化查看团队共享记忆、编码规范
4. **监控面板**：实时查看 Token 消耗、任务成功率、模型调用延迟

### 核心设计

#### Tauri 架构

桌面应用基于 Tauri 框架，架构如下：

```
+----------------------------------+
|         前端（WebView，内嵌的浏览器组件）            |
|     React / Vue / Svelte（三种主流前端界面框架）         |
|     负责 UI 渲染和交互            |
+----------------------------------+
|        Tauri Bridge (IPC)        |
|     前后端通信桥梁                |
+----------------------------------+
|        Rust 后端                  |
|     调用 jcode 核心库             |
|     文件系统、进程管理、配置       |
+----------------------------------+
```

为什么选 Tauri 而不是 Electron（另一种桌面应用框架，基于 Node.js（JavaScript 运行时）和 Chromium（Chrome 浏览器的开源内核））？

| 对比 | Tauri | Electron |
|------|-------|----------|
| 安装包大小 | 约 10MB | 约 150MB |
| 内存占用 | 约 50MB | 约 200MB |
| 启动速度 | 小于 1 秒 | 3-5 秒 |
| 前端框架 | 任意 | 任意 |
| 后端语言 | Rust | Node.js |

jcode 核心本身就是 Rust 写的，用 Tauri 可以直接复用核心代码，不需要 Node.js 中间层。

#### 功能模块

桌面应用提供以下功能模块：

1. **项目面板**：项目列表、最近打开、项目结构树
2. **任务面板**：当前任务状态、历史任务列表、任务详情
3. **对话窗口**：和 Agent 的对话界面，支持 Markdown（一种轻量级文本标记语言）渲染
4. **配置面板**：Provider 配置、模型选择、API Key（应用程序接口密钥）管理
5. **记忆面板**：查看和管理长期记忆
6. **监控面板**：Token 消耗、响应延迟、成功率图表
7. **设置面板**：主题、语言、快捷键、自动更新

#### 与 CLI（命令行界面）的关系

桌面应用和命令行版本共享同一套核心代码，功能完全对等：

- CLI（命令行界面）有的功能，桌面应用都有（反过来不一定）
- 桌面应用是 CLI（命令行界面）的超集，提供更多可视化功能
- 配置和记忆在 CLI（命令行界面）和桌面应用之间同步

## 11. 工具系统

### 一句话说明

工具系统是 jcode 的工具箱。Agent 不是只能想，还能做：读文件、写代码、跑命令、搜代码、查文档、管理 Git……30+ 个工具让 Agent 能真正操作你的代码仓库。

### 业务价值

| 维度 | 说明 |
|------|------|
| **能力边界** | Agent 能做什么，完全取决于工具有多少 |
| **安全性** | 每个工具都有权限控制，危险操作需确认 |
| **可扩展** | 用户可以自定义工具，满足特殊需求 |
| **可观测** | 每个工具调用都有日志，可审计 |

### 核心设计

#### 工具注册机制

新增工具非常简单：实现一个 trait（Rust 语言的接口，类似其他语言的 interface），注册到工具注册表即可。

```rust
// 伪代码示意
trait Tool {
    fn name(&self) -> &str;           // 工具名称
    fn description(&self) -> &str;    // 工具描述（给大模型看的）
    fn parameters(&self) -> Schema;   // 参数定义（JSON Schema）
    async fn execute(&self, params: Value) -> Result<Value>;  // 执行逻辑
}
```

这个设计的好处：

- **大模型自动理解**：description 和 parameters 会被注入到 Prompt 中，大模型自己决定什么时候调用哪个工具
- **类型安全**：参数定义用 JSON Schema，调用时自动校验
- **易于扩展**：第三方可以写自己的工具插件

#### 权限分级

不是所有工具都能随便调用。jcode 有三级权限：

| 级别 | 权限 | 示例工具 |
|------|------|----------|
| **只读** | 只能读，不能改 | read_file、grep_search、git_log |
| **写入** | 可以修改文件 | write_file、edit_file、git_commit |
| **危险** | 可能造成破坏性后果 | exec_command（rm -rf）、git_push --force |

- 只读工具：Agent 可以自由调用
- 写入工具：首次使用时弹窗确认，可勾选本次会话不再询问
- 危险工具：每次调用都需要用户确认

#### 工具调用格式

大模型返回的不是自然语言，而是结构化的工具调用指令：

```json
{
  "tool": "read_file",
  "params": {
    "path": "src/auth/login.ts",
    "offset": 40,
    "limit": 10
  }
}
```

Agent 运行时解析这个指令，调用真正的工具函数，把结果返回给大模型。大模型看到结果后，决定下一步做什么。

#### 工具组合

单个工具的能力有限，但组合起来就很强大。例如：

```
'修复这个 bug' ->
  1. grep_search('JWT')      -> 找到相关文件
  2. read_file('login.ts')   -> 理解代码
  3. git_log('login.ts')     -> 看谁改的、什么时候改的
  4. edit_file('login.ts')   -> 修改代码
  5. exec_command('npm test（Node.js 包管理器的测试命令）')-> 跑测试验证
  6. git_diff()              -> 查看变更
  7. git_commit('fix: ...')  -> 提交
```
