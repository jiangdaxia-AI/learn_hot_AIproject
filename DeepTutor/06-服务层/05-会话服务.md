# 05-会话服务（Session Service）

> 把每一次对话都完整地"记住"——DeepTutor 的会话服务就像一个永不疲倦的秘书，记录你和 AI 的每一轮对话，自动整理上下文，确保对话不会"失忆"。

---

## 1. 整体概述

会话服务是 DeepTutor 的"记忆系统"。它负责管理所有对话的存储、检索、上下文构建和轮次管理。你可以把它想象成一座图书馆——每个对话是一个书架，每轮对话是一本书，每本书里的每一页（消息）都被精心归档。

**核心文件：**

| 文件 | 路径 | 职责 |
|------|------|------|
| `protocol.py` | `deeptutor/services/session/protocol.py` | 会话存储的"接口契约" |
| `base_session_manager.py` | `deeptutor/services/session/base_session_manager.py` | 会话管理的抽象基类 |
| `unified_session_manager.py` | `deeptutor/services/session/unified_session_manager.py` | 统一会话管理器 |
| `sqlite_store.py` | `deeptutor/services/session/sqlite_store.py` | SQLite 存储实现 |
| `pocketbase_store.py` | `deeptutor/services/session/pocketbase_store.py` | PocketBase 存储实现 |
| `context_builder.py` | `deeptutor/services/session/context_builder.py` | 上下文构建器 |
| `turn_runtime.py` | `deeptutor/services/session/turn_runtime.py` | 轮次运行时管理器 |
| `source_inventory.py` | `deeptutor/services/session/source_inventory.py` | 附件来源清单管理 |

## 2. 存储接口契约（protocol.py）

*文件：`deeptutor/services/session/protocol.py`*

### 2.1 `SessionStoreProtocol`（会话存储协议）

*文件位置：protocol.py，第 13-82 行*

```python
@runtime_checkable
class SessionStoreProtocol(Protocol):
    async def create_session(self, title, session_id) -> dict[str, Any]: ...
    async def get_session(self, session_id) -> dict[str, Any] | None: ...
    async def add_message(self, session_id, role, content, ...) -> int: ...
    async def get_messages(self, session_id) -> list[dict[str, Any]]: ...
    ...
```

**业务含义：** 这是一个"接口合同"——不管底层用什么数据库（SQLite 还是 PocketBase），都必须实现这些方法。就像不管用 iPhone 还是 Android，打电话的"拨号"功能都是一样的。

**核心方法清单：**

| 方法 | 业务含义 | 大白话 |
|------|----------|--------|
| `create_session()` | 创建新会话 | 开一个新笔记本 |
| `get_session()` | 获取会话信息 | 找到某本笔记本 |
| `ensure_session()` | 确保会话存在（不存在则创建） | 找不到就新建一本 |
| `create_turn()` | 创建新轮次 | 开始新的一轮对话 |
| `get_turn()` | 获取轮次信息 | 查看某轮对话 |
| `get_active_turn()` | 获取当前活跃轮次 | 找到正在进行的对话 |
| `update_turn_status()` | 更新轮次状态 | 标记对话状态（完成/失败/取消） |
| `append_turn_event()` | 追加轮次事件 | 记录对话中的每个动作 |
| `add_message()` | 添加消息 | 在笔记本里写一行 |
| `get_messages()` | 获取所有消息 | 翻看笔记本全部内容 |
| `get_messages_for_context()` | 获取上下文消息（支持分支） | 只看当前路径上的记录 |
| `delete_session()` | 删除会话 | 撕掉一本笔记本 |
| `update_summary()` | 更新对话摘要 | 在本子封面写一句话概括 |
| `update_session_title()` | 更新会话标题 | 给本子改个名字 |
| `list_sessions()` | 列出会话列表 | 查看书架上有哪些本子 |

**大白话解释：** 这个协议就像"开书店的统一标准"——不管你的店面是木制的还是钢架的，你必须能存书、找书、翻书、删书。SQLite 和 PocketBase 就是两种不同的"店面"。

## 3. 会话管理基类（base_session_manager.py）

*文件：`deeptutor/services/session/base_session_manager.py`*

### 3.1 `BaseSessionManager`（会话管理抽象基类）

*文件位置：base_session_manager.py，第 23-254 行*

```python
class BaseSessionManager(ABC):
    MAX_SESSIONS = 100  # 最多保留 100 个会话

    def __init__(self, module_name: str):
        self.module_name = module_name
```

**业务含义：** 这是所有会话管理器的"模板"。它使用 JSON 文件存储会话数据，提供了会话的增删改查（CRUD）等通用功能。

**子类必须实现的抽象方法：**
- `_get_session_id_prefix()`：返回会话 ID 前缀（如 `"solve_"`、`"chat_"`）
- `_get_default_title()`：返回新会话的默认标题
- `_create_session_data()`：创建模块特定的会话数据结构
- `_get_session_summary()`：创建会话摘要（用于列表展示）

**`sessions_file` 属性（第 52-54 行）：**
- **业务做什么：** 返回会话存储的 JSON 文件路径
- **大白话解释：** 告诉系统"笔记本放在哪个抽屉里"

**`create_session(self, title, **kwargs)`（第 115-146 行）：**
- **业务做什么：** 创建新会话
- **输入：** `title`（会话标题，可选）、`**kwargs`（额外参数如模式、工具列表）
- **输出：** 会话字典，包含 `session_id`、`title`、`messages`、`created_at` 等
- **关键逻辑：**
  1. 生成唯一会话 ID：`{前缀}{时间戳}_{随机字符}`
  2. 设置默认标题
  3. 合并模块特定的数据
  4. 插入到会话列表的最前面
  5. 如果超过 `MAX_SESSIONS`（100），删除最旧的会话
- **大白话解释：** 买一本新笔记本，写上编号和标题，放在书架最前面

**`get_session(self, session_id)`（第 148-153 行）：**
- **业务做什么：** 根据会话 ID 查找会话
- **输入：** `session_id`
- **输出：** 会话字典，找不到返回 `None`
- **大白话解释：** 按编号找笔记本

**`update_session(self, session_id, messages, title, **kwargs)`（第 155-183 行）：**
- **业务做什么：** 更新会话信息（消息列表、标题等），并把会话移到列表最前面
- **关键逻辑：** 更新后把会话从原来的位置取出，插入到列表开头（最近使用的排在前面）
- **大白话解释：** 修改笔记本内容后，把它放到书架最方便拿的位置

**`add_message(self, session_id, role, content, **metadata)`（第 185-213 行）：**
- **业务做什么：** 向会话中添加一条消息
- **输入：** `session_id`、`role`（"user"/"assistant"）、`content`（消息内容）、`**metadata`（额外元数据）
- **关键逻辑：** 如果会话标题还是默认标题，且这是用户的第一条消息，就自动用消息的前 50 个字作为标题
- **大白话解释：** 在笔记本里写一条新记录，如果本子还没标题，就用第一句话当前几个字做标题

**`list_sessions(self, limit, include_messages)`（第 215-225 行）：**
- **业务做什么：** 列出会话列表
- **输入：** `limit`（最多返回多少条）、`include_messages`（是否包含消息内容）
- **输出：** 会话列表（按更新时间倒序）
- **大白话解释：** 看一眼书架上最近用了哪些本子

**`delete_session(self, session_id)`（第 227-237 行）：**
- **业务做什么：** 删除指定会话
- **输出：** `True`（删除成功）/ `False`（未找到）
- **大白话解释：** 把一本笔记本从书架上拿掉

**`clear_all_sessions(self)`（第 239-243 行）：**
- **业务做什么：** 清空所有会话
- **输出：** 被清空的会话数量
- **大白话解释：** 清空整个书架

## 5. SQLite 存储实现（sqlite_store.py）

*文件：`deeptutor/services/session/sqlite_store.py`*

### 5.1 `SQLiteSessionStore`（SQLite 会话存储）

*文件位置：sqlite_store.py，第 96 行开始*

**业务含义：** SQLiteSessionStore 是会话服务的"主力存储方案"。它使用 SQLite 数据库来持久化存储会话、消息、轮次、轮次事件、笔记本条目等。这是默认的本地存储方案，适用于单用户或小规模部署。

**数据库表结构：**

| 表名 | 用途 | 大白话 |
|------|------|--------|
| `sessions` | 会话基本信息 | 笔记本的目录 |
| `messages` | 消息记录 | 笔记本里的每一行字 |
| `turns` | 轮次记录 | 每次对话的"回合" |
| `turn_events` | 轮次事件流 | 回合中发生的每个动作 |
| `notebook_entries` | 笔记本条目（测验题） | 错题本 |
| `notebook_categories` | 笔记本分类 | 错题本的分类标签 |
| `notebook_entry_categories` | 条目与分类关联 | 哪道题属于哪个分类 |

**`_initialize(self)`（第 119-281 行）：**
- **业务做什么：** 初始化数据库，创建所有表、索引，并执行数据库迁移
- **关键逻辑：** 包含了完整的数据库迁移逻辑——自动检测旧数据库的字段变化并补齐
- **大白话解释：** 开书店时先搭好书架——确保所有的表、索引都存在，旧数据能自动升级

**会话 CRUD 方法：**

**`create_session(self, title, session_id)`（第 449-454 行）：**
- **业务做什么：** 在 SQLite 中创建新会话
- **输入：** `title`（标题）、`session_id`（可选，不提供则自动生成）
- **输出：** 会话字典
- **大白话解释：** 在数据库里登记一本新笔记本

**`get_session(self, session_id)`（第 456-512 行）：**
- **业务做什么：** 获取会话信息，同时查询关联的最新轮次状态和活跃轮次 ID
- **关键逻辑：** 使用 SQL 子查询同时获取 `status`、`active_turn_id`、`capability` 等字段
- **大白话解释：** 查一本笔记本的信息，同时看看它有没有正在进行的对话

**消息管理方法：**

**`add_message(self, session_id, role, content, ..., parent_message_id)`（第 762-851 行）：**
- **业务做什么：** 向会话添加一条消息，支持编辑分支（branching）
- **关键逻辑：** 支持 `parent_message_id`——可以指定消息的父消息，实现"对话分支"。就像你可以从对话的某个节点开始"如果当时这样说会怎样"的平行对话
- **大白话解释：** 在笔记本里写一行，如果指定了"接在哪一行后面"，就创建一条分支路径

**`get_messages_for_context(self, session_id, leaf_message_id)`（第 1211-1267 行）：**
- **业务做什么：** 获取上下文消息，支持分支感知
- **关键逻辑：** 如果指定了 `leaf_message_id`，会沿着 `parent_message_id` 链向上追溯，只返回当前分支的祖先消息，排除兄弟分支
- **大白话解释：** 只看当前路径上的对话记录，不看边上岔路的内容

**`get_message_path(self, session_id, leaf_message_id)`（第 1173-1206 行）：**
- **业务做什么：** 获取从根消息到指定消息的完整路径
- **大白话解释：** 画出从对话开始到当前位置的完整路线图

**轮次管理方法：**

**`create_turn(self, session_id, capability)`（第 538-579 行）：**
- **业务做什么：** 创建新轮次，并检查是否有未完成的轮次
- **关键逻辑：** 如果会话已有活跃轮次（`status='running'`），抛出 `RuntimeError`——每个会话同时只能有一个活跃轮次
- **大白话解释：** 开始新的一轮对话前，先检查上一轮有没有结束

**`update_turn_status(self, turn_id, status, error)`（第 639-655 行）：**
- **业务做什么：** 更新轮次状态（`completed`/`failed`/`cancelled`）
- **大白话解释：** 标记这轮对话的状态——完成了、出错了、还是被取消了

**`append_turn_event(self, turn_id, event)`（第 657-704 行）：**
- **业务做什么：** 向轮次追加事件，自动分配序列号
- **关键逻辑：** 使用 `INSERT OR REPLACE` 和 `UNIQUE(turn_id, seq)` 约束，防止重复事件
- **大白话解释：** 记录对话中发生的每个动作，给每个动作编号

**`delete_turn_by_message(self, session_id, message_id)`（第 987-1104 行）：**
- **业务做什么：** 删除一对消息（用户消息 + 助手回复）及其关联的轮次和事件
- **关键逻辑：**
  1. 如果删除的是用户消息，找到紧随其后的助手消息
  2. 如果删除的是助手消息，找到它前面的用户消息
  3. 如果对应轮次正在运行中，拒绝删除
  4. 同时清理关联的轮次事件和附件
- **大白话解释：** 删除一轮对话——同时删掉问题和回答，以及相关的所有记录

**笔记本条目管理：**

**`upsert_notebook_entries(self, session_id, items)`（第 1419-1511 行）：**
- **业务做什么：** 插入或更新笔记本条目（测验题记录）
- **关键逻辑：** 使用 `ON CONFLICT(session_id, turn_id, question_id) DO UPDATE` 实现 upsert——同一轮次的同一道题只保留一条记录，新的答案会覆盖旧的
- **大白话解释：** 把测验题记录存入错题本，如果同一道题之前存过，就更新答案

**`list_notebook_entries(self, ...)`（第 1543-1609 行）：**
- **业务做什么：** 列出笔记本条目，支持按分类、收藏状态、正确性筛选
- **大白话解释：** 翻看错题本，可以按分类、是否收藏、是否答对来筛选

**导入会话：**

**`import_session(self, session_id, title, ...)`（第 887-976 行）：**
- **业务做什么：** 导入外部会话（如 Claude Code 或 Codex 的历史对话）
- **关键逻辑：** 导入的会话带有 `imported_` 前缀的 ID，存储在同一个表中但通过 ID 前缀区分
- **大白话解释：** 把其他 AI 助手的对话记录搬进 DeepTutor 的书架，标上"外部导入"的标签

**`get_sqlite_session_store()`（第 1836-1841 行）：**
- **业务做什么：** 获取全局单例的 SQLiteSessionStore
- **大白话解释：** 获取唯一的 SQLite 书架管理员

## 6. PocketBase 存储实现（pocketbase_store.py）

*文件：`deeptutor/services/session/pocketbase_store.py`*

### 6.1 `PocketBaseSessionStore`（PocketBase 会话存储）

*文件位置：pocketbase_store.py，第 102 行开始*

**业务含义：** PocketBaseSessionStore 是会话服务的"多用户存储方案"。当 DeepTutor 需要支持多用户时，使用 PocketBase（一个轻量级后端服务）作为数据库。它通过 `user_id` 字段来隔离不同用户的数据。

**与 SQLite 存储的关键区别：**
- SQLite 是本地文件数据库，每个用户一个文件
- PocketBase 是远程服务，所有用户共享一个数据库，通过 `user_id` 过滤隔离

**`_current_user_id()`（第 68-86 行）：**
- **业务做什么：** 获取当前请求的上下文用户 ID，用于数据隔离
- **大白话解释：** 确定"现在是谁在操作"，确保用户只能看到自己的数据

**`_find_session_record(pb, session_id, user_id)`（第 89-99 行）：**
- **业务做什么：** 在 PocketBase 中查找指定用户拥有的会话记录
- **关键逻辑：** 使用 `session_id` 和 `user_id` 双重过滤，这是多用户安全的关键保障
- **大白话解释：** 在公共书架上找到"属于某个人的特定笔记本"

**`append_turn_event(self, turn_id, event)`（第 659-672 行）：**
- **业务做什么：** 追加轮次事件（不立即写入 PocketBase，只在内存中分配序列号）
- **关键设计：** 事件先写入本地的 `events.jsonl` 文件（由 `turn_runtime` 的 `_mirror_event_to_workspace` 负责），等轮次完成后再批量写入 PocketBase。这样设计是为了避免实时写入导致的延迟
- **大白话解释：** 先把动作记在草稿纸上，等对话结束再一次性抄到正式记录本上

**`_flush_turn_events(self, turn_id)`（第 585-638 行）：**
- **业务做什么：** 从本地 JSONL 文件读取轮次事件，批量写入 PocketBase
- **大白话解释：** 把草稿纸上的内容正式抄录到数据库

## 7. 上下文构建器（context_builder.py）

*文件：`deeptutor/services/session/context_builder.py`*

### 7.1 `ContextBuilder`（上下文构建器）

*文件位置：context_builder.py，第 104-467 行*

```python
class ContextBuilder:
    def __init__(
        self,
        store: SessionStoreProtocol,
        history_budget_ratio: float = 0.35,   # 对话历史占 token 预算的 35%
        summary_target_ratio: float = 0.40,   # 摘要占对话历史预算的 40%
    ) -> None:
```

**业务含义：** ContextBuilder 是 DeepTutor 的"记忆压缩器"。当对话越来越长，token 消耗越来越大时，它会把较早的对话压缩成摘要，确保 LLM 始终能看到最相关的上下文，同时不会超出 token 限制。

**核心概念：**
- **Token 预算：** LLM 一次能处理的最大 token 数。ContextBuilder 把预算的 35% 分配给对话历史。
- **摘要目标：** 对话历史中，约 40% 的 token 用来放摘要，剩下的留给最近的消息。
- **滚动摘要：** 随着对话增长，较早的部分被压缩成摘要，较新的部分保持原样。

**`build(self, session_id, llm_config, language, ...)`（第 348-467 行）：**
- **业务做什么：** 构建当前轮次的对话上下文
- **输入：** 会话 ID、LLM 配置、语言、叶子消息 ID（支持分支）
- **输出：** `ContextBuildResult`（包含对话历史、摘要、上下文文本、token 数等）

**执行流程（大白话解释）：**

1. **获取消息（第 357-363 行）：** 从存储中获取当前分支的消息。如果指定了 `leaf_message_id`，只获取祖先路径的消息。
2. **计算预算（第 367-369 行）：** 算出历史预算、摘要预算和最近消息预算各是多少 token。
3. **检查现有摘要（第 371-384 行）：** 读取之前已经压缩的摘要及其水位线（`summary_up_to_msg_id`）。如果水位线指向的消息不在当前分支上（比如用户切换了分支），就丢弃旧摘要。
4. **快速路径（第 386-396 行）：** 如果当前上下文（摘要 + 未压缩消息）的 token 数还没超过预算，直接返回，不用压缩。
5. **选择最近消息（第 398-403 行）：** 从最新消息开始往前数，直到 token 数接近"最近消息预算"，这些消息保持原样。
6. **构建前缀文本（第 404 行）：** 把不在"最近消息"范围内的消息拼成文本，准备压缩。
7. **反漂移策略（第 406-423 行）：** 如果原始前缀文本还能装进"重建预算"，就从原始消息重新生成摘要，而不是在旧摘要上叠加（避免层层压缩导致信息丢失）。如果装不下，才把旧摘要和新消息合并。
8. **调用 LLM 生成摘要（第 427-437 行）：** 调用 LLM 按结构化格式生成摘要，包含：目标、关键事实、决定与偏好、进展、待办事项。
9. **保存摘要（第 439-446 行）：** 如果摘要生成成功，更新存储中的摘要和水位线。
10. **截断保护（第 453-457 行）：** 如果最终还是超了预算，从最旧的消息开始逐条删除。

**`_summarize(self, session_id, language, source_text, summary_budget, ...)`（第 182-346 行）：**
- **业务做什么：** 调用 LLM 将对话历史压缩成结构化摘要
- **关键逻辑：** 
  - System prompt 要求 LLM 按五个部分组织摘要：目标、关键事实与上下文、决定与偏好、进展、待办事项
  - 支持中英文双语 prompt
  - 如果摘要长度接近硬上限（95%），就裁掉不完整的最后一行
- **大白话解释：** 请 LLM 帮忙把长对话浓缩成几个要点，就像把一本书的内容写成一页纸的读书笔记

**辅助函数：**

**`count_tokens(text)`（第 23-33 行）：**
- **业务做什么：** 估算文本的 token 数量
- **大白话解释：** 数一数这段文字有多"重"——token 数越多，占用 LLM 的处理空间越大

**`trim_incomplete_tail(text)`（第 36-45 行）：**
- **业务做什么：** 删除被截断的摘要的最后一行
- **大白话解释：** 如果 LLM 生成的摘要被截断了，把最后那句不完整的话删掉

**`format_messages_as_transcript(text)`（第 48-61 行）：**
- **业务做什么：** 把消息列表格式化为对话文本
- **大白话解释：** 把"User: xxx\nAssistant: yyy"这样的格式变成可读的对话记录

## 8. 轮次运行时管理器（turn_runtime.py）

*文件：`deeptutor/services/session/turn_runtime.py`*

### 8.1 `TurnRuntimeManager`（轮次运行时管理器）

*文件位置：turn_runtime.py，第 607 行开始*

**业务含义：** TurnRuntimeManager 是会话服务的"调度中心"。它负责管理每一轮对话的完整生命周期——从接收用户消息、创建轮次、执行 AI 处理、推送事件流，到最终保存结果。

**`start_turn(self, payload)`（第 668-836 行）：**
- **业务做什么：** 启动一轮新的对话处理
- **输入：** `payload`（包含会话 ID、用户消息、工具列表、知识库等）
- **输出：** `(session, turn)` 元组
- **执行流程（大白话解释）：**
  1. 解析能力类型（chat / deep_solve 等）
  2. 验证配置参数
  3. 确保会话存在
  4. 处理角色设定（persona）
  5. 处理 LLM 模型选择
  6. 恢复孤儿轮次（服务器重启后残留的"运行中"轮次）
  7. 创建新轮次
  8. 启动异步任务执行对话处理
- **大白话解释：** 收到用户消息后，做好一切准备工作，然后启动一个后台任务来处理

**`regenerate_last_turn(self, session_id, overrides)`（第 838-946 行）：**
- **业务做什么：** 重新生成上一轮对话（用户想换个回答）
- **关键逻辑：** 删除上一次的助手回复，保留用户消息，用新参数重新执行
- **大白话解释：** "刚才的回答不满意，换个说法再来一次"

**`cancel_turn(self, turn_id)`（第 948-964 行）：**
- **业务做什么：** 取消正在进行的轮次
- **大白话解释：** "别说了，停下"

**`subscribe_turn(self, turn_id, after_seq)`（第 995-1092 行）：**
- **业务做什么：** 订阅轮次的事件流（用于实时推送对话进度）
- **关键逻辑：**
  1. 先推送已持久化的事件（backlog）
  2. 再推送内存中的事件（live backlog）
  3. 然后持续监听新的实时事件
  4. 如果轮次已结束但没收到 DONE 事件，合成一个 DONE 事件
- **大白话解释：** 打开"直播频道"——先看回放（已发生的事件），再实时看直播（正在发生的事件）

**`_run_turn(self, execution)`（第 1155-1839 行）：**
- **业务做什么：** 执行一轮对话的核心逻辑（异步任务的主体）
- **这是 turn_runtime 最核心的方法，约 700 行，包含以下关键步骤：**

1. **解析附件（第 1259-1331 行）：** 处理用户上传的文件，提取文本内容，持久化到附件存储
2. **处理追问上下文（第 1333-1346 行）：** 如果是测验题的追问，自动注入题目上下文
3. **构建对话历史（第 1348-1362 行）：** 调用 ContextBuilder 构建压缩后的对话上下文
4. **加载记忆（第 1363-1364 行）：** 读取长期记忆（L3 记忆层）
5. **加载角色设定（第 1366-1386 行）：** 加载用户选择的 persona（角色人格）
6. **加载技能清单（第 1388-1413 行）：** 加载用户可用的技能列表
7. **构建来源清单（第 1420-1457 行）：** 为 chat 模式构建"附件来源索引"（source inventory）
8. **处理引用的知识库/笔记本/历史（第 1458-1577 行）：** 加载用户引用的笔记本记录、历史对话、题库等
9. **组装统一上下文（第 1613-1659 行）：** 把所有信息打包成 `UnifiedContext`
10. **执行对话编排（第 1661-1681 行）：** 调用 `ChatOrchestrator` 执行 AI 对话处理
11. **保存结果（第 1692-1720 行）：** 保存助手消息、生成标题
12. **异常处理（第 1745-1825 行）：** 处理取消、错误等异常情况

**`_maybe_generate_session_title(self, execution, session_id, ui_language)`（第 1872-1985 行）：**
- **业务做什么：** 用 LLM 自动生成会话标题
- **关键逻辑：** 只在标题还是 "New conversation" 时触发；使用第一轮用户消息和助手回复来生成标题；结果经过清理（去掉引号、前缀、markdown 标记等）
- **大白话解释：** 第一轮对话结束后，请 LLM 根据对话内容起一个简短的名字

**`_sanitize_session_title(raw)`（第 135-163 行）：**
- **业务做什么：** 清理 LLM 生成的标题中的噪音（引号、前缀、表情符号等）
- **大白话解释：** 把 LLM 生成的"标题：'关于微积分的学习'"变成干净的"关于微积分的学习"

## 9. 来源清单管理（source_inventory.py）

*文件：`deeptutor/services/session/source_inventory.py`*

### 9.1 `SourceInventory`（来源清单）

*文件位置：source_inventory.py，第 68-101 行*

**业务含义：** SourceInventory 管理每轮对话中用户附加的"来源材料"——包括笔记本记录、电子书、附件文件、历史对话、题库等。它确保 LLM 能看到当前轮次和之前轮次附加的所有来源，但不会在分支之间泄漏。

**核心设计：**
- **新鲜来源（fresh）：** 当前轮次附加的，展示完整预览
- **历史来源（historical）：** 之前轮次附加的，只展示一行摘要（ID、名称、大小、出现在第几轮）
- **分支隔离：** 沿着 `parent_message_id` 链追溯，不同分支的来源互不干扰
- **去重：** 同一个来源如果在多轮中出现，只保留最新版本，新鲜来源优先于历史来源

**`build_inventory(self, store, ...)`（第 108-162 行）：**
- **业务做什么：** 构建当前轮次的来源清单
- **输入：** 存储实例、会话 ID、叶子消息 ID、当前轮次序号、各种来源引用
- **输出：** `SourceInventory` 对象
- **大白话解释：** 整理"参考资料清单"——这一轮用户给了哪些资料，之前轮次给过哪些资料，都列清楚

**`render_manifest(self, inv)`（第 165-189 行）：**
- **业务做什么：** 把来源清单渲染成 LLM 可读的文本
- **输出：** `(manifest_text, source_index)`——manifest_text 是给 LLM 看的清单文本，source_index 是 `{source_id: full_text}` 的字典
- **大白话解释：** 把参考资料清单写成 LLM 能看懂的一段话，同时准备好参考资料全文，方便 LLM 随时查阅

**`serialize_referenced_transcript(meta, messages, language)`（第 644-713 行）：**
- **业务做什么：** 把引用的外部对话序列化为清晰的文本
- **关键设计：** 对于外部 AI 助手的对话，会明确标注"这是用户与外部 AI 的对话，不是你（当前 AI）的对话"，防止模型混淆身份
- **大白话解释：** 把其他对话的聊天记录转成文字，并明确标注"这是别人的对话，不是你的"

```
用户发送消息 "帮我解释一下微积分"

        ├──────────────────────────────────────┐
        │  _run_turn() 异步执行                  │
        │                                       │
        │  ├─ 解析附件 → 提取文本                │
        │  ├─ 处理追问上下文                     │
        │  ├─ ContextBuilder.build()             │
        │  │   ├─ 获取消息历史                    │
        │  │   ├─ 计算 token 预算                 │
        │  │   ├─ 压缩旧消息 → 生成摘要            │
        │  │   └─ 返回 ContextBuildResult         │
        │  ├─ 加载记忆、角色、技能                │

        │  ├─ ChatOrchestrator.handle() → AI 处理 │
        │  ├─ 保存助手消息                       │
        │  ├─ 生成会话标题                        │
        │  └─ 更新轮次状态为 completed            │
        │                                       │
        ▼                                       │
   subscribe_turn() 实时推送事件流 ◄──────────────┘
        │
        └─ 前端收到每个事件，展示对话进度
```

## 11. 一句话总结

会话服务是 DeepTutor 的"记忆中枢"——它把每一轮对话都安全地存储下来，智能地压缩长对话以节省 token，支持对话分支和重新生成，还能在不同用户之间严格隔离数据，确保 AI 永远不会"失忆"也不会"串台"。
