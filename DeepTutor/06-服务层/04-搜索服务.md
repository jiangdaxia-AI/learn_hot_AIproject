## 1. 整体概述

搜索服务是 DeepTutor 的"外脑"——当 AI 需要查找最新信息时，它会调用这个服务去互联网上搜索，然后把结果整理成结构化的答案返回。它支持 Baidu、Brave、Tavily、Serper、Jina、DuckDuckGo、Perplexity、SearXNG、Exa 等十余种搜索引擎，并且可以自动在它们之间切换。

**核心文件：**

| 文件 | 路径 | 职责 |
|------|------|------|
| `__init__.py` | `deeptutor/services/search/__init__.py` | 服务入口，`web_search()` 函数 |
| `base.py` | `deeptutor/services/search/base.py` | 所有搜索引擎的抽象基类 |
| `types.py` | `deeptutor/services/search/types.py` | 搜索结果的统一数据结构 |
| `consolidation.py` | `deeptutor/services/search/consolidation.py` | 把原始搜索结果整理成格式化答案 |

## 2. 数据模型（types.py）

*文件：`deeptutor/services/search/types.py`*

搜索服务定义了三个核心数据结构，它们就像三张"标准表格"——不管底层的搜索引擎返回什么格式的数据，最终都会被填入这三张表格里。

### 2.1 `Citation`（引用）

*文件位置：types.py，第 13-28 行*

```python
@dataclass
class Citation:
    id: int
    reference: str  # 例如 "[1]"
    url: str
    title: str = ""
    snippet: str = ""
    ...
```

**业务含义：** Citation 代表一条"引用来源"。就像写论文时需要标注参考文献，AI 回答问题时也需要告诉用户"这个信息来自哪里"。每条引用包含编号、URL、标题和摘要片段。

**使用场景：** 当 AI 生成回答时，会附带引用列表，用户点击 `[1]` 就能看到来源链接。

**大白话解释：** 这是"信息的名片"——一张卡片上写着信息来源的编号、网址、标题和简短摘要。

### 2.2 `SearchResult`（搜索结果）

*文件位置：types.py，第 31-44 行*

```python
@dataclass
class SearchResult:
    title: str
    url: str
    snippet: str
    date: str = ""
    source: str = ""
    content: str = ""  # 完整内容（如果有的话）
    score: float = 0.0
    sitelinks: list[dict[str, str]] = field(default_factory=list)
    attributes: dict[str, Any] = field(default_factory=dict)
```

**业务含义：** SearchResult 代表"一条搜索结果"。就像你用 Google 搜出来的每一条结果，包含标题、URL、摘要、日期等信息。

**关键字段：**
- `title`：结果的标题
- `url`：结果的链接
- `snippet`：摘要片段
- `content`：完整内容（某些搜索引擎如 Jina 会返回整篇文章）
- `score`：相关性评分（越高越相关）
- `sitelinks`：子链接列表（如 Wikipedia 条目下的相关页面）
- `attributes`：额外属性（如论文的发表年份、引用数等）

**大白话解释：** 这是"搜查到的线索"——每条线索都记录了它在哪个网站、标题是什么、内容梗概是什么。

### 2.3 `WebSearchResponse`（搜索响应）

*文件位置：types.py，第 47-111 行*

```python
@dataclass
class WebSearchResponse:
    query: str
    answer: str  # LLM 生成的答案，或空字符串
    provider: str
    timestamp: str
    model: str = ""
    citations: list[Citation] = field(default_factory=list)
    search_results: list[SearchResult] = field(default_factory=list)
    usage: dict[str, Any] = field(default_factory=dict)
    metadata: dict[str, Any] = field(default_factory=dict)
```

**业务含义：** WebSearchResponse 是搜索服务的"最终交付物"。它把一次搜索的所有信息打包在一起——用户的查询是什么、搜索引擎返回了什么结果、AI 生成了什么答案、引用了哪些来源。

**关键方法 `to_dict()`（第 61-111 行）：** 把整个响应对象转换为字典格式，方便 JSON 序列化。它会把 citations、search_results 等字段递归展开，并合并额外的 metadata。

**大白话解释：** 这是"档案袋"——用户问的问题、找到的线索、整理好的答案、引用的来源，统统装进一个档案袋里，给下游使用。

## 3. 搜索引擎基类（base.py）

*文件：`deeptutor/services/search/base.py`*

### 3.1 `BaseSearchProvider`（搜索引擎抽象基类）

*文件位置：base.py，第 20-86 行*

```python
class BaseSearchProvider(ABC):
    name: str = "base"
    display_name: str = "Base Provider"
    description: str = ""
    requires_api_key: bool = True
    supports_answer: bool = False  # 是否自带 LLM 答案
    BASE_URL: str = ""
```

**业务含义：** 这是所有搜索引擎的"模板"。就像所有汽车都有方向盘和油门，所有搜索引擎都必须实现 `search()` 方法。具体的搜索引擎（如 Brave、Serper）继承这个基类，填写自己的实现。

**关键属性：**
- `name`：引擎的内部名称（如 `"brave"`、`"serper"`）
- `display_name`：给用户看的名称
- `requires_api_key`：是否需要 API 密钥（DuckDuckGo 不需要，Brave 需要）
- `supports_answer`：这个引擎是否自带 AI 答案生成能力。Perplexity、Tavily 等 = `True`，它们自己就会生成答案；Serper、Jina 等 = `False`，只返回原始搜索结果，需要 DeepTutor 自己来整理
- `BASE_URL`：API 端点地址

**`__init__(self, api_key, **kwargs)`（第 35-46 行）：**
- **业务做什么：** 初始化搜索引擎，设置 API 密钥和配置
- **输入：** `api_key`（可选 API 密钥）、`**kwargs`（额外配置如代理地址）
- **大白话解释：** 搜索引擎启动时，先检查有没有钥匙（API 密钥），再记下配置信息

**`_get_api_key(self)`（第 48-56 行）：**
- **业务做什么：** 从 DeepTutor 的设置中读取当前活跃的搜索配置的 API 密钥
- **输入：** 无
- **输出：** API 密钥字符串
- **大白话解释：** 去"设置中心"拿钥匙——如果用户配了 Brave 的 API 密钥，就从那里读出来用

**`search(self, query, **kwargs)`（第 58-70 行）：**
- **业务做什么：** 执行搜索（抽象方法，子类必须实现）
- **输入：** `query`（搜索关键词）、`**kwargs`（引擎特定参数如最大结果数）
- **输出：** `WebSearchResponse`（标准化的搜索响应）
- **大白话解释：** 这是"搜索"的最终动作——每个引擎用自己的方式去网上搜，但结果必须包装成统一的格式

**`is_available(self)`（第 72-86 行）：**
- **业务做什么：** 检查搜索引擎是否可用（依赖是否安装、API 密钥是否配置）
- **输出：** `True` / `False`
- **大白话解释：** 启动前的"自检"——看看能不能用，不能用的引擎不会出现在选项中

## 4. 答案整合器（consolidation.py）

*文件：`deeptutor/services/search/consolidation.py`*

### 4.1 设计理念

不是所有搜索引擎都会生成漂亮的答案。一些搜索引擎（如 Serper、Jina）只返回原始的搜索结果列表（SERP）。Consolidation 模块的作用就是把这些"原材料"加工成"成品"。它有两种加工方式：

1. **模板渲染（默认）：** 用 Jinja2 模板把搜索结果排版成 Markdown 格式
2. **LLM 合成（可选）：** 调用大模型把搜索结果总结成一段连贯的答案

### 4.2 `PROVIDER_TEMPLATES`（引擎专属模板）

*文件位置：consolidation.py，第 27-135 行*

这是一个字典，存储了不同搜索引擎的 Jinja2 模板。每个模板定义了如何把特定引擎的搜索结果渲染成 Markdown。

**包含的模板：**
- `serper`：Google 搜索结果的模板，包含知识图谱（Knowledge Graph）、直接答案（Answer Box）、相关搜索等
- `jina`：Jina Reader 的结果模板，包含内容预览和提取的链接/图片
- `serper_scholar`：Google Scholar 学术搜索模板，显示论文标题、年份、发表信息、引用数

**大白话解释：** 就像不同的食材需要不同的烹饪方式——Google 搜索用的模板和学术搜索用的模板不一样，但最终都做成一道菜（Markdown 格式的答案）。

### 4.3 `AnswerConsolidator`（答案整合器类）

*文件位置：consolidation.py，第 138-368 行*

```python
class AnswerConsolidator:
    def __init__(
        self,
        *,
        use_llm: bool = False,       # 是否用 LLM 合成答案
        custom_template: str | None = None,  # 自定义模板
        llm_config: dict[str, Any] | None = None,  # LLM 配置
        max_results: int = 5,         # 最多展示多少条结果
        autoescape: bool = True,      # 是否自动转义 HTML
    ):
```

**业务含义：** AnswerConsolidator 是"答案的加工厂"。它接收原始的搜索结果，按照指定的方式加工成用户可读的答案。

**`consolidate(self, response)`（第 174-189 行）：**
- **业务做什么：** 根据配置选择用模板还是 LLM 来整合搜索结果
- **输入：** `response`（WebSearchResponse，包含原始搜索结果）
- **输出：** `WebSearchResponse`（`response.answer` 已被填充）
- **大白话解释：** 把搜索结果送进加工线——如果用户选了 LLM 模式，就请大模型帮忙总结；否则用模板排版

**`_get_template_for_provider(self, provider)`（第 191-203 行）：**
- **业务做什么：** 根据搜索引擎名称找到对应的渲染模板
- **输入：** `provider`（搜索引擎名称如 `"serper"`）
- **输出：** Jinja2 模板字符串，或 `None`（使用通用后备格式）
- **大白话解释：** 给不同的搜索引擎配不同的"菜谱"——Serper 有专门的菜谱，没有的用通用配方

**`_build_provider_context(self, response)`（第 205-263 行）：**
- **业务做什么：** 构建模板渲染时需要的上下文变量
- **输入：** `response`（WebSearchResponse）
- **输出：** 字典，包含 `query`、`results`、`citations` 等变量
- **关键逻辑：** 针对不同搜索引擎提取不同的专属字段。例如 Serper 会提取 `knowledgeGraph`（知识图谱）、`answerBox`（直接答案框）、`peopleAlsoAsk`（相关问题）；Jina 会提取 `links` 和 `images`
- **大白话解释：** 准备"食材"——把搜索结果中的各种信息按搜索引擎分类整理好，方便模板"烹饪"

**`_consolidate_with_template(self, response)`（第 265-291 行）：**
- **业务做什么：** 用 Jinja2 模板把搜索结果渲染成 Markdown
- **输入：** `response`（WebSearchResponse）
- **输出：** 字符串（Markdown 格式的答案）
- **大白话解释：** 按菜谱做菜——把搜索结果填入模板，生成漂亮的答案

**`_consolidate_with_llm(self, response)`（第 293-306 行）：**
- **业务做什么：** 调用 LLM 把搜索结果总结成连贯的答案
- **输入：** `response`（WebSearchResponse）
- **输出：** 字符串（LLM 生成的答案）
- **大白话解释：** 请大厨来做——把搜索结果送给大模型，让它帮忙总结成一段话

**`_build_prompts(self, response)`（第 308-344 行）：**
- **业务做什么：** 构建发送给 LLM 的 system prompt 和 user prompt
- **输出：** `(system_prompt, user_prompt)` 元组
- **关键逻辑：** system prompt 告诉 LLM "你是一个搜索结果整合器，输出要结构化、事实化、带引用编号"；user prompt 把搜索结果拼接进去
- **大白话解释：** 给大厨写"做菜指令"——告诉它要输出什么风格、什么格式

**`_format_simple_results(self, response)`（第 346-368 行）：**
- **业务做什么：** 当没有特定模板时，用简单的通用格式排版
- **输出：** 字符串（简单格式化的搜索结果）
- **大白话解释：** 没有菜谱时的"家常做法"——简单地把结果按标题、摘要、链接列出来

## 5. 服务入口（__init__.py）

*文件：`deeptutor/services/search/__init__.py`*

### 5.1 `web_search()`（核心搜索函数）

*文件位置：__init__.py，第 73-170 行*

```python
def web_search(
    query: str,
    output_dir: str | None = None,
    verbose: bool = False,
    provider: str | None = None,
    consolidation_custom_template: str | None = None,
    consolidation_llm_model: str | None = None,
    **provider_kwargs,
) -> dict[str, Any]:
```

**业务含义：** 这是搜索服务的"大门"。所有搜索请求都从这里进来。它负责选择搜索引擎、执行搜索、整合答案。

**参数说明：**
- `query`：搜索关键词
- `output_dir`：可选，结果保存到的目录
- `verbose`：是否打印详细日志
- `provider`：指定使用哪个搜索引擎（不指定则用默认配置）
- `consolidation_custom_template`：自定义答案排版模板
- `consolidation_llm_model`：如果指定了 LLM 模型，就用 LLM 合成答案而不是模板

**执行流程（大白话解释）：**

1. **检查开关（第 88-98 行）：** 先看搜索功能有没有被禁用。如果禁用了，直接返回"搜索已禁用"。
2. **确定引擎（第 100-102 行）：** 如果用户指定了搜索引擎就用指定的，否则用系统默认的。
3. **处理"none"（第 103-111 行）：** 如果引擎是 `"none"`，表示用户明确关闭搜索，返回空结果。
4. **密钥检查（第 113-133 行）：**
   - Brave/Tavily/Jina：需要 API 密钥，没有密钥就自动降级为 DuckDuckGo（免费且不需要密钥）
   - Perplexity/Serper：需要 API 密钥，没有密钥直接报错（因为它们是核心引擎，不能降级）
   - SearXNG：需要配置 base_url，没有就降级为 DuckDuckGo
5. **执行搜索（第 139-145 行）：** 调用搜索引擎的 `search()` 方法，去互联网上搜索。如果失败，抛出明确的错误信息。
6. **整合答案（第 148-158 行）：** 如果搜索引擎不自带答案（`supports_answer=False`），就用 AnswerConsolidator 来整合。如果用户指定了 LLM 模型，就用 LLM 合成；否则用模板排版。
7. **保存结果（第 161-163 行）：** 如果指定了 `output_dir`，就把结果保存为 JSON 文件。
8. **返回结果（第 170 行）：** 把结构化结果返回给调用方。

### 5.2 `get_current_config()`（获取当前配置）

*文件位置：__init__.py，第 173-192 行*

**业务含义：** 获取搜索服务的当前配置状态，用于 UI 展示。返回当前使用哪个搜索引擎、哪些引擎可用、哪些需要配置密钥等。

**大白话解释：** 这是"仪表盘"——告诉用户搜索服务现在的状态：用的是什么引擎、有没有配好密钥、支持哪些引擎。

### 5.3 辅助函数

**`_get_web_search_config()`（第 34-41 行）：**
- **业务做什么：** 从 `main.yaml` 配置文件中读取搜索相关配置
- **大白话解释：** 去"设置文件"里找搜索的配置

**`_save_results()`（第 43-51 行）：**
- **业务做什么：** 把搜索结果保存为 JSON 文件
- **输出：** 保存的文件路径
- **大白话解释：** 把搜索报告"存档"到磁盘上

**`_assert_provider_supported()`（第 58-70 行）：**
- **业务做什么：** 检查用户指定的搜索引擎是否在支持列表中
- **大白话解释：** "门卫"——检查访客（搜索引擎名称）是否在邀请名单上

## 6. 搜索引擎提供商目录

搜索服务支持以下搜索引擎，每个都继承 `BaseSearchProvider` 并实现自己的 `search()` 方法：

| 引擎 | 文件 | 需要密钥 | 自带答案 | 特点 |
|------|------|----------|----------|------|
| Brave | `providers/brave.py` | 是 | 否 | 隐私友好的搜索引擎 |
| Tavily | `providers/tavily.py` | 是 | 是 | 专为 AI agent 设计的搜索 |
| Serper | `providers/serper.py` | 是 | 否 | Google 搜索 API |
| Jina | `providers/jina.py` | 是 | 否 | 返回网页全文内容 |
| DuckDuckGo | `providers/duckduckgo.py` | 否 | 否 | 免费、无需密钥 |
| Perplexity | `providers/perplexity.py` | 是 | 是 | AI 驱动的搜索 |
| SearXNG | `providers/searxng.py` | 否 | 否 | 自托管元搜索引擎 |
| Exa | `providers/exa.py` | 是 | 是 | 语义搜索 |
| Baidu | `providers/baidu.py` | 是 | 是 | 百度搜索 |
| OpenRouter | `providers/openrouter.py` | 是 | 是 | 通过 OpenRouter 的搜索 |

## 7. 数据流总览

```
用户输入 "今天天气怎么样"
        │
        ▼
   web_search(query="今天天气怎么样")
        │
        ├─ 检查配置：搜索是否启用？
        ├─ 确定引擎：用哪个搜索引擎？
        ├─ 检查密钥：有没有 API 密钥？
        │     └─ 没有 → 降级为 DuckDuckGo
        │
        ▼
   search_provider.search(query)
        │
        ├─ 引擎去互联网上搜索
        └─ 返回 WebSearchResponse（原始结果）
        │
        ▼
   AnswerConsolidator.consolidate(response)
        │
        ├─ supports_answer=False？
        │     ├─ 是 → 用模板渲染或用 LLM 合成
        │     └─ 否 → 引擎已经自带答案，直接用
        │
        ▼
   返回结构化结果
        │
        ├─ answer: Markdown 格式的答案
        ├─ citations: 引用来源列表
        └─ search_results: 原始搜索结果
```

## 8. 一句话总结

搜索服务是 DeepTutor 的"信息采购员"——接收用户的问题，自动选择最合适的搜索引擎，去互联网上搜集信息，然后把原始材料整理成一份结构清晰、带引用的答案报告。
