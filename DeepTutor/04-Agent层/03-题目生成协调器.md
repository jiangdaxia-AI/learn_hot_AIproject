## 整体架构

如果把 DeepTutor 的题目生成比作一家"出题出版社"，那么这几个文件的分工如下：

| 文件 | 角色比喻 | 职责 |
|------|----------|------|
| `capability.py` | 出版社前台 | 接收用户请求，判断是"自定义出题"还是"模仿试卷出题"，分发给对应的管线 |
| `pipeline.py` | 编辑部主任 | 三阶段流程：研究主题 → 制定出题计划 → 逐题生成 |
| `coordinator.py` | 旧版前台（仍在用） | 兼容旧的 API 调用方式，内部转发给新管线 |
| `history.py` | 档案管理员 | 读取用户之前做过哪些题，避免重复出题 |

它们之间的关系是：**Capability（前台）→ Pipeline（编辑部）→ LoopHost（具体执行）**。

## 核心数据结构

在开始讲流程之前，先理解几个关键的概念容器——它们就像流水线上的"零件盒"，每个阶段的数据都装在对应的盒子里传递。

### QuizTemplate（出题模板）

**源码位置**：`pipeline.py` 第302-313行

```python
@dataclass(frozen=True)
class QuizTemplate:
    question_id: str       # 题目编号，如 "q_1"
    topic: str             # 考察的知识点，如 "牛顿第二定律"
    question_type: str     # 题型：choice / concept / fill_in_blank / short_answer / written / coding
    difficulty: str        # 难度：easy / medium / hard
    source: str = "custom" # 来源：custom（自定义）或 mimic（模仿试卷）
    reference_question: str | None = None  # 模仿模式下的参考题目原文
    reference_answer: str | None = None    # 模仿模式下的参考答案
```

**大白话解释**：QuizTemplate 是"出题计划书"里的一行。它告诉系统：第几题、考什么、什么题型、什么难度。如果是模仿试卷模式，还会附上原题作为参考，让 AI 照着风格出题。

### QuizPlan（出题计划）

**源码位置**：`pipeline.py` 第316-319行

```python
@dataclass(frozen=True)
class QuizPlan:
    analysis: str                        # 对整个出题任务的分析描述
    templates: list[QuizTemplate] = []   # 逐题的模板列表
```

**大白话解释**：QuizPlan 是 Phase 2（规划阶段）的输出。它相当于"编辑部主任"签发的出题任务单，上面写着"我们要出 N 道题，分别考这些知识点，难度分别是……"。

### QuizHistoryEntry（历史答题记录）

**源码位置**：`pipeline.py` 第322-331行

```python
@dataclass(frozen=True)
class QuizHistoryEntry:
    question: str          # 题目内容
    question_type: str     # 题型
    correct_answer: str    # 正确答案
    user_answer: str       # 用户的回答
    is_correct: bool | None # 是否做对（None 表示未作答）
    turn_id: str = ""      # 属于哪一轮对话
```

**大白话解释**：这是用户之前做过的题的记录。系统会把它喂给 AI，让 AI 知道"这个知识点用户已经做过了，而且做对了/做错了"，从而避免重复出题或针对薄弱点出题。

### QuizPair（最终题目）

**源码位置**：`pipeline.py` 第334-349行

```python
@dataclass
class QuizPair:
    question_id: str       # 题目编号
    question: str          # 题目正文
    question_type: str     # 题型
    correct_answer: str    # 正确答案
    explanation: str       # 解析
    options: dict[str, str] | None = None  # 选项（仅选择题有）
    topic: str = ""        # 知识点
    difficulty: str = ""   # 难度
    metadata: dict = {}    # 额外元数据
```

**大白话解释**：这是最终产物——一道完整的题目，包含题干、答案、解析、选项（如果是选择题）。前端拿到这个数据结构后，就能渲染出题目卡片。

### QuestionType（题型枚举）

**源码位置**：`pipeline.py` 第144-153行

```python
class QuestionType(StrEnum):
    CHOICE = "choice"            # 选择题（A/B/C/D）
    CONCEPT = "concept"          # 判断对错题（True/False）
    FILL_IN_BLANK = "fill_in_blank"  # 填空题
    SHORT_ANSWER = "short_answer"    # 简答题
    WRITTEN = "written"              # 论述题
    CODING = "coding"                # 编程题
```

**大白话解释**：这是系统支持的 6 种题型。每种题型在后端有不同的校验规则——比如选择题必须有 A/B/C/D 四个选项，填空题的题干中必须包含 `[BLANK]` 标记——这些规则在 `_collect_quiz_issues` 方法中实现。

## DeepQuestionCapability — 能力入口

**源码位置**：`capability.py` 第28-329行

### 业务场景

当用户在 DeepTutor 中说"帮我出 5 道关于牛顿定律的题"或者上传一份试卷 PDF 说"模仿这份试卷出题"，系统就会调用 `DeepQuestionCapability`。

### 类定义

```python
class DeepQuestionCapability(BaseCapability):
    manifest = CapabilityManifest(
        name="deep_question",
        description="Fast question generation (Template batches -> Generate).",
        stages=["ideation", "generation"],
        tools_used=["rag", "web_search", "code_execution"],
        cli_aliases=["quiz"],
    )
```

**基本信息**：
- **能力名称**：`deep_question`
- **命令行别名**：`quiz`（用户可以在 CLI 中用 `quiz` 触发）
- **可用工具**：知识库检索（rag）、网络搜索（web_search）、代码执行（code_execution）
- **阶段**：构思（ideation）→ 生成（generation）

### run() 方法 — 核心调度逻辑

**源码位置**：`capability.py` 第38-156行

**输入**：
- `context: UnifiedContext` — 统一上下文，包含用户消息、附件、知识库、启用的工具等信息
- `stream: StreamBus` — 事件流总线，用于向前端推送实时进度

**输出**：无直接返回值，通过 `stream` 推送结果事件

**处理流程**（大白话版）：

```
用户请求进来
    │
    ├─ 是追问模式？（用户针对某道题提问）
    │   yes → 调用 FollowupAgent 作答 → 结束
    │
    ├─ 是模仿模式？（用户上传了试卷）
    │   yes → 解析试卷 → 提取模板 → 跳过研究+规划 → 直接逐题生成
    │
    └─ 是自定义模式？（用户说了主题）
        yes → 加载历史记录 → 创建 QuestionPipeline → 三阶段生成
```

**关键判断逻辑**：

1. **追问模式判断**（第49-83行）：检查 `context.metadata` 中是否有 `question_followup_context`，如果有，说明用户是在对某道已有题目进行追问，直接调用 `FollowupAgent` 回答。

2. **模仿模式判断**（第99行）：通过 `overrides.get("mode")` 判断。如果是 `mimic`，则进入 `_run_mimic_mode`。

3. **自定义模式**（第99-142行）：这是最常见的路径。先加载用户的历史答题记录（`load_session_quiz_history`），然后创建 `QuestionPipeline` 并调用 `pipeline.run()`。

### _run_mimic_mode() — 模仿模式处理

**源码位置**：`capability.py` 第158-328行

**三种输入形态**：

| 输入形态 | 处理方式 |
|----------|----------|
| 用户上传了 PDF 附件 | 先写入临时文件，调用 MinerU 解析引擎提取题目模板，然后把模板传给 Pipeline |
| 服务端已经解析好的目录路径 | 直接调用解析函数提取模板 |
| 用户消息中只有 `[Attached Documents]` 标记 | 降级为自定义模式，但给用户消息加上"尽量模仿附件风格"的前缀提示 |

**大白话解释**：模仿模式的核心思路是"照猫画虎"。先把原试卷的题目结构提取出来（每题什么题型、什么难度、考什么知识点），然后把这些作为"模板"传给生成管线，让 AI 按照原题风格出新的题目。

## QuestionPipeline — 三阶段管线

**源码位置**：`pipeline.py` 第357-1876行

这是整个题目生成系统的核心，一个"一次性"的编排器——每次用户请求创建一次实例，调用一次 `run()` 方法。

### __init__() — 初始化

**源码位置**：第360-433行

**输入参数**：
| 参数 | 类型 | 说明 |
|------|------|------|
| `language` | str | 语言，默认 "en" |
| `kb_name` | str or None | 知识库名称 |
| `enabled_tools` | list[str] or None | 启用的工具列表 |
| `max_explore_iterations` | int | 研究阶段最大迭代次数，默认 8 |
| `max_quiz_iterations_per_question` | int | 每题最大迭代次数，默认 5 |
| `runtime_config` | dict or None | 运行时配置 |

**初始化做了什么**（大白话）：
1. 读取 LLM 配置（用什么模型、API 地址等）
2. 加载工具注册表（有哪些工具可用）
3. 加载提示词模板（从 YAML 配置文件读取各阶段的 prompt）
4. 设置温度参数为 0.4（控制 AI 输出的随机性）

### run() — 三阶段主流程

**源码位置**：第438-493行

**输入**：
| 参数 | 说明 |
|------|------|
| `context` | 统一上下文 |
| `user_message` | 用户输入的主题 |
| `num_questions` | 要生成的题目数量 |
| `difficulty` | 难度 |
| `question_types` | 题型白名单（空=不限） |
| `per_type_counts` | 每种题型出几道 |
| `quiz_history` | 历史答题记录 |
| `templates_override` | 模仿模式的模板覆盖 |
| `stream` | 事件流 |

**输出**：`dict` 包含 `response`（前端展示文本）、`summary`（题目列表、成功/失败统计）等。

**三阶段流程图**：

```
┌─────────────────────────────────────────────────┐
│                  Phase 1: 研究                   │
│  输入：用户主题                                  │
│  过程：AI 调用工具（搜索、知识库）研究主题          │
│  输出：研究总结文本 + 研究轨迹                     │
│  时长：最多 8 轮迭代                              │
└──────────────────┬──────────────────────────────┘
                   ▼
┌─────────────────────────────────────────────────┐
│                  Phase 2: 规划                   │
│  输入：研究轨迹 + 用户主题                        │
│  过程：AI 一次性输出 JSON 出题计划                 │
│  输出：QuizPlan（每题的知识点、题型、难度）          │
└──────────────────┬──────────────────────────────┘
                   ▼
┌─────────────────────────────────────────────────┐
│                  Phase 3: 逐题生成               │
│  输入：每道题的模板 + 研究轨迹                     │
│  过程：逐题调用 AI（可调用工具）→ 解析 → 校验 → 修复  │
│  输出：QuizPair 列表（完整的题目）                 │
│  时长：每题最多 5 轮迭代                          │
└─────────────────────────────────────────────────┘
```

### Phase 1: _explore() — 研究阶段

**源码位置**：第607-686行

**业务含义**：让 AI 先"备课"。AI 在收到出题请求后，不是直接拍脑袋出题，而是先调用工具研究主题。

**输入**：
- 用户主题、题目数量、题型要求、难度、对话历史、历史答题记录

**输出**：`(finish_text, exploration_trace)` 元组
- `finish_text`：研究总结，会流式展示给用户看（比如"我已经研究了牛顿定律的相关内容，现在为你出 5 道题"）
- `exploration_trace`：完整的研究轨迹（思考过程+工具调用结果），供后续阶段使用

**关键机制**：

1. **工具调用**：AI 可以使用 `rag`（知识库检索）、`web_search`（网络搜索）、`code_execution`（代码执行）等工具来研究主题。

2. **工具摘要器**（Tool Summarizer，第962-1081行）：每次工具调用返回的结果可能很长（比如搜索返回几千字），直接喂给 AI 会撑爆上下文窗口。工具摘要器是另一个 LLM 调用，把长结果压缩成简洁的摘要，既保留关键信息，又不占太多空间。

3. **流式展示**：`stream_body_live=True`，意味着 AI 的研究思考过程会实时推送到前端，用户可以看到"AI 正在思考"的效果。

### Phase 2: _plan() — 规划阶段

**源码位置**：第691-750行

**业务含义**：在研究的基础上，AI 制定出题计划——每道题考什么知识点、什么题型、什么难度。

**输入**：
- 用户主题、研究轨迹、题目数量、题型约束

**输出**：`QuizPlan` 对象

**为什么需要规划阶段？**

想象一下，如果直接让 AI "出 5 道关于牛顿定律的题"，它可能 5 道题都考同一个知识点（比如都考 F=ma），缺乏覆盖度。规划阶段强制 AI 先想清楚："我要出 5 道题，分别覆盖牛顿第一定律、第二定律、第三定律、万有引力、动量守恒，让它们难度递进，题型多样化。"

**规划解析**（`_parse_plan`，第752-815行）：
- 从 AI 返回的 JSON 中提取 `templates` 列表
- 校验题型是否在允许范围内
- 去重：同一个知识点不会出现两次
- 数量控制：如果 AI 返回的模板数量超过要求，截断；如果不够，也接受（后面会发出警告）

### Phase 3: _quiz_one() — 逐题生成

**源码位置**：第820-911行

**业务含义**：按照规划好的模板，逐题生成完整的题目内容。

**输入**：
- 当前题的模板（知识点、题型、难度）
- 研究轨迹（让 AI 知道背景知识）
- 出题计划（让 AI 知道自己在整套题中的位置）
- 已经生成的题目（避免重复）

**输出**：`QuizPair` 对象

**关键流程**：

1. **组装 Prompt**：把模板信息、研究轨迹、计划摘要、已出题目等拼成 prompt
2. **Agentic Loop**：AI 在 `THINK → TOOL → FINISH` 的协议下运行，可以调用工具辅助出题
3. **解析 JSON**（`_parse_quiz_payload`，第1291-1309行）：从 AI 的 FINISH 输出中提取 JSON 格式的题目
4. **规范化**（`_normalize_quiz_payload`，第1311-1353行）：根据题型做针对性处理
   - 选择题：确保选项是 A/B/C/D 格式，正确答案是选项字母
   - 判断题：把"对/正确/True/yes"统一为 "true"，"错/错误/False/no"统一为 "false"
   - 填空题：确保题干包含 `[BLANK]` 标记
5. **校验**（`_collect_quiz_issues`，第1355-1391行）：检查题目是否完整、格式是否正确
6. **修复**（`_repair_quiz_payload`，第913-957行）：如果校验不通过，再调一次 AI 专门修复问题
7. **实时推送**（`_emit_quiz_question`，第1200-1225行）：每道题生成完就立刻推给前端，不需要等全部完成

### 题型校验规则详解

**源码位置**：`_collect_quiz_issues` 第1355-1391行

| 题型 | 必须满足的条件 |
|------|---------------|
| choice（选择） | 必须有 A/B/C/D 四个选项；正确答案必须是选项字母 |
| concept（判断） | 不能有选项；正确答案必须是 true/false |
| fill_in_blank（填空） | 不能有选项；题干必须包含 `[BLANK]` 标记 |
| 其他（简答/论述/编程） | 不能有选项；正确答案不能是单个字母（那看起来像选项） |

### 强制结束机制

**源码位置**：`_force_finish` 第1418-1474行

当 AI 在某个阶段"卡住了"（迭代次数用完还没输出 FINISH），系统会：

1. 插入一条用户消息："请立即输出 FINISH"
2. 最多尝试 2 次修复
3. 如果还是不行，返回一个兜底文本

## QuizHistoryLoader — 历史记录加载器

**源码位置**：`history.py` 第1-103行

### load_session_quiz_history()

**源码位置**：第34-100行

**业务含义**：读取当前会话中用户之前做过的所有题目，用于让 AI 避免重复出题，以及针对用户的薄弱点出题。

**输入**：
- `session_id`：会话 ID
- `max_entries`：最多返回多少条记录，默认 30

**输出**：`list[QuizHistoryEntry]`，按时间从早到晚排列

**大白话解释**：
- 从 SQLite 数据库的 `notebook_entries` 表读取
- 数据来源是前端调用 `POST /sessions/{id}/quiz-results` 写入的
- 不解析聊天消息（那太不可靠了），只读结构化数据
- 如果用户没作答（`user_answer` 为空），`is_correct` 设为 `None`（表示"未知"），而不是"错误"
- 按 `(created_at ASC, id ASC)` 排序，保证最早→最新
- 任何错误都返回空列表（降级策略），不会阻塞出题流程

## LoopHost 机制

**源码位置**：`pipeline.py` 第1883-2160行

LoopHost 是 DeepTutor 中的一个设计模式——它像一个"回调接口"，让通用的 Agentic Loop 引擎在执行循环时，能够根据不同阶段做不同的事情。

### _BaseLoopHost（基类）

**源码位置**：第1883-1972行

定义了所有 LoopHost 共有的方法：
- `dispatch_tools`：分发工具调用
- `guard_context_window`：检查上下文窗口是否溢出
- `resolve_pause`：处理暂停（如等待用户回复）
- `emit_terminator`：处理终止信号
- `protocol_retry_notice` / `protocol_repair_message`：协议违规时的提示

### _ExploreLoopHost（研究阶段主机）

**源码位置**：第1974-2088行

**特殊之处**：在 `dispatch_tools` 中，每次工具调用完成后，会自动触发**工具摘要器**——用一个额外的 LLM 调用把原始工具结果压缩成摘要，替换掉原始内容。这样后续阶段拿到的是"精炼版"研究轨迹，而非原始数据洪流。

### _QuizLoopHost（出题阶段主机）

**源码位置**：第2090-2156行

**特殊之处**：`emit_final` 是空操作——因为出题阶段的 FINISH 是 JSON 格式的题目数据，不应该直接流式推送到聊天区（那会显示一堆 JSON）。真正的题目展示由 `_emit_quiz_question` 方法负责，它会生成格式化的 Markdown 再推送。

## 总结

### 数据流全景图

```
用户输入："出 5 道关于牛顿定律的题"
         │
         ▼
DeepQuestionCapability.run()
         │
         ├─ 加载历史答题记录
         ├─ 创建 QuestionPipeline
         │
         ▼
Phase 1: 研究 (Explore)
  AI 调用 rag/web_search 研究牛顿定律
  → 工具摘要器压缩结果
  → 输出：研究总结 + 研究轨迹
         │
         ▼
Phase 2: 规划 (Plan)
  AI 输出 JSON 出题计划
  → 解析并校验
  → 输出：QuizPlan（5 道题的模板）
         │
         ▼
Phase 3: 逐题生成 (Quiz)
  对每道题：
    AI 生成题目 → 解析 JSON → 规范化 → 校验
    → 不通过？修复 → 再校验
    → 通过！推送给前端
         │
         ▼
组装结果信封 → 推送给前端展示
```

### 关键设计决策

| 决策 | 原因 |
|------|------|
| 三阶段分离（研究→规划→生成） | 让 AI 先"备课"再"出题"，比一次性出题质量更高，覆盖面更广 |
| 工具摘要器 | 搜索结果可能几千字，不压缩会导致上下文溢出且后续阶段无法有效利用 |
| 逐题流式推送 | 用户体验更好——不需要等所有题出完才能看到第一题 |
| 自动修复机制 | AI 偶尔输出格式不对，自动修复比直接报错更友好 |
| 历史记录注入 | 避免给用户出已经做过的题，可根据弱项针对性出题 |
| 模仿模式跳过前两阶段 | 试卷已经提供了结构，不需要 AI 再研究规划和规划 |
