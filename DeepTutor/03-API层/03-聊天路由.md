# 聊天路由 — DeepTutor 的对话引擎接口

> 源码位置: deeptutor/api/routers/chat.py（249 行）  
> 角色: 处理用户与 AI 的实时对话，管理会话生命周期  
> 类比: 如果把 DeepTutor 比作一个 AI 家教，chat.py 就是你和家教之间的对讲机——你说的话通过它传给 AI，AI 的回答通过它传回来，而且它还负责记录你们的对话历史。

---

## 一、本章概述

chat.py 是 DeepTutor 中最简洁但最常用的路由模块，仅有 249 行代码。它实现了两个核心功能：

1. 会话管理（REST API）：创建、查看、删除对话会话
2. 实时聊天（WebSocket）：用户与 AI 的一问一答，支持流式输出

虽然代码量不大，但它承载了 DeepTutor 最核心的用户体验——与 AI 对话。

---

## 二、会话是什么？

在深入源码之前，先理解会话（Session）的概念：

会话 = 一次完整的对话记录

每一次你与 AI 的对话，系统都会创建一个会话。会话包含：
- 会话 ID（唯一标识）
- 标题（通常是对话的第一句话）
- 消息列表（你问的 + AI 答的）
- 设置（使用了哪个知识库、是否开启了联网搜索等）

类比：会话就像一本对话日记。每次你打开 DeepTutor 开始聊天，系统就翻开新的一页，记录下你和 AI 的每一句对话。下次你回来，可以翻到之前的某一页继续聊。

## 四、会话管理详解

### 4.1 列出所有会话

路由: GET /api/v1/chat/sessions
源码行号: 第 34～36 行

业务上做什么：返回用户最近的所有对话会话列表，就像聊天软件的对话列表。

什么场景下会用到：前端加载侧边栏的对话历史列表时调用。

输入：可选的 limit 参数（默认 20），控制返回多少条会话。

输出：会话列表，每个会话包含 session_id、title、创建时间等基本信息，但不包含具体的消息内容（include_messages=False）。

源码逻辑：直接调用 SessionManager.list_sessions()，传入 limit 和 include_messages=False。不返回消息内容是为了减少数据传输量——前端只在用户点击某个会话时才加载具体消息。

### 4.2 获取单个会话详情

路由: GET /api/v1/chat/sessions/{session_id}
源码行号: 第 39～44 行

业务上做什么：返回指定会话的完整信息，包括所有历史消息。

什么场景下会用到：用户点击侧边栏的某个历史对话，前端需要加载完整的对话内容。

输入：session_id（会话 ID），从 URL 路径中获取。

输出：完整的会话对象，包括所有消息（每条消息包含 role 和 content）。

源码逻辑：调用 SessionManager.get_session(session_id)，如果找不到会话返回 404。

### 4.3 删除会话

路由: DELETE /api/v1/chat/sessions/{session_id}
源码行号: 第 47～51 行

业务上做什么：删除一个对话会话。

什么场景下会用到：用户在对话列表中右键删除某个对话。

输入：session_id（会话 ID）。

输出：删除成功返回 {status: deleted, session_id: ...}，找不到会话返回 404。

## 五、WebSocket 实时聊天详解

这是 chat.py 最核心的部分，占用了 190 行代码（第 59～249 行）。

### 5.1 为什么用 WebSocket 而不是普通 HTTP？

普通 HTTP 请求是请求-响应模式：你发一个问题，等 AI 全部回答完，一次性返回。这有两个问题：
1. 用户体验差：AI 生成回答可能需要 10-30 秒，用户只能干等
2. 无法展示思考过程：用户看不到 AI 正在做什么

WebSocket 是全双工通信：建立一个长连接后，服务器可以随时向客户端推送数据。这样 AI 可以：
- 逐字逐句地输出回答（流式输出，像打字一样）
- 实时告诉用户正在做什么（搜索知识库中、联网搜索中、生成回答中）

类比：HTTP 就像寄信——你寄出去，等几天收到回信。WebSocket 就像打电话——你说一句，对方马上回应你。

### 5.2 认证流程

源码行号: 第 61～66 行

WebSocket 的认证与 REST 不同——FastAPI 的依赖注入在 WebSocket 上有限制。所以 chat.py 在 WebSocket 处理函数内部手动调用 ws_require_auth(websocket) 进行认证。

如果认证失败，ws_require_auth 会返回一个特殊值 ws_auth_failed，函数直接 return，WebSocket 连接被拒绝。

### 5.3 消息处理主循环

源码行号: 第 71～241 行

整个聊天流程在一个 while True 循环中运行，每次循环处理一条用户消息。流程如下：

第一步：接收并解析消息（第 72～86 行）

前端通过 WebSocket 发送 JSON 格式的消息，包含以下字段：
- message：用户输入的问题（必填，如果为空返回错误）
- session_id：会话 ID。如果为空，系统会创建新会话
- language：对话语言（zh/en），影响 AI 用哪种语言回答
- kb_name：使用的知识库名称
- enable_rag：是否启用知识库检索
- enable_web_search：是否启用联网搜索
- history：对话历史。如果为空，使用会话中已有的历史消息

第二步：语言处理（第 73～80 行）

系统根据用户指定的 language 参数来决定 AI 的回答语言：
- 如果以 zh 开头，使用中文
- 如果以 en 开头，使用英文
- 否则使用系统默认语言（从 UI 设置中获取）

第三步：会话管理（第 98～128 行）

这是会话管理的关键逻辑：
1. 如果用户提供了 session_id，尝试获取该会话
2. 如果会话不存在，创建一个新会话（标题取消息的前 50 个字符）
3. 如果用户没有提供 session_id，创建一个新会话
4. 将会话 ID 通过 WebSocket 发回给前端

第四步：准备历史消息（第 130～136 行）

如果前端传了 explicit_history（显式历史），直接使用。
否则，从会话中提取已有的消息，构建对话历史。

第五步：保存用户消息（第 138～142 行）

将用户刚发送的消息保存到会话中。

第六步：获取 LLM 配置（第 144～152 行）

从系统配置中获取 LLM（大语言模型）的连接信息：API Key、Base URL、API Version。

第七步：创建 ChatAgent（第 154～160 行）

ChatAgent 是实际执行对话的代理对象。传入 language、config、api_key、base_url、api_version 等参数。

第八步：发送状态通知（第 162～186 行）

在 AI 真正开始回答之前，系统会通过 WebSocket 告诉前端当前正在做什么：
- 如果启用了知识库检索，发送 rag 状态
- 如果启用了联网搜索，发送 web 状态
- 总是发送 generating 状态

前端收到这些状态后，可以在界面上显示搜索中、生成中的动画。

第九步：流式输出回答（第 191～221 行）

agent.process() 返回一个异步生成器（stream_generator），逐块输出 AI 的回答。
系统通过 async for 循环遍历这个生成器：
- 收到 type: chunk，通过 WebSocket 发送给前端，前端逐字显示
- 收到 type: complete，记录完整的回答内容和引用来源

第十步：发送引用来源（第 213～214 行）

如果 AI 的回答引用了知识库或网页内容，发送引用来源。

第十一步：发送最终结果（第 216～221 行）

发送 type: result 告诉前端回答已完成。

第十二步：保存 AI 回答（第 223～228 行）

将 AI 的回答保存到会话中。

### 5.4 错误处理

源码行号: 第 232～248 行

整个聊天过程包裹在 try/except 中：
- WebSocketDisconnect：客户端断开连接，正常退出
- 其他异常：记录错误日志，尝试通过 WebSocket 发送错误消息给前端

## 八、与前端交互的完整时序

前端点击发送按钮 → WebSocket 发送 JSON 消息 → 后端接收并解析 → 创建或获取会话 → 发送 session_id 给前端 → 发送状态通知（rag/web/generating）→ 流式输出文本片段 → 发送引用来源 → 发送最终结果 → 保存到会话 → 前端显示完整回答

## 十、ChatAgent 与 SessionManager 的关系

chat.py 依赖两个核心组件：

### 10.1 SessionManager

源码行号: 第 25～26 行

SessionManager 负责会话的持久化存储。每次调用 _get_session_manager() 都会创建一个新的 SessionManager 实例。它提供三个核心方法：

- list_sessions(limit, include_messages)：列出会话列表
- get_session(session_id)：获取单个会话
- create_session(title, settings)：创建新会话
- delete_session(session_id)：删除会话
- add_message(session_id, role, content, sources)：添加消息

### 10.2 ChatAgent

源码行号: 第 154～160 行

ChatAgent 是实际与 LLM 交互的代理。它负责：
- 构建提示词（prompt）
- 调用 LLM API
- 处理 RAG 检索结果
- 处理联网搜索结果
- 生成流式输出

ChatAgent 的 process() 方法（第 191 行）是核心入口，它接受消息、历史、知识库设置等参数，返回一个异步生成器。

## 十一、语言设置的优先级

源码行号: 第 73～80 行

语言选择有三个优先级（从高到低）：

1. 用户在消息中指定的 language 参数（最高优先级）
2. 系统 UI 语言设置（get_ui_language()）
3. 系统配置中的默认语言（main.yaml 中的 system.language）

这个设计让用户可以灵活切换对话语言——即使在英文界面下，也可以指定某次对话使用中文。

---

## 十二、RAG 与联网搜索的协作

源码行号: 第 162～178 行

当用户同时启用知识库检索和联网搜索时，系统会：

1. 先搜索知识库，将相关内容作为上下文
2. 再搜索网络，将网络结果作为补充
3. 将两者合并后发给 LLM

前端会收到两个状态通知，分别显示搜索进度。最终回答中会包含两类引用来源。

---

## 十三、会话自动创建的设计意图

源码行号: 第 100～121 行

为什么 session_id 不存在时要自动创建新会话，而不是返回错误？

这是一个用户体验设计决策。在实际使用中，常见场景是：
- 用户打开 DeepTutor，开始新的对话（没有 session_id）
- 用户刷新页面后继续对话（session_id 可能已过期）

如果返回错误，用户需要手动处理。自动创建新会话让体验更加流畅——用户只需要输入问题，系统自动处理会话管理。

---

## 十四、流式输出的实现原理

源码行号: 第 191～211 行

agent.process(stream=True) 返回的是一个异步生成器。每次 LLM 生成一个新的 token（词元），生成器就会 yield 一个包含 type: "chunk" 和 content 的字典。

前端收到这些 chunk 后，将它们拼接起来显示，就像 ChatGPT 那样逐字输出。

当 LLM 完成生成后，生成器 yield 一个 type: "complete" 的字典，包含完整的回答文本和引用来源。

---

## 十五、与前端的数据契约

chat.py 通过 WebSocket 与前端通信，双方约定了一套消息格式：

### 前端发送给后端

{
  "message": "用户问题",
  "session_id": "可选",
  "language": "zh或en",
  "kb_name": "知识库名称",
  "enable_rag": true/false,
  "enable_web_search": true/false,
  "history": null
}

### 后端发送给前端（多种类型）

会话确认：{"type": "session", "session_id": "..."}
状态更新：{"type": "status", "stage": "rag|web|generating", "message": "..."}
流式文本：{"type": "stream", "content": "..."}
引用来源：{"type": "sources", "rag": [...], "web": [...]}
最终结果：{"type": "result", "content": "..."}
错误信息：{"type": "error", "message": "..."}

这个数据契约是前后端协作的基础，任何一方修改格式都需要另一方同步更新。
