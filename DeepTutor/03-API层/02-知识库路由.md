# 知识库路由 — DeepTutor 的资料管理系统

> 源码位置: deeptutor/api/routers/knowledge.py（2808 行）  
> 角色: 整个知识库功能的 HTTP 接口层，负责接收前端请求并调用底层服务  
> 类比: 如果把 DeepTutor 的知识库比作一座图书馆，knowledge.py 就是图书馆的前台管理系统——你可以在这里创建新书架（知识库）、往书架上放书（上传文件）、查书（检索）、整理书架（文件夹管理），甚至连接隔壁图书馆（关联外部文件夹）。

---

## 一、本章概述

knowledge.py 是整个 DeepTutor 项目中最长的单文件之一（2808 行），它实现了知识库的完整 CRUD（创建、读取、更新、删除）操作，以及文件上传、索引、同步、RAG 引擎配置等高级功能。

用一句话概括：这是 DeepTutor 喂资料给 AI 的入口。你上传的所有 PDF、Word 文档、Markdown 笔记，都通过这个模块进入知识库，被 AI 索引和理解。

---

## 二、知识库是什么？

在深入源码之前，先理解知识库在 DeepTutor 中的概念：

知识库 = 一个文件夹 + 一个 AI 索引

- 文件夹（data/knowledge_bases/<kb_name>/raw/）：存放你上传的原始文件（PDF、Word 等）
- AI 索引（向量数据库）：把文件内容转换成 AI 能理解的向量，方便快速检索

当你问 AI 一个问题时，系统会先去知识库中搜索相关内容，然后把找到的资料作为参考材料发给 AI，让 AI 基于这些资料来回答。这就是 RAG（检索增强生成）的核心思想。

类比：知识库就像你给 AI 准备的一本参考书。你先把书（文件）放进去，AI 会在回答问题时翻阅这本书，找到相关内容后再回答你。这样 AI 的回答就不再是凭空想象，而是有据可查。

## 四、核心流程详解

### 4.1 创建知识库的完整流程

路由: POST /api/v1/knowledge/create  
源码行号: 第 2140～2235 行

这是最核心的流程之一。当用户在前端点击创建知识库时，整个流程如下：

用户操作 → 前端发送请求 → 后端接收 → 验证 → 保存文件 → 后台处理

第一步：名称验证（第 2150～2153 行）
系统调用 validate_knowledge_base_name(name) 验证名称是否合法。不允许包含特殊字符、不能为空、不能与已有知识库重名。

第二步：检查是否已存在（第 2157 行）
如果同名知识库已存在，直接返回 400 错误知识库已存在。

第三步：验证 RAG 引擎（第 2160～2162 行）
- _validate_registered_provider(rag_provider)：将传入的引擎名称标准化（比如空字符串或无效名称会被映射为默认引擎 LlamaIndex）
- _assert_provider_ready(rag_provider)：检查引擎是否可用（比如 PageIndex 需要 API Key、GraphRAG 需要安装额外包）

第四步：验证文件格式（第 2162～2164 行）
- _enforce_provider_formats(rag_provider, files)：PageIndex 引擎只接受特定格式的文件
- _validate_upload_batch(files, ...)：检查文件名安全性、文件大小、重复文件名

第五步：立即注册知识库（第 2172～2189 行）
系统会立刻将知识库注册到配置文件中，状态设为 initializing。这样用户在前端就能立即看到新知识库出现在列表中，而不需要等待处理完成。

类比：就像你去餐厅点菜，服务员会先给你一个号码牌（initializing 状态），然后才开始做菜。你不用在柜台干等，可以回到座位，通过号码牌追踪进度。

第六步：保存文件（第 2208～2210 行）
_save_uploaded_files() 将上传的文件保存到知识库的 raw/ 目录下。

第七步：启动后台任务（第 2219 行）
background_tasks.add_task(run_initialization_task, ...) 将实际的索引处理交给后台执行，API 立即返回响应，不阻塞用户。

返回内容（第 2223～2228 行）包含 message、name、files 列表和 task_id。

关键设计：task_id 是前端用来追踪处理进度的凭证。前端可以通过 WebSocket 连接到进度端点来实时查看处理进度。

### 4.2 文件上传流程

路由: POST /api/v1/knowledge/{kb_name}/upload  
源码行号: 第 2061～2137 行

与创建知识库类似，但知识库已存在，只是往里面追加文件。

关键差异：
- 需要验证上传的引擎类型与知识库绑定的引擎类型一致（第 2085～2092 行）
- 上传前会将知识库状态设为 processing（第 2109～2114 行的 _mark_kb_queued_for_processing）
- ZIP 文件会被自动解压，ZIP 内的每个文件单独处理（第 383～401 行的 _save_zip_archive）

实际场景：你已经创建了一个机器学习知识库，现在想追加一篇新的论文 PDF。你只需打开这个知识库，拖入 PDF 文件，系统会自动处理它。

---

### 4.3 后台处理任务：run_upload_processing_task

源码行号: 第 815～955 行

这是上传文件后实际执行索引的后台任务。它不阻塞 API 响应，在后台默默运行。

流程：
1. 创建 ProgressTracker 记录进度
2. 创建 DocumentAdder 处理文件
3. 调用 adder.add_documents() 对比已有文件，筛出新增文件
4. 调用 adder.process_new_documents() 进行实际索引
5. 更新元数据和同步状态
6. 将最终状态写入知识库配置

错误处理：如果部分文件索引失败（比如某个 PDF 是扫描版无法提取文字），系统会记录详细信息并通过 WebSocket 推送给前端，而不是整个任务失败。已经成功索引的文件不受影响。

类比：就像快递分拣——100 个包裹中有一个地址写错了，分拣员会把它挑出来单独处理，其他 99 个正常派送。

### 4.4 知识库列表：多用户权限隔离

路由: GET /api/v1/knowledge/list  
源码行号: 第 1660～1813 行

这是最复杂的路由之一（150+ 行），因为它需要处理多用户场景下的权限隔离。

逻辑概要：
1. 获取当前用户自己的所有知识库
2. 获取该用户被分配的知识库（管理员分配给普通用户的）
3. 合并两份列表，标记每个知识库的来源（自己的 vs 分配的）
4. 对不可用的知识库（如管理员删除了但还没取消分配的），返回特殊状态

关键字段：
- source: admin 或 user — 表示知识库的归属
- assigned: true/false — 是否是管理员分配的
- read_only: true/false — 是否只读
- available: true/false — 是否可用

类比：就像公司的共享文件夹——有的文件夹是你自己创建的（可编辑），有的是老板分享给你的（只读），有的是曾经分享过但现在已失效的（不可用）。

### 4.5 重建索引（Reindex）

路由: POST /api/v1/knowledge/{kb_name}/reindex  
源码行号: 第 2379～2462 行

使用场景：
- 你更换了 Embedding 模型（比如从 OpenAI 的 embedding 模型换成了本地模型），需要重建索引
- 索引文件损坏了，需要重新生成
- 知识库的 RAG 引擎发生了变化

智能跳过：对于 LlamaIndex 引擎，系统会检查当前 Embedding 配置是否与已有索引匹配。如果匹配且索引有效，直接返回 noop: true（无需重建），避免重复工作。

源码行号：第 2401～2435 行实现了这个智能跳过逻辑。

类比：就像图书馆的索引卡片——如果你没有换分类体系，就不需要重新整理所有卡片；只有当分类体系变了，才需要重新整理。

### 4.6 重试失败的初始化

路由: POST /api/v1/knowledge/{kb_name}/retry  
源码行号: 第 2465～2490 行

使用场景：知识库创建过程中因为某些原因失败了（比如文件格式不支持、API Key 过期等），修复问题后可以点重试。

实现：实际上就是调用 reindex_knowledge_base()，但只允许在 error 状态下调用。如果知识库状态正常，会返回 409 错误，提示用户使用 reindex 功能。

## 五、RAG 引擎管理

### 5.1 什么是 RAG 引擎？

DeepTutor 支持多种 RAG（检索增强生成）引擎，每种引擎有不同的特点和适用场景：

| 引擎 | 特点 | 适用场景 |
|------|------|---------|
| LlamaIndex（默认） | 本地运行，向量检索 + 关键词检索 | 通用场景，隐私敏感 |
| PageIndex | 云端服务，需要 API Key | 快速部署，不想管理本地索引 |
| GraphRAG | 知识图谱检索，理解实体关系 | 复杂知识体系，需要理解概念关联 |
| LightRAG | 轻量级，支持本地和远程 | 资源受限环境 |

源码行号：第 55～66 行定义了这些引擎的常量。

### 5.2 引擎就绪检查：_assert_provider_ready

源码行号: 第 574～616 行

在创建知识库或使用某个引擎之前，系统会检查该引擎是否可用：

- PageIndex：检查 API Key 是否已配置
- GraphRAG：检查 graphrag 包是否已安装
- LightRAG：检查 lightrag 包是否已安装

如果检查不通过，返回 400 错误并给出明确的修复指引。

类比：就像你想用打印机，系统会先检查打印机是否连接、是否有墨。如果没墨，它会告诉你请更换墨盒，而不是等你按了打印按钮后才报错。

### 5.3 引擎配置的读写

每个引擎都有自己的配置项，比如：
- LlamaIndex：top_k（返回多少条结果）、chunk_size（文本分块大小）、chunk_overlap（分块重叠大小）
- GraphRAG：community_level（社区层级）、response_type（回答类型）
- LightRAG：top_k、response_type

这些配置都有对应的 GET/PUT 路由，前端可以在设置页面中修改。

### 5.4 引擎模式切换

路由: PUT /api/v1/knowledge/rag-providers/{provider}/mode  
源码行号: 第 1007～1030 行

不同的引擎支持不同的检索模式。例如 LlamaIndex 支持多种模式，你可以选择最适合当前场景的模式。这个路由允许你为引擎设置默认的检索模式。

### 6.1 连接 Obsidian 笔记库

路由: POST /api/v1/knowledge/connect-obsidian  
源码行号: 第 1474～1498 行

使用场景：你已经在 Obsidian 中维护了大量笔记，不想重新上传到 DeepTutor。通过这个功能，你可以直接连接你的 Obsidian 笔记库，DeepTutor 会实时读取其中的内容。

输入：

- 不需要上传、不需要索引，直接读取

### 6.2 连接外部文件夹（已有索引）

路由: POST /api/v1/knowledge/connect-folder  
源码行号: 第 1531～1579 行

使用场景：你已经有一个已经索引好的文件夹（比如之前用 LlamaIndex 索引过的），想直接把它挂载为 DeepTutor 的知识库。

流程：
1. 前端先调用 POST /probe-folder 探测文件夹是否有可用索引
2. 确认后调用 POST /connect-folder 注册连接
3. 系统会重新探测一次（不信任客户端），确保索引有效
4. 注册成功后，这个文件夹就是只读知识库了

安全设计：即使前端的探测结果显示 OK，后端也会再次探测。这是防御中间人攻击的重要措施——永远不信任客户端传来的结果。

### 6.3 连接 LightRAG 服务器

路由: POST /api/v1/knowledge/connect-lightrag-server  
源码行号: 第 1610～1657 行

使用场景：你有一个独立的 LightRAG 服务器在运行，想把它的检索能力接入 DeepTutor。

输入：
- name：连接名称
- server_url：LightRAG 服务器的 URL
- api_key：API Key（可选）
- search_mode：检索模式（可选，如 naive/local/global/hybrid/mix）

关键点：
- 支持多种检索模式
- 检索请求会被转发到远程服务器，不占用本地资源
- 同样有双重探测的安全机制

## 七、文件安全机制

### 7.1 文件名安全化

源码行号: 第 295～332 行

上传的文件名可能包含危险字符（如 ../、*、? 等），系统会进行安全处理：

- _BAD_PATH_CHARS：正则表达式，匹配所有禁止的文件名字符（第 295 行）
- _sanitize_path_segment()：清除禁止字符，限制长度（第 298～301 行）
- _sanitize_rel_subdir()：防止路径穿越攻击（第 304～322 行）

### 7.2 路径穿越防护

源码行号: 第 325～332 行

_safe_join_raw() 函数确保解析后的路径一定在知识库的 raw/ 目录下。它使用 Path.relative_to() 来验证——如果解析后的路径不在 raw/ 目录下，会抛出 ValueError，系统返回 403 错误。

类比：就像酒店的门禁卡——你的卡只能打开你房间的门，即使你尝试把卡插进其他房间的锁，门也不会开。

### 7.3 ZIP 炸弹防护

源码行号: 第 230～289 行

_save_zip_archive() 在解压 ZIP 文件时有以下安全措施：
- 文件大小限制：如果 ZIP 文件超过最大大小限制，直接拒绝
- ZIP Slip 防护：防止解压到目标目录之外
- 扩展名白名单：只解压支持的文档格式，跳过 .exe、.sh 等可执行文件
- 压缩炸弹检测：检测解压后文件是否异常大

## 八、实时进度推送（WebSocket）

### 8.1 为什么需要 WebSocket？

知识库的初始化和索引是耗时操作（可能需要几分钟），如果用普通的 HTTP 请求，用户只能看到处理中，不知道进度。WebSocket 可以实时推送进度信息，让用户看到：
- 正在处理哪个文件
- 当前进度百分比
- 是否有错误

### 8.2 进度 WebSocket 端点

路由: WS /api/v1/knowledge/{kb_name}/progress/ws  
源码行号: 第 2525～2668 行

流程：
1. 前端通过 WebSocket 连接到这个端点
2. 系统先发送当前进度（如果有的话）
3. 然后进入轮询循环，每秒检查一次进度文件
4. 当进度变化时，推送新的进度数据
5. 当进度达到 completed 或 error 时，等待 3 秒后断开连接

智能连接管理（第 2567～2592 行）：
- 如果知识库已经就绪且没有活跃任务，直接发送完成状态并关闭连接（快速路径）
- 如果任务在 2 分钟前就完成了，不会进入无限轮询
- 这避免了前端不断重连导致的资源浪费

### 8.3 任务日志流

路由: GET /api/v1/knowledge/tasks/{task_id}/stream  
源码行号: 第 2049～2058 行

除了进度百分比，系统还提供了详细的任务日志流。使用 SSE（Server-Sent Events）协议，前端可以实时看到后台任务的详细日志，包括：
- 正在处理哪个文件
- 提取了多少文本
- 索引了多少向量
- 是否有错误及其详细信息

## 九、关联文件夹同步

### 9.1 业务场景

假设你有一个本地文件夹，这个文件夹通过 Dropbox 或 Google Drive 自动同步。你可以把这个文件夹关联到 DeepTutor 的知识库，然后 DeepTutor 会：
- 检测文件夹中的新文件
- 检测已有文件的修改
- 自动同步变更

类比：就像 iPhone 的照片流——你在手机上拍了照片，电脑上自动就有了。关联文件夹同步让你在本地文件夹中放了新文档，DeepTutor 自动就能检索到。

### 9.2 关联文件夹

路由: POST /api/v1/knowledge/{kb_name}/link-folder  
源码行号: 第 2671～2698 行

输入一个文件夹路径，系统会将其注册为知识库的关联文件夹。

输入：folder_path，本地文件夹路径。支持绝对路径、相对路径和 ~ 开头的用户目录路径。

### 9.3 同步文件夹

路由: POST /api/v1/knowledge/{kb_name}/sync-folder/{folder_id}  
源码行号: 第 2735～2808 行

流程：
1. 获取关联文件夹信息
2. 调用 manager.detect_folder_changes() 检测变更
3. 筛选出新增和修改的文件
4. 如果没有变更，直接返回
5. 如果有变更，启动后台任务处理

关键设计：同步状态只在索引成功后才更新（第 2773～2775 行）。这避免了标记为已同步但实际索引失败的竞态问题。

| 设计决策 | 说明 | 源码行号 |
|---------|------|---------|

## 十二、阅读建议

对于产品经理和运营人员，理解以下几点就足够了：

1. 知识库是 AI 的参考资料库，你上传的文件会被 AI 索引和理解
2. 创建知识库是异步的，大文件需要时间处理，可以实时看进度条
3. 支持多种 RAG 引擎，可以根据需求选择（默认的 LlamaIndex 适合大多数场景）
4. 可以连接外部数据源（Obsidian、本地文件夹、远程 LightRAG 服务器）
5. 文件管理是安全的，系统会防止恶意文件名和路径穿越
6. 多用户场景下有权限隔离，自己的知识库和分配的知识库有不同权限

对于技术人员，建议重点关注：
- 创建知识库的完整流程（第 2140～2235 行）
- 后台处理任务（第 815～955 行）
- 多用户权限隔离（第 1660～1813 行）
- WebSocket 进度推送（第 2525～2668 行）
- 文件安全机制（第 295～332 行）
