## 概述

DeepTutor 是一个主打 **STEM 教学**的 AI 助手。在数学、物理、化学等学科中，"图"和"坐标"是不可或缺的——一道几何题需要配图，一个函数需要画曲线，一张试卷里可能有几十张图片。视觉工具层就是 DeepTutor 的"眼睛"和"绘图手"：它负责**下载图片**、**理解图片中的几何元素**、**转换坐标系统**、以及**生成和校验 GeoGebra 绘图脚本**。

如果把整个视觉工具层看作一个图像处理车间，它包含四个工位：

```
┌─────────────────────────────────────────────────────────────┐
│                 deeptutor/tools/vision/                      │
├───────────────┬───────────────┬───────────────┬─────────────┤
│  image_utils  │  block_parser │ coord_transform│ ggb_validator│
│  图片下载与   │  GGBScript    │  坐标转换      │  GeoGebra    │
│  格式转换     │  块解析器     │  (BBox↔GGB)   │  命令校验    │
└───────────────┴───────────────┴───────────────┴─────────────┘
```

> 💡 **一句话理解**：这个模块教 DeepTutor "看懂几何图" 并 "画出数学图"。

## 工具一：`image_utils` — 图片下载与格式转换

### 业务场景

当用户上传一张手写的几何题照片，或者 DeepTutor 需要从 URL 获取一张函数图像时，`image_utils` 就是第一个被调用的。它负责把各种来源的图片统一转换成 LLM 能理解的 base64 格式。

| `image_bytes_to_base64` | 将二进制转为 base64 data URL | 137-152 |
| `url_to_base64` | URL → base64 一站式转换 | 155-168 |
| `resolve_image_input` | 智能解析：优先用 base64，否则下载 URL | 171-209 |

### 关键设计

#### 多来源统一入口：`resolve_image_input`

```
源码位置：image_utils.py:171-209
```

这是整个模块的"总开关"。它接受两种输入：
- `image_base64`：已经编码好的 base64 图片数据
- `image_url`：需要下载的图片 URL

优先级策略是"先到先得"：
1. 如果提供了 `image_base64`，直接校验格式后返回（不浪费时间下载）
2. 如果没有 base64，但有 URL，就下载并转换成 base64
3. 两者都没有？返回 `None`——告诉调用方"没有图片"

```python
# 优先级逻辑（简化版）
if image_base64:
    if is_base64_image(image_base64):
        return image_base64    # 直接返回，不下载
    else:
        raise ImageError(...)  # 格式不对就报错
if image_url:
    return await url_to_base64(image_url)  # 下载 + 转换
return None
```

## 工具二：`block_parser` — GGBScript 代码块解析器

### 业务场景

DeepTutor 在回答几何问题时，LLM 会生成 GeoGebra 绘图脚本。这些脚本不是直接混在回答文本里的——它们被包裹在特殊的代码块中：

````
```ggbscript[page-1;三角形ABC]
A = (0, 0)
B = (4, 0)
C = (2, 3)
Polygon[A, B, C]
```
````

`block_parser` 负责从 LLM 的输出中**识别、提取、校验**这些代码块，把它们从"文本"变成"可执行的绘图指令"。

### 核心数据结构

```python
# 源码位置：block_parser.py:17-34
@dataclass
class GGBBlock:
    page_id: str              # 关联的页面 ID（如 "page-1"）
    title: str                # 块的标题（如 "三角形ABC"）
    content: str              # 校验后的脚本内容
    original_content: str     # 原始内容（仅在被修改时填充）
    validation_warnings: list # 校验警告列表
    block_type: BlockType     # 块类型：ggbscript 或 geogebra

@dataclass
class ParsedContent:
    text_segments: list       # 普通文本段落
    ggb_blocks: list[GGBBlock] # 提取出的 GeoGebra 块
```

### 核心解析算法：`parse_ggb_blocks`

```
源码位置：block_parser.py:47-106
```

这是一个基于正则表达式的解析器，工作流程如下：

```
输入文本
    │
    ▼
┌─────────────────────────────┐
│ 1. 用正则 BLOCK_START_PATTERN│
│    匹配 ```ggbscript[...]    │
│    或 ```geogebra[...]       │
└──────────────┬──────────────┘
               │ 找到块起始标记
               ▼
┌─────────────────────────────┐
│ 2. 提取 page_id 和 title     │
│    如 [page-1;三角形ABC]     │
│    → page_id="page-1"       │
│    → title="三角形ABC"       │
└──────────────┬──────────────┘
               │
               ▼
┌─────────────────────────────┐
│ 3. 用 BLOCK_END_PATTERN      │
│    匹配 ``` 结束标记          │
│    提取中间的内容             │
└──────────────┬──────────────┘
               │
               ▼
┌─────────────────────────────┐
│ 4. 调用 validate_ggbscript   │
│    对脚本内容进行校验和修复    │
└──────────────┬──────────────┘
               │
               ▼
┌─────────────────────────────┐
│ 5. 创建 GGBBlock 对象        │
│    将块前后的文本放入         │
│    text_segments             │
└─────────────────────────────┘
```

正则表达式 `BLOCK_START_PATTERN`（第 39-42 行）：
```python
r"```\s*(ggbscript|geogebra)\s*\[([^\]\s;]+)(?:;([^\]]*))?\]\s*\n?"
```
这个正则可以匹配：
- ```` ```ggbscript[page-1] ````
- ```` ```geogebra[page-1;三角形ABC] ````
- 甚至 ```` ```  ggbscript  [  page-1  ;  我的图  ]  ````（带空格也兼容）

### 流式解析器：`StreamingBlockParser`

```
源码位置：block_parser.py:109-251
```

当 LLM 以流式（streaming）方式输出时，文本是一块一块到达的——可能一个 GGBScript 代码块被切成了好几段。`StreamingBlockParser` 是一个**有状态**的增量解析器，解决了这个问题。

**状态机设计**：

```
        ┌──────────┐
        │   idle   │ ← 初始状态：等待块的开始
        └────┬─────┘
             │ 发现 ```ggbscript[...]
             ▼
        ┌──────────┐
        │ in_block │ ← 正在收集块内容
        └────┬─────┘
             │ 发现 ```
             ▼
        ┌──────────┐
        │   idle   │ ← 块完成，继续等待下一个
        └──────────┘
```

**关键细节**：
- `feed(chunk)` 方法每次接收一小段文本，返回已完成的事件列表
- 在 `idle` 状态下，如果发现 ` ``` ` 但还没看到完整的块起始标记，会保留最多 50 个字符在缓冲区中等待（第 159-167 行）
- `flush()` 方法在流结束时调用——即使块不完整，也会尽力输出

## 工具三：`coord_transform` — 坐标系统转换

### 业务场景

这是视觉工具层中最"数学"的部分。当 DeepTutor 分析一张几何图片时，它先用 BBox（边界框检测）识别出图中的点、线、三角形等元素的位置——这些位置是**像素坐标**（以图片左上角为原点，向右为 X 正方向，向下为 Y 正方向）。

但 GeoGebra 使用的是**数学坐标**（以画面中心为原点，向右为 X 正方向，**向上**为 Y 正方向）。`coord_transform` 就是这两个坐标系统之间的"翻译官"。

### 两个坐标系统

```
BBox 坐标系统（像素坐标）          GeoGebra 坐标系统（数学坐标）
┌─────────────────────┐           ┌─────────────────────┐
│ (0,0)               │           │                     │
│  ┌──────────────────│           │  (-10, 8)  (10, 8)  │
│  │                  │           │    ┌─────────────┐  │
│  │       ●          │           │    │      ●      │  │
│  │    (400, 300)    │           │    │   (0, 0)    │  │
│  │                  │           │    │             │  │
│  └──────────────────│           │    └─────────────┘  │
│                (800,600)        │  (-10, -8) (10, -8) │
│ 原点：左上角                     │  原点：中心           │
│ X：向右为正                      │  X：向右为正          │
│ Y：向下为正                      │  Y：向上为正          │
└─────────────────────┘           └─────────────────────┘
```

| `convert_bbox_elements_to_ggb` | 批量转换 BBox 检测结果中的所有元素 | 133-228 |

| `is_perpendicular` / `is_parallel` | 几何关系判断 | 276-326 |
| `format_ggb_point` / `format_set_coord_system` | 格式化为 GeoGebra 命令 | 409-436 |

### 核心转换算法：`bbox_to_ggb`

```
源码位置：coord_transform.py:68-99
```

转换公式非常直观——就是"归一化 + 映射 + 翻转"：

```
步骤 1：归一化到 [0, 1]
  norm_x = bbox_x / img_width
  norm_y = bbox_y / img_height

步骤 2：映射到 GeoGebra 坐标范围
  ggb_x = x_min + norm_x * (x_max - x_min)    # X 轴：线性映射

步骤 3：Y 轴翻转（BBox 的 Y 向下，GeoGebra 的 Y 向上）
  ggb_y = y_max - norm_y * (y_max - y_min)    # 注意：用 y_max 减去
```

### 批量转换：`convert_bbox_elements_to_ggb`

```
源码位置：coord_transform.py:133-228
```

这个函数是整个模块的"集大成者"。它接收 BBox 检测的完整输出（包含各种几何元素），把每个元素的坐标都转换成 GeoGebra 坐标，并添加 `ggb_` 前缀的新字段。支持的几何元素类型包括：

| 元素类型 | 原始字段 | 转换后字段 |
|----------|----------|------------|
| 点（Point） | `position` | `ggb_position` |
| 线段（Segment） | `start`, `end` | `ggb_start`, `ggb_end` |
| 多边形（Polygon） | `vertices` | `ggb_vertices` |
| 圆（Circle） | `center`, `radius` | `ggb_center`, `ggb_radius` |

> 📌 **圆的半径处理**：半径不是简单地坐标转换，而是按比例缩放——`ggb_radius = pixel_radius × (ggb_width / img_width)`。这样保证圆在 GeoGebra 中的形状和原图一致。

### 智能坐标范围推荐：`suggest_coord_system`

```
源码位置：coord_transform.py:329-406
```

在不知道图片中几何元素的实际数学范围时，这个函数根据 BBox 检测结果自动推荐一个合适的 GeoGebra 坐标范围。

算法思路：
1. 收集所有几何元素的坐标点
2. 计算 X 和 Y 的最小/最大值
3. 根据图片宽高比估算合适的坐标范围
4. 加上 20% 的 padding（留白）
5. 保持宽高比一致，确保图形不变形

### 几何关系判断：`is_perpendicular` 和 `is_parallel`

```
源码位置：coord_transform.py:276-326
```

这两个函数使用向量运算判断几何关系：
- **垂直判断**：两条线段的方向向量做**点积**，结果接近 0 → 垂直
- **平行判断**：两条线段的方向向量做**叉积**，结果接近 0 → 平行

两个函数都接受 `tolerance` 参数（默认 0.01），允许一定的浮点误差。

## 工具四：`ggb_validator` — GeoGebra 命令校验器

### 业务场景

LLM 生成的 GeoGebra 脚本不总是完美的。它们可能会犯一些"低级错误"：
- 用圆括号 `()` 代替方括号 `[]`（如 `Circle(A, B)` 而不是 `Circle[A, B]`）
- 包含 Python 风格的 `# 注释`
- 使用 `Point({x, y})` 这种错误语法
- 数学公式写法不规范

`ggb_validator` 是一个"质检员"——它在脚本执行前进行校验和自动修复，降低因语法错误导致的绘图失败率。

### 核心函数

| 函数 | 作用 | 源码行 |
|------|------|--------|
| `validate_command` | 校验单条命令 | 172-211 |
| `validate_ggbscript` | 校验完整脚本（逐行） | 214-252 |
| `fix_brackets` | 修复括号错误 | 106-126 |
| `fix_common_mistakes` | 修复常见错误 | 129-148 |
| `validate_equation_format` | 校验方程格式 | 151-169 |
| `get_command_help` | 获取命令帮助文档 | 255-283 |

### 校验规则详解

#### 规则 1：方括号修复（`fix_brackets`）

```
源码位置：ggb_validator.py:106-126
```

GeoGebra 的标准语法要求**函数参数用方括号 `[]`，而不是圆括号 `()`**。但 LLM 经常混淆——毕竟在大多数编程语言中，圆括号才是标准的。

`COMMANDS_WITH_BRACKETS`（第 23-87 行）定义了 50+ 个应该使用方括号的命令，包括：
- 几何构造：`Point`, `Midpoint`, `Line`, `Segment`, `Circle`, `Polygon`...
- 变换操作：`Translate`, `Rotate`, `Reflect`, `Dilate`...
- 样式设置：`SetColor`, `SetLineThickness`, `SetPointSize`...
- 视图控制：`SetCoordSystem`, `ShowAxes`, `ShowGrid`...

正则 `PAREN_TO_BRACKET_PATTERN`（第 100-103 行）自动匹配这些命令的圆括号用法并替换为方括号。

#### 规则 2：常见错误修复（`fix_common_mistakes`）

```
源码位置：ggb_validator.py:129-148
```

预定义的错误模式及修复：

| 错误模式 | 修复 | 说明 |
|----------|------|------|
| `Point({x, y})` | `(x, y)` | 大括号是 Python 语法，不是 GeoGebra |
| `log(10, x)` | `lg(x)` | GeoGebra 没有双参数 log，用 lg |
| `# 注释` | 删除整行 | GeoGebra 不支持 `#` 注释 |

#### 规则 3：方程格式检查（`validate_equation_format`）

```
源码位置：ggb_validator.py:151-169
```

检查分数系数——如 `x^2/4 + y^2/9 = 1`，建议改为整数形式 `9x^2 + 4y^2 = 36`。这不是语法错误，而是一个**最佳实践建议**——整数形式在某些 GeoGebra 版本中渲染更稳定。

### 完整脚本校验：`validate_ggbscript`

```
源码位置：ggb_validator.py:214-252
```

逐行处理脚本，每行调用 `validate_command`，收集所有警告和错误，返回修复后的脚本。

### 内置命令帮助：`get_command_help`

```

## 设计亮点

### 1. 流式兼容
`StreamingBlockParser` 让 GGBScript 代码块解析可以在流式 LLM 输出中增量进行——不需要等完整响应到达，文本一到就实时解析。

### 2. 自动修复，而非拒绝
`ggb_validator` 的设计哲学是"能修就修，不能修再报错"。LLM 生成的脚本大概率有语法瑕疵，直接拒绝会让用户体验很差——自动修复括号、删除注释，让"差不多对的"脚本变成"能用的"。

### 3. 坐标系统封装
`coord_transform` 把像素坐标和数学坐标的转换封装成纯函数，输入输出明确——方便测试，也方便组合使用。

### 4. 图片下载的安全边界
`image_utils` 对 URL 校验、格式白名单、大小限制、超时控制层层把关——防止恶意 URL 或超大文件导致服务崩溃。

### 5. 智能坐标推荐
`suggest_coord_system` 不需要用户手动指定坐标范围，自动从检测结果推算——降低了使用门槛。

## 小结

视觉工具层是 DeepTutor 从"文字 AI"走向"多模态 STEM 教学"的关键基础设施。它让 AI 能够"看懂"几何图（图片下载 + 坐标转换）、"画对"数学图（GeoGebra 校验 + 块解析），并且在各个环节都做了容错和自动修复——因为 LLM 的输出不总是完美的，但用户体验必须是可靠的。
