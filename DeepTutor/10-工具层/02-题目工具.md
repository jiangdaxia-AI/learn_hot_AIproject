# 02 — 题目工具：从试卷到题库的自动化流水线

> Understand-Anything 知识图谱: 26 节点, 25 边, 7 层
> **源码位置**：`deeptutor/tools/question/`  
> **涉及文件**：`__init__.py` (38行), `question_extractor.py` (413行), `exam_mimic.py` (70行)  
> **核心依赖**：MinerU PDF 解析引擎、LLM 统一调用工厂、题目协调器 AgentCoordinator

---

## 概述

如果把 DeepTutor 的"题目工具"比作一个厨房，那么它做的只有一件事：**把一张试卷 PDF 扔进去，端出一盘结构化的题目 JSON**。这背后是一套"OCR + AI 理解 + 仿写生成"的三段式流水线。本章聚焦于工具层的两把"刀"：`extract_questions_from_paper`（从已有试卷中精准提取题目）和 `mimic_exam_questions`（模仿试卷风格仿写新题）。它们共同构成了 DeepTutor 题库构建的核心引擎。

> 💡 **一句话理解**：先"读懂"试卷里有什么题，再"仿照"它的风格出类似的题。

## 工具一：`extract_questions_from_paper` — 从试卷中提取题目

### 业务场景

假设你上传了一份 2023 年高考数学卷的 PDF。DeepTutor 需要知道这份卷子里有哪些题、每道题是什么类型、难度如何、有没有配图、答案是什么。这个工具就是干这件事的——它把"非结构化"的试卷 PDF 变成"结构化"的题目列表，供后续的题库检索、自适应练习、智能出题等场景使用。

### 输入与输出

| 项目 | 说明 |
|------|------|
| **输入** | `paper_dir`（字符串）：MinerU 解析后的试卷目录路径；可选的 `output_dir`（输出目录） |
| **输出** | 一个 JSON 文件，包含提取出的题目列表，每道题有：题号、题目文本、题目类型、难度、参考答案、关联图片 |
| **返回值** | `True` / `False`（是否成功） |

### 关键逻辑拆解

整个提取过程分为四个步骤，就像一位老师在批改试卷：

#### 第一步：定位解析产物（`_find_parsed_content_dir`）

```
源码位置：question_extractor.py:29-55
```

MinerU 解析 PDF 后会生成一个目录，里面有 `.md` 文件（Markdown 格式的试卷内容）和 `_content_list.json`（结构化内容清单）。但这个目录的位置不是固定的——可能是 `auto/`、`hybrid_auto/`，也可能是嵌套的子目录。

`_find_parsed_content_dir` 就像一个"寻宝探测器"，按优先级依次搜索：
1. 先找 `auto/` 或 `hybrid_auto/` 子目录
2. 再遍历所有子目录
3. 最后用 `rglob` 全局搜索 `.md` 文件

找到第一个包含 `.md` 文件的目录就返回。

#### 第二步：加载试卷内容（`load_parsed_paper`）

```
源码位置：question_extractor.py:58-100
```

这一步把 MinerU 的输出"翻译"成工具能理解的三样东西：
- **Markdown 内容**：试卷的纯文本表示（包括公式、表格）
- **Content List**：结构化的页面元素列表（段落、图片、表格的位置信息）
- **图片目录**：试卷中所有图片的文件路径

> 📌 **设计细节**：如果 `content_list.json` 不存在，工具不会报错，只是打印一条警告，然后用 Markdown 内容继续。这是"优雅降级"的思路——少一个信息源总比完全失败强。

#### 第三步：LLM 智能分析（`extract_questions_with_llm`）

```
源码位置：question_extractor.py:102-280
```

这是整个工具的"大脑"。它把试卷内容发给大语言模型，让 LLM 像一个经验丰富的阅卷老师一样，识别出每一道题。

**核心流程**：

1. **构建系统提示词**（第 145-198 行）：这是一个精心设计的 Prompt，告诉 LLM：
   - 你的角色是"专业试卷分析助手"
   - 需要提取 6 个字段：题号、题目文本、题目类型、难度、参考答案、关联图片
   - 题目类型必须是 6 种标准类型之一：`choice`（选择题）、`concept`（判断题）、`fill_in_blank`（填空题）、`short_answer`（简答题）、`written`（写作/证明题）、`coding`（编程题）
   - 难度必须是 `easy`、`medium`、`hard` 之一
   - 输出格式必须是严格的 JSON

2. **构建用户提示词**（第 200-208 行）：把 Markdown 内容（截取前 15000 字符）和可用图片列表一起发给 LLM

3. **调用 LLM**（第 228-260 行）：
   - 使用统一 LLM 工厂的 `llm_complete` 函数
   - 如果提供商支持 `response_format`，就开启 JSON 模式（强制输出 JSON）
   - 使用 `get_agent_params("question")` 获取温度、最大 token 等参数
   - 兼容同步和异步两种调用方式（通过检测是否有运行中的事件循环）

4. **解析 JSON 响应**（第 262-279 行）：使用 `parse_json_response` 安全解析 LLM 的返回，提取 `questions` 数组

> 🎯 **关键设计**：题目类型被严格限定为 6 种标准类型。这不是随意选的——这 6 种类型对应了 DeepTutor 后续的 6 种不同教学策略。选择题需要即时反馈，简答题需要语义理解评分，编程题需要沙箱执行——每一种类型都对应着不同的下游处理逻辑。

#### 第四步：保存结果（`save_questions_json`）

```
源码位置：question_extractor.py:283-318
```

把提取出的题目保存为 JSON 文件，命名格式为 `{试卷名}_{时间戳}_questions.json`。同时打印统计信息：总题数、带图片的题数。

## 工具二：`mimic_exam_questions` — 仿照试卷风格生成新题

### 业务场景

你已经用上面的工具提取了一份试卷的题目结构。现在你想出一些"类似但不相同"的题目——比如给学生做变式练习，或者生成模拟试卷。这个工具就是"仿写引擎"——它分析原试卷的题目风格、难度分布、知识点覆盖，然后生成一批"神似"的新题。

### 输入与输出

| 项目 | 说明 |
|------|------|
| **输入** | `pdf_path`（原始试卷 PDF）或 `paper_dir`（已解析的试卷目录）；`kb_name`（知识库名）；`max_questions`（题目数量上限，默认 10） |
| **输出** | 一个字典，包含 `success`、`summary`（完整的生成摘要）、`generated_questions`（生成的题目列表）、`failed_questions`（失败列表）、`total_reference_questions`（参考题目总数） |

### 关键逻辑

```
源码位置：exam_mimic.py:18-70
```

`exam_mimic.py` 本身是一个**薄封装**（thin wrapper），真正的工作在 `deeptutor/agents/question/coordinator.py` 中的 `AgentCoordinator`。这个封装层做了三件事：

1. **参数校验**（第 29-32 行）：确保 `pdf_path` 和 `paper_dir` 不能同时提供（互斥）
2. **创建协调器**（第 34-41 行）：初始化 `AgentCoordinator`，传入 LLM 配置、知识库名称、输出目录
3. **WebSocket 回调桥接**（第 43-49 行）：如果调用方提供了 `ws_callback`，就包装一个 `_forward` 函数，把协调器的进度事件转发给 WebSocket——这样前端可以实时看到"正在生成第 3/10 题..."
4. **委托生成**（第 51-62 行）：根据输入类型调用 `coordinator.generate_from_exam()`，传入 `paper_mode="upload"`（直接上传 PDF）或 `paper_mode="parsed"`（使用已解析的目录）

> 📌 **为什么用薄封装**：`exam_mimic.py` 的角色是"适配器"——它把旧的 `mimic_exam_questions` 函数签名桥接到新的 `AgentCoordinator` 架构上，保证向后兼容。真正的复杂度在协调器里（多 Agent 协作、题目生成策略、质量校验），但那是另一个章节的故事了。

## 模块入口：`__init__.py` 的职责

```
源码位置：__init__.py:1-38
```

`__init__.py` 做了三件事：

1. **重新导出 MinerU 解析能力**（第 10-15 行）：从 `deeptutor/services/parsing/engines/mineru` 导入 `parse_pdf_to_workdir`、`parse_pdf_with_mineru` 等函数，这样使用者只需要 `from deeptutor.tools.question import parse_pdf_with_mineru` 即可，不用关心底层路径。

## 深入：LLM Prompt 工程设计

`extract_questions_with_llm` 的核心不是代码逻辑，而是那段精心设计的系统提示词（第 145-198 行）。让我们逐段拆解这个 Prompt 的设计思路：

### 角色定义

```
你是专业的试卷分析助手。你的任务是从提供的试卷内容中提取所有题目信息。
```

开门见山，不给 LLM 太多"我是谁"的哲学空间——这减少了它"自由发挥"的倾向。

### 提取字段清单

Prompt 明确列出 6 个字段，每个都有具体的填写要求：

| 字段 | 要求 | 设计意图 |
|------|------|----------|
| `question_number` | 保留原始题号 | 支持"第 3 题做错了"的场景 |
| `question_text` | 选择题需合并题干+选项 | 保证题目完整性，下游可直接使用 |
| `question_type` | 6 种标准类型之一 | 严格枚举，对应 6 种教学策略 |
| `difficulty` | 3 级难度 | 支持自适应难度调节 |
| `answer` | 有则填，无则空字符串 | 区分"此题无答案"和"LLM 忘了填" |
| `images` | 关联图片文件名 | 支持图文混排题目 |

### 类型枚举的严格约束

```
"question_type" MUST be exactly one of: choice, concept, fill_in_blank, 
short_answer, written, coding
```

大写 "MUST" 不是巧合——这是 Prompt Engineering 中的"强调技巧"。相比"请从以下选项中选择"，用 "MUST" 可以显著提高 LLM 遵守约束的比例。

### 六种题目类型的教学设计

为什么是这 6 种？每种类型对应不同的教学策略：

| 类型 | 教学策略 | 典型场景 |
|------|----------|----------|
| `choice` | 即时反馈 + 错误选项解析 | 知识点快速检测 |
| `concept` | 二元判断 + 解释引导 | 概念辨析 |
| `fill_in_blank` | 精确匹配 + 近似语义 | 术语/公式记忆 |
| `short_answer` | 语义理解评分 + 要点覆盖 | 概念理解 |
| `written` | 多维度评分（逻辑/表达/完整） | 深度思考 |
| `coding` | 沙箱执行 + 测试用例校验 | 编程实践 |

### JSON 输出格式的强制约束

```
请按以下 JSON 格式返回结果：
```json
{
    "questions": [
        {
            "question_number": "1",
            ...
        }
    ]
}
```

通过提供一个"示例骨架"，LLM 更容易生成格式正确的 JSON。这比只说"请返回 JSON 格式"可靠得多——因为 LLM 有了一个具体的模板可以"填空"。

### 容错指令

Prompt 末尾的 9 条 "Important Notes" 是关键的容错设计：

1. **"确保提取所有题目，不要遗漏"** → 防止 LLM 偷懒只提取前几题
2. **"保留原始题目文本，不要修改或总结"** → 防止 LLM 自动"优化"题目表述
3. **"选择题必须合并题干和选项"** → 保证下游系统可用
4. **"如果试卷没有答案，answer 设为空字符串"** → 区分"无答案"和"未提取"
5. **"如果没有关联图片，设为空数组 []"** → 保证 JSON 结构一致
6. **"图片文件名应为实际存在的文件名"** → 防止 LLM 编造文件名
7. **"确保返回格式是有效的 JSON"** → 最后的保险

## 深入：Content List 的辅助作用

```
源码位置：question_extractor.py:83-91
```

`content_list.json` 是 MinerU 解析引擎生成的**结构化内容清单**。它记录了试卷中每个页面元素的位置、类型和属性。虽然 `extract_questions_with_llm` 主要使用 Markdown 内容，但 `content_list` 在以下场景中非常有用：

1. **图片关联**：通过 `content_list` 可以精确定位每张图片在哪个题目附近，辅助 LLM 判断图片归属
2. **公式识别**：MinerU 解析的 LaTeX 公式在 `content_list` 中有专门标记，可以用来验证 Markdown 中的公式是否正确
3. **表格处理**：试卷中的表格（如选择题选项排列）在 `content_list` 中有结构化表示

目前代码中 `content_list` 被加载但未深度使用（第 89 行只是打印了日志），这是未来优化的空间——比如将 `content_list` 也传给 LLM 作为辅助上下文。

| 检查点 | 行号 | 错误条件 | 处理方式 |

## 扩展：与 deeptutor/services/parsing 的关系

`__init__.py` 重新导出了 MinerU 相关的函数（第 10-15 行），这意味着 `deeptutor.tools.question` 是 MinerU 解析能力的"公共入口"之一。实际架构是：

```
deeptutor/tools/question/__init__.py  ← 公共 API（薄导出层）
    ↓ 重新导出
deeptutor/services/parsing/engines/mineru/  ← 真正的解析引擎
    ├── backend.py    → parse_pdf_to_workdir
    ├── config.py     → MinerUConfig, resolve_mineru_config
    └── local.py      → parse_pdf_with_mineru
```

这种分层设计的好处：
- 使用者不需要知道 MinerU 引擎在 `services/parsing/engines/` 的深层路径
- 未来如果替换解析引擎（如换成 MathPix），只需修改 `__init__.py` 的导入路径
- 题目工具和解析引擎之间保持松耦合

## 工具三：`parse_pdf_to_workdir` 和 `parse_pdf_with_mineru` — PDF 解析入口

虽然在 `__init__.py` 中只是重新导出，但这两个函数是题目工具链的"第一环"——没有它们，`extract_questions_from_paper` 就没有 Markdown 可读。

### `parse_pdf_to_workdir`
- **业务场景**：将 PDF 试卷解析为结构化的 Markdown + 图片 + content_list
- **输入**：PDF 文件路径
- **输出**：一个工作目录，包含 `.md` 文件、`_content_list.json`、`images/` 目录

### `parse_pdf_with_mineru`
- **业务场景**：在本地环境使用 MinerU 引擎解析 PDF
- **输入**：PDF 文件路径 + MinerU 配置
- **输出**：同 `parse_pdf_to_workdir`

> 📌 这两个函数的详细实现不在本章范围，但理解它们的作用对于理解整个题目工具链至关重要。

## 数据流示例

为了让你直观感受整个过程，下面是"一份 3 道题的数学试卷"的处理过程：

### 输入：MinerU 解析后的 Markdown

```markdown
# 2023 年高中数学测试

## 一、选择题

1. 已知集合 A = {1, 2, 3}，B = {2, 3, 4}，则 A ∩ B = ( )
   A. {1, 2}  B. {2, 3}  C. {3, 4}  D. {1, 4}

2. 函数 f(x) = x² + 2x + 1 的最小值是 ( )
   A. -1  B. 0  C. 1  D. 2

## 二、解答题

3. 证明：三角形内角和为 180°。
   ![triangle](images/image_001.jpg)
```

### 输出：LLM 提取的结构化 JSON

```json
{
  "questions": [
    {
      "question_number": "1",
      "question_text": "已知集合 A = {1, 2, 3}，B = {2, 3, 4}，则 A ∩ B = ( )
A. {1, 2}  B. {2, 3}  C. {3, 4}  D. {1, 4}",
      "question_type": "choice",
      "difficulty": "easy",
      "answer": "B",
      "images": []
    },
    {
      "question_number": "2",
      "question_text": "函数 f(x) = x² + 2x + 1 的最小值是 ( )
A. -1  B. 0  C. 1  D. 2",
      "question_type": "choice",
      "difficulty": "easy",
      "answer": "B",
      "images": []
    },
    {
      "question_number": "3",
      "question_text": "证明：三角形内角和为 180°。",
      "question_type": "written",
      "difficulty": "medium",
      "answer": "",
      "images": ["image_001.jpg"]
    }
  ]
}
```

可以看到，选择题的题干和选项被合并到 `question_text` 中，解答题关联了图片，难度被自动评估。这就是一个"非结构化 → 结构化"的完整转换。

## 设计亮点
## 设计亮点

### 1. 优雅降级
`load_parsed_paper` 在找不到 `content_list.json` 时不会崩溃，只是打印警告继续——用 Markdown 内容也能提取题目，只是少了一些结构化信息。

### 2. 严格的类型枚举
题目类型被限定为 6 种标准类型，难度限定为 3 种。这不是限制 LLM 的创造力，而是保证下游系统的可靠性——教学策略、评分逻辑、UI 渲染都依赖这些类型做路由。

### 3. 循环导入规避
`__init__.py` 中的懒加载 `mimic_exam_questions` 是典型的"延迟导入"模式，避免了模块间的循环依赖。

### 4. 同步/异步双兼容
`extract_questions_with_llm` 通过 `asyncio.get_running_loop()` 检测当前环境，自动选择同步或异步调用方式——同一个函数可以在命令行脚本和 Web 服务中无缝使用。

### 5. JSON 模式优化
当 LLM 提供商支持 `response_format: json_object` 时，显式开启——这大大提高了 JSON 输出的可靠性，减少了"LLM 返回了非 JSON 文本"的解析失败。

## 小结

题目工具层的两个核心函数，一个负责"读"（从试卷中提取题目），一个负责"写"（仿照试卷风格生成新题）。它们共同构成了 DeepTutor 题库能力的基石。在架构上，工具层保持了"薄"的特点——真正复杂的协调逻辑（如多 Agent 协作出题）被下放到 `agents/question/coordinator.py` 中，工具层只做"调用"和"结果整理"。
