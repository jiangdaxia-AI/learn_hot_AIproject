# 配置管理

> Understand-Anything 知识图谱: 26 节点, 25 边, 7 层
> **源码位置**：`deeptutor/services/config/`、`deeptutor/services/settings/`
> **阅读对象**：产品经理 / 运营 / 非技术人员
> **目标**：看懂 DeepTutor 的多层配置体系、各类设置文件的用途和管理方式

---

## 一句话概括

配置管理系统是 DeepTutor 的"控制面板"。它管理着系统的所有设置——从端口号、语言偏好，到模型选择、知识库配置、文档解析引擎切换。所有这些配置以 JSON 文件的形式存储在 `data/user/settings/` 目录下，由统一的 `RuntimeSettingsService` 负责读写和校验。

---

## 一、整体架构

配置管理分为三个层次：

```
┌─────────────────────────────────────────────────────┐
│                  入口层                              │
│   config/__init__.py  — 统一导出所有配置 API          │
├─────────────────────────────────────────────────────┤
│                  加载层                              │
│   config/loader.py          — YAML 配置加载器        │
│   config/launch_settings.py — 启动参数解析            │
├─────────────────────────────────────────────────────┤
│                  服务层                              │
│   config/runtime_settings.py  — 运行时设置服务        │
│   config/model_catalog.py     — 模型目录管理          │
│   settings/interface_settings.py — UI 设置           │
│   config/capabilities_settings.py — 能力设置          │
│   config/knowledge_base_config.py — 知识库配置        │
└─────────────────────────────────────────────────────┘
```

## 二、配置文件的存储位置

| 文件名 | 用途 | 格式 |

| `graphrag.json` | GraphRAG 检索参数 | JSON |
| `lightrag.json` | LightRAG 检索参数 | JSON |
| `llamaindex.json` | LlamaIndex 检索参数 | JSON |
| `pageindex.json` | PageIndex API 配置 | JSON |

## 三、config/loader.py —— 配置加载器

**源码路径**：`deeptutor/services/config/loader.py`

### 3.1 它解决什么问题？

DeepTutor 的配置来源多样——有系统默认值、有用户修改的 JSON 文件、有环境变量覆盖。`loader.py` 负责把这些来源统一加载、合并、校验，给上层提供一个干净的配置字典。

### 3.2 核心组件

#### 常量：`PROJECT_ROOT`（第 20 行）

**业务上做什么**：指向 DeepTutor 的运行时根目录。所有配置文件的路径都基于这个目录计算。

**获取方式**：`get_runtime_home()` —— 自动检测 DeepTutor 的安装位置。

#### 函数：`get_runtime_settings_dir()`（第 23-26 行）

**业务上做什么**：返回配置文件的目录路径：`PROJECT_ROOT/data/user/settings/`。

#### 函数：`_deep_merge()`（第 29-50 行）

**业务上做什么**：深度合并两个字典。用户配置覆盖默认配置时使用。

**关键逻辑**：如果两个字典的同一个 key 都是字典类型，递归合并；否则直接用新值覆盖旧值。

**示例**：
```python
# 默认配置
base = {"chat": {"temperature": 0.2, "max_rounds": 8}}
# 用户配置
override = {"chat": {"temperature": 0.5}}
# 合并结果
result = {"chat": {"temperature": 0.5, "max_rounds": 8}}  # 只覆盖了 temperature
```

#### 函数：`resolve_config_path()`（第 86-108 行）

**业务上做什么**：解析配置文件路径。如果文件不存在，抛出 `FileNotFoundError`。

**输入**：配置文件名（如 `"system.json"`）
**输出**：`(完整路径, False)`

#### 函数：`load_config_with_main()`（第 111-126 行）

**业务上做什么**：加载一个 YAML 配置文件，并注入运行时路径。

**关键步骤**：
1. 解析配置文件路径
2. 读取 YAML 文件
3. 调用 `_inject_runtime_paths()` 注入运行时路径（如代码执行工作区、知识库目录等）

#### 函数：`_inject_runtime_paths()`（第 59-78 行）

**业务上做什么**：给配置字典注入运行时路径。

**注入的路径**：
- `user_data_dir`：用户数据目录
- `knowledge_bases_dir`：知识库目录
- `user_log_dir`：日志目录
- `performance_log_dir`：性能日志目录
- `question_output_dir`：深度提问输出目录
- `research_output_dir`：研究输出目录
- `solve_output_dir`：深度解题输出目录
- `tools.run_code.workspace`：代码执行工作区

**为什么需要**：这些路径在运行时才能确定（比如用户数据目录取决于安装位置），不能硬编码在配置文件中。

#### 函数：`get_agent_params()`（第 198-273 行）

**业务上做什么**：获取某个模块的 Agent 参数（温度和最大 token 数）。

**输入**：模块名（如 `"solve"`、`"research"`、`"question"`、`"chat"` 等）
**输出**：`{"temperature": 0.3, "max_tokens": 8192}`

**配置来源**：`agents.yaml` 文件。不同模块有不同的默认值：
- 解题（solve）：低温度（0.3），高 token（8192）——需要精确推理
- 研究（research）：中等温度（0.5），中等 token（4096）——需要一定创造力
- 聊天（chat）：低温度（0.2），高 token（8000）——需要稳定输出

**优先级**：用户配置文件 > 模块默认值 > 全局默认值（temperature=0.5, max_tokens=4096）

#### 函数：`get_chat_params()`（第 286-308 行）

**业务上做什么**：获取聊天能力的参数配置。

**特殊之处**：聊天能力有两个阶段（探索 exploring 和 回复 responding），每个阶段有独立的 `max_tokens`。返回的字典确保所有阶段键都存在，调用方可以安全索引。

#### 常量：`DEFAULT_CHAT_PARAMS`（第 276-283 行）

```python
{
    "temperature": 0.2,
    "max_rounds": 8,           # 最大探索轮次
    "exploring": {"max_tokens": 1600},
    "responding": {"max_tokens": 8000},
}
```

**设计思路**：探索阶段 token 较少（1600），因为探索阶段只需要简短的思考；回复阶段 token 较多（8000），因为需要输出完整的答案。

## 四、config/runtime_settings.py —— 运行时设置服务

**源码路径**：`deeptutor/services/config/runtime_settings.py`

### 4.1 它解决什么问题？

这是配置管理的"核心引擎"。它负责：
- 创建和维护所有 JSON 配置文件
- 提供默认值并在缺失时自动创建文件
- 校验配置值的合法性
- 处理环境变量覆盖（用于 Docker 部署等场景）
- 支持旧版本配置文件的迁移

### 4.2 核心组件

#### 类：`RuntimeSettingsService`（第 309-927 行）

这是整个配置系统中最核心的类，约 600 行代码。它管理着 8 种配置文件。

**设计模式**：单例模式（`_instances` 字典，第 317 行），确保同一个设置目录只有一个服务实例。

**构造函数**（第 319-328 行）：
- `settings_dir`：设置文件目录
- `process_env`：环境变量字典（默认 `os.environ`）
- 维护 `_external_process_keys` 和 `_internal_exported_values` 用于区分"外部设置的环境变量"和"自己导出的环境变量"

**核心方法：`_load_or_create()`**（第 567-583 行）

这是所有 `load_*` 方法的底层实现。逻辑：
1. 读取 JSON 文件
2. 如果有内容 → 合并默认值，校验，写回
3. 如果没内容 → 用默认值创建新文件
4. 返回校验后的配置

**比喻**：这就像酒店的前台——你入住时如果房间已经布置好了，检查一下就行；如果还没布置，按标准配置布置好再给你。

**各类设置的管理方法**：

| 方法对 | 管理对象 | 配置文件 |
|--------|---------|---------|
| `load_system()` / `save_system()` | 系统设置 | `system.json` |
| `load_auth()` / `save_auth()` | 认证设置 | `auth.json` |
| `load_integrations()` / `save_integrations()` | 集成设置 | `integrations.json` |
| `load_document_parsing()` / `save_document_parsing()` | 文档解析 | `document_parsing.json` |
| `load_mineru()` / `save_mineru()` | MinerU 引擎 | `document_parsing.json` 的子集 |
| `load_pageindex()` / `save_pageindex()` | PageIndex | `pageindex.json` |
| `load_llamaindex()` / `save_llamaindex()` | LlamaIndex | `llamaindex.json` |
| `load_graphrag()` / `save_graphrag()` | GraphRAG | `graphrag.json` |
| `load_lightrag()` / `save_lightrag()` | LightRAG | `lightrag.json` |

**环境变量覆盖机制**（第 606-667 行）：

每个 `load_*` 方法都有对应的 `_apply_*_process_overrides` 方法。当 `include_process_overrides=True` 时，环境变量的值会覆盖文件中的配置。例如：

- 系统设置中 `backend_port` 可以被 `BACKEND_PORT` 环境变量覆盖
- MinerU 的 `api_token` 可以被 `MINERU_API_TOKEN` 环境变量覆盖

**为什么要区分内部导出和外部设置**（第 554-565 行）：
- 启动时 `export_environment()` 会把配置导出为环境变量（给子进程用）
- 如果有用户手动设置的环境变量，标记为 `_external_process_keys`
- 下次读取时，只使用外部设置的环境变量，忽略自己导出的（避免循环覆盖）

**数据校验**（各类 `_normalize_*` 方法）：

每个配置类型都有对应的校验方法，确保配置值合法：

- `_normalize_system()`（第 866-907 行）：校验端口范围（1-65535）、附件大小限制（1-2048MB）、字符数限制（10000-5000000）
- `_normalize_auth()`（第 909-917 行）：token 过期时间至少 1 小时
- `_normalize_llamaindex()`（第 718-739 行）：chunk_size 范围 64-8192，chunk_overlap 必须小于 chunk_size
- `_normalize_document_parsing()`（第 764-806 行）：处理 v1→v2 迁移，确保所有引擎都存在

**配置迁移**：`_migrate_legacy_document_parsing_file()`（第 585-601 行）

旧版本中 MinerU 的配置存储在 `mineru.json`，新版本统一为 `document_parsing.json`。这个方法在首次访问时自动重命名文件，确保旧用户升级后配置不丢失。

#### 系统设置详解：`DEFAULT_SYSTEM_SETTINGS`（第 15-42 行）

```python
{
    "version": 1,
    "backend_port": 8001,                # 后端端口
    "frontend_port": 3782,               # 前端端口
    "disable_ssl_verify": False,         # 是否禁用 SSL 验证
    "sandbox_allow_subprocess": True,    # 是否允许代码执行沙箱
    # 附件限制
    "chat_attachment_max_file_mb": 20,   # 单文件最大 20MB
    "chat_attachment_max_total_mb": 25,  # 总附件最大 25MB
    "chat_attachment_max_chars_per_doc": 200_000,  # 单文档最多 20 万字符
    "chat_attachment_max_chars_total": 150_000,    # 总字符数最多 15 万
}
```

**附件限制的设计思路**：单文件限制（20MB）和总限制（25MB）分开，允许用户上传一个 20MB 的大文件 + 一个 5MB 的小文件，但拒绝两个 20MB 的文件。

#### 文档解析引擎配置（第 84-183 行）

DeepTutor 支持 5 种文档解析引擎：

| 引擎名 | 特点 | 适用场景 |
|--------|------|---------|
| `text_only` | 内置文本提取，无额外依赖 | 默认引擎，开箱即用 |
| `mineru` | 专业 PDF 解析，支持公式/表格 | 学术文档、技术文档 |
| `docling` | IBM 开源，支持布局分析 | 复杂排版的文档 |
| `markitdown` | 纯 Python，轻量 | 简单文档，低配机器 |
| `pymupdf4llm` | 基于 PyMuPDF，可提取图片 | 图文混排的 PDF |

每个引擎有自己的配置项。用户可以在设置界面切换引擎，所有配置持久化在一个 `document_parsing.json` 文件中。

#### 全局便捷函数（第 943-1043 行）

这些函数为上层代码提供简洁的调用方式：

- `get_runtime_settings_service()`：获取服务实例
- `ensure_runtime_settings_files()`：启动时确保所有配置文件存在
- `load_system_settings()`：加载系统设置
- `load_auth_settings()`：加载认证设置
- `get_chat_attachment_limits()`：获取附件限制（转为字节单位）
- `get_ws_max_size()`：计算 WebSocket 帧大小上限
- `export_runtime_settings_to_env()`：导出所有设置为环境变量

#### 数据类：`ChatAttachmentLimits`（第 965-972 行）

**业务上做什么**：将附件限制从配置文件中的 MB/字符数，转换为代码中直接可用的字节数。

**字段**：
- `max_file_bytes`：单文件最大字节数
- `max_total_bytes`：总附件最大字节数
- `max_chars_per_doc`：单文档最大字符数
- `max_chars_total`：总字符数上限

#### WebSocket 帧大小计算：`compute_ws_max_size()`（第 996-1005 行）

**业务上做什么**：计算 WebSocket 消息的最大帧大小。

**为什么需要**：聊天附件通过 WebSocket 以 base64 编码传输（膨胀约 4/3 倍），还需要额外的 JSON 信封空间。帧大小必须足够大才能容纳完整附件，否则大文件上传会失败。

## 五、config/launch_settings.py —— 启动参数

**源码路径**：`deeptutor/services/config/launch_settings.py`

### 5.1 它解决什么问题？

DeepTutor 启动时需要知道端口号、语言等参数。这些参数可能来自多个来源：配置文件、环境变量、默认值。`launch_settings.py` 负责统一解析这些来源，确定最终的启动参数。

### 5.2 核心组件

#### 数据类：`LaunchSettings`（第 19-28 行）

**业务上做什么**：封装启动参数。

**字段**：
- `backend_port`：后端端口
- `frontend_port`：前端端口
- `language`：界面语言（`"en"` 或 `"zh"`）
- `source`：参数来源说明（如 `"data/user/settings/system.json + environment"`）
- `settings_dir`：设置目录路径
- `interface_json_path` / `system_json_path`：配置文件路径

#### 函数：`load_launch_settings()`（第 61-114 行）

**业务上做什么**：加载启动参数，按优先级合并多个来源。

**优先级**（从高到低）：
1. 环境变量（`BACKEND_PORT`、`FRONTEND_PORT`、`UI_LANGUAGE`）
2. 配置文件（`system.json`、`interface.json`）
3. 默认值（后端 8001、前端 3782、英文）

**`source` 字段**：记录了参数的实际来源，方便调试。例如 `"data/user/settings/system.json + environment"` 表示端口来自配置文件，但被环境变量覆盖了。

## 六、config/model_catalog.py —— 模型目录

**源码路径**：`deeptutor/services/config/model_catalog.py`

### 6.1 它解决什么问题？

DeepTutor 支持多种 AI 服务：LLM（大语言模型）、Embedding（嵌入模型）、Search（搜索）、TTS（文本转语音）、STT（语音转文本）、ImageGen（图片生成）、VideoGen（视频生成）。每种服务可以有多个提供商配置（profile），每个提供商可以有多个模型。`ModelCatalogService` 管理这个多层结构。

### 6.2 核心组件

#### 数据结构（第 19-46 行）

模型目录的 JSON 结构：

```json
{
  "version": 1,
  "services": {
    "llm": {
      "active_profile_id": "llm-profile-abc123",
      "active_model_id": "llm-model-def456",
      "profiles": [
        {
          "id": "llm-profile-abc123",
          "name": "我的 OpenAI",
          "binding": "openai",
          "base_url": "https://api.openai.com/v1",
          "api_key": "sk-xxx",
          "models": [
            {
              "id": "llm-model-def456",
              "name": "GPT-4o",
              "model": "gpt-4o"
            }
          ]
        }
      ]
    },
    "embedding": { ... },
    "search": { ... },
    "tts": { ... },
    "stt": { ... },
    "imagegen": { ... },
    "videogen": { ... }
  }
}
```

#### 类：`ModelCatalogService`（第 49-202 行）

**核心方法**：

- **`load()`**（第 63-79 行）：加载模型目录。如果文件不存在，创建默认的；如果文件存在但缺少某些服务类型，自动补全。

- **`save()`**（第 90-96 行）：保存模型目录，自动校验后写入。

- **`_normalize()`**（第 102-177 行）：校验和补全目录数据。确保：
  - 所有 7 种服务类型都存在
  - 每个 profile 有 ID（没有则自动生成）
  - 每个 model 有 ID（没有则自动生成）
  - 活跃 profile 和 model 的 ID 指向实际存在的项
  - 嵌入模型的 base_url 自动补全端点路径

- **`get_active_profile()`**（第 179-188 行）：获取某个服务的当前活跃配置。

- **`get_active_model()`**（第 190-202 行）：获取某个服务的当前活跃模型。

#### 函数：`get_model_catalog_service()`（第 205-216 行）

**业务上做什么**：获取模型目录服务实例。支持多用户模式——非管理员用户只能读取管理员的目录配置。

## 八、总结：配置的完整生命周期

以"用户修改后台端口"为例，展示配置系统的完整流程：

```
1. 用户在前端设置页面修改端口：8001 → 9000
   → 前端调用 API：POST /api/settings/system {backend_port: 9000}

2. API 层调用 RuntimeSettingsService.save_system({backend_port: 9000})
   → _normalize_system() 校验：9000 在 1-65535 范围内 ✓
   → 合并默认值（其他字段保持不变）
   → 原子写入 data/user/settings/system.json

3. 下次启动时：
   → load_launch_settings() 读取 system.json
   → 检测到 backend_port: 9000
   → 如果环境变量 BACKEND_PORT 也设置了，环境变量优先
   → 返回 LaunchSettings(backend_port=9000, ...)

4. 启动服务器：
   → uvicorn 使用 backend_port=9000 启动
```

**关键设计原则**：

1. **默认值全覆盖**：每个配置项都有默认值，缺失不报错
2. **校验在前**：所有配置值都经过类型和范围校验
3. **原子写入**：使用 `atomic_write_json` 确保写入不损坏文件
4. **环境变量优先**：Docker 等部署场景可通过环境变量覆盖文件配置
5. **向后兼容**：旧版配置文件自动迁移到新格式
6. **多用户支持**：配置文件路径支持按用户隔离
