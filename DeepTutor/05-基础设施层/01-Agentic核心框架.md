# Agentic 核心框架

> **源码位置**：`deeptutor/core/agentic/`
> **阅读对象**：产品经理 / 运营 / 非技术人员
> **目标**：看懂这个模块是做什么的、每个组件解决什么问题

---

## 一句话概括

Agentic 核心框架是 DeepTutor 的"大脑控制中枢"。它负责跟大模型（LLM）对话、理解模型返回的内容、执行模型要求的工具调用，以及管理整个对话循环。你可以把它理解为 DeepTutor 的"自动驾驶系统"——它决定了 AI 每一步该做什么、怎么做、什么时候停下来。

---

## 一、整体架构：8 个模块的分工

框架由 8 个文件组成，每个文件负责一个独立的职责。它们之间像拼图一样组合在一起：

## 二、labels.py —— 协议标签解析器

**源码路径**：`deeptutor/core/agentic/labels.py`

### 2.1 它解决什么问题？

大模型不会直接告诉你"我要调用工具了"或者"我要输出最终答案了"。Agentic 框架用一套**标签协议**来让模型"说话有条理"：模型必须在回复的第一行用一个标签声明自己接下来要做什么，就像写作文先写标题一样。

例如：
- \`\`THINK\`\` → "我要开始推理了"
- \`\`TOOL\`\` → "我要调用工具了"
- \`\`FINISH\`\` → "这是最终答案"
- \`\`PLAN\`\` → "这是我的计划"

### 2.2 核心组件

#### 常量：`LABEL_UNKNOWN` 和 `LABEL_PROBE_MAX_CHARS`（第 17-18 行）

- **`LABEL_UNKNOWN`**：当模型没有按规矩发标签时，系统用这个标记表示"无法识别"。相当于老师批改作业，学生没写标题，老师标注"未分类"。
- **`LABEL_PROBE_MAX_CHARS`**（64）：系统最多检查回复的前 64 个字符来找标签。如果 64 个字符内还找不到标签，就认为模型"犯规"了。这个上限是为了防止模型在开头长篇大论而不发标签。

#### 函数：`strip_label_probe_prefix()`（第 24-31 行）

**业务上做什么**：清理模型回复开头的"杂质"。

**什么场景用**：每次收到模型回复的文本片段时，先调用这个函数去掉前导空格和不可见字符（比如零宽字符 `\u200B`），再开始找标签。

**输入**：一个字符串 buffer
**输出**：清理后的字符串

**大白话解释**：模型有时候会在标签前面加空格、换行，甚至一些看不见的"幽灵字符"（零宽字符）。这个函数把它们都去掉，确保标签解析器能准确识别。

#### 核心函数：`classify_label()`（第 34-95 行）

**业务上做什么**：检查一段文本开头是不是合法的标签。

**什么场景用**：Agentic 循环每收到模型的一段输出，就把这段文本丢给这个函数，问它"开头是合法标签吗？"

**输入**：
- `buffer`：当前收到的文本（可能只是部分内容，因为流式传输是一个字一个字来的）
- `allowed_labels`：当前场景允许哪些标签（比如普通聊天只允许 `FINISH`、`TOOL`、`THINK`；解题模式还多一个 `REPLAN`）
- `final`：是不是最后一波数据了（流结束时设 `True`）

**输出**：
- 如果找到了标签，返回 `(标签名, 标签后面的文本)` 
- 如果还没找到（数据不够），返回 `None`，让调用方继续等待更多数据
- 如果确定不是合法标签，也返回 `None`，调用方会在超时后按 `UNKNOWN` 处理

**关键逻辑大白话解释**：

1. **先清理**：去掉前导空格和幽灵字符。
2. **检查反引号包裹形式**：如 \`\`FINISH\`\`。这是标准格式，用正则匹配。注意一个细节：如果标签后面紧跟的是反引号（比如 \`\`FINISH\`\`\`），那说明标签还没闭合完，不算匹配成功——防止把多余的引号误当成正文。
3. **检查裸标签形式**：有些模型不听话，直接写 `FINISH` 而不是 \`\`FINISH\`\`。系统也接受这种形式，但要求标签后面必须有分隔符（空格、换行、冒号等），避免把 `FINISHED` 这种正文单词误判为标签。
4. **流结束时特殊处理**：如果 `final=True`，即使标签后面没有分隔符，也接受——因为不会再收到更多数据了。

**比喻**：这个函数就像一个快递分拣员，每看到一个包裹（文本片段），就看标签上写的是什么（THINK/TOOL/FINISH），然后把它送到对应的传送带上。

#### 函数：`find_inline_labels()`（第 98-119 行）

**业务上做什么**：检查正文里是否"偷偷"出现了第二个标签。

**什么场景用**：标签协议要求一个回复只能有一个标签（在第一行）。如果模型在正文中间又写了一个 \`\`TOOL\`\`，这是违规的。这个函数负责检测这种情况。

**输入**：正文文本 + 允许的标签列表
**输出**：所有在正文中发现的标签列表

**大白话解释**：相当于"查重"——你已经声明了你要干啥，不能在正文里又偷偷声明一次。如果发现了，agentic 循环会触发"协议违规修复"流程。

## 三、client.py —— LLM 客户端工厂

**源码路径**：`deeptutor/core/agentic/client.py`

### 3.1 它解决什么问题？

DeepTutor 支持多种大模型提供商：OpenAI、Azure、Anthropic（Claude）、GitHub Copilot、OpenAI Codex 等。不同提供商的 API 格式、连接方式各不相同。这个模块的作用是**屏蔽差异**，给上层提供一个统一的"打电话"接口——不管背后接的是谁，上层代码的调用方式都一样。

### 3.2 核心组件

#### 数据类：`LLMClientConfig`（第 43-53 行）

**业务上做什么**：封装连接一个 LLM 提供商所需的所有信息。

**字段说明**：
- `binding`：提供商类型（`"openai"`、`"azure_openai"`、`"anthropic"` 等）
- `model`：模型名称（如 `"gpt-4o"`、`"claude-sonnet-4-20250514"`）
- `api_key`：API 密钥
- `base_url`：API 地址（自部署或代理时使用）
- `reasoning_effort`：推理力度（部分模型支持）

**比喻**：这就是一张"电话卡"——上面写了你要打给谁（binding）、用什么套餐（model）、密码是多少（api_key）。

#### 函数：`build_openai_client()`（第 56-81 行）

**业务上做什么**：根据配置创建一个可用的 LLM 客户端实例。

**输入**：`LLMClientConfig` 配置
**输出**：一个 OpenAI 兼容的客户端对象（可能是 `AsyncOpenAI`、`AsyncAzureOpenAI`，也可能是自定义适配器）

**关键逻辑大白话解释**：

1. 先查提供商注册表，看是不是"原生适配器"（Anthropic、OpenAI Codex、GitHub Copilot）。如果是，走专门的适配器路线。
2. 如果不是，判断是 Azure 还是普通 OpenAI 兼容。Azure 用 `AsyncAzureOpenAI`，普通用 `AsyncOpenAI`。
3. 如果用户关了 SSL 验证（内网自部署场景），创建一个跳过证书验证的 HTTP 客户端。

#### 类：`_ProviderOpenAIAdapter`（第 127-184 行）

**业务上做什么**：把 Anthropic、OpenAI Codex 等非 OpenAI 提供商的 API 包装成 OpenAI 格式。

**大白话解释**：就像电源转换插头——不同国家的插座形状不同，但通过转换插头，你都能充电。这个适配器让上层代码始终用 OpenAI 的格式调用，内部自动翻译成对应提供商的格式。

**关键方法**：
- `_create_completion()`（第 134-184 行）：处理流式和非流式两种模式。流式模式返回 `_ProviderOpenAIStream`，非流式直接返回结果。
- 注意第 142-143 行：`max_tokens` 参数做了兼容处理，优先取 `max_completion_tokens`（OpenAI 新参数名），其次取 `max_tokens`（旧参数名）。

#### 类：`_ProviderOpenAIStream`（第 187-268 行）

**业务上做什么**：把非 OpenAI 提供商的流式响应包装成 OpenAI 的流式格式。

**关键逻辑**：
- 使用 `asyncio.Queue` 作为内部缓冲区（第 210 行）
- 后台任务 `_run()` 调用提供商的 `chat_stream()` 方法，把结果逐个放入队列（第 235-268 行）
- 支持 `on_content_delta` 回调实现实时内容推送

#### 函数：`build_completion_kwargs()`（第 310-329 行）

**业务上做什么**：组装调用 LLM 时需要的参数（温度、最大 token 数等）。

**输入**：temperature、model、max_tokens、binding、reasoning_effort
**输出**：一个参数字典

**大白话解释**：相当于"调料包"——把温度（控制回答的随机性）、最大长度（控制回答的篇幅）、推理力度等参数打包好，一次传给 LLM。

#### 函数：`can_use_native_tool_calling()`（第 354-381 行）

**业务上做什么**：判断当前提供商是否支持 OpenAI 风格的函数调用（工具调用）。

**什么场景用**：在决定是否给 LLM 发送工具定义之前，先问这个函数"这个模型能用工具吗？"如果模型不支持，就走纯文本模式，不让模型调用工具。

**判断逻辑**（按优先级）：
1. 原生适配器（Anthropic、OpenAI Codex）→ 支持
2. 本地模型（Ollama、vLLM 等）→ 不支持（工具支持不稳定）
3. 查提供商能力表 → 如果明确标记支持，就支持
4. 云端 OpenAI 兼容提供商 → 默认支持

## 四、labeled_step.py —— 单次 LLM 调用

**源码路径**：`deeptutor/core/agentic/labeled_step.py`

### 4.1 它解决什么问题？

这是框架的"核心原子操作"——一次完整的流式 LLM 调用。它不仅调用模型，还负责：
- 实时解析模型输出的标签
- 根据标签类型把内容路由到不同的目的地（推理区 vs 最终答案区）
- 处理推理模型的特殊输出格式（如 ` thinking` 标签）
- 收集工具调用请求

### 4.2 核心组件

#### 数据类：`LabeledStepResult`（第 95-102 行）

**业务上做什么**：封装一次 LLM 调用的完整结果。

**字段说明**：
- `label`：模型用了哪个标签（`"FINISH"`、`"TOOL"`、`"THINK"` 等）
- `text`：标签后面的正文内容（已清理）
- `tool_calls`：如果模型请求了工具调用，这里存放工具名和参数列表

#### 核心函数：`run_labeled_step()`（第 104-566 行）

这是整个框架最长的函数（约 460 行），也是最重要的函数。我们分段理解。

**业务上做什么**：驱动一次流式 LLM 调用，实时解析标签，路由内容，收集结果。

**参数说明**（关键参数）：

| 参数 | 含义 | 比喻 |
|------|------|------|
| `client` | LLM 客户端 | 电话机 |
| `messages` | 对话历史 | 聊天记录 |
| `tool_schemas` | 可用工具列表 | 工具箱清单 |
| `allowed_labels` | 允许的标签 | 答题卡上的选项 |
| `final_labels` | 哪些标签的内容要给用户看 | 哪些答案是"公开的" |
| `tool_label` | 哪个标签代表"调用工具" | 哪个选项是"请求帮助" |
| `stream` | 事件总线 | 广播系统 |
| `final_meta` | 如果设为非空，最终答案实时流式输出 | 是否"直播" |

**关键逻辑大白话解释**：

**阶段一：准备阶段**（第 147-159 行）
- 组装调用参数，包括模型名、消息历史、流式开关、工具定义等
- 如果提供了 `usage` 追踪器，加上 `stream_options` 以获取 token 用量

**阶段二：实时流处理**（第 423-511 行）
- 逐块读取模型的流式输出
- 对于每一块数据，先检查是不是 `reasoning_content`（推理模型的思考过程），如果是，直接推到推理区展示
- 对于普通文本，如果还没找到标签 → 送入 `_ingest_pre_label()` 状态机；如果已经找到标签 → 送入 `_emit_text()` 路由

**阶段三：标签探测状态机**（`_ingest_pre_label()`，第 307-373 行）

这是最精巧的部分。模型输出是逐字到达的，你不能等收到全部内容再做判断（那样用户会等很久）。所以需要一个状态机，边收边判断：

1. **如果正在 ` thinking` 预演中**：缓冲内容，等待 ` response` 闭合标签
2. **如果缓冲区开头是 ` thinking`**：进入预演模式，把思考内容实时推送到推理区
3. **如果缓冲区匹配到了允许的标签**：解析标签，把标签后的内容按路由规则发送
4. **如果超过 64 字符还没找到标签**：放弃，标记为 `UNKNOWN`

**阶段四：推理模型支持**（第 62-92 行正则 + 第 269-305 行预演处理）

一些推理模型（如 DeepSeek-R1、Qwen 思考模式）会在正文前插入 ` thinking... response` 块。框架能识别这种格式：
- 检测到 ` thinking` 时，将后续内容实时推送到推理区
- 检测到 ` response` 时，结束推理区，开始正常标签探测
- 即使流结束在 ` thinking` 中间，也会自动补一个 ` response` 来闭合

**阶段五：容错与重试**（第 381-421 行）

如果 LLM 调用失败，框架会自动尝试修复：
- 如果因为 `stream_options` 不支持而失败 → 去掉这个参数重试
- 如果因为工具 schema 不支持而失败 → 去掉工具定义重试（降级为纯文本模式）
- 如果因为图片不支持而失败 → 去掉图片重试（降级为纯文本模式）

**阶段六：收尾**（第 513-566 行）
- 流结束后，如果还没找到标签，用 `final=True` 再检查一次
- 记录 token 用量
- 清理思考标签（`clean_thinking_tags`）
- 返回 `LabeledStepResult`

**比喻**：`run_labeled_step` 就像一次"回合制对话"的单回合——你发消息给模型，模型回复，你解析回复内容，判断它是在思考、在要工具、还是在给最终答案。

## 五、tool_dispatch.py —— 并行工具调度

**源码路径**：`deeptutor/core/agentic/tool_dispatch.py`

### 5.1 它解决什么问题？

当模型说"我要调用工具"时，它可能一次调用多个工具（比如同时查资料、搜网页、读文件）。这个模块负责**并行执行**这些工具调用，收集结果，并处理各种情况（用户中断、任务终止、重复调用等）。

### 5.2 核心组件

#### 数据类：`DispatchOutcome`（第 49-69 行）

**业务上做什么**：封装一次工具调度的完整结果。

**字段说明**：
- `sources`：所有工具返回的引用来源列表
- `tool_messages`：角色为 `tool` 的消息列表（发给 LLM 的工具结果）
- `terminate`：是否有工具要求结束循环
- `pause`：是否有工具要求暂停等待用户输入
- `pause_tool_call_id`：是哪个工具请求的暂停

**注意**：`terminate` 和 `pause` 是互斥的。有两个特殊场景：
- **终止（terminate）**：工具执行完后，循环直接结束，不再继续迭代
- **暂停（pause）**：工具执行完后，等待用户回复，然后继续迭代（不结束）

#### 核心函数：`dispatch_tool_calls()`（第 72-188 行）

**业务上做什么**：并行执行一批工具调用，收集结果。

**关键逻辑**：

1. **数量限制**（第 94-102 行）：最多并行执行 8 个工具（`MAX_PARALLEL_TOOL_CALLS`）。超过则截断并发出警告。

2. **去重**（第 104-118 行）：模型偶尔会重复发出相同的工具调用。框架通过 JSON 参数对比来检测重复，重复的调用只执行一次，其余返回一个"跳过"提示。

3. **并行执行**（第 147-178 行）：使用 `asyncio.gather` 同时执行所有工具调用，每个工具独立运行。

4. **结果收集**（`_collect_outcome()`，第 430-512 行）：
   - 遍历所有工具结果
   - 收集引用来源
   - 第一个请求终止的工具生效
   - 第一个请求暂停的工具生效
   - 对于 UI 去重（`ask_user` 重复调用的后续调用），不发送前端事件

#### 函数：`execute_tool_call()`（第 324-427 行）

**业务上做什么**：执行单个工具调用。

**关键逻辑**：
- 通过 `ToolRegistry` 找到对应工具并执行
- 支持 `event_sink` 回调，让工具在执行过程中实时推送进度
- 如果工具执行失败，捕获异常并返回错误信息（而不是让整个循环崩溃）

#### 去重机制：`_detect_duplicate_calls()`（第 191-223 行）

**业务上做什么**：检测同一批次中的重复工具调用。

**特殊规则**：`ask_user`（询问用户）有更严格的去重——同一批次中只要出现多个 `ask_user`，只保留第一个。因为 UI 只能展示一个"询问卡片"，多个询问会让用户困惑。

## 六、loop.py —— 迭代循环调度器

**源码路径**：`deeptutor/core/agentic/loop.py`

### 6.1 它解决什么问题？

单次 LLM 调用不能解决复杂问题。你可能需要模型先思考（THINK）、再查资料（TOOL）、再思考（THINK）、最后给答案（FINISH）。这需要多轮迭代。`loop.py` 就是管理这个"多轮对话"的调度器。

### 6.2 核心组件

#### 数据类：`LabelProtocol`（第 39-64 行）

**业务上做什么**：声明一个能力（capability）的标签词汇表。

**字段说明**：
- `allowed`：所有合法标签（如 `("THINK", "TOOL", "FINISH", "REPLAN")`）
- `terminal`：哪些标签会让循环结束（如 `{"FINISH"}`）
- `intermediate`：哪些标签只是中间步骤（如 `{"THINK", "REPLAN"}`）
- `final`：哪些标签的内容要输出给用户看（如 `{"FINISH"}`）
- `tool_label`：哪个标签代表"调用工具"（如 `"TOOL"`）

**示例**：普通聊天的协议是 `allowed=(FINISH, TOOL, THINK)`, `terminal={FINISH}`, `tool_label="TOOL"`。解题模式的协议多一个 `REPLAN`，允许模型在思考后调整计划。

#### 数据类：`LoopOutcome`（第 67-76 行）

**业务上做什么**：封装一次完整循环的结果。

**字段说明**：
- `final_label`：最终是用哪个标签结束的
- `final_text`：最终答案文本
- `iterations`：一共迭代了多少轮
- `sources`：所有引用来源
- `messages`：完整的对话历史
- `completed`：是否正常完成（还是被强制终止/超时）

#### 协议类：`LoopHost`（第 79-170 行）

**业务上做什么**：这是循环和具体能力之间的"接口约定"。每个能力（聊天、解题、研究等）都要实现这个接口。

**关键方法**：

| 方法 | 作用 | 比喻 |
|------|------|------|
| `guard_context_window()` | 检查是否超出上下文窗口，必要时裁剪 | 内存管理 |
| `build_iteration_trace_meta()` | 生成每轮迭代的追踪元数据 | 日志记录 |
| `dispatch_tools()` | 执行工具调用 | 实际操作 |
| `resolve_pause()` | 处理暂停后的恢复 | 等待用户 |
| `emit_final()` | 输出最终答案 | 展示结果 |
| `validate_terminal()` | 验证终止标签是否合法 | 安全检查 |
| `protocol_repair_message()` | 生成协议违规的修复提示 | 纠错机制 |
| `force_finalize()` | 超时/超轮次时的强制结束 | 兜底策略 |
| `before_iteration()` | 每轮迭代前的钩子 | 预处理 |
| `on_intermediate()` | 中间标签的副作用处理 | 状态更新 |

#### 核心函数：`run_agentic_loop()`（第 173-372 行）

**业务上做什么**：执行完整的标签驱动循环，直到触发终止标签或达到最大迭代次数。

**关键逻辑**（每轮迭代的流程）：

```
1. guard_context_window()  → 检查上下文窗口，必要时裁剪
2. before_iteration()      → 迭代前预处理
3. build_iteration_trace_meta() → 生成元数据
4. run_labeled_step()      → 调用 LLM，获取标签+内容
5. 检查协议违规：
   - 标签缺失？→ 发送修复提示，重新迭代
   - 多个标签？→ 发送修复提示，重新迭代
   - 工具标签但没工具调用？→ 发送修复提示
   - 非工具标签但有工具调用？→ 发送修复提示
6. 如果是终止标签：
   - validate_terminal() 验证
   - emit_final() 输出结果
   - 结束循环
7. 如果是工具标签：
   - 添加 assistant 消息
   - dispatch_tools() 并行执行工具
   - 如果有暂停 → 等待用户回复
   - 如果有终止 → 结束循环
   - 否则继续下一轮
8. 如果是中间标签：
   - 添加 assistant 消息（保留上下文）
   - 如果是 final 标签 → 也输出给用户
   - 调用 on_intermediate() 钩子
   - 继续下一轮
9. 如果超出最大迭代次数：
   - force_finalize() 强制结束
```

**协议违规修复机制**（第 374-433 行）：

当模型"犯规"时（比如没发标签、发了多个标签），系统不会直接报错，而是：
1. 发送一个"警告"事件到前端
2. 把模型的违规回复保存为 assistant 消息（让模型知道它说了什么）
3. 追加一条 user 消息，告诉模型"你犯规了，请按规则重新来"

**比喻**：`run_agentic_loop` 就像一个国际象棋裁判——它确保每一步都符合规则，发现违规就给黄牌警告并要求重走，直到棋局结束或超时。

## 七、messages.py —— 消息构建器

**源码路径**：`deeptutor/core/agentic/messages.py`

### 7.1 它解决什么问题？

OpenAI 的对话格式中，当 assistant 要调用工具时，需要同时发送文本内容和工具调用列表。这个模块提供了一个标准化的构建方法。

### 7.2 核心函数：`assistant_message_with_tool_calls()`（第 8-27 行）

**业务上做什么**：构建一条包含工具调用的 assistant 消息。

**输入**：
- `content`：模型的文本内容（可以为空）
- `tool_calls`：工具调用列表，每个包含 `id`、`name`、`arguments`

**输出**：一条符合 OpenAI 格式的消息字典

**关键细节**（第 15 行）：`content` 为空时设为 `None` 而不是空字符串。这是 OpenAI 的要求——当有工具调用时，content 必须是 `None`，不能是空字符串。

## 八、usage.py —— Token 用量追踪

**源码路径**：`deeptutor/core/agentic/usage.py`

### 8.1 它解决什么问题？

每次 LLM 调用都消耗 token（和钱）。这个模块负责统计整个对话过程中消耗了多少 token，估算成本。对于产品运营来说，这个数据很重要——可以用来分析成本、优化 prompt、给用户提供用量报告。

### 8.2 核心组件

#### 类：`UsageTracker`（第 11-98 行）

**业务上做什么**：跨多次 LLM 调用累积 token 消耗。

**关键方法**：

- **`add_from_response()`**（第 32-41 行）：从 OpenAI 返回的 usage 对象中读取精确的 token 数。这是首选方式，数据最准确。

- **`add_estimated()`**（第 43-49 行）：当提供商不返回 usage 数据时，用字符数 ÷ 3.5 来估算 token 数。虽然不精确，但总比没有好。

- **`add_usage()`**（第 51-78 行）：适配器方法，兼容 BaseAgent 的旧接口。也是用字符估算。

- **`summary()`**（第 80-98 行）：生成汇总报告，包括：
  - `total_cost_usd`：估算的总费用（美元）
  - `total_tokens`：总 token 数
  - `total_calls`：总调用次数
  - `prompt_tokens` / `completion_tokens`：输入/输出 token 分别统计

**费用计算逻辑**（第 84-91 行）：通过 `get_pricing()` 查询模型定价表，按输入/输出 token 分别计算费用。

#### 函数：`message_content_chars()`（第 101-116 行）

**业务上做什么**：计算一条消息的字符数。用于 token 估算。

**为什么需要这个函数**：消息内容可能是纯文本、多模态数组（图文混合）、或 `None`。需要统一处理这些情况。

#### 函数：`record_streamed_usage()`（第 119-144 行）

**业务上做什么**：记录一次流式调用完成后的用量。

**关键细节**：有些提供商（如 Gemini 的 OpenAI 兼容 API）会在多个流式 chunk 中重复发送 usage 数据。这个函数确保只记录一次，避免重复计数。

## 九、__init__.py —— 公共 API 入口

**源码路径**：`deeptutor/core/agentic/__init__.py`

### 9.1 它做什么？

这个文件不包含业务逻辑，它做了两件事：
1. 用文档字符串说明了整个模块的分层架构（第 1-19 行）
2. 统一导出所有公共 API，让外部代码只需 `from deeptutor.core.agentic import ...` 即可使用

### 9.2 分层架构（文档中的说明）

```
labels          → 协议标签解析（参数化标签集）
client          → OpenAI/Azure 客户端工厂 + 调用参数
usage           → Token 用量累加器
labeled_step    → 一次流式 LLM 调用 + 标签路由
tool_dispatch   → 并行工具执行 + 子追踪
loop            → 迭代调度器，串联以上所有组件
```

## 十、总结：一次完整的 Agentic 循环长什么样？

假设用户在 DeepTutor 中问了一个需要查资料的问题，完整的流程如下：

```
用户提问："Python 的 asyncio 和 threading 有什么区别？"

第 1 轮：
  LLM 回复: ``THINK`` 这个问题需要对比 asyncio 和 threading...
  → 标签是 THINK（中间标签），保留为上下文，继续

第 2 轮：
  LLM 回复: ``TOOL`` {工具: web_search, 参数: "asyncio vs threading"}
  → 标签是 TOOL，并行执行工具调用
  → 工具返回搜索结果

第 3 轮：
  LLM 回复: ``THINK`` 根据搜索结果，asyncio 是单线程协程...
  → 标签是 THINK，保留为上下文，继续

第 4 轮：
  LLM 回复: ``FINISH`` asyncio 和 threading 的主要区别如下...
  → 标签是 FINISH（终止标签），输出结果给用户，循环结束
```

总共 4 轮迭代，调用了 1 次工具，最终输出答案。整个过程由 `loop.py` 调度，`labeled_step.py` 执行每次 LLM 调用，`tool_dispatch.py` 执行工具，`labels.py` 解析标签，`usage.py` 统计 token 消耗。
