# 事件系统

> **源码位置**：`deeptutor/core/stream.py`、`stream_bus.py`、`context.py`、`trace.py`、`errors.py`、`i18n.py`、`capability_protocol.py`、`tool_protocol.py`
> **阅读对象**：产品经理 / 运营 / 非技术人员
> **目标**：看懂 DeepTutor 的事件通信机制、上下文传递、工具和能力协议

---

## 一句话概括

事件系统是 DeepTutor 的"神经系统"。它负责在 AI 引擎（后端）和用户界面（前端）之间传递实时消息——AI 每想一步、每查一个资料、每输出一段文字，都会通过事件系统"广播"出去，前端收到后实时更新界面。没有事件系统，用户就只能对着一个空白屏幕等 AI 全部算完才知道结果。

---

## 一、整体架构

事件系统由 8 个文件组成，可以分为三层：

```
┌─────────────────────────────────────────────────────┐
│                    协议层                             │
│  capability_protocol.py  │  tool_protocol.py         │
│  (能力接口规范)           │  (工具接口规范)            │
├─────────────────────────────────────────────────────┤
│                    通信层                             │
│  stream.py  │  stream_bus.py  │  trace.py            │
│  (事件定义)  │  (事件总线)      │  (追踪元数据)         │
├─────────────────────────────────────────────────────┤
│                    支撑层                             │
│  context.py  │  errors.py  │  i18n.py                │
│  (统一上下文)  │  (异常体系)  │  (国际化)              │
└─────────────────────────────────────────────────────┘
```

## 二、stream.py —— 事件定义

**源码路径**：`deeptutor/core/stream.py`

### 2.1 它解决什么问题？

系统中所有模块都需要一种统一的方式来"报告自己正在做什么"。如果每个模块都用自己的格式，前端就得写 N 种解析代码。`stream.py` 定义了**所有事件类型**和**事件数据结构**，相当于制定了一套"普通话"——大家都用这套语言沟通。

### 2.2 核心组件

#### 枚举：`StreamEventType`（第 17-34 行）

**业务上做什么**：定义系统中所有可能的事件类型。每个事件类型对应前端 UI 的一种展示方式。

| 事件类型 | 含义 | 前端展示效果 |
|----------|------|-------------|
| `STAGE_START` | 一个阶段开始 | 展示阶段标题，开始一个折叠区域 |
| `STAGE_END` | 一个阶段结束 | 折叠区域闭合 |
| `THINKING` | AI 正在思考 | 展示"思考中"动画，或折叠的推理过程 |
| `OBSERVATION` | AI 的观察/分析 | 展示观察结果卡片 |
| `CONTENT` | AI 输出正文 | 打字机效果逐字显示 |
| `TOOL_CALL` | AI 要调用工具 | 展示"正在调用 XX 工具" |
| `TOOL_RESULT` | 工具返回结果 | 展示工具返回的内容 |
| `PROGRESS` | 进度更新 | 展示进度条或状态文字 |
| `SOURCES` | 引用来源 | 展示引用卡片 |
| `RESULT` | 结构化结果 | 展示结果摘要 |
| `ERROR` | 发生错误 | 展示错误提示 |
| `SESSION` | 会话级别事件 | 会话状态更新 |
| `SESSION_META` | 会话元数据 | 会话信息更新 |
| `DONE` | 完成 | 结束加载状态 |
| `WAIT_FOR_INPUT` | 等待用户输入 | 展示输入框 |

**比喻**：这些事件类型就像快递包裹上的标签——"易碎品"、"加急"、"普通包裹"。前端看到标签就知道该怎么处理。

#### 数据类：`StreamEvent`（第 37-72 行）

**业务上做什么**：封装一个完整的流式事件，包含所有必要的上下文信息。

**字段说明**：

| 字段 | 类型 | 含义 | 比喻 |
|------|------|------|------|
| `type` | `StreamEventType` | 事件类型 | 信封上的标签 |
| `source` | `str` | 哪个模块产生的 | 发件人 |
| `stage` | `str` | 当前阶段 | 当前步骤 |
| `content` | `str` | 人类可读的文本 | 信件正文 |
| `metadata` | `dict` | 结构化附加数据 | 附件 |
| `session_id` | `str` | 会话 ID | 房间号 |
| `turn_id` | `str` | 当前轮次 ID | 对话序号 |
| `seq` | `int` | 事件序号 | 流水号 |
| `timestamp` | `float` | 时间戳 | 发件时间 |

**关键方法**：`to_dict()`（第 61-72 行）将事件序列化为字典，方便转成 JSON 发给前端。

**设计亮点**：`metadata` 字段是一个"万能口袋"——可以放任何结构化数据。比如工具调用时可以放参数，引用来源时可以放链接列表。这让事件结构保持统一的同时又足够灵活。

## 三、stream_bus.py —— 事件总线

**源码路径**：`deeptutor/core/stream_bus.py`

### 3.1 它解决什么问题？

事件定义好了，但需要一个"运输系统"把事件从生产者（AI 引擎）送到消费者（前端 WebSocket）。`StreamBus` 就是这个运输系统——它是一个**发布-订阅**模式的事件总线。

### 3.2 核心组件

#### 类：`StreamBus`（第 31-305 行）

**业务上做什么**：一个异步事件总线，支持多个订阅者同时接收事件。

**核心机制**：

1. **发布-订阅**：生产者调用 `emit()` 发送事件，所有订阅者通过 `subscribe()` 接收事件。

2. **历史回放**（第 41-68 行）：新订阅者加入时，可以收到之前已经发出的事件（`_history` 列表）。这很重要——如果前端页面刷新后重新连接 WebSocket，它能收到完整的历史，不会丢失信息。

3. **关闭信号**（第 70-74 行）：调用 `close()` 后，所有订阅者收到 `None` 信号，知道流结束了。

**关键方法详解**：

##### `emit()`（第 40-46 行）
**业务上做什么**：发送一个事件给所有订阅者。

**关键逻辑**：先存到历史记录，再逐个推送给每个订阅者的队列。如果总线已关闭，不再推送。

##### `subscribe()`（第 48-68 行）
**业务上做什么**：订阅事件流，返回一个异步迭代器。

**关键逻辑**：
1. 创建订阅者专属队列
2. 先回放历史事件（防止丢失）
3. 如果总线已关闭且队列为空，直接返回
4. 否则持续等待新事件，直到收到 `None`（关闭信号）

##### `stage()`（第 78-104 行）
**业务上做什么**：一个上下文管理器，自动在代码块前后发送 `STAGE_START` 和 `STAGE_END` 事件。

**使用示例**：
```python
async with stream.stage("planning", source="deep_solve"):
    # 这里面做的事情都会在"planning"阶段下展示
    plan = await self._plan(context)
```

**比喻**：就像给一段工作内容加上"开始"和"结束"的标记——前端看到 `STAGE_START` 就展开一个折叠面板，看到 `STAGE_END` 就折叠起来。

##### 便捷方法（第 106-260 行）

`StreamBus` 提供了一系列便捷方法，每种方法对应一种事件类型：

| 方法 | 对应事件类型 | 用途 |
|------|-------------|------|
| `content(text)` | `CONTENT` | AI 输出正文 |
| `thinking(text)` | `THINKING` | AI 推理过程 |
| `observation(text)` | `OBSERVATION` | AI 观察分析 |
| `tool_call(tool_name, args)` | `TOOL_CALL` | 发起工具调用 |
| `tool_result(tool_name, result)` | `TOOL_RESULT` | 工具返回结果 |
| `progress(message)` | `PROGRESS` | 进度更新 |
| `sources(sources)` | `SOURCES` | 引用来源 |
| `result(data)` | `RESULT` | 结构化结果 |
| `error(message)` | `ERROR` | 发生错误 |

##### `wait_for_input()`（第 262-292 行）

**业务上做什么**：暂停 AI 执行，等待用户在前端输入。

**什么场景用**：当 AI 需要向用户提问时（比如"请确认是否继续"），调用这个方法。它会：
1. 发送 `WAIT_FOR_INPUT` 事件给前端
2. 前端展示输入框
3. 等待用户输入
4. 返回用户输入的内容

**超时机制**：可以设置 `timeout` 参数。如果超时还没收到输入，返回空字符串。这在命令行环境下很重要——命令行可能没法输入，总不能让程序永远卡住。

##### `submit_input()`（第 294-298 行）

**业务上做什么**：从前端/WebSocket 接收用户输入，交给等待中的 `wait_for_input()`。

**比喻**：`wait_for_input` 是"我等你回复"，`submit_input` 是"你的回复到了"。

#### 总线注册表（第 310-325 行）

**业务上做什么**：维护一个全局的 `turn_id → StreamBus` 映射表。

**为什么需要**：WebSocket 收到的用户输入消息只知道 `turn_id`，不知道对应的 `StreamBus` 实例。通过注册表，可以快速找到正确的总线。

**三个函数**：
- `register_bus(turn_id, bus)`：注册
- `unregister_bus(turn_id)`：注销
- `get_bus(turn_id)`：查找

## 四、context.py —— 统一上下文

**源码路径**：`deeptutor/core/context.py`

### 4.1 它解决什么问题？

DeepTutor 的每个功能模块（聊天、解题、研究等）都需要访问大量信息：用户说了什么、历史对话、启用了哪些工具、附件文件、知识库配置等。如果每个模块都自己从各处拼凑这些信息，代码会非常混乱。

`UnifiedContext` 把所有信息集中到一个对象里，像一个"信息背包"——每个模块都从这个背包里取自己需要的东西。

### 4.2 核心组件

#### 数据类：`Attachment`（第 15-30 行）

**业务上做什么**：描述一个用户上传的附件（图片/文件/PDF）。

**字段说明**：
- `type`：附件类型（`"image"`、`"file"`、`"pdf"`）
- `url`：附件 URL
- `base64`：base64 编码（用于直接传给 LLM）
- `filename`：原始文件名
- `mime_type`：MIME 类型
- `id`：稳定标识符，也用作存储目录名
- `extracted_text`：从二进制文档中提取的纯文本（PDF/DOCX/XLSX/PPTX）

#### 数据类：`UnifiedContext`（第 33-84 行）

**业务上做什么**：封装一次用户请求所需的所有上下文信息。

**字段详解**：

| 字段 | 类型 | 含义 |
|------|------|------|
| `session_id` | `str` | 持久会话 ID |
| `user_message` | `str` | 当前用户输入 |
| `conversation_history` | `list` | 历史对话（OpenAI 格式） |
| `enabled_tools` | `list` | 用户启用的工具名列表 |
| `allowed_builtin_tools` | `list` | 内置工具的白名单 |
| `active_capability` | `str` | 当前选中的能力（如 `"deep_solve"`） |
| `knowledge_bases` | `list` | 知识库名称列表 |
| `attachments` | `list[Attachment]` | 附件列表 |
| `config_overrides` | `dict` | 请求级配置覆盖（如临时调温度） |
| `language` | `str` | UI/回复语言（`"en"` 或 `"zh"`） |
| `memory_context` | `str` | 记忆快照文本 |
| `persona_context` | `str` | 当前人格的指令 |
| `skills_manifest` | `str` | 可用技能清单文本 |
| `source_manifest` | `str` | 附加来源清单 |
| `metadata` | `dict` | 能力特定的额外数据 |

**设计亮点**：

1. **`enabled_tools` vs `allowed_builtin_tools`**：`enabled_tools` 是用户在前端开关的，`allowed_builtin_tools` 是管理员/合作伙伴配置的。两层控制，灵活且安全。

2. **`skills_manifest`**：DeepTutor 的"技能"功能。不直接把所有技能定义发给 LLM（太浪费 token），而是发一个清单，LLM 需要时再通过 `read_skill` 工具获取完整内容。

3. **`persona_context`**：人格功能。用户选择了一个人格后，人格的指令被注入到上下文中，影响 AI 的说话风格和知识范围。

## 五、trace.py —— 追踪元数据

**源码路径**：`deeptutor/core/trace.py`

### 5.1 它解决什么问题？

前端有一个"调用追踪面板"（CallTracePanel），展示 AI 执行的每一步——调用了哪个工具、推理过程、结果等。为了让这个面板能正确展示层级结构和时序关系，每个事件需要携带追踪元数据。

### 5.2 核心组件

#### 函数：`new_call_id()`（第 9-11 行）

**业务上做什么**：生成一个简短的唯一 ID，用于标识一个追踪卡片。

**输出**：如 `"call-a1b2c3d4e5"`（前缀 + 10 位随机 hex）

#### 函数：`build_trace_metadata()`（第 14-41 行）

**业务上做什么**：构建追踪元数据的基础结构。

**关键字段**：
- `call_id`：唯一标识
- `phase`：阶段（如 `"planning"`、`"reasoning"`）
- `label`：显示标签（如 `"Tool call"`、`"Retrieve"`）
- `call_kind`：调用类型（如 `"tool_planning"`、`"llm_final_response"`）
- `trace_id`：追踪 ID（用于关联同一追踪链上的事件）
- `trace_role`：追踪角色（如 `"tool"`）
- `trace_group`：追踪分组（如 `"tool_call"`）

#### 函数：`derive_trace_metadata()`（第 44-70 行）

**业务上做什么**：基于已有的元数据，覆盖部分字段生成新的元数据。

**使用场景**：一个工具调用开始时创建了基础元数据，工具执行过程中产生进度事件时，用 `derive_trace_metadata` 基于基础元数据派生，保持 `call_id` 等关键字段不变。

#### 函数：`merge_trace_metadata()`（第 73-83 行）

**业务上做什么**：合并两个元数据字典。

**大白话解释**：把基础元数据和额外字段合并，后面的覆盖前面的。这是最常用的元数据操作。

## 六、errors.py —— 异常体系

**源码路径**：`deeptutor/core/errors.py`

### 6.1 它解决什么问题？

统一的异常类型让错误处理变得清晰。不同层级的错误用不同的异常类，调用方可以精确捕获和处理。

### 6.2 异常层次结构

```
DeepTutorError                    ← 所有异常的基类
├── ConfigurationError            ← 配置相关错误
│   └── EnvironmentConfigError    ← 环境配置错误
├── ValidationError               ← 输入验证错误
└── ServiceError                  ← 服务层错误
    └── LLMServiceError           ← LLM 服务错误
        └── LLMContextError       ← 上下文窗口超限
```

### 6.3 基类：`DeepTutorError`（第 10-21 行）

**业务上做什么**：所有 DeepTutor 异常的基类。

**关键特性**：支持 `details` 字典，可以在抛出异常时附带结构化信息。例如：
```python
raise ConfigurationError("模型配置无效", details={"model": "gpt-5", "reason": "不支持"})
```

**`__str__` 方法**：如果有 details，自动拼接到错误消息中。这让日志更加信息丰富。

## 七、i18n.py —— 国际化

**源码路径**：`deeptutor/core/i18n.py`

### 7.1 它解决什么问题？

DeepTutor 支持中英文界面。后端的一些错误提示、状态消息需要根据用户语言设置显示不同语言。

### 7.2 核心组件

#### 消息字典：`_MESSAGES`（第 15-62 行）

**业务上做什么**：存储所有后端消息的中英文翻译。

**结构**：`{"en": {key: text}, "zh": {key: text}}`。每个 key 对应一条消息，有两个语言版本。

#### 函数：`current_language()`（第 65-71 行）

**业务上做什么**：获取当前用户的语言设置。

**优先级**：从 `interface_settings` 读取 → 默认英文

#### 函数：`t()`（第 74-82 行）

**业务上做什么**：翻译一条消息。类似前端框架中的 `t()` 函数。

**输入**：
- `key`：消息键
- `default`：找不到翻译时的默认值
- `language`：指定语言（可选，默认自动检测）
- `**kwargs`：格式化参数

**示例**：
```python
t("api.tool_not_found", name="web_search")
# 中文 → "未找到工具 'web_search'"
# 英文 → "Tool 'web_search' not found"
```

## 八、capability_protocol.py —— 能力协议

**源码路径**：`deeptutor/core/capability_protocol.py`

### 8.1 它解决什么问题？

DeepTutor 的"能力"（Capability）是第二层架构——当用户选择"深度解题"或"深度研究"时，对应的能力模块被激活。每种能力都是多步骤的 AI 流水线。这个文件定义了所有能力必须遵守的接口规范。

### 8.2 核心组件

#### 数据类：`CapabilityManifest`（第 20-30 行）

**业务上做什么**：声明一个能力的静态元数据。

**字段说明**：
- `name`：能力名称（如 `"deep_solve"`）
- `description`：描述
- `stages`：执行阶段列表（如 `["planning", "reasoning", "writing"]`）
- `tools_used`：使用的工具列表
- `cli_aliases`：命令行别名
- `request_schema`：请求参数 schema
- `config_defaults`：默认配置

#### 抽象类：`BaseCapability`（第 33-66 行）

**业务上做什么**：所有能力的抽象基类。

**核心方法**：`run(context, stream)` —— 每个能力必须实现这个方法，接收统一上下文和事件总线，执行完整的能力流水线。

**比喻**：`BaseCapability` 就像"岗位说明书"——规定了每个能力模块必须做什么，但具体怎么做由各模块自己决定。

---

## 九、tool_protocol.py —— 工具协议

**源码路径**：`deeptutor/core/tool_protocol.py`

### 9.1 它解决什么问题？

DeepTutor 有大量工具（搜索、读文件、代码执行等），每个工具都需要：定义自己的参数 schema（让 LLM 知道怎么调用）、执行逻辑、返回结果。这个文件定义了所有工具必须遵守的接口规范。

### 9.2 核心组件

#### 数据类：`ToolParameter`（第 16-44 行）

**业务上做什么**：描述工具的一个参数。

**字段说明**：
- `name`：参数名
- `type`：参数类型（`"string"`、`"integer"`、`"boolean"`、`"number"`、`"array"`、`"object"`）
- `description`：参数描述
- `required`：是否必填
- `default`：默认值
- `enum`：可选值列表
- `items`：数组元素类型（仅 `type="array"` 时使用）

**关键方法**：`to_schema()`（第 37-44 行）—— 将参数定义转换为 JSON Schema 格式，用于发给 LLM。

**设计细节**：当 `type="array"` 且 `items` 为空时，自动填充 `{"type": "string"}`（第 43 行）。这是因为 Gemini 和 Anthropic 等严格提供商要求 array 必须有 items 定义，否则返回 400 错误。

#### 数据类：`ToolDefinition`（第 47-94 行）

**业务上做什么**：描述一个工具的完整元数据，包括名称、描述和参数列表。

**关键方法**：`to_openai_schema()`（第 63-94 行）—— 生成 OpenAI 函数调用格式的工具定义。

**两种模式**：
1. **结构化参数**（`parameters`）：用 `ToolParameter` 列表描述参数，自动生成 schema。
2. **原始参数**（`raw_parameters`）：直接传入完整的 JSON Schema 对象。用于 MCP 等外部工具，它们的 schema 可能很复杂，不适合拆成 `ToolParameter`。

#### 数据类：`ToolResult`（第 121-155 行）

**业务上做什么**：封装工具执行的标准结果。

**字段说明**：

| 字段 | 含义 | 关键场景 |
|------|------|----------|
| `content` | 返回给 LLM 的文本 | 主要输出 |
| `sources` | 引用来源列表 | 前端展示引用卡片 |
| `metadata` | 结构化附加数据 | UI 提示（如 `ask_user.options`） |
| `success` | 是否成功 | `False` 时 LLM 仍可读取 content |
| `terminate_turn` | 是否结束当前轮次 | 已废弃，改用 `pause_for_user` |
| `pause_for_user` | 是否暂停等待用户输入 | `ask_user` 工具使用 |

**`pause_for_user` 机制详解**：
- 当工具（如 `ask_user`）需要向用户提问时，设置 `pause_for_user` 为提问数据
- Agentic 循环检测到后，暂停迭代，等待用户回复
- 用户回复后，回复文本被替换到工具消息中，循环继续
- 这样一问一答在同一个轮次内完成，不需要新建轮次

#### 数据类：`ToolPromptHints`（第 108-118 行）

**业务上做什么**：提供工具在 prompt 中的使用指导。

**字段说明**：`short_description`（简短描述）、`when_to_use`（何时使用）、`input_format`（输入格式）、`guideline`（使用指南）、`note`（注意事项）、`phase`（适用阶段）、`aliases`（别名列表）。

#### 抽象类：`BaseTool`（第 170-216 行）

**业务上做什么**：所有工具的抽象基类。

**核心方法**：
- `get_definition()`：返回工具定义（必须实现）
- `execute(**kwargs)`：执行工具逻辑（必须实现）
- `get_prompt_hints()`：返回 prompt 指导（可选重写）

**`deferred` 属性**（第 196 行）：标记为延迟加载的工具。设为 `True` 时，工具的完整 schema 不会在每轮对话中发送给 LLM，而是在 system prompt 中只放一行简介。LLM 需要时通过 `load_tools` 工具动态加载完整 schema。这节省了大量 token——想象一下如果有 50 个 MCP 工具，每个都发送完整 schema 会浪费多少 token。

#### 回调协议：`ToolEventSink`（第 159-167 行）

**业务上做什么**：工具执行过程中用来推送实时进度的回调接口。

**使用场景**：一个长时间运行的工具（如搜索大量文档）可以周期性调用 `event_sink` 来报告进度，前端就能实时展示"正在搜索第 3/10 个文档..."。

## 十、总结：一个事件的生命周期

以"AI 搜索网页"为例，看看事件是如何流转的：

```
1. AI 引擎决定调用 search_web 工具
   → tool_dispatch.py 调用 stream.tool_call("search_web", {"query": "..."})
   → StreamBus 创建 StreamEvent(type=TOOL_CALL, ...)
   → StreamBus.emit() 推送给所有订阅者
   → WebSocket 订阅者收到事件，发给前端
   → 前端展示"正在搜索：..."

2. 工具执行中
   → search_web 工具多次调用 event_sink("正在获取第 X 页...")
   → StreamBus 创建 StreamEvent(type=PROGRESS, ...)
   → 前端更新进度文字

3. 工具执行完成
   → tool_dispatch.py 调用 stream.tool_result("search_web", "搜索到 3 条结果...")
   → StreamBus 创建 StreamEvent(type=TOOL_RESULT, ...)
   → 前端展示搜索结果

4. AI 输出最终答案
   → labeled_step.py 调用 stream.content("根据搜索结果...")
   → StreamBus 创建 StreamEvent(type=CONTENT, ...)
   → 前端打字机效果逐字显示

5. 回答完成
   → StreamBus.close()
   → 所有订阅者收到 None 信号
   → 前端停止加载动画
```
