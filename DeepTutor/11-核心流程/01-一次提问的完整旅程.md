# 01 — 一次提问的完整旅程：从输入到回答的端到端追踪

> **源码位置**：`deeptutor/agents/chat/`  
> **涉及文件**：`capability.py` (26行), `agentic_pipeline.py` (1386行), `agent_loop.py` (667行), `chat_agent.py` (434行), `prompt_blocks.py` (167行), `session_manager.py` (179行)  
> **核心依赖**：LLM 客户端、工具注册表、统一上下文（UnifiedContext）、流总线（StreamBus）

---

## 概述

你在 DeepTutor 的聊天框里输入"请帮我证明三角形内角和为 180 度"，然后看到 AI 一边搜索知识库，一边调出 GeoGebra 画图，最后给出一个结构清晰的证明——这个过程在几秒钟内完成，但背后经历了一个精心设计的"多阶段流水线"。

本章将追踪一个提问从"进入系统"到"返回答案"的完整旅程，标注每一步涉及的模块和关键源码位置。

> 💡 **阅读建议**：建议先看下面的全景流程图，建立整体印象，再逐阶段深入。如果只关心某个特定环节（如工具调用、流式输出），可以直接跳到对应阶段。

## 阶段 0：请求接入 — ChatCapability

```
源码位置：capability.py:1-27
```

一切始于 `ChatCapability`。它是 DeepTutor 的"能力注册表"中的一个条目——当系统收到一个聊天请求时，它根据请求的 `capability` 字段路由到对应的能力处理器。

```python
class ChatCapability(BaseCapability):
    manifest = CapabilityManifest(
        name="chat",
        description="Agentic chat: an exploring agent loop with tools...",
        stages=["exploring", "responding"],
        tools_used=CHAT_OPTIONAL_TOOLS,
    )

    async def run(self, context: UnifiedContext, stream: StreamBus) -> None:
        pipeline = AgenticChatPipeline(language=context.language)
        await pipeline.run(context, stream)
```

三行代码，但承载了两个关键对象：
- **`UnifiedContext`**：统一上下文——包含用户消息、对话历史、知识库绑定、附件、元数据等所有信息
- **`StreamBus`**：流总线——负责向客户端实时推送文本、进度、来源等事件

> 📌 **比喻**：`ChatCapability` 就像餐厅的前台——它接收订单，然后交给厨房（`AgenticChatPipeline`）去烹饪。

## 阶段 1：流水线初始化 — AgenticChatPipeline.run()

```
源码位置：agentic_pipeline.py:301-321
```

这是整个流水线的"启动引擎"。在 20 行代码内，完成了 6 个关键初始化步骤：

### 1.1 准备延迟加载工具（Deferred Tools）

```
源码位置：agentic_pipeline.py:444-498
```

MCP（Model Context Protocol）工具需要按需加载，因为：
- 每个 MCP 服务器可能暴露数十个工具
- 一次性加载所有工具有性能和上下文窗口的开销
- 用户可能有权限限制（只有部分 MCP 工具可用）

`_prepare_deferred_tools` 做了：
1. 确保 MCP 管理器已启动
2. 解析调用方白名单（`mcp_tools_filter`）
3. 处理 PageIndex 知识库的自动授权（有 KB 就用对应的 MCP 工具）
4. 创建 `DeferredToolLoader` 实例

### 1.2 判断 exec 权限

```
源码位置：agentic_pipeline.py:527-558
```

不是所有用户都能执行代码。`_exec_allowed` 根据沙箱隔离级别判断：
- `SYSTEM` 级别：管理员可控制，默认所有人可用
- `APPLICATION` 级别：仅管理员可用
- 伙伴（Partner）回合：始终允许（伙伴是管理员的扩展）

### 1.3 组装可用工具列表

```
源码位置：agentic_pipeline.py:560-595
```

`_compose_enabled_tools` 是工具列表的"装配线"。它根据当前上下文动态决定哪些工具可用：

| 条件 | 装载的工具 |
|------|-----------|
| 有知识库绑定 | `rag` |
| 用户有记忆功能 | `read_memory`, `write_memory` |
| 用户有笔记本 | `list_notebook`, `write_note` |
| 有技能清单 | 技能相关工具 |
| 有延迟加载工具 | 延迟工具相关的 `load_tools` |
| exec 可用 | `exec`, `code_execution` |
| 伙伴回合 | 强制装载 `partner_*` 工具，抑制 `read_memory`/`write_memory` |

### 1.4 判断是否使用原生 Tool Calling

```
源码位置：agentic_pipeline.py:305-306
```

不是所有 LLM 提供商都支持 OpenAI 风格的 Function Calling。`can_use_native_tool_calling` 根据 binding 和 model 判断——如果不支持，工具列表会退化为纯文本提示词中的描述。

### 1.5 构建 LLM 工具 Schema

```
源码位置：agentic_pipeline.py:669-708
```

为每个工具生成 OpenAI 兼容的 JSON Schema。还做了特殊处理：
- `rag` 工具：注入知识库名称枚举（`enum`）
- `geogebra_analysis` 工具：移除 `image_base64` 参数（图片由系统自动注入）
- `list_notebook`/`write_note`：注入笔记本 ID 枚举

### 1.6 创建 AgentLoop

```python
loop = AgentLoop(
    pipeline=self,
    context=context,
    stream=stream,
    client=self._build_openai_client(),
    enabled_tools=enabled_tools,
    tool_schemas=tool_schemas,
)
await loop.run()
```

## 阶段 2：Agent 循环执行 — AgentLoop.run()

```
源码位置：agent_loop.py:169-199
```

`AgentLoop` 是 DeepTutor 最核心的执行引擎。它的设计哲学是"**一个循环解决一切**"——没有独立的"探索阶段"和"回答阶段"，而是在同一个对话中交替进行工具调用和文本生成。

### 2.1 能力前置 Briefings

```
源码位置：agent_loop.py:174-176
```

在进入回答循环之前，先执行活动能力的 `pre_loop` 钩子。比如 `explore_context` 能力会在这个阶段对附件中的来源做初步分析，把分析结果作为种子注入到后续的对话中。

### 2.2 知识库种子检索

```
源码位置：agentic_pipeline.py:1041-1111
```

如果有挂载的知识库，`_retrieve_kb_seed_block` 会预先检索相关内容，作为"种子"注入到用户消息中。这样 LLM 在第一次调用时就已经有了相关知识，不需要额外调用 `rag` 工具。

关键参数：
- 最多检索 3 个知识库（`KB_SEED_MAX_KBS = 3`）
- 每个知识库最多 4000 字符（`KB_SEED_CHARS_PER_KB = 4000`）

### 2.3 构建对话消息

```
源码位置：agentic_pipeline.py:345-386
```

`_build_loop_messages` 构建了一个完整的 messages 数组，包含：
1. 系统提示词（由 `ChatPromptAssembler` 组装）
2. 对话历史摘要（如果上下文过长，会被压缩）
3. 历史消息（user/assistant 交替）
4. 当前用户消息（末尾附上 KB 种子）

> 📌 **关键设计**：`_build_loop_messages` 只在循环开始时调用一次，之后每轮 LLM 调用都在这个 messages 数组上追加。系统提示词在整个循环中**保持不变**（byte-stable），这保证了 LLM 的 KV Cache 可以复用，提高性能。

## 阶段 3：提示词组装 — ChatPromptAssembler

```
源码位置：prompt_blocks.py:1-167
```

系统提示词不是一段简单文本，而是由多个"块"（block）组成的结构化文档。每个块有独立的名称和内容，最后由 `system_prompt` 方法用 `---` 分隔符拼接。

### 提示词块组装顺序

```
源码位置：prompt_blocks.py:46-93
```

```
1. general          → "你是 DeepTutor，一名互动式学习教练..."
2. runtime_policy   → 运行时行为规则（语言、Markdown、来源引用）
3. loop             → 循环工作流说明（何时调用工具、何时停止）
4. capability_blocks → 活动能力（如 deep solve）的专属指令
5. persona_style    → 个性化风格（Soul）
6. partner_turn_policy → 伙伴回合行为规则
7. memory           → 长期记忆上下文
8. tools            → 可用工具列表（含 KB 提示）
9. skills           → 可用技能清单
10. sources         → 附件来源清单
11. extended_tools  → 延迟加载工具说明
12. notebooks       → 笔记本列表
13. workspace       → 工作区路径
```

> 📌 **比喻**：提示词块就像一份"员工手册"的不同章节——身份介绍、工作流程、可用工具、特别注意事项……每个章节各司其职，共同构成 AI 的"工作指南"。

### 伙伴回合的特殊处理

```
源码位置：prompt_blocks.py:95-128
```

当用户通过伙伴（Partner）功能与 AI 交互时，`general` 块会被替换为 `general_partner`——AI 的身份从"DeepTutor 学习教练"变为"用户创建的专属伙伴"，并由 Soul 定义其人格。

## 阶段 4：LLM 调用循环 — _run_loop()

```
源码位置：agent_loop.py:226-349
```

这是整个旅程中最核心的阶段。`_run_loop` 是一个 while 循环，每一次迭代称为一个"轮次"（round）。循环的终止条件有三个：

1. **正常结束**：LLM 返回了一轮不带工具调用的回复（"finish"）
2. **预算耗尽**：轮次达到上限（默认 8 轮），强制结束
3. **异常终止**：工具返回了 terminator 标记

### 4.1 每轮的执行流程

```
源码位置：agent_loop.py:242-346
```

```
┌──────────────────────────────────────┐
│  _call_llm(messages, tool_schemas)   │
│  → 流式调用 LLM，实时推送文本到前端     │
│  → 返回：text + tool_calls 列表       │
└──────────────┬───────────────────────┘
               │
               ├── 无 tool_calls ──→ 这是最终答案！→ _finalize_finish()
               │
               ├── 有 tool_calls ──→ 继续处理
               │
               ▼
┌──────────────────────────────────────┐
│  _dispatch_tool_calls(tool_calls)    │
│  → 并行执行工具调用                    │
│  → 将结果追加到 messages 数组          │
└──────────────┬───────────────────────┘
               │
               ├── 有 pause 标记 ──→ 等待用户回复
               │
               ├── 有 terminate 标记 ──→ 提前结束
               │
               └── 继续下一轮
```

### 4.2 LLM 调用详情：`_call_llm()`

```
源码位置：agent_loop.py:430-591
```

`_call_llm` 是 LLM 调用的完整封装，做了以下事情：

1. **上下文窗口守护**（第 440 行）：调用 `_guard_context_window`，确保 messages 不超出模型上下文窗口（90% 阈值），超出则裁剪旧的工具结果。

2. **构建请求参数**（第 462-472 行）：包括 model、messages、stream=True、tools（如果有）、tool_choice="auto"。

3. **流式处理**（第 496-556 行）：
   - 文本内容（`content`）→ 通过 `stream.content()` 实时推送到前端
   - 思考内容（`reasoning_content`）→ 通过 `stream.thinking()` 推送到侧边栏
   - 行内 `thinking` 标签 → 通过 `InlineThinkFilter` 分离
   - 工具调用增量（`tool_calls` delta）→ 累积到 `tool_acc` 字典

4. **使用量追踪**（第 559-564 行）：记录输入/输出 token 数。

5. **返回 LLMCallResult**（第 591 行）：包含完整文本、工具调用列表、结束原因。

### 4.3 空回答保护

```
源码位置：agent_loop.py:267-304
```

有一种特殊情况：LLM 的回复全在 `thinking` 标签内，没有任何用户可见内容，也没有工具调用。这表示模型在"思考"，但没有执行。此时系统会注入一条提示：

```
你上一轮只输出了内部推理——既没有调用工具，也没有写出面向用户的回答。
现在继续：要么调用工具执行你计划好的步骤，要么直接写出最终回答。
```

然后继续下一轮循环。

### 4.4 强制结束

```
源码位置：agent_loop.py:371-411
```

当循环轮次用尽（默认 8 轮）或 LLM 调用出错时，`_forced_finish` 会：
1. 发送一条进度通知（"探索轮次预算已用尽..."）
2. 注入一条"结束指令"消息
3. **不带工具**调用一次 LLM（`tool_schemas=None`）
4. 将这次调用的结果作为最终答案

> 📌 **为什么是 8 轮？** 这是一个经验值。大多数问题在 2-3 轮内就能完成（检索 → 确认 → 回答）。8 轮的上限给了复杂问题足够的探索空间，同时防止无限循环。如果需要调整，可以通过 `chat_cfg.max_rounds` 配置。

## 阶段 5：工具派发 — _dispatch_tool_calls()

```
源码位置：agentic_pipeline.py:790-831
```

当 LLM 决定调用工具时，`_dispatch_tool_calls` 负责执行。核心逻辑：

### 5.1 并行限制

```
源码位置：agentic_pipeline.py:800-805
```

单轮最多并行调用 `MAX_PARALLEL_TOOL_CALLS` 个工具（默认值由 `deeptutor.core.agentic.tool_dispatch` 定义）。如果 LLM 请求了更多，会截断并通知。

### 5.2 参数增强（`_augment_tool_kwargs`）

```
源码位置：agentic_pipeline.py:886-996
```

这是工具调用的"中间件"——在真正执行之前，根据工具类型注入系统级参数：

| 工具 | 注入的参数 | 说明 |
|------|-----------|------|
| `rag` | `mode="hybrid"` | 默认混合检索模式 |
| `load_tools` | `_tool_loader` | 传入延迟加载器实例 |
| `exec` | `_sandbox_user_id`, `_sandbox_workdir`, `_sandbox_mounts` | 沙箱隔离 |
| `code_execution` | 同上 | 独立的代码运行目录 |
| `imagegen`/`videogen` | `_workspace_dir` | 媒体文件输出目录 |
| `cron` | `_cron_owner` | 定时任务的所有者信息 |
| `geogebra_analysis` | `image_base64` | 从附件中提取图片 |
| `web_search` | `query`, `output_dir` | 默认搜索词和输出路径 |
| `write_note` | `conversation_history`, `current_user_message` | 上下文注入 |

### 5.3 ask_user 暂停机制

```
源码位置：agentic_pipeline.py:833-884
```

当 LLM 调用 `ask_user` 工具时（例如需要用户澄清问题），流程会暂停，等待用户回复。回复到来后，将用户答案注入到对应的工具结果中，循环继续。

如果用户没有回复（或等待超时），`ask_user` 的内容作为最终输出展示给用户。

### 5.4 上下文检查点

```
源码位置：agent_loop.py:351-369
```

某些工具（如 `rag`）会返回 `_context_checkpoint` 摘要。当对话消息过长时，系统会将摘要前的所有内容替换为一条 `[Context checkpoint]` 系统消息，保持上下文窗口在限制内。

## 阶段 6：响应交付

```
源码位置：agent_loop.py:201-219, 413-426
```

循环结束后，`AgentLoop.run()` 做三件事：

1. **发送引用来源**：如果循环中收集了来源（RAG 结果、Web 搜索结果），通过 `stream.sources()` 发送。

2. **发送最终结果**：通过 `emit_capability_result()` 发送包含 `response`、`completed`、`engine`、`rounds`、`tool_steps` 的结构化结果。

3. **空回答保护**：如果最终文本为空，发送一条友好的 fallback 消息。

## 错误处理全景

DeepTutor 的聊天流程在多个层面做了错误处理：

### 层面 1：LLM 调用失败

```
源码位置：agent_loop.py:252-264
```

- 第一轮就失败 → 直接抛出异常（没有可挽救的内容）
- 后续轮次失败 → 强制结束，基于已有材料作答

### 层面 2：Tool Schema 不支持

```
源码位置：agent_loop.py:606-623
```

如果 LLM 提供商不支持原生 Tool Calling，自动回退：移除 `tools` 和 `tool_choice` 参数，仅用文本提示词描述工具。

### 层面 3：图片输入不支持

```
源码位置：agent_loop.py:624-642
```

如果模型不支持图片输入（如某些纯文本模型），自动剥离图片部分，以纯文本重试。

### 层面 4：上下文窗口溢出

```
源码位置：agentic_pipeline.py:1178-1213
```

当 messages 总 token 数超过上下文窗口的 90% 时，自动裁剪旧的工具结果，替换为 `[较早的工具结果已裁剪...]` 标记。

### 层面 5：强制结束失败

```
源码位置：agent_loop.py:404-409
```

连强制结束的 LLM 调用都失败了？发送空字符串给 `_finalize_finish`，它会生成一个 fallback 消息。

## 设计哲学总结

### 1. "一个循环"设计

DeepTutor 没有分离的"思考"和"回答"阶段——所有事情都在同一个 `_run_loop` 中完成。LLM 自己决定"什么时候该查资料"、"什么时候该画图"、"什么时候该回答"。这比预设的流水线更灵活。

### 2. "流式优先"架构

从 LLM 调用到工具执行，整个流程都是流式的。用户不需要等完整回答——文本生成的同时就已经在推送了。`StreamBus` 是这个架构的核心，它统一了所有事件（文本、思考、进度、来源、工具结果）的推送通道。

### 3. "渐进增强"的工具系统

工具不是静态的——它们根据上下文动态组装。有知识库就装 `rag`，有 MCP 服务就装延迟工具，有 exec 权限就装 `exec`。这种"按需组装"让同一个聊天引擎可以服务于不同的场景。

### 4. "多层防御"的错误处理

从 LLM 调用失败到上下文溢出，每种异常都有对应的处理策略。系统不会因为一个工具调用失败就让整个回答崩溃——它尽力"优雅降级"。

### 5. "提示词即配置"的理念

系统提示词不是硬编码的——它们存储在 YAML 文件中，按语言分版本（`zh/` 和 `en/`），由 `ChatPromptAssembler` 按块组装。这让提示词的迭代和 A/B 测试变得简单。

---

## 小结

一次提问的旅程，从 `ChatCapability` 的入口，到 `AgentLoop` 的循环，再到 `StreamBus` 的推送——经历了 6 个阶段、涉及 7 个核心模块。这不是一个简单的"请求-响应"模型，而是一个**自主探索 + 工具调用 + 流式交付**的智能代理系统。
