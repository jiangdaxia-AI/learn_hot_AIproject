# 01 解题能力（Deep Solve）

> **源码位置**：`deeptutor/capabilities/solve/`
> **涉及文件**：`capability.py`、`loop.py`、`session.py`、`tools.py`、`prompts/zh/system.md`

---

## 1. 一句话概述

**解题能力**是 DeepTutor 的"做题模式"。当用户把一道题发给 AI 时，AI 不是随口回答，而是像一位严谨的家教老师那样：先定计划、再逐步执行、每步确认、必要时调整方向，最后给出完整解答。

---

## 2. 整体设计思路

### 2.1 核心哲学：把"做题"当作一个状态机来管

传统的 AI 解题往往是一次性回答——模型看到题目，直接输出答案。但 DeepTutor 的做法不同：

- **AI 发挥智力**（想怎么解、用什么工具）——这是模型负责的部分
- **引擎守住纪律**（必须按计划走、不能跳步、重规划有次数限制）——这是代码负责的部分

这就像考试时，学生负责解题思路，但监考老师负责确保你不作弊、不跳题。DeepTutor 在这两个角色之间划了一条清晰的线。

### 2.2 架构分层

解题能力由四个文件协作完成，各司其职：

| 文件 | 角色 | 比喻 |
|------|------|------|
| `capability.py` | 启动器 | 按下"解题模式"的开关 |
| `loop.py` | 挂载器 | 把解题工具装到对话循环上 |
| `session.py` | 记忆本 | 记录当前这道题的解题计划与进度 |
| `tools.py` | 工具箱 | 三个解题专属工具的定义 |

## 3. 逐文件剖析

### 3.1 `capability.py` — 解题模式的入口

**源码路径**：`deeptutor/capabilities/solve/capability.py`

#### 3.1.1 `_sanitize(raw: str) -> str`（第 38-40 行）

```
功能：把任意字符串"清洗"成安全的 ID 格式
```

**大白话解释**：系统内部需要用一个 ID 来标记"这是哪次解题"。这个 ID 可能来自用户消息、会话编号等，但原始字符串里可能有特殊字符（空格、中文、表情等），不能直接当键名用。`_sanitize` 做的事情很简单——把所有不是字母、数字、下划线、短横线的字符统一替换成下划线，然后去掉首尾的下划线。

**输入**：任意字符串（比如 `"用户消息_abc-123"`）

**输出**：安全的 ID 字符串（比如 `"用户消息_abc-123"` —— 已经安全了）

**使用场景**：每次解题启动时调用，确保生成的 session ID 不会引发存储问题。

#### 3.1.2 `resolve_solve_session_id(context: UnifiedContext) -> str`（第 43-56 行）

```
功能：确定本次解题会话的唯一标识
```

**大白话解释**：DeepTutor 支持同时解多道题（比如用户开了两个窗口各发一道），每道题需要独立的"解题记忆"。这个函数按优先级从上下文中找：先看有没有 `turn_id`（本轮对话 ID），没有就用 `session_id`（会话 ID），再没有就用 `message_id`（消息 ID），最后兜底用 `"default"`。

**关键逻辑**：
1. 优先取 `turn_id`——因为一道题可能跨多轮对话，但一次解题是一个 turn
2. 逐级降级取 `session_id` → `message_id` → `"default"`
3. 最后调用 `_sanitize` 清洗

**输入**：`UnifiedContext`（每个请求的上下文对象，包含各类元数据）

**输出**：一个安全的 session ID 字符串

**使用场景**：每次解题能力激活时调用，确保同一道题的多次工具调用操作同一个 session。

#### 3.1.3 `DeepSolveCapability` 类（第 59-88 行）

```
功能：解题能力的主入口，负责标记模式并启动解题流水线
```

这是整个解题能力的"总开关"。它继承自 `BaseCapability`，是 DeepTutor 能力注册体系中的一员。

**`manifest` 属性**（第 60-67 行）：
- `name`: `"deep_solve"` — 能力的唯一标识名
- `description`: 简要描述，供系统注册和 UI 展示
- `stages`: `["responding"]` — 这个能力在"回复阶段"生效
- `tools_used`: 列出了解题时会用到的所有工具——`solve_plan`、`solve_finish_step`、`solve_replan`（解题三件套）以及 `rag`（检索）、`code_execution`（代码执行）、`geogebra_analysis`（几何分析）、`reason`（推理）
- `cli_aliases`: `["solve"]` — 命令行中可以用 `solve` 简写

**`run` 方法**（第 69-88 行）——解题流程的起点：

1. **打标记**（第 70 行）：`context.metadata["solve_mode"] = True` —— 告诉后续所有组件"现在进入解题模式"
2. **确定 session ID**（第 71 行）：调用 `resolve_solve_session_id` 算出本次解题的标识
3. **读取配置**（第 77-81 行）：从配置系统中读取解题参数，包括：
   - `max_replans`：最多允许重规划几次（默认 2 次）
   - `max_rounds`：对话循环最多跑几轮
   - `temperature`：模型回答的"创造性"温度
   - `max_tokens`：模型回答的最大长度
4. **启动流水线**（第 82-88 行）：创建 `AgenticChatPipeline` 并运行。这个 pipeline 是 DeepTutor 的核心对话引擎，它会把解题工具挂载到对话循环中，让模型在"计划→执行→确认→下一步"的节奏中完成解题。

**输入**：`context`（上下文）、`stream`（流式输出总线）

**输出**：无返回值（副作用：通过 stream 输出解题过程）

**使用场景**：用户在前端点击"解题"或通过 API 发送解题请求时，系统路由到此类。

### 3.2 `loop.py` — 解题循环挂载器

**源码路径**：`deeptutor/capabilities/solve/loop.py`

#### 3.2.1 `SolveLoopCapability` 类（第 21-73 行）

```
功能：将解题专属工具和系统提示注入到对话循环中
```

如果说 `DeepSolveCapability` 是按下开关，那 `SolveLoopCapability` 就是"接线工"——它负责把解题需要的工具和指令接到对话循环上，确保模型在解题时：
- 能看到解题专属的系统提示（告诉它"你现在是解题模式"）
- 能调用解题三件套工具
- 解题工具的调用能自动注入 session ID（模型不需要知道，服务端代劳）

**关键属性**：
- `name = "solve"`：能力名称
- `owned_tools = SOLVE_TOOL_NAMES`：声明自己"拥有"的三个工具（`solve_plan`、`solve_finish_step`、`solve_replan`）

**`is_active` 方法**（第 33-34 行）：
检查 `context.metadata` 中是否有 `"solve_mode": True` 标记。只有标记存在时，解题能力才生效。这保证了：普通聊天不会不小心触发解题工具。

**`system_block` 方法**（第 36-47 行）——注入系统提示：

当解题模式激活时，这个方法返回一段"解题系统提示"（`PromptBlock`），会被拼接到模型能看到的系统指令中。提示内容来自 `prompts/zh/system.md`（中文）或 `prompts/en/system.md`（英文）。

提示的核心内容（中文版）：
- 先调用 `solve_plan` 做计划，再开始解题
- 按计划逐步推进，用合适的工具完成每一步
- 完成一步后调用 `solve_finish_step` 标记
- 卡住了用 `solve_replan` 重规划（有次数限制）
- 最后写出完整答案

**`augment_kwargs` 方法**（第 49-69 行）——自动注入 session ID：

这是解题能力最精妙的设计之一。当模型调用解题工具时，它只需要传 `analysis`、`steps`、`step_id` 等业务参数，**不需要知道 session ID**。`augment_kwargs` 会在工具调用前自动把 `_solve_session_id` 注入到参数中。

同时，它还会把 `max_replans` 配置同步到 `SolveSession` 对象中，确保重规划预算始终是最新的。

**大白话比喻**：就像你去餐厅点菜，你只需要告诉服务员"我要宫保鸡丁"，服务员会自动在你的订单上标注"3号桌"——你不需要关心自己是哪桌，但厨房必须知道。

**`pre_loop_seed` 方法**（第 71-73 行）：
解题模式不需要额外的预设文本，返回空字符串。

**`_load_system_prompt` 函数**（第 85-88 行）：
根据语言（中文/英文）加载对应的系统提示文件。中文用 `zh`，其他语言默认用 `en`。

### 3.3 `session.py` — 解题会话（解题的"记忆本"）

**源码路径**：`deeptutor/capabilities/solve/session.py`

这是解题能力的"数据层"——它不涉及任何 AI 调用，纯粹是数据结构 + 内存管理。

#### 3.3.1 `SolveStep` 类（第 25-35 行）

```
功能：解题计划中的一个步骤
```

**大白话解释**：解题计划由多个步骤组成，每个步骤有：
- `id`：步骤编号，如 `"S1"`、`"S2"`（服务端生成，模型不控制）
- `goal`：步骤目标，如"计算函数的导数"
- `done`：是否已完成（布尔值）
- `summary`：完成后的总结文本

**关键设计**：`id` 是服务端生成的（`S1`、`S2`……），模型只提供 `goal`。这样模型永远不能"伪造"一个步骤编号，保证了数据一致性。

**`to_dict` 方法**（第 34-35 行）：把步骤序列化为字典，方便输出到 JSON 或前端展示。

#### 3.3.2 `SolveSession` 类（第 38-76 行）

```
功能：一道题的完整解题会话，包含计划、进度和重规划预算
```

这是解题能力的核心数据结构。一个 `SolveSession` 代表"解一道题的全过程"。

**关键属性**：
- `session_id`：会话标识
- `analysis`：解题分析（模型对题目的理解和解题思路概述）
- `steps`：步骤列表（`list[SolveStep]`）
- `replans`：已使用的重规划次数
- `max_replans`：最多允许重规划几次（默认 2）

**关键方法**：

| 方法 | 功能 | 大白话 |
|------|------|--------|
| `set_plan(analysis, steps)` | 设定解题计划 | "这是你的作战计划，按这个来" |
| `replan(analysis, steps)` | 重规划（替换旧计划） | "原计划行不通，换一套新方案" |
| `mark_done(step_id, summary)` | 标记某步完成 | "第3步做完了，记录一下结果" |
| `next_step()` | 获取下一个未完成的步骤 | "接下来该做哪步了？" |
| `map()` | 所有步骤的快照 | "给我看看整体进度" |
| `all_done()` | 是否所有步骤都完成了 | "题做完了吗？" |

**`set_plan` 方法**（第 48-50 行）：
接收模型提供的分析文本和步骤列表，创建 `SolveStep` 对象。注意步骤数上限是 `_MAX_STEPS = 12`，超过的部分会被截断——防止模型生成过于冗长的计划。

**`replan` 方法**（第 52-59 行）：
重规划的逻辑：
1. 先检查 `replans` 是否已达上限（`max_replans`），到了就返回 `False`，拒绝重规划
2. 没到上限：`replans += 1`，然后调用 `set_plan` 替换计划
3. 返回 `True` 表示重规划成功

这是解题能力的"纪律约束"——不能无限重来，最多 2 次（可配置）。

**`mark_done` 方法**（第 61-67 行）：
在步骤列表中按 `step_id` 找到对应步骤，将其 `done` 设为 `True`，记录 `summary`。找不到对应步骤时返回 `None`。

**`next_step` 方法**（第 69-70 行）：
遍历步骤列表，返回第一个 `done=False` 的步骤。如果所有步骤都完成了，返回 `None`。

**`all_done` 方法**（第 75-76 行）：
当步骤列表非空且所有步骤都 `done=True` 时返回 `True`。

#### 3.3.3 全局 Session 存储（第 79-92 行）

```
功能：在内存中管理所有解题会话，有上限防泄漏
```

**`_SESSIONS`**（第 79 行）：一个 `OrderedDict`（有序字典），key 是 session ID，value 是 `SolveSession` 对象。使用 `OrderedDict` 是为了方便实现"最久未使用先淘汰"（LRU）策略。

**`_MAX_SESSIONS = 256`**（第 80 行）：最多存储 256 个会话——超过后，最老的会话会被自动清除。

**`get_session(session_id)` 函数**（第 83-92 行）：
获取或创建会话。逻辑：
1. 如果 session ID 已存在，直接返回
2. 如果不存在，创建新的 `SolveSession`
3. 如果总数超过 256，用 `popitem(last=False)` 移除最老的（先进先出）

**为什么用内存而不是数据库？** 解题是一次性的——一道题解完就不需要了。用内存存储简单高效，256 的上限防止了长期运行的内存泄漏。

### 3.4 `tools.py` — 解题工具三件套

**源码路径**：`deeptutor/capabilities/solve/tools.py`

这是解题能力的"工具层"——定义了三个解题专属工具，模型通过调用它们来与解题引擎交互。

#### 3.4.1 工具概览

| 工具名 | 一句话 | 调用时机 |
|--------|--------|----------|
| `solve_plan` | 制定解题计划 | 解题开始时，**必须第一个调用** |
| `solve_finish_step` | 标记当前步骤完成 | 每完成一步后调用 |
| `solve_replan` | 重规划（换方案） | 当前方案走不通时调用 |

#### 3.4.2 辅助函数

**`_resolve_session_id(kwargs)`（第 33-34 行）**：
从工具参数中提取 `_solve_session_id`。这个参数是服务端通过 `augment_kwargs` 自动注入的，模型看不到也传不了。

**`_json_result(payload, meta_key, extra_meta)`（第 37-47 行）**：
构造工具返回结果。把 Python 字典序列化为 JSON 字符串，同时附加元数据。

**`_no_session_result()`（第 50-54 行）**：
没有活跃解题会话时的错误返回。

**`_parse_steps(raw_steps)`（第 57-74 行）**：
验证并解析模型提交的步骤列表。关键设计：
- 步骤 ID 是服务端生成的（`S1`、`S2`……），不是模型提供的
- 没有 `goal` 的步骤会被丢弃
- 只接受字典格式的步骤（`{"goal": "..."}`）

**大白话**：模型说"我要做三件事：求导、找极值、验证"，引擎把它变成 `[("S1", "求导"), ("S2", "找极值"), ("S3", "验证")]`——编号由引擎来定，模型只负责描述内容。

#### 3.4.3 `SolvePlanTool` 类（第 77-136 行）

```
功能：让模型提交解题计划
```

**工具定义**（`get_definition`，第 80-107 行）：
- 参数 `analysis`：一两句话描述题目和解题思路
- 参数 `steps`：有序步骤列表，每个步骤包含 `goal`

**执行逻辑**（`execute`，第 109-136 行）：
1. 解析 session ID
2. 验证步骤列表不为空
3. 调用 `session.set_plan(analysis, steps)` 存储计划
4. 获取第一个未完成步骤（`next_step()`）
5. 返回 JSON：包含状态、分析、步骤列表、下一步、以及指令"现在开始做第一步"

**业务场景**：用户发来一道题，AI 分析后说"这道题需要三步：① 建立方程 ② 求解 ③ 验证"。`solve_plan` 就是把这个计划"登记在案"的工具。

#### 3.4.4 `SolveFinishStepTool` 类（第 139-203 行）

```
功能：标记当前步骤完成，推进到下一步
```

**工具定义**（`get_definition`，第 142-165 行）：
- 参数 `step_id`：步骤编号（如 `"S1"`）
- 参数 `summary`：这一步的结果总结

**执行逻辑**（`execute`，第 166-203 行）：
1. 解析 session ID
2. 检查是否有计划（没有计划就报错）
3. 调用 `session.mark_done(step_id, summary)` 标记完成
4. 获取下一个未完成步骤
5. 关键：生成 `_context_checkpoint`——这是一个"上下文压缩点"，告诉对话循环"这一步的中间过程可以折叠了，只保留总结"

**`_context_checkpoint` 的设计**（第 198-203 行）：
这是解题能力的一个巧妙优化。解题过程中，模型可能调用大量工具（rag、code_execution 等），产生大量中间输出。如果不做处理，上下文窗口很快会被撑爆。`_context_checkpoint` 就是告诉对话循环："把这一步的中间对话压缩成一句话总结，释放空间给下一步"。

**大白话比喻**：你做数学题时，草稿纸上写满了中间计算。做完一步后，你在正式答卷上只写关键结果，草稿纸可以扔了。`_context_checkpoint` 就是那个"扔草稿纸"的动作。

**业务场景**：AI 完成了第 1 步"求导数"，调用 `solve_finish_step(step_id="S1", summary="导数为 2x+3")`，引擎记录完成，返回"下一步是 S2：找极值点"。

#### 3.4.5 `SolveReplanTool` 类（第 206-275 行）

```
功能：放弃当前计划，换一套新方案
```

**工具定义**（`get_definition`，第 209-235 行）：
- 参数 `reason`：为什么原方案不行，新方案改了什么
- 参数 `steps`：新的有序步骤列表

**执行逻辑**（`execute`，第 237-275 行）：
1. 解析 session ID
2. 验证新步骤列表不为空
3. 调用 `session.replan(reason, steps)`
4. **如果预算耗尽**（`replan` 返回 `False`）：返回错误，告诉模型"重规划次数已用完，用现有结果收尾"
5. **如果重规划成功**：返回新计划、已用次数/上限、下一步

**预算机制**：默认最多重规划 2 次。这是为了防止模型无限"重来"——如果连续两次方案都走不通，说明可能题目本身有问题，或者模型能力不足，这时候应该"认输"，给出当前最好的答案。

**业务场景**：AI 发现原计划的第 2 步推导有误，调用 `solve_replan(reason="原方法假设了连续性，但函数不连续", steps=[...])` 换一套新方案重新来。

### 3.5 `prompts/zh/system.md` — 解题系统提示

**源码路径**：`deeptutor/capabilities/solve/prompts/zh/system.md`

这是注入到模型系统指令中的中文提示词。内容在前文 `system_block` 中已详述，这里不再重复。核心要点：

1. **先计划再行动**：`solve_plan` 必须第一个调用
2. **严格执行顺序**：按计划逐步推进，不跳步
3. **工具使用指南**：`code_execution` 做计算，`rag` 做检索，`geogebra_analysis` 做几何图形
4. **重规划有节制**：只在真正卡住时用，预算用尽就收尾
5. **最终输出**：先给精确结果，再给清晰讲解

## 4. 完整解题流程（时序图）

```
用户发送题目
    ↓
DeepSolveCapability.run()
    ├── context.metadata["solve_mode"] = True      ← 标记解题模式
    ├── resolve_solve_session_id()                  ← 确定 session ID
    ├── 读取配置（max_replans 等）
    └── AgenticChatPipeline.run()                   ← 启动对话循环
            ↓
        SolveLoopCapability.system_block()          ← 注入解题系统提示
            ↓
        模型第一轮：调用 solve_plan(analysis, steps)
            ↓
        SolvePlanTool.execute()
            ├── session.set_plan(...)               ← 存储计划
            └── 返回：下一步是 S1
            ↓
        模型第二轮：用工具做 S1 的工作
            ├── code_execution(...)                 ← 计算
            ├── rag(...)                            ← 检索
            └── solve_finish_step("S1", summary)    ← 标记完成
                    ↓
                SolveFinishStepTool.execute()
                    ├── session.mark_done("S1", ...)← 标记完成
                    ├── _context_checkpoint         ← 压缩上下文
                    └── 返回：下一步是 S2
            ↓
        模型第三轮：做 S2 ...（循环直到 all_done）
            ↓
        模型最后一轮：输出最终答案
```

---

## 5. 设计亮点总结

### 5.1 智能与纪律的分离

这是整个解题能力最核心的设计思想。模型负责"怎么解"（智能），引擎负责"必须按流程走"（纪律）。这种分离带来了几个好处：

- **可控性**：产品经理可以调整 `max_replans`、`max_rounds` 等参数来控制解题行为
- **可观测性**：每个步骤的状态（计划中/执行中/已完成）都有明确记录
- **可调试性**：出问题时可以精确定位是"模型想错了"还是"引擎约束太严"

### 5.2 Session ID 的透明注入

模型不需要知道 session ID——它只传业务参数。`augment_kwargs` 在服务端自动注入。这保证了：
- 模型不能伪造或篡改 session ID
- 并发解题互不干扰
- 代码更简洁，模型提示词更短

### 5.3 上下文压缩（_context_checkpoint）

解题过程中产生的大量中间输出会被自动折叠，只保留关键总结。这解决了长对话场景下的上下文窗口溢出问题。

### 5.4 重规划预算

不是无限重来——给模型一个"试错额度"，用完就认。这既给了模型灵活性，又防止了死循环。

### 5.5 内存存储 + LRU 淘汰

解题是一次性的，用内存存储简单高效。256 的上限 + 最老淘汰策略，既保证了性能，又防止了内存泄漏。

## 6. 给产品/运营的总结

**解题能力本质上是一个"带解题纪律的 AI 对话循环"**。它不是让 AI 直接回答，而是：

1. 先让 AI 做计划（`solve_plan`）
2. 按计划一步步执行（每步用合适的工具）
3. 每步完成后打卡确认（`solve_finish_step`）
4. 卡住了可以换方案，但有次数限制（`solve_replan`）
5. 最后给出完整解答

这种设计保证了 AI 解题的**严谨性**和**可追溯性**——用户可以看到解题的每一步推理过程，而不是一个黑盒答案。
