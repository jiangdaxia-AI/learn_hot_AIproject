# 02 掌握度评估（Mastery Path）

> **源码位置**：`deeptutor/capabilities/mastery/`
> **涉及文件**：`capability.py`、`loop.py`、`choices.py`、`tools.py`、`prompts/zh/system.md`

---

## 1. 一句话概述

**掌握度评估**是 DeepTutor 的"自适应教学引擎"。它不像传统 AI 家教那样"讲完就完了"，而是为每个知识点设了一道硬性门槛——学生必须通过测验或解释来证明自己"真的会了"，否则绝对不能跳过，AI 必须反复打磨直到掌握。

---

## 2. 整体设计思路

### 2.1 核心哲学：把"会不会"的判断权交给引擎，而非 AI

一个常见的产品陷阱是：AI 家教问学生"你懂了吗？"，学生说"懂了"，AI 就翻篇了。但学生可能只是"以为自己懂了"。

DeepTutor 的做法是：
- **AI 负责教学**（教什么、怎么教、怎么提问）——这是模型的智力工作
- **引擎负责判定**（这道题答对了吗？掌握度达标了吗？可以进入下一个知识点了吗？）——这是代码的确定性工作

**类比**：老师负责讲课和出题，但"60 分及格"这个规则是学校定的，不是老师凭感觉定的。DeepTutor 的引擎就是那个"硬性及格线"。

### 2.2 知识点类型

DeepTutor 将知识点分为四种类型，每种类型有不同的"过关方式"：

| 类型 | 英文 | 含义 | 过关方式 | 举例 |
|------|------|------|----------|------|
| 记忆型 | memory | 需要记住的事实 | 选择题/简答题 → 引擎自动批改 | 牛顿第一定律的内容 |
| 程序型 | procedure | 需要掌握的步骤技能 | 选择题/简答题 → 引擎自动批改 | 解一元二次方程的步骤 |
| 概念型 | concept | 需要理解的思想 | 费曼式讲解 → AI 判断理解程度 | 导数的几何意义 |
| 设计型 | design | 开放性的判断力 | 费曼式讲解 → AI 判断理解程度 | 选用哪种算法更合适 |

**关键区别**：记忆型和程序型有"标准答案"，引擎可以自动批改（`mastery_quiz` + `mastery_grade`）。概念型和设计型没有标准答案，需要 AI 判断学生是否真正理解了（`mastery_assess`）。

### 2.3 架构分层

| 文件 | 角色 | 比喻 |
|------|------|------|
| `capability.py` | 启动器 | 按下"教学评估模式"的开关 |
| `loop.py` | 挂载器 | 把评估工具装到对话循环上 |
| `choices.py` | 选择题数据层 | 处理选择题的"选项→标签"映射 |
| `tools.py` | 工具箱 | 五个评估专属工具的定义 |

## 3. 逐文件剖析

### 3.1 `capability.py` — 评估模式的入口

**源码路径**：`deeptutor/capabilities/mastery/capability.py`

#### 3.1.1 `_sanitize_path_id(raw: str) -> str`（第 29-32 行）

```
功能：清洗字符串为安全的路径 ID
```

与解题能力中的 `_sanitize` 功能相同——把用户输入的字符串（可能是书名、课程名等）转为安全的存储键名。只保留字母、数字、下划线、短横线。

#### 3.1.2 `resolve_mastery_path_id(context: UnifiedContext) -> str`（第 35-54 行）

```
功能：确定本次教学评估操作的是哪条学习路径
```

**大白话解释**：一个用户可能同时学多门课（比如同时学数学和物理），每门课有独立的知识点地图和掌握度数据。这个函数决定"当前操作的是哪条路径"。

**优先级逻辑**：
1. **显式指定**（最高优先级）：前端传了 `mastery_path_id`，直接用
2. **书籍引用**：如果上下文中有 `book_references`（用户附加了教材），用第一本书的 ID
3. **会话 ID**（兜底）：用当前会话 ID 作为路径 ID

**使用场景**：每次评估能力激活时调用。确保同一门课的数据始终操作同一个存储键。

#### 3.1.3 `MasteryPathCapability` 类（第 57-73 行）

```
功能：评估模式的主入口，标记模式并启动教学流水线
```

**`manifest` 属性**（第 58-67 行）：
- `name`: `"mastery_path"` — 能力标识
- `description`: 简要描述
- `tools_used`: `mastery_status`、`mastery_quiz`、`mastery_grade`、`mastery_assess`、`mastery_build`（评估五件套）+ `rag`（检索）+ `read_source`（读材料）+ `ask_user`（向学生提问）
- `cli_aliases`: `["mastery"]` — 命令行简写

**`run` 方法**（第 69-73 行）：
1. 打标记：`context.metadata["mastery_mode"] = True`
2. 确定路径 ID：`resolve_mastery_path_id(context)`
3. 启动对话流水线：和解题模式一样，复用 `AgenticChatPipeline`

**注意**：与解题模式不同，评估模式没有读取额外配置（如 max_replans）——因为评估的硬性门槛在引擎层（`learning` 模块）中定义，不在能力层配置。

### 3.2 `loop.py` — 评估循环挂载器

**源码路径**：`deeptutor/capabilities/mastery/loop.py`

#### 3.2.1 `MasteryLoopCapability` 类（第 13-55 行）

```
功能：将评估专属工具和系统提示注入到对话循环中
```

与解题的 `SolveLoopCapability` 结构几乎相同，但注入的内容不同。

**关键属性**：

**`is_active` 方法**（第 23-24 行）：
检查 `context.metadata` 中是否有 `"mastery_mode": True`。

**`system_block` 方法**（第 26-37 行）：
注入评估系统提示。提示的核心内容（中文版）：
- 每一轮先调用 `mastery_status` 查看当前状态
- 根据知识点类型选择合适的评估方式
- 未触碰的知识点先探查
- memory/procedure 用 `mastery_quiz` + `mastery_grade`
- concept/design 用 `mastery_assess`
- 有到期复习项要再考一次

**`augment_kwargs` 方法**（第 39-51 行）：

- `_turn_id`：当前轮次 ID

模型不需要知道这些，但引擎需要它们来定位正确的数据。

### 3.3 `choices.py` — 选择题数据层

**源码路径**：`deeptutor/capabilities/mastery/choices.py`

这是一个纯函数模块，负责处理选择题的"选项"在不同场景下的格式转换。它不涉及任何 AI 调用，不依赖任何外部服务，是一个教科书级的"数据转换层"。

#### 3.3.1 为什么需要这个模块？

选择题的选项数据在系统中以不同形态出现：

| 场景 | 形态 | 例子 |
|------|------|------|
| 模型通过 `mastery_quiz` 注册 | `["A: 牛顿第一定律", "B: 牛顿第二定律", ...]` | 完整选项文本 |
| 学生通过 `ask_user` 作答 | `"B"` | 一个标签 |
| 引擎批改时比较 | 需要比较 `"B"` 和 `"B"`（标签对标签） | 标签对标签 |
| 题库持久化 | 需要保留完整选项文本 | 完整文本 |

这个模块就是这些形态之间的"翻译官"。

#### 3.3.2 `OPTION_PREFIX_RE` 正则（第 33 行）

```
匹配带标签的选项字符串，如 "C: 这是答案" / "C) 这是答案" / "C、这是答案"
```

支持多种分隔符：冒号（中英文）、句号、顿号、括号、短横线。

#### 3.3.3 `parse_options(options: list[str]) -> dict[str, str]`（第 36-55 行）

```
功能：把选项字符串列表解析为 {标签: 正文} 字典
```

**大白话解释**：把模型传过来的 `["A: 牛顿第一定律", "B: 牛顿第二定律"]` 变成 `{"A": "牛顿第一定律", "B": "牛顿第二定律"}`。

**解析逻辑**：
1. 如果字符串匹配 `OPTION_PREFIX_RE`（如 `"C: 内容"`），提取标签和正文
2. 如果字符串是单个字母/数字（如 `"C"`），视为纯标签
3. 否则，按位置分配标签（A, B, C, … 到 Z，超过 26 个用数字）

#### 3.3.4 `has_option_bodies(options: dict[str, str]) -> bool`（第 58-62 行）

```
功能：判断选项字典是否包含真正的正文（而非仅标签）
```

**大白话解释**：有些旧数据可能只存了 `{"A": "A", "B": "B", "C": "C"}`（标签即正文），这不够。这个函数判断选项是否有"真正的描述文字"。

**判断标准**：至少 2 个选项，且每个选项的正文不等于其标签（忽略大小写）。

#### 3.3.5 `format_options(options: dict[str, str]) -> list[str]`（第 65-67 行）

```
功能：把 {标签: 正文} 字典还原为 "标签: 正文" 格式的字符串列表
```

与 `parse_options` 互为逆操作。

#### 3.3.6 `resolve_answer(expected_answer: str, options: dict[str, str]) -> str`（第 70-95 行）

```
功能：把模型提供的"正确答案"解析为稳定的选项标签
```

**大白话解释**：模型有时候会传 `"C"`（标签），有时候会传 `"C: 牛顿第三定律"`（带标签的完整文本），有时候甚至传 `"牛顿第三定律"`（纯正文）。这个函数统一把它们解析为 `"C"`（标签）。

**解析策略**（按优先级）：
1. 直接匹配标签：`"C"` → 在 options 的 key 中找 `"C"`
2. 正则匹配前缀：`"C: 牛顿第三定律"` → 提取标签 `"C"`
3. 精确匹配正文：`"牛顿第三定律"` → 在 options 的 value 中精确查找
4. 模糊匹配正文：`"牛顿第三定律"` → 在 options 的 value 中模糊查找（子串匹配）
5. 如果匹配到多个或一个都没有，返回空字符串

**为什么需要这么复杂？** 因为不同模型的行为不一致——有的返回标签，有的返回正文，有的返回"标签: 正文"。这个函数屏蔽了这些差异。

#### 3.3.7 `recover_options_from_turn(store, turn_id, question)`（第 103-142 行）

```
功能：从历史轮次中恢复选择题的完整选项正文（兼容旧数据）
```

**大白话解释**：旧版本的 `mastery_quiz` 在存储时只保留了 `["A", "B", "C", "D"]`（标签），把完整正文丢了。但完整正文其实在 `ask_user` 工具调用的事件中还能找到。这个函数就是去"翻旧账"，把完整正文找回来。

**查找逻辑**：
1. 从 `store`（会话存储）中获取该轮次的所有事件
2. 逆序遍历事件（从最新到最旧），找 `ask_user` 工具调用
3. 在 `ask_user` 的问题列表中，找到问题文本匹配的那道题
4. 提取其选项的完整标签和正文

**使用场景**：当批改旧版本注册的选择题时，需要完整正文来判断"学生选的是不是正确答案"。

### 3.4 `tools.py` — 评估工具五件套

**源码路径**：`deeptutor/capabilities/mastery/tools.py`

这是整个评估能力最核心的文件，包含五个工具。每个工具都像一个"API 端点"，模型通过调用它们来与掌握度引擎交互。

#### 3.4.1 工具概览

| 工具名 | 一句话 | 调用时机 |
|--------|--------|----------|
| `mastery_status` | 查看学习路径当前状态 | **每轮必调**，获取当前该做什么 |
| `mastery_quiz` | 注册一道测验题 | 要对 memory/procedure 知识点出题时 |
| `mastery_grade` | 批改学生的回答 | 学生作答后，引擎自动批改 |
| `mastery_assess` | 记录费曼式讲解的评估 | 对 concept/design 知识点做口头检查后 |
| `mastery_build` | 创建/扩展学习路径 | 首次建立知识地图或追加新模块时 |

#### 3.4.2 辅助函数

**`_new_service() -> LearningService`（第 72-76 行）**：
每次调用都新建一个 `LearningService` + `LearningStore` 实例。这样设计是因为：并发请求各自操作独立实例，不会互相干扰；用完即弃，没有状态残留。

**`_resolve_path_id(kwargs)`（第 79-80 行）**：
从工具参数中提取 `_mastery_path_id`（服务端注入的）。

**`_resolve_session_id(kwargs)`（第 83-84 行）**：
从工具参数中提取 `_session_id`。

**`_resolve_turn_id(kwargs)`（第 87-88 行）**：
从工具参数中提取 `_turn_id`。

**`_question_bank_type(question_type)`（第 91-97 行）**：
把工具层的题型名称映射到题库的题型名称：
- `"choice"` → `"choice"`（选择题）
- `"open"` → `"written"`（开放题）
- 其他 → `"short_answer"`（简答题）

**`_resolve_pending_choice(pending, turn_id)`（第 100-121 行）**：
解析待批改的选择题。对于旧版本数据（只存了标签），调用 `recover_options_from_turn` 恢复完整正文。

**`_sync_mastery_attempt_to_question_bank(...)`（第 124-158 行）**：
把学生的作答记录同步到题库（Question Bank）。这是一个"副作用"操作——即使同步失败也不影响批改结果，只是题库中少了这条记录。

**`_no_path_result()`（第 169-173 行）**：
没有活跃评估路径时的错误返回。

#### 3.4.3 `MasteryStatusTool` 类（第 176-214 行）

```
功能：查看学习路径的当前状态——"接下来该做什么？"
```

**大白话解释**：这就像老师上课前先看一眼教案——"上次讲到哪了？还有哪个学生没过关？有没有需要复习的旧知识点？"

**工具定义**（`get_definition`，第 179-189 行）：
- 无参数
- 描述：返回下一个要攻克的知识点、待批改的作答、到期复习项、整张地图的状态

**执行逻辑**（`execute`，第 192-214 行）：
1. 解析路径 ID
2. 创建学习服务，获取或创建该路径的学习进度
3. **如果路径为空**（还没有任何知识点）：返回 `{"status": "empty", ...}`，提示模型"需要先设计知识地图"
4. **如果路径有内容**：返回：
   - `next`：下一个要攻克的知识点（由引擎的 `next_objective` 函数决定）
   - `map`：整张地图的摘要（每个知识点的状态：new / learning / mastered）

**关键设计**：`next` 不是模型决定的，是引擎的 `next_objective` 函数按顺序 + 掌握度门槛计算出来的。模型必须信任引擎的判断——"引擎说下一个该学什么就学什么"。

**业务场景**：学生打开教学会话，AI 第一件事就是调用 `mastery_status`，看到"当前该学知识点 #3：导数定义"，于是开始教学。

#### 3.4.4 `MasteryQuizTool` 类（第 217-349 行）

```
功能：注册一道测验题，把题目和正确答案存入引擎
```

**大白话解释**：老师出题时，把题目和答案一起交给"教务处"存档。以后学生作答时，教务处用存档的答案自动批改——老师不需要再翻答案，也不会"不小心"把答案泄露给学生。

**工具定义**（`get_definition`，第 220-274 行）：
- `knowledge_point_id`：知识点 ID（从 `mastery_status` 获取）
- `question`：题目文本
- `expected_answer`：正确答案（仅服务端使用，不会显示给学生）
- `question_type`：题型（`"choice"` / `"short"` / `"open"`），默认 `"short"`
- `options`：选择题的选项列表（如 `["A: 牛顿第一定律", "B: 牛顿第二定律"]`）

**执行逻辑**（`execute`，第 276-349 行）：
1. 解析路径 ID，验证必填参数
2. **选择题特殊处理**（第 292-315 行）：
   - 解析选项，检查是否有完整正文（不是裸标签）
   - 解析正确答案为稳定标签
   - 如果选项不合法，返回错误提示
3. 查找知识点，验证其存在
4. 创建 `PendingQuestion` 对象（待批改问题）
5. 调用 `service.set_pending_question(progress, pending)` 存入引擎
6. 返回 JSON，包含指令："现在用 ask_user 把题目呈现给学生，然后调用 mastery_grade 批改"

**关键约束**（第 293-298 行）：
选择题必须传完整选项正文（如 `"A: 牛顿第一定律"`），不能只传裸标签（`"A"`）。如果传了裸标签，工具会返回错误。这个约束确保了：
- 引擎中有完整的选项数据
- 批改时可以正确匹配
- 题库中有完整的题目记录

**业务场景**：AI 教到"牛顿定律"这个知识点，出了一道选择题，调用 `mastery_quiz` 注册题目和答案，然后用 `ask_user` 工具把题目以可点选卡片的形式发给学生。

#### 3.4.5 `MasteryGradeTool` 类（第 352-427 行）

```
功能：批改学生的回答，更新掌握度，判断是否通过门槛
```

**大白话解释**：学生交卷了，教务处自动批改。如果答对了，掌握度上升；如果达标了，这个知识点标记为"已掌握"，可以进入下一个。

**工具定义**（`get_definition`，第 355-372 行）：
- `answer`：学生的回答（原文原样传入）

**执行逻辑**（`execute`，第 374-427 行）：
1. 解析路径 ID
2. 检查是否有待批改的题目（`pending_question`），没有则报错
3. 如果是选择题，先解析选项和正确答案
4. 调用 `service.grade_and_record(...)` —— **引擎的核心批改逻辑**：
   - 比较学生答案和正确答案
   - 更新该知识点的掌握度
   - 调用间隔重复调度器（`SpacedRepetitionScheduler`）安排复习
5. 同步到题库（`_sync_mastery_attempt_to_question_bank`）
6. 清除待批改状态（`service.clear_pending_question`）
7. 返回结果：
   - `is_correct`：是否正确
   - `mastery`：当前掌握度（浮点数，如 0.85）
   - `threshold`：通过门槛（浮点数，如 0.80）
   - `mastered`：是否已掌握（`mastery >= threshold`）
   - `next`：下一个要攻克的知识点

**关键设计**：`mastered` 的判断是引擎做的，不是模型做的。模型只负责读取 `mastered` 字段，然后决定"继续打磨"还是"进入下一个"。

**业务场景**：学生选了 "B"，AI 调用 `mastery_grade(answer="B")`，引擎返回 `{"is_correct": true, "mastered": true, ...}`。AI 说"答对了！这个知识点你已经掌握了，我们进入下一个。"

#### 3.4.6 `MasteryAssessTool` 类（第 430-498 行）

```
功能：记录费曼式讲解的评估结果（用于 concept/design 类知识点）
```

**大白话解释**：对于"理解型"的知识点，没有标准答案，不能自动批改。替代方案是"费曼式检查"：让学生用自己的话解释这个概念，AI 判断解释是否到位，然后用 `mastery_assess` 记录结果。

**工具定义**（`get_definition`，第 433-462 行）：
- `knowledge_point_id`：知识点 ID
- `passed`：是否通过（布尔值）
- `feedback`：评估备注（可选，记录为什么通过/不通过）

**执行逻辑**（`execute`，第 464-498 行）：
1. 解析路径 ID
2. 查找知识点，验证其存在
3. **类型检查**（第 482-489 行）：如果知识点类型是 memory/procedure，拒绝调用——这些类型应该用 `mastery_quiz` + `mastery_grade`
4. 调用 `service.record_qualitative(...)` 记录评估结果
5. 返回结果：`passed`、`mastered`、`mastery`、`next`

**业务场景**：AI 让学生解释"导数的几何意义"，学生说"导数就是函数在某一点的切线斜率"。AI 判断为正确，调用 `mastery_assess(knowledge_point_id="...", passed=true, feedback="解释准确，理解到位")`。

#### 3.4.7 `MasteryBuildTool` 类（第 501-589 行）

```
功能：创建或扩展学习路径（知识地图）
```

**大白话解释**：这是"搭建知识地图"的工具。在开始教学前，AI 需要先根据学生的教材/材料设计一条学习路径——包含哪些模块、每个模块有哪些知识点、每个知识点是什么类型。

**工具定义**（`get_definition`，第 504-555 行）：
- `modules`：模块列表，每个模块有 `name` 和 `knowledge_points`（知识点列表，每个知识点有 `name` 和 `type`）
- `mode`：`"replace"`（从头开始，默认）或 `"append"`（追加到已有路径）

**执行逻辑**（`execute`，第 557-589 行）：
1. 解析路径 ID 和模式
2. 调用 `_parse_modules` 验证并解析模块数据
3. 根据模式合并或替换模块
4. **关键**：重建路径后，清除待批改问题（`progress.pending_question = None`）——因为旧题目可能对应已不存在的知识点
5. 重置当前进度到第一个模块的第一个知识点
6. 保存并返回摘要

**`_parse_modules` 函数**（第 592-634 行）：
验证模型提交的模块数据。关键安全设计：
- 模块 ID 和知识点 ID 是服务端生成的（`<path>_m<i>_kp<j>`），不是模型提供的——防止模型伪造 ID
- 知识点名称长度限制 200 字符
- 未知类型回退为 `"concept"`
- 知识点名称至少 2 个字符

**业务场景**：学生上传了一本数学教材，AI 分析后设计了一条学习路径，调用 `mastery_build(modules=[...], mode="replace")` 建立知识地图。

## 4. 完整评估流程

```
学生进入教学会话
    ↓
MasteryPathCapability.run()
    ├── context.metadata["mastery_mode"] = True
    ├── resolve_mastery_path_id()
    └── AgenticChatPipeline.run()
            ↓
        模型第一轮：mastery_status()
            └── 返回：next = 知识点#1, 状态 = new
            ↓
        模型判断：知识点#1 是 memory 类型
            ├── 先 probe：问学生是否已经知道
            └── 学生不知道 → 开始教学
            ↓
        模型第二轮：mastery_quiz(kp_id, question, answer, type="choice", options=[...])
            └── 引擎登记题目和答案
            ↓
        模型：ask_user(...) → 把题目以可点选卡片发给学生
            ↓
        学生作答：选了 "B"
            ↓
        模型第三轮：mastery_grade(answer="B")
            └── 引擎批改：is_correct=true, mastery=0.85, threshold=0.80, mastered=true
            ↓
        模型："答对了！我们进入下一个知识点。"
            ↓
        模型第四轮：mastery_status()
            └── 返回：next = 知识点#2, 状态 = new
            ↓
        ...（循环直到所有知识点 mastered）
```

## 5. 设计亮点总结

### 5.1 硬性门槛 vs 软性判断

记忆型和程序型知识点有"标准答案"，引擎自动批改，threshold 一到就过关——这是冷冰冰的、不容商量的硬性门槛。

概念型和设计型知识点没有标准答案，AI 判断学生是否理解到位——这是需要 AI 发挥智力的软性判断。但 AI 的判断结果仍然通过 `mastery_assess` 记录在引擎中，而不是直接口头说"过了"。

### 5.2 选择题的格式转换链

`choices.py` 模块处理了选择题在"模型注册 → 学生作答 → 引擎批改 → 题库持久化"全链路中的格式差异。每个环节的格式需求不同，但通过这个模块统一转换，保证了一致性。

### 5.3 旧数据兼容

`recover_options_from_turn` 函数体现了对历史数据的兼容性。即使旧版本存储的选项不完整，新版本也能通过"翻旧账"恢复完整数据。

### 5.4 间隔重复

`SpacedRepetitionScheduler`（间隔重复调度器）在批改时被调用，自动安排复习计划。这意味着即使学生当时答对了，系统也会在适当的时间安排复习，防止遗忘。

### 5.5 服务端 ID 生成

模块 ID 和知识点 ID 都是服务端生成的（`<path>_m<i>_kp<j>`），模型不能控制。这保证了 ID 的唯一性和安全性。

## 6. 给产品/运营的总结

**掌握度评估本质上是一个"带硬性门槛的自适应教学引擎"**。它的核心价值在于：

1. **不是"讲完就算"**：每个知识点必须通过测验或讲解证明掌握，否则不能跳过
2. **因材施"考"**：记忆型用选择题/简答题自动批改，理解型用费曼式讲解人工判断
3. **门槛可配置**：掌握度 threshold 可以在引擎层调整，不需要改 AI 提示词
4. **有复习机制**：间隔重复确保学生不会"学完就忘"
5. **数据可追溯**：每次作答都同步到题库，可以查看学生的学习轨迹

这种设计让 AI 教学从"聊天式问答"升级为"有纪律的教学管理"——AI 负责"教得好"，引擎负责"管得严"。
