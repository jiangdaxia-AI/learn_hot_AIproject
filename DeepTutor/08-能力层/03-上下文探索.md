# 03 上下文探索（Explore Context）

> Understand-Anything 知识图谱: 26 节点, 25 边, 7 层
> **源码位置**：`deeptutor/capabilities/explore_context/`
> **涉及文件**：`capability.py`、`explorer.py`、`prompts/zh/explore_context.yaml`

---

## 1. 一句话概述

**上下文探索**是 DeepTutor 的"课前预习员"。当用户发送请求时附带了文档、聊天记录、教材章节等材料，这个能力会在 AI 正式回答之前，先偷偷把这些材料读一遍，写一份客观的"调查简报"，交给 AI 作为回答时的背景参考。

---

## 2. 整体设计思路

### 2.1 为什么需要这个能力？

这可能是 DeepTutor 最"隐形"但最巧妙的能力。它的存在解决了两个实际问题：

**问题一：角色混淆**

当用户把一段"我跟另一个 AI 的聊天记录"发给 DeepTutor 时，如果让 AI 直接读这段记录，AI 会看到记录里那个"AI"用第一人称说话（"我帮你做了 X"）。AI 可能会不自觉地"代入"那个角色，认为那些事是自己做的——这会导致严重的角色混淆：AI 会说"我帮你做了 X"，但实际上它根本没做过。

**类比**：你把你和张三的聊天记录给李四看，李四不应该把张三说的话当成自己说的。

**问题二：弱模型不会主动读材料**

有些 AI 模型在工具调用方面比较"懒"——它明明有 `read_source` 工具可以读附件，但就是不主动调用，直接凭附件标题或第一句话就瞎回答。把"读材料"这个动作从回答环节中剥离出来，放在一个独立的"预习"环节中强制执行，确保材料一定被读过。

### 2.2 核心设计：读材料和回答问题分离

上下文探索的设计哲学是：**把"理解材料"和"回答问题"分成两个独立的阶段**。

```
传统做法：
用户消息 + 附件 → AI 边读材料边回答 → 容易角色混淆，弱模型可能跳过阅读

DeepTutor 做法：
用户消息 + 附件 → 调查员先读材料，写简报 → AI 只看简报来回答 → 角色清晰，材料一定被读过
```

### 2.3 架构分层

| 文件 | 角色 | 比喻 |
|------|------|------|
| `capability.py` | 调度器 | 判断是否需要预习，启动调查员 |
| `explorer.py` | 调查员 | 实际执行调查，生成简报 |
| `prompts/zh/explore_context.yaml` | 调查指南 | 告诉调查员怎么工作 |

### 2.4 两条执行路径

上下文探索有两条路径，根据模型能力自动选择：

| 路径 | 适用场景 | 工作方式 |
|------|----------|----------|
| 智能循环（agentic loop） | 支持原生工具调用的模型 | 调查员用 `read_source` 工具按需读取材料，边读边分析 |
| 单次兜底（single pass） | 不支持工具调用的模型 | 把所有材料全文一次性塞进上下文，让模型直接写简报 |

**为什么叫"兜底"？** 因为智能循环更好——调查员可以"按需读取"（只看用户问题相关的材料，跳过无关的），节省上下文。但有些模型不支持工具调用，所以必须有兜底方案。

## 3. 逐文件剖析

### 3.1 `capability.py` — 探索能力的调度器

**源码路径**：`deeptutor/capabilities/explore_context/capability.py`

#### 3.1.1 提示词加载与缓存（第 45-65 行）

**`_PROMPT_CACHE`**（第 45 行）：一个模块级字典缓存，key 是语言代码（`"zh"` / `"en"`），value 是解析后的提示词字典。因为提示词文件是静态的，加载一次就够了，不需要每次都读文件。

**`_load_prompts(language)` 函数**（第 48-65 行）：
1. 根据语言选择中文或英文提示词文件
2. 先查缓存，有就直接返回
3. 缓存没有就读 YAML 文件，解析后存入缓存
4. 解析失败也不崩溃，返回空字典——"有提示词更好，没有也能工作"

#### 3.1.2 `_has_readable_sources(context)` 函数（第 68-79 行）

```
功能：判断当前回合是否有可读的文本附件
```

**大白话解释**：不是所有附件都需要"预习"。图片不需要（因为视觉模型可以直接看），纯文本附件才需要。这个函数检查上下文中是否有 `source_index`（一个 `{source_id: full_text}` 的字典）。如果这个字典非空，说明有文本附件需要预习。

**关键细节**：`source_index` 是"会话累积"的——用户在本回合新附的材料，加上之前回合已附的材料，都会出现在索引中。所以即使不是本回合刚附的，只要还存在，调查员就能看到。

#### 3.1.3 `ExploreContextCapability` 类（第 82-141 行）

```
功能：上下文探索能力的主入口——一个"几乎不可见"的循环能力
```

**关键属性**：
- `name = "explore_context"`：能力名称
- `owned_tools = ()`：**空元组**——这个能力在回答循环中不挂载任何工具！因为 `read_source` 工具只在预习阶段（调查员内部）使用，回答阶段的 AI 根本看不到这个工具。

**`is_active` 方法**（第 90-91 行）：
仅当 `_has_readable_sources(context)` 返回 `True` 时激活。没有附件就不需要预习。

**`system_block` 方法**（第 93-103 行）：
返回 `None`——这个能力不注入系统提示。调查结论是通过 `pre_loop` 以"用户消息种子"的形式注入的，而不是静态的系统提示。

**`augment_kwargs` 方法**（第 105-112 行）：
不做任何参数注入——因为回答循环中没有探索能力的工具。

**`pre_loop_seed` 方法**（第 114-116 行）：
返回空字符串——不需要额外的预设文本。

**`pre_loop` 方法**（第 118-141 行）——整个能力的核心：

这是 `LoopCapability` 协议中定义的**可选异步钩子**。对话流水线在回答循环的第一次 LLM 调用之前，会先调用这个钩子。

**执行逻辑**：
1. 检查是否有可读附件（`is_active`）
2. 懒加载 `ContextExplorer`（延迟导入避免循环依赖）
3. 创建调查员实例，传入语言和提示词
4. 调用 `explorer.investigate(...)` 执行调查
5. 如果调查结果非空，包装成 `PromptBlock("explore_context", investigation)` 返回
6. 对话流水线会将这个 `PromptBlock` 的内容折叠到回答循环的初始用户消息中

**为什么叫"近不可见"？** 因为从用户角度看，这个能力完全透明——用户看不到调查员在工作，只看到 AI 回答时"好像已经了解了附件内容"。但在前端 trace 面板中，可以看到"上下文调查"这个阶段。

### 3.2 `explorer.py` — 调查员（核心引擎）

**源码路径**：`deeptutor/capabilities/explore_context/explorer.py`

这是整个上下文探索能力最核心的文件，包含调查员的所有逻辑。

#### 3.2.1 常量与配置（第 48-78 行）

**`EXPLORE_STAGE = "context_exploration"`**（第 54 行）：
前端 trace 面板用来标识"上下文调查"阶段的标签。前端代码（`web/components/chat/home/TracePanels.tsx`）根据这个字段来显示"正在探索上下文…"的状态和"上下文调查"行标题。

**`EXPLORE_SOURCE = "chat"`**（第 55 行）：
调查阶段的 trace 来源标记为 `"chat"`，跟主对话共享同一个活动通道。

**智能循环预算**（第 60-61 行）：
- `MAX_LOOP_ROUNDS = 5`：最多 5 轮 LLM 调用（读材料 → 分析 → 再读 → 再分析，最多 5 轮）
- `LOOP_MAX_TOKENS = 2000`：每轮 LLM 输出最多 2000 token

**单次兜底预算**（第 65-68 行）：
- `MAX_SOURCES = 12`：最多读 12 个来源
- `CHARS_PER_SOURCE = 8000`：每个来源最多 8000 字符
- `TOTAL_CHARS = 48000`：所有来源总计最多 48000 字符
- `BRIEFING_MAX_TOKENS = 1400`：简报输出最多 1400 token

**来源类型映射**（第 71-77 行）：
根据来源 ID 的前缀判断来源类型，用于在简报中标注：
- `hs-`：对话记录（Conversation transcript）
- `nb-`：笔记本记录（Notebook record）
- `bk-`：书籍节选（Book excerpt）
- `qb-`：题库条目（Question-bank entry）
- `at-`：文档（Document）

#### 3.2.2 `_CallResult` 数据类（第 80-84 行）

```
功能：一次 LLM 调用的结果封装
```

包含三个字段：
- `text`：LLM 返回的文本（调查内容）
- `tool_calls`：LLM 请求的工具调用列表
- `output_chars`：输出字符数（用于用量统计）

#### 3.2.3 `ContextExplorer` 类（第 87-531 行）

```
功能：调查员的完整实现——读取附件，生成客观简报
```

**构造函数**（`__init__`，第 90-110 行）：
1. 确定语言（中文/英文）
2. 保存提示词
3. 从 LLM 配置中读取模型信息（model、api_key、base_url、binding 等）
4. 构建 `LLMClientConfig`（LLM 客户端配置）
5. 获取工具注册表（`get_tool_registry()`）——调查员需要调用 `read_source` 工具

---

##### 3.2.3.1 `investigate` 方法（第 112-147 行）——调查入口

```
功能：执行调查，返回调查简报文本
```

**大白话解释**：这是调查流程的"总指挥"。它决定用哪条路径（智能循环还是单次兜底），调用对应的调查方法，最后把结果包装成带标题的简报。

**执行流程**：
1. 获取 `source_index`（附件索引），没有附件直接返回空
2. 尝试智能循环路径（如果模型支持原生工具调用）
3. 如果智能循环失败或返回空，降级到单次兜底
4. 清理结果中的"思考标签"（`clean_thinking_tags`）
5. 如果结果非空，加上简报标题（`[上下文调查]`）返回

**关键设计**：智能循环失败时自动降级——保证回答循环永远不会"没有背景"。

---

##### 3.2.3.2 `_run_loop` 方法（第 151-241 行）——智能循环调查

```
功能：用工具调用做"按需阅读"的智能调查
```

**大白话解释**：这是上下文探索的"主路径"。调查员不是一次性读完所有材料，而是像侦探一样：先看用户问题，判断需要读哪些材料，用 `read_source` 工具读取，根据读到的内容决定是否继续读其他材料，直到信息足够，然后写调查简报。

**执行流程**：

1. **构建消息**（第 164-174 行）：
   - 系统提示：告诉调查员"你是谁，你的任务是什么"（来自 `loop.system` 提示词）
   - 用户消息：包含用户的原始问题、当前模式（chat/solve/mastery）、附件清单（来自 `loop.user_template` 提示词）

2. **准备工具**（第 175-176 行）：
   - `tool_schemas`：`read_source` 工具的 OpenAI 格式定义，其中 `source_id` 参数被限制为只能从 `source_index` 的 key 中选择（防止调查员请求不存在的来源）
   - `augmenter`：一个闭包，在 `read_source` 被调用时自动注入 `source_index`（调查员只需要传 `source_id`，全文由服务端根据索引提供）

3. **设置 trace**（第 179-190 行）：
   创建 trace 元数据，让前端可以显示"正在探索上下文…"的状态。

4. **进入循环**（第 203-238 行）：
   ```
   for round_idx in range(MAX_LOOP_ROUNDS):  # 最多 5 轮
       如果是最后一轮：
           强制收尾指令（停止调用工具，立即写简报）
       调用 LLM
       如果 LLM 没有请求工具调用 → 调查完成，退出循环
       如果 LLM 请求了工具调用 → 执行工具（read_source），结果追加到消息中
       继续下一轮
   ```

5. **用量统计**（第 240 行）：记录本次调查消耗的 token 数。

**为什么最后一轮要强制收尾？** 防止调查员陷入"无限阅读"的循环——每读一个材料就发现新的线索，然后又想读更多。5 轮后强制它停下来，基于已读的内容写简报。

---

##### 3.2.3.3 `_call_llm` 方法（第 243-331 行）——流式 LLM 调用

```
功能：调用 LLM，流式处理响应，提取工具调用
```

**大白话解释**：这是一个"流式 LLM 调用器"。它发送消息给 LLM，然后一边接收流式响应，一边做三件事：
1. 把推理内容（reasoning）通过 `stream.thinking` 发送到前端
2. 把文本内容拼起来
3. 把工具调用请求收集起来

**关键设计**：所有输出都走 `stream.thinking` 通道，**不走 `stream.content` 通道**。因为 `content` 是回答循环的通道——如果调查员往 `content` 发东西，前端会把它当成 AI 的回答显示给用户。`thinking` 通道的内容只在 trace 面板中可见，不会干扰主对话。

**参数**：
- `temperature=0.2`：低温度，让调查结果更客观、更一致
- `max_tokens=LOOP_MAX_TOKENS`（2000）：限制输出长度

**返回值**：`_CallResult` 对象，包含文本、工具调用列表、输出字符数。

---

##### 3.2.3.4 `_read_source_schemas` 方法（第 333-351 行）

```
功能：构建 read_source 工具的 OpenAI schema，限制可用的 source_id
```

**大白话解释**：`read_source` 工具有一个 `source_id` 参数。正常情况下，这个参数可以是任意字符串。但在调查员场景中，我们要限制调查员只能读取当前回合的附件——不能让它随意读取系统中的任意文件。

这个函数从工具注册表中获取 `read_source` 的 schema，然后把 `source_id` 的 `enum` 设为 `source_index` 中所有 key 的列表。这样 LLM 就知道它只能从这些 ID 中选择。

**类比**：图书馆管理员给你一张"今日可借书目清单"，你只能从清单上选书，不能随便要一本不存在的书。

---

##### 3.2.3.5 `_augmenter` 静态方法（第 353-361 行）

```
功能：在工具调用时自动注入 source_index
```

**大白话解释**：调查员调用 `read_source(source_id="nb-123")` 时，`_augmenter` 闭包会自动把 `source_index` 注入到参数中。这样 `read_source` 工具就能直接从索引中获取全文，而不需要去数据库查询。

**为什么用闭包而不是全局变量？** 因为 `source_index` 是每个回合独有的——不同回合的附件不同。闭包捕获了当前回合的 `source_index`，确保工具调用时访问的是正确的数据。

---

##### 3.2.3.6 `_single_pass` 方法（第 365-439 行）——单次兜底调查

```
功能：把所有附件全文一次性塞给 LLM，生成简报（兜底方案）
```

**大白话解释**：这是为不支持工具调用的模型准备的降级方案。逻辑很简单：把所有附件的前 8000 字符（最多 12 个来源，总共 48000 字符）拼在一起，加上系统提示和用户问题，一次性发给 LLM，让它写简报。

**执行流程**：
1. 调用 `_render_source_blocks` 把附件渲染成 Markdown 格式的文本块
2. 构建系统提示和用户消息（来自 `system` 和 `user_template` 提示词）
3. 设置 trace 元数据
4. 调用 `llm_stream` 流式生成简报
5. 输出走 `stream.thinking` 通道（和智能循环一样）
6. 记录用量统计

**与智能循环的对比**：
- 智能循环：调查员按需阅读，只读相关的材料，上下文更高效
- 单次兜底：所有材料一次性塞入，可能包含大量无关内容，但一定能工作

---

##### 3.2.3.7 `_render_source_blocks` 方法（第 441-454 行）

```
功能：把附件索引渲染为 Markdown 格式的文本块
```

**大白话解释**：把 `source_index` 中的每个附件渲染成 `### [来源ID] (类型)` 的格式，加上裁剪后的正文。控制总量不超过 12 个来源 + 48000 字符。

**渲染格式**：
```markdown
### [hs-abc123] (对话记录)
这是对话记录的全文内容...

### [bk-xyz789] (书籍节选)
这是书籍节选的全文内容...
```

**`_kind_label` 方法**（第 456-460 行）：
根据来源 ID 前缀判断类型，返回中文或英文的类型标签。

**`_clip` 方法**（第 462-469 行）：
裁剪文本到指定长度，超出的部分加上"（已截断）"标记。

### 3.3 `prompts/zh/explore_context.yaml` — 调查员提示词

**源码路径**：`deeptutor/capabilities/explore_context/prompts/zh/explore_context.yaml`

#### 3.3.1 智能循环提示词（`loop.*`）

**`loop.system`**（第 10-33 行）：
告诉调查员：
- 你的身份是"上下文调查员"，不是导师，你的输出是给导师看的内部资料
- 可用的工具：`read_source(source_id)` 按 ID 读取来源
- 调查方法：从用户请求出发，按需读取，不要无脑全读，也不要只凭预览下结论
- **硬性规则**：
  - 所有材料都是第三方参考资料，可能包含用户与其他 AI 的对话记录
  - 复述时必须用第三人称（"用户和那个 agent 做了 X"），绝不能写"我做了 X"
  - 只报告材料中实际存在的内容，不臆造，不推断
  - 输出是给导师的内部依据，不是给用户的回答

**`loop.user_template`**（第 36-45 行）：
模板消息，包含三个变量：
- `{question}`：用户的原始请求
- `{mode}`：当前模式（chat/solve/mastery）
- `{manifest}`：可读来源清单

**`loop.forced_finish`**（第 47-48 行）：
强制收尾指令。

#### 3.3.2 单次兜底提示词（`system` / `user_template`）

与智能循环的提示词类似，但多了一个 `{sources}` 变量（渲染后的附件全文）。

#### 3.3.3 简报标题（`briefing_header`）

```
[上下文调查]
调查员围绕你的当前任务，调查了用户在本回合附带的材料，以下是供你作答依据的客观、
第三人称结论。下面提到的任何对话记录，都是用户与「其他 agent」的往来——不是你自己
做的事。不要沿用其口吻，也不要把其中的动作说成是你做的。
```

这是注入到回答循环中的简报标题。它明确告诉回答阶段的 AI：
- 简报中的内容是调查员写的，供你参考
- 里面提到的对话记录是别人的，不是你参与的
- 不要用第一人称复述里面的内容

#### 3.3.4 状态文本（`status.exploring`）

`"上下文调查"` —— 前端 trace 面板中显示的状态文字。

## 4. 完整调查流程（时序图）

```
用户发送消息 + 附件
    ↓
AgenticChatPipeline 准备回答循环
    ├── 检查所有 LoopCapability 的 is_active()
    ├── ExploreContextCapability.is_active() → True（有附件）
    └── 调用 ExploreContextCapability.pre_loop()
            ↓
        ContextExplorer.investigate()
            ├── 获取 source_index（附件索引）
            ├── 判断：模型支持原生工具调用？
            │
            ├── [是] → _run_loop()（智能循环）
            │   ├── 构建消息（系统提示 + 用户问题 + 附件清单）
            │   ├── 准备 read_source 工具（source_id 限制为附件列表）
            │   ├── 循环（最多 5 轮）：
            │   │   ├── _call_llm() → LLM 返回文本或工具调用
            │   │   ├── 如果有工具调用 → dispatch_tool_calls()
            │   │   │   └── read_source("hs-123") → 获取全文
            │   │   │   └── 追加到消息中
            │   │   ├── 如果无工具调用 → 调查完成
            │   │   └── 最后一轮 → 强制收尾
            │   └── 返回调查文本
            │
            └── [否或失败] → _single_pass()（单次兜底）
                ├── _render_source_blocks() → 渲染附件全文
                ├── 构建消息（系统提示 + 用户问题 + 附件全文）
                ├── llm_stream() → 生成简报
                └── 返回调查文本
            ↓
        包装：briefing_header + investigation
            ↓
        返回 PromptBlock("explore_context", investigation)
            ↓
    AgenticChatPipeline 把 PromptBlock 折叠到用户消息种子中
            ↓
    回答循环开始：AI 看到的是"用户消息 + 调查简报"，而非原始附件
            ↓
    AI 回答用户问题（基于简报，而非原始附件）
```

## 5. 设计亮点总结

### 5.1 角色隔离——解决"第一人称混淆"

这是上下文探索能力解决的核心问题。当用户把"我和另一个 AI 的聊天记录"发给 DeepTutor 时：

- **没有探索能力**：AI 直接读聊天记录，看到 `## Assistant: 我帮你做了 X`，可能会说"好的，我帮你做了 X"——但实际上它根本没做
- **有探索能力**：调查员先读聊天记录，写简报："在这段记录里，用户和那个 agent 讨论了 X"，然后 AI 看到简报，回答时不会把自己代入那个角色

提示词中反复强调"用第三人称复述"、"不要写'我做了 X'"——这些约束确保了角色清晰。

### 5.2 按需阅读 vs 全量阅读

智能循环路径中，调查员不是无脑读完所有材料，而是根据用户问题判断需要读哪些。这有几个好处：
- 节省上下文（不读无关材料）
- 节省 token（不浪费在无关内容上）
- 结果更聚焦（只关注与问题相关的内容）

### 5.3 流式输出走 thinking 通道

调查员的所有输出都走 `stream.thinking` 通道，不走 `stream.content` 通道。这保证了：
- 用户看不到调查过程（不会被中间输出干扰）
- 开发者可以在 trace 面板中查看调查过程（调试用）
- 回答循环的 content 通道保持干净

### 5.4 自动降级机制

`investigate` 方法中，智能循环失败时自动降级到单次兜底。这意味着：
- 好模型用智能循环（体验更好，更省 token）
- 弱模型用单次兜底（功能保证，不会因为不支持工具调用而罢工）
- 用户无感知——无论哪条路径，最终回答循环都能拿到一份调查简报

### 5.5 来源 ID 白名单

`_read_source_schemas` 方法把 `source_id` 的 `enum` 限制为 `source_index` 的 key。这防止了 LLM 通过 `read_source` 工具访问系统中的任意文件，是一个安全设计。

### 5.6 循环预算控制

智能循环最多 5 轮，最后一轮强制收尾。这防止了调查员陷入"无限阅读"的死循环。

## 6. 给产品/运营的总结

**上下文探索本质上是一个"回答之前的秘密预习环节"**。它的核心价值在于：

1. **角色安全**：防止 AI 把其他 AI 说的话当成自己说的（解决"第一人称混淆"）
2. **强制阅读**：弱模型也不会跳过材料——因为预习是独立于回答的强制环节
3. **用户无感**：预习过程对用户完全透明，用户只看到 AI"好像已经了解了附件"
4. **可调试**：开发者可以在 trace 面板中查看调查过程
5. **降级兜底**：好模型用智能循环，弱模型用单次兜底，总有一条路能走通

这个能力虽然"隐形"，但它是 DeepTutor 处理附件场景的基石——没有它，AI 在处理聊天记录、文档、教材等附件时，很容易出现角色混淆或信息遗漏的问题。
