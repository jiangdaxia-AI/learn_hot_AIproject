# DeepTutor 架构总览 — 8 层架构详解

> 本章从技术架构角度，逐层拆解 DeepTutor 的 8 层架构设计，帮助产品经理和运营同学理解系统是怎么组织起来的。

---

## 1. 8 层架构全景图

把 DeepTutor 想象成一栋 8 层的大楼，每一层都有明确的职责，层与层之间通过标准接口通信：

### 第 1 层：Web 前端层
Chat（聊天界面）· Book（互动教材）· Co-Writer（协作写作）· Settings（设置面板）· Dashboard（管理后台）
技术栈：Next.js · React · TypeScript · TailwindCSS · SSE 流式接收

### 第 2 层：API 层（FastAPI）
ChatRouter · KnowledgeRouter · NotebookRouter · BookRouter · SessionRouter · AdminRouter
技术栈：FastAPI · Pydantic · SSE · CORS · 中间件 · 认证

### 第 3 层：Agent 层
AgenticChatPipeline（工具组装+能力编排）· AgentLoop（LLM循环调度）· QuestionCoordinator（题目生成）
ResearchAgent（深度研究）· BaseAgent（Agent基类）· MathAnimator/Visualize（动画/可视化）
核心设计：Pipeline 组装 + AgentLoop 执行 + 能力系统叠加

### 第 4 层：能力层（Capabilities）
Solve（解题）· Mastery（掌握度）· Obsidian（知识库独占）· Subagent（子代理）· Explore（上下文探索）
核心设计：LoopCapability 协议 + 工具叠加/替换 + 系统提示词注入

### 第 5 层：基础设施层（Agentic Core）
Dispatch（工具分发）· Messages（消息构建）· Usage（Token追踪）· StreamBus（流式事件）· Context（统一上下文）
Trace（追踪）· Config（配置）· Registry（工具注册表）
核心设计：纯函数 + 数据类 + 可观测性

### 第 6 层：服务层
LLM · RAG · Memory · Search · Session · Embedding · Parsing · Notebook · Sandbox · MCP · Path · Config · Prompt
核心设计：每个服务独立封装，通过依赖注入/工厂模式获取实例

### 第 7 层：学习层
Grading（评分）· Mastery（掌握度）· Scheduler（调度）· Diagnostic（诊断）· Review（复习）
核心设计：掌握度路径（7阶段）+ 错误分类（4种）+ 间隔重复算法

### 第 8 层：工具层
Builtin（内置）· Question（题目）· Vision（视觉）· WebSearch（搜索）· Exec（代码执行）
Paper（论文）· ImageGen（图片生成）· VideoGen（视频生成）· Cron（定时）· Subagent（子代理）
核心设计：工具注册表 + 条件挂载 + 参数增强 + JSON Schema 生成

## 2. 第 1 层：Web 前端层

前端负责用户交互，是用户看到和操作的界面。它通过 HTTP 请求和 SSE（Server-Sent Events）流与后端通信。

### 主要页面

| 页面 | 功能 | 关键交互 |
|------|------|----------|
| Chat | 聊天对话界面 | 发送消息、上传附件、选择知识库、切换能力 |
| Book | 互动教材阅读器 | 翻页、做测验、查看进度、概念图谱 |
| Co-Writer | 协作写作 | 创建教材、编辑章节、预览、发布 |
| Settings | 设置面板 | 配置模型、管理工具开关、知识库管理 |
| Dashboard | 管理后台 | 用户管理、系统监控、日志查看 |

### 流式响应机制

前端通过 SSE 接收后端的实时事件流。事件类型包括：
- content：AI 的文字输出（逐字流式推送）
- thinking：AI 的思考过程（可选展示）
- progress：进度通知（如正在检索知识库...）
- tool_call：工具调用通知
- sources：引用来源
- error：错误信息

## 3. 第 2 层：API 层（FastAPI）

API 层是前后端之间的桥梁。它接收 HTTP 请求，解析参数，调用 Agent 层，返回结果。

### 主要路由

| 路由 | 路径 | 功能 |
|------|------|------|
| ChatRouter | /api/chat | 聊天对话 |
| KnowledgeRouter | /api/kb | 知识库管理（上传、删除、查询） |
| NotebookRouter | /api/notebook | 笔记本管理 |
| BookRouter | /api/book | 教材管理 |
| SessionRouter | /api/session | 会话管理 |
| AdminRouter | /api/admin | 管理功能 |

### 请求处理流程

用户请求 -> FastAPI 路由 -> 认证中间件 -> 参数解析（Pydantic） -> 构建 UnifiedContext -> 调用 Agent 层 -> 流式返回 SSE -> 记录日志

## 4. 第 3 层：Agent 层

> 源码位置：deeptutor/agents/

Agent 层是 DeepTutor 的大脑，负责决策这一轮对话应该做什么。

### 核心组件

| 组件 | 文件 | 行数 | 职责 |
|------|------|------|------|
| AgenticChatPipeline | agents/chat/agentic_pipeline.py | 1386 | 工具组装、LLM配置、能力编排 |
| AgentLoop | agents/chat/agent_loop.py | 667 | LLM调用循环、工具分发、结束判定 |
test
| ResearchAgent | agents/research/ | - | 深度研究代理 |
| MathAnimator | agents/math_animator/ | - | 数学动画生成 |
| VisualizeAgent | agents/visualize/ | - | 可视化分析 |

### 关键设计：Pipeline + Loop 分工

AgenticChatPipeline（组装工）负责决定用什么工具、用什么模型、提示词怎么写、允许多少轮。
AgentLoop（执行工）负责执行LLM调用、分发工具调用、管理对话轮数、处理ask_user暂停、流式输出内容。
Pipeline在初始化时做完所有决策，然后创建一个AgentLoop去执行。AgentLoop通过回调Pipeline的方法来获取结果。

## 5. 第 4 层：能力层（Capabilities）

> 源码位置：deeptutor/capabilities/

能力层是 DeepTutor 最巧妙的设计之一。它允许在不修改聊天流程的前提下，给 AI 添加新的技能。

### 核心协议：LoopCapability

> 源码：deeptutor/capabilities/protocol.py 第 19-85 行

LoopCapability 协议定义了能力的标准接口：
- name：能力名称
- owned_tools：专属工具列表
- is_active(context)：判断是否在当前轮激活
- system_block(context, language, prompts)：返回系统提示词块
- augment_kwargs(tool_name, kwargs, context)：增强工具参数
- pre_loop_seed(context)：循环前种子文本

### 5 个内置能力

| 能力 | 类 | 类型 | 激活条件 |
|------|-----|------|---------|
| Solve | SolveLoopCapability | 叠加 | 用户选择解题模式 |
| Mastery | MasteryLoopCapability | 叠加 | 用户选择学习模式 |
| Obsidian | ObsidianCapability | 独占 | 绑定 Obsidian 知识库 |
| Subagent | SubagentCapability | 叠加 | 任务需要子代理 |
| ExploreContext | ExploreContextCapability | 叠加 | 有附加源文件 |

### 叠加 vs 独占

叠加能力（Augment）：聊天工具 + 能力专属工具 = 完整工具集
独占能力（Replace）：能力专属工具 = 完整工具集（如 Obsidian 模式下只保留知识库工具）

## 8. 第 7 层：学习层

> 源码位置：deeptutor/learning/

学习层是 DeepTutor 的教学引擎，实现了完整的掌握度追踪和个性化学习路径。

### 核心组件

| 组件 | 功能 |
|------|------|
| Grading | 题目评分，比对答案 |
| Mastery | 掌握度评估（0.0~1.0） |
| Scheduler | 学习调度（间隔重复） |
| Diagnostic | 初始水平诊断 |
| Review | 复习任务管理 |

### 掌握度路径（Mastery Path）7 阶段

diagnostic -> explain -> feynman_check -> practice -> error_diagnosis -> review -> completed

### 错误分类（4 种）

| 错误类型 | 含义 | 应对策略 |
|---------|------|---------|
| structural | 知识结构性缺失 | 回到 explain 阶段重新讲解 |
| deviation | 理解偏差 | 换一种方式解释，用更多例子 |
| application | 应用错误 | 加练同类题目 |
| metacognitive | 元认知（不知道自己不知道） | 费曼检查，让学生自己发现盲区 |

### 架构的数据流总结

DeepTutor 的 8 层架构遵循请求从外到内、数据从内到外的原则：

1. **请求流入**：Web 前端 → API 层 → Agent 层
2. **Agent 编排**：Agent 层 → 基础设施层（框架支撑）→ 服务层（能力调用）
3. **业务处理**：学习层 / 能力层（教学逻辑）
4. **响应流出**：Agent 层 → API 层 → Web 前端

**关键数据流**：
- 用户消息：Web → API → Agent → LLM → Agent → API → Web
- 教材内容：Web → API → 服务层(RAG) → 向量数据库
- 学习数据：Agent → 学习层 → 掌握度记录 → 学习调度器
- 记忆数据：Agent → 服务层(Memory) → 文件系统

### 架构的核心设计原则

1. **关注点分离**：每一层只做自己该做的事，不越界
2. **依赖单向**：上层依赖下层，下层不依赖上层
3. **接口稳定**：层间通过明确的接口通信，不直接访问内部实现
4. **可替换性**：每一层都可以独立替换（如换 LLM Provider、换 RAG Pipeline）
5. **可测试性**：每一层都可以独立测试，不依赖其他层的真实实现

### 架构演进历史

**v1.0（早期）**：
- 简单的请求-响应架构
- 没有 Agent 层，LLM 直接回答
- 没有知识库，只能泛泛而谈

**v2.0（当前）**：
- 引入 Agent 层，支持多轮推理和工具调用
- 引入知识库（RAG），支持基于教材回答
- 引入三级记忆，支持长期个性化
- 引入学习层，支持出题、评分、学习调度

**v3.0（规划中）**：
- 多模态支持（图片、语音、视频）
- 协作学习（多人同时学习）
- 联邦学习（跨学校共享学习模型）
- 自适应考试（根据学生水平动态调整难度）

### 总结

DeepTutor 的 8 层架构是一个经过深思熟虑的设计。它从最开始的简单请求-响应模式，逐步演进到支持 Agent 驱动、知识库检索、三级记忆、学习调度的复杂系统。每一层都有明确的职责，层间通过稳定的接口通信，保证了系统的可维护性和可扩展性。

对于产品经理和运营人员来说，理解这 8 层架构就能理解 DeepTutor 的全貌：它不仅仅是一个 AI 聊天机器人，而是一个完整的、分层的、可扩展的智能教学平台。

对于开发者来说，这 8 层架构提供了一条清晰的代码导航路径：从 Web 层进入，经过 API 和 Agent 层，深入到服务和数据层，理解整个系统的运作方式。

## 10. 层间调用关系

```
Web 前端层
    │  HTTP / SSE
    ▼
API 层（FastAPI）
    │  构建 UnifiedContext
    ▼
Agent 层（AgenticChatPipeline）
    │  组装工具、配置参数
    ├──→ 能力层（Capabilities）：检查激活状态、注入提示词块、增强参数
    ├──→ 基础设施层（Agentic Core）：工具分发、消息构建、用量追踪、流式事件
    ├──→ 服务层（Services）：LLM 调用、RAG 检索、Memory 读写、文档解析
    ├──→ 学习层（Learning）：评分、掌握度评估、学习调度
    └──→ 工具层（Tools）：执行具体工具调用
```

**关键原则**：上层只依赖下层，下层不知道上层。Agent 层知道服务层，但服务层不知道 Agent 层。这保证了每层可以独立演化。

## 11. 数据流转：一次请求的完整路径

```
1. 用户发送消息
   -> Web 前端 -> HTTP POST /api/chat

2. API 层接收请求
   -> ChatRouter -> 解析参数 -> 构建 UnifiedContext

3. Agent 层启动
   -> AgenticChatPipeline.run()
       ├─ _prepare_deferred_tools()    -> 服务层（MCP 管理）
       ├─ _compose_enabled_tools()     -> 工具层（工具注册表）
       ├─ _build_loop_messages()       -> 服务层（提示词管理）
       └─ AgentLoop.run()
           ├─ _call_llm()              -> 服务层（LLM 服务）
           │   └─ StreamBus            -> 基础设施层（流式事件）
           │       └─ SSE               -> API 层 -> 前端
           ├─ _dispatch_tool_calls()   -> 基础设施层（工具分发）
           │   └─ execute_tool()       -> 工具层 / 服务层
           └─ 判断是否继续循环
```

## 2.1 为什么是八层架构？

DeepTutor 的架构设计遵循一个核心原则：**关注点分离（Separation of Concerns）**。

简单来说：每一层只做一件事，且只和相邻的层打交道。这带来三个好处：

1. **可替换**：想换一个 RAG 引擎？只改知识层，其他层不受影响。
2. **可测试**：每一层可以独立测试，不用启动整个系统。
3. **可理解**：新人看代码时，可以一层一层看，不用同时理解所有东西。

> 类比：八层架构就像一栋 8 层的大楼。1 楼是地基（基础设施），8 楼是屋顶（用户界面）。每一层都有自己的职责，快递（数据）只能通过楼梯（接口）在相邻楼层之间传递。
## 12. 设计原则总结

| 原则 | 说明 | 体现 |
|------|------|------|
| 分层解耦 | 每层只依赖下层 | 8 层架构，上层不感知下层实现 |
| 协议优于实现 | 通过 Protocol/接口编程 | LoopCapability、SessionStoreProtocol |
| 纯函数 + 数据类 | 业务逻辑纯函数化 | compose_enabled_tools()、build_completion_kwargs() |
| 可观测性 | 全链路追踪 | Trace、Usage、StreamBus |
| 条件挂载 | 工具按需出现 | AUTO_MOUNTED_TOOLS、ToolMountFlags |
| 能力叠加 | 功能可插拔 | Capability 系统 |
| 安全优先 | 沙箱隔离、权限控制 | Sandbox、UserScope、exec_override |

---

## 13. 总结

DeepTutor 的 8 层架构可以概括为：

1. **前端层**：用户看到和操作的界面
2. **API 层**：前后端桥梁，HTTP 请求入口
3. **Agent 层**：决策大脑，Pipeline 组装 + Loop 执行
4. **能力层**：可插拔的功能扩展
5. **基础设施层**：操作系统级的基础能力
6. **服务层**：独立封装的能力中台
7. **学习层**：教学引擎，掌握度追踪
8. **工具层**：AI 的工具箱，条件挂载

这 8 层通过清晰的接口和单向依赖关系协作，构成了一个模块化、可扩展、可观测的 AI 教学平台。

## 2.3 逐层详解

### 第 1 层：外部依赖层（External Dependencies）

**源码位置**：无（外部服务）

**职责**：提供 DeepTutor 依赖的所有外部能力。

| 依赖类型 | 具体服务 | 用途 |
|:---|:---|:---|
| LLM API | OpenAI / Anthropic / Google / DeepSeek / 阿里 / 本地模型 | 核心推理能力 |
| Embedding API | OpenAI / Gemini / Ollama / 本地 | 文本向量化，驱动 RAG 检索 |
| Search API | DuckDuckGo / SearXNG / Brave / Tavily | 网页搜索 |
| Document Parsers | MinerU / Docling / markitdown / PyMuPDF4LLM | 文档解析为结构化文本 |
| Math Rendering | Manim | 数学动画生成 |

| Database | PocketBase | 可选的外部数据库 |

> 设计意图：这一层是"不可控的"——DeepTutor 无法控制外部服务的可用性和行为。因此所有外部调用都经过适配器（Adapter）封装，以便在服务不可用时优雅降级。

**源码位置**：`deeptutor/core/`、`deeptutor/utils/`

**职责**：提供全系统共享的基础能力。

| 版本信息 | `__version__.py` | 版本号管理 |

> 设计意图：这一层是"不变的"——无论上层如何变化，日志、配置、错误处理这些基础能力保持稳定。新加入的开发者可以先看这一层来理解代码规范。### 第 3 层：数据访问层（Data Access Layer）

```

## 2.4 层间调用关系

### 数据流（用户提问 -> AI 回答）

```
用户输入 (第8层)
    |
    v
API 网关 (第7层)  -- 参数校验、认证
    |
    v
Agent 引擎 (第6层)  -- 组装上下文、调用 LLM
    |
    +---> 能力层 (第5层)  -- 确定能力模式、可用工具
    |         |
    |         +---> 服务层 (第4层)  -- RAG检索、记忆读取、技能加载
    |                   |
    |                   +---> 数据访问层 (第3层)  -- 读写文件/数据库
    |                   +---> 外部依赖层 (第1层)  -- LLM API、Search API
    |
    +---> LLM 返回响应 (可能是工具调用)
    |         |
    |         +---> 是工具调用? -> 执行工具 (回到服务层)
    |         +---> 否? -> 流式输出
    |
    v
API 网关 (第7层)  -- WebSocket/SSE 推送
    |
    v
用户看到回答 (第8层)
```

### 关键设计原则

**1. 单向依赖**：上层依赖下层，下层不依赖上层。第 8 层可以调用第 7 层，但第 7 层不能调用第 8 层。

**2. 接口隔离**：层与层之间通过明确的接口通信。比如 Agent 引擎层通过 `tool.call()` 调用工具，不关心工具内部如何实现。

**3. 适配器模式**：所有外部依赖（LLM、搜索、文档解析等）都通过适配器封装。切换供应商只需换一个适配器。

**4. 配置驱动**：几乎所有行为都由配置文件控制，而不是硬编码。新增一个模型提供商只需要在 `model_catalog.json` 中添加配置。

## 2.5 架构的"为什么"

### 为什么选择 Python + FastAPI？

- Python 是 AI 生态的第一语言，所有 LLM SDK 都有 Python 版本
- FastAPI 原生支持异步和 WebSocket，适合流式输出场景
- Pydantic 提供类型安全的数据验证，减少运行时错误

### 为什么选择 Next.js 而非纯 React？

- App Router 提供文件系统路由，新人容易理解项目结构
- SSR 能力让首屏加载更快
- API Routes 可以充当 BFF（Backend for Frontend），减少前端对后端的直接依赖

### 为什么 Agent Loop 是"思考-工具-观察"循环？

- 这是 OpenAI/Anthropic 等主流 LLM 的原生工具调用模式
- 循环是确定的——不会无限循环（有最大轮次限制）
- 工具调用结果直接注入上下文，Agent 可以基于最新信息继续推理

### 为什么 Memory 是三层而非向量数据库？

- **可审计**：Markdown 文件人类可读，LLM 也可以直接读取
- **可编辑**：用户可以直接修改或删除任何记忆
- **可追溯**：每条 L3 综合都引用 L2 摘要，L2 摘要都引用 L1 轨迹
- **无黑盒**：不需要"信任"一个向量数据库的内部状态---
